## Real incidents, verified facts, and claims in the post to handle with care

### Verified facts (checked in the post AND in a source that was actually opened for this brief)

- **Dual writes** (opened `https://www.confluent.io/blog/using-logs-to-build-a-solid-data-infrastructure-or-why-dual-writes-are-a-bad-idea/`): two clients setting `X = A` and `X = B` can reach the database in one order and the search index in the opposite order; both succeed, the stores stay inconsistent until someone overwrites `X` again, and no error is raised. The partial-failure example is an inbox insert followed by an unread-counter increment where the process dies in between. Morling (`https://www.morling.dev/blog/revisiting-the-outbox-pattern/`, opened): never write to a database and a broker without global transactional guarantees; the outbox table only receives inserts; `pg_logical_emit_message()` writes messages to the WAL without any table growth. Morling's wording is "data contract" and "exposes a service's internal data model", not "public API" (see loose claims).
- **Shopify** (opened `https://shopify.engineering/capturing-every-change-shopify-sharded-monolith`): Longboat queries read-only replicas of the sharded core monolith (`100+` MySQL shards), per table, no joins, "as often as once an hour" so data is at least an hour old; it misses hard deletes, changes that do not move `updated_at` (large migrations, coding errors), intermediate states of rows updated several times between runs, and a sales snapshot at `2:15` joined with a products snapshot at `2:30` raises the freshness-timestamp question. Fix: one Debezium connector per shard (about `150` connectors across `12` Kubernetes pods), events go to shard-level topics, a custom Kafka Streams app writes one compacted topic per table; "the p99 latency is less than 10 seconds" from MySQL insert to Kafka.
- **Kafka log facts** (opened `https://kafka.apache.org/41/design/design/`): a record with a key and a `null` payload is a tombstone; tombstones are themselves removed after a period, and a consumer lagging more than `delete.retention.ms` (default `24 hours`) can miss delete markers; the design page has a "Share groups" section (consistent with the post's KIP-932 mention, which was not opened separately).
