<En>

A trading screen I worked on had a classic problem. The orders table showed only the first few hundred rows, because two layers each had a hard cap. Worse, every order event made each open browser tab re-read the **entire** order book from the upstream system that owns the orders. More traders, more tabs, more events: the read load on that upstream system grew with all three.

The fix was not a bigger cap. It was to stop treating the upstream system as the place to read from, and to build our own view of the book from the events we were already receiving.

<Figure src={azureEventSourcing} alt="Event sourcing architecture showing events flowing through a queue to event handlers that populate a dedicated read-only store" caption="Instead of querying the upstream command system on every tab refresh, event handlers project the event stream into a dedicated read-only store tailored for the UI." sourceTitle="Microsoft Learn — Event Sourcing Pattern" sourceUrl="https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing" />

This post walks through the four decisions that made that work. The stack was a Python service, a Go backend-for-frontend (BFF) and a React UI, with PostgreSQL and Kafka in between, but the ideas carry over to any stack.

<Concepts>

- **Order book**: here, the table of every order placed today and where each one stands (working, filled, cancelled).
- **Upstream system**: the system that owns the orders and is the source of truth. Other services ask it, or listen to it, to learn about orders.
- **Hard cap**: a fixed maximum, here on how many rows a layer returns. Anything past it is silently cut off.
- **Event sourcing**: treating every change as an event ("order accepted", "order filled") and building the current state by applying those events in order. Like a bank balance worked out from the list of transactions.
- **Read-only store (projection)**: a copy of the data shaped for one screen, kept up to date by applying events. The UI reads from it instead of asking the upstream system each time.
- **BFF (backend-for-frontend)**: a small server built for one UI. It gathers and shapes data so the browser gets exactly what it shows.

</Concepts>

- **Order book (sổ lệnh)**: ở bài này là bảng chứa mọi lệnh đặt trong ngày và tình trạng hiện tại của từng lệnh (đang chờ, đã khớp, đã hủy).

- **Event sourcing**: coi mỗi thay đổi là một sự kiện ("lệnh được nhận", "lệnh đã khớp") và dựng trạng thái hiện tại bằng cách áp lần lượt các sự kiện đó. Giống số dư tài khoản được tính ra từ danh sách giao dịch.
- **Read-only store (kho chỉ đọc, hay projection)**: một bản sao dữ liệu sắp xếp sẵn cho một màn hình, được cập nhật bằng cách áp sự kiện. Giao diện đọc từ đây thay vì lần nào cũng hỏi hệ thống lõi.
- **BFF (backend-for-frontend)**: một server nhỏ làm riêng cho một giao diện. Nó gom và nắn dữ liệu để trình duyệt nhận đúng thứ cần hiển thị.

## 1. Store live state, and never let a late event move a row backwards

The service that sends orders also receives every execution report for them: accepted, partially filled, filled, cancelled. Instead of only logging those reports, it now writes each order's **current** state into PostgreSQL.

Events can arrive out of order. A "filled" report can be followed by a delayed "accepted" for the same order. If the write simply overwrites, the row goes back in time. So every row stores the event time it was built from, and an update only applies when the incoming event is newer:

```sql
INSERT INTO orders (order_id, status, filled_qty, avg_price, event_ns)
VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (order_id) DO UPDATE
SET status     = EXCLUDED.status,
    filled_qty = EXCLUDED.filled_qty,
    avg_price  = EXCLUDED.avg_price,
    event_ns   = EXCLUDED.event_ns
WHERE orders.event_ns < EXCLUDED.event_ns;   -- older events are ignored
```

One more rule sits on top: **a finished order never reopens.** Once a row is filled, cancelled or rejected, later events can add detail but cannot set it back to a working status.

<Callout type="tip" title="If the migration hasn't run yet">
New code often ships before its database migration. If the new columns are missing, the writer logs one warning and skips the live-state write, instead of failing the whole order path.
</Callout>

<Concepts>

- **Execution report**: a message saying what happened to an order: accepted, partially filled, filled, cancelled.
- **Out of order**: events arriving in a different order than they happened, for example when one message is delayed on the way.
- **Upsert (`ON CONFLICT ... DO UPDATE`)**: insert the row, or update it if a row with that key already exists, in one statement. The `WHERE` at the end lets the update happen only when the incoming event is newer.
- **Event time (`event_ns`)**: when the event happened at the source, not when we received it. Comparing it tells us which of two events is newer.
- **Monotonic write**: a write that can only move a row forward in time, never back to an older state.
- **Final status**: filled, cancelled or rejected. The order is done and must not go back to a working status.
- **Database migration**: a script that changes the database structure, such as adding columns. Code is often deployed before the migration has run.

</Concepts>

## 2. Merge two sources with explicit rules

The BFF builds the book from two sources:

- **PostgreSQL**, which holds every order's last stored state, and
- **an order-event stream from Kafka**, which carries the newest changes, sometimes before they reach the database.

Merging two sources is where bugs hide, so the rules are written down and tested one by one:

1. **The newer event time wins.** Same rule as the write path, so the two never disagree.
2. **A finished order stays finished**, whichever source reports it first.
3. **Match rows that do not have an upstream ID yet.** An order sent a moment ago may have only our own ID; it must not appear twice when the upstream ID arrives.

```go
func merge(stored, live Order) Order {
	if isFinal(stored.Status) && !isFinal(live.Status) {
		return stored // never reopen a finished order
	}
	if live.EventNs > stored.EventNs {
		return live
	}
	return stored
}
```

<YouTube id="lg6aF5PP4Tc" title="Event Sourcing 101: Command Query Responsibility Segregation (CQRS)" start={176} end={252} caption="Between 2:56 and 4:12, Confluent explains why CQRS read views lag slightly behind the Kafka log (eventual consistency) and how retaining the full topic lets a service rebuild its read view from scratch after a restart." sourceTitle="Confluent — Event Sourcing 101 (CQRS)" />

<Concepts>

- **Kafka**: a service that keeps events in an append-only log. Producers write events to it; readers go through them in order and can start again from an earlier point.
- **Event stream**: the ordered sequence of events, here every change to every order.
- **Merge**: combining two sources into one list with fixed rules for which value wins when they disagree.
- **Upstream ID**: the order number assigned by the upstream system. It arrives a moment after the order is sent; until then we only have our own ID.
- **CQRS (Command Query Responsibility Segregation)**: keeping the side that changes data (commands) apart from the side that reads it (queries), so reads can use their own view.
- **Eventual consistency**: the read view may be a little behind the log, but it catches up once it has processed the newest events.

</Concepts>

## 3. Say "incomplete" instead of returning a short list

After a restart, the BFF has to read the event stream from the start of the day before its view is whole. During those seconds it could return a short list and look fine, which is exactly the kind of quiet wrong answer that erodes trust in a trading screen.

Instead, every response carries a `complete` flag. While the stream is still catching up, the UI shows that the book is loading rather than presenting a partial book as the full one.

```json
{ "orders": [ ... ], "complete": false, "next_cursor": "..." }
```

In a Go BFF using `kafka-go`, tracking whether the partition reader has caught up to the high-watermark directly determines when `complete` flips to `true`:

<GitHubCode repo="segmentio/kafka-go" path="reader.go" lines="L1004-L1015" url="https://github.com/segmentio/kafka-go/blob/2e0b3968aa51b16beb4e221876499a6ff816cd91/reader.go#L1004-L1015" caption="Note that kafka-go exposes Lag() only for explicit partition readers; consumer-group readers return -1, so replay health needs explicit partition tracking.">
```go
// Lag returns the lag of the last message returned by ReadMessage, or -1
// if r is backed by a consumer group.
func (r *Reader) Lag() int64 {
	if r.useConsumerGroup() {
		return -1
	}

	r.mutex.Lock()
	lag := r.lag
	r.mutex.Unlock()
	return lag
}
```
</GitHubCode>

<Concepts>

- **Replay**: reading the event stream again from a starting point, here the start of the day, to rebuild the view.
- **Partition**: Kafka splits a topic into partitions. Each one is its own ordered log that a reader goes through independently.
- **High-watermark**: the position just past the newest message readers can see in a partition. A reader that reaches it has caught up.
- **Lag**: how many messages a reader is still behind the high-watermark. Zero lag on every partition means the replay is done.
- **Consumer group**: a set of readers that split a topic's partitions between them automatically. In `kafka-go`, `Lag()` returns -1 for this kind of reader.

</Concepts>

## 4. Page with a cursor, not an offset

With thousands of rows and new ones arriving all the time, `LIMIT/OFFSET` breaks down: a row inserted at the top shifts every page, so users see duplicates or miss rows. A cursor on a stable, unique sort key does not have that problem.

<Figure src={offsetDrift} alt="Three-step diagram showing how inserting a new row at the top causes OFFSET 10 to return row 10 a second time on page 2" caption="When a new order arrives at the top of the book between page loads, OFFSET 10 shifts the window down by one and returns row 10 a second time." sourceTitle="Use The Index, Luke — No Offset!" sourceUrl="https://use-the-index-luke.com/no-offset" />

```sql
SELECT *
FROM fills
WHERE (ts, id) < ($1, $2)          -- the cursor: last row of the previous page
ORDER BY ts DESC, id DESC
LIMIT 200;
```

The `id` breaks ties between rows with the same timestamp, so no row is ever skipped or shown twice. Filtering moved into SQL too, instead of loading everything and filtering in memory.

<EventSourcedOffsetVsCursor />

Even in a local SQLite table with 100,000 rows indexed on `(ts DESC, id DESC)`, querying page 401 (`OFFSET 80000`) forces a full index scan of 80,000 rows, while a keyset cursor seeks directly into the B-tree:

Keyset cursors also avoid holding open server-side database portals—a trap engineers frequently hit when running behind transaction-level connection poolers like PgBouncer:

<QuoteCard author="mmakeev" sourceTitle="Hacker News — Why we built yet another Postgres connection pooler" sourceUrl="https://news.ycombinator.com/item?id=48827997">
The honest knock on the streaming kind isn't "bad design", it's that it holds a portal open server-side, which is why it can't survive transaction pooling. So the pooler-friendly fix isn't one giant fetch, it's keyset pagination (`where id > last limit n`), stateless and constant memory, which is what we moved those paths to.
</QuoteCard>

On the React side the table is **virtualized** (only visible rows are in the DOM) and **scroll-anchored**, so loading the next page or inserting a new row does not make the list jump under the reader's eyes. The UI reloads after a quiet period, on reconnect, or when the user asks, instead of on every single event.

<Concepts>

- **Offset pagination (`LIMIT/OFFSET`)**: "skip N rows, give me the next M". Simple, but the database still walks the skipped rows, and one new row at the top shifts every page.
- **Cursor (keyset) pagination**: remember the sort key of the last row you showed and ask for the rows after it. The page always starts in the same place.
- **Tie-breaker**: a second sort column (`id`) that decides the order when the first one (`ts`) is equal, so every row has exactly one position.
- **Index and B-tree**: an index is a sorted copy of some columns that the database keeps next to the table. A B-tree is the usual shape for it: a few levels of nodes, so the database can find a key in a few hops (an index seek) instead of reading entries one by one (a scan).
- **Connection pooler (PgBouncer) and portal**: a pooler shares a few database connections among many clients. A portal is a query result the server keeps open on one connection, which transaction-level pooling cannot promise to keep.
- **Virtualized, scroll-anchored table**: only the rows on screen exist in the page, and the row you are looking at stays put when rows are added above it.

</Concepts>

## What changed

In local testing, repeated loads of the book made **zero** reads to the upstream system, a fill showed up immediately on its stored order, and after a BFF restart the book reported itself incomplete and then completed within seconds.

Code review was worth it here. It caught four real problems before release: duplicate rows before an order was acknowledged, a final state being overwritten, a crash when the migration was missing, and a stream reader that could be lost on restart.

## Takeaways

- **Make ordering explicit.** Store event time and only write forward. Do not rely on arrival order.
- **Write merge rules down and test each one.** "Newer wins" and "finished stays finished" are simple to state and easy to break.
- **Be honest about incomplete data.** A `complete: false` flag is better than a confident, short answer.
- **Use cursors for live lists.** Offsets and inserts do not mix.

## 1. Lưu trạng thái trực tiếp và không bao giờ để sự kiện đến trễ kéo lùi trạng thái (monotonic writes)

Service gửi lệnh cũng là nơi nhận toàn bộ báo cáo thực thi (execution reports): đã tiếp nhận (accepted), khớp một phần (partially filled), khớp hết (filled), hay đã hủy (cancelled). Thay vì chỉ ghi log những báo cáo đó, giờ nó ghi **trạng thái hiện tại** của từng lệnh vào PostgreSQL.

Các sự kiện có thể đến sai thứ tự (out of order). Một báo cáo "đã khớp hết" (filled) có thể bị theo sau bởi một báo cáo "đã tiếp nhận" (accepted) đến muộn của chính lệnh đó. Nếu lệnh ghi chỉ ghi đè mù quáng, dòng dữ liệu sẽ bị quay ngược thời gian. Vì vậy mỗi dòng đều lưu lại dấu thời gian sự kiện (event time) tạo ra nó, và chỉ cho phép cập nhật khi sự kiện mới đến có thời gian lớn hơn (ghi đơn điệu — monotonic write):

```sql
INSERT INTO orders (order_id, status, filled_qty, avg_price, event_ns)
VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (order_id) DO UPDATE
SET status     = EXCLUDED.status,
    filled_qty = EXCLUDED.filled_qty,
    avg_price  = EXCLUDED.avg_price,
    event_ns   = EXCLUDED.event_ns
WHERE orders.event_ns < EXCLUDED.event_ns;   -- bỏ qua các sự kiện cũ hơn
```

Thêm một quy tắc nữa nằm ở tầng trên: **một lệnh đã kết thúc sẽ không bao giờ mở lại (final order never reopens).** Khi một dòng đã ở trạng thái khớp hết, đã hủy hoặc bị từ chối, các sự kiện đến sau có thể bổ sung thông tin chi tiết nhưng không bao giờ được phép đưa nó quay về trạng thái đang chờ xử lý.

<Callout type="tip" title="Nếu migration chưa kịp chạy">
Code mới thường được triển khai trước khi chạy di trú cơ sở dữ liệu (database migration). Nếu thiếu các cột mới, trình ghi chỉ ghi một dòng cảnh báo và bỏ qua bước lưu trạng thái trực tiếp, thay vì làm lỗi cả luồng đặt lệnh.
</Callout>

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Execution report (báo cáo thực thi)**: tin nhắn cho biết chuyện gì đã xảy ra với một lệnh: đã nhận, khớp một phần, khớp hết, đã hủy.
- **Out of order (sai thứ tự)**: sự kiện đến không theo đúng thứ tự xảy ra, ví dụ khi một tin nhắn bị chậm trên đường đi.
- **Upsert (`ON CONFLICT ... DO UPDATE`)**: thêm dòng mới, hoặc cập nhật nếu đã có dòng cùng khóa, trong cùng một câu lệnh. Mệnh đề `WHERE` ở cuối chỉ cho cập nhật khi sự kiện mới đến thật sự mới hơn.
- **Event time (`event_ns`, thời điểm sự kiện)**: lúc sự kiện xảy ra ở nguồn, không phải lúc mình nhận được. So hai giá trị này là biết sự kiện nào mới hơn.
- **Monotonic write (ghi đơn điệu)**: kiểu ghi chỉ cho một dòng tiến về phía trước theo thời gian, không bao giờ lùi về trạng thái cũ.
- **Final status (trạng thái kết thúc)**: đã khớp hết, đã hủy hoặc bị từ chối. Lệnh đã xong và không được quay về trạng thái đang chờ.
- **Database migration (di trú cơ sở dữ liệu)**: script đổi cấu trúc database, như thêm cột. Code mới hay được deploy trước khi migration kịp chạy.

</Concepts>

## 2. Hợp nhất hai nguồn dữ liệu bằng các quy tắc tường minh

Lớp BFF dựng sổ lệnh từ hai nguồn:

- **PostgreSQL**, lưu trạng thái ghi nhận gần nhất của mọi lệnh, và
- **luồng sự kiện lệnh từ Kafka**, mang những thay đổi mới nhất — đôi khi đi trước cả khi dữ liệu kịp ghi xuống database.

Hợp nhất (merge) hai nguồn là nơi lỗi rất dễ ẩn mình, nên các quy tắc cần được viết rõ ràng và viết unit test kiểm chứng từng quy tắc một:

1. **Thời gian sự kiện mới hơn thắng.** Giống hệt quy tắc trên đường ghi (write path), để hai phía không bao giờ mâu thuẫn nhau.
2. **Lệnh đã kết thúc phải giữ nguyên trạng thái kết thúc**, bất kể nguồn nào báo cáo điều đó trước.
3. **Khớp các dòng chưa có mã định danh từ hệ thống lõi (upstream ID).** Một lệnh vừa gửi cách đây vài tích tắc có thể mới chỉ có mã nội bộ của ta; nó tuyệt đối không được xuất hiện thành hai dòng khi mã từ hệ thống lõi trả về.

```go
func merge(stored, live Order) Order {
	if isFinal(stored.Status) && !isFinal(live.Status) {
		return stored // không bao giờ mở lại một lệnh đã kết thúc
	}
	if live.EventNs > stored.EventNs {
		return live
	}
	return stored
}
```

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Kafka**: một service lưu sự kiện vào một log chỉ ghi nối thêm. Bên gửi ghi sự kiện vào; bên đọc đi qua lần lượt và có thể đọc lại từ một điểm trước đó.
- **Event stream (luồng sự kiện)**: chuỗi sự kiện có thứ tự, ở đây là mọi thay đổi của mọi lệnh.
- **Merge (hợp nhất)**: gộp hai nguồn thành một danh sách, với quy tắc cố định để quyết định giá trị nào thắng khi hai bên lệch nhau.
- **Upstream ID (mã từ hệ thống lõi)**: số hiệu lệnh do hệ thống lõi cấp. Nó về chậm hơn lúc gửi lệnh một chút; trước đó mình chỉ có mã nội bộ của mình.
- **CQRS (Command Query Responsibility Segregation)**: tách phần thay đổi dữ liệu (command) khỏi phần đọc dữ liệu (query), để phía đọc dùng khung nhìn riêng của nó.
- **Eventual consistency (nhất quán cuối cùng)**: khung nhìn đọc có thể chậm hơn log một chút, nhưng sẽ bắt kịp khi xử lý xong các sự kiện mới nhất.

</Concepts>

## 3. Báo rõ "chưa đầy đủ" (`incomplete`) thay vì trả về một danh sách thiếu

Sau khi khởi động lại (restart), lớp BFF phải đọc lại luồng sự kiện từ đầu ngày trước khi có được bức tranh toàn vẹn. Trong vài giây ngắn ngủi đó, nếu nó cứ im lặng trả về một danh sách ngắn trông có vẻ bình thường thì chính những câu trả lời "sai một cách âm thầm" như vậy sẽ làm mất niềm tin trên màn hình giao dịch.

Thay vào đó, mọi phản hồi (response) đều mang theo cờ `complete`. Trong lúc luồng sự kiện vẫn đang bắt kịp (catching up), giao diện hiển thị trạng thái đang tải sổ lệnh thay vì giả vờ một danh sách thiếu là toàn bộ sổ lệnh.

```json
{ "orders": [ ... ], "complete": false, "next_cursor": "..." }
```

Trong Go BFF sử dụng `kafka-go`, việc theo dõi xem trình đọc phân vùng (partition reader) đã đuổi kịp mốc cao nhất (high-watermark) hay chưa quyết định trực tiếp thời điểm `complete` chuyển sang `true`:

<GitHubCode repo="segmentio/kafka-go" path="reader.go" lines="L1004-L1015" url="https://github.com/segmentio/kafka-go/blob/2e0b3968aa51b16beb4e221876499a6ff816cd91/reader.go#L1004-L1015" caption="Lưu ý rằng kafka-go chỉ trả về Lag() cho partition reader chỉ định trực tiếp; consumer-group reader trả về -1, nên việc theo dõi trạng thái replay cần quản lý rõ theo từng phân vùng (partition).">
```go
// Lag returns the lag of the last message returned by ReadMessage, or -1
// if r is backed by a consumer group.
func (r *Reader) Lag() int64 {
	if r.useConsumerGroup() {
		return -1
	}

	r.mutex.Lock()
	lag := r.lag
	r.mutex.Unlock()
	return lag
}
```
</GitHubCode>

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Replay (đọc lại)**: đọc lại luồng sự kiện từ một điểm xuất phát, ở đây là đầu ngày, để dựng lại khung nhìn.
- **Partition (phân vùng)**: Kafka chia một topic thành nhiều partition. Mỗi partition là một log có thứ tự riêng, được đọc độc lập.
- **High-watermark (mốc cao nhất)**: vị trí ngay sau tin nhắn mới nhất mà bên đọc thấy được trong một partition. Đọc tới đó là đã bắt kịp.
- **Lag (độ trễ)**: bên đọc còn cách high-watermark bao nhiêu tin nhắn. Lag bằng 0 trên mọi partition nghĩa là replay đã xong.
- **Consumer group (nhóm consumer)**: một nhóm bên đọc tự chia nhau các partition của một topic. Trong `kafka-go`, `Lag()` trả về -1 với kiểu reader này.

</Concepts>

## 4. Phân trang bằng con trỏ (cursor), không dùng độ lệch (offset)

Với hàng nghìn dòng dữ liệu và các dòng mới đổ về liên tục, `LIMIT/OFFSET` sẽ gãy ngay: chỉ cần một dòng mới chèn vào đầu bảng là toàn bộ các trang sau bị xê dịch (shift), khiến người dùng thấy trùng dòng hoặc sót dòng. Phân trang bằng con trỏ (cursor / keyset pagination) dựa trên một khóa sắp xếp ổn định và duy nhất (unique sort key) không gặp vấn đề này.

<Figure src={offsetDrift} alt="Sơ đồ ba bước cho thấy khi chèn thêm một dòng mới ở đầu bảng, lệnh OFFSET 10 sẽ trả lại dòng 10 thêm một lần nữa ở trang 2" caption="Khi có một lệnh mới chèn vào đầu sổ lệnh giữa hai lần tải trang, OFFSET 10 đẩy cửa sổ lấy dữ liệu xuống một dòng và trả lại dòng 10 lần thứ hai." sourceTitle="Use The Index, Luke — No Offset!" sourceUrl="https://use-the-index-luke.com/no-offset" />

```sql
SELECT *
FROM fills
WHERE (ts, id) < ($1, $2)          -- con trỏ (cursor): dòng cuối cùng của trang trước
ORDER BY ts DESC, id DESC
LIMIT 200;
```

Trường `id` đóng vai trò phân định khi hai dòng có cùng dấu thời gian `ts` (tie-breaker), nhờ vậy không dòng nào bị bỏ sót hay hiển thị hai lần. Việc lọc dữ liệu (filtering) cũng được đưa thẳng vào SQL thay vì tải hết lên RAM rồi mới lọc.

Keyset cursor cũng tránh được lỗi giữ kết nối mở ở phía server (server-side database portals) — một cái bẫy kỹ sư thường vấp phải khi chạy sau các bộ gom kết nối theo giao dịch (transaction-level connection poolers) như PgBouncer:

Điểm yếu thật sự của kiểu streaming cursor không phải do "thiết kế tệ", mà là nó giữ một portal mở trên server, khiến nó không thể sống sót qua transaction pooling. Vì vậy cách sửa thân thiện với pooler không phải là tải một cục khổng lồ, mà là dùng keyset pagination (`where id > last limit n`), không trạng thái (stateless) và tốn bộ nhớ hằng số — đó là hướng chúng tôi đã chuyển toàn bộ các luồng đó sang.

Ở phía React, bảng dữ liệu được **ảo hóa (virtualized)** — chỉ đưa các dòng đang nằm trong khung nhìn vào DOM — và **neo vị trí cuộn (scroll-anchored)**, nên việc tải trang tiếp theo hay chèn thêm dòng mới không làm danh sách nhảy giật dưới mắt người đọc. Giao diện chỉ tải lại sau một khoảng lặng (quiet period), khi kết nối lại, hoặc khi người dùng chủ động bấm làm mới, thay vì tải lại theo từng sự kiện đơn lẻ.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Offset pagination (`LIMIT/OFFSET`, phân trang bằng độ lệch)**: "bỏ qua N dòng, đưa tôi M dòng tiếp theo". Đơn giản, nhưng database vẫn phải đi qua những dòng bị bỏ, và chỉ một dòng mới chèn lên đầu là mọi trang bị xô lệch.
- **Cursor / keyset pagination (phân trang bằng con trỏ)**: nhớ khóa sắp xếp của dòng cuối đã hiển thị rồi xin các dòng đứng sau nó. Trang luôn bắt đầu đúng chỗ.
- **Tie-breaker (cột phân xử)**: cột sắp xếp thứ hai (`id`) quyết định thứ tự khi cột đầu (`ts`) bằng nhau, nhờ vậy mỗi dòng có đúng một vị trí.
- **Index và B-tree (chỉ mục và cây B)**: index là bản sao đã sắp xếp của vài cột, database giữ bên cạnh bảng. B-tree là dạng phổ biến của nó: vài tầng nút, nên database tìm một khóa chỉ trong vài bước (index seek) thay vì đọc từng mục một (scan).
- **Connection pooler (PgBouncer) và portal**: pooler cho nhiều client dùng chung vài kết nối database. Portal là một kết quả truy vấn server giữ mở trên một kết nối, điều mà pooling theo giao dịch không hứa giữ được.
- **Bảng virtualized, scroll-anchored (ảo hóa, neo vị trí cuộn)**: chỉ những dòng đang thấy trên màn hình mới có trong trang, và dòng bạn đang nhìn đứng yên khi có dòng mới chèn phía trên.

</Concepts>

## Kết quả thay đổi

Trong quá trình kiểm thử cục bộ, các lần tải lại sổ lệnh tạo ra **bằng không** lượt đọc lên hệ thống lõi phía trên, một lệnh khớp mới hiển thị ngay lập tức lên dòng lệnh đã lưu, và sau khi khởi động lại BFF, sổ lệnh tự báo chưa đầy đủ (`complete: false`) rồi hoàn tất chỉ trong vài giây.

Khâu đánh giá mã nguồn (code review) đã phát huy giá trị rất rõ ở đây: nó bắt được bốn lỗi thực tế trước khi phát hành — trùng dòng khi lệnh chưa được hệ thống lõi xác nhận, trạng thái kết thúc bị ghi đè, lỗi sập khi chưa chạy migration, và trình đọc luồng sự kiện có nguy cơ bị mất vị trí khi khởi động lại.

## Điểm rút ra (Takeaways)

- **Biến thứ tự thời gian thành tường minh.** Lưu dấu thời gian sự kiện và chỉ ghi tiến tới, đừng tin vào thứ tự gói tin đến mạng.
- **Viết rõ quy tắc hợp nhất và test từng quy tắc một.** "Sự kiện mới hơn thắng" và "đã kết thúc thì giữ nguyên kết thúc" nghe đơn giản nhưng rất dễ gãy nếu không khóa bằng test.
- **Trung thực khi dữ liệu chưa đầy đủ.** Một cờ `complete: false` tốt hơn nhiều so với một câu trả lời thiếu nhưng tự tin.
- **Dùng con trỏ (cursor) cho danh sách biến động liên tục.** `OFFSET` và thao tác chèn dòng mới không đi cùng nhau được.
