<En>

Price boards, order books, monitoring dashboards: they all show a table whose cells change many times per second. Libraries like AG Grid already virtualize rows, so a table with 10,000 rows only keeps a handful of them in the DOM. That head start is easy to waste. How you *feed* the grid usually matters more than the grid's own settings.

This post walks through four changes that keep a streaming table smooth, and gives you a live demo to feel the difference yourself.

## Try it first

The demo below simulates a market-data feed. Both modes receive exactly the same stream of updates; only the way they hand it to the grid differs.

Watch the last stat card, **rows pushed to grid per second**. That number is the story: the naive mode hands the grid every row on every message, while the optimized mode sends only the rows that actually changed, a few times per second.

## 1. Give every row a stable ID and send deltas

The most common mistake is replacing the whole dataset whenever a message arrives:

```ts
// Anti-pattern: the grid has to diff (or rebuild) every row on every tick
socket.onmessage = () => {
  api.setGridOption('rowData', rows.map((r) => ({ ...r })));
};
```

Without a way to identify rows, the grid treats each new array as brand-new data and rebuilds its row nodes. Tell it how to identify a row, then send only what changed:

```ts
<AgGridReact
  getRowId={(p) => p.data.id}   // stable, unique key per row
  rowData={initialRows}
/>

// later, for each batch of changes:
api.applyTransaction({ update: changedRows });
```

`getRowId` matters twice. It lets the grid find the existing row for an update, and it keeps row identity stable so the DOM for unchanged rows is left alone. Without it, update transactions match rows by object reference, and the fresh objects coming off the wire would never match.

## 2. Coalesce updates, then flush in batches

Real feeds are bursty and often update the same instrument many times within a few milliseconds. Painting every intermediate value is wasted work: the human eye cannot see them, and the browser can only paint once per frame anyway.

Keep a map of the **latest** value per row ID and flush it on a timer:

```ts
const pending = new Map<string, Row>();

socket.onmessage = (msg) => {
  const row = parse(msg);
  pending.set(row.id, row); // latest wins
};

setInterval(() => {
  if (pending.size === 0) return;
  const batch = Array.from(pending.values());
  pending.clear();
  api.applyTransaction({ update: batch });
}, 100);
```

A 100 ms flush interval means at most 10 grid updates per second, however fast the feed runs, and each update contains each changed row only once. That is how the demo turns thousands of incoming updates per second into a few thousand rows pushed, instead of tens or hundreds of thousands.

<Callout type="note" title="Built-in alternative">
AG Grid also offers `api.applyTransactionAsync()`, which queues transactions and applies them together after `asyncTransactionWaitMillis` (50 ms by default). It batches for you, but it does not coalesce multiple updates to the same row. Writing the small `Map` above gives you that, plus full control over the flush rate.
</Callout>

## 3. Keep cells cheap

At thousands of updates per second, per-cell cost dominates. Two habits help:

- **Prefer `valueFormatter` and `cellClassRules` over custom cell renderers.** A framework component per cell has a real mount and update cost. Formatting a number and toggling a CSS class does not.
- **Be selective with `enableCellChangeFlash`.** The flash effect is lovely on a price column and distracting (and not free) on all six columns.

```ts
const columnDefs = [
  { field: 'last', valueFormatter: fmtPrice, enableCellChangeFlash: true },
  {
    field: 'changePct',
    valueFormatter: fmtChange,
    // colour via a class instead of rendering a <span> in a component
    cellClassRules: {
      'up': (p) => p.value >= 0,
      'down': (p) => p.value < 0,
    },
  },
];
```

The naive mode in the demo uses a React cell renderer for the change column; the optimized mode uses the code above.

## 4. Turn off what you are not using

Some defaults are tuned for friendly, low-frequency data:

- **`animateRows={false}`** for fast streams. Animating rows that move or update at high frequency only adds work.
- **`deltaSort`** if the grid is sorted on a column that changes. With it enabled, the grid re-sorts only the changed rows instead of the entire dataset on every transaction.
- **Leave `rowBuffer` alone** unless you have measured a reason. A larger buffer renders more rows outside the viewport, which is the opposite of what you want while streaming.

## How to measure, not guess

The stat cards in the demo are deliberately simple, and you can reproduce them in any app:

1. **Frames per second:** count `requestAnimationFrame` callbacks per second. Below roughly 30, the UI feels laggy.
2. **Longest frame:** track the largest gap between frames. A single 150 ms frame is a visible stutter even when the average looks healthy.
3. **Chrome DevTools → Performance:** record a few seconds of streaming with CPU throttling on. Look for long tasks, and for scripting time spent in the grid's row creation versus your own code.

<Callout type="warning" title="Don't skip the throttle">
Optimizing on a fast development machine hides exactly the problem you are trying to fix. Always profile with CPU throttling, and on a real mid-range device if you can.
</Callout>

## Checklist

- Every row has a stable `getRowId`.
- Incoming messages are coalesced per row and flushed on an interval, not applied one by one.
- Updates go through `applyTransaction`, never a full `rowData` replacement.
- Cells use `valueFormatter` and `cellClassRules`, not heavy renderers.
- `animateRows` is off, and flashing is limited to the columns that need it.
- Performance was checked with CPU throttling.

If you have a streaming table that still struggles after these, the next places to look are column count, expensive `valueGetter`s, and whether anything else on the page is competing for the main thread.

## 1. Gán ID ổn định cho từng dòng và chỉ gửi phần bù (delta updates)

Sai lầm phổ biến nhất là thay mới toàn bộ tập dữ liệu (dataset) mỗi lần có tin nhắn tới:

```ts
// Anti-pattern: bảng phải so sánh (diff) hoặc dựng lại toàn bộ dòng ở mỗi nhịp
socket.onmessage = () => {
  api.setGridOption('rowData', rows.map((r) => ({ ...r })));
};
```

Nếu không có khóa định danh dòng, bảng coi mỗi mảng mới là dữ liệu hoàn toàn mới và dựng lại toàn bộ nút dòng (row nodes). Hãy chỉ cho bảng cách nhận diện từng dòng, rồi chỉ gửi những dòng thay đổi:

```ts
<AgGridReact
  getRowId={(p) => p.data.id}   // khóa định danh ổn định, duy nhất cho mỗi dòng
  rowData={initialRows}
/>

// sau đó, với mỗi lô thay đổi:
api.applyTransaction({ update: changedRows });
```

`getRowId` giải quyết hai việc cùng lúc. Nó giúp bảng tìm đúng dòng đang tồn tại để cập nhật, và giữ nguyên danh tính dòng (row identity) để phần DOM của những dòng không đổi được giữ yên. Thiếu nó, giao dịch cập nhật (update transaction) phải dò theo tham chiếu đối tượng (object reference) — điều bất khả thi với các đối tượng mới giải mã từ mạng.

## 2. Hợp nhất cập nhật (coalesce) rồi đẩy theo lô (batch)

Luồng dữ liệu thực tế thường đến dồn dập (bursty) và cập nhật cùng một mã nhiều lần chỉ trong vài mili-giây. Vẽ lại mọi giá trị trung gian là việc làm vô ích: mắt người không kịp nhìn thấy, và trình duyệt cũng chỉ vẽ tối đa một lần mỗi khung hình (frame).

Hãy giữ một `Map` lưu giá trị **mới nhất** theo từng ID dòng và đẩy định kỳ theo bộ đếm thời gian:

```ts
const pending = new Map<string, Row>();

socket.onmessage = (msg) => {
  const row = parse(msg);
  pending.set(row.id, row); // giá trị mới nhất ghi đè lên giá trị cũ
};

setInterval(() => {
  if (pending.size === 0) return;
  const batch = Array.from(pending.values());
  pending.clear();
  api.applyTransaction({ update: batch });
}, 100);
```

Chu kỳ đẩy (flush interval) 100 ms nghĩa là bảng chỉ cập nhật tối đa 10 lần/giây bất kể luồng dữ liệu đầu vào nhanh đến đâu, và mỗi lần cập nhật chỉ chứa mỗi dòng thay đổi đúng một lần. Đó là cách bản demo biến hàng nghìn cập nhật đầu vào mỗi giây thành vài nghìn dòng đẩy vào bảng, thay vì hàng chục hay hàng trăm nghìn dòng.

<Callout type="note" title="Giải pháp có sẵn trong AG Grid">
AG Grid cũng có `api.applyTransactionAsync()`, tự gom hàng đợi giao dịch và áp dụng cùng lúc sau khoảng `asyncTransactionWaitMillis` (mặc định 50 ms). Nó tự gom lô (batching) giúp bạn, nhưng không tự hợp nhất (coalesce) nhiều lần cập nhật của cùng một dòng. Tự viết chiếc `Map` nhỏ ở trên giúp bạn có cả hai, đồng thời kiểm soát hoàn toàn nhịp đẩy dữ liệu.
</Callout>

## 3. Giữ cho từng ô nhẹ nhất có thể (cheap cells)

Ở mức hàng nghìn cập nhật mỗi giây, chi phí xử lý trên từng ô (per-cell cost) sẽ chiếm phần lớn thời gian. Có hai thói quen rất hiệu quả:

- **Ưu tiên `valueFormatter` và `cellClassRules` thay cho trình dựng ô tùy biến (custom cell renderers).** Gắn một component của framework vào từng ô tốn chi phí khởi tạo (mount) và cập nhật rất thật. Trong khi định dạng một con số và bật/tắt class CSS thì gần như miễn phí.
- **Chọn lọc kỹ khi dùng `enableCellChangeFlash`.** Hiệu ứng nhấp nháy rất hữu ích ở cột giá khớp, nhưng sẽ gây rối mắt (và tốn thêm công vẽ lại) nếu bật cho cả sáu cột.

```ts
const columnDefs = [
  { field: 'last', valueFormatter: fmtPrice, enableCellChangeFlash: true },
  {
    field: 'changePct',
    valueFormatter: fmtChange,
    // đổi màu qua class CSS thay vì dựng một component chứa <span>
    cellClassRules: {
      'up': (p) => p.value >= 0,
      'down': (p) => p.value < 0,
    },
  },
];
```

Chế độ naive trong bản demo dùng một React cell renderer cho cột phần trăm thay đổi; còn chế độ tối ưu dùng đúng đoạn cấu hình ở trên.

## 4. Tắt những tính năng không dùng tới

Một số cấu hình mặc định được thiết kế cho dữ liệu tần suất thấp:

- **`animateRows={false}`** cho các luồng dữ liệu nhanh. Tạo hiệu ứng chuyển động cho các dòng nhảy liên tục chỉ làm nặng thêm giao diện.
- **`deltaSort`** nếu bảng đang sắp xếp theo một cột có giá trị thay đổi liên tục. Khi bật, bảng chỉ sắp xếp lại các dòng thay đổi thay vì sắp xếp lại toàn bộ dữ liệu sau mỗi giao dịch.
- **Giữ nguyên `rowBuffer`** trừ khi bạn đo thấy lý do cần sửa. Bộ đệm dòng (row buffer) lớn hơn sẽ dựng sẵn nhiều dòng nằm ngoài vùng nhìn thấy (viewport), đi ngược lại mục tiêu khi truyền dữ liệu nhanh.

## Đo lường thực tế, đừng đoán

Các thẻ thống kê trong bản demo cố ý làm rất đơn giản để bạn có thể tự tái tạo trong bất kỳ ứng dụng nào:

1. **Số khung hình mỗi giây (FPS):** đếm số lần callback `requestAnimationFrame` chạy mỗi giây. Dưới ngưỡng khoảng 30 FPS, giao diện bắt đầu giật lag.
2. **Khung hình dài nhất (Longest frame):** theo dõi khoảng nghỉ lớn nhất giữa hai khung hình. Chỉ cần một khung hình kéo dài 150 ms là mắt đã thấy khựng dù FPS trung bình trông vẫn ổn.
3. **Chrome DevTools → Performance:** ghi lại vài giây khi bật giới hạn CPU (CPU throttling). Tìm các tác vụ dài (long tasks), và soi xem thời gian chạy script nằm ở phần tạo dòng của AG Grid hay nằm ở code của bạn.

<Callout type="warning" title="Đừng bỏ qua bước bóp CPU">
Tối ưu trên một chiếc máy dev cấu hình mạnh sẽ che khuất đúng nút thắt bạn đang cần sửa. Luôn kiểm tra hiệu năng (profile) với CPU throttling, và tốt hơn nữa là trên một thiết bị tầm trung thực tế.
</Callout>

## Danh sách kiểm tra (Checklist)

- Mỗi dòng đều có `getRowId` ổn định.
- Tin nhắn đến được hợp nhất (coalesce) theo từng dòng và đẩy định kỳ theo chu kỳ, không áp dụng lẻ tẻ từng cái một.
- Cập nhật đi qua `applyTransaction`, tuyệt đối không thay mới toàn bộ `rowData`.
- Các ô dùng `valueFormatter` và `cellClassRules`, tránh các component dựng ô nặng nề.
- Đã tắt `animateRows`, và chỉ bật nhấp nháy ở những cột thực sự cần.
- Đã đo lại hiệu năng khi bật giới hạn CPU (CPU throttling).

Nếu bảng real-time của bạn vẫn chậm sau khi áp dụng hết các bước này, những chỗ tiếp theo cần kiểm tra là tổng số lượng cột, các hàm `valueGetter` nặng nề, và xem có tác vụ nào khác trên trang đang tranh chấp luồng chính (main thread) hay không.
