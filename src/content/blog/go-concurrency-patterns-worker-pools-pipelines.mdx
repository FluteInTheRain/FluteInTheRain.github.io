### Kubernetes has a knob for how many workers to run

Kubernetes runs its built-in controllers inside one program, `kube-controller-manager`. Each controller has a queue of objects to look at and a fixed number of workers that take from it. The number is a command-line flag. For deployments, `--concurrent-deployment-syncs` defaults to 5, and the reference page describes the trade-off in one line: "Larger number = more responsive deployments, but more CPU (and network) load." The same flag exists for replica sets and many other objects.

Concurrency in Go means choosing a shape for the work: how many workers, how they hand data to each other, and how they stop. Done well, load stays bounded and nothing is left running by mistake. [Post 7](/blog/go-goroutines-channels-select/) taught the pieces: goroutines, channels, `select`. This post puts them together into the six shapes you will meet most often, and for each one it shows how the program shuts down.

<Callout type="note" title="TL;DR">
A worker pool is N goroutines reading one jobs channel. A pipeline is stages connected by channels, and it needs a cancellation signal so an early exit does not strand the stages. Fan-out is several goroutines reading one channel, and fan-in merges several channels into one. A buffered channel of empty structs works as a semaphore that limits concurrency. A ticker, or `rate.Limiter`, limits speed. `errgroup` runs a group of tasks, returns the first error, and cancels the rest. In every pattern, the sender closes channels and something cancels the goroutines that are still waiting.
</Callout>

## Coming from Java, Python or JavaScript

You probably already have a name for most of these shapes. Go builds them from channels instead of from a library class.

| You want to | Java | Python | JavaScript | Go |
|---|---|---|---|---|
| Fixed number of workers on a queue | `Executors.newFixedThreadPool(n)` | `ThreadPoolExecutor(max_workers=n)` | a library such as `p-limit` | N goroutines reading one channel |
| Limit how many run at once | `Semaphore` | `asyncio.Semaphore` | a library such as `p-limit` | buffered `chan struct{}` |
| Stages that feed each other | streams, `BlockingQueue` between threads | generators, `asyncio.Queue` | async iterators | stages connected by channels |
| Limit calls per second | Guava `RateLimiter` | a library such as `ratelimit` | a library such as `bottleneck` | `time.Ticker` or `rate.Limiter` |
| Run a group, stop on first error | `ExecutorCompletionService` and manual cancel | `asyncio.TaskGroup` (cancels the rest) | `Promise.all` rejects, but the others keep running | `errgroup` |

The big difference is where the pool lives. In Java the pool is an object you configure. In Go the pool is only a loop in each goroutine and a channel they share, so there is nothing to configure and nothing to hide: you can read the whole pattern in twenty lines.

Six patterns is a lot for one sitting. If you only want the short version, jump to the "Choosing a pattern" table near the end, then come back for the ones you need.

<Concepts>

- **Worker pool**: a fixed number of goroutines that all take jobs from one channel. The number of workers caps how much work runs at once.
- **Pipeline**: stages connected by channels. Each stage receives values from the stage before it, does one step, and sends the result to the stage after it.
- **Fan-out and fan-in**: fan-out means several goroutines read from the same channel to share the work. Fan-in means merging the outputs of several channels into one.
- **Semaphore**: a counter that lets at most N holders in at once. In Go, a buffered channel does the job.
- **Backpressure**: when a slow stage makes the stage before it wait, instead of letting work pile up without limit.

</Concepts>

## A worker pool

A worker pool starts a fixed number of goroutines that each loop on the same channel of jobs. Whichever worker is free takes the next job. If there are more jobs than workers, the extra jobs wait in the channel, and that waiting is the backpressure that keeps load bounded.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type result struct {
	job    int
	square int
}

func run(workers int) (int, time.Duration) {
	start := time.Now()
	jobs := make(chan int)
	results := make(chan result)

	var wg sync.WaitGroup
	for w := 1; w <= workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for n := range jobs {
				time.Sleep(50 * time.Millisecond) // pretend work
				results <- result{job: n, square: n * n}
			}
		}()
	}

	go func() {
		for n := 1; n <= 9; n++ {
			jobs <- n
		}
		close(jobs)
	}()

	go func() {
		wg.Wait()
		close(results)
	}()

	sum := 0
	for r := range results {
		sum += r.square
	}
	return sum, time.Since(start).Round(50 * time.Millisecond)
}

func main() {
	for _, workers := range []int{1, 3} {
		sum, took := run(workers)
		fmt.Printf("%d worker(s): sum of squares %d in %v\n", workers, sum, took)
	}
}
```

Read it in four parts. The three workers each run `for n := range jobs`, which keeps taking jobs until `jobs` is closed and empty (that is the `range`-over-a-channel rule from post 7). One more goroutine feeds the numbers 1 to 9 into `jobs` and then calls `close(jobs)`. Each worker sends its answer on `results`. And `main` loops over `results` and adds the numbers up.

The goroutine that feeds `jobs` is separate on purpose. If `main` fed the jobs itself, it would block on a send while the workers block on sending results back, and nobody would be reading. Both sides would wait for each other forever.

Nine jobs of 50 ms take 450 ms on one worker and 150 ms on three. That is the point of the pool, and it also shows its limit: the speed-up stops when the workers outnumber the jobs, or when the real bottleneck (a database, a CPU core, an API with a quota) is saturated. A common starting point is one worker per CPU core for CPU-bound work, and more for work that mostly waits on a network. Measure, then change the number.

Shutdown path: Closing `jobs` ends every worker's `range` loop. Each worker's `defer wg.Done()` fires. A small goroutine waits on the `WaitGroup` and then closes `results`, which ends the loop in `main`. The rule behind this is the one from post 7: the sender closes. Here the producer closes `jobs`, and the closer goroutine closes `results` because it is the only one that knows when every worker is done. This path only works while `main` keeps reading `results`. If `main` stopped early, every worker would block on its next send and never exit. Measured on the program above with `main` reading just one result: 6 goroutines stay alive (`main`, 3 workers, the producer and the closer). The next snippet fixes that.

Since Go 1.25 a `WaitGroup` also has a `Go` method, so `wg.Go(func() { ... })` replaces the `Add(1)`, `go` and `defer wg.Done()` triple. This post keeps the long form so each step is visible.

### Stopping a pool early

To let a pool stop when the caller walks away, give every goroutine that can block on a channel a second way out. A `context` carries a `Done()` channel that closes when somebody calls `cancel()`; [post 8](/blog/go-context-timeouts-mutexes/) covers it in full, and the pipeline section below uses the same three pieces. Here the producer and each worker replace a plain send with a `select` between the send and `<-ctx.Done()`, and `main` reads one result and then calls `cancel()`.

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"sync"
	"time"
)

type result struct {
	job    int
	square int
}

func run(ctx context.Context, workers int) <-chan result {
	jobs := make(chan int)
	results := make(chan result)

	var wg sync.WaitGroup
	for w := 1; w <= workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for n := range jobs {
				time.Sleep(50 * time.Millisecond) // pretend work
				select {
				case results <- result{job: n, square: n * n}:
				case <-ctx.Done():
					return
				}
			}
		}()
	}

	go func() {
		defer close(jobs)
		for n := 1; n <= 9; n++ {
			select {
			case jobs <- n:
			case <-ctx.Done():
				return
			}
		}
	}()

	go func() {
		wg.Wait()
		close(results)
	}()

	return results
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	results := run(ctx, 3)

	<-results
	fmt.Println("took one result, now stopping")
	cancel() // main stops reading, so tell the pool to stop

	time.Sleep(200 * time.Millisecond)
	fmt.Println("goroutines still alive:", runtime.NumGoroutine())
}
```

<TerminalOutput command="go run -race main.go" label="Go 1.27.1 · darwin/arm64" caption="Two real runs with the race detector on, no race reported. After cancel only main is left, so the count is 1. The same program without the two selects printed 6 on the same check.">
```text

goroutines still alive: 1
took one result, now stopping
goroutines still alive: 1
```
</TerminalOutput>

Now there are two exits. If `main` reads everything, `jobs` closes and the pool ends as before. If `main` cancels, the producer and every worker leave through their `ctx.Done()` case, the `WaitGroup` fills, and the closer closes `results`.

The pool's capacity is the number of workers times how many jobs one worker finishes per second. While the arrival rate is below that capacity, throughput matches the arrival rate and the queue stays short. Once arrivals exceed it, throughput is stuck at the capacity and the queue grows for as long as the overload lasts. Adding workers beyond what the arrival rate needs buys nothing.

## Pipelines and cancellation

A pipeline is a chain of stages, each one a goroutine that reads from an input channel, does one step, and writes to an output channel. The Go blog puts it this way: "There's no formal definition of a pipeline in Go; it's just one of many kinds of concurrent programs." What you get from the shape is that each stage is small, and the channels between them give you backpressure for free: a slow stage makes the stage before it wait.

Before the code, two bits of syntax. `nums ...int` is a variadic parameter: the caller can pass any number of `int` values, and inside the function `nums` is a slice. `<-chan int` is a receive-only channel: the function returns a channel that the caller can read from but not send on, which makes it clear who owns the sending.

Here is a two-stage pipeline: `gen` sends numbers, and `square` squares them. The `main` function reads two results and then stops, the way a caller does when it only needed the first few.

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func gen(nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		for _, n := range nums {
			out <- n
		}
		close(out)
	}()
	return out
}

func square(in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		for n := range in {
			out <- n * n
		}
		close(out)
	}()
	return out
}

func main() {
	out := square(gen(1, 2, 3, 4, 5, 6))
	fmt.Println(<-out, <-out) // take two values, then stop reading

	time.Sleep(100 * time.Millisecond)
	fmt.Println("goroutines still alive:", runtime.NumGoroutine())
}
```

<TerminalOutput command="go run main.go" label="Go 1.27.1 · darwin/arm64" caption="One real run. Three goroutines are still alive: main, and two stages that will never finish. The first line shows the squares of 1 and 2.">
```text

goroutines still alive: 3
```
</TerminalOutput>

`runtime.NumGoroutine()` is just a counter of live goroutines, which is enough to show the problem. After `main` reads two values, `square` is stuck trying to send the third, and `gen` is stuck trying to send to `square`. Nobody will ever receive, so both wait forever. That is the leak the Go blog warns about, and it is the same kind of bug as the one in post 7.

The fix is to give every stage a way to hear "stop". The standard tool is a `context`: it carries a `Done()` channel that closes when somebody calls `cancel()`. [Post 8](/blog/go-context-timeouts-mutexes/) covers `context` in full. For now you only need three pieces. `context.WithCancel` returns a context and a `cancel` function. Every send becomes a `select` between sending and `<-ctx.Done()`. And `main` calls `cancel()` when it is finished.

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"
)

func gen(ctx context.Context, nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			select {
			case out <- n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func square(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			select {
			case out <- n * n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())

	out := square(ctx, gen(ctx, 1, 2, 3, 4, 5, 6))
	fmt.Println(<-out, <-out) // take two values, then stop reading
	cancel()                  // tell every stage to stop

	time.Sleep(100 * time.Millisecond)
	fmt.Println("goroutines still alive:", runtime.NumGoroutine())
}
```

<TerminalOutput command="go run main.go" label="Go 1.27.1 · darwin/arm64" caption="One real run. After cancel, only main is left, so the count is 1.">
```text
1 4
goroutines still alive: 1
```
</TerminalOutput>

Each stage uses `defer close(out)`, so its output channel closes no matter which path it leaves by. Now the two unfinished stages see `ctx.Done()` close, return, and the count drops to 1. `square` can leave by either door: if it is stuck sending, through its own `ctx.Done()` case; if it is waiting to receive, because `gen` returned through `ctx.Done()` and its `defer close(out)` closed the channel `square` calls `in`, which ends `for n := range in`.

Shutdown path: There are two exits, and a good pipeline handles both. On the normal path the first stage runs out of input and closes its channel, and the close travels down the chain as each stage's `range` loop ends. On the early path somebody cancels the context, and each stage leaves through its `ctx.Done()` case. The habit to build is to check `ctx.Done()` at every point where a goroutine can block on a channel.

## Fan-out and fan-in

If one stage is the slow one, you can run several copies of it. Fan-out means several goroutines read from the same channel: each value goes to exactly one of them, so the work is shared. Fan-in means merging the outputs of those copies back into one channel so the next stage has a single place to read from. The worker pool above is fan-out and fan-in in one piece. Here the same idea is applied to a pipeline stage.

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func gen(ctx context.Context, nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			select {
			case out <- n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func square(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			time.Sleep(50 * time.Millisecond) // a slow stage
			select {
			case out <- n * n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func merge(ctx context.Context, cs ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	for _, c := range cs {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for n := range c {
				select {
				case out <- n:
				case <-ctx.Done():
					return
				}
			}
		}()
	}
	go func() {
		wg.Wait()
		close(out)
	}()
	return out
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	start := time.Now()
	in := gen(ctx, 1, 2, 3, 4, 5, 6, 7, 8, 9)

	// fan out: three copies of the slow stage read from the same channel
	a, b, c := square(ctx, in), square(ctx, in), square(ctx, in)

	// fan in: merge their outputs into one channel
	sum := 0
	for n := range merge(ctx, a, b, c) {
		sum += n
	}
	fmt.Println("sum of squares:", sum, "in", time.Since(start).Round(50*time.Millisecond))
}
```

Read `merge` in four steps. (1) It makes one output channel, `out`. (2) For each input channel `c` it starts a goroutine that copies every value from `c` to `out`, or leaves early if the context is cancelled. (3) Each copier calls `wg.Done()` when it leaves. (4) One last goroutine waits on the `WaitGroup` and only then closes `out`, for the same reason the pool did: closing earlier would let a copier send on a closed channel. Each copier uses `c` from the loop. That is safe since Go 1.22, because every iteration gets its own `c` (and its own `i` or `id` in the later examples); [post 7](/blog/go-goroutines-channels-select/) explains it. In `main`, three copies of `square` all read from the same `in` channel (fan-out), and `merge` turns their three outputs into one (fan-in). Each copy sleeps 50 ms per value to stand in for slow work.

<TerminalOutput command="go run main.go" label="Go 1.27.1 · darwin/arm64" caption="One real run. Nine values at 50 ms each would take 450 ms in one stage, and three copies take about 150 ms. The sum is always 285. The order in which values come out of merge is not fixed, which is why the program only adds them up.">
```text

```
</TerminalOutput>

The price of fan-out is order. Values can finish in a different order than they went in, because a copy that got a quick value overtakes one that got a slow value. If the order matters, attach an index to each value and sort at the end, or do not fan out that stage.

Shutdown path: Cancellation reaches every copier through the same `ctx`, and the `defer cancel()` in `main` guarantees it fires even when the loop ends early. The normal path is the close chain again: `gen` closes `in`, each `square` closes its output, and the `WaitGroup` in `merge` closes `out` once all three have.

## Bounding concurrency with a semaphore

Sometimes you do not want a pool of long-lived workers. You have a list of tasks, you are happy to start one goroutine per task, and you only need to cap how many do real work at the same time. A buffered channel of empty structs does it. The channel's capacity is the limit. Sending into it takes a slot, and receiving from it gives the slot back.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func main() {
	sem := make(chan struct{}, 3) // at most 3 tasks at once
	var wg sync.WaitGroup

	for i := 1; i <= 8; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			sem <- struct{}{}        // take a slot; blocks when all 3 are taken
			defer func() { <-sem }() // give the slot back
			fmt.Println("task", i, "running, slots in use:", len(sem))
			time.Sleep(100 * time.Millisecond)
		}()
	}
	wg.Wait()
	fmt.Println("done")
}
```

`chan struct{}` is a channel whose values carry no data (an empty struct takes no memory), which is the usual way to write "just a token". With capacity 3, the fourth `sem <- struct{}{}` blocks until some task runs `<-sem`. The `defer func() { <-sem }()` line returns the slot even if the task exits early. It is wrapped in a small function because `defer` needs a function call, and `<-sem` on its own is a receive, not a call. Each goroutine also gets its own `i`, the same Go 1.22 rule as in `merge`. And `len(sem)` is the number of slots in use right now, which the program prints so you can see the limit at work.

<TerminalOutput command="go run main.go" label="Go 1.27.1 · darwin/arm64" caption="One real run. The slot count climbs to 3 and stays there. The order of the tasks is different every run, and the lines come out in the order the goroutines reached `Println`, which is not the order they took a slot. That is why the first line can say task 8 with 1 slot in use: it simply got there first, while the others were still waiting for a slot.">
```text

task 4 running, slots in use: 2
task 1 running, slots in use: 3
task 2 running, slots in use: 3
task 3 running, slots in use: 3
```

In this version all 8 goroutines start immediately, and 5 of them wait at the `sem <-` line. That is fine for a few hundred tasks. For a million, move `sem <- struct{}{}` above the `go` statement, so the loop itself blocks and only 3 goroutines exist at any moment.

When to use which? A worker pool is the better fit when each worker has setup cost (a database connection, a buffer) that you want to reuse, or when you want a queue in front of the workers. A semaphore is the better fit for "do these N things, at most K at a time" with no state to share.

Shutdown path: The `defer` that releases the slot is the whole shutdown story: whether a task finishes or returns early, its slot comes back. A panic that nobody recovers (post 5) crashes the whole program, so slots only matter after a panic if the task recovers it. The `WaitGroup` tells `main` when every task is done. To stop waiting for a slot when the caller gives up, replace the plain send with a `select` that also listens to `<-ctx.Done()`, as in the pipeline.

## Rate limiting

Bounding concurrency limits how many calls are in flight. Rate limiting limits how often calls start. They are different problems: an API that allows 5 requests per second does not care that only 2 are in flight if you send them in a burst of 50 in the first second.

The standard library already has the simplest version. A `time.Ticker` sends the current time on its channel `C` at a fixed interval, so receiving from `C` is "wait until the next slot".

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	ticker := time.NewTicker(200 * time.Millisecond)
	defer ticker.Stop()

	start := time.Now()
	for i := 1; i <= 5; i++ {
		<-ticker.C // wait for the next tick
		fmt.Printf("call %d at %v\n", i, time.Since(start).Round(50*time.Millisecond))
	}
}
```

`defer ticker.Stop()` releases the ticker when the function returns. A ticker does not pile up ticks for a slow receiver: its channel holds one tick, and further ticks are dropped until the receiver catches up. So a ticker gives you a steady pace, not a catch-up burst.

When you need bursts, or a limit shared by many goroutines, use the `rate` package. It lives in `golang.org/x/time`, an extension repository maintained by the Go team but not part of the standard library, so you add it to your module first with `go get` (the same command from [post 1](/blog/go-first-program-modules-packages/)).

```text
go get golang.org/x/time/rate
```

```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/time/rate"
)

func main() {
	// one call every 200ms, bursts of at most 1
	limiter := rate.NewLimiter(rate.Every(200*time.Millisecond), 1)
	ctx := context.Background()

	start := time.Now()
	for i := 1; i <= 5; i++ {
		if err := limiter.Wait(ctx); err != nil {
			fmt.Println("stopped:", err)
			return
		}
		fmt.Printf("call %d at %v\n", i, time.Since(start).Round(50*time.Millisecond))
	}
}
```

`rate.NewLimiter(rate.Every(200*time.Millisecond), 1)` allows one event every 200 ms with a burst of 1. A burst of 5 would let five calls go at once after a quiet spell. `limiter.Wait(ctx)` blocks until the next call is allowed, and it returns an error if the context is cancelled first.

Shutdown path: The ticker version stops with `ticker.Stop()`. The limiter has no goroutine or timer of its own to stop, so the exit is the context you pass to `Wait`: cancel it and `Wait` returns an error instead of blocking, which lets a caller leave a long queue of waiting requests.

## errgroup: run a group and stop on the first error

The pool and the pipeline have a gap. If one task fails, how do the others find out? You could add an error channel, a shared variable behind a lock, and a cancel function, and wire all of them correctly. The 100 Go Mistakes book lists doing this by hand as a mistake, because the Go team already ships the package: `errgroup`.

Like `rate`, it lives in `golang.org/x`, so add it with `go get`.

```text
go get golang.org/x/sync/errgroup
```

An `errgroup.Group` has two methods you need. `g.Go(f)` runs `f`, a function that returns an `error`, in a new goroutine. `g.Wait()` blocks until all of them finish and returns the first non-nil error. `errgroup.WithContext` also gives you a context that is cancelled when any function returns an error, so the other tasks can stop early. `g.SetLimit(3)` caps how many run at once, and it makes `g.Go` block when the limit is reached, so the semaphore from the previous section comes built in.

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func fetch(ctx context.Context, id int) error {
	select {
	case <-time.After(time.Duration(id) * 100 * time.Millisecond):
		if id == 2 {
			return errors.New("fetch 2: upstream returned 503")
		}
		fmt.Println("fetch", id, "ok")
		return nil
	case <-ctx.Done():
		fmt.Println("fetch", id, "cancelled:", ctx.Err())
		return ctx.Err()
	}
}

func main() {
	g, ctx := errgroup.WithContext(context.Background())
	g.SetLimit(3) // at most 3 goroutines at once

	for id := 1; id <= 5; id++ {
		g.Go(func() error {
			return fetch(ctx, id)
		})
	}

	if err := g.Wait(); err != nil {
		fmt.Println("group failed:", err)
	}
}
```

Task `id` takes `id` times 100 ms. Task 2 fails after 200 ms, with 3, 4 and 5 still waiting or about to start. The failure cancels `ctx`, and each task is waiting in a `select` that includes `<-ctx.Done()`, so it leaves at once instead of sitting out its full time.

<TerminalOutput command="go run main.go" label="Go 1.27.1 · darwin/arm64" caption="One real run, using golang.org/x/sync v0.25.0. Which of tasks 3, 4 and 5 print their cancel line first can change between runs, but fetch 2 is the error Wait returns, and the three others are cancelled.">
```text

fetch 4 cancelled: context canceled
fetch 5 cancelled: context canceled
fetch 3 cancelled: context canceled
group failed: fetch 2: upstream returned 503
```
</TerminalOutput>

One thing to remember: cancelling the context only helps tasks that look at it. A function that ignores `ctx` runs to the end no matter what, so every function you pass to `g.Go` should pass `ctx` down to whatever it calls (an HTTP request, a database query) or `select` on it.

Shutdown path: `g.Wait()` returns only after every goroutine has returned, so nothing is left behind. The group's context is cancelled when a task fails or when `Wait` returns, whichever comes first. Task 5 shows the edge: it only got a free slot after task 2 failed, so it started with an already-cancelled context and left right away. Task 3 is the other case: it started at 0 ms and would have finished at 300 ms, but the cancel at 200 ms reached it first. Task 4 got task 1's slot at 100 ms and was cancelled at 200 ms the same way.

## Choosing a pattern

| Pattern | Problem it solves | Stops when | Watch for |
|---|---|---|---|
| Worker pool | Cap how much runs at once, with a queue in front | the jobs channel is closed, or the context is cancelled (the early-stop version above) | a consumer that stops reading `results` and strands the workers |
| Pipeline | Split work into small steps with backpressure | the first stage closes, or the context is cancelled | a stage with a send that does not also select on `ctx.Done()` |
| Fan-out and fan-in | Speed up one slow stage | every copy has returned, then the merge closes | output order is no longer the input order |
| Semaphore channel | At most K tasks do real work at once | each task releases its slot with `defer` | acquiring the slot inside the goroutine still starts every goroutine |
| Ticker or `rate.Limiter` | Limit how often calls start | `Stop()`, or the context given to `Wait` | confusing a rate limit with a concurrency limit |
| `errgroup` | Run a group and keep the first error | `Wait` returns after all tasks return | tasks that ignore the cancelled `ctx` |

Whichever you pick, ask the same two questions that post 7 ended on. Who closes each channel? And what makes each goroutine leave if the caller walks away?

## Key takeaways

- A worker pool is N goroutines ranging over one jobs channel. The worker count is the cap on concurrent work, and the channel is the queue in front of it.
- The producer closes the jobs channel. A separate goroutine waits on a `WaitGroup` and then closes the results channel.
- In a pipeline, every send that can block also selects on `ctx.Done()`. A stage that does not leaves goroutines stuck when the consumer quits early.
- Fan-out shares one channel between several goroutines. Fan-in merges several channels into one, and it does not keep the input order.
- A buffered `chan struct{}` is a semaphore: send to take a slot, receive to give it back, and release with `defer`.
- Limiting concurrency and limiting rate are different. Use a `time.Ticker` or `rate.Limiter` for rate.
- `errgroup` runs a group, returns the first error, and cancels the group's context. Its tasks must watch that context for the cancel to matter. `golang.org/x/sync` and `golang.org/x/time` are separate modules you add with `go get`.

Khác biệt lớn nhất là chỗ pool nằm ở đâu. Trong Java, pool là một đối tượng bạn cấu hình. Trong Go, pool chỉ là một vòng lặp trong mỗi goroutine cộng một channel dùng chung, nên không có gì để cấu hình và không có gì bị giấu: bạn đọc hết mẫu này trong hai chục dòng.

Sáu mẫu là nhiều cho một lần ngồi đọc. Nếu chỉ cần bản ngắn, hãy nhảy tới bảng "Chọn mẫu nào" gần cuối bài, rồi quay lại đọc những mẫu bạn cần.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Worker pool**: một số goroutine cố định cùng lấy job từ một channel. Số worker là mức trần cho lượng việc chạy cùng lúc.
- **Pipeline**: các stage nối nhau bằng channel. Mỗi stage nhận giá trị từ stage trước, làm một bước, rồi gửi kết quả cho stage sau.
- **Fan-out và fan-in**: fan-out là nhiều goroutine cùng đọc một channel để chia việc. Fan-in là gộp đầu ra của nhiều channel thành một.
- **Semaphore**: một bộ đếm cho tối đa N bên vào cùng lúc. Trong Go, một channel có buffer làm được việc này.
- **Backpressure**: khi một stage chậm bắt stage đứng trước phải chờ, thay vì để việc chất đống không giới hạn.

</Concepts>

## Worker pool

Worker pool mở một số goroutine cố định, mỗi cái lặp trên cùng một channel job. Worker nào rảnh sẽ lấy job kế tiếp. Nếu job nhiều hơn worker, phần dư chờ trong channel, và sự chờ đó là backpressure giữ cho tải bị chặn trên.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type result struct {
	job    int
	square int
}

func run(workers int) (int, time.Duration) {
	start := time.Now()
	jobs := make(chan int)
	results := make(chan result)

	var wg sync.WaitGroup
	for w := 1; w <= workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for n := range jobs {
				time.Sleep(50 * time.Millisecond) // pretend work
				results <- result{job: n, square: n * n}
			}
		}()
	}

	go func() {
		for n := 1; n <= 9; n++ {
			jobs <- n
		}
		close(jobs)
	}()

	go func() {
		wg.Wait()
		close(results)
	}()

	sum := 0
	for r := range results {
		sum += r.square
	}
	return sum, time.Since(start).Round(50 * time.Millisecond)
}

func main() {
	for _, workers := range []int{1, 3} {
		sum, took := run(workers)
		fmt.Printf("%d worker(s): sum of squares %d in %v\n", workers, sum, took)
	}
}
```

Đọc nó theo bốn phần. Ba worker mỗi cái chạy `for n := range jobs`, vòng này cứ lấy job cho đến khi `jobs` đóng và hết dữ liệu (quy tắc `range` trên channel từ bài 7). Một goroutine khác đưa các số từ 1 đến 9 vào `jobs` rồi gọi `close(jobs)`. Mỗi worker gửi đáp án lên `results`. Còn `main` lặp trên `results` và cộng các số lại.

Goroutine đưa job vào là một goroutine riêng, có chủ đích. Nếu `main` tự đưa job, nó sẽ bị chặn ở lệnh gửi trong khi các worker bị chặn ở lệnh gửi kết quả về, mà không ai đang đọc. Hai bên chờ nhau mãi mãi.

<TerminalOutput command="go run main.go" label="Go 1.27.1 · darwin/arm64" caption="Một lần chạy thật. Tổng luôn là 285, nhưng thời gian đến từ lệnh sleep nên có thể lệch vài mili giây. Ba worker tốn khoảng một phần ba thời gian của một worker.">
```text
1 worker(s): sum of squares 285 in 450ms
3 worker(s): sum of squares 285 in 150ms
```
</TerminalOutput>

Chín job, mỗi job 50 ms, mất 450 ms với một worker và 150 ms với ba worker. Đó là cái lợi của pool, và nó cũng cho thấy giới hạn: tốc độ ngừng tăng khi worker nhiều hơn job, hoặc khi chỗ nghẽn thật (một database, một nhân CPU, một API có hạn mức) đã bão hòa. Điểm xuất phát hay dùng là một worker cho mỗi nhân CPU với việc nặng tính toán, và nhiều hơn với việc chủ yếu chờ mạng. Hãy đo rồi mới đổi số.

Đường tắt: Đóng `jobs` làm vòng `range` của mọi worker kết thúc. `defer wg.Done()` của từng worker chạy. Một goroutine nhỏ chờ `WaitGroup` rồi đóng `results`, nhờ đó vòng lặp trong `main` kết thúc. Quy tắc phía sau là quy tắc từ bài 7: bên gửi đóng. Ở đây producer đóng `jobs`, còn goroutine đóng `results` là vì chỉ nó biết khi nào mọi worker đã xong. Đường này chỉ chạy được khi `main` còn đọc `results`. Nếu `main` dừng sớm, mọi worker sẽ bị chặn ở lệnh gửi kế tiếp và không bao giờ thoát. Đo trên chương trình ở trên khi `main` chỉ đọc một kết quả: còn 6 goroutine sống (`main`, 3 worker, producer và goroutine đóng). Đoạn code kế tiếp sửa chuyện đó.

Từ Go 1.25, `WaitGroup` còn có phương thức `Go`, nên `wg.Go(func() { ... })` thay cho bộ ba `Add(1)`, `go` và `defer wg.Done()`. Bài này giữ dạng dài để từng bước nhìn thấy được.

### Dừng pool sớm

Để pool dừng được khi bên gọi bỏ đi, hãy cho mọi goroutine có thể bị chặn trên channel một lối thoát thứ hai. Một `context` mang channel `Done()` đóng lại khi có người gọi `cancel()`; [bài 8](/blog/go-context-timeouts-mutexes/) nói đầy đủ về nó, và phần pipeline bên dưới dùng đúng ba mảnh này. Ở đây producer và từng worker thay lệnh gửi trơn bằng một `select` giữa lệnh gửi và `<-ctx.Done()`, còn `main` đọc một kết quả rồi gọi `cancel()`.

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"sync"
	"time"
)

type result struct {
	job    int
	square int
}

func run(ctx context.Context, workers int) <-chan result {
	jobs := make(chan int)
	results := make(chan result)

	var wg sync.WaitGroup
	for w := 1; w <= workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for n := range jobs {
				time.Sleep(50 * time.Millisecond) // pretend work
				select {
				case results <- result{job: n, square: n * n}:
				case <-ctx.Done():
					return
				}
			}
		}()
	}

	go func() {
		defer close(jobs)
		for n := 1; n <= 9; n++ {
			select {
			case jobs <- n:
			case <-ctx.Done():
				return
			}
		}
	}()

	go func() {
		wg.Wait()
		close(results)
	}()

	return results
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	results := run(ctx, 3)

	<-results
	fmt.Println("took one result, now stopping")
	cancel() // main stops reading, so tell the pool to stop

	time.Sleep(200 * time.Millisecond)
	fmt.Println("goroutines still alive:", runtime.NumGoroutine())
}
```

```text
goroutines still alive: 1
took one result, now stopping
goroutines still alive: 1
```

Giờ có hai lối thoát. Nếu `main` đọc hết, `jobs` đóng và pool kết thúc như trước. Nếu `main` hủy, producer và mọi worker thoát qua nhánh `ctx.Done()` của mình, `WaitGroup` đầy, và goroutine đóng đóng `results`.

### Thử đi: đổi số worker

Trình mô phỏng bên dưới đưa job vào một pool. Hãy tăng tốc độ job đến hoặc thời gian mỗi job, rồi xem hàng đợi và thông lượng khi bạn đổi số worker.

<GoWorkerPoolDemo />

Sức chứa của pool bằng số worker nhân với số job một worker xong mỗi giây. Khi tốc độ job đến còn dưới mức đó, thông lượng bằng tốc độ job đến và hàng đợi ngắn. Khi job đến vượt mức đó, thông lượng dừng ở sức chứa và hàng đợi dài ra suốt thời gian quá tải. Thêm worker vượt mức tốc độ đến cần thì chẳng được gì.

## Pipeline và việc hủy

Pipeline là một chuỗi các stage, mỗi stage là một goroutine đọc từ channel đầu vào, làm một bước và ghi ra channel đầu ra. Go blog nói: "There's no formal definition of a pipeline in Go; it's just one of many kinds of concurrent programs" (Go không có định nghĩa chính thức cho pipeline; nó chỉ là một trong nhiều kiểu chương trình concurrent). Cái bạn có từ hình dạng này là mỗi stage nhỏ, và các channel giữa chúng cho bạn backpressure miễn phí: stage chậm khiến stage đứng trước phải chờ.

Trước khi xem code, hai chỗ cú pháp. `nums ...int` là tham số variadic: bên gọi truyền bao nhiêu giá trị `int` cũng được, và trong hàm `nums` là một slice. `<-chan int` là channel chỉ-nhận: hàm trả về một channel mà bên gọi chỉ đọc được, không gửi vào được, nên rõ ràng ai sở hữu phía gửi.

Đây là pipeline hai stage: `gen` gửi các số, `square` bình phương chúng. Hàm `main` đọc hai kết quả rồi dừng, như một bên gọi chỉ cần vài giá trị đầu.

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func gen(nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		for _, n := range nums {
			out <- n
		}
		close(out)
	}()
	return out
}

func square(in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		for n := range in {
			out <- n * n
		}
		close(out)
	}()
	return out
}

func main() {
	out := square(gen(1, 2, 3, 4, 5, 6))
	fmt.Println(<-out, <-out) // take two values, then stop reading

	time.Sleep(100 * time.Millisecond)
	fmt.Println("goroutines still alive:", runtime.NumGoroutine())
}
```

`runtime.NumGoroutine()` chỉ là bộ đếm số goroutine đang sống, đủ để cho thấy vấn đề. Sau khi `main` đọc hai giá trị, `square` kẹt ở lệnh gửi giá trị thứ ba, và `gen` kẹt ở lệnh gửi sang `square`. Sẽ không ai nhận nữa, nên cả hai chờ mãi. Đó là lỗi leak mà Go blog cảnh báo, cùng loại với lỗi trong bài 7.

Cách sửa là cho mỗi stage một cách nghe thấy "dừng". Công cụ chuẩn là `context`: nó mang một channel `Done()` đóng lại khi có người gọi `cancel()`. [Bài 8](/blog/go-context-timeouts-mutexes/) nói đầy đủ về `context`. Lúc này bạn chỉ cần ba mảnh. `context.WithCancel` trả về một context và một hàm `cancel`. Mỗi lệnh gửi trở thành một `select` giữa việc gửi và `<-ctx.Done()`. Và `main` gọi `cancel()` khi xong.

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"
)

func gen(ctx context.Context, nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			select {
			case out <- n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func square(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			select {
			case out <- n * n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())

	out := square(ctx, gen(ctx, 1, 2, 3, 4, 5, 6))
	fmt.Println(<-out, <-out) // take two values, then stop reading
	cancel()                  // tell every stage to stop

	time.Sleep(100 * time.Millisecond)
	fmt.Println("goroutines still alive:", runtime.NumGoroutine())
}
```

<TerminalOutput command="go run main.go" label="Go 1.27.1 · darwin/arm64" caption="Một lần chạy thật. Sau khi cancel chỉ còn main, nên số đếm là 1.">
```text
1 4
goroutines still alive: 1
```
</TerminalOutput>

Mỗi stage dùng `defer close(out)`, nên channel đầu ra của nó đóng dù thoát bằng đường nào. Giờ hai stage còn dang dở thấy `ctx.Done()` đóng, return, và số đếm giảm về 1. `square` có thể thoát bằng một trong hai cửa: nếu đang kẹt ở lệnh gửi thì qua nhánh `ctx.Done()` của chính nó; nếu đang chờ nhận thì vì `gen` đã return qua `ctx.Done()` và `defer close(out)` của nó đóng channel mà `square` gọi là `in`, làm `for n := range in` kết thúc.

Đường tắt: Có hai lối thoát, và một pipeline tốt xử lý cả hai. Ở đường bình thường, stage đầu hết đầu vào và đóng channel của nó, rồi việc đóng lan xuống chuỗi khi vòng `range` của từng stage kết thúc. Ở đường thoát sớm, có người hủy context, và mỗi stage thoát qua nhánh `ctx.Done()` của nó. Thói quen cần tập là kiểm tra `ctx.Done()` ở mọi chỗ mà một goroutine có thể bị chặn trên channel.

## Fan-out và fan-in

Nếu một stage là stage chậm, bạn có thể chạy nhiều bản sao của nó. Fan-out nghĩa là nhiều goroutine cùng đọc một channel: mỗi giá trị đến đúng một trong số đó, nên việc được chia. Fan-in nghĩa là gộp đầu ra của các bản sao đó về một channel để stage sau chỉ có một chỗ để đọc. Worker pool ở trên chính là fan-out và fan-in trong một khối. Ở đây ta áp ý đó cho một stage của pipeline.

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func gen(ctx context.Context, nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			select {
			case out <- n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func square(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			time.Sleep(50 * time.Millisecond) // a slow stage
			select {
			case out <- n * n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func merge(ctx context.Context, cs ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	for _, c := range cs {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for n := range c {
				select {
				case out <- n:
				case <-ctx.Done():
					return
				}
			}
		}()
	}
	go func() {
		wg.Wait()
		close(out)
	}()
	return out
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	start := time.Now()
	in := gen(ctx, 1, 2, 3, 4, 5, 6, 7, 8, 9)

	// fan out: three copies of the slow stage read from the same channel
	a, b, c := square(ctx, in), square(ctx, in), square(ctx, in)

	// fan in: merge their outputs into one channel
	sum := 0
	for n := range merge(ctx, a, b, c) {
		sum += n
	}
	fmt.Println("sum of squares:", sum, "in", time.Since(start).Round(50*time.Millisecond))
}
```

Đọc `merge` theo bốn bước. (1) Nó tạo một channel đầu ra là `out`. (2) Với mỗi channel đầu vào `c`, nó mở một goroutine chép từng giá trị từ `c` sang `out`, hoặc thoát sớm nếu context bị hủy. (3) Mỗi goroutine chép gọi `wg.Done()` khi thoát. (4) Một goroutine cuối chờ `WaitGroup` rồi mới đóng `out`, cùng lý do như pool: đóng sớm hơn thì một goroutine chép có thể gửi vào channel đã đóng. Mỗi goroutine chép dùng `c` của vòng lặp. Việc đó an toàn từ Go 1.22, vì mỗi vòng có biến `c` riêng (và `i` hay `id` riêng ở các ví dụ sau); [bài 7](/blog/go-goroutines-channels-select/) giải thích. Trong `main`, ba bản `square` cùng đọc từ một channel `in` (fan-out), và `merge` biến ba đầu ra thành một (fan-in). Mỗi bản ngủ 50 ms cho mỗi giá trị để đại diện cho việc chậm.

```text

```
</TerminalOutput>

Cái giá của fan-out là thứ tự. Giá trị có thể xong theo thứ tự khác với lúc vào, vì bản sao nhận giá trị nhanh sẽ vượt bản nhận giá trị chậm. Nếu thứ tự quan trọng, hãy gắn chỉ số vào mỗi giá trị rồi sắp xếp ở cuối, hoặc đừng fan-out stage đó.

Đường tắt: Việc hủy đến mọi goroutine chép qua cùng một `ctx`, và `defer cancel()` trong `main` đảm bảo nó chạy kể cả khi vòng lặp kết thúc sớm. Đường bình thường lại là chuỗi đóng channel: `gen` đóng `in`, mỗi `square` đóng đầu ra của nó, và `WaitGroup` trong `merge` đóng `out` khi cả ba đã xong.

## Giới hạn số việc chạy cùng lúc bằng semaphore

Đôi khi bạn không cần một pool worker sống lâu. Bạn có một danh sách việc, bạn thoải mái mở một goroutine cho mỗi việc, và chỉ cần giới hạn có bao nhiêu việc thật sự làm cùng lúc. Một channel có buffer chứa struct rỗng làm được. Dung lượng channel là giới hạn. Gửi vào là lấy một slot, nhận ra là trả slot.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func main() {
	sem := make(chan struct{}, 3) // at most 3 tasks at once
	var wg sync.WaitGroup

	for i := 1; i <= 8; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			sem <- struct{}{}        // take a slot; blocks when all 3 are taken
			defer func() { <-sem }() // give the slot back
			fmt.Println("task", i, "running, slots in use:", len(sem))
			time.Sleep(100 * time.Millisecond)
		}()
	}
	wg.Wait()
	fmt.Println("done")
}
```

`chan struct{}` là channel mà giá trị không mang dữ liệu (struct rỗng không tốn bộ nhớ), cách quen thuộc để viết "chỉ là một cái thẻ". Với dung lượng 3, lệnh `sem <- struct{}{}` thứ tư bị chặn cho đến khi một task chạy `<-sem`. Dòng `defer func() { <-sem }()` trả slot kể cả khi task thoát sớm. Nó được bọc trong một hàm nhỏ vì `defer` cần một lời gọi hàm, còn `<-sem` đứng một mình là một phép nhận, không phải lời gọi. Mỗi goroutine cũng có `i` riêng, cùng quy tắc Go 1.22 như trong `merge`. Còn `len(sem)` là số slot đang dùng ngay lúc này, chương trình in ra để bạn thấy giới hạn hoạt động.

Khi nào dùng cái nào? Worker pool hợp hơn khi mỗi worker có chi phí khởi tạo (một kết nối database, một buffer) mà bạn muốn tái dùng, hoặc khi bạn muốn có hàng đợi trước các worker. Semaphore hợp hơn với kiểu "làm N việc này, mỗi lần tối đa K việc" và không có trạng thái nào để chia sẻ.

Đường tắt: Câu `defer` trả slot chính là toàn bộ câu chuyện tắt: task xong hay return sớm thì slot đều được trả. Một panic không ai recover (bài 5) làm sập cả chương trình, nên sau panic slot chỉ có ý nghĩa nếu task tự recover nó. `WaitGroup` báo cho `main` biết khi mọi task đã xong. Để thôi chờ slot khi bên gọi bỏ cuộc, hãy thay lệnh gửi trơn bằng một `select` có thêm `<-ctx.Done()`, như trong pipeline.

## Giới hạn tốc độ

Giới hạn số việc chạy cùng lúc chặn số lệnh gọi đang bay. Giới hạn tốc độ chặn tần suất lệnh gọi bắt đầu. Hai bài toán khác nhau: một API cho 5 request mỗi giây không quan tâm bạn chỉ có 2 request đang bay, nếu bạn gửi một loạt 50 request trong giây đầu.

Thư viện chuẩn đã có bản đơn giản nhất. `time.Ticker` gửi thời điểm hiện tại lên channel `C` sau mỗi khoảng cố định, nên nhận từ `C` nghĩa là "chờ đến slot kế tiếp".

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	ticker := time.NewTicker(200 * time.Millisecond)
	defer ticker.Stop()

	start := time.Now()
	for i := 1; i <= 5; i++ {
		<-ticker.C // wait for the next tick
		fmt.Printf("call %d at %v\n", i, time.Since(start).Round(50*time.Millisecond))
	}
}
```

`defer ticker.Stop()` giải phóng ticker khi hàm return. Ticker không dồn các tick lại cho bên nhận chậm: channel của nó chứa một tick, và các tick sau bị bỏ cho đến khi bên nhận theo kịp. Nên ticker cho bạn nhịp đều, không phải một loạt bù.

Khi cần cho phép bùng nổ, hoặc một giới hạn dùng chung cho nhiều goroutine, hãy dùng package `rate`. Nó nằm trong `golang.org/x/time`, một repo mở rộng do đội Go duy trì nhưng không thuộc thư viện chuẩn, nên bạn thêm nó vào module bằng `go get` trước (cùng lệnh từ [bài 1](/blog/go-first-program-modules-packages/)).

```text
go get golang.org/x/time/rate
```

```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/time/rate"
)

func main() {
	// one call every 200ms, bursts of at most 1
	limiter := rate.NewLimiter(rate.Every(200*time.Millisecond), 1)
	ctx := context.Background()

	start := time.Now()
	for i := 1; i <= 5; i++ {
		if err := limiter.Wait(ctx); err != nil {
			fmt.Println("stopped:", err)
			return
		}
		fmt.Printf("call %d at %v\n", i, time.Since(start).Round(50*time.Millisecond))
	}
}
```

`rate.NewLimiter(rate.Every(200*time.Millisecond), 1)` cho phép một sự kiện mỗi 200 ms, burst là 1. Burst là 5 thì sau một lúc yên ắng cho năm lệnh gọi đi cùng lúc. `limiter.Wait(ctx)` chặn đến khi lệnh gọi kế tiếp được phép, và trả về lỗi nếu context bị hủy trước.

Đường tắt: Bản ticker dừng bằng `ticker.Stop()`. Limiter không có goroutine hay timer riêng để dừng, nên lối thoát là context bạn truyền cho `Wait`: hủy nó thì `Wait` trả về lỗi thay vì chặn, giúp bên gọi rời khỏi một hàng dài các request đang chờ.

## errgroup: chạy một nhóm và dừng khi có lỗi đầu tiên

Worker pool và pipeline có một lỗ hổng. Nếu một task lỗi, các task khác biết bằng cách nào? Bạn có thể thêm một channel lỗi, một biến dùng chung sau một cái khóa, và một hàm cancel, rồi nối tất cả cho đúng. Sách 100 Go Mistakes xếp việc tự làm tay này vào danh sách lỗi, vì đội Go đã có sẵn package cho việc đó: `errgroup`.

Giống `rate`, nó nằm trong `golang.org/x`, nên thêm bằng `go get`.

```text
go get golang.org/x/sync/errgroup
```

`errgroup.Group` có hai phương thức bạn cần. `g.Go(f)` chạy `f`, một hàm trả về `error`, trong một goroutine mới. `g.Wait()` chặn đến khi tất cả xong và trả về lỗi khác nil đầu tiên. `errgroup.WithContext` còn cho bạn một context bị hủy khi có hàm nào trả về lỗi, để các task khác dừng sớm. `g.SetLimit(3)` giới hạn số task chạy cùng lúc, và làm `g.Go` bị chặn khi chạm giới hạn, nên semaphore ở phần trước có sẵn trong đó.

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func fetch(ctx context.Context, id int) error {
	select {
	case <-time.After(time.Duration(id) * 100 * time.Millisecond):
		if id == 2 {
			return errors.New("fetch 2: upstream returned 503")
		}
		fmt.Println("fetch", id, "ok")
		return nil
	case <-ctx.Done():
		fmt.Println("fetch", id, "cancelled:", ctx.Err())
		return ctx.Err()
	}
}

func main() {
	g, ctx := errgroup.WithContext(context.Background())
	g.SetLimit(3) // at most 3 goroutines at once

	for id := 1; id <= 5; id++ {
		g.Go(func() error {
			return fetch(ctx, id)
		})
	}

	if err := g.Wait(); err != nil {
		fmt.Println("group failed:", err)
	}
}
```

Task `id` mất `id` nhân 100 ms. Task 2 lỗi sau 200 ms, khi 3, 4 và 5 còn đang chờ hoặc sắp bắt đầu. Lỗi đó hủy `ctx`, và mỗi task đang chờ trong một `select` có `<-ctx.Done()`, nên nó thoát ngay thay vì ngồi hết thời gian của mình.

## Chọn mẫu nào

| Mẫu | Giải quyết việc gì | Dừng khi | Cần để ý |
|---|---|---|---|
| Worker pool | Giới hạn lượng việc chạy cùng lúc, có hàng đợi phía trước | channel jobs bị đóng, hoặc context bị hủy (bản dừng sớm ở trên) | bên tiêu thụ ngừng đọc `results` làm worker kẹt lại |
| Pipeline | Chia việc thành các bước nhỏ có backpressure | stage đầu đóng, hoặc context bị hủy | stage có lệnh gửi mà không `select` thêm `ctx.Done()` |
| Fan-out và fan-in | Tăng tốc một stage chậm | mọi bản sao đã return, rồi merge đóng | thứ tự đầu ra không còn là thứ tự đầu vào |
| Semaphore channel | Tối đa K task làm việc thật cùng lúc | mỗi task trả slot bằng `defer` | lấy slot bên trong goroutine vẫn mở hết các goroutine |
| Ticker hoặc `rate.Limiter` | Giới hạn tần suất lệnh gọi bắt đầu | `Stop()`, hoặc context đưa cho `Wait` | nhầm giới hạn tốc độ với giới hạn số việc chạy cùng lúc |
| `errgroup` | Chạy một nhóm và giữ lỗi đầu tiên | `Wait` return sau khi mọi task return | task bỏ qua `ctx` đã bị hủy |

## Key takeaways

- Worker pool là N goroutine cùng `range` trên một channel jobs. Số worker là mức trần của lượng việc chạy cùng lúc, và channel là hàng đợi phía trước.
- Producer đóng channel jobs. Một goroutine riêng chờ `WaitGroup` rồi đóng channel results.
- Trong pipeline, mỗi lệnh gửi có thể bị chặn đều `select` thêm `ctx.Done()`. Stage nào không làm vậy sẽ để goroutine kẹt lại khi bên tiêu thụ bỏ đi sớm.
- Fan-out chia một channel cho nhiều goroutine. Fan-in gộp nhiều channel thành một, và không giữ thứ tự đầu vào.
- `chan struct{}` có buffer là một semaphore: gửi để lấy slot, nhận để trả slot, và trả bằng `defer`.
- Giới hạn số việc chạy cùng lúc và giới hạn tốc độ là hai chuyện khác nhau. Dùng `time.Ticker` hoặc `rate.Limiter` cho tốc độ.
- `errgroup` chạy một nhóm, trả về lỗi đầu tiên và hủy context của nhóm. Task phải nhìn vào context đó thì việc hủy mới có tác dụng. `golang.org/x/sync` và `golang.org/x/time` là các module riêng, thêm bằng `go get`.
