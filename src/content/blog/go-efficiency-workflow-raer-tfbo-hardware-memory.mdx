> "We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%."
> &mdash; *Donald Knuth*, *Structured Programming with go to Statements* (1974)

Google engineers Jeffrey Dean and Luiz André Barroso describe an idealized service where each server answers slowly, in more than one second, on only 1 request in 100. That sounds fine. Then a page needs answers from 100 of those servers at once, and [63% of pages take more than a second](https://research.google/pubs/the-tail-at-scale/). Nobody's code got worse. The page just waits for its slowest part, and with 100 parts the slowest one is usually slow.

The usual reaction to a slow service is to run more copies of it. Here that does nothing for those 63%. This post is about what to do instead: decide **whether** a piece of code needs tuning, **where** to change things, and **when to stop**. Writing a faster loop is the easy part. Knowing whether it was worth writing is the skill.

<Callout type="note" title="TL;DR">
More pods add capacity but leave tail latency alone. Before tuning anything, write a **RAER** (Resource-Aware Efficiency Requirements): the operation, the data size, a p99 latency budget and a memory budget. Measure against it. If you are within budget, stop. If not, find the bottleneck, change **one** of the five levels, and run the **TFBO** loop (Test, Fix, Benchmark, Optimize) again, starting with tests.
</Callout>

<Concepts>

- **Pod**: one running copy of a service in Kubernetes. Adding pods means running more copies.
- **Latency and p99**: latency is how long one request takes. The p99 is the time that 99% of requests beat, so 1 request in 100 is slower than it.
- **Fan-out**: one incoming request that triggers many calls to other servers and waits for all of them.
- **Tail latency**: the slow end of the latency distribution, the p99 and beyond.

</Concepts>

## Why more pods do not fix tail latency

A pod is one running copy of your service. A load balancer spreads requests across pods, so adding pods means each pod gets fewer requests. That shortens queues and raises the total traffic you can serve. It is called **capacity**.

It does not change how long one request takes on one pod. If a request is slow because it parses a large body, allocates too much, or waits on a lock, a new pod runs the same code and is slow in the same way. The numbers in the Google paper make this visible. Here is the arithmetic as a short Go program. A page is slow if at least one of its servers is slow, which is 1 minus the chance that all of them are fast.

```go
package main

import (
	"fmt"
	"math"
)

func main() {
	slow := 0.01 // each server is slow on 1 request in 100
	for _, servers := range []int{1, 10, 100} {
		// A page is slow if at least one of its servers is slow:
		// 1 minus the chance that every server is fast.
		pageSlow := 1 - math.Pow(1-slow, float64(servers))
		fmt.Printf("%3d servers per page: %5.1f%% of pages are slow\n", servers, pageSlow*100)
	}
}
```

`math.Pow(x, y)` raises `x` to the power `y`. `%5.1f%%` prints a float with one decimal, and `%%` prints a literal percent sign.

```text

100 servers per page:  63.4% of pages are slow
```

<GoP15TailFanout />

Doubling the pods does not move the `0.01` in that program. Only making each server slow less often does, which means changing the code or what it waits for. That is why "just scale it" has a ceiling for latency, even when it works for load.

Scaling can also be a trap on the cost side. The Thanos project (a long-term store for Prometheus metrics) once hit this. Its first compaction code was deliberately naive and assumed one CPU and a small amount of memory. Users hit compaction that was too slow to keep up with incoming data, or that used hundreds of GB of memory per operation. Bartłomiej Płotka, who worked on the project, writes in *Efficient Go* that the team discussed a scheduler that would hand compaction jobs to many machines, and that this would probably have doubled or tripled the complexity of the system. Instead, a few days of work on the algorithm and code made compaction twice as fast and let it stream data from disk with little peak memory. A few years on, the project still had no distributed compaction beyond simple sharding.

Scaling out is fine when you need it. It also brings network calls, partial failures and extra moving parts, and a few days in the code can sometimes avoid all of that. You can only tell which case you are in by measuring.

<Concepts>

- **Capacity**: how much total traffic a service can handle. More pods raise it.
- **Tail amplification**: when a request waits on `k` parts, the chance that at least one is slow is `1 - (1 - p)^k`. It grows quickly with `k`.

</Concepts>

## Efficiency is not the same as speed

People say "performance" for many things. *Efficient Go* splits it into three: **accuracy** (how many wrong results you produce), **speed** (how fast the work finishes, as latency or throughput) and **efficiency** (how much extra work and resources you spent). Płotka's example of efficiency: fetching 64 bytes of useful data from disk but allocating 420 bytes of memory to do it. That is about 15% memory efficiency (64 of 420 bytes), whatever the speed was.

Speed and efficiency often move together, because a program that does less work usually finishes sooner. They can also split apart. *Efficient Go* gives a search that reads data from disk a million times. A faster disk might cut latency to a tenth, but making the code read the data a few times instead would beat that, and it costs nothing in hardware. Doing less work is usually the better first move.

There is a second reason to aim at efficiency first. Speed is fragile: it depends on the machine, other processes, thermal limits and the network. The amount of work your code does, such as how many database calls it makes, is something you control and it travels with the code to any machine.

Knuth's 97/3 quote fits here. Most code does not need tuning, and a small part does. The risk is not tuning too much or too little by itself. The risk is tuning without knowing which part is which. *Efficient Go* names this directly: programmers are bad at guessing which part of a program uses the most resources, and in most programs a small share of operations (the Pareto rule, often 20%) accounts for most of the cost.

A small note on Big-O. It says how the work grows as the input grows, not how long one step takes. Two approaches with the same growth can differ a lot in real time, and on small inputs a "worse" one can win. So a Big-O argument does not replace a measurement. [Go benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/) shows how to measure across input sizes.

One cost is left for the hardware and runtime post: why a value lives on the stack or the heap, and what that costs. It has its own home in [Go hardware and GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/).

<Concepts>

- **Accuracy, speed, efficiency**: wrong results, time taken, and wasted resources. They are three different things you can improve or give up.
- **Efficiency ratio**: useful work divided by total work or resources used, for one named resource such as memory.

</Concepts>

## RAER: write the budget first

"Make it faster" is not a goal you can finish. A **RAER** (Resource-Aware Efficiency Requirements) is a short written budget for one operation. *Efficient Go* suggests an entry with the operation, the size and shape of the data, the maximum latency, and limits for the resources that matter, usually CPU and memory. You do not need an entry for every function. Start with the operations that are used the most or cost the most, and add more only when they matter.

The point of the numbers is a stop rule. With a budget, step one of any tuning job is to measure, and if you are inside the budget, you are done.

### A RAER for GET /todos

The `Todo` service from the HTTP post has `GET /todos`, which returns every todo as JSON. Here is a RAER for it. I picked these numbers as an example for this post. In a real project they would come from your users or from your own capacity plan.

```text
Operation:    GET /todos (list all todos as JSON)
Dataset:      1,000 todos
p99 latency:  5 ms or less (handler only, measured in-process)
Memory:       200 KB or less allocated per request
CPU:          1 core
```

Note that the dataset is part of the budget. "5 ms" means nothing until you say for how much data.

### Measure it

To check the budget we need numbers. The program below runs `GET /todos` 2,000 times against an in-memory server with `n` todos, then prints the p50 (the median), the p99 and the memory allocated per request. It is a rough measurement tool, not a proper benchmark. [Go benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/) covers the right way to measure.

First the service pieces, copied unchanged from the HTTP post (`Todo`, a mutex-guarded `store` with `add` and `list`, `server`, `listTodos` and `writeJSON`). There is no middleware here, only the router.

```go
package main

import (
	"encoding/json"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
	"runtime"
	"slices"
	"strconv"
	"sync"
	"time"
)

type Todo struct {
	ID    int    `json:"id"`
	Title string `json:"title"`
	Done  bool   `json:"done"`
}

type store struct {
	mu    sync.Mutex
	todos []Todo
}

func (s *store) add(title string) Todo {
	s.mu.Lock()
	defer s.mu.Unlock()
	t := Todo{ID: len(s.todos) + 1, Title: title}
	s.todos = append(s.todos, t)
	return t
}

func (s *store) list() []Todo {
	s.mu.Lock()
	defer s.mu.Unlock()
	out := make([]Todo, len(s.todos))
	copy(out, s.todos)
	return out
}

type server struct{ store *store }

func (s *server) listTodos(w http.ResponseWriter, r *http.Request) {
	writeJSON(w, http.StatusOK, s.store.list())
}

func writeJSON(w http.ResponseWriter, status int, v any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	if err := json.NewEncoder(w).Encode(v); err != nil {
		slog.Error("write response", "err", err)
	}
}
```

Then the measuring `main`. It reads `n` from the command line (`os.Args[1]`, turned into an int by `strconv.Atoi`) and builds the store. `httptest.NewRequest` and `httptest.NewRecorder` are from the standard library: they let the router handle a request without a network, as in the [HTTP post](/blog/go-http-service-net-http-json-middleware/). `runtime.ReadMemStats` fills in counters about the heap, and `TotalAlloc` is the total bytes allocated so far, so its difference divided by the number of requests is the allocation per request. `slices.Sort` puts the times in order so we can pick the middle one and the 99th percentile. `for range requests` loops that many times ([Go memory](/blog/go-memory-data-types-slices-maps-strings/) shows this integer range).

```go
func main() {
	n, _ := strconv.Atoi(os.Args[1])
	s := &server{store: &store{}}
	for i := 1; i <= n; i++ {
		s.store.add("todo " + strconv.Itoa(i))
	}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /todos", s.listTodos)

	const requests = 2000
	times := make([]time.Duration, 0, requests)
	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)
	for range requests {
		req := httptest.NewRequest("GET", "/todos", nil)
		rec := httptest.NewRecorder()
		start := time.Now()
		mux.ServeHTTP(rec, req)
		times = append(times, time.Since(start))
	}
	runtime.ReadMemStats(&after)

	slices.Sort(times)
	fmt.Printf("todos=%d requests=%d\n", n, requests)
	fmt.Printf("p50=%v p99=%v\n", times[requests/2], times[requests*99/100])
	fmt.Printf("allocated per request: %d KB\n", (after.TotalAlloc-before.TotalAlloc)/requests/1024)
}
```

The recorder keeps the response body in memory, so the allocation figure includes that copy of the response. That is fine for a comparison between sizes, which is what we want.

At 1,000 todos, which is the dataset the RAER names, the handler is far inside the budget: 352 µs against 5 ms, 86 KB against 200 KB. By the stop rule there is nothing to do. At 10,000 todos the p99 still passes (3.06 ms) but memory is five times over (1,027 KB). At 100,000 both fail. Memory and latency both grow roughly with the number of todos, and the budget told us which of the two broke first.

- **RAER (Resource-Aware Efficiency Requirements)**: a written budget for one operation: the operation, the data size, a p99 latency limit, and CPU and memory limits.
- **Stop rule**: if the measurement is inside the RAER, you stop. No more tuning.
- **p50 and p99**: the median request time, and the time that 99 of 100 requests beat.

## Five levels to optimize at

Say `GET /todos` misses its budget at 10,000 todos. Where do you start? *Efficient Go* lists five **optimization design levels**, from the top down: the system, the algorithm and data structure, the code, the operating system, and the hardware. Each one is a place where you can make the work cheaper.

<GoP15Levels />

Here is the reasoning for starting at the top. It points to older studies that find speedups of about 10 to 20 times are often possible at any one level. Changes at a higher level can also make lower ones less valuable. If you serve 50 todos per request instead of 10,000, then the effort you spent shaving allocations from the 10,000-item path was wasted. The opposite does not hold. A code-level fix does not remove the need for a page limit.

Some levels are not yours to change. As a Go developer you usually cannot choose the operating system's scheduler or the CPU, though you can set container limits and understand what they do. And Płotka notes that a level where you already got a 10 to 20 times gain gets expensive to push further, which is the point where looking at another level pays.

For the rest of this series the levels line up like this: [Go production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/) and [Go hardware and GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/) are about levels 4 and 5, [Go optimization patterns](/blog/go-three-rs-optimization-patterns-streaming-pooling/) about levels 2 and 3.

<Concepts>

- **Optimization design level**: one of five places to make work cheaper: system, algorithm and data structure, code, operating system, hardware.
- **One level at a time**: change a single level in each round, so you know what helped.

</Concepts>

## TFBO: the loop that keeps you honest

Tuning a program can break it. A change that saves a copy can also share a slice that two goroutines now write to. *Efficient Go* handles this with a nine-step flow it calls **TFBO**: Test, Fix, Benchmark, Optimize. It splits the work into two phases that never mix.

<GoP15TfboLoop />

**The functionality phase (steps 1 to 3).** Write tests for what the code must do and run them. If they pass, move on. If they do not, fix the code, with no tuning yet, and test again. Tests first, because, as *Efficient Go* quotes, it is far easier to make a correct program fast than to make a fast program correct.

**The efficiency phase (steps 4 to 8).** Measure a baseline, which is what we did above with the program that printed p99 and KB. Then compare it to the RAER (step 5). Inside budget? Release (step 9). Not? Find the bottleneck (step 6), pick one level (step 7) and optimize (step 8). Then go back to step 1: run the tests on the optimized code, then run the same measurement and compare it to the baseline.

Two habits in that loop save the most pain:

1. **Find the bottleneck before you change anything.** We are bad at guessing. For `GET /todos` at 10,000 todos, the budget says memory per request is the problem, but it does not say which line allocates. A profile does, and [Go profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/) shows how to read one.
2. **Change one level per round, and test after every change.** Płotka admits to skipping the tests after a small change and then not being able to tell which of several changes broke things, which meant reverting all of them. A scoped test run after each attempt is cheap.

For our service the walk goes like this. Step 4 was the measurement above. Step 5 says memory is over budget at 10,000 todos. Step 6 needs a profile, which we leave for the profiling post. Step 7 is a choice between levels: serving a page of todos is a system-level change, while encoding the JSON more cheaply is a code-level one. Which one is right depends on what the users need, and that is why the RAER names the dataset in the first place.

Each round ends with the same question: are we within the budget now? When the answer is yes, stop. Rewriting readable code to save a few more microseconds that nobody asked for is the kind of premature work Knuth warned about.

Next in the series: [Go hardware and GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/) for what happens under the budget, [Go benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/) for measuring properly, [Go profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/) for step 6, and [Go optimization patterns](/blog/go-three-rs-optimization-patterns-streaming-pooling/) for step 8.

<Concepts>

- **TFBO (Test, Fix, Benchmark, Optimize)**: a nine-step loop: test and fix until correct, measure against the RAER, then optimize one level and go back to the tests.
- **Baseline**: the measurement taken before you change anything. Every later number is compared to it.
- **Bottleneck**: the place where most of a resource is spent. Programs usually have only a few.

</Concepts>

## Key takeaways

- **More pods add capacity, not speed for one request.** If a request waits on many parts, the chance of at least one slow part is `1 - (1 - p)^k`, and new pods do not change `p`.
- **Efficiency is doing less work.** Fixing the algorithm or the code first can avoid the cost and complexity of scaling out, as the Thanos compaction story shows.
- **Write a RAER before tuning.** Operation, data size, p99 latency, memory and CPU. The data size is part of the budget.
- **Inside the budget means stop.** Outside it, find the bottleneck, change one of the five levels and run the TFBO loop again, starting with the tests.
- **Start at the top.** Changes to the system or the algorithm can make code-level work unnecessary.

Trước khi tối ưu bất cứ thứ gì, hãy viết một **RAER** (Resource-Aware Efficiency Requirements, yêu cầu hiệu năng có tính tới tài nguyên): thao tác, cỡ dữ liệu, ngân sách độ trễ p99 và ngân sách bộ nhớ. Đo theo nó. Nếu đã trong ngân sách thì dừng. Nếu chưa, tìm điểm nghẽn, đổi **một** trong năm tầng, rồi chạy lại vòng **TFBO** (Test, Fix, Benchmark, Optimize), bắt đầu bằng test.
</Callout>

<Concepts>

- **Pod**: một bản sao đang chạy của service trong Kubernetes. Thêm pod nghĩa là chạy thêm bản sao.
- **Độ trễ (latency) và p99**: độ trễ là thời gian một request mất. p99 là mốc thời gian mà 99% request nhanh hơn, tức cứ 100 request có 1 cái chậm hơn mốc này.
- **Fan-out**: một request đến kéo theo nhiều lệnh gọi sang server khác và chờ tất cả.
- **Độ trễ đuôi (tail latency)**: phần chậm của phân phối độ trễ, từ p99 trở lên.

</Concepts>

## Vì sao thêm pod không chữa được độ trễ đuôi

Pod là một bản sao đang chạy của service. Bộ cân bằng tải (load balancer) chia request cho các pod, nên thêm pod nghĩa là mỗi pod nhận ít request hơn. Hàng đợi ngắn đi và tổng lưu lượng phục vụ được tăng lên. Cái này gọi là **công suất (capacity)**.

Nó không đổi thời gian một request mất trên một pod. Nếu request chậm vì phải parse body lớn, cấp phát quá nhiều hoặc chờ một lock, thì pod mới chạy cùng đoạn code đó và chậm y như vậy. Con số trong bài báo của Google cho thấy rõ điều này. Phép tính dưới đây viết thành chương trình Go ngắn. Một trang chậm khi ít nhất một server của nó chậm, tức là 1 trừ đi xác suất tất cả đều nhanh.

```go
package main

import (
	"fmt"
	"math"
)

func main() {
	slow := 0.01 // each server is slow on 1 request in 100
	for _, servers := range []int{1, 10, 100} {
		// A page is slow if at least one of its servers is slow:
		// 1 minus the chance that every server is fast.
		pageSlow := 1 - math.Pow(1-slow, float64(servers))
		fmt.Printf("%3d servers per page: %5.1f%% of pages are slow\n", servers, pageSlow*100)
	}
}
```

`math.Pow(x, y)` lấy `x` mũ `y`. `%5.1f%%` in số thực với một chữ số thập phân, còn `%%` in ra dấu phần trăm.

```text

100 servers per page:  63.4% of pages are slow
```

Nhân đôi số pod không làm thay đổi con số `0.01` trong chương trình đó. Chỉ có làm cho mỗi server ít chậm hơn mới đổi được, nghĩa là sửa code hoặc sửa thứ nó phải chờ. Vì vậy "cứ scale lên" có trần đối với độ trễ, dù với tải thì nó hiệu quả.

Scale cũng có thể là cái bẫy về chi phí. Dự án Thanos (kho lưu trữ dài hạn cho metric của Prometheus) từng gặp chuyện này. Đoạn code compaction (gộp dữ liệu) đầu tiên được viết đơn giản có chủ đích, giả định một CPU và rất ít bộ nhớ. Người dùng gặp tình trạng compaction chậm không theo kịp dữ liệu đến, hoặc tốn hàng trăm GB bộ nhớ cho mỗi thao tác. Bartłomiej Płotka, người làm trong dự án, viết trong *Efficient Go* rằng nhóm đã bàn việc dựng một bộ lập lịch giao việc compaction cho nhiều máy, và việc đó nhiều khả năng làm độ phức tạp của hệ thống tăng gấp đôi hoặc gấp ba. Thay vào đó, vài ngày làm lại thuật toán và code đã giúp compaction nhanh gấp đôi và đọc dữ liệu từ đĩa theo dòng với bộ nhớ đỉnh rất thấp. Nhiều năm sau, dự án vẫn chưa có compaction phân tán nào ngoài sharding đơn giản.

Scale ngang vẫn ổn khi bạn thật sự cần. Nhưng nó kéo theo lệnh gọi mạng, lỗi một phần và thêm nhiều bộ phận chuyển động, và đôi khi vài ngày trong code tránh được tất cả những thứ đó. Muốn biết mình đang ở trường hợp nào thì phải đo.

<Concepts>

- **Công suất (capacity)**: tổng lưu lượng service xử lý được. Thêm pod làm nó tăng.
- **Khuếch đại độ trễ đuôi (tail amplification)**: khi một request chờ `k` phần, xác suất ít nhất một phần chậm là `1 - (1 - p)^k`. Nó tăng rất nhanh theo `k`.

</Concepts>

## Hiệu quả không đồng nghĩa với nhanh

Người ta dùng chữ "performance" cho nhiều thứ. *Efficient Go* tách nó làm ba: **độ chính xác (accuracy)**, tức số kết quả sai; **tốc độ (speed)**, tức việc xong nhanh thế nào, đo bằng độ trễ hoặc thông lượng; và **hiệu quả (efficiency)**, tức mình tốn thêm bao nhiêu việc và tài nguyên. Ví dụ của Płotka về hiệu quả: lấy 64 byte dữ liệu có ích từ đĩa nhưng cấp phát 420 byte bộ nhớ để làm việc đó. Hiệu quả bộ nhớ khi đó khoảng 15% (64 trên 420 byte), bất kể tốc độ ra sao.

Tốc độ và hiệu quả thường đi cùng nhau, vì chương trình làm ít việc hơn thường xong sớm hơn. Nhưng chúng cũng có thể tách rời. *Efficient Go* nêu một phép tìm kiếm đọc dữ liệu từ đĩa cả triệu lần. Đĩa nhanh hơn có thể cắt độ trễ xuống một phần mười, nhưng sửa code để chỉ đọc dữ liệu vài lần còn thắng hơn, và không tốn đồng phần cứng nào. Làm ít việc hơn thường là nước đi đầu tiên tốt hơn.

Còn một lý do nữa để nhắm vào hiệu quả trước. Tốc độ rất mong manh: nó phụ thuộc vào máy, các tiến trình khác, giới hạn nhiệt và mạng. Lượng việc code của bạn làm, ví dụ gọi database bao nhiêu lần, là thứ bạn kiểm soát được và nó đi theo code sang mọi máy.

Câu 97/3 của Knuth hợp ở đây. Phần lớn code không cần tối ưu, và một phần nhỏ thì cần. Rủi ro không nằm ở chuyện tối ưu nhiều hay ít, mà ở chỗ tối ưu mà không biết phần nào là phần nào. *Efficient Go* nói thẳng: lập trình viên đoán rất tệ phần nào của chương trình dùng nhiều tài nguyên nhất, và ở hầu hết chương trình, một phần nhỏ các thao tác (quy tắc Pareto, thường quanh 20%) chiếm phần lớn chi phí.

Một lưu ý nhỏ về Big-O. Nó nói công việc tăng thế nào khi đầu vào lớn lên, không nói một bước mất bao lâu. Hai cách có cùng độ tăng có thể chênh nhau rất nhiều về thời gian thực, và với đầu vào nhỏ thì cách "tệ hơn" vẫn có thể thắng. Nên lập luận Big-O không thay được một lần đo. [Benchmarking trong Go](/blog/go-observability-metrics-microbenchmarks-benchstat/) chỉ cách đo theo nhiều cỡ đầu vào.

Còn một chi phí dành cho bài về phần cứng và runtime: vì sao một giá trị nằm trên stack hay heap, và nó tốn gì. Chủ đề đó có nhà riêng ở [Phần cứng và GC trong Go](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/).

<Concepts>

- **Chính xác, tốc độ, hiệu quả (accuracy, speed, efficiency)**: kết quả sai, thời gian mất và tài nguyên lãng phí. Đây là ba thứ khác nhau mà bạn có thể cải thiện hoặc đánh đổi.
- **Tỉ lệ hiệu quả (efficiency ratio)**: công việc có ích chia cho tổng công việc hay tài nguyên đã dùng, tính cho một tài nguyên cụ thể như bộ nhớ.

</Concepts>

## RAER: viết ngân sách trước

"Làm cho nhanh hơn" không phải mục tiêu mà bạn có thể hoàn thành. **RAER** (Resource-Aware Efficiency Requirements) là một ngân sách ngắn, viết ra giấy, cho một thao tác. *Efficient Go* gợi ý một mục gồm: thao tác, cỡ và hình dạng dữ liệu, độ trễ tối đa, và giới hạn của các tài nguyên đáng quan tâm, thường là CPU và bộ nhớ. Bạn không cần một mục cho mọi hàm. Hãy bắt đầu với các thao tác được dùng nhiều nhất hoặc tốn kém nhất, rồi thêm khi nào thật sự cần.

Tác dụng của các con số là một quy tắc dừng. Có ngân sách rồi, bước đầu của mọi đợt tối ưu là đo, và nếu đã nằm trong ngân sách thì xong việc.

### RAER cho GET /todos

`Todo` service ở bài HTTP có `GET /todos`, trả về mọi todo dưới dạng JSON. Đây là một RAER cho nó. Các con số này mình chọn làm ví dụ cho bài. Trong dự án thật, chúng đến từ người dùng hoặc từ kế hoạch công suất của bạn.

```text
Operation:    GET /todos (list all todos as JSON)
Dataset:      1,000 todos
p99 latency:  5 ms or less (handler only, measured in-process)
Memory:       200 KB or less allocated per request
CPU:          1 core
```

Để ý rằng cỡ dữ liệu là một phần của ngân sách. "5 ms" vô nghĩa cho tới khi bạn nói rõ là với bao nhiêu dữ liệu.

### Đo thử

Để kiểm tra ngân sách ta cần số đo. Chương trình dưới đây chạy `GET /todos` 2.000 lần trên một server trong bộ nhớ có `n` todo, rồi in p50 (trung vị), p99 và bộ nhớ cấp phát cho mỗi request. Đây là công cụ đo thô, không phải benchmark đúng nghĩa. [Benchmarking trong Go](/blog/go-observability-metrics-microbenchmarks-benchstat/) nói về cách đo đúng.

Trước hết là các mảnh của service, chép nguyên từ bài HTTP (`Todo`, `store` có mutex với `add` và `list`, `server`, `listTodos` và `writeJSON`). Ở đây không có middleware, chỉ có router.

```go
package main

import (
	"encoding/json"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
	"runtime"
	"slices"
	"strconv"
	"sync"
	"time"
)

type Todo struct {
	ID    int    `json:"id"`
	Title string `json:"title"`
	Done  bool   `json:"done"`
}

type store struct {
	mu    sync.Mutex
	todos []Todo
}

func (s *store) add(title string) Todo {
	s.mu.Lock()
	defer s.mu.Unlock()
	t := Todo{ID: len(s.todos) + 1, Title: title}
	s.todos = append(s.todos, t)
	return t
}

func (s *store) list() []Todo {
	s.mu.Lock()
	defer s.mu.Unlock()
	out := make([]Todo, len(s.todos))
	copy(out, s.todos)
	return out
}

type server struct{ store *store }

func (s *server) listTodos(w http.ResponseWriter, r *http.Request) {
	writeJSON(w, http.StatusOK, s.store.list())
}

func writeJSON(w http.ResponseWriter, status int, v any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	if err := json.NewEncoder(w).Encode(v); err != nil {
		slog.Error("write response", "err", err)
	}
}
```

Rồi đến `main` làm nhiệm vụ đo. Nó đọc `n` từ dòng lệnh (`os.Args[1]`, đổi sang số nguyên bằng `strconv.Atoi`) và dựng store. `httptest.NewRequest` và `httptest.NewRecorder` thuộc thư viện chuẩn: chúng cho router xử lý một request mà không cần mạng, như ở [bài HTTP](/blog/go-http-service-net-http-json-middleware/). `runtime.ReadMemStats` điền các bộ đếm về heap, và `TotalAlloc` là tổng số byte đã cấp phát cho đến lúc đó, nên hiệu của nó chia cho số request chính là lượng cấp phát mỗi request. `slices.Sort` sắp xếp các thời gian để ta lấy được giá trị giữa và phân vị thứ 99. `for range requests` lặp đúng chừng đó lần ([Bộ nhớ trong Go](/blog/go-memory-data-types-slices-maps-strings/) có nói về range trên số nguyên).

```go
func main() {
	n, _ := strconv.Atoi(os.Args[1])
	s := &server{store: &store{}}
	for i := 1; i <= n; i++ {
		s.store.add("todo " + strconv.Itoa(i))
	}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /todos", s.listTodos)

	const requests = 2000
	times := make([]time.Duration, 0, requests)
	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)
	for range requests {
		req := httptest.NewRequest("GET", "/todos", nil)
		rec := httptest.NewRecorder()
		start := time.Now()
		mux.ServeHTTP(rec, req)
		times = append(times, time.Since(start))
	}
	runtime.ReadMemStats(&after)

	slices.Sort(times)
	fmt.Printf("todos=%d requests=%d\n", n, requests)
	fmt.Printf("p50=%v p99=%v\n", times[requests/2], times[requests*99/100])
	fmt.Printf("allocated per request: %d KB\n", (after.TotalAlloc-before.TotalAlloc)/requests/1024)
}
```

Recorder giữ body phản hồi trong bộ nhớ, nên con số cấp phát có tính cả bản sao phản hồi đó. Không sao, vì ta chỉ so sánh giữa các cỡ dữ liệu.

## Năm tầng để tối ưu

Giả sử `GET /todos` trượt ngân sách ở 10.000 todo. Bắt đầu từ đâu? *Efficient Go* liệt kê năm **tầng thiết kế tối ưu (optimization design levels)**, từ trên xuống: hệ thống, thuật toán và cấu trúc dữ liệu, code, hệ điều hành, và phần cứng. Mỗi tầng là một chỗ bạn có thể làm công việc rẻ đi.

<GoP15Levels />

Lý do bắt đầu từ trên cùng như sau. *Efficient Go* dẫn các nghiên cứu cũ cho thấy ở mỗi tầng thường có thể tăng tốc khoảng 10 đến 20 lần. Thay đổi ở tầng cao cũng có thể làm các tầng thấp bớt giá trị. Nếu mỗi request chỉ trả 50 todo thay vì 10.000, công sức bạn bỏ ra để bớt cấp phát trên đường đi 10.000 phần tử là uổng. Chiều ngược lại không đúng: sửa ở tầng code không làm giới hạn trang trở nên thừa.

Có tầng không phải do bạn quyết. Là lập trình viên Go, thường bạn không chọn được bộ lập lịch của hệ điều hành hay CPU, dù bạn đặt được giới hạn container và nên hiểu chúng làm gì. Płotka cũng lưu ý rằng một tầng đã cho bạn mức tăng 10 đến 20 lần thì rất tốn kém để vắt thêm, và đó là lúc nhìn sang tầng khác có lời.

Trong phần còn lại của series, các tầng ứng với: [Go trong production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/) và [Phần cứng và GC trong Go](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/) nói về tầng 4 và 5, [Mẫu tối ưu trong Go](/blog/go-three-rs-optimization-patterns-streaming-pooling/) nói về tầng 2 và 3.

<Concepts>

- **Tầng thiết kế tối ưu**: một trong năm chỗ để làm công việc rẻ đi: hệ thống, thuật toán và cấu trúc dữ liệu, code, hệ điều hành, phần cứng.
- **Mỗi lần một tầng**: mỗi vòng chỉ đổi một tầng, để biết cái gì có tác dụng.

</Concepts>

## TFBO: vòng lặp giữ bạn trung thực

Tối ưu có thể làm hỏng chương trình. Một thay đổi tiết kiệm được một lần sao chép cũng có thể chia sẻ một slice mà hai goroutine giờ cùng ghi. *Efficient Go* xử lý chuyện này bằng một quy trình chín bước gọi là **TFBO**: Test, Fix, Benchmark, Optimize. Nó chia việc thành hai giai đoạn không bao giờ trộn lẫn.

<GoP15TfboLoop />

**Giai đoạn chức năng (bước 1 đến 3).** Viết test cho điều code phải làm và chạy chúng. Nếu qua, đi tiếp. Nếu không, sửa code, chưa tối ưu gì cả, rồi test lại. Test trước, vì như *Efficient Go* trích dẫn, làm một chương trình đúng chạy nhanh dễ hơn nhiều so với làm một chương trình nhanh chạy đúng.

**Giai đoạn hiệu năng (bước 4 đến 8).** Đo mốc ban đầu, chính là việc ta vừa làm với chương trình in p99 và KB. Rồi so với RAER (bước 5). Trong ngân sách? Phát hành (bước 9). Chưa? Tìm điểm nghẽn (bước 6), chọn một tầng (bước 7) và tối ưu (bước 8). Sau đó quay lại bước 1: chạy test trên code đã tối ưu, rồi chạy lại đúng phép đo cũ và so với mốc ban đầu.

Hai thói quen trong vòng lặp này đỡ đau đầu nhất:

1. **Tìm điểm nghẽn trước khi đổi gì.** Ta đoán rất tệ. Với `GET /todos` ở 10.000 todo, ngân sách cho biết bộ nhớ mỗi request là vấn đề, nhưng không cho biết dòng nào cấp phát. Profile mới cho biết, và [Profiling trong Go](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/) chỉ cách đọc một profile.
2. **Mỗi vòng đổi một tầng, và test sau mỗi thay đổi.** Płotka thú nhận từng bỏ qua test sau một thay đổi nhỏ, rồi không biết trong vài thay đổi cái nào làm hỏng, và phải hoàn tác tất cả. Chạy một lượt test hẹp sau mỗi lần thử rất rẻ.

Với service của ta, quá trình đi như sau. Bước 4 là phép đo ở trên. Bước 5 cho thấy bộ nhớ vượt ngân sách ở 10.000 todo. Bước 6 cần một profile, mình để cho bài profiling. Bước 7 là chọn giữa các tầng: trả về từng trang todo là thay đổi ở tầng hệ thống, còn mã hóa JSON rẻ hơn là thay đổi ở tầng code. Cái nào đúng phụ thuộc người dùng cần gì, và đó là lý do RAER nêu cỡ dữ liệu ngay từ đầu.

Mỗi vòng kết thúc bằng cùng một câu hỏi: giờ đã trong ngân sách chưa? Khi câu trả lời là có thì dừng. Viết lại code dễ đọc để tiết kiệm thêm vài micro giây mà không ai yêu cầu chính là loại tối ưu sớm mà Knuth cảnh báo.

Tiếp theo trong series: [Phần cứng và GC trong Go](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/) cho những gì nằm dưới ngân sách, [Benchmarking trong Go](/blog/go-observability-metrics-microbenchmarks-benchstat/) để đo cho đúng, [Profiling trong Go](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/) cho bước 6, và [Mẫu tối ưu trong Go](/blog/go-three-rs-optimization-patterns-streaming-pooling/) cho bước 8.

<Concepts>

- **TFBO (Test, Fix, Benchmark, Optimize)**: vòng lặp chín bước: test và sửa cho tới khi đúng, đo theo RAER, rồi tối ưu một tầng và quay lại test.
- **Mốc ban đầu (baseline)**: phép đo thực hiện trước khi đổi gì. Mọi số đo sau đều so với nó.
- **Điểm nghẽn (bottleneck)**: nơi tốn phần lớn một loại tài nguyên. Chương trình thường chỉ có vài điểm nghẽn.

</Concepts>

## Điểm rút ra (Key takeaways)

- **Thêm pod tăng công suất, không làm một request nhanh hơn.** Nếu request chờ nhiều phần, xác suất có ít nhất một phần chậm là `1 - (1 - p)^k`, và pod mới không đổi `p`.
- **Hiệu quả là làm ít việc hơn.** Sửa thuật toán hoặc code trước có thể tránh chi phí và độ phức tạp của scale ngang, như chuyện compaction của Thanos cho thấy.
- **Viết RAER trước khi tối ưu.** Thao tác, cỡ dữ liệu, độ trễ p99, bộ nhớ và CPU. Cỡ dữ liệu là một phần của ngân sách.
- **Trong ngân sách nghĩa là dừng.** Ngoài ngân sách thì tìm điểm nghẽn, đổi một trong năm tầng và chạy lại vòng TFBO, bắt đầu bằng test.
- **Bắt đầu từ trên cùng.** Đổi ở tầng hệ thống hoặc thuật toán có thể khiến việc ở tầng code trở nên không cần thiết.
