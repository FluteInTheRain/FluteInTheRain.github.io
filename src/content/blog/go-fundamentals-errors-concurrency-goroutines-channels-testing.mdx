### How error paths and concurrency trip up early production Go services

Most Go beginners pick up basic `if err != nil` and `go fn()` in an afternoon—and then get paged at 3 a.m. weeks later by failure modes invisible on happy-path laptop tests:

- **Goroutine leaks from abandoned unbuffered channels.** An API endpoint hits a 50 ms deadline and returns `504` to the user, leaving its downstream `go fetchInventory(ch)` worker blocked permanently on `ch <- res` because no receiver remains alive to read `ch`. After 50,000 timeouts, idle `2 KB+` stacks and pinned buffers OOM-kill the container.
- **Entire API server killed by one background panic.** An HTTP middleware wraps handlers cleanly with `defer recover()`, but one request launches `go sendAuditWebhook()` asynchronously. Inside the child goroutine, a `nil` pointer panic skips the parent handler's `recover()` completely and kills the entire OS process mid-flight!
- **Concurrent map corruption passing local tests.** Two worker goroutines write to the same cached `map` or unsynchronized counter: normal `go test ./...` passes 99 times in a row until production traffic hits `fatal error: concurrent map writes`.

Before opening memory allocators, schedulers, and flamegraphs later in the series, let's lock down every layer of Go errors, concurrency primitives, and testing discipline:

1. **Errors as inspectable trees**: `%w` wrapping, Go 1.20+ `errors.Join`, and depth-first matching in `errors/wrap.go`.
2. **Open-coded `defer` stacks and `panic`/`recover` boundaries**: eager argument snapshots, named returns, and per-goroutine recovery.
3. **Goroutines vs. OS threads**: why a `runtime.g` starts at `2 KB`, how `morestack` grows contiguously, and safe `WaitGroup` ownership.
4. **Channels, `select`, `sync.Mutex`, and `context.WithTimeout`**: unbuffered rendezvous vs. buffered queues (`hchan`), closing rules, and zero-leak cancellation.
5. **Table-driven subtests and the ThreadSanitizer `-race` detector**: vector-clock Happens-Before checking on real Apple M2 runs.

<Callout type="note" title="TL;DR">
Handle failures as explicit `(T, error)` return values chained with `%w` or `errors.Join` and inspected via `errors.Is` / `errors.As`. Reserve `panic` strictly for fatal startup invariants, remember every child goroutine needs its own `defer recover()`, always launch workers with `wg.Add(1)` before `go func()`, terminate channel waits with `select` + `ctx.Done()`, and run `go test -race ./...` in CI.
</Callout>

<Concepts>

- **Error tree (`%w` / `errors.Join`)**: layered wrappers holding `Unwrap() error` or `Unwrap() []error` links so callers preserve full operational context without erasing underlying root causes.
- **Open-coded `defer`**: modern Go compiler optimization (Go 1.14+) that inlines deferred cleanups directly onto the stack return path (~0–1 ns overhead unless wrapped inside loops).
- **Goroutine leak**: spawning a goroutine that stays blocked forever waiting on an unclosed channel or missing `ctx.Done()` branch, pinning RAM permanently.
- **Happens-Before edge**: a formal ordering relation established by Mutex lock/unlock, channel send/receive, or `WaitGroup` completion proving shared memory accesses cannot race.

</Concepts>

## 1. Errors are values: unwrap trees (`%w`, `Join`), `errors.Is`, and `errors.As`

Why did Go reject Java/Python `try/catch` exceptions? Hidden stack unwinding makes it effortless to miss which third-party function can throw mid-transaction, leaving locks held or partial records committed silently. Treating `error` as a normal interface value (`type error interface { Error() string }`) forces every failure edge right onto the readable code path.

Think of wrapped errors like nested shipping receipts attached to a returned package. The warehouse stamps `"storage timeout"` on the inner box (`TimeoutErr`); the fulfillment service tapes a slip saying `"reserve stock: ..."` (`%w`) on top; the HTTP controller stamps `"checkout handler: ..."`. Any supervisor upstream can peel receipts cleanly using `errors.Is` (checking a sentinel receipt) or `errors.As` (reading structured fields like `Ms: 250`)!

Look straight at the standard library DFS walker in Go's `src/errors/wrap.go` and trace how `fmt.Errorf("checkout: %w", errors.Join(...))` traverses multi-cause trees:

<GitHubCode repo="golang/go" path="src/errors/wrap.go" lines="L44-L72" url="https://github.com/golang/go/blob/master/src/errors/wrap.go#L44-L72" caption="Real DFS unwrapper inside Go's stdlib: errors.Is traverses both single Unwrap() error chains and multi-error Unwrap() []error slices.">
```go
func Is(err, target error) bool {
	if err == nil || target == nil {
		return err == target
	}
	isComparable := reflectlite.TypeOf(target).Comparable()
	return is(err, target, isComparable)
}

func is(err, target error, targetComparable bool) bool {
	for {
		if targetComparable && err == target {
			return true
		}
		if x, ok := err.(interface{ Is(error) bool }); ok && x.Is(target) {
			return true
		}
		switch x := err.(type) {
		case interface{ Unwrap() error }:
			err = x.Unwrap()
			if err == nil { return false }
		case interface{ Unwrap() []error }:
			for _, sub := range x.Unwrap() {
				if is(sub, target, targetComparable) { return true }
			}
			return false
		default:
			return false
		}
	}
}
```

Notice one clean boundary convention used across experienced Go teams: **mark external service boundaries deliberately**. Inside your repository and domain services, wrap errors with `%w` so HTTP middleware can map `errors.Is(err, sql.ErrNoRows)` to HTTP `404` or `errors.As(err, &timeoutErr)` to HTTP `504`. When crossing out to untrusted clients—or hiding third-party internal schema names—redact internal SQL errors and format public messages safely without leaking raw stack internals.

<Concepts>

- **Sentinel error (`var Err... = errors.New(...)`)**: package-level immutable error value matched cleanly across callers using `errors.Is`.
- **`errors.Is` vs. `errors.As`**: `Is` tests identity equality across unwrap chains; `As` extracts a concrete custom struct error (`*TimeoutErr`) to read metadata fields like retry delays.
- **Unwrap boundary (`%w` vs `%v`)**: `%w` links caller and inner error for programmatic inspection; `%v` renders human text only and strips inner identities cleanly.

</Concepts>

## 2. Defer LIFO stacks, argument snapshots, and `panic`/`recover` boundaries

Pairing `defer f.Close()` right below opening a socket guarantees cleanup across early error returns. Before Go 1.14, every `defer` allocated a small `_defer` struct on the heap and walked a linked list on return—making teams avoid `defer mu.Unlock()` inside ultra-hot mutex paths. Starting in **Go 1.14**, the compiler compiles most normal functions using **open-coded defers**: an 8-bit bitmap stored inside the stack frame records which defers executed, and the function epilogue runs them directly inline (`~0–1 ns` overhead!). Only inside loops or functions exceeding 8 defers does Go fall back to heap/stack linked `_defer` records.

Two critical pitfalls still catch teams off guard in production:

1. **Direct arguments evaluate at the `defer` line; closures capture live variables.** Writing `defer logLatency(start)` snapshots `start` immediately when the `defer` line runs (see our Go 1.27 test below printing `snapshot=10` even after `x = 99`), whereas `defer func() { ... }()` captures references and reads live values when returning—including updating a named return `(err error)` so a failed `tx.Close()` error merges via `errors.Join` rather than disappearing!
2. **Every background goroutine needs its own `defer recover()` boundary.** Placing `recover()` in HTTP middleware shields requests *on that HTTP handler's goroutine*, but calling `go sendAuditWebhook()` creates an empty new goroutine stack. Put a reusable wrapper like `GoSafe(fn func())` across asynchronous jobs so panics convert into alert logs + `debug.Stack()` instead of crashing the whole container.

Also watch one subtle test/resource bug: **never wrap `defer f.Close()` inside a loop iterating thousands of files**. Because `defer` waits until the *enclosing function* exits rather than the loop iteration block, holding thousands of open files quickly hits OS `ulimit -n` (`EMFILE: too many open files`). Move the per-file open/read/close body into a helper function so `defer f.Close()` executes cleanly on every single file.

```go
func GoSafe(name string, fn func()) {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				log.Printf("panic recovered in %s: %v\n%s", name, r, debug.Stack())
			}
		}()
		fn()
	}()
}
```

## 3. Goroutines vs. OS threads: the `2 KB` dynamic stack and `WaitGroup`

Think of an OS kernel thread (POSIX `pthread`) like chartering a full freight truck just to deliver one letter: the OS reserves `1–2 MB` of guard-paged virtual stack immediately and pays an expensive kernel context switch (`1–2 µs` plus TLB/cache churn) whenever switching trucks. A **goroutine (`runtime.g`)**, by contrast, works like a courier on a collapsible scooter inside user space: Go allocates just **2 KB** of contiguous heap stack (`_StackMin = 2048 bytes`) and multiplexes tens of thousands of goroutines onto only `GOMAXPROCS` (8 on an Apple M2) OS worker threads.

When deep recursion pushes past `2 KB`, Go's function prologue triggers `runtime.morestack()`: it allocates a `2x` larger contiguous stack buffer, copies existing frames cleanly, and adjusts internal stack pointers. Why didn't Go stick with segmented linked stack chunks? Early Go (pre-1.4) hit the notorious **"hot split" problem** whenever a tight loop bounced repeatedly right across a segment boundary, forcing allocate-and-free thrashing on every iteration. Contiguous doubling stacks eliminate hot splits entirely while preserving tiny `2 KB` starting cost.

For structured parallel fan-out where any sub-task failure should abort remaining siblings cleanly, production services pair goroutines with **`errgroup.WithContext`** (from `golang.org/x/sync/errgroup`)—which manages `WaitGroup` synchronization, error capture, and `context` cancellation in one cohesive pattern:

```go
g, ctx := errgroup.WithContext(parentCtx)
g.SetLimit(4) // cap max concurrent workers without writing manual semaphores!
for _, item := range items {
	g.Go(func() error {
		return fetchPrice(ctx, item) // returning non-nil err cancels sibling ctx!
	})
}
if err := g.Wait(); err != nil {
	return fmt.Errorf("pricing batch: %w", err)
}
```

And if writing manual loops with `sync.WaitGroup`, keep the placement rule sacred:

```go
var wg sync.WaitGroup
for w := 0; w < 4; w++ {
	wg.Add(1) // MUST execute BEFORE `go` so wg.Wait() cannot slip past zero!
	go func(workerID int) {
		defer wg.Done()
		processBatch(workerID)
	}(w)
}
wg.Wait() // blocks until all 4 workers decrement counter back to 0
```

Wait—why does placing `wg.Add(1)` *inside* `go func()` cause intermittent flakiness? Because `wg.Wait()` on the parent goroutine often races ahead before the OS scheduler even executes line 1 of the child goroutine, seeing counter `== 0`, returning early, and abandoning background tasks! (Wait: in Go 1.25+, `wg.Go(func() { ... })` was even added to handle `Add(1)` + `defer Done()` automatically!)

Think carefully about why bounded worker concurrency matters in real backend servers too. Launching `for _, url := range urls { go fetch(url) }` without `g.SetLimit(N)` or a worker pool looks fast for 10 URLs on your laptop—and promptly explodes under production scale if an import job feeds 50,000 URLs at once, exhausting OS file descriptors, spiking TLS handshake CPU, and knocking over downstream databases. Always cap concurrency with `errgroup.SetLimit(N)` or a fixed pool of worker goroutines pulling jobs from one buffered channel.

Notice what happens inside Go's runtime when one of those 4 goroutines calls an ordinary `http.Get()` or `db.Query()` over TCP: Go's **netpoller** (`epoll` on Linux, `kqueue` on macOS) automatically parks the waiting `g` off the OS thread onto a non-blocking socket wait list so that the underlying OS thread (`M`) immediately moves on to execute another ready goroutine. That single architectural design explains why a modest 4-core Go container comfortably sustains 20,000 idle HTTP/WebSocket streams simultaneously without spawning 20,000 OS threads.

<Concepts>

- **Contiguous dynamic stack**: starting each goroutine at `2 KB` and copying into a `2x` buffer (`morestack`) when needed, permitting 100,000+ idle goroutines per gigabyte of RAM.
- **`GOMAXPROCS`**: runtime ceiling capping how many OS threads can simultaneously execute Go CPU instructions (defaulting to logical CPU cores, or container CPU quota in modern Go).
- **User-space context switch**: swapping register state (`PC`, `SP`) directly inside Go's runtime scheduler (`~100–200 ns`) without calling the OS kernel.

## 4. Channels, `select`, `sync.Mutex`, and cancellation without leaks

Rob Pike famously summarized Go concurrency: *"Don't communicate by sharing memory; share memory by communicating."* Yet real production systems use **both** idioms intentionally:

- **Channels (`chan T` — backed by `runtime.hchan` ring buffer + lock + `sudog` waiter queues)** excel for transferring ownership of jobs, pipelines, worker pools, and structured shutdown signals. An **unbuffered channel (`make(chan T)`)** acts like a synchronized baton handoff: sender blocks until receiver catches. A **buffered channel (`make(chan T, N)`)** behaves like a bounded queue holding up to `N` messages before backpressure kicks in.
- **`sync.Mutex` / `sync.RWMutex` / `atomic`** excels for high-frequency local state protection (protecting an in-memory map, rate limiter bucket, or shared metrics counter) with far lower overhead than running a dedicated actor goroutine. Never copy a locked mutex, keep critical sections as tiny as possible (never perform slow network HTTP calls while holding `mu.Lock()`!), and use `atomic.Int64` or `atomic.Bool` whenever guarding single scalar flags or counters.

| Synchronization Primitive | Primary Use Case | Overhead / Contention Profile | Common Production Trap |
| :--- | :--- | :--- | :--- |
| `make(chan T)` (unbuffered) | Ownership handoff & strict barrier sync | Context switch (~150 ns) on handoff | Sender blocks forever if receiver exits early |
| `make(chan T, N)` (buffered) | Worker job queues & timeout result slot (`cap=1`) | Fast lock-protected ring copy when space free | Treating huge buffers as infinite queues hides latency |
| `sync.Mutex` / `RWMutex` | Guarding multi-field invariants (`map`, slices) | ~15–25 ns uncontended atomic CAS | Holding lock across slow network/DB I/O stalls everyone |
| `sync/atomic` (`atomic.Int64`) | Counters, feature flags, health states | ~2–5 ns single CPU lock-free instruction | Combining two separate atomics without a lock breaks invariants |

Look at why naive timeouts leak goroutines and how `select` + buffered result slots (`cap = 1`) eliminate leaks completely:

```go
ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
defer cancel() // ALWAYS defer cancel() to release timer heap entries immediately!

ch := make(chan int, 1) // buffer 1 lets slow worker deposit & exit even if caller timed out!
go func() {
	res := computeSlowValue()
	ch <- res // non-blocking if caller already abandoned select branch!
}()

select {
case v := <-ch:
	return v, nil
case <-ctx.Done():
	return 0, ctx.Err() // ContextDeadlineExceeded without leaving worker stuck forever
}
```

Inside Go's runtime (`src/runtime/chan.go`), a channel is not magic compiler syntax—it is a concrete heap struct **`hchan`** holding an array ring buffer and two intrusive waiter queues of sleeping goroutines (`sendq` and `recvq`):

<GitHubCode repo="golang/go" path="src/runtime/chan.go" lines="L33-L56" url="https://github.com/golang/go/blob/master/src/runtime/chan.go#L33-L56" caption="The real runtime.hchan structure under every chan T: circular ring buffer cursors (sendx/recvx), wait queues (sendq/recvq), and its protective mutex lock.">
```go
type hchan struct {
	qcount   uint           // total elements currently buffered
	dataqsiz uint           // capacity passed to make(chan T, N)
	buf      unsafe.Pointer // pointer to circular array of dataqsiz slots
	elemsize uint16
	closed   uint32
	timer    *timer
	elemtype *_type
	sendx    uint           // next ring write slot index
	recvx    uint           // next ring read slot index
	recvq    waitq          // goroutines blocked waiting to read <-ch
	sendq    waitq          // goroutines blocked waiting to write ch<-
	lock     mutex          // synchronizes channel buffer & waiter queues
}
```
</GitHubCode>

Look closely at all four runtime channel states—memorizing this table eliminates 90% of channel deadlocks and panics in production:

| Channel State | Send (`ch <- x`) | Receive (`v, ok := <-ch`) | `close(ch)` |
| :--- | :--- | :--- | :--- |
| **`nil` channel** (`var ch chan int`) | **Blocks forever!** (disabled in `select`) | **Blocks forever!** (disabled in `select`) | **Panic!** (`close of nil channel`) |
| **Open & empty** | Copies direct to waiter `sudog` or blocks | Enqueues `g` into `recvq` & parks `gopark()` | Marks `closed=1` and wakes all `recvq` |
| **Open with free buffer** | Copies into `buf[sendx++]`, never blocks | Reads `buf[recvx++]` (FIFO) | Drains remaining buffered items, then yields zero value |
| **Closed** | **Panic!** (`send on closed channel`) | Returns `(zeroValue, false)` immediately without blocking | **Panic!** (`close of closed channel`) |

Notice why `select` picks randomly whenever multiple `case` branches are ready simultaneously: deterministic top-to-bottom priority would starve lower branches under sustained producer load. Prior to Go 1.23, calling `time.After(d)` repeatedly inside a hot `for { select { ... } }` loop leaked timers until the duration expired; starting in **Go 1.23**, unreferenced `time.Timer` / `time.Ticker` objects get garbage collected cleanly as soon as they become unreachable.

Finally, think clearly about **`context.Context` propagation** across real microservices: pass `ctx` explicitly as the very first parameter (`func ChargeCard(ctx context.Context, req ChargeReq) error`), never store `context.Context` inside a struct field, and always forward the incoming HTTP `r.Context()` to downstream SQL drivers (`db.QueryContext(ctx, ...)`) and outbound HTTP requests (`http.NewRequestWithContext(ctx, ...)`) so cancelled user requests halt wasted downstream database work immediately.

<Concepts>

- **`runtime.hchan`**: internal heap struct holding a mutex, circular buffer array (for buffered channels), `sendx`/`recvx` cursors, and linked wait queues (`sendq`/`recvq`) of paused goroutines.
- **Unbuffered rendezvous**: `make(chan T)` synchronizes sender and receiver tightly so delivery itself guarantees completion up to that handoff point.
- **Buffered channel (`make(chan T, N)`)**: decouples speed momentarily up to `N` queued slots; using `cap = 1` prevents orphan workers from hanging when callers cancel early.
- **Channel close invariant**: strictly close on the **producer/sender side** (`close(ch)` broadcasts zero-values with `ok == false` to all listeners); sending to a closed channel panics.

## 5. Table-driven unit tests and the ThreadSanitizer `-race` detector

Go ships first-class unit testing, subtests (`t.Run`), HTTP test servers (`net/http/httptest`), fuzzing, and **ThreadSanitizer race detection** right inside `go test`. Instead of writing ten nearly identical `TestPortValid`, `TestPortInvalid`, `TestPortNegative` boilerplate functions, idiomatic Go packs inputs and assertions into a **table slice**:

```go
cases := []struct {
	name     string
	fail     bool
	wantPort int
	wantErr  error
}{
	{name: "valid config", fail: false, wantPort: 8080},
	{name: "wrapped missing", fail: true, wantErr: ErrConfigMissing},
}
for _, tc := range cases {
	t.Run(tc.name, func(t *testing.T) {
		t.Parallel() // captures loop var cleanly per iteration (Go 1.22+ loopvar semantics!)
		got, err := loadPort(tc.fail)
		if tc.wantErr != nil && !errors.Is(err, tc.wantErr) {
			t.Fatalf("got err %v, want %v", err, tc.wantErr)
		}
		if tc.wantErr == nil && (err != nil || got != tc.wantPort) {
			t.Fatalf("got (%d, %v), want %d", got, err, tc.wantPort)
		}
	})
}
```

### Testing HTTP handlers cleanly without real sockets (`net/http/httptest`) and `-race`

For web services, Go ships **`net/http/httptest`** right in the standard library: `httptest.NewRecorder()` tests HTTP handlers directly in memory with zero TCP overhead, while `httptest.NewServer(mux)` spins up a real ephemeral loopback HTTP server to exercise client retries and timeouts cleanly:

```go
func TestOrderHandler_BadRequest(t *testing.T) {
	req := httptest.NewRequest(http.MethodPost, "/orders", strings.NewReader(`{}`))
	rec := httptest.NewRecorder() // captures status code, headers, and JSON body in memory
	OrderHandler(rec, req)
	if rec.Code != http.StatusBadRequest {
		t.Fatalf("status=%d, want 400", rec.Code)
	}
}
```

### How `go test -race` catches subtle timing bugs deterministically

### Ba tai nạn production đầu đời khi mới viết concurrency và error handling trong Go

Học thuộc cú pháp `if err != nil` và `go fn()` chỉ mất nửa buổi chiều — nhưng vài tuần sau khi lên production, rất nhiều hệ thống chết đứng vì những kịch bản không bao giờ lộ ra lúc test tay ở localhost:

- **Rò rỉ hàng vạn goroutine do channel không buffer bị bỏ rơi.** API gặp ngưỡng timeout 50 ms và trả `504` cho người dùng, nhưng worker `go fetchInventory(ch)` bên dưới vẫn đứng chờ mòn mỏi ở dòng `ch <- res` mãi mãi vì không còn ai mở đầu kia đọc ra. Sau 50.000 lần timeout, đống stack `2 KB+` và buffer bị giữ lại đẩy container tới OOMKill.
- **Một panic nhỏ ở goroutine nền kéo sập cả server.** Tầng HTTP middleware đã đặt sẵn `defer recover()` tưởng rất chắc, nhưng handler lại gọi `go sendAuditWebhook()` chạy nền. Lỗi `nil pointer` trong worker con bỏ qua hoàn toàn `recover()` của cha và hạ gục toàn bộ OS process ngay giữa giờ cao điểm!
- **Xung đột map song song vượt qua unit test bình thường.** Hai worker ghi đồng thời vào cùng một `map` hoặc biến đếm: chạy `go test ./...` qua trót lọt 99 lần, cho tới khi tải thật làm server crash với dòng `fatal error: concurrent map writes`.

Bài kết thúc chặng nền tảng Go này mổ xẻ đầy đủ cả năm trụ cột xử lý lỗi, concurrency và kiểm thử chuẩn sản xuất:

1. **Lỗi là một cây cấu trúc (`%w`, `errors.Join`)**: hàm duyệt DFS bên trong `errors/wrap.go` và lúc nào cần `%v` để chặn rò chi tiết.
2. **Ngăn xếp `defer` tối ưu, biến trả về định danh và biên `panic`/`recover`**: chốt tham số eager vs closure và bẫy goroutine con mất bảo vệ.
3. **Goroutine `2 KB` so với OS thread `1–2 MB`**: cơ chế mở rộng stack liên tục (`morestack`) và luật đặt `wg.Add(1)`.
4. **Channel (`hchan`), `select`, `sync.Mutex` và `context.WithTimeout`**: thoát rò rỉ worker bằng buffer 1 slot và quy tắc đóng channel.
5. **Unit test kiểu bảng (`t.Run`) & máy dò `-race`**: cách đồng hồ vector ThreadSanitizer bắt lỗi data race ngay trên máy Apple M2.

<Callout type="note" title="Tóm tắt nhanh (TL;DR)">
Xử lý thất bại bằng giá trị trả về `(T, error)` nối mạch qua `%w` / `errors.Join` để truy vết bằng `errors.Is` và `errors.As`. Giữ `panic` chỉ cho lỗi bất khả kháng lúc khởi động app; nhớ đặt `defer recover()` riêng bên trong mỗi goroutine nền; luôn viết `wg.Add(1)` trước `go func()`; bọc chờ channel bằng `select` + `ctx.Done()`; và bắt buộc chạy `go test -race ./...` trên CI.
</Callout>

<Concepts title="Giải thích nhanh mấy thuật ngữ nền tảng">

- **Cây bọc lỗi (`%w` / `errors.Join`)**: chuỗi liên kết lưu `Unwrap() error` hoặc `Unwrap() []error`, vừa thêm ngữ cảnh dễ đọc vừa giữ nguyên danh tính lỗi gốc bên dưới.
- **Open-coded `defer`**: tối ưu từ Go 1.14 nhúng thẳng lệnh dọn dẹp vào cuối Stack frame (chi phí ~0–1 ns trừ phi đặt trong vòng lặp).
- **Rò rỉ goroutine (Goroutine leak)**: goroutine bị kẹt vĩnh viễn tại channel hoặc không nghe `ctx.Done()`, giữ RAM không bao giờ giải phóng.
- **Cạnh Happens-Before**: mối quan hệ thứ tự thời gian chuẩn xác tạo bởi `Mutex.Unlock -> Lock`, gửi/nhận channel hay `WaitGroup`, chứng minh hai truy cập bộ nhớ không thể tranh chấp.

</Concepts>

## 1. Lỗi là giá trị: cây unwrap (`%w`, `Join`), `errors.Is` và `errors.As`

Vì sao Go cố ý từ bỏ `try/catch` kiểu Java hay Python? Luồng nhảy cóc khi ném exception dễ làm bạn bỏ sót một hàm sâu bên dưới bất ngờ văng lỗi giữa chừng, bỏ quên chưa nhả Lock hoặc ghi dở dữ liệu vào DB. Đưa `error` về thành một interface trả về bình thường (`type error interface { Error() string }`) ép mọi nhánh lỗi hiện hình rành mạch trước mắt người đọc.

Hãy hình dung chuỗi bọc lỗi như các tem biên lai dán chồng lên thùng hàng hoàn trả. Kho hàng đóng tem `"timeout"` lên thùng gốc (`TimeoutErr`); bộ phận đóng gói dán đè phiếu `"reserve stock: ..."` (`%w`); cổng HTTP dán tiếp nhãn `"checkout handler: ..."`. Thanh tra phía trên chỉ việc dùng `errors.Is` (đối chiếu đúng mẫu tem chuẩn) hoặc `errors.As` (bóc vỏ đọc số `Ms: 250` bên trong)!

Đọc thẳng mã nguồn thư viện chuẩn tại `src/errors/wrap.go` để thấy cách `errors.Is` tự động lội sâu qua cả chuỗi 1 lỗi lẫn cây nhiều lỗi `errors.Join`:

<GitHubCode repo="golang/go" path="src/errors/wrap.go" lines="L44-L72" url="https://github.com/golang/go/blob/master/src/errors/wrap.go#L44-L72" caption="Hàm duyệt DFS thực tế bên trong thư viện chuẩn Go: errors.Is lội qua cả Unwrap() error đơn lẫn Unwrap() []error đa nhánh.">
```go
func Is(err, target error) bool {
	if err == nil || target == nil {
		return err == target
	}
	isComparable := reflectlite.TypeOf(target).Comparable()
	return is(err, target, isComparable)
}

func is(err, target error, targetComparable bool) bool {
	for {
		if targetComparable && err == target {
			return true
		}
		if x, ok := err.(interface{ Is(error) bool }); ok && x.Is(target) {
			return true
		}
		switch x := err.(type) {
		case interface{ Unwrap() error }:
			err = x.Unwrap()
			if err == nil { return false }
		case interface{ Unwrap() []error }:
			for _, sub := range x.Unwrap() {
				if is(sub, target, targetComparable) { return true }
			}
			return false
		default:
			return false
		}
	}
}
```

Các đội ngũ dày dạn kinh nghiệm thường giữ một ranh giới rõ ràng: **bọc `%w` xuyên suốt nội bộ, cắt `%v` khi ra biên ngoài.** Giữa các tầng repository và service, `%w` giúp lớp middleware map chính xác `errors.Is(err, sql.ErrNoRows)` về HTTP `404` hoặc `errors.As(err, &timeoutErr)` về `504`. Nhưng tới lúc trả JSON cho client bên ngoài — hoặc giấu tên bảng/schema database nhạy cảm — hãy cắt chuỗi bằng `%v` hoặc trả thông báo chuẩn hóa để không làm lộ cấu trúc hệ thống.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Lỗi mẫu (Sentinel error)**: biến lỗi toàn cục cố định (`var Err... = errors.New(...)`) dùng đối chiếu danh tính trực tiếp bằng `errors.Is`.
- **`errors.Is` vs. `errors.As`**: `Is` dò xem trong cây lỗi có chứa một giá trị lỗi cụ thể hay không; `As` rút hẳn kiểu struct lỗi cụ thể (`*TimeoutErr`) để đọc các trường phụ trợ như độ trễ.
- **Ranh giới `%w` vs `%v`**: `%w` giữ sợi dây nối để code tầng trên truy vấn ngược vào lỗi gốc; `%v` cố ý cắt sợi dây đó, chỉ biến thành văn bản thuần.

</Concepts>

## 2. Ngăn xếp `defer` LIFO, chốt tham số và biên giải cứu `panic`/`recover`

Đặt `defer f.Close()` sát dưới dòng mở socket đảm bảo đóng kết nối ở mọi nhánh thoát hàm. Trước Go 1.14, mỗi lệnh `defer` đều phải xin một struct `_defer` trên Heap gây chậm đường nóng. Từ **Go 1.14 trở đi**, trình biên dịch dùng kỹ thuật **open-coded defers**: dùng một byte bitmask ngay trên Stack frame để đánh dấu các `defer` đã qua rồi chèn thẳng code dọn dẹp vào cuối hàm (`~0–1 ns`!). Chỉ khi đặt `defer` trong vòng lặp hoặc quá 8 lệnh `defer` thì runtime mới rơi về danh sách liên kết `_defer`.

Vẫn có hai cạm bẫy kinh điển ở production:

1. **Tham số truyền thẳng vào `defer fn(x)` tính NGAY lập tức; còn closure chỉ đọc biến khi thoát hàm.** Lệnh `defer logLatency(start)` chụp cứng giá trị `start` tại dòng khai báo `defer` (xem test Go 1.27 bên dưới xác nhận `snapshot=10` dù `x` sau đó tăng lên `99`). Ngược lại, một closure `defer func() { ... }()` đọc trực tiếp giá trị lúc `return` — và nếu bạn đặt tên cho biến trả về (`(err error)`), closure có thể gộp thêm lỗi lúc `tx.Close()` vào `err` bằng `errors.Join` thay vì làm rơi mất lỗi đóng transaction!
2. **Mỗi goroutine con phải tự đặt `defer recover()` riêng.** Đặt `recover()` trong middleware HTTP chỉ che chắn riêng cho goroutine xử lý request đó. Khi bạn tung `go sendAuditWebhook()`, goroutine mới có một Stack mới toanh không dính dáng gì tới middleware cha — nên hãy gói bằng một helper như `GoSafe` để bắt panic an toàn kèm `debug.Stack()`.

Cũng chớ quên lỗi cạn file descriptor cực phổ biến: **đừng đặt `defer f.Close()` trực tiếp bên trong vòng lặp nghìn file**. Vì `defer` chỉ chạy khi *toàn bộ hàm cha thoát ra*, hàng nghìn handle file sẽ mở treo cho tới cuối vòng lặp và chạm trần `EMFILE: too many open files`. Tách thân xử lý mỗi file thành một hàm riêng để `defer` đóng sạch ngay sau từng vòng lặp.

```go
func GoSafe(name string, fn func()) {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				log.Printf("panic recovered in %s: %v\n%s", name, r, debug.Stack())
			}
		}()
		fn()
	}()
}
```

Xem kết quả đo thật Go 1.27 kiểm tra cây lỗi đa nhánh `errors.Join` và snapshot tham số của `defer` — sau đó bấm từng bước qua 4 kịch bản thực chiến trong trình mô phỏng dưới đây:

## 3. Goroutine `2 KB` vs. OS thread & quy tắc vàng với `WaitGroup`

Một thread hệ điều hành (`pthread`) chẳng khác gì thuê hẳn một chiếc xe tải đầu kéo chỉ để đi giao một phong bì: nhân OS phải cắt sẵn `1–2 MB` vùng nhớ Stack kèm bảng trang bảo vệ, và mỗi lần đổi xe phải chui xuống kernel tốn `1–2 µs`. Trong khi đó, **Goroutine (`runtime.g`)** giống shipper chạy xe điện gọn trong user-space: mới sinh chỉ tốn đúng **2 KB** Stack (`_StackMin = 2048 byte`), và Go runtime linh hoạt ghép hàng vạn goroutine chạy nhịp nhàng lên đúng `GOMAXPROCS` (8 luồng trên Apple M2) thread thật của CPU.

Khi gọi hàm lồng sâu vượt quá `2 KB`, phần đầu hàm tự động kích hoạt `runtime.morestack()`: cấp phát vùng Stack liền mạch gấp đôi `2x`, copy toàn bộ khung Stack sang gọn ghẽ và cập nhật lại con trỏ. Nhờ đổi sang Stack liền mạch từ Go 1.4, Go đã giải quyết dứt điểm lỗi **"hot split"** ngày trước (khi vòng lặp lặp đi lặp lại ngay ranh giới phân đoạn stack làm cấp phát và thu hồi giật cục liên hồi).

Trong các luồng gọi song song nhiều downstream RPC nơi chỉ cần 1 nhánh hỏng là hủy toàn bộ nhánh còn lại, hãy ưu tiên **`errgroup.WithContext`** (`golang.org/x/sync/errgroup`) — nó gộp sẵn `WaitGroup`, gom lỗi đầu tiên và truyền tín hiệu hủy `ctx`:

```go
g, ctx := errgroup.WithContext(parentCtx)
g.SetLimit(4) // giới hạn tối đa 4 worker chạy đồng thời, khỏi viết semaphore tay!
for _, item := range items {
	g.Go(func() error {
		return fetchPrice(ctx, item) // 1 worker lỗi -> tự động cancel ctx các nhánh khác!
	})
}
if err := g.Wait(); err != nil {
	return fmt.Errorf("pricing batch: %w", err)
}
```

Còn khi tự viết vòng lặp với `sync.WaitGroup`, luôn giữ nguyên tắc đặt chỗ bất di bất dịch:

```go
var wg sync.WaitGroup
for w := 0; w < 4; w++ {
	wg.Add(1) // BẮT BUỘC đặt TRƯỚC chữ `go` để Wait() không trượt qua lúc count == 0!
	go func(workerID int) {
		defer wg.Done()
		processBatch(workerID)
	}(w)
}
wg.Wait() // chờ toàn bộ 4 goroutine xong dứt điểm mới đi tiếp
```

Lưu ý: đặt `wg.Add(1)` *bên trong* `go func()` rất dễ gây race condition khiến test lúc qua lúc rớt, bởi hàm cha có thể chạy tới dòng `wg.Wait()` trước khi bộ lập lịch kịp chạm vào dòng đầu tiên của goroutine con! (Từ Go 1.25 trở đi, thư viện chuẩn còn bổ sung `wg.Go(func() { ... })` để gói gọn cặp `Add(1)` + `defer Done()` chống viết nhầm.)

Trên server thực tế, luôn nhớ **giới hạn mức độ song song** thay vì viết `for _, url := range urls { go fetch(url) }` thả phanh: 50.000 URL đổ về cùng lúc sẽ giết chết socket và database downstream trong vài giây! Dùng `errgroup.SetLimit(N)` hoặc một nhóm worker cố định đọc từ queue channel là quy chuẩn an toàn. Và điều làm Go nhẹ nhàng tới vậy khi chạy 20.000 HTTP/WebSocket song song là cơ chế **netpoller** (`epoll` / `kqueue`): hễ goroutine dừng chờ mạng, runtime lập tức nhấc `g` ra khỏi thread OS (`M`) để CPU quay sang phục vụ ngay goroutine khác sẵn sàng chạy.

<GoFund3GoroutineVsThread />

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Stack co giãn liên tục (Contiguous stack)**: mỗi goroutine khởi đầu chỉ với `2 KB` và tự nhân đôi (`morestack`) khi cần, cho phép nuôi hơn 100.000 goroutine nhàn rỗi trên 1 GB RAM.
- **`GOMAXPROCS`**: trần số thread hệ điều hành được phép chạy đồng thời mã Go trên CPU (mặc định khớp số core vật lý hoặc hạn mức CPU trong container).
- **Chuyển ngữ cảnh user-space**: đổi goroutine ngay trong tầng Go runtime (`~100–200 ns`) mà không cần làm phiền OS kernel.

</Concepts>

## 4. Channel, `select`, `sync.Mutex` và triệt tiêu rò rỉ với `context`

Rob Pike từng gói gọn triết lý song song của Go: *"Đừng giao tiếp bằng cách dùng chung bộ nhớ; hãy chia sẻ bộ nhớ bằng cách giao tiếp qua thông điệp."* Nhưng thực chiến production cần dùng khéo léo **cả hai** công cụ đúng việc:

- **Channel (`chan T` — chạy trên struct `runtime.hchan` có vòng đệm + khóa + hàng đợi `sudog`)**: tuyệt vời cho việc chuyển quyền sở hữu job, dựng worker pool và báo tín hiệu dừng. **Unbuffered channel (`make(chan T)`)** bắt buộc hai bên gửi-nhận chạm mặt đồng thời mới trao tay; còn **Buffered channel (`make(chan T, N)`)** trữ tối đa `N` phần tử giúp giảm nghẽn tức thời.
- **`sync.Mutex` / `sync.RWMutex` / `atomic`**: lựa chọn tối ưu hơn hẳn mỗi khi bạn chỉ cần bảo vệ một biến đếm, map cấu hình hay bảng cache nằm chung một chỗ. Đừng bao giờ giữ `mu.Lock()` xuyên qua lúc gọi HTTP/DB chậm chạp, và hãy dùng `atomic.Int64` cho bộ đếm/cờ trạng thái đơn lẻ.

| Công cụ đồng bộ | Dùng chuẩn cho bài toán | Chi phí cơ bản | Cạm bẫy production phổ biến |
| :--- | :--- | :--- | :--- |
| `make(chan T)` (không đệm) | Chuyển giao quyền sở hữu & đồng bộ | Đổi goroutine (~150 ns) | Bên gửi treo chết nếu bên nhận thoát sớm |
| `make(chan T, N)` (có đệm) | Hàng đợi worker & hứng kết quả `cap=1` | Chép qua vòng đệm có khóa ngắn | Đặt buffer quá lớn dễ che giấu nghẽn chậm thật |
| `sync.Mutex` / `RWMutex` | Khóa cấu trúc nhiều trường (`map`, slice) | ~15–25 ns atomic CAS khi ít đụng | Ôm lock gọi I/O mạng làm đứng toàn bộ traffic |
| `sync/atomic` (`atomic.Int64`) | Biến đếm, cờ healthcheck, thống kê nhanh | ~2–5 ns lệnh CPU không cần lock | Tách 2 biến atomic rời làm vỡ tính nhất quán |

Nhìn cách dùng **`cap = 1` cho channel trả kết quả** kết hợp `select` + `ctx.Done()` để tiêu diệt sạch bóng rò rỉ goroutine khi client rớt mạng giữa chừng:

```go
ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
defer cancel() // LUÔN defer cancel() để thu hồi timer ngay khi việc xong sớm!

ch := make(chan int, 1) // buffer 1 ô giúp worker bỏ kết quả vào rồi thoát hẳn dù bên gọi đã timeout!
go func() {
	res := computeSlowValue()
	ch <- res // không bao giờ bị kẹt chết ở đây nếu caller bỏ đi!
}()

select {
case v := <-ch:
	return v, nil
case <-ctx.Done():
	return 0, ctx.Err() // Trả DeadlineExceeded tức thì mà không để lại zombie goroutine
}
```

Bên trong runtime Go (`src/runtime/chan.go`), mỗi biến `chan T` thực chất trỏ tới struct **`hchan`** nằm trên Heap, chứa mảng vòng tròn lưu dữ liệu và hai hàng đợi chứa các goroutine đang tạm dừng (`sendq` và `recvq`):

<GitHubCode repo="golang/go" path="src/runtime/chan.go" lines="L33-L56" url="https://github.com/golang/go/blob/master/src/runtime/chan.go#L33-L56" caption="Cấu trúc runtime.hchan thật dưới mọi Go channel: chỉ mục đọc/ghi vòng đệm (sendx/recvx), hàng đợi ngủ (sendq/recvq) và khóa lock.">
```go
type hchan struct {
	qcount   uint           // số phần tử hiện có trong hàng đợi
	dataqsiz uint           // kích thước đệm N từ make(chan T, N)
	buf      unsafe.Pointer // con trỏ tới mảng vòng dataqsiz phần tử
	elemsize uint16
	closed   uint32
	timer    *timer
	elemtype *_type
	sendx    uint           // vị trí ghi kế tiếp trong vòng đệm
	recvx    uint           // vị trí đọc kế tiếp trong vòng đệm
	recvq    waitq          // hàng đợi goroutine đang treo chờ đọc <-ch
	sendq    waitq          // hàng đợi goroutine đang treo chờ gửi ch<-
	lock     mutex          // bảo vệ toàn bộ trạng thái hchan & hàng đợi
}
```

Thuộc lòng bảng 4 trạng thái dưới đây sẽ giúp bạn tránh tới 90% lỗi kẹt luồng và panic trong dự án Go thật:

| Trạng thái Channel | Gửi (`ch <- x`) | Nhận (`v, ok := <-ch`) | Đóng (`close(ch)`) |
| :--- | :--- | :--- | :--- |
| **Channel `nil`** (`var ch chan int`) | **Treo vĩnh viễn!** (vô hiệu hóa trong `select`) | **Treo vĩnh viễn!** (vô hiệu hóa trong `select`) | **Panic!** (`close of nil channel`) |
| **Đang mở & rỗng** | Chép thẳng qua `sudog` đang chờ hoặc chặn | Đưa `g` vào `recvq` và ngủ `gopark()` | Đặt `closed=1`, đánh thức toàn bộ `recvq` |
| **Đang mở & còn buffer** | Chép vào `buf[sendx++]`, trả ngay | Đọc `buf[recvx++]` (FIFO) | Đọc hết phần tử còn sót, sau đó trả zero |
| **Đã đóng (`closed`)** | **Panic!** (`send on closed channel`) | Trả ngay `(zeroValue, false)` không chặn | **Panic!** (`close of closed channel`) |

Để ý hai chi tiết quan trọng: khối `select` cố ý **chọn ngẫu nhiên** khi nhiều nhánh cùng sẵn sàng để không bỏ đói nhánh nằm dưới; và từ **Go 1.23 trở đi**, các `time.Timer` / `time.Ticker` không còn bị tham chiếu (như `time.After(d)` đặt trong vòng `for { select ... }`) đã được GC thu hồi ngay thay vì rò rỉ bộ nhớ chờ hết hạn giờ như các bản Go cũ. Cuối cùng, hãy truyền **`ctx context.Context`** ở ngay tham số đầu tiên của hàm (`func ChargeCard(ctx context.Context, req ...)`), tuyệt đối không cất `ctx` vào trường của struct, và chuyển tiếp thẳng `r.Context()` vào SQL driver (`db.QueryContext`) để khi user hủy kết nối thì câu SQL phía dưới cũng dừng theo ngay lập tức.

Bấm tương tác qua mọi trạng thái truyền nhận channel, lệnh `close(ch)` phát sóng tới nhiều listener, bẫy panic khi ghi vào channel đã đóng và luồng ngắt `context.WithTimeout` ngay bên dưới:

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Struct `runtime.hchan`**: cấu trúc dữ liệu thật của channel nằm trên Heap, chứa mảng vòng ring buffer, khóa nội bộ và hai hàng đợi `sendq`/`recvq` cất các goroutine đang ngủ chờ.
- **Unbuffered rendezvous**: `make(chan T)` đồng bộ hóa hai đầu gửi-nhận phải gặp nhau cùng thời điểm mới chạy tiếp được.
- **Buffered channel (`make(chan T, N)`)**: đệm tối đa `N` giá trị; tạo kênh kết quả với `cap = 1` là mẹo kinh điển để cứu worker khỏi kẹt vĩnh viễn khi bên đợi đã thoát do timeout.
- **Quy tắc đóng Channel**: chỉ phía **bên gửi** mới gọi `close(ch)` (`close` phát tín hiệu hoàn tất `ok == false` cho toàn bộ người nhận); gửi vào channel đã đóng sẽ nổ panic.

## 5. Table-Driven Unit Test và máy dò đồng hồ vector `go test -race`

Go đóng gói sẵn công cụ test, `t.Run`, test server HTTP (`net/http/httptest`), fuzz test lẫn bộ phát hiện tranh chấp **ThreadSanitizer (`-race`)** ngay trong lệnh `go test`. Thay vì copy paste mười hàm `TestCase1`, `TestCase2`, hãy gom hết input/expected output vào một bảng **Table-driven test**:

```go
cases := []struct {
	name     string
	fail     bool
	wantPort int
	wantErr  error
}{
	{name: "valid config", fail: false, wantPort: 8080},
	{name: "wrapped missing", fail: true, wantErr: ErrConfigMissing},
}
for _, tc := range cases {
	t.Run(tc.name, func(t *testing.T) {
		t.Parallel() // từ Go 1.22+, biến vòng lặp tc tự tách riêng an toàn từng subtest!
		got, err := loadPort(tc.fail)
		if tc.wantErr != nil && !errors.Is(err, tc.wantErr) {
			t.Fatalf("got err %v, want %v", err, tc.wantErr)
		}
		if tc.wantErr == nil && (err != nil || got != tc.wantPort) {
			t.Fatalf("got (%d, %v), want %d", got, err, tc.wantPort)
		}
	})
}
```

### Test HTTP handler không cần mở socket thật (`net/http/httptest`) và cờ `-race`

Với API web, Go tặng sẵn gói **`net/http/httptest`**: dùng `httptest.NewRecorder()` để ghi lại status code, header và JSON trả về ngay trong RAM, hoặc `httptest.NewServer(mux)` để dựng server loopback chạy thật cho test retry và timeout:

```go
func TestOrderHandler_BadRequest(t *testing.T) {
	req := httptest.NewRequest(http.MethodPost, "/orders", strings.NewReader(`{}`))
	rec := httptest.NewRecorder() // hứng trọn status code, header, body ngay trong RAM
	OrderHandler(rec, req)
	if rec.Code != http.StatusBadRequest {
		t.Fatalf("status=%d, want 400", rec.Code)
	}
}
```

### Vì sao `go test -race` tóm được bug chạy lúc qua lúc rớt?

Độ trễ giữa các goroutine trên CPU biến thiên liên tục theo lịch trình của OS, khiến nhiều bug data race chạy test thường 1.000 lần vẫn xanh mượt. Khi bật **`-race`**, trình biên dịch dành riêng **4 từ shadow 64-bit cho mỗi 8 byte bộ nhớ** kèm đồng hồ vector ThreadSanitizer để truy lùng cặp đọc-ghi thiếu cạnh **Happens-Before**. Chạy kèm **`go test -shuffle=on -race ./...`** còn tự động xáo thứ tự test để bắt sống các biến toàn cục bị rò rỉ giữa các test case:

### Câu hỏi tự kiểm tra trước khi mổ xẻ lõi bộ nhớ & bẫy production

1. Dựa vào code trong `errors/wrap.go`, `errors.Is` và `errors.As` lội qua cây đa lỗi của `errors.Join` bằng cách nào — và khi nào nên dùng `%v` thay vì `%w`? *(Xem Mục 1)*

3. Tại sao một server Go chứa 50.000 goroutine nhàn rỗi nhẹ tênh trong khi 50.000 OS thread lại ngốn hàng chục GB — và phải đặt `wg.Add(1)` ở đâu? *(Xem Mục 3)*
4. Làm thế nào một channel đệm 1 phần tử `make(chan T, 1)` cứu worker khỏi rò rỉ vĩnh viễn khi nhánh `select` thoát ra qua `ctx.Done()`? *(Xem Mục 4)*
