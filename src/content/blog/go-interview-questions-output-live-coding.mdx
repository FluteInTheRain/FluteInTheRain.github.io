Reading a Go post and answering a Go question out loud are different skills. In a room with a timer you have to name the idea, give a short example, and say where it breaks, with someone watching. The way to get good at that is to practise it somewhere a mistake costs nothing, which is what this post is for.

It has three parts, and every answer links to the post that teaches the idea in full:

1. **Concept questions**, grouped by the four levels of the series, each with a model answer and what a weak answer leaves out.
2. **Predict the output**: six short programs. Guess first, then check. Every output was captured from a real `go run` on Go 1.27.1.
3. **Live coding**: three tasks, a bounded parallel fetcher, a cache with expiry and a rate limiter, each with a test and its real `go test -race` output.

## Part 1: Concept questions, by level

Read the question, answer it out loud, then read the model answer. If you cannot say it in thirty seconds, open the linked post.

### Level 1: the basics

**1. What is the difference between an array and a slice?**
An array has a fixed length that is part of its type, and assigning it copies every element. A slice is a small header (a pointer to an array, a length and a capacity) over an array, and assigning it copies only the header. That is why two slices can share one array.
*A weak answer misses:* the header, and that `append` can write into an array another slice still sees. See [slices, maps and strings](/blog/go-slices-maps-strings/) and, for the memory view, [Go memory](/blog/go-memory-data-types-slices-maps-strings/).

**2. What is a zero value, and what can you do with a nil map and a nil slice?**
Every variable starts at the zero value of its type: `0`, `""`, `false`, `nil`. You can read from a nil map and `append` to a nil slice. Writing to a nil map panics.
*A weak answer misses:* the read/write difference. Predict-the-output card 6 below is exactly this. See [types and pointers](/blog/go-variables-types-pointers-functions/).

**3. When do you use a pointer receiver instead of a value receiver?**
Use a pointer receiver when the method changes the value, or when the value is large or holds something that must not be copied, such as a mutex. Keep one kind per type so the method set stays predictable.
*A weak answer misses:* the copy that a value receiver makes, and that a type's method set decides which interfaces it satisfies. See [structs and interfaces](/blog/go-structs-methods-interfaces/).

**4. How do you handle and wrap errors?**
An error is an ordinary value returned as the last result. Check it right away, add context with `fmt.Errorf("...: %w", err)`, and test for a cause with `errors.Is` or `errors.As`. Handle an error once: either log it or return it.
*A weak answer misses:* `%w`, and that `panic` is not for ordinary failures. See [errors and defer](/blog/go-errors-defer-panic/).

**5. When are the arguments of a deferred call evaluated, and in what order do deferred calls run?**
The arguments are evaluated at the `defer` line. The call itself runs when the surrounding function returns, last in first out. A `defer` inside a loop therefore waits for the function, not for the iteration (card 2 below).
*A weak answer misses:* the loop case, and that closing a file in a loop with `defer` keeps every file open until the end. See [errors and defer](/blog/go-errors-defer-panic/).

### Level 2: concurrency and a service

**6. How do you stop a goroutine?**
A goroutine cannot be killed from outside. You give it a way to stop: a `context.Context` it checks, or a channel it receives from. Every goroutine you start needs an answer to "what ends this?".
*A weak answer misses:* the leak, a goroutine blocked forever on a channel nobody will use again. See [goroutines and channels](/blog/go-goroutines-channels-select/) and [context and mutexes](/blog/go-context-timeouts-mutexes/).

**7. What is the difference between a buffered and an unbuffered channel?**
A send on an unbuffered channel waits until a receiver is ready, so the two goroutines meet. A buffered channel lets a sender continue until the buffer is full. A full buffer then blocks the sender, which is how you get back-pressure.
*A weak answer misses:* that only the sender should close a channel, and that receiving from a closed channel returns the zero value. See [goroutines and channels](/blog/go-goroutines-channels-select/).

**8. How do you limit how many goroutines run at once?**
Either start a fixed number of workers that read from one jobs channel, or use a buffered channel as a semaphore: send before starting the work, receive when it ends. Live-coding task 1 below uses the semaphore.
*A weak answer misses:* what stops the producer when the context is cancelled. See [concurrency patterns](/blog/go-concurrency-patterns-worker-pools-pipelines/).

**9. Which timeouts does a `net/http` server need?**
The zero value of each timeout on `http.Server` means "no limit", so a slow client can hold a connection for as long as it likes. Set at least a header read timeout, and give handlers a context with a deadline.
*A weak answer misses:* that the defaults are unlimited. See [an HTTP service](/blog/go-http-service-net-http-json-middleware/) and, for what breaks under real traffic, [Go in production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/).

### Level 3: how Go works inside

**10. Why can `append` change a slice you did not pass to it?**
If the capacity has room, `append` writes into the existing array and returns a header with a longer length. Any other slice over that array sees the write. When the capacity is full, `append` allocates a new array and copies, and the old slices stop sharing.
*A weak answer misses:* that you cannot tell from the code alone which case you are in. Card 1 and the first figure below show it. See [Go memory](/blog/go-memory-data-types-slices-maps-strings/).

**11. What is a typed nil, and why can an error be non-nil when it holds a nil pointer?**
An interface value is a pair of a type and a value. If you return a nil `*MyErr` as `error`, the type slot is filled, so the interface is not nil, even though the pointer inside is. Return a plain `nil` on the success path.
*A weak answer misses:* the two slots. Card 4 below. See [abstractions](/blog/go-abstractions-interfaces-generics-errors/).

**12. Describe how the scheduler runs goroutines.**
Go multiplexes many goroutines (G) onto a few operating-system threads (M). Each logical processor (P), one per `GOMAXPROCS`, has a queue of runnable goroutines and lends its slot to a thread. When a goroutine blocks on the network, the thread moves on to the next goroutine; when a P runs dry it steals work from another.
*A weak answer misses:* what happens in a blocking system call, and the work stealing. See [the scheduler](/blog/go-concurrency-scheduler-channels-context-mutexes/).

**13. What is the difference between a data race and a race condition?**
A data race is two goroutines touching the same memory at once with at least one write and no synchronisation. A race condition is a bug that depends on timing, and it can exist with no data race at all, for example when every access holds a lock but the order of two steps still matters.
*A weak answer misses:* that `go test -race` finds the first kind only. See [the scheduler](/blog/go-concurrency-scheduler-channels-context-mutexes/).

### Level 4: performance

**14. What do `GOGC` and `GOMEMLIMIT` do, and when does `GOMEMLIMIT` help?**
`GOGC` sets how much the heap may grow past the live data before the next collection (the default `100` means it may double). `GOMEMLIMIT` is a soft ceiling on the memory Go manages: as the program nears it, the collector runs more often. It helps in a container with a hard memory limit, where you set it somewhat below that limit.
*A weak answer misses:* that it is soft, and that the collector can burn CPU when live data sits near the limit. See [hardware and GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/).

**15. What is escape analysis, and why does it matter?**
The compiler decides whether a value can live on the stack, which is freed for free when the function returns, or must go to the heap, which the garbage collector has to clean up. You can see its decisions with `-gcflags=-m`. Fewer heap allocations means less GC work.
*A weak answer misses:* that returning a pointer to a local is what usually moves it to the heap. See [hardware and GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/) and [when to optimize](/blog/go-efficiency-workflow-raer-tfbo-hardware-memory/).

**16. A service got slower. What do you do first?**
Measure before changing anything. Check the service metrics to see what changed, reproduce it with a benchmark, compare runs with `benchstat`, and use a profile to find the lines that cost the time. Only then change code, and measure again.
*A weak answer misses:* the order: measure, find, change, measure. See [benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/), [profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/) and [when to optimize](/blog/go-efficiency-workflow-raer-tfbo-hardware-memory/).

**17. In a CPU profile, what is the difference between `flat` and `cum`?**
`flat` is time spent in the function's own code. `cum` (cumulative) also includes everything the function called. A function with a small `flat` and a large `cum` is mostly a caller; the real cost is below it.
*A weak answer misses:* that you read `flat` to find where the CPU burns and `cum` to find which call path leads there. See [profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/).

**18. Why can a Go service be slow in Kubernetes while its CPU graph looks fine?**
A CPU limit is enforced in short time slices, and a service that uses its share early in a slice is paused until the next one, even if the average over a minute is low. That pause is called throttling and shows up as latency.
*A weak answer misses:* the metric that shows it, the throttled-seconds counter. See [Go in production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/) and [benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/).

**19. When can `sync.Pool` hurt?**
A pool keeps objects around so you can reuse them instead of allocating. The objects it holds still count as memory, and the runtime may drop them at any collection, so you pay for the cache and still cannot rely on a hit.
*A weak answer misses:* that a pool can raise peak memory. See [optimization patterns](/blog/go-three-rs-optimization-patterns-streaming-pooling/).

### Card 1: `append` on a shared slice

Slices are small headers over an array. `a` was made with length 3 and capacity 4, so there is one free slot, and both `append` calls use it.

<GoP20SliceSharing />

```go
package main

import "fmt"

func main() {
	a := make([]int, 3, 4)
	b := append(a, 1)
	c := append(a, 2)
	fmt.Println(a, b, c)
	fmt.Println(len(a), cap(a))
}
```

<TerminalOutput command="go run ." label="Go 1.27.1 · darwin/arm64" caption="Captured from a real run. b and c print the same last element because both appends wrote into slot 3.">
```text
[0 0 0] [0 0 0 2] [0 0 0 2]
3 4
```
</TerminalOutput>

The follow-up question is usually "how do you make `b` independent?". Copy first, or use a full slice expression such as `a[:3:3]` so the capacity is 3 and the next `append` must allocate. More in [Go memory](/blog/go-memory-data-types-slices-maps-strings/).

### Card 2: `defer` in a loop

```go
package main

import "fmt"

func main() {
	for i := 0; i < 3; i++ {
		defer fmt.Println("defer", i)
	}
	fmt.Println("loop done")
}
```

<TerminalOutput command="go run ." label="Go 1.27.1 · darwin/arm64" caption="The three deferred calls run after the last Println, in reverse order.">
```text
loop done
defer 2
defer 1
defer 0
```
</TerminalOutput>

`i` is copied at each `defer` line, which is why you see `2`, `1`, `0` and not `3` three times. In a real program a `defer file.Close()` inside a loop keeps every file open until the function returns, so move the loop body into its own function. See [errors and defer](/blog/go-errors-defer-panic/).

### Card 3: `select` with two ready cases

Both channels hold a value before each `select`, so both cases can proceed. The program counts which one wins in 1000 rounds.

<GoP20SelectReadiness />

```go
package main

import "fmt"

func main() {
	a := make(chan string, 1)
	b := make(chan string, 1)
	counts := map[string]int{}
	for i := 0; i < 1000; i++ {
		a <- "a"
		b <- "b"
		select {
		case v := <-a:
			counts[v]++
			<-b
		case v := <-b:
			counts[v]++
			<-a
		}
	}
	fmt.Println("a:", counts["a"], "b:", counts["b"])
}
```

<TerminalOutput command="go run ." label="Go 1.27.1 · darwin/arm64" caption="One real run. The program is random: run it again and the two numbers change, staying near 500 each.">
```text
a: 484 b: 516
```
</TerminalOutput>

The [Go language specification](https://go.dev/ref/spec#Select_statements) says that when several cases can proceed, one is chosen by a uniform pseudo-random selection. The shape of the question to expect: "which case runs first?" The answer is "no guarantee", and code that needs a priority has to check the preferred channel first in its own `select` with a `default`. See [the scheduler](/blog/go-concurrency-scheduler-channels-context-mutexes/) and [goroutines and channels](/blog/go-goroutines-channels-select/).

### Card 4: a nil pointer inside an `error`

```go
package main

import "fmt"

type MyErr struct{}

func (*MyErr) Error() string { return "my error" }

func find(fail bool) error {
	var e *MyErr
	if fail {
		e = &MyErr{}
	}
	return e
}

func main() {
	err := find(false)
	fmt.Println(err == nil)
	fmt.Printf("%T %v\n", err, err == nil)
}
```

<TerminalOutput command="go run ." label="Go 1.27.1 · darwin/arm64" caption="err == nil is false even though find(false) never created a MyErr. %T shows the type slot is filled.">
```text
false
*main.MyErr false
```
</TerminalOutput>

`find` returns the variable `e`, which has type `*MyErr`. Converting it to `error` fills the interface's type slot, so the interface is not nil. The Go FAQ has an entry on exactly this: [Why is my nil error value not equal to nil?](https://go.dev/doc/faq#nil_error) The fix is to `return nil` on the success path. See [abstractions](/blog/go-abstractions-interfaces-generics-errors/).

### Card 5: closures over a loop variable, before and after Go 1.22

```go
import "fmt"

func main() {
	var fs []func()

	}
	for _, f := range fs {
		f()
	}

}
```

```text
// loop22/go.mod

```

## Part 3: Live coding

In a coding round the sequence matters more than the final code. A good run looks like this:

1. **Ask what you need**: input and output shapes, what happens on error, what happens when the caller gives up.
2. **Write the simplest version that works**, and say out loud what it does not handle yet.
3. **Take the follow-ups one at a time**: limits, cancellation, concurrency, tests.
4. **Finish with a test** that would fail if the property you claim were broken.

Every solution below ships with a test. The outputs are the real `go test -race -v` results on Go 1.27.1; `-race` turns on the race detector described in [the scheduler](/blog/go-concurrency-scheduler-channels-context-mutexes/). The tests use `atomic.Int32`, a counter that is safe to change from several goroutines, as in [context and mutexes](/blog/go-context-timeouts-mutexes/).

### Task 1: a bounded parallel fetcher

> "Given a list of URLs, fetch them in parallel, but never more than N at a time. Return the results in input order."

A first working version starts one goroutine per URL and waits for all of them. Each goroutine writes only its own slot in `results`, so there is no race on the slice.

```go
package fetcher

import "sync"

type Result struct {
	URL  string
	Body string
	Err  error
}

func FetchAll(urls []string, fetch func(string) (string, error)) []Result {
	results := make([]Result, len(urls))
	var wg sync.WaitGroup
	for i, u := range urls {
		wg.Add(1)
		go func() {
			defer wg.Done()
			body, err := fetch(u)
			results[i] = Result{u, body, err}
		}()
	}
	wg.Wait()
	return results
}
```

It works for ten URLs and breaks at a hundred thousand: there is no limit, no way to cancel and no context passed to `fetch`. The interviewer's follow-ups come in that order:

- **"Limit it to N."** Use a buffered channel as a semaphore, as in [concurrency patterns](/blog/go-concurrency-patterns-worker-pools-pipelines/). Send before starting the work, receive when it ends.
- **"What if the caller gives up?"** Pass a `context.Context` into `fetch`, and stop starting new calls when it is done. See [context and mutexes](/blog/go-context-timeouts-mutexes/).
- **"How do I test it without real HTTP?"** Take `fetch` as a function parameter. A test passes a fake that sleeps and counts how many calls run at the same time.

The final version:

```go
package fetcher

import (
	"context"
	"sync"
)

// Result is the outcome for one URL. Results come back in the same order as the input.
type Result struct {
	URL  string
	Body string
	Err  error
}

// FetchAll calls fetch for every URL with at most limit calls running at once.
// It stops starting new calls when ctx is done; those URLs get ctx.Err().
func FetchAll(ctx context.Context, urls []string, limit int, fetch func(context.Context, string) (string, error)) []Result {
	if limit < 1 {
		limit = 1
	}
	results := make([]Result, len(urls))
	sem := make(chan struct{}, limit) // a buffered channel used as a counter of free slots
	var wg sync.WaitGroup

	for i, u := range urls {
		results[i].URL = u
		select {
		case sem <- struct{}{}: // take a slot, blocks while limit calls are running
		case <-ctx.Done():
			results[i].Err = ctx.Err()
			continue
		}
		if ctx.Err() != nil { // select picks at random when both cases are ready, so check again
			<-sem
			results[i].Err = ctx.Err()
			continue
		}
		wg.Add(1)
		go func() {
			defer wg.Done()
			defer func() { <-sem }() // give the slot back
			body, err := fetch(ctx, u)
			results[i].Body, results[i].Err = body, err
		}()
	}
	wg.Wait()
	return results
}
```

Two details are worth saying out loud. The `select` in the loop picks at random when a slot is free and the context is done at the same moment, so the code checks `ctx.Err()` once more after taking a slot. Without that second check, a test that cancels can still see one extra call start; the first version of this very test did, on a real run. Also, `results[i]` is written by exactly one goroutine, so no lock is needed.

The tests check the two properties you claim: the limit holds, and a cancel stops new work.

### Task 2: a cache with expiry that is safe for concurrent use

> "Write an in-memory cache where each entry expires after a fixed time. Many goroutines will use it."

The first version is a map and a `sync.Mutex`: `Set` and `Get` each lock, touch the map, unlock. A plain map is not safe for concurrent use, so the lock is not optional. Then the follow-ups:

- **"Add expiry."** Store the expiry time next to the value. `Get` treats an entry whose time has passed as missing and deletes it. This is lazy expiry: nothing runs in the background.
- **"Entries nobody reads again stay forever."** Add `Sweep`, which deletes every expired entry. A caller can run it on a ticker. A background goroutine inside the cache would need a `Close` so it can stop.
- **"How do you test expiry without waiting a minute?"** Give the cache a clock it can be handed. The test moves a fake clock by hand.

```go
package ttlcache

import (
	"sync"
	"time"
)

type entry[V any] struct {
	value   V
	expires time.Time
}

// Cache holds values for a fixed time. It is safe for concurrent use.
type Cache[K comparable, V any] struct {
	mu    sync.Mutex
	ttl   time.Duration
	now   func() time.Time // replaced by a fake clock in tests
	items map[K]entry[V]
}

func New[K comparable, V any](ttl time.Duration) *Cache[K, V] {
	return &Cache[K, V]{ttl: ttl, now: time.Now, items: make(map[K]entry[V])}
}

func (c *Cache[K, V]) Set(key K, value V) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.items[key] = entry[V]{value: value, expires: c.now().Add(c.ttl)}
}

// Get returns the value if it is present and not expired.
// An expired entry is deleted on the way out (lazy expiry).
func (c *Cache[K, V]) Get(key K) (V, bool) {
	c.mu.Lock()
	defer c.mu.Unlock()
	e, ok := c.items[key]
	if !ok {
		var zero V
		return zero, false
	}
	if !c.now().Before(e.expires) {
		delete(c.items, key)
		var zero V
		return zero, false
	}
	return e.value, true
}

// Sweep deletes every expired entry and returns how many it removed.
func (c *Cache[K, V]) Sweep() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	n := 0
	now := c.now()
	for k, e := range c.items {
		if !now.Before(e.expires) {
			delete(c.items, k)
			n++
		}
	}
	return n
}

func (c *Cache[K, V]) Len() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return len(c.items)
}
```

The type parameters `K` and `V` are generics from [structs and interfaces](/blog/go-structs-methods-interfaces/). The `now` field is the clock: the real one in production, a fake in tests.

### Task 3: a token-bucket rate limiter

> "Allow at most R requests per second, but let a short burst of B through."

Picture a bucket that holds up to B tokens. Each allowed request takes one token out. The bucket gets tokens back at a steady rate, and it never holds more than B. If it is empty, the request is refused.

<GoP20BucketRefill />

A tempting first version is a goroutine that puts a token into a buffered channel every `1/R` seconds. It works, but it needs a goroutine that must be stopped, and it wakes up even when nobody calls. The follow-up that reveals this: "what happens when the limiter is dropped?" The goroutine keeps running.

The version below has no goroutine. It does not add tokens on a timer; it works out how many tokens have come back since the last call, each time you ask.

```go
package bucket

import (
	"sync"
	"time"
)

// Limiter is a token bucket: it holds up to burst tokens and refills at rate tokens per second.
// Every allowed call spends one token. It is safe for concurrent use.
type Limiter struct {
	mu     sync.Mutex
	rate   float64 // tokens added per second
	burst  float64 // bucket size
	tokens float64
	last   time.Time
	now    func() time.Time // replaced by a fake clock in tests
}

func New(rate float64, burst int) *Limiter {
	l := &Limiter{rate: rate, burst: float64(burst), tokens: float64(burst), now: time.Now}
	l.last = l.now()
	return l
}

// Allow reports whether one call may go ahead right now.
func (l *Limiter) Allow() bool {
	l.mu.Lock()
	defer l.mu.Unlock()

	now := l.now()
	l.tokens += now.Sub(l.last).Seconds() * l.rate // refill for the time that passed
	if l.tokens > l.burst {
		l.tokens = l.burst
	}
	l.last = now

	if l.tokens < 1 {
		return false
	}
	l.tokens--
	return true
}
```

```go
	l, clock := newTestLimiter(2, 3) // 2 tokens per second, bucket of 3

			t.Fatalf("call %d should use the initial burst", i+1)
		}

	if l.Allow() {
		t.Fatal("4th call should be refused, the bucket is empty")

	if !l.Allow() {
		t.Fatal("one token should be back after 500ms")
	}
	if l.Allow() {
		t.Fatal("only one token was added")
	}
}

func TestRefillStopsAtBurst(t *testing.T) {

	l.Allow()

	allowed := 0

		if l.Allow() {
			allowed++
		}
	}
	if allowed != 2 {
		t.Fatalf("allowed %d calls after a long wait, want 2 (the burst size)", allowed)
	}
}

func TestConcurrentCallsNeverExceedBurst(t *testing.T) {
	l, _ := newTestLimiter(1, 50) // the clock never moves, so no refill

			}

	}
}
```

## Key takeaways

- **Say the idea, then the trap.** A model answer names the mechanism and one way it surprises you. The links under each question lead to the full explanation.
- **Slices and interfaces fail quietly.** A shared array under `append` and a typed nil in an `error` both compile and run; only the output tells you.
- **Some outputs are not fixed.** `select` with several ready cases is random, and loop-variable behaviour follows the `go` line in `go.mod`. Say which, and do not guess one answer.

## Phần 1: Câu hỏi khái niệm, theo tầng

Đọc câu hỏi, trả lời thành tiếng, rồi mới đọc đáp án mẫu. Nếu bạn không nói nổi trong ba mươi giây, hãy mở bài được dẫn.

### Tầng 1: nền tảng

**1. Array khác slice thế nào?**
Array có độ dài cố định và độ dài đó là một phần của kiểu, gán array sẽ chép mọi phần tử. Slice là một header nhỏ (con trỏ tới array, độ dài và capacity) bọc trên một array, gán slice chỉ chép header. Vì vậy hai slice có thể dùng chung một array.
*Câu trả lời yếu thiếu:* header, và chuyện `append` có thể ghi vào array mà slice khác vẫn đang nhìn. Xem [slice, map và string](/blog/go-slices-maps-strings/) và, cho góc nhìn bộ nhớ, [Go memory](/blog/go-memory-data-types-slices-maps-strings/).

**2. Zero value là gì, và làm được gì với map nil và slice nil?**
Mỗi biến bắt đầu bằng zero value của kiểu: `0`, `""`, `false`, `nil`. Bạn đọc được từ map nil và `append` được vào slice nil. Ghi vào map nil thì panic.
*Câu trả lời yếu thiếu:* sự khác nhau giữa đọc và ghi. Thẻ 6 ở phần đoán kết quả bên dưới chính là chuyện này. Xem [kiểu và con trỏ](/blog/go-variables-types-pointers-functions/).

**3. Khi nào dùng pointer receiver thay cho value receiver?**
Dùng pointer receiver khi method đổi giá trị, hoặc khi giá trị lớn hay chứa thứ không được chép, như mutex. Giữ một loại cho mỗi type để method set dễ đoán.
*Câu trả lời yếu thiếu:* bản sao mà value receiver tạo ra, và việc method set của type quyết định nó thỏa interface nào. Xem [struct và interface](/blog/go-structs-methods-interfaces/).

**4. Xử lý và bọc lỗi thế nào?**
Lỗi là một giá trị bình thường, trả về ở kết quả cuối. Kiểm tra ngay, thêm ngữ cảnh bằng `fmt.Errorf("...: %w", err)`, và kiểm tra nguyên nhân bằng `errors.Is` hoặc `errors.As`. Mỗi lỗi chỉ xử lý một lần: hoặc log, hoặc trả về.
*Câu trả lời yếu thiếu:* `%w`, và việc `panic` không dành cho lỗi thông thường. Xem [lỗi và defer](/blog/go-errors-defer-panic/).

**5. Đối số của lời gọi defer được tính lúc nào, và các defer chạy theo thứ tự nào?**
Đối số được tính ngay tại dòng `defer`. Bản thân lời gọi chạy khi hàm bao ngoài return, theo thứ tự vào sau ra trước. Vì vậy `defer` trong vòng lặp chờ hàm kết thúc chứ không chờ hết lượt lặp (thẻ 2 bên dưới).
*Câu trả lời yếu thiếu:* trường hợp vòng lặp, và chuyện đóng file bằng `defer` trong vòng lặp giữ mọi file mở đến cuối hàm. Xem [lỗi và defer](/blog/go-errors-defer-panic/).

### Tầng 2: đồng thời và một service

**6. Dừng một goroutine bằng cách nào?**
Không thể giết goroutine từ bên ngoài. Bạn phải cho nó một cách để dừng: một `context.Context` nó kiểm tra, hoặc một channel nó nhận từ đó. Mỗi goroutine bạn khởi chạy cần có câu trả lời cho "cái gì kết thúc nó?".
*Câu trả lời yếu thiếu:* rò rỉ, tức một goroutine bị chặn mãi trên channel mà không ai dùng nữa. Xem [goroutine và channel](/blog/go-goroutines-channels-select/) và [context và mutex](/blog/go-context-timeouts-mutexes/).

**7. Channel có buffer khác channel không buffer thế nào?**
Gửi vào channel không buffer sẽ chờ tới khi có bên nhận, nên hai goroutine gặp nhau. Channel có buffer cho phép bên gửi đi tiếp tới khi buffer đầy. Buffer đầy thì bên gửi bị chặn, đó là cách có back-pressure.
*Câu trả lời yếu thiếu:* chỉ bên gửi nên đóng channel, và nhận từ channel đã đóng trả về zero value. Xem [goroutine và channel](/blog/go-goroutines-channels-select/).

**8. Giới hạn số goroutine chạy cùng lúc bằng cách nào?**
Hoặc khởi chạy số worker cố định cùng đọc một channel job, hoặc dùng channel có buffer làm semaphore: gửi vào trước khi làm việc, nhận ra khi xong. Bài live coding số 1 bên dưới dùng semaphore.
*Câu trả lời yếu thiếu:* cái gì dừng bên sản xuất khi context bị hủy. Xem [mẫu đồng thời](/blog/go-concurrency-patterns-worker-pools-pipelines/).

**9. Server `net/http` cần những timeout nào?**
Zero value của mỗi timeout trên `http.Server` nghĩa là "không giới hạn", nên một client chậm có thể giữ kết nối bao lâu tùy thích. Đặt ít nhất timeout đọc header, và cho handler một context có deadline.
*Câu trả lời yếu thiếu:* mặc định là không giới hạn. Xem [HTTP service](/blog/go-http-service-net-http-json-middleware/) và, cho chuyện gì hỏng khi có tải thật, [Go trên production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/).

### Tầng 3: Go chạy bên trong ra sao

**10. Vì sao `append` có thể đổi một slice mà bạn không truyền vào?**
Nếu capacity còn chỗ, `append` ghi vào array hiện có và trả về header có độ dài lớn hơn. Mọi slice khác trên array đó đều thấy lần ghi. Khi capacity đầy, `append` cấp phát array mới và chép sang, các slice cũ thôi dùng chung.
*Câu trả lời yếu thiếu:* chỉ đọc code thì không biết mình đang ở trường hợp nào. Thẻ 1 và hình đầu tiên bên dưới cho thấy điều này. Xem [Go memory](/blog/go-memory-data-types-slices-maps-strings/).

**11. Typed nil là gì, và vì sao một error có thể khác nil khi chứa con trỏ nil?**
Giá trị interface là một cặp gồm kiểu và giá trị. Nếu bạn trả một `*MyErr` nil dưới dạng `error`, ô kiểu đã có nội dung, nên interface không nil dù con trỏ bên trong thì nil. Ở nhánh thành công, hãy trả `nil` trơn.
*Câu trả lời yếu thiếu:* hai ô trong interface. Thẻ 4 bên dưới. Xem [abstraction](/blog/go-abstractions-interfaces-generics-errors/).

**12. Mô tả cách scheduler chạy goroutine.**
Go ghép nhiều goroutine (G) lên một ít thread của hệ điều hành (M). Mỗi processor logic (P), mỗi cái ứng với một đơn vị của `GOMAXPROCS`, có hàng đợi các goroutine sẵn sàng chạy và cho một thread mượn chỗ. Khi goroutine bị chặn ở mạng, thread chuyển sang goroutine kế tiếp; khi một P cạn việc, nó lấy bớt việc của P khác.
*Câu trả lời yếu thiếu:* chuyện gì xảy ra trong một system call bị chặn, và việc work stealing. Xem [scheduler](/blog/go-concurrency-scheduler-channels-context-mutexes/).

**13. Data race khác race condition thế nào?**
Data race là hai goroutine đụng vào cùng một vùng nhớ cùng lúc, ít nhất một bên ghi, và không đồng bộ. Race condition là lỗi phụ thuộc thời điểm, và có thể tồn tại mà không có data race, ví dụ mọi truy cập đều giữ lock nhưng thứ tự của hai bước vẫn quan trọng.
*Câu trả lời yếu thiếu:* `go test -race` chỉ tìm được loại đầu. Xem [scheduler](/blog/go-concurrency-scheduler-channels-context-mutexes/).

### Tầng 4: hiệu năng

**14. `GOGC` và `GOMEMLIMIT` làm gì, và khi nào `GOMEMLIMIT` có ích?**
`GOGC` quy định heap được phình thêm bao nhiêu so với dữ liệu còn sống trước lần thu gom kế tiếp (mặc định `100` nghĩa là được gấp đôi). `GOMEMLIMIT` là trần mềm cho bộ nhớ Go quản lý: càng gần trần, bộ thu gom chạy càng thường. Nó có ích trong container có giới hạn bộ nhớ cứng, khi bạn đặt nó thấp hơn giới hạn đó một chút.
*Câu trả lời yếu thiếu:* nó là trần mềm, và bộ thu gom có thể đốt CPU khi dữ liệu sống nằm sát trần. Xem [phần cứng và GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/).

**15. Escape analysis là gì, và vì sao quan trọng?**
Compiler quyết định một giá trị sống được trên stack, được giải phóng miễn phí khi hàm return, hay phải lên heap, nơi garbage collector phải dọn. Bạn xem được quyết định đó bằng `-gcflags=-m`. Ít cấp phát heap hơn nghĩa là GC có ít việc hơn.
*Câu trả lời yếu thiếu:* trả về con trỏ tới biến cục bộ thường là thứ đẩy nó lên heap. Xem [phần cứng và GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/) và [khi nào nên tối ưu](/blog/go-efficiency-workflow-raer-tfbo-hardware-memory/).

**16. Một service chậm đi. Việc đầu tiên bạn làm là gì?**
Đo trước khi sửa gì. Xem metric của service để biết cái gì đã đổi, tái hiện bằng benchmark, so các lần chạy bằng `benchstat`, và dùng profile tìm những dòng ngốn thời gian. Chỉ sau đó mới sửa code, rồi đo lại.
*Câu trả lời yếu thiếu:* thứ tự: đo, tìm, sửa, đo lại. Xem [benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/), [profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/) và [khi nào nên tối ưu](/blog/go-efficiency-workflow-raer-tfbo-hardware-memory/).

**17. Trong CPU profile, `flat` khác `cum` thế nào?**
`flat` là thời gian ở trong code của chính hàm đó. `cum` (cộng dồn) tính cả mọi thứ hàm đó gọi. Hàm có `flat` nhỏ mà `cum` lớn chủ yếu là bên gọi; chi phí thật nằm bên dưới.
*Câu trả lời yếu thiếu:* đọc `flat` để biết CPU cháy ở đâu, đọc `cum` để biết đường gọi nào dẫn tới đó. Xem [profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/).

**18. Vì sao service Go có thể chậm trên Kubernetes dù biểu đồ CPU trông ổn?**
Giới hạn CPU được áp theo những lát thời gian ngắn, và service dùng hết phần của mình sớm trong một lát sẽ bị tạm dừng đến lát sau, kể cả khi trung bình một phút vẫn thấp. Việc tạm dừng đó gọi là throttling và hiện ra thành độ trễ.
*Câu trả lời yếu thiếu:* metric cho thấy nó, bộ đếm throttled-seconds. Xem [Go trên production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/) và [benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/).

**19. Khi nào `sync.Pool` có hại?**
Pool giữ đối tượng lại để tái sử dụng thay vì cấp phát. Các đối tượng nó giữ vẫn tính vào bộ nhớ, và runtime có thể bỏ chúng ở bất kỳ lần thu gom nào, nên bạn trả giá cho cache mà vẫn không chắc có trúng.
*Câu trả lời yếu thiếu:* pool có thể làm đỉnh bộ nhớ tăng. Xem [mẫu tối ưu](/blog/go-three-rs-optimization-patterns-streaming-pooling/).

### Thẻ 3: `select` khi hai case cùng sẵn sàng

Cả hai channel đều có giá trị trước mỗi `select`, nên cả hai case đều chạy được. Chương trình đếm case nào thắng trong 1000 vòng.

<GoP20SelectReadiness />

```go
package main

import "fmt"

func main() {
	a := make(chan string, 1)
	b := make(chan string, 1)
	counts := map[string]int{}
	for i := 0; i < 1000; i++ {
		a <- "a"
		b <- "b"
		select {
		case v := <-a:
			counts[v]++
			<-b
		case v := <-b:
			counts[v]++
			<-a
		}
	}
	fmt.Println("a:", counts["a"], "b:", counts["b"])
}
```

<TerminalOutput command="go run ." label="Go 1.27.1 · darwin/arm64" caption="Một lần chạy thật. Chương trình này ngẫu nhiên: chạy lại thì hai con số đổi, vẫn quanh 500 mỗi bên.">
```text

```
</TerminalOutput>

[Đặc tả ngôn ngữ Go](https://go.dev/ref/spec#Select_statements) nói rằng khi nhiều case chạy được, một case được chọn theo uniform pseudo-random selection. Dạng câu hỏi nên chờ: "case nào chạy trước?" Câu trả lời là "không có đảm bảo", và code cần ưu tiên thì phải kiểm tra channel ưu tiên trước trong một `select` riêng có `default`. ### Thẻ 4: con trỏ nil nằm trong một `error`

```go
package main

import "fmt"

type MyErr struct{}

func (*MyErr) Error() string { return "my error" }

func find(fail bool) error {
	var e *MyErr
	if fail {
		e = &MyErr{}
	}
	return e
}

func main() {
	err := find(false)
	fmt.Println(err == nil)
	fmt.Printf("%T %v\n", err, err == nil)
}
```

<TerminalOutput command="go run ." label="Go 1.27.1 · darwin/arm64" caption="err == nil là false dù find(false) chưa hề tạo MyErr. %T cho thấy ô kiểu đã có nội dung.">

</TerminalOutput>

`find` trả về biến `e` có kiểu `*MyErr`. Chuyển nó sang `error` làm ô kiểu của interface có nội dung, nên interface không nil. Go FAQ có một mục đúng về chuyện này: [Why is my nil error value not equal to nil?](https://go.dev/doc/faq#nil_error) Cách sửa là `return nil` ở nhánh thành công. ## Phần 3: Live coding

Trong vòng viết code, thứ tự làm việc quan trọng hơn code cuối cùng. Một buổi làm tốt trông thế này:

1. **Hỏi điều cần biết**: hình dạng đầu vào và đầu ra, chuyện gì xảy ra khi lỗi, chuyện gì xảy ra khi bên gọi bỏ cuộc.
2. **Viết bản đơn giản nhất chạy được**, và nói thành tiếng nó chưa xử lý gì.
3. **Nhận từng câu hỏi nối tiếp một**: giới hạn, hủy, đồng thời, test.
4. **Kết thúc bằng một test** sẽ fail nếu tính chất bạn nói bị phá.

Mỗi lời giải bên dưới đều có test. Kết quả là `go test -race -v` thật trên Go 1.27.1; `-race` bật race detector đã nói ở [scheduler](/blog/go-concurrency-scheduler-channels-context-mutexes/). Các test dùng `atomic.Int32`, một bộ đếm an toàn khi nhiều goroutine cùng đổi, như trong [context và mutex](/blog/go-context-timeouts-mutexes/).

### Bài 1: bộ fetch song song có giới hạn

> "Cho một danh sách URL, fetch song song nhưng không quá N cái cùng lúc. Trả kết quả theo thứ tự đầu vào."

Bản đầu chạy được là khởi chạy một goroutine cho mỗi URL rồi chờ tất cả. Mỗi goroutine chỉ ghi vào ô của chính nó trong `results`, nên không có race trên slice.

```go
package fetcher

import "sync"

type Result struct {
	URL  string
	Body string
	Err  error
}

func FetchAll(urls []string, fetch func(string) (string, error)) []Result {
	results := make([]Result, len(urls))
	var wg sync.WaitGroup
	for i, u := range urls {
		wg.Add(1)
		go func() {
			defer wg.Done()
			body, err := fetch(u)
			results[i] = Result{u, body, err}
		}()
	}
	wg.Wait()
	return results
}
```

Nó chạy tốt với mười URL và hỏng ở một trăm nghìn: không có giới hạn, không có cách hủy và không truyền context vào `fetch`. Các câu hỏi nối tiếp của người phỏng vấn đến theo thứ tự đó:

- **"Giới hạn ở N."** Dùng channel có buffer làm semaphore, như ở [mẫu đồng thời](/blog/go-concurrency-patterns-worker-pools-pipelines/). Gửi vào trước khi làm việc, nhận ra khi xong.
- **"Nếu bên gọi bỏ cuộc thì sao?"** Truyền `context.Context` vào `fetch`, và ngừng khởi chạy lời gọi mới khi nó đã xong. Xem [context và mutex](/blog/go-context-timeouts-mutexes/).
- **"Test thế nào mà không cần HTTP thật?"** Nhận `fetch` làm tham số hàm. Test truyền vào một hàm giả có sleep và đếm số lời gọi chạy cùng lúc.

Bản cuối:

```go
package fetcher

import (
	"context"
	"sync"
)

// Result is the outcome for one URL. Results come back in the same order as the input.
type Result struct {
	URL  string
	Body string
	Err  error
}

// FetchAll calls fetch for every URL with at most limit calls running at once.
// It stops starting new calls when ctx is done; those URLs get ctx.Err().
func FetchAll(ctx context.Context, urls []string, limit int, fetch func(context.Context, string) (string, error)) []Result {
	if limit < 1 {
		limit = 1
	}
	results := make([]Result, len(urls))
	sem := make(chan struct{}, limit) // a buffered channel used as a counter of free slots
	var wg sync.WaitGroup

	for i, u := range urls {
		results[i].URL = u
		select {
		case sem <- struct{}{}: // take a slot, blocks while limit calls are running
		case <-ctx.Done():
			results[i].Err = ctx.Err()
			continue
		}
		if ctx.Err() != nil { // select picks at random when both cases are ready, so check again
			<-sem
			results[i].Err = ctx.Err()
			continue
		}
		wg.Add(1)
		go func() {
			defer wg.Done()
			defer func() { <-sem }() // give the slot back
			body, err := fetch(ctx, u)
			results[i].Body, results[i].Err = body, err
		}()
	}
	wg.Wait()
	return results
}
```

Có hai chi tiết nên nói thành tiếng. `select` trong vòng lặp chọn ngẫu nhiên khi vừa có ô trống vừa có context đã xong, nên code kiểm tra `ctx.Err()` thêm một lần sau khi lấy ô. Thiếu lần kiểm tra thứ hai, test có hủy vẫn có thể thấy thêm một lời gọi chạy; bản đầu tiên của chính test này đã gặp đúng như vậy trong một lần chạy thật. Ngoài ra, `results[i]` chỉ do đúng một goroutine ghi, nên không cần lock.

Các test kiểm tra hai tính chất bạn khẳng định: giới hạn được giữ, và hủy thì ngừng việc mới.

```go

	"context"
	"errors"
	"fmt"

		n := running.Add(1)
		defer running.Add(-1)
		for { // record the highest number of calls seen at the same time
			p := peak.Load()
			if n <= p || peak.CompareAndSwap(p, n) {
				break
			}
		}
		time.Sleep(10 * time.Millisecond)
		if u == "bad" {
			return "", errors.New("boom")
		}
		return "body of " + u, nil
	}

	urls := []string{"a", "b", "bad", "d", "e", "f", "g", "h"}

		t.Fatalf("peak concurrency %d, want <= 3", peak.Load())

		if got[i].URL != u {
			t.Fatalf("result %d is for %q, want %q", i, got[i].URL, u)
		}
	}
	if got[2].Err == nil || got[0].Err != nil || got[0].Body != "body of a" {
		t.Fatalf("unexpected results: %+v", got)
	}

	fetch := func(ctx context.Context, u string) (string, error) {

			cancel() // cancel while the first batch is running
		}

		return "", ctx.Err()
	}

	urls := make([]string, 10)
	for i := range urls {
		urls[i] = fmt.Sprint("u", i)
	}
	got := FetchAll(ctx, urls, 2, fetch)

	if started.Load() != 2 {
		t.Fatalf("started %d calls, want exactly 2 (the two that ran before cancel)", started.Load())
	}
	for _, r := range got {
		if !errors.Is(r.Err, context.Canceled) {
			t.Fatalf("every URL should report context.Canceled, got %+v", r)
		}
	}
}
```

### Bài 2: cache có hết hạn, an toàn khi dùng đồng thời

> "Viết một cache trong bộ nhớ, mỗi mục hết hạn sau một khoảng thời gian cố định. Nhiều goroutine sẽ dùng nó."

Bản đầu là một map và một `sync.Mutex`: `Set` và `Get` đều khóa, chạm vào map, rồi mở khóa. Map thường không an toàn khi dùng đồng thời, nên lock là bắt buộc. Sau đó là các câu nối tiếp:

- **"Thêm hết hạn."** Lưu thời điểm hết hạn cạnh giá trị. `Get` coi mục đã quá hạn là không có và xóa nó. Đây là hết hạn lười (lazy expiry): không có gì chạy nền.
- **"Mục không ai đọc lại cứ nằm mãi."** Thêm `Sweep`, xóa mọi mục đã hết hạn. Bên gọi có thể chạy nó theo ticker. Một goroutine nền bên trong cache thì cần `Close` để dừng.
- **"Test hết hạn thế nào mà không chờ một phút?"** Cho cache một đồng hồ có thể truyền vào. Test chỉnh đồng hồ giả bằng tay.

```go
package ttlcache

import (
	"sync"
	"time"
)

type entry[V any] struct {
	value   V
	expires time.Time
}

// Cache holds values for a fixed time. It is safe for concurrent use.
type Cache[K comparable, V any] struct {
	mu    sync.Mutex
	ttl   time.Duration
	now   func() time.Time // replaced by a fake clock in tests
	items map[K]entry[V]
}

func New[K comparable, V any](ttl time.Duration) *Cache[K, V] {
	return &Cache[K, V]{ttl: ttl, now: time.Now, items: make(map[K]entry[V])}
}

func (c *Cache[K, V]) Set(key K, value V) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.items[key] = entry[V]{value: value, expires: c.now().Add(c.ttl)}
}

// Get returns the value if it is present and not expired.
// An expired entry is deleted on the way out (lazy expiry).
func (c *Cache[K, V]) Get(key K) (V, bool) {
	c.mu.Lock()
	defer c.mu.Unlock()
	e, ok := c.items[key]
	if !ok {
		var zero V
		return zero, false
	}
	if !c.now().Before(e.expires) {
		delete(c.items, key)
		var zero V
		return zero, false
	}
	return e.value, true
}

// Sweep deletes every expired entry and returns how many it removed.
func (c *Cache[K, V]) Sweep() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	n := 0
	now := c.now()
	for k, e := range c.items {
		if !now.Before(e.expires) {
			delete(c.items, k)
			n++
		}
	}
	return n
}

func (c *Cache[K, V]) Len() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return len(c.items)
}
```

Tham số kiểu `K` và `V` là generics từ [struct và interface](/blog/go-structs-methods-interfaces/). Trường `now` là đồng hồ: đồng hồ thật khi chạy thật, đồng hồ giả trong test.

```go
import (
	"fmt"
	"sync"
	"testing"
	"time"
)

// fakeClock lets a test move time by hand instead of sleeping.
type fakeClock struct {
	mu sync.Mutex
	t  time.Time
}

func (f *fakeClock) Now() time.Time {
	f.mu.Lock()
	defer f.mu.Unlock()
	return f.t
}

func (f *fakeClock) Advance(d time.Duration) {
	f.mu.Lock()
	defer f.mu.Unlock()
	f.t = f.t.Add(d)
}

func newTestCache(ttl time.Duration) (*Cache[string, int], *fakeClock) {
	clock := &fakeClock{t: time.Unix(1_000, 0)}
	c := New[string, int](ttl)
	c.now = clock.Now
	return c, clock
}

func TestGetExpires(t *testing.T) {
	c, clock := newTestCache(time.Minute)
	c.Set("a", 1)

	if v, ok := c.Get("a"); !ok || v != 1 {
		t.Fatalf("fresh entry: got %v, %v", v, ok)
	}
	clock.Advance(59 * time.Second)
	if _, ok := c.Get("a"); !ok {
		t.Fatal("entry should live until the full ttl has passed")
	}
	clock.Advance(time.Second) // exactly ttl: expired
	if _, ok := c.Get("a"); ok {
		t.Fatal("entry should be expired at ttl")
	}
	if c.Len() != 0 {
		t.Fatalf("expired entry should be deleted, Len = %d", c.Len())
	}
}

func TestSweep(t *testing.T) {
	c, clock := newTestCache(time.Minute)
	c.Set("old", 1)
	clock.Advance(40 * time.Second)
	c.Set("new", 2)
	clock.Advance(30 * time.Second) // "old" is 70s old, "new" is 30s old

	if n := c.Sweep(); n != 1 {
		t.Fatalf("Sweep removed %d, want 1", n)
	}
	if _, ok := c.Get("new"); !ok {
		t.Fatal("new entry should survive the sweep")
	}
}

func TestConcurrentUse(t *testing.T) {
	c, _ := newTestCache(time.Minute)
	var wg sync.WaitGroup
	for g := 0; g < 8; g++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := 0; i < 1000; i++ {
				key := fmt.Sprint("k", i%10)
				c.Set(key, i)
				c.Get(key)
				if i%100 == 0 {
					c.Sweep()
				}
			}
		}()
	}
	wg.Wait()
	if c.Len() > 10 {
		t.Fatalf("Len = %d, want <= 10", c.Len())
	}
}
```

### Bài 3: bộ giới hạn tốc độ token bucket

> "Cho phép tối đa R request mỗi giây, nhưng cho một đợt ngắn B request đi qua."

Hình dung một cái xô chứa tối đa B token. Mỗi request được phép lấy ra một token. Xô được nạp lại token với tốc độ đều, và không bao giờ chứa quá B. Xô rỗng thì request bị từ chối.

<GoP20BucketRefill />

Bản đầu hấp dẫn là một goroutine bỏ một token vào channel có buffer mỗi `1/R` giây. Nó chạy được, nhưng cần một goroutine phải được dừng, và nó thức dậy ngay cả khi không ai gọi. Câu nối tiếp làm lộ chuyện này: "khi limiter bị bỏ đi thì sao?" Goroutine vẫn tiếp tục chạy.

Bản bên dưới không có goroutine. Nó không thêm token theo đồng hồ; mỗi lần được hỏi, nó tính xem từ lần gọi trước đã có bao nhiêu token quay lại.

```go
package bucket

import (
	"sync"
	"time"
)

// Limiter is a token bucket: it holds up to burst tokens and refills at rate tokens per second.
// Every allowed call spends one token. It is safe for concurrent use.
type Limiter struct {
	mu     sync.Mutex
	rate   float64 // tokens added per second
	burst  float64 // bucket size
	tokens float64
	last   time.Time
	now    func() time.Time // replaced by a fake clock in tests
}

func New(rate float64, burst int) *Limiter {
	l := &Limiter{rate: rate, burst: float64(burst), tokens: float64(burst), now: time.Now}
	l.last = l.now()
	return l
}

// Allow reports whether one call may go ahead right now.
func (l *Limiter) Allow() bool {
	l.mu.Lock()
	defer l.mu.Unlock()

	now := l.now()
	l.tokens += now.Sub(l.last).Seconds() * l.rate // refill for the time that passed
	if l.tokens > l.burst {
		l.tokens = l.burst
	}
	l.last = now

	if l.tokens < 1 {
		return false
	}
	l.tokens--
	return true
}
```

```go
type fakeClock struct {

func newTestLimiter(rate float64, burst int) (*Limiter, *fakeClock) {

	l := New(rate, burst)
	l.now = clock.Now
	l.last = clock.Now()
	return l, clock
}

func TestBurstThenRefill(t *testing.T) {
	l, clock := newTestLimiter(2, 3) // 2 tokens per second, bucket of 3

	for i := 0; i < 3; i++ {
		if !l.Allow() {
			t.Fatalf("call %d should use the initial burst", i+1)
		}
	}
	if l.Allow() {
		t.Fatal("4th call should be refused, the bucket is empty")
	}

	clock.Advance(500 * time.Millisecond) // refills 1 token
	if !l.Allow() {
		t.Fatal("one token should be back after 500ms")
	}
	if l.Allow() {
		t.Fatal("only one token was added")
	}
}

func TestRefillStopsAtBurst(t *testing.T) {
	l, clock := newTestLimiter(10, 2)
	l.Allow()
	clock.Advance(time.Hour) // would refill thousands of tokens, but the bucket holds 2

	allowed := 0
	for i := 0; i < 5; i++ {
		if l.Allow() {
			allowed++
		}
	}
	if allowed != 2 {
		t.Fatalf("allowed %d calls after a long wait, want 2 (the burst size)", allowed)
	}
}

func TestConcurrentCallsNeverExceedBurst(t *testing.T) {
	l, _ := newTestLimiter(1, 50) // the clock never moves, so no refill
	var allowed atomic.Int32
	var wg sync.WaitGroup
	for g := 0; g < 10; g++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := 0; i < 100; i++ {
				if l.Allow() {
					allowed.Add(1)
				}
			}
		}()
	}
	wg.Wait()
	if allowed.Load() != 50 {
		t.Fatalf("allowed %d, want exactly 50", allowed.Load())
	}
}
```

## Điểm rút ra (Key takeaways)

- **Nói ý tưởng, rồi nói cái bẫy.** Đáp án mẫu gọi tên cơ chế và một cách nó làm bạn bất ngờ. Các link dưới mỗi câu dẫn tới phần giải thích đầy đủ.
- **Slice và interface hỏng một cách âm thầm.** Một array dùng chung dưới `append` và một typed nil trong `error` đều biên dịch và chạy; chỉ có kết quả mới cho bạn biết.
- **Có kết quả không cố định.** `select` với nhiều case sẵn sàng là ngẫu nhiên, và hành vi biến vòng lặp theo dòng `go` trong `go.mod`. Hãy nói rõ là trường hợp nào, đừng đoán một đáp án.
- **Giới hạn mọi thứ bạn khởi chạy.** Bộ fetch giới hạn đồng thời và tôn trọng việc hủy, còn cache và limiter bảo vệ trạng thái dùng chung bằng lock.
- **Truyền đồng hồ và công việc vào như giá trị.** Truyền `fetch` và `now` giúp test nhanh và chính xác, không cần sleep chờ deadline.
- **Một test khớp với điều bạn khẳng định là hết tranh luận.** "Tối đa 3 cùng lúc" thành bộ đếm đỉnh; "đúng 50 đi qua" thành một phép đếm dưới `-race`.
