### The hook: thirty seconds of generated endpoints

Ask any model for "a small case-tracking API" and you'll have a working FastAPI service in under a minute: routers, models, tests, even a README. The code runs. What the model cannot hand you is the judgment behind the surface it picked — and that surface *is* the product. Leave it unreviewed and the generated defaults sneak in: one verb for every operation, one status code for every outcome, failures wrapped politely inside a 200, and a list endpoint that returns the whole table because nobody chose a page size.

None of that is a code bug. The service works right up until a client retries a create after a flaky timeout and files the same case twice, or your uptime dashboard glows green while every request fails quietly. They are contract bugs, and the contract is the one thing the code generator never sees.

This post grows the series' demo service — the one-URL trace service from [the pilot post](/blog/backend-http-request-lifecycle/) — into a versioned, resource-shaped API, and walks the five decisions that make an HTTP API honest:

1. **Resources** — the URL names a thing.
2. **Verbs and status codes** — the method is the action, the code is the receipt.
3. **Pagination** — every list ends somewhere.
4. **Idempotency** — what a retry is allowed to do.
5. **Versioning** — a version is a promise.

Every terminal block below is real output from `demo/rest_api.py`, captured on the stack in its label — run the file yourself and you will see the same lines.

## 1. The URL names a thing

Start from the one thing every client must hold: the URL. In a well-shaped API a URL is not a function name. It is the address of a thing — a resource. That single decision drives everything else in this post, which is why Fielding put longevity first: as he put it in that same 2008 thread, "implementations change, but cool URIs don't."

Three naming rules fall out:

- **Nouns, not verbs.** `/v1/cases`, not `/v1/getCases`. The verb slot is already taken — by the HTTP method.
- **Plural nouns for collections.** `/v1/cases` is every case; `/v1/cases/3` is one of them.
- **The id names the item, nothing else.** `/v1/cases/3` addresses case 3 no matter what you plan to do with it — read it, change it, delete it. The *what* never enters the URL.

Here is the read side of the demo service — the models that define what a case *is*, and one router that owns every `/v1/cases` path. This is `demo/rest_api.py`:

```python
class CaseIn(BaseModel):
    """What a caller may send — the request body."""

    title: str
    priority: str


class Case(CaseIn):
    """What the API returns — the stored case, with the id its URL names."""

    case_id: int


# One resource, one router, one version prefix. In a bigger service this
# router would live in its own module (routers/cases.py) and be included
# by the main app; the pattern and the code stay the same.
cases_router = APIRouter(prefix="/v1/cases", tags=["cases"])
```

The `APIRouter` is FastAPI's pattern for exactly this: a "mini app" that owns one resource's paths, which the main app then includes with `app.include_router(cases_router)` — the same pattern the framework's own [bigger-applications guide](https://fastapi.tiangolo.com/tutorial/bigger-applications/) uses to split users, items and admin into modules. The store behind it is a plain in-memory dict seeded with twelve cases; a later post in this series swaps it for a database, and none of the URLs will change.

Fetching one case reads the way it sounds:

```python
@cases_router.get("/{case_id}")
def get_case(case_id: int) -> Case:
    """Fetch one case — or admit it isn't there."""
    case = cases.get(case_id)
    if case is None:
        raise HTTPException(status_code=404, detail="case not found")
    return Case(**case)
```

<Concepts>
- **Resource**: the thing a URL names — one case, one user, one payment. The URL is its identity: same URL, same thing, every time.
- **Collection**: a resource that holds other resources. Plural noun in the path — `/v1/cases` is all the cases.
- **APIRouter**: FastAPI's "mini app" for one resource. Declare its paths once with a prefix and tags, then include it into the main app.

## 2. The verb is the action, the code is the receipt

With the nouns fixed, HTTP hands you exactly four verbs for the basic shape: GET reads, POST creates, PUT replaces, DELETE removes. Each verb carries promises we'll cash in section 4 — for now, watch what each one *answers*.

The generated habit and the resource contract, side by side:

<BeP02VerbsBeforeAfter />

A create, done honestly:

```python
@cases_router.post("", status_code=status.HTTP_201_CREATED)
def create_case(case: CaseIn, response: Response) -> Case:
    """Create a case; the response says 201 and where the new case lives."""
    global next_id
    case_id = next_id
    next_id += 1
    new_case = Case(case_id=case_id, title=case.title, priority=case.priority)
    cases[case_id] = new_case.model_dump()
    response.headers["Location"] = f"/v1/cases/{case_id}"
    return new_case
```

FastAPI's default for a POST is 200, so the code says `201 Created` out loud, and adds the one header a receipt needs: `Location`, the address of the thing that just came into existence. Fielding described the same exchange in that 2008 thread — a resource-creating POST results in a 201 response with the new resource's URI.

    del cases[case_id]

Two defaults show up in generated endpoints again and again. **POST everything** — generated code reaches for POST because it always works, but POST is the one verb a client may not blindly retry, and the one shared caches refuse by default; when reads hide inside POSTs you lose half of HTTP for free. **200-only** — when failures also come back `200` with an error tucked in the body, every monitor, load balancer and retry loop reads your service as healthy, because the status line is the one field all of them already parse.

## 3. Every list ends somewhere

A collection endpoint has one more honesty rule: it never returns everything. An unbounded list is a slow query that becomes an outage on someone's busiest day — which is why GitHub's own API returns 30 issues at a time even when the repository has over 1,600 open ones, and caps `per_page` at 100, quietly reducing anything larger ([GitHub REST docs](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)).

The demo ships pages the simplest way — skip some, take some:

```python
@cases_router.get("")
def list_cases(
    limit: int = Query(20, ge=1, le=100), offset: int = Query(0, ge=0)
) -> list[Case]:
    """One page of the collection, ordered by case_id."""
    ids = sorted(cases)
    return [Case(**cases[i]) for i in ids[offset : offset + limit]]
```

Twelve cases are seeded, so ask for five at a time:

Offset is easy arithmetic: page *N* is `offset = (N - 1) * limit`, and a short page (or an empty one) means the end. Clients can build "page 7 of 23" with it, and admins can jump straight to the middle — that's worth something.

Its cost is that **the offset is a position, and positions lie when the list moves**. The classic case is a newest-first feed:

<BeP02OffsetCursor />

To be clear about our own demo: `list_cases` sorts by `case_id` ascending, and new cases get bigger ids — offsets there are stable, and that's a legitimate choice for admin tables and small bounded sets. The moment your list is "newest first" — feeds, activity, comments, the default for anything humans watch — an offset quietly serves duplicates and skips rows whenever anything lands or leaves above the page.

The fix is to stop counting positions and anchor to the data: a **cursor** says "start after id 8", so the next page is whatever follows id 8, whenever it is requested. Insertions above can't move that anchor. GitHub's REST API goes one step further for clients: every paginated response carries a `link` header with ready-made URLs — `rel="next"`, `rel="prev"`, `rel="last"` — so the client never counts pages at all; it follows the URL the server hands back. Stripe's list endpoints work the same way with `starting_after` cursors.

When to pick which: offset when the list is stable and humans want page numbers; cursor when the list moves and clients just want "everything since I last looked". The tradeoff is the lesson — a generated endpoint ships whichever one the model defaulted to, and never notices the list was a feed.

<Concepts>
- **Offset pagination**: "skip N, take the next page." The client counts positions. Simple, supports jumping to page 7 — and lies the moment rows move around.
- **Cursor pagination**: "start after this item." The client holds a marker into the data itself. Immune to insertions and deletions above it; page numbers are harder.
- **Link header**: a response header carrying ready-made next/previous page URLs — GitHub's REST API does this so clients follow instead of counting.
</Concepts>

## 4. What a retry may do

[The pilot post](/blog/backend-http-request-lifecycle/) traced one request across six stations outside your code. Here is the station failure that shapes API design: **a timeout is ambiguous.** The request may have died on the way out — or it may have arrived, done its work, and lost the response on the way back. The only safe client assumption is "it might have happened", so networks retry: browsers, mobile OSes, proxies, the SDK in your own codebase.

So the question every write endpoint answers implicitly: what is a retry allowed to *do*?

Watch what a retry of our create does — this is exactly the two POSTs a client sends when the first answer times out:

That is the whole reason the verb choices from section 2 are not style points. The HTTP spec divides methods by what retries may assume:

- **Safe** — GET, HEAD: the caller intends to change nothing. Retry as often as you like.
- **Idempotent** — GET, PUT, DELETE: one request or several identical ones leave the server in the same state ([MDN](https://developer.mozilla.org/en-US/docs/Glossary/Idempotent)). Retry freely; the second PUT in section 2 would have returned the same case 13 either way.
- **Neither** — POST: every delivery creates a new thing. Retry unprotected and you just watched it happen: cases 14 *and* 15.

Idempotent does not mean "the same response", though. Delete case 14 (a 204, exactly like the one in section 2), then let the timeout force the client to retry the delete:

<TerminalOutput command="curl -i -X DELETE http://127.0.0.1:4326/v1/cases/14" label="macOS · curl 8.7.1 · Python 3.13 · FastAPI 0.165 · captured Nov 2026" caption="The retried DELETE answers 404 — no harm done to the data (case 14 is gone either way), but the client cannot tell 'I deleted it' from 'it was never there'. The state is identical; that is all idempotency promises.">
```text
HTTP/1.1 404 Not Found
date: Mon, 23 Nov 2026 07:39:25 GMT
server: uvicorn
content-length: 27
content-type: application/json

{"detail":"case not found"}
```
</TerminalOutput>

MDN's own glossary example makes the same point: a first DELETE answers 200 (ours answers 204), the retries answer 404, and all of that is fine — idempotency is about the state left behind, not about matching status codes.

So what do you do about POST, which you cannot give up — payments, orders, case creation are POSTs because each one genuinely creates something? You make the *operation* idempotent instead of the method, with an **idempotency key**:

<BeP02RetryTimeline />

The client generates a unique key per operation — Stripe suggests a UUID — and sends it along with the POST. The server executes once, saves the response under that key, and replays the saved answer to any retry carrying the same key. Stripe runs exactly this for every POST: the saved response includes its status code and body, keys are pruned after about 24 hours, and their docs are blunt that you don't send keys on GET and DELETE — those are idempotent by definition already.

None of this is exotic. It's the difference between "the network hiccuped and we charged one card twice" and "the network hiccuped".

<Concepts>
- **Safe method**: read-only for the caller's intent — GET, HEAD. Caches may serve it; retries are free.
- **Idempotent**: one request or several identical ones leave the same state. GET, PUT and DELETE are; POST is not. Responses may differ — only the resulting state must not.
- **Idempotency key**: a client-generated unique key on a POST; the server executes once and replays the saved response to retries with the same key.
</Concepts>

## 5. A version is a promise

Every URL in this post has carried a `/v1` that we never discussed. It is load-bearing: it names the version of the contract the client is depending on.

**A version is a promise: responses under this prefix keep their shape.** Same field names, same types, same meaning. The day you quietly rename a field under a live version, every client that coded against it breaks at once — and most of them won't even get an error, just silently wrong data. That is the nastiest failure an API can hand out, and a version prefix is how you promise it won't happen:

<BeP02VersionPaths />

Where the version lives is a real design choice, and serious APIs disagree:

- **In the URL path** — this demo's `/v1/cases`. Blunt, visible in every log, cacheable per version.
- **In a request header** — GitHub's REST API keeps its paths bare and pins the version in `X-GitHub-Api-Version` instead.
- **Pinned per account** — Stripe dates every version (the current one reads like `2026-11-18.endive`), pins it to your account, and only moves you when *your* code opts in via the `Stripe-Version` header or a pinned SDK ([Stripe upgrades guide](https://docs.stripe.com/upgrades)).

Pick whichever fits your callers; the rule is the same behind all three: **a breaking change ships under a new version, never under a live one.** And know what counts as breaking: a renamed field, a removed field, a changed type — anything a running client cannot ignore.

One honest caveat, because versioning also has a cost: if you own both ends — one client, one server, deployed together from the same repo — a version prefix is usually ceremony. The promise matters the moment you don't control the callers.

<Concepts>
- **Versioning**: pinning the shape of responses so clients can depend on it — in the URL path, a request header, or a dated version pinned per account.
- **Breaking change**: anything a running client cannot ignore — a renamed field, a removed field, a changed type. It ships under a new version, never a live one.
</Concepts>

## 6. The two-minute wire audit

None of the five decisions above is hard to *check*, which is the point. The model wrote your endpoints in seconds; reading the contract it produced takes minutes, and the whole audit is three curls:

1. **Run each operation once with `curl -i`** — fresh case, missing case, existing case. The pairs must line up: 201 + `Location` on create, 204 with an empty body on delete, 404 with a machine-readable body on missing, `allow` on the verbs you don't offer.
2. **Send the create twice** — the two-minute version of section 4. Count the rows that come back. If two identical POSTs made two things, decide *now* whether that's acceptable, because the network will do it for you eventually.
3. **Read one screen of the access log** — the receipt column from section 2. If every line says 200 while your own curls said 201, 204 and 404, the surface is lying to everything that watches it.

The contract is on the wire, not in the code review. Read it before your clients do.

1. **Tài nguyên** — URL gọi tên một thứ.
2. **Verb và status code** — method là hành động, code là biên lai.
3. **Phân trang** — mọi danh sách đều phải dừng ở đâu đó.
4. **Idempotency** — một lần retry được phép làm gì.
5. **Versioning** — một phiên bản là một lời hứa.

## 1. URL gọi tên một thứ

Bắt đầu từ thứ duy nhất mọi client đều phải nắm giữ: URL. Trong một API thiết kế đúng, URL không phải tên hàm. Nó là địa chỉ của một thứ — một tài nguyên (resource). Quyết định nhỏ đó kéo theo cả bài viết này, và đó là lý do Fielding đặt "sống lâu" lên hàng đầu: như ông nói trong chính thread 2008 đó, "implementations change, but cool URIs don't" — bản cài đặt thay đổi, URI ngon thì không.

Ba quy tắc đặt tên rơi ra từ đó:

- **Danh từ, không phải động từ.** `/v1/cases`, không phải `/v1/getCases`. Ô verb đã có chủ rồi — HTTP method.
- **Danh từ số nhiều cho bộ sưu tập.** `/v1/cases` là mọi vụ việc; `/v1/cases/3` là một trong số đó.
- **Id chỉ gọi tên item, không hơn.** `/v1/cases/3` trỏ tới vụ số 3 bất kể bạn định làm gì với nó — đọc, sửa, xoá. Cái *làm gì* không bao giờ lọt vào URL.

Đây là phần đọc của demo service — model định nghĩa vụ việc *là gì*, và một router sở hữu mọi đường dẫn `/v1/cases`. Đây là `demo/rest_api.py`:

```python
class CaseIn(BaseModel):
    """What a caller may send — the request body."""

    title: str
    priority: str


class Case(CaseIn):
    """What the API returns — the stored case, with the id its URL names."""

    case_id: int


# One resource, one router, one version prefix. In a bigger service this
# router would live in its own module (routers/cases.py) and be included
# by the main app; the pattern and the code stay the same.
cases_router = APIRouter(prefix="/v1/cases", tags=["cases"])
```

`APIRouter` là pattern FastAPI dùng cho đúng việc này: một "mini app" sở hữu đường dẫn của một tài nguyên, rồi app chính gắn vào bằng `app.include_router(cases_router)` — y như [hướng dẫn bigger-applications](https://fastapi.tiangolo.com/tutorial/bigger-applications/) của chính framework tách users, items, admin thành từng module. Cái store phía sau là một dict trong bộ nhớ, gieo sẵn mười hai vụ việc; một bài sau trong series sẽ thay nó bằng database, và không URL nào phải đổi.

Đọc một vụ việc nghe đúng như câu nói của nó:

```python
@cases_router.get("/{case_id}")
def get_case(case_id: int) -> Case:
    """Fetch one case — or admit it isn't there."""
    case = cases.get(case_id)
    if case is None:
        raise HTTPException(status_code=404, detail="case not found")
    return Case(**case)
```

## 2. Verb là hành động, code là biên lai

Danh từ đã chốt, HTTP đưa sẵn đúng bốn verb cho hình cơ bản: GET đọc, POST tạo, PUT thay thế, DELETE xoá. Mỗi verb kèm lời hứa mình sẽ xử lý ở mục 4 — giờ hãy xem mỗi verb *trả lời* cái gì.

```python
@cases_router.post("", status_code=status.HTTP_201_CREATED)
def create_case(case: CaseIn, response: Response) -> Case:
    """Create a case; the response says 201 and where the new case lives."""
    global next_id
    case_id = next_id
    next_id += 1
    new_case = Case(case_id=case_id, title=case.title, priority=case.priority)
    cases[case_id] = new_case.model_dump()
    response.headers["Location"] = f"/v1/cases/{case_id}"
    return new_case
```

## 3. Mọi danh sách đều phải có điểm dừng

Endpoint của bộ sưu tập còn một quy tắc nói thật nữa: không bao giờ trả tất cả. Danh sách không giới hạn là một query chậm chờ ngày trở thành sự cố vào lúc ai đó bận nhất — vì thế API của chính GitHub trả mỗi lần 30 issue dù repo có hơn 1.600 issue mở, và chặn `per_page` ở 100, giá trị lớn hơn bị hạ xuống âm thầm ([GitHub REST docs](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)).

Demo đóng gói theo cách đơn giản nhất — bỏ qua vài dòng, lấy vài dòng:

```python
@cases_router.get("")
def list_cases(
    limit: int = Query(20, ge=1, le=100), offset: int = Query(0, ge=0)
) -> list[Case]:
    """One page of the collection, ordered by case_id."""
    ids = sorted(cases)
    return [Case(**cases[i]) for i in ids[offset : offset + limit]]
```

Nói rõ về chính demo của mình: `list_cases` sắp theo `case_id` tăng dần, vụ mới sinh id lớn hơn — offset ở đó ổn, và đó là lựa chọn hợp lệ cho bảng admin hay tập dữ liệu nhỏ có giới hạn. Nhưng danh sách của bạn thành "mới trước" — feed, activity, comment, mặc định của bất cứ gì con người xem — thì offset lặng lẽ trả trùng và sót mỗi khi có thứ thêm vào hoặc rời đi phía trên trang.

Cách sửa là thôi đếm vị trí, neo vào dữ liệu: một **con trỏ (cursor)** nói "bắt đầu sau id 8", nên trang kế là những gì đi sau id 8, bất kể lúc nào hỏi. Chèn bao nhiêu phía trên cũng không xê dịch mốc neo. REST API của GitHub đi xa hơn một bước cho client: mỗi response phân trang mang header `link` chứa sẵn URL — `rel="next"`, `rel="prev"`, `rel="last"` — nên client không phải đếm trang nào hết; chỉ việc theo URL server đưa. Endpoint dạng list của Stripe chạy y như vậy với cursor `starting_after`.

Chọn cái nào: offset khi danh sách ổn định và người cần số trang; cursor khi danh sách di chuyển và client chỉ cần "mọi thứ từ lần xem trước". Sự đánh đổi chính là bài học — endpoint do AI sinh sẽ mặc định cái nào model quen, và không bao giờ nhận ra danh sách kia là một feed.

<Concepts title="Mấy thuật ngữ phía trên, nói dễ hiểu">
- **Offset pagination (phân trang theo vị trí)**: "bỏ qua N dòng, lấy trang kế." Client đếm vị trí. Đơn giản, nhảy được tới trang 7 — và nói dối ngay khi dữ liệu xê dịch.
- **Cursor pagination (phân trang bằng con trỏ)**: "bắt đầu sau item này." Client giữ mốc neo vào chính dữ liệu. Miễn nhiễm với chèn/xoá phía trên; đánh số trang khó hơn.
- **Link header**: response header chứa sẵn URL trang trước/sau — REST API của GitHub dùng để client theo link thay vì tự đếm.
</Concepts>

## 4. Một lần retry được phép làm gì

[Bài mở màn](/blog/backend-http-request-lifecycle/) đã truy vết một request qua sáu trạm ngoài code của bạn. Đây là kiểu trạm hỏng định hình nên thiết kế API: **timeout là tín hiệu mơ hồ.** Request có thể đã chết lúc gửi đi — hoặc đã tới nơi, làm xong việc, và mất response trên đường về. Giả định an toàn duy nhất của client là "có thể nó đã xảy ra", nên mạng luôn retry: browser, mobile OS, proxy, SDK trong chính repo bạn.

Thế nên câu hỏi ngầm sau mỗi endpoint ghi dữ liệu: một lần retry được phép *làm gì*?

Hãy xem thử retry của create — đúng hai POST mà một client sẽ gửi khi câu trả lời đầu timed out:

Đó là toàn bộ lý do các lựa chọn verb ở mục 2 không phải gu thẩm mỹ. HTTP chia method theo thứ retry được phép tin:

- **Safe** — GET, HEAD: ý định của người gọi là không đổi gì. Retry thoải mái.
- **Idempotent (lũy đẳng)** — GET, PUT, DELETE: một request hay nhiều request giống hệt nhau để lại cùng một state ([MDN](https://developer.mozilla.org/en-US/docs/Glossary/Idempotent)). Retry thoải mái; PUT thứ hai ở mục 2 cũng trả lại vụ 13 y như thế.
- **Không phải cái nào** — POST: mỗi lần giao hàng tạo một thứ mới. Retry không bảo vệ thì bạn vừa thấy hậu quả: vụ 14 *và* vụ 15.

Idempotent không đồng nghĩa "response giống nhau" đâu nhé. Xoá vụ 14 (một 204, y như cái ở mục 2), rồi để timeout ép client retry cú xoá:

<TerminalOutput command="curl -i -X DELETE http://127.0.0.1:4326/v1/cases/14" label="macOS · curl 8.7.1 · Python 3.13 · FastAPI 0.165 · chụp tháng 11/2026" caption="DELETE retry trả 404 — dữ liệu chẳng hề hại (vụ 14 đã mất dù sao đi nữa), nhưng client phân biệt không nổi 'tôi xoá nó' với 'nó chưa từng có'. State y hệt nhau; idempotency chỉ hứa nhiêu đó.">
```text
HTTP/1.1 404 Not Found
date: Mon, 23 Nov 2026 07:39:25 GMT
server: uvicorn
content-length: 27
content-type: application/json

{"detail":"case not found"}
```
</TerminalOutput>

Chính ví dụ trong glossary MDN cũng nói vậy: DELETE đầu trả 200 (bản demo trả 204), các lần retry trả 404, và tất cả đều ổn — idempotency là về state để lại, không phải về status code khớp nhau.

Thế còn POST — thứ bạn không bỏ được — thì sao? Payment, order, tạo vụ việc đều là POST vì mỗi cái thật sự tạo ra một thứ. Giải pháp: làm cho *thao tác* idempotent, thay vì method, bằng một **idempotency key**:

Client sinh một khoá duy nhất cho mỗi thao tác — Stripe gợi ý UUID — gửi kèm theo POST. Server chạy đúng một lần, lưu response theo khoá đó, rồi phát lại câu đã lưu cho bất kỳ retry nào mang cùng khoá. Stripe chạy nguyên cái này cho mọi POST: response lưu trọn status code lẫn body, khoá được dọn sau khoảng 24 giờ, và docs của họ nói thẳng đừng gửi khoá trên GET với DELETE — hai thứ đó idempotent sẵn rồi.

Không gì trong này là cao siêu. Đó là toàn bộ khoảng cách giữa "mạng bùng một cái và mình quẹt thẻ hai lần" với "mạng bùng một cái".

<Concepts title="Mấy thuật ngữ phía trên, nói dễ hiểu">
- **Safe method (phương thức an toàn)**: chỉ đọc theo ý định người gọi — GET, HEAD. Cache phục vụ được; retry miễn phí.
- **Idempotent (lũy đẳng)**: một hay nhiều request giống hệt nhau để lại cùng một state. GET, PUT, DELETE là idempotent; POST thì không. Response có thể khác — chỉ state kết quả là phải giống.
- **Idempotency key (khoá chống lặp)**: khoá duy nhất do client sinh ra gắn vào POST; server chạy một lần rồi phát lại response đã lưu cho mọi retry mang cùng khoá.
</Concepts>

## 5. Một phiên bản là một lời hứa

Mọi URL trong bài này đều mang `/v1` mà mình chưa một lần bàn tới. Nó không phải trang trí: nó gọi tên phiên bản của hợp đồng mà client đang dựa vào.

**Một phiên bản là một lời hứa: response dưới prefix này giữ nguyên hình dạng.** Cũng field đó, cũng kiểu đó, cũng nghĩa đó. Ngày bạn lặng lẽ đổi tên field dưới một version đang sống, mọi client đã code theo nó gãy cùng lúc — và đa số chẳng nhận được error nào, chỉ nhận dữ liệu sai im lặng. Đó là kiểu hỏng xấu nhất một API có thể trao cho người dùng, và prefix version là cách hứa nó không xảy ra:

<BeP02VersionPaths />

Version sống ở đâu là một lựa chọn thiết kế thật, và các API nghiêm túc không thống nhất với nhau:

- **Trong URL path** — `/v1/cases` của demo. Thẳng thắn, nhìn thấy trong mọi log, cache được theo từng version.
- **Trong request header** — REST API của GitHub để path trần và ghim version vào `X-GitHub-Api-Version`.
- **Ghim theo account** — Stripe gắn ngày cho mỗi version (bản mới nhất đọc kiểu `2026-11-18.endive`), ghim vào account của bạn, và chỉ dời bạn khi *code của bạn* chủ động xin qua header `Stripe-Version` hay một SDK đã ghim ([hướng dẫn upgrade của Stripe](https://docs.stripe.com/upgrades)).

Chọn kiểu nào hợp với người gọi của bạn; quy tắc sau cả ba là một: **thay đổi phá vỡ (breaking change) phát hành dưới version mới, không bao giờ dưới version đang sống.** Và phải biết cái gì mới là breaking: đổi tên field, bỏ field, đổi kiểu dữ liệu — bất cứ thứ gì một client đang chạy không thể làm ngơ.

Một lời thẳng thẳn, vì versioning cũng có giá của nó: nếu bạn sở hữu cả hai đầu — một client, một server, deploy chung từ một repo — thì prefix version thường chỉ là nghi thức. Lời hứa chỉ quan trọng từ khoảnh khắc bạn không còn kiểm soát người gọi.

<Concepts title="Mấy thuật ngữ phía trên, nói dễ hiểu">
- **Versioning (đánh phiên bản)**: ghim hình dạng response để client dựa vào được — trong URL path, trong request header, hay version có ngày ghim theo account.
- **Breaking change (thay đổi phá vỡ)**: thứ mà client đang chạy không thể làm ngơ — đổi tên field, bỏ field, đổi kiểu. Phát hành dưới version mới, không bao giờ dưới version đang sống.
</Concepts>

## 6. Soi lại bản tin HTTP trong hai phút

Không quyết định nào trong năm cái trên là khó *kiểm tra*, và đó chính là điểm mấu chốt. Model viết endpoint cho bạn trong vài giây; đọc lại hợp đồng nó tạo ra mất vài phút, và toàn bộ cuộc soi là ba cú curl:

1. **Chạy từng thao tác một lần với `curl -i`** — vụ mới, vụ thiếu, vụ có thật. Các cặp phải khớp: 201 + `Location` khi tạo, 204 body rỗng khi xoá, 404 kèm body máy đọc được khi thiếu, `allow` cho những verb bạn không hỗ trợ.
2. **Gửi create hai lần** — bản hai phút của mục 4. Đếm số dòng quay về. Nếu hai POST giống hệt tạo ra hai thứ, quyết định *ngay bây giờ* có chấp nhận không — vì mạng sẽ làm điều đó giúp bạn sớm muộn gì.
3. **Đọc một màn hình access log** — cột biên lai ở mục 2. Nếu dòng nào cũng 200 trong khi cú curl của chính bạn nói 201, 204, 404, nghĩa là bề mặt API đang nói dối mọi thứ đứng coi nó.

Hợp đồng nằm trên bản tin HTTP, không nằm trong code review. Đọc nó trước khi client của bạn đọc.
