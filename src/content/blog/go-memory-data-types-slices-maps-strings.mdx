### A ten-byte model name that pinned 330 MB of request bodies

In November 2026, a production gateway in `vllm-project/aibrix` ([PR #3508](https://github.com/vllm-project/aibrix/pull/3508)) showed ~330 MB of live heap held across ~1,450 request copies (~250 KB each) on `/v1/responses`. Nothing was looping forever. The JSON decoder `sonic.Unmarshal` had copied each HTTP request body into a string and returned the `model` field as a substring pointing into that copy.

Because the gateway kept that short `model` string in its routing context, in-flight gauges, and Prometheus labels after the request finished, every tiny `model` name kept an entire 250 KB request body reachable to the garbage collector. The fix was one line: `model = strings.Clone(model)`.

Slices, maps, and strings in Go look like ordinary self-contained values when you assign or pass them around, yet each is a compact header pointing at shared heap memory underneath. In the HTTP todo service from [the HTTP service post](/blog/go-http-service-net-http-json-middleware/), `store.list()` had to `make` and `copy` a fresh `[]Todo` slice precisely so callers could not mutate or `append` into the store's backing array outside the mutex. This post opens those runtime layouts on Go 1.27.1 and answers four questions:

1. **Slice headers and growth**: why `append` on a sub-slice overwrites neighbouring slots, and how `runtime.growslice` scales capacity up to and past 256 elements.
2. **Garbage collection traps**: how sub-slices, trailing pointers, substrings, and Go 1.24+ SwissTable maps hold memory after you drop or `delete` data.
3. **Loops and iteration**: what `range` copies, why `&c` inside a loop still differs from `&s[i]` in Go 1.22+, and how `break` behaves inside `switch` or `select`.
4. **Strings and value equality**: why `TrimRight("todo.json", ".json")` returns `"tod"`, when `strings.Builder` and `bytes` stop needless copies, and when `==` panics at run time.

<Callout type="note" title="TL;DR">
Go slices (24 bytes), strings (16 bytes), and maps are thin descriptors pointing at heap storage. Uncapped sub-slices let `append` overwrite adjacent slots (`s[low:high:max]` stops that), short sub-slices or substrings pin huge parent buffers (`copy`, `bytes.Clone`, `strings.Clone`, or `clear` frees them), SwissTable maps never shrink after `delete` (`make(map, hint)` and periodic map rebuilds keep RAM bounded), `range` evaluates once and copies elements, and `TrimRight` strips a rune set rather than a suffix.
</Callout>

<Concepts>

- **Descriptor (header)**: a tiny fixed-size struct (`slice`, `string`, or `map` pointer) passed by value that points to a separate heap allocation holding the real elements.
- **Backing array**: the contiguous block of memory storing the elements behind one or more slice headers or the bytes behind one or more string headers.
- **Value semantics**: Go's rule that assignment and function calls copy the value itself; for a slice, Go copies the 24-byte header while leaving the backing array shared.
- **Reachability (GC)**: Go's garbage collector frees a heap block only when zero live pointers anywhere in the program point into any address inside that block.

</Concepts>

## 1. Slice headers, append growth, and shared arrays

On 64-bit hardware, a Go slice variable is a 24-byte header holding a pointer to the backing array, the active length `len`, and the total allocated slots `cap`. Passing a slice to a function or assigning `s2 := s1` copies only those 24 bytes, so both variables read and write the exact same backing array. Think of the slice header as a 3-line shipping tag glued onto a shelf: copying the tag gives two people the same shelf address.

<Figure src={goSliceStruct} alt="Official Go blog diagram showing a slice descriptor with ptr, len, and cap fields" caption="The 24-byte slice header on 64-bit systems: eight bytes each for the backing-array pointer, length, and capacity." sourceTitle="The Go Blog: Go Slices: usage and internals" sourceUrl="https://go.dev/blog/slices-intro" />

Inside the Go runtime (`src/runtime/slice.go`), that header is literally three words:

### How `append` overwrites a sibling slice

When you take a sub-slice `s2 := s1[1:3]` from a 5-element slice `[10, 20, 30, 40, 50]`, `s2` gets `len = 2`, while its `cap` inherits every slot from index 1 to the end of `s1`'s array (`cap = 4`). Calling `append(s2, 99)` sees two spare slots, writes `99` straight into `s1[3]`, and allocates nothing.

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	s1 := []int{10, 20, 30, 40, 50}
	s2 := s1[1:3]
	fmt.Printf("header=%d bytes len(s2)=%d cap(s2)=%d\n", unsafe.Sizeof(s1), len(s2), cap(s2))

	s2 = append(s2, 99)
	fmt.Printf("uncapped: s1=%v s2=%v sameAddr=%t\n", s1, s2, &s1[3] == &s2[2])

	base := []int{10, 20, 30, 40, 50}
	safe := base[1:3:3]
	safe = append(safe, 99)
	fmt.Printf("capped:   base=%v safe=%v len(safe)=%d cap(safe)=%d sameAddr=%t\n",
		base, safe, len(safe), cap(safe), &base[3] == &safe[2])
}
```

In [the HTTP service post](/blog/go-http-service-net-http-json-middleware/), `store.list()` wrote `out := make([]Todo, len(s.todos)); copy(out, s.todos)` instead of `return s.todos` or `return s.todos[:limit]`. Returning a direct sub-slice would expose the backing array after `s.mu.Unlock()`: a handler calling `append` on the returned list could overwrite the next `Todo` inside `store` without holding the lock. To stop shared-array writes, either cap the slice with a **full slice expression** `s[low:high:max]` (setting `cap = max - low`) or allocate and `copy` (remembering `copy(dst, src)` copies `min(len(dst), len(src))` items, or use `slices.Clone(s)`).

Notice one detail carried over from [Go collections](/blog/go-slices-maps-strings/): `var s []T` (`nil`) and `s := []T{}` both satisfy `len(s) == 0`, yet `encoding/json` encodes `nil` as `null` and `[]T{}` as `[]`. That is why `store.list()` used `make([]Todo, len(s.todos))` even when empty, while `slices.Clone(nil)` returns `nil`.

### How `append` grows capacity in Go 1.27

When `len == cap`, `append` calls `runtime.growslice` to allocate a larger array, copy old elements over, and return the new header. Inside `nextslicecap` in Go 1.27.1, Go doubles capacity (`2x`) while `oldCap < 256` so small slices grow without frequent copies, then smoothly tapers toward `1.25x` (`newcap += (newcap + 3*256) >> 2`) before rounding up to an allocator size class. For a 500 MB slice, growing by 25% instead of 100% avoids reserving an extra half gigabyte just to add one item.

Here is the benchmark of appending 10,000 `int` values into a `var s []int` versus `make([]int, 0, 10_000)` on Apple M2 with Go 1.27.1:

```go
var sliceSink []int

func BenchmarkSliceNoCap(b *testing.B) {
	for b.Loop() {
		var s []int
		for i := range 10_000 {
			s = append(s, i)
		}
		sliceSink = s
	}
}

func BenchmarkSlicePrealloc(b *testing.B) {
	for b.Loop() {
		s := make([]int, 0, 10_000)
		for i := range 10_000 {
			s = append(s, i)
		}
		sliceSink = s
	}
}
```

<Concepts>

- **Full slice expression (`s[low:high:max]`)**: three-index slicing that sets `cap = max - low` so the next `append` allocates a fresh backing array instead of mutating parent slots.
- **`runtime.growslice` taper**: Go's capacity growth rule that doubles (`2x`) below `oldCap = 256` and tapers smoothly toward `1.25x` above `256` before size-class rounding.
- **Allocator size class**: fixed memory block sizes (such as 8, 16, 32, 64, 848 elements) used by Go's heap allocator, which is why `cap` can jump slightly past the raw formula.

</Concepts>

## 2. Heap retention in slices, substrings, and SwissTable maps

Because Go's garbage collector sweeps whole heap allocations rather than individual bytes inside an array, any single live pointer to any offset inside a heap block keeps the entire block alive. Imagine holding a claim ticket to the front seat of a 50-car train: as long as your ticket stays in use, the yard cannot scrap the other 49 cars.

### Sub-slice capacity leaks and pointer tails

Two slice patterns keep dead memory pinned on the heap:

1. **Slicing a giant buffer**: taking `header := msg[:5]` from a 1 MiB network payload keeps all 1 MiB alive as long as `header` survives. Writing `msg[:5:5]` still keeps all 1 MiB pinned because the pointer still lands inside that same heap object. Copy only the 5 bytes with `copy` or `bytes.Clone(msg[:5])`.
2. **Shrinking a slice of structs with pointers**: slicing `items = items[:2]` on `[]Todo` where each `Todo` holds a `Payload []byte` drops `len` from 500 to 2, yet indices `2..499` inside the backing array still hold valid `Payload` slice headers that the GC must scan and keep alive.

Here is that pointer-tail retention measured on Go 1.27.1 (`runtime.GC()` runs twice before reading `runtime.MemStats` so sweep completes):

```go
package main

import (
	"fmt"
	"runtime"
)

type Todo struct {
	ID      int
	Payload []byte
}

func heapMiB() float64 {
	runtime.GC()
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return float64(m.HeapAlloc) / (1024 * 1024)
}

func main() {
	items := make([]Todo, 500)
	for i := range items {
		items[i] = Todo{ID: i + 1, Payload: make([]byte, 1<<20)}
	}
	fmt.Printf("filled 500 items:    %.1f MiB\n", heapMiB())

	kept := items[:2]
	fmt.Printf("after items[:2]:     %.1f MiB\n", heapMiB())
	runtime.KeepAlive(kept)

	clear(items[2:])
	kept = items[:2]
	fmt.Printf("after clear([2:]):   %.1f MiB\n", heapMiB())
	runtime.KeepAlive(kept)
}
```

<TerminalOutput command="go run ./prog_leaks" label="Apple M2 · Go 1.27.1" caption="Reslicing to items[:2] keeps all 500.2 MiB alive; clear(items[2:]) zeroes the hidden tail and drops HeapAlloc to 2.2 MiB.">

You can fix this either by copying `items[:2]` into a fresh 2-element slice (`slices.Clone(items[:2])`) or by zeroing the excluded tail (`clear(items[2:])` in Go 1.21+) before reslicing. Copying walks `0..i-1` and drops excess capacity; `clear` walks `i..n-1` and preserves capacity if the slice will refill soon.

### Substring leaks and `strings.Clone`

A `string` is a 16-byte header (`ptr`, `len`) sharing the same trap as a slice. Slicing `uuid := hugeLog[:36]` or keeping `model` from a 250 KB JSON body in `vllm-project/aibrix#3508` pins the entire parent string on the heap. Use `strings.Clone(log[:36])` whenever a short substring outlives a large input string.

### Map size hints and Go 1.24+ SwissTables

Starting in Go 1.24, built-in maps use an open-addressed **SwissTable** layout instead of linked overflow buckets (`hmap` + `bmap`). As Michael Pratt details on [The Go Blog](https://go.dev/blog/swisstable), a map splits keys into independent tables of at most 1,024 slots (`maxTableCapacity`) using extendible hashing so no single insert ever stalls copying a giant map all at once. Within each table, slots sit in 8-slot groups paired with a 64-bit control word: the 64-bit key hash splits into a 57-bit upper prefix (`h1`) to pick the group and a 7-bit fingerprint (`h2`) stored in each slot's control byte so the CPU tests all 8 slots in parallel.

Two rules still surprise developers every day:

- **Pre-size with `make(map[K]V, hint)`**: as shown in the benchmark below, passing a size hint allocates the right directory and tables up front rather than doubling and rehashing repeatedly. It is a hint, not a cap, so the map still grows past `hint` if needed.
- **Map elements are not addressable (`&m[k]` refuses to compile)**: table splits and grows move entries to new addresses in memory, so Go forbids holding a pointer directly into a map slot. Also note from `internal/abi/map.go` that keys or values larger than `128 bytes` are stored indirectly via heap pointers rather than inline in the group slot.

```go
func BenchmarkMapNoHint(b *testing.B) {
	for b.Loop() {
		m := make(map[int]int)
		for i := range 100_000 {
			m[i] = i
		}
		_ = m
	}
}

func BenchmarkMapWithHint(b *testing.B) {
	for b.Loop() {
		m := make(map[int]int, 100_000)
		for i := range 100_000 {
			m[i] = i
		}
		_ = m
	}
}
```

### Why `delete(m, k)` never shrinks a map

Calling `delete(m, k)` zeroes the slot and sets its control byte to empty or deleted (tombstone) so pointed-to objects can be collected, yet Go maps **never shrink allocated tables or directories** ([golang/go#20135](https://github.com/golang/go/issues/20135), still open). Below is the heap measurement for `map[int][128]byte` (inline 128-byte values) and `map[int]*[128]byte` (8-byte pointer values) across 1,000,000 inserts and 990,000 deletes on Go 1.27.1:

```go
package main

import (
	"fmt"
	"runtime"
)

func heapMiB() float64 {
	runtime.GC()
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return float64(m.HeapAlloc) / (1024 * 1024)
}

func main() {
	m := make(map[int][128]byte)
	for i := range 1_000_000 {
		m[i] = [128]byte{byte(i)}
	}
	fmt.Printf("value map 1M inserts:    len=%-7d HeapAlloc=%.1f MiB\n", len(m), heapMiB())
	for i := range 990_000 {
		delete(m, i)
	}
	fmt.Printf("value map 990k deletes:  len=%-7d HeapAlloc=%.1f MiB\n", len(m), heapMiB())
	fresh := make(map[int][128]byte, len(m))
	for k, v := range m {
		fresh[k] = v
	}
	m = nil
	fmt.Printf("value map rebuilt:       len=%-7d HeapAlloc=%.1f MiB\n", len(fresh), heapMiB())
	runtime.KeepAlive(fresh)
	fresh = nil

	mp := make(map[int]*[128]byte)
	for i := range 1_000_000 {
		b := [128]byte{byte(i)}
		mp[i] = &b
	}
	fmt.Printf("pointer map 1M inserts:  len=%-7d HeapAlloc=%.1f MiB\n", len(mp), heapMiB())
	for i := range 990_000 {
		delete(mp, i)
	}
	fmt.Printf("pointer map 990k deletes:len=%-7d HeapAlloc=%.1f MiB\n", len(mp), heapMiB())
	runtime.KeepAlive(mp)
}
```

<TerminalOutput command="go run ./prog_map" label="Apple M2 · Go 1.27.1" caption="Deleting 99% of entries in map[int][128]byte frees 0.0 MiB; rebuilding drops HeapAlloc from 287.8 MiB to 2.4 MiB, while pointer values drop to 37.4 MiB.">

If your HTTP `Todo` service switches `store` from a slice to a `map[int]Todo` or caches per-request rate-limit entries during a burst, deleting finished items leaves peak table RAM pinned until process restart. Store pointers for large payloads so `delete` lets GC collect payloads, and periodically copy surviving keys into `make(map[K]V, len(old))` after spikes subside (noting that both old and new maps briefly overlap in memory until the next GC cycle).

## 3. Range copies, map iteration, and labeled break

Go replaces `while` and `foreach` with `for`. Its `range` form looks declarative, yet three evaluation rules quietly drop updates, freeze loop bounds, or turn `break` into a no-op.

### `range` evaluates once and copies every element

Two rules govern every `for ... range exp` loop:

1. **The value variable `v` is a copy**: writing `for _, acc := range accounts { acc.Balance += 100 }` updates a local copy that disappears on the next iteration. Mutate through the slice index (`for i := range accounts { accounts[i].Balance += 100 }`) or store pointers (`[]*Account`), keeping in mind that walking a slice of pointers chases random heap addresses instead of contiguous structs (covered in [Go hardware and GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/)).
2. **`exp` is evaluated once before iteration starts**: Go copies the slice header, array, or channel variable into a hidden loop variable before step 0. Appending inside `for range s` stops after the original length, whereas `for i := 0; i < len(s); i++` checks `len(s)` every step and loops forever. Likewise, ranging over an array `[3]int` reads a snapshot copy (`for i, v := range &a` or `a[i]` sees mutations), and reassigning `ch = ch2` inside `for v := range ch` keeps draining `ch1`.

```go
package main

import "fmt"

func main() {
	s := []int{0, 1, 2}
	for range s {
		s = append(s, 10)
	}
	fmt.Println("slice after range:", s)

	a := [3]int{0, 1, 2}
	for i, v := range a {
		a[2] = 99
		if i == 2 {
			fmt.Println("range a: v=", v, "a[2]=", a[2])
		}
	}
}
```

### Taking `&c` inside `range` in Go 1.22+

Before Go 1.22, taking `&c` inside `for _, c := range customers` reused the exact same stack address on every iteration, so storing `&c` in a map left every key pointing to the last customer. Go 1.22 fixed loop-variable lifetime:

<QuoteCard author="Russ Cox & David Chase" role="Go Compiler Team" sourceTitle="Fixing For Loops in Go 1.22" sourceUrl="https://go.dev/blog/loopvar-preview">
In Go 1.22, variables declared by a for loop are created once per iteration instead of once per loop, eliminating one of Go's most common production gotchas when goroutines or closures capture loop variables.
</QuoteCard>

Even in Go 1.27.1, one trap remains: `c` is still a **value copy** of `customers[i]`. Storing `&c` gives distinct pointers to loop copies rather than pointers into the `customers` slice itself. Both variants run side by side:

```go
package main

import "fmt"

type Customer struct {
	ID      string
	Balance int
}

func main() {
	customers := []Customer{{ID: "1", Balance: 10}, {ID: "2", Balance: 20}}
	byCopy := make(map[string]*Customer)
	for _, c := range customers {
		byCopy[c.ID] = &c // distinct in Go 1.22+, but points to a loop copy
	}
	byCopy["1"].Balance += 100
	fmt.Println("range &c:   slice[0]=", customers[0], "map[\"1\"]=", *byCopy["1"])

	byElem := make(map[string]*Customer)
	for i := range customers {
		byElem[customers[i].ID] = &customers[i]
	}
	byElem["1"].Balance += 100
	fmt.Println("index &s[i]: slice[0]=", customers[0], "map[\"1\"]=", *byElem["1"])
}
```

### Map iteration mutations and labeled `break`

As covered in [Go collections](/blog/go-slices-maps-strings/), map iteration order is unspecified and randomized from run to run. Mutating the map while iterating makes results doubly unpredictable: the Go spec says a key added during `range` may or may not be visited in the same loop. Look at four runs of the exact same loop in Go 1.27.1:

```go
package main

import "fmt"

func main() {
	for run := range 4 {
		m := map[int]bool{0: true, 1: false, 2: true}
		for k, v := range m {
			if v {
				m[10+k] = true
			}
		}
		fmt.Printf("run %d: len=%d %v\n", run+1, len(m), m)
	}
}
```

Read from `m` and write new entries into a separate map `m2` (or collect keys into a slice first) when updates depend on existing entries.

Also watch `break` inside a `for` loop that contains a `switch` or `select`. In Go, `break` exits the innermost `for`, `switch`, or `select`, so an unlabeled `break` inside `switch` or `select` leaves the `for` loop running. Attach a label to the `for` loop and write `break loop` (or `continue loop`):

```go
package main

import "fmt"

func main() {
	fmt.Print("without label: ")
	for i := range 5 {
		fmt.Printf("%d ", i)
		switch i {
		case 2:
			break
		}
	}
	fmt.Println()

	fmt.Print("with label:    ")
loop:
	for i := range 5 {
		fmt.Printf("%d ", i)
		switch i {
		case 2:
			break loop
		}
	}
	fmt.Println()
}
```

One related loop trap (`defer` inside a `for` loop piling up open file descriptors until the surrounding function exits) is already covered in [Go errors](/blog/go-errors-defer-panic/).

<Concepts>

- **Range expression copy**: Go evaluates `exp` in `for ... range exp` once before iteration begins and loops over that copy.
- **Loop variable lifetime (Go 1.22+)**: each loop iteration gets a fresh `c` variable so `&c` has a distinct address, yet `c` remains a copy of a slice element rather than `&s[i]`.
- **Labeled `break`**: writing `label:` above `for` and `break label` inside `switch` or `select` so execution exits the loop rather than just the inner branch.

</Concepts>

## 4. Trim traps, `strings.Builder`, `bytes`, and value equality

Remember from [Go collections](/blog/go-slices-maps-strings/#strings-and-runes) that a Go `string` is an immutable slice of UTF-8 bytes, so `len("Phở")` counts 5 bytes rather than 3 runes, and truncating by character count requires `[]rune(s)`. Beyond indexing, four daily `strings` and comparison habits cause quiet bugs or needless heap churn.

### `TrimRight` vs `TrimSuffix`

`strings.TrimRight(s, cutset)` and `strings.TrimLeft(s, cutset)` treat the second argument as an unordered set of runes to peel off from the edge, NOT an exact prefix or suffix string. If your Todo HTTP handler strips `".json"` from `"todo.json"` using `TrimRight`, `'o'` happens to be in `".json"`, so Go trims the `'o'` off `"todo"` and gives you `"tod"`:

```go
package main

import (
	"fmt"
	"strings"
)

func main() {
	fmt.Printf("TrimRight:  %q\n", strings.TrimRight("todo.json", ".json"))
	fmt.Printf("TrimSuffix: %q\n", strings.TrimSuffix("todo.json", ".json"))
	fmt.Printf("TrimRight:  %q\n", strings.TrimRight("123oxo", "xo"))
	fmt.Printf("TrimSuffix: %q\n", strings.TrimSuffix("123oxo", "xo"))
}
```

<TerminalOutput command="go run ./prog_trim" label="Apple M2 · Go 1.27.1" caption="TrimRight strips every trailing rune present in the cutset; TrimSuffix removes an exact suffix at most once.">

```text
TrimSuffix: "123o"
```

Use `TrimSuffix` / `TrimPrefix` for exact suffixes or prefixes, and reserve `TrimRight` / `TrimLeft` / `Trim` for character sets such as whitespace or trailing slashes.

### Concatenating strings and staying in `[]byte`

Because strings are immutable, writing `s += part` in a loop allocates and copies the entire accumulated string on every iteration. `strings.Builder` maintains an internal `[]byte` buffer and writes sequentially, and calling `sb.Grow(totalBytes)` up front drops 500 string concatenations from 499 allocations to 1 (keep in mind `strings.Builder` is not safe for concurrent use and panics if copied by value after writing, as shown in [Go structs and interfaces](/blog/go-structs-methods-interfaces/)).

```go
var testParts = slices.Repeat([]string{"todo-123"}, 500)

func BenchmarkStringConcatPlus(b *testing.B) {
	for b.Loop() {
		s := ""
		for _, p := range testParts {
			s += p
		}
		_ = s
	}
}

func BenchmarkStringConcatBuilder(b *testing.B) {
	for b.Loop() {
		var sb strings.Builder
		for _, p := range testParts {
			sb.WriteString(p)
		}
		_ = sb.String()
	}
}

func BenchmarkStringConcatBuilderGrow(b *testing.B) {
	for b.Loop() {
		total := 0
		for _, p := range testParts {
			total += len(p)
		}
		var sb strings.Builder
		sb.Grow(total)
		for _, p := range testParts {
			sb.WriteString(p)
		}
		_ = sb.String()
	}
}
```

Just as costly in HTTP and file code is converting `[]byte` to `string` and back (`[]byte(strings.TrimSpace(string(b)))`). func sanitizeString(b []byte) []byte {
```go
	s := strings.TrimSpace(string(b))
	return []byte(s)
}

//go:noinline
func sanitizeBytes(b []byte) []byte {
	return bytes.TrimSpace(b)
}

func BenchmarkSanitizeViaString(b *testing.B) {

	}
}

func BenchmarkSanitizeViaBytes(b *testing.B) {
	for b.Loop() {
		sinkB = sanitizeBytes(payload)
	}
}
```

### Comparing composite values (`==`, `any`, and `slices.Equal`)

Before closing on Go's memory types, remember two boundary rules already covered earlier in the series: numeric overflow, octal `0o` notation, and float tolerance live in [Go variables, types, pointers and functions](/blog/go-variables-types-pointers-functions/), and choosing value vs pointer receivers on structs lives in [Go structs and interfaces](/blog/go-structs-methods-interfaces/).

Here is the trap specific to composite memory types: `==` and `!=` work only on **comparable** types (booleans, numbers, strings, pointers, channels, interfaces, and structs or arrays made entirely of comparable fields). Slices, maps, and functions are not comparable, so a struct holding a `[]float64` refuses to compile with `==`.

Worse, if two non-comparable structs are boxed inside `any`, the compiler allows `a == b` and **Go panics at run time**:

```go
package main

import "fmt"

type snapshot struct {
	id  string
	ops []float64
}

func main() {
	var a any = snapshot{id: "x", ops: []float64{1}}
	var b any = snapshot{id: "x", ops: []float64{1}}
	fmt.Println(a == b)
}
```

<TerminalOutput command="go run ./prog_compare" label="Apple M2 · Go 1.27.1" caption="Comparing two uncomparable structs hidden inside any compiles cleanly and panics at run time (file path shortened).">
```text

goroutine 1 [running]:
main.main()
	.../prog_compare/main.go:13 +0x8c
exit status 2
```
</TerminalOutput>

When comparing structs with slices or maps, pick the standard-library helper over `reflect.DeepEqual` in hot paths:

1. **`reflect.DeepEqual` is slow and treats `nil` as unequal to `[]int{}`**: on a 100-int `todoSnapshot`, `reflect.DeepEqual` took `1047 ns/op` (`96 B/op`, `2 allocs/op`) versus `35.48 ns/op` (`0 allocs/op`) for a custom `equal` method using `slices.Equal`.
2. **Standard comparison helpers**: use `slices.Equal` / `slices.EqualFunc`, `maps.Equal`, and `bytes.Equal` in production code, or `google/go-cmp` in tests.

```go
package main

import (
	"fmt"
	"reflect"
	"slices"
)

func main() {
	var a []int
	b := []int{}
	fmt.Println("reflect.DeepEqual:", reflect.DeepEqual(a, b))
	fmt.Println("slices.Equal:     ", slices.Equal(a, b))
}
```

```text

```
</TerminalOutput>

<Concepts>

- **Cutset vs suffix/prefix**: `TrimRight` / `TrimLeft` strip any rune belonging to a character set, whereas `TrimSuffix` / `TrimPrefix` strip one exact trailing or leading substring.
- **`strings.Builder`**: mutable byte-slice builder that turns quadratic `+=` string copies into linear writes when `Grow(n)` reserves space up front.
- **Comparable type**: a type supporting `==` and `!=`; slices, maps, and functions are not comparable, and hiding them inside `any` turns a compile error into a runtime panic.

</Concepts>

## Key takeaways

- **Treat slice, map, and string variables as small descriptors**: cap shared sub-slices with `s[low:high:max]` or `copy` whenever callers might `append`, and preallocate `make([]T, 0, n)` when size is known to cut reallocations from `runtime.growslice`.
- **Break heap links when keeping small slices or substrings**: `msg[:5:5]` still pins a giant backing array, so use `copy`, `bytes.Clone`, or `strings.Clone` (as in `vllm-project/aibrix#3508`), and `clear(s[n:])` before shrinking slices of pointers.
- **Do not rely on `delete()` to reclaim map RAM**: pre-size with `make(map[K]V, hint)`, store pointer values when payloads are large, and rebuild long-lived maps after traffic spikes so GC can free old SwissTable tables.
- **Index intentionally in loops**: `range` evaluates its expression once and copies elements, `&c` in Go 1.22+ points to a loop copy rather than `&s[i]`, inserting into a map during `range` yields erratic lengths, and `break` inside `switch` or `select` needs a loop label.
- **Avoid subtle string and equality traps**: use `TrimSuffix`/`TrimPrefix` instead of `TrimRight`/`TrimLeft` for fixed affixes, use `strings.Builder` or `bytes` for I/O buffers, and prefer `slices.Equal`/`maps.Equal` or custom `.Equal()` methods over `reflect.DeepEqual`.

### Cái tên model dài 10 byte nhưng ghim 330 MB request body trên heap

Tháng 11/2026, một API gateway viết bằng Go trong repo `vllm-project/aibrix` ([PR #3508](https://github.com/vllm-project/aibrix/pull/3508)) bị giữ khoảng 330 MB bộ nhớ heap cho tầm 1.450 bản sao request (~250 KB mỗi cái) trên đường dẫn `/v1/responses`. Không có vòng lặp vô tận nào ở đây cả. Thư viện `sonic.Unmarshal` chép cả HTTP body vào một chuỗi nội bộ rồi giải mã tên `model` dưới dạng chuỗi con (substring) trỏ thẳng vào chuỗi lớn đó.

Vì gateway giữ tên `model` ngắn ngủi này trong routing context, gauge theo dõi và nhãn Prometheus sau khi request kết thúc, mỗi tên `model` vô tình giữ sống nguyên một request body 250 KB trong mắt bộ dọn rác (garbage collector). Cách sửa gọn đúng một dòng: `model = strings.Clone(model)`.

Slice, map và string trong Go nhìn bên ngoài như những giá trị độc lập khi truyền qua hàm, nhưng thực chất mỗi biến chỉ là một nhãn nhỏ (descriptor) trỏ vào vùng nhớ heap bên dưới. Ngay trong dịch vụ Todo ở [bài dựng HTTP service bằng Go](/blog/go-http-service-net-http-json-middleware/), hàm `store.list()` phải chủ động `make` và `copy` ra slice mới chính là để người gọi không thể sửa hay `append` đè ngược vào mảng của `store` bên ngoài mutex. Bài này bóc tách cấu trúc runtime trên Go 1.27.1 qua bốn câu hỏi cốt lõi:

1. **Slice header và cơ chế tăng trưởng**: vì sao `append` trên sub-slice ghi đè ô bên cạnh, và `runtime.growslice` mở rộng sức chứa trước và sau ngưỡng 256 phần tử ra sao.
2. **Bẫy giữ RAM dù có GC**: sub-slice, đuôi con trỏ, chuỗi con và map SwissTable từ Go 1.24+ ghim bộ nhớ thế nào sau khi bạn cắt ngắn hay gọi `delete`.
3. **Vòng lặp `range` và câu lệnh `break`**: `range` copy thứ gì, vì sao `&c` từ Go 1.22+ vẫn khác `&s[i]`, và `break` trong `switch`/`select` thoát khối nào.
4. **Chuỗi và phép so sánh**: vì sao `TrimRight("todo.json", ".json")` ra `"tod"`, khi nào `strings.Builder` và `bytes` bỏ được cấp phát thừa, và khi nào `==` gây panic lúc chạy.

<Callout type="note" title="Tóm tắt nhanh">
Slice (24 byte), string (16 byte) và map đều là header nhỏ trỏ vào vùng nhớ heap. Cắt sub-slice mà không khóa `cap` khiến `append` ghi đè ô kế bên (dùng `s[low:high:max]` để chặn); cắt chuỗi hay slice ngắn từ buffer to giữ sống cả khối lớn (tách bằng `copy`, `bytes.Clone`, `strings.Clone` hoặc `clear`); map SwissTable không tự thu hẹp sau `delete` (ước lượng trước bằng `make(map, hint)` và tạo map mới sau cao điểm); `range` định giá một lần và copy phần tử; còn `TrimRight` gọt theo tập ký tự chứ không gọt đúng hậu tố.
</Callout>

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Descriptor (header)**: cấu trúc nhỏ kích thước cố định (`slice`, `string` hoặc con trỏ `map`) được truyền theo giá trị, bên trong chứa con trỏ tới vùng nhớ heap thật.
- **Backing array (mảng nền)**: khối bộ nhớ liên tiếp giữ các phần tử phía sau một hoặc nhiều slice header, hay dãy byte phía sau các string header.
- **Value semantics (truyền theo giá trị)**: quy tắc gán hay truyền tham số luôn sao chép giá trị; với slice, Go chỉ copy 24 byte header chứ không copy mảng nền.
- **Reachability (khả năng chạm tới của GC)**: bộ dọn rác chỉ thu hồi một khối nhớ trên heap khi không còn con trỏ nào trong chương trình trỏ tới bất kỳ địa chỉ nào bên trong khối đó.

</Concepts>

## 1. Slice header, tăng trưởng `append` và mảng nền dùng chung

Trên máy 64-bit, một biến slice là khối header 24 byte chứa con trỏ tới mảng nền, độ dài đang dùng `len` và tổng sức chứa đã cấp `cap`. Khi truyền slice vào hàm hoặc gán `s2 := s1`, Go chỉ chép đúng 24 byte đó, nên cả hai biến cùng đọc ghi trên một mảng nền. Hãy hình dung slice như tờ nhãn 3 dòng dán trên thùng hàng: copy tờ nhãn thì hai người cầm chung một địa chỉ kho.

<Figure src={goSliceStruct} alt="Sơ đồ trên blog chính thức của Go mô tả slice gồm 3 trường ptr, len và cap" caption="Slice header 24 byte trên máy 64-bit: 8 byte cho con trỏ mảng nền, 8 byte cho len và 8 byte cho cap." sourceTitle="The Go Blog: Go Slices: usage and internals" sourceUrl="https://go.dev/blog/slices-intro" />

Mở mã nguồn runtime của Go (`src/runtime/slice.go`) ra xem thì một slice đúng nghĩa gồm ba trường này:

<GitHubCode repo="golang/go" path="src/runtime/slice.go" lines="L15-L25" url="https://github.com/golang/go/blob/074522c96ce70350453c164ecb17904881106b6a/src/runtime/slice.go#L15-L25" caption="Cấu trúc slice header bên trong mã nguồn Go runtime (golang/go).">
```go
type slice struct {
	array unsafe.Pointer
	len   int
	cap   int
}
```

### Vì sao `append` trên sub-slice ghi đè sang slice gốc

Khi cắt `s2 := s1[1:3]` từ slice 5 phần tử `[10, 20, 30, 40, 50]`, `s2` có `len = 2` nhưng `cap` vẫn ôm trọn phần đuôi của mảng nền (`cap = 4`). Lệnh `append(s2, 99)` thấy còn 2 ô trống nên ghi thẳng `99` đè lên vị trí `s1[3]`, không hề cấp phát mảng mới.

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	s1 := []int{10, 20, 30, 40, 50}
	s2 := s1[1:3]
	fmt.Printf("header=%d bytes len(s2)=%d cap(s2)=%d\n", unsafe.Sizeof(s1), len(s2), cap(s2))

	s2 = append(s2, 99)
	fmt.Printf("uncapped: s1=%v s2=%v sameAddr=%t\n", s1, s2, &s1[3] == &s2[2])

	base := []int{10, 20, 30, 40, 50}
	safe := base[1:3:3]
	safe = append(safe, 99)
	fmt.Printf("capped:   base=%v safe=%v len(safe)=%d cap(safe)=%d sameAddr=%t\n",
		base, safe, len(safe), cap(safe), &base[3] == &safe[2])
}
```

Quay lại [bài dựng HTTP service](/blog/go-http-service-net-http-json-middleware/), lý do `store.list()` viết `out := make([]Todo, len(s.todos)); copy(out, s.todos)` thay vì trả thẳng `s.todos` hay `s.todos[:limit]` nằm ở đây. Nếu trả sub-slice trực tiếp, một handler gọi `append` sau khi `s.mu.Unlock()` có thể ghi đè lên `Todo` tiếp theo trong `store` mà không qua khóa mutex. Để chặn ghi đè chéo, hãy khóa trần bằng **full slice expression** `s[low:high:max]` (đặt `cap = max - low`) hoặc cấp phát và `copy` (lưu ý `copy(dst, src)` chỉ chép `min(len(dst), len(src))` phần tử, hoặc dùng `slices.Clone(s)`).

Nhớ lại quy tắc ở [Collection trong Go](/blog/go-slices-maps-strings/): `var s []T` (`nil`) và `s := []T{}` đều có `len(s) == 0`, nhưng `encoding/json` xuất `nil` thành `null` còn `[]T{}` thành `[]`. Đó là lý do `store.list()` luôn `make([]Todo, len(s.todos))` dù mảng đang rỗng, còn `slices.Clone(nil)` thì trả về `nil`.

### `append` tăng sức chứa thế nào trên Go 1.27

Khi `len == cap`, `append` gọi `runtime.growslice` để xin mảng mới lớn hơn, chép dữ liệu cũ sang và trả về header mới. Trong `nextslicecap` của Go 1.27.1, dưới ngưỡng `oldCap < 256` Go nhân đôi sức chứa (`2x`), còn qua ngưỡng 256 hệ số giảm dần theo công thức `newcap += (newcap + 3*256) >> 2` về quanh mức `1,25x` rồi làm tròn theo size class của bộ cấp phát. Với slice 500 MB, tăng 25% giúp tránh việc xin thêm nửa gigabyte chỉ để nhét thêm một phần tử.

## 2. Rò bộ nhớ heap ở slice, chuỗi con và map SwissTable

Bộ dọn rác (garbage collector - GC) của Go thu hồi theo từng khối nhớ được cấp phát trên heap, không dọn lẻ từng byte bên trong khối. Chỉ cần còn một con trỏ trỏ vào bất kỳ vị trí nào trong khối nhớ đó, toàn bộ khối đều bị giữ lại. Cứ tưởng tượng bạn giữ vé của một ghế trên đoàn tàu 50 toa: chừng nào ghế đó còn khách, nhà ga không thể tháo 49 toa còn lại.

### Rò sức chứa và đuôi con trỏ trong slice

Hai kiểu cắt slice rất hay ghim RAM vô ích trên heap:

1. **Cắt vài byte từ buffer lớn**: giữ `header := msg[:5]` từ gói tin 1 MiB là ghim trọn 1 MiB trên heap chừng nào `header` còn sống. Viết `msg[:5:5]` cũng không cứu được vì con trỏ vẫn nằm trong khối 1 MiB đó. Phải chép riêng 5 byte bằng `copy` hoặc `bytes.Clone(msg[:5])`.
2. **Thu ngắn slice chứa struct có con trỏ**: cắt `items = items[:2]` trên `[]Todo` khi mỗi `Todo` giữ `Payload []byte` làm `len` tụt từ 500 xuống 2, nhưng các ô `2..499` trong mảng nền vẫn giữ header `Payload` nên GC buộc phải quét và giữ sống cả 498 buffer kia.

Đo trực tiếp trên Go 1.27.1 (gọi `runtime.GC()` hai lượt trước khi đọc `runtime.MemStats` để chắc chắn pha quét đã xong):

```go
package main

import (
	"fmt"
	"runtime"
)

type Todo struct {
	ID      int
	Payload []byte
}

func heapMiB() float64 {
	runtime.GC()
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return float64(m.HeapAlloc) / (1024 * 1024)
}

func main() {
	items := make([]Todo, 500)
	for i := range items {
		items[i] = Todo{ID: i + 1, Payload: make([]byte, 1<<20)}
	}
	fmt.Printf("filled 500 items:    %.1f MiB\n", heapMiB())

	kept := items[:2]
	fmt.Printf("after items[:2]:     %.1f MiB\n", heapMiB())
	runtime.KeepAlive(kept)

	clear(items[2:])
	kept = items[:2]
	fmt.Printf("after clear([2:]):   %.1f MiB\n", heapMiB())
	runtime.KeepAlive(kept)
}
```

### Chuỗi con ghim bộ nhớ và `strings.Clone`

Kiểu `string` là header 16 byte (`ptr`, `len`), nên gặp đúng cái bẫy y hệt slice. Cắt `uuid := hugeLog[:36]` hoặc giữ lại tên `model` từ body 250 KB trong sự cố `vllm-project/aibrix#3508` đều kéo theo toàn bộ chuỗi gốc nằm lì trên heap. Hãy dùng `strings.Clone(log[:36])` mỗi khi chuỗi con sống lâu hơn chuỗi cha.

### Ước lượng kích thước map và SwissTable từ Go 1.24+

Từ Go 1.24, map mặc định dùng thiết kế **SwissTable** đánh địa chỉ mở thay cho chuỗi bucket liên kết (`hmap` + `bmap`) trước đây. Như Michael Pratt giải thích trên [The Go Blog](https://go.dev/blog/swisstable), mỗi map chia dữ liệu thành nhiều bảng con tối đa 1.024 ô (`maxTableCapacity`) bằng kỹ thuật extendible hashing để không bao giờ bị khựng lúc nhân đôi một bảng khổng lồ. Trong mỗi bảng con, các ô chia theo từng nhóm 8 ô gắn với một control word 64 bit: mã băm 64 bit được tách thành 57 bit đầu (`h1`) chọn nhóm và 7 bit cuối (`h2`) lưu trong từng byte control để CPU kiểm tra song song cả 8 ô trong một nhịp.

Hai quy tắc dùng map hằng ngày vẫn không đổi:

- **Truyền ước lượng kích thước `make(map[K]V, hint)`**: benchmark dưới đây cho thấy truyền sẵn `hint` giúp cấp phát bảng đủ chỗ từ đầu thay vì mở rộng và rehash liên tục. Đây là gợi ý kích thước chứ không phải giới hạn cứng, map vẫn tự lớn thêm nếu vượt quá `hint`.
- **Phần tử trong map không lấy được địa chỉ (`&m[k]` báo lỗi biên dịch)**: khi bảng tách đôi hoặc phình lớn, Go dời phần tử sang vùng nhớ khác nên con trỏ vào ô map sẽ thành con trỏ treo. Ngoài ra, theo `internal/abi/map.go`, key hoặc value lớn hơn `128 byte` không nằm trực tiếp trong ô của group mà được Go tự bọc qua con trỏ trên heap.

### Vì sao `delete(m, k)` không làm map nhỏ đi

Lệnh `delete(m, k)` xóa trắng dữ liệu trong ô và đổi byte control sang `empty` hoặc `deleted` (tombstone) để GC dọn đối tượng được trỏ tới, nhưng bản thân bảng SwissTable **không bao giờ tự thu nhỏ** ([golang/go#20135](https://github.com/golang/go/issues/20135), vẫn đang mở). Mình đo cả `map[int][128]byte` (giá trị nằm thẳng trong ô) lẫn `map[int]*[128]byte` (ô chỉ giữ con trỏ 8 byte) với 1 triệu lần chèn rồi xóa 990.000 khóa trên Go 1.27.1:

```go
package main

import (
	"fmt"
	"runtime"
)

func heapMiB() float64 {
	runtime.GC()
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return float64(m.HeapAlloc) / (1024 * 1024)
}

func main() {
	m := make(map[int][128]byte)
	for i := range 1_000_000 {
		m[i] = [128]byte{byte(i)}
	}
	fmt.Printf("value map 1M inserts:    len=%-7d HeapAlloc=%.1f MiB\n", len(m), heapMiB())
	for i := range 990_000 {
		delete(m, i)
	}
	fmt.Printf("value map 990k deletes:  len=%-7d HeapAlloc=%.1f MiB\n", len(m), heapMiB())
	fresh := make(map[int][128]byte, len(m))
	for k, v := range m {
		fresh[k] = v
	}
	m = nil
	fmt.Printf("value map rebuilt:       len=%-7d HeapAlloc=%.1f MiB\n", len(fresh), heapMiB())
	runtime.KeepAlive(fresh)
	fresh = nil

	mp := make(map[int]*[128]byte)
	for i := range 1_000_000 {
		b := [128]byte{byte(i)}
		mp[i] = &b
	}
	fmt.Printf("pointer map 1M inserts:  len=%-7d HeapAlloc=%.1f MiB\n", len(mp), heapMiB())
	for i := range 990_000 {
		delete(mp, i)
	}
	fmt.Printf("pointer map 990k deletes:len=%-7d HeapAlloc=%.1f MiB\n", len(mp), heapMiB())
	runtime.KeepAlive(mp)
}
```

## 3. Bản sao trong vòng lặp `range`, duyệt map và `break` có nhãn

Go gom `while` và `foreach` vào duy nhất từ khóa `for`. Cú pháp `range` nhìn rất gọn, nhưng ba quy tắc định giá và sao chép ngầm của nó rất dễ làm rơi dữ liệu sửa đổi hoặc làm câu lệnh `break` nhảy nhầm chỗ.

### `range` định giá một lần và copy từng phần tử

Hai quy tắc chạy xuyên suốt mọi vòng `for ... range exp`:

1. **Biến giá trị `v` luôn là bản sao**: viết `for _, acc := range accounts { acc.Balance += 100 }` chỉ sửa bản nháp rồi bỏ ở bước kế tiếp. Muốn cập nhật thật thì đi qua chỉ số (`for i := range accounts { accounts[i].Balance += 100 }`) hoặc dùng `[]*Account`, lưu ý slice chứa con trỏ khiến CPU phải nhảy cóc theo địa chỉ heap thay vì đọc mảng liên tiếp (sẽ mổ xẻ ở [Phần cứng và GC trong Go](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/)).
2. **`exp` được tính đúng một lần trước khi vào vòng lặp**: Go copy slice header, array hoặc biến channel vào một biến ẩn ngay trước bước đầu tiên. Vì thế `append` vào slice trong `for range s` vẫn dừng đúng độ dài ban đầu, trong khi `for i := 0; i < len(s); i++` kiểm tra `len(s)` mỗi vòng nên lặp vô tận. Tương tự, duyệt mảng cố định `[3]int` bằng `range a` chạy trên bản copy (`range &a` hoặc `a[i]` mới thấy thay đổi), và gán `ch = ch2` bên trong `for v := range ch` vẫn tiếp tục đọc từ `ch1`.

```go
package main

import "fmt"

func main() {
	s := []int{0, 1, 2}
	for range s {
		s = append(s, 10)
	}
	fmt.Println("slice after range:", s)

	a := [3]int{0, 1, 2}
	for i, v := range a {
		a[2] = 99
		if i == 2 {
			fmt.Println("range a: v=", v, "a[2]=", a[2])
		}
	}
}
```

### Lấy địa chỉ `&c` trong `range` từ Go 1.22 trở đi

Trước Go 1.22, lấy `&c` trong `for _, c := range customers` dùng chung một địa chỉ stack qua mọi lượt lặp, khiến cả map trỏ về mỗi phần tử cuối cùng. Go 1.22 đã đổi vòng đời biến lặp:

<QuoteCard author="Russ Cox & David Chase" role="Nhóm Trình Biên Dịch Go" sourceTitle="Fixing For Loops in Go 1.22" sourceUrl="https://go.dev/blog/loopvar-preview">
Từ Go 1.22, biến khai báo trong vòng lặp for được tạo mới ở từng lượt lặp thay vì dùng chung cho cả vòng, chấm dứt một trong những cái bẫy phổ biến nhất khi goroutine hoặc closure bắt biến lặp.
</QuoteCard>

Ngay cả trên Go 1.27.1, một bẫy nữa vẫn còn nguyên: biến `c` vẫn là **bản sao theo giá trị** của `customers[i]`. Lấy `&c` giờ cho các con trỏ khác nhau thật, nhưng chúng trỏ vào các bản sao riêng chứ không trỏ vào mảng nền của `customers`. Dưới đây là kết quả khi chạy cả hai cách:

```go
package main

import "fmt"

type Customer struct {
	ID      string
	Balance int
}

func main() {
	customers := []Customer{{ID: "1", Balance: 10}, {ID: "2", Balance: 20}}
	byCopy := make(map[string]*Customer)
	for _, c := range customers {
		byCopy[c.ID] = &c // khác địa chỉ từ Go 1.22+, nhưng vẫn trỏ bản sao
	}
	byCopy["1"].Balance += 100
	fmt.Println("range &c:   slice[0]=", customers[0], "map[\"1\"]=", *byCopy["1"])

	byElem := make(map[string]*Customer)
	for i := range customers {
		byElem[customers[i].ID] = &customers[i]
	}
	byElem["1"].Balance += 100
	fmt.Println("index &s[i]: slice[0]=", customers[0], "map[\"1\"]=", *byElem["1"])
}
```

### Thêm khóa khi đang duyệt map và `break` có nhãn

Như [Collection trong Go](/blog/go-slices-maps-strings/) đã chỉ ra, thứ tự duyệt map không được bảo đảm và thay đổi giữa các lần chạy. Nếu bạn lại chèn thêm khóa mới ngay trong lúc chạy `for k, v := range m`, đặc tả Go nói khóa mới có thể xuất hiện ngay trong vòng lặp đó hoặc bị bỏ qua. Thử chạy 4 lượt liên tiếp trên Go 1.27.1:

```go
package main

func main() {

				m[10+k] = true
			}
		}
		fmt.Printf("run %d: len=%d %v\n", run+1, len(m), m)
	}
}
```

Cũng nhớ để ý câu lệnh `break` khi đặt `switch` hoặc `select` bên trong vòng `for`. Trong Go, `break` chỉ thoát khỏi khối `for`, `switch` hoặc `select` gần nhất bên trong, nên một lệnh `break` trơn nằm trong `switch` sẽ để vòng `for` chạy tiếp. Đặt một nhãn trước `for` và gọi `break loop` (hoặc `continue loop`):

```go
package main

import "fmt"

func main() {
	fmt.Print("without label: ")
	for i := range 5 {
		fmt.Printf("%d ", i)
		switch i {
		case 2:
			break
		}
	}
	fmt.Println()

	fmt.Print("with label:    ")
loop:
	for i := range 5 {
		fmt.Printf("%d ", i)
		switch i {
		case 2:
			break loop
		}
	}
	fmt.Println()
}
```

Một bẫy vòng lặp khác (`defer` đặt trong `for` giữ mở toàn bộ file descriptor cho tới khi hàm bao ngoài return) đã có mục riêng trong [Lỗi trong Go](/blog/go-errors-defer-panic/).

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Sao chép biểu thức `range`**: Go tính giá trị biểu thức sau `range` một lần duy nhất trước bước lặp đầu và chạy trên bản copy đó.
- **Vòng đời biến lặp (Go 1.22+)**: mỗi lượt lặp tạo biến `c` riêng nên `&c` không còn trùng địa chỉ nữa, nhưng `c` vẫn là bản sao giá trị chứ không phải `&s[i]`.
- **`break` có nhãn**: gắn `label:` trước `for` và gọi `break label` bên trong `switch` hoặc `select` để thoát thẳng ra khỏi vòng lặp ngoài.

## 4. Bẫy `TrimRight`, `strings.Builder`, `bytes` và so sánh giá trị

Từ [Collection trong Go](/blog/go-slices-maps-strings/#strings-and-runes), ta đã biết `string` là dãy byte UTF-8 bất biến nên `len("Phở")` ra 5 byte chứ không phải 3 ký tự, và cắt theo ký tự cần đổi sang `[]rune(s)`. Ngoài chuyện đếm chữ, bốn thói quen xử lý chuỗi và so sánh dưới đây cũng hay tạo lỗi ngầm hoặc đốt RAM không đáng.

### `TrimRight` khác gì `TrimSuffix`

Hai hàm `strings.TrimRight(s, cutset)` và `strings.TrimLeft(s, cutset)` coi tham số thứ hai là **một tập ký tự rời nhau**, không phải một chuỗi tiền tố hay hậu tố nguyên vẹn. Nếu handler của ứng dụng Todo cắt đuôi `".json"` khỏi `"todo.json"` bằng `TrimRight`, vì chữ `'o'` cũng nằm trong `".json"`, Go gọt luôn cả chữ `'o'` cuối từ `"todo"` và trả về `"tod"`:

```go
package main

import (
	"fmt"
	"strings"
)

func main() {
	fmt.Printf("TrimRight:  %q\n", strings.TrimRight("todo.json", ".json"))
	fmt.Printf("TrimSuffix: %q\n", strings.TrimSuffix("todo.json", ".json"))
	fmt.Printf("TrimRight:  %q\n", strings.TrimRight("123oxo", "xo"))
	fmt.Printf("TrimSuffix: %q\n", strings.TrimSuffix("123oxo", "xo"))
}
```

### Cộng chuỗi bằng `strings.Builder` và giữ nguyên `[]byte`

Vì chuỗi bất biến, viết `s += part` trong vòng lặp bắt Go cấp phát một chuỗi mới và chép lại toàn bộ phần đã nối ở mỗi bước. `strings.Builder` ghi nối tiếp vào một `[]byte` nội bộ, và gọi trước `sb.Grow(totalBytes)` giảm chi phí nối 500 chuỗi từ 499 lần cấp phát xuống đúng 1 lần (nhớ rằng `strings.Builder` không an toàn khi nhiều goroutine ghi cùng lúc và sẽ panic nếu copy theo giá trị sau khi đã ghi, như đã thử ở [Struct và interface trong Go](/blog/go-structs-methods-interfaces/)).

```go
var testParts = slices.Repeat([]string{"todo-123"}, 500)

func BenchmarkStringConcatPlus(b *testing.B) {
	for b.Loop() {
		s := ""
		for _, p := range testParts {
			s += p
		}
		_ = s
	}
}

func BenchmarkStringConcatBuilder(b *testing.B) {
	for b.Loop() {
		var sb strings.Builder
		for _, p := range testParts {
			sb.WriteString(p)
		}
		_ = sb.String()
	}
}

func BenchmarkStringConcatBuilderGrow(b *testing.B) {
	for b.Loop() {
		total := 0
		for _, p := range testParts {
			total += len(p)
		}
		var sb strings.Builder
		sb.Grow(total)
		for _, p := range testParts {
			sb.WriteString(p)
		}
		_ = sb.String()
	}
}
```

### So sánh giá trị (`==`, panic với `any` và `slices.Equal`)

Trước khi khép lại phần kiểu dữ liệu, hai nhóm quy tắc khác đã có bài riêng: tràn số nguyên, viết số bát phân `0o` và sai số dấu phẩy động nằm ở [Kiểu dữ liệu và hàm trong Go](/blog/go-variables-types-pointers-functions/), còn quy tắc chọn value hay pointer receiver cho struct nằm ở [Struct và interface trong Go](/blog/go-structs-methods-interfaces/).

Riêng phép so sánh `==` và `!=` chỉ dùng được với các kiểu **comparable** (boolean, số, string, pointer, channel, interface, cùng struct/array mà mọi trường bên trong đều so sánh được). Slice, map và function không so sánh được, nên struct nào chứa một slice `[]float64` sẽ bị trình biên dịch chặn ngay khi gõ `==`.

Nhưng nếu bạn nhét hai struct không so sánh được đó vào biến kiểu `any`, trình biên dịch cho qua và **chương trình panic ngay lúc chạy**:

```go
package main

import "fmt"

type snapshot struct {
	id  string
	ops []float64
}

func main() {
	var a any = snapshot{id: "x", ops: []float64{1}}
	var b any = snapshot{id: "x", ops: []float64{1}}
	fmt.Println(a == b)
}
```

Khi cần so sánh struct chứa slice hay map trong code chạy thật, hãy tránh `reflect.DeepEqual`:

1. **`reflect.DeepEqual` vừa chậm vừa phân biệt `nil` với `[]int{}`**: trên cùng một `todoSnapshot` dài 100 phần tử `int`, `reflect.DeepEqual` tốn `1047 ns/op` (`96 B/op`, `2 allocs/op`) trong khi hàm `equal` tự viết bằng `slices.Equal` chỉ mất `35,48 ns/op` (`0 allocs/op`).
2. **Hàm chuẩn sẵn có**: hãy ưu tiên `slices.Equal` / `slices.EqualFunc`, `maps.Equal` và `bytes.Equal` cho logic nghiệp vụ, hoặc dùng `google/go-cmp` khi viết test.

```go
	"fmt"

	"slices"

}
```

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Cutset và suffix/prefix**: `TrimRight` / `TrimLeft` cắt theo một tập ký tự bất kể thứ tự, còn `TrimSuffix` / `TrimPrefix` chỉ gỡ đúng một chuỗi đuôi hoặc đầu cố định.
- **`strings.Builder`**: bộ đệm byte giúp nối chuỗi tuyến tính và tránh tạo hàng trăm bản sao trung gian khi gọi kèm `Grow(n)`.
- **Comparable type (kiểu so sánh được)**: kiểu hỗ trợ `==` và `!=`; slice, map và hàm không thuộc nhóm này, và nếu bọc vào `any` thì lỗi chuyển thành panic lúc chạy.

## Điểm rút ra (Key takeaways)

- **Xem slice, map và string như mấy cái header nhỏ**: luôn khóa trần bằng `s[low:high:max]` hoặc `copy` nếu bên nhận có thể gọi `append`, và khai báo sẵn `make([]T, 0, n)` khi biết kích thước để giảm các bước cấp phát từ `runtime.growslice`.
- **Cắt đứt liên kết tới buffer lớn khi giữ lát cắt nhỏ**: `msg[:5:5]` vẫn ghim nguyên mảng gốc trên heap, nên hãy tách riêng bằng `copy`, `bytes.Clone` hay `strings.Clone` (như cách `vllm-project/aibrix#3508` đã sửa), và gọi `clear(s[n:])` trước khi thu ngắn slice chứa con trỏ.
- **Đừng trông chờ `delete()` làm giảm RAM của map**: ước lượng trước bằng `make(map[K]V, hint)`, dùng con trỏ cho giá trị lớn, và định kỳ dựng lại map mới sau đợt tải nhọn để GC thu hồi bảng SwissTable cũ.
- **Đọc kỹ hành vi của `range` và `break`**: `range` định giá biểu thức một lần và copy phần tử, `&c` từ Go 1.22+ trỏ vào bản sao chứ không trỏ vào `&s[i]`, chèn khóa khi đang duyệt map cho độ dài khó đoán, và `break` trong `switch`/`select` cần nhãn vòng lặp.
- **Tránh bẫy chuỗi và so sánh**: dùng `TrimSuffix`/`TrimPrefix` thay cho `TrimRight`/`TrimLeft` khi bỏ hậu tố cố định, dùng `strings.Builder` hoặc `bytes` để giảm cấp phát I/O, và chọn `slices.Equal`/`maps.Equal` hoặc hàm `.Equal()` thay vì `reflect.DeepEqual`.
