### Simple code meets production load
In a toy project or a computer science classroom, software engineering looks straightforward: you write an algorithm, store data in a table, and query it. But the moment code moves into production under real-world load, the ground shifts completely beneath your feet:

- An innocent SQL query that runs in 2ms during development suddenly locks the entire database when 300,000 users refresh their timelines at once.
- A single user publishing an update triggers a cascade of 30,000,000 writes across an in-memory cache, choking the message queue for minutes.
- Every individual backend microservice reports a glowing 99% success rate, yet more than 63% of your paying customers experience agonizing lag.

<NfrToyVsProd />

Every modern data system is judged by three non-negotiable pillars: **Reliability** (continuing to work correctly even when hardware dies or humans make mistakes), **Scalability** (maintaining performance as traffic multiplies), and **Maintainability** (allowing new engineers to evolve the system without breaking existing behavior).

Here is how those three pillars function in the real world, starting from first principles.

<NfrThreePillars />

<Concepts>

- **Production**: the real system serving real users, as opposed to your laptop or a test environment.
- **Microservice**: a small, separate program that does one job (pricing, reviews, profiles). A big app is made of many of them talking over the network.
- **Message queue**: a waiting line for tasks. One program drops a job in; worker programs pick jobs out when they are free.
- **In-memory cache**: a copy of data kept in RAM so it can be read fast without asking the database. Redis is a popular one.

</Concepts>

## Social timelines and the fan-out problem

To see how scalability forces architecture to evolve, consider how social networks deliver home timelines (feeds). Twitter's real-world architectural journey is the classic example.

Twitter handles two primary operations:
1. **Post tweet**: A user publishes a new message (approx. 5,000 tweets/sec average, 12,000+ peak).
2. **Read home timeline**: A user views recent tweets posted by the people they follow (approx. 300,000 requests/sec).

Notice the sheer asymmetry: **reads outnumber writes by more than 50 to 1**.

<NfrReadWriteRatio />

### 1. Fan-out on read: join when the feed loads
The simplest implementation stores users, follows, and tweets in relational tables. When a user posts a tweet, it is a single fast insert:

```sql
INSERT INTO tweets (user_id, text, timestamp) VALUES (:me, :text, NOW());
```

However, when a user views their home timeline, the database must find all people they follow, retrieve their recent tweets, and sort them:

```sql
SELECT tweets.* FROM tweets
JOIN follows ON follows.followee_id = tweets.user_id
WHERE follows.follower_id = :current_user
ORDER BY tweets.timestamp DESC
LIMIT 800;
```

<NfrJoinExample />

At 300,000 read requests per second, this approach completely melts the database. The database server thrashes its buffer pool, exhausts disk IOPS, and memory caches are constantly invalidated. Under heavy load, response times degrade from milliseconds into seconds.

### 2. Fan-out on write: precompute each inbox
To protect the read path, Twitter flipped the model: **do the expensive work at write time**.

Each user is assigned a precomputed timeline cache (a Redis list of tweet IDs acting as a mailbox). When a user opens their app, reading their timeline is a single fast lookup:

```text
LRANGE timeline:user_12345 0 50
```

This read executes in under 2 milliseconds!

**The Catastrophe:** What happens when a user posts a tweet? A cluster of background workers queries the social graph, retrieves the poster's followers, and pushes the tweet ID into every follower's Redis mailbox.

<NfrMailboxSteps />

For an ordinary user with 200 followers, 200 writes is trivial. But consider a celebrity account like Lady Gaga or Elon Musk with **30,000,000+ followers**. A single tweet triggers **30,000,000 write operations** into Redis! 

During major events (such as the 2010 World Cup or New Year's Eve), celebrity tweets created massive queue backlogs. Fan-out workers lagged behind by several minutes, and the site frequently crashed into the iconic "Fail Whale" screen.

### 3. The hybrid that runs in production
Twitter realized that treating all users identically was the architectural flaw. The distribution of followers follows a power law (Pareto distribution): 99.9% of users have modest follower counts, while a tiny fraction have millions.

The solution is a **Hybrid Fan-Out** model:
- **Regular users (< 20,000 followers)**: Continue using **Fan-Out on Write**. Their tweets are pushed directly into their friends' Redis mailboxes.
- **Celebrities (> 1,000,000 followers)**: **Completely skip write fan-out!** Their tweets are written only once to a separate, indexed celebrity timeline store.
- **At read time**: When a follower opens Twitter, a lightweight Timeline Merger service reads their Redis mailbox (regular friends) and queries the recent tweets of the specific celebrities they follow, merging the sorted arrays in-memory in under 5 milliseconds.

<Callout type="tip" title="What to take away">
Scalability is not a single number; it is about how a system handles load parameters. When load distributions are skewed (power-law followers), applying a one-size-fits-all algorithm creates severe bottlenecks. Hybrid architectures route traffic based on load characteristics.
</Callout>

<Concepts>

- **Home timeline (feed)**: the list of recent posts from everyone you follow, newest first.
- **Fan-out**: one action spreading into many. One tweet "fans out" into the timeline of every follower.
- **Fan-out on read / on write**: do that spreading work when someone reads (build the feed on demand) or when someone writes (deliver a copy to each follower in advance).
- **JOIN**: a SQL operation that combines rows from two tables through a shared column, e.g. matching `tweets` with `follows`.
- **Buffer pool & thrashing**: the buffer pool is the database's RAM area for frequently used data. Thrashing means it keeps throwing pages out and loading them back, so it spends its time shuffling data instead of answering queries.
- **IOPS**: input/output operations per second: how many reads and writes a disk can handle each second.
- **Power law (skew)**: most users have few followers while a tiny number have millions. The average hides these extremes.
- **Load parameters**: numbers that describe the load on a system, such as requests per second, read/write ratio, or followers per user.

</Concepts>

## Why averages hide tail latency

When software teams measure system performance, they frequently look at **average (mean) response time**. In distributed systems, relying on the average is a dangerous lie.

Imagine a service where 99 requests take 10ms, but 1 request takes 1,000ms (1 second). The arithmetic mean is:

```text
Mean = (99 * 10ms + 1 * 1,000ms) / 100 = 19.9ms
```

An average of 19.9ms looks great on a monitoring dashboard. But it completely hides the fact that real users experienced a 1-second delay. If an outage causes 2% of requests to stall for 30 seconds, the average might only jump slightly, concealing customer pain.

<PercentileStrip />

### Percentiles show what users actually feel
To understand real user experience, engineers sort all response times from fastest to slowest and calculate percentiles:

- **p50 (Median)**: Exactly half of all requests are faster than this threshold. This represents the typical user experience.
- **p95 & p99**: 95% or 99% of requests are faster. This captures users who hit minor queueing delays, network retries, or garbage collection pauses.
- **p99.9 (The Tail)**: 1 out of every 1,000 requests is slower than this. 

<NfrSortedRequests />

### Why Amazon cares about p99.9
In their landmark Dynamo paper, Amazon engineers explained why they set strict Service Level Objectives (SLOs) around **p99.9** rather than p50.

Amazon observed that a 100ms increase in latency decreased overall sales by 1%. More importantly, the customers who experienced p99.9 tail latency were not random: **they were Amazon's highest-spending VIP customers**. 

A customer buying a single book makes a tiny request with a fast database lookup. But a commercial buyer or power shopper with 200 items in their cart requires hundreds of database queries, recommendation evaluations, and inventory checks. If you ignore the tail, you alienate your most profitable users.

### Dean and Barroso: fan-out makes the tail worse
In 2013, Google Fellow Jeffrey Dean and Luiz André Barroso published a seminal paper in the *Communications of the ACM* titled **"The Tail at Scale"**. They proved mathematically why microservices make tail latency catastrophic.

In modern web applications, rendering a single page (such as a search results page or an e-commerce dashboard) requires a root API Gateway to make parallel backend calls to dozens or hundreds of leaf microservices (pricing, reviews, recommendations, user profile, ads, inventory).

The user's total response time is bounded by the **slowest backend service**.

Suppose a single backend service has an excellent latency profile:
- 99% of calls finish in 10ms.
- Only 1% of calls (p99) experience a 1-second delay (due to a JVM garbage collection pause, a page fault, or thread contention).

If a user request fans out to **100 independent services** in parallel, what is the probability that the user experiences the 1-second delay?

```text
P(all 100 fast)      = 0.99^100 ≈ 0.366 (36.6%)
P(at least one slow) = 1 - 0.99^100 = 1 - 0.366 = 63.4%
```

| Backend Calls per Page (N) | Single Service Tail Prob (p) | User Request Tail Penalty |
|---|---|---|
| **1 call** | 1% (0.01) | **1.0%** |
| **10 calls** | 1% (0.01) | **9.6%** |
| **50 calls** | 1% (0.01) | **39.5%** |
| **100 calls** | 1% (0.01) | **63.4%** |
| **200 calls** | 1% (0.01) | **86.6%** |

Think about that result: **even though 99% of your microservice operations are blisteringly fast, nearly two-thirds (63.4%) of your end users will experience a frustrating 1-second lag!**

<TailAmplification />

<Figure src={tailChart} alt="Chart of the probability that a request takes over one second as the number of servers grows, for server outliers of 1 in 100, 1 in 1,000 and 1 in 10,000; the 1-in-100 curve passes 0.63 at 100 servers" caption="Google's own plot of the same effect: with a 1-in-100 slow server, the chance of a slow page is 0.63 at 100 servers and keeps climbing." sourceTitle="The Tail at Scale, Communications of the ACM (Dean and Barroso)" sourceUrl="https://www.barroso.org/publications/TheTailAtScale.pdf" />

<Callout type="note" title="So how do teams fight the tail?">
As Dean and Barroso demonstrated, tail-tolerant systems cannot rely on making every server 100% predictable. Instead, systems use **Hedged Requests** (firing a duplicate request to a second replica if the first takes longer than p95) and **Tied Requests** (coordinating between replicas so whichever starts first cancels the other).
</Callout>

<NfrHedgedRequest />

### Real case: hedged requests on a 100-server BigTable read
Dean and Barroso tested this on a Google benchmark that reads 1,000 keys from a BigTable table spread across 100 servers. One read touches every server, so the slowest server decides the answer time, the same effect as the 63% above.

<NfrBigtableRead />

The fix is cheap. The client sends the request to one replica. If no answer comes within 10ms, it sends the same request to a second replica and uses whichever answers first. In the paper's numbers, this cut the 99.9th-percentile latency for fetching all 1,000 values from 1,800ms to 74ms while sending only 2% more requests. It works because the delay is usually caused by interference around one server (a queue, a pause), not by the request itself, so a second server is very likely to be fine.

<NfrHedgeResult />

<Concepts>

- **Latency**: how long one request takes, from sending it to getting the answer back.
- **Mean vs. median**: the mean is sum ÷ count, so a few very slow requests can hide inside it. The median (p50) is the middle value after you sort all requests.
- **Percentile (p95, p99, p99.9)**: "p99 = 200ms" means 99% of requests finish within 200ms and 1% are slower.
- **Tail latency**: the slow end of that sorted list: the p99 and p99.9 requests.
- **SLO (Service Level Objective)**: a performance target the team commits to, e.g. "p99.9 under 300ms".
- **Garbage collection (GC) pause**: in Java and similar languages, the runtime briefly stops the program to clean up unused memory. Requests in flight have to wait.
- **Replica**: an identical copy of a server or its data, kept for speed or safety.
- **Hedged / tied request**: hedged: if the answer is slow, send the same request to a second replica and take whichever replies first. Tied: send to two replicas at once, and the one that starts first tells the other to cancel.

</Concepts>

## Faults, failures and human error

No matter how pristine your architecture is on paper, production systems operate in an imperfect physical world. Components will fail.

### Faults vs. failures
Engineers draw a critical distinction between two terms:
- **Fault**: A single component deviating from its specification (a hard drive throwing read errors, a network switch dropping packets, a server losing power).
- **Failure**: The entire system ceasing to provide service to its users.

The goal of reliability is **fault tolerance**: designing a system such that individual component faults are contained, isolated, and absorbed without escalating into a catastrophic system failure.

<FaultVsFailure />

### Three places faults come from

<NfrFaultSources />

1. **Hardware Faults**:
   Hard drives have a Mean Time Between Failures (MTBF) of about 10–50 years. That sounds safe until you scale: 10,000 disks fail at 10,000 ÷ (MTBF in years × 365) per day, which is between about 0.5 and 2.7 disks a day, so in a datacenter you replace a failed hard drive **nearly every day**. Redundancy (RAID arrays, dual power supplies, hot-standby nodes) protects against hardware faults.

<DiskFailures />

2. **Software Faults (Systematic Bugs)**:
   Hardware faults are usually uncorrelated: one disk dying does not cause other disks in the rack to die. Software faults, by contrast, are systematic and correlated. Examples include:
   - A leap second causing CPU runaway across an entire cluster.
   - A runaway query that consumes all database memory, causing one replica to crash, which diverts traffic to the second replica, crashing it in a **cascading failure**.
   - A thundering herd problem when a cache expires and thousands of requests overwhelm the backend simultaneously.

3. **Human Error (The Leading Cause of Outages)**:
   A study of three large internet services by Oppenheimer, Ganapathi and Patterson found a sobering pattern: **operator mistakes caused the largest share of failures in two of the three services**, took longer to fix than other failures, and configuration mistakes were the largest kind of operator mistake.

The cascading failure from the second item is the one that surprises people, because every step looks reasonable:

<NfrCascade />

### Designing for human error
Because humans will inevitably make mistakes, reliable systems are designed defensively:

- **Decoupled Sandbox Environments**: Allow operators to experiment safely where mistakes have no user impact.
- **Canary Rollouts**: Gradually release configuration and code changes to a small fraction of users (1% &rarr; 10% &rarr; 100%) while automated monitors watch error rates.
- **Fast, Automated Rollbacks**: When metrics degrade, rollback immediately without waiting for an engineer to debug root causes.
- **Chaos Engineering**: Pioneered by Netflix with *Chaos Monkey*, constantly inject controlled faults (killing random instances, throttling networks) during business hours so systems prove their self-healing capability before real disasters occur.

<NfrSafetyNet />

<CanaryRollout />

<Concepts>

- **Fault vs. failure**: a fault is one part breaking (a disk, a cable, a process). A failure is the whole service stopping for users. Good design lets faults happen without causing failures.
- **Fault tolerance**: the ability to keep working correctly while some parts are broken.
- **MTBF (Mean Time Between Failures)**: the average time a component runs before it breaks.
- **Redundancy & RAID**: keeping spare copies so one broken part does not lose data or stop service. RAID spreads data over several disks so one disk can die safely.
- **Cascading failure**: one overloaded part fails, its traffic moves to the next part, which then fails too, like falling dominoes.
- **Thundering herd**: a crowd of requests hitting the backend at the same moment, e.g. right after a popular cache entry expires.
- **Canary rollout**: release a change to a small slice of users first, watch the error rate, then widen it step by step.
- **Rollback**: switch back to the last version that worked.
- **Chaos engineering**: breaking things on purpose, in a controlled way, to prove the system really recovers.

</Concepts>

## Maintainability and the complexity trap

The majority of software cost is not spent during initial development; it is spent during **maintenance**: fixing bugs, keeping dependencies up to date, onboarding new engineers, and adapting to changing business needs.

Maintainability rests on three principles:

### 1. Operability: easy to run
A system is operable when ops teams can monitor its health, deploy updates safely, and restore service quickly during incidents. Operability requires:
- Exposing clear runtime telemetry (metrics, logs, distributed traces).
- Providing predictable default behaviors and clean self-healing mechanisms.
- Avoiding manual runbooks in favor of declarative automation.

<NfrOperability />

### 2. Simplicity: cut accidental complexity
Complexity is the primary obstacle to software maintainability. It leads to hidden dependencies, tight coupling, and fragile modifications.

Engineers distinguish between two forms of complexity:
- **Essential Complexity**: The inherent difficulty of the business problem itself (e.g., tax calculation rules or trading exchange order matching).
- **Accidental Complexity**: Complexity introduced solely by the implementation choices, clumsy abstractions, or technology sprawl.

The most potent weapon against accidental complexity is **clean abstractions**. A good abstraction hides overwhelming implementation details behind a clean, intuitive interface (like how an LSM-tree or B-tree abstracts raw disk sectors into a simple key-value store).

<NfrAbstraction />

### 3. Evolvability: easy to change
Requirements change constantly. A system designed around rigid assumptions becomes impossible to modify without breaking legacy clients. Evolvability means structuring systems with loose coupling, clean API contracts, and backward/forward-compatible serialization schemas (such as Protocol Buffers or Avro) so components can be upgraded independently.

<NfrCompat />

<Concepts>

- **Operability**: how easy the system is for the people who run it: watching it, deploying it, fixing incidents.
- **Telemetry (metrics, logs, traces)**: data the system reports about itself: numbers over time, text records of events, and the path one request takes across services.
- **Runbook**: a written step-by-step guide for operators, e.g. "if the disk fills up, do X".
- **Essential vs. accidental complexity**: essential complexity comes from the problem itself. Accidental complexity comes from how we chose to build the solution.
- **Abstraction**: a simple interface that hides messy details, like a key-value API that hides how bytes sit on disk.
- **B-tree / LSM-tree**: two common ways a database organises data on disk so lookups stay fast. Each is a topic of its own.
- **Loose coupling**: parts depend on each other as little as possible, so you can change one without breaking the others.
- **Backward / forward compatibility**: backward: new code can read old data. Forward: old code can still read data written by new code.
- **Protocol Buffers / Avro**: formats for encoding data to send or store, built so the data structure (schema) can change safely over time.

</Concepts>

## Key takeaways

- **Averages are misleading**: Never evaluate production systems using arithmetic mean latency. Focus on percentiles (**p50, p95, p99, p99.9**) to capture what real users endure.
- **Tail latency amplification is real**: When a request fans out across 100 backend services, a 1% anomaly rate (p99) balloons into a **63.4% chance** that the end-user request stalls.
- **Skew breaks uniform architectures**: A single celebrity post can trigger millions of writes in a fan-out architecture. Successful systems use hybrid routing based on load parameters.
- **Reliability means tolerating faults**: Assume hardware dies and humans misconfigure systems. Build with canary rollouts, fast rollbacks, and self-healing redundancy.
- **Fight accidental complexity**: The longevity of a software system depends on clean abstractions that allow future engineers to change behavior without fear.

### Khi code đơn giản gặp tải thật trên production
Trong các bài tập lập trình ở trường đại học hoặc dự án mẫu, kỹ thuật phần mềm có vẻ rất dễ hiểu: bạn viết một thuật toán, lưu dữ liệu vào một bảng và dùng câu lệnh SQL để lấy ra. Nhưng khoảnh khắc đoạn code đó bước ra môi trường production dưới tải thực tế, thực tế sẽ làm sụp đổ mọi giả định ngây thơ:

- Một câu lệnh truy vấn SQL chạy chỉ mất 2 mili-giây trên máy cá nhân lại làm nghẽn đứng toàn bộ database khi 300,000 người dùng đồng loạt làm mới bảng tin vào buổi sáng.
- Một bài đăng duy nhất của người nổi tiếng kích hoạt cơn bão 30,000,000 lệnh ghi vào bộ nhớ đệm cache, làm tê liệt hoàn toàn hàng đợi thông điệp trong nhiều phút.
- Từng microservice riêng lẻ đều báo cáo trạng thái xanh mượt 99%, nhưng hơn 63% khách hàng thực tế lại phải chờ đợi quay vòng trong ức chế.

<NfrToyVsProd />

Mọi hệ thống dữ liệu hiện đại đều được đo lường bằng 3 trụ cột phi chức năng cốt lõi: **Độ tin cậy (Reliability)** (vẫn vận hành chính xác kể cả khi phần cứng cháy hoặc con người thao tác sai), **Khả năng mở rộng (Scalability)** (giữ vững hiệu năng khi lưu lượng tăng gấp nhiều lần), và **Khả năng bảo trì (Maintainability)** (giúp kỹ sư thế hệ sau dễ dàng nâng cấp tính năng mà không làm vỡ hệ thống).

Hãy cùng mình phân tích sâu 3 trụ cột này từ những nguyên lý đầu tiên (first principles).

<NfrThreePillars />

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Production**: hệ thống thật đang phục vụ người dùng thật, khác với máy cá nhân hay môi trường test.
- **Microservice**: một chương trình nhỏ, chạy riêng, chỉ lo một việc (giá, đánh giá, hồ sơ người dùng). Một ứng dụng lớn gồm nhiều microservice gọi nhau qua mạng.
- **Message queue (hàng đợi thông điệp)**: hàng chờ cho các tác vụ. Một chương trình bỏ việc vào; các worker rảnh thì lấy việc ra làm.
- **In-memory cache**: bản sao dữ liệu để trong RAM để đọc nhanh mà không phải hỏi database. Redis là loại phổ biến.

</Concepts>

## Timeline mạng xã hội và bài toán fan-out

Để thấy được việc quy mô (scale) buộc kiến trúc hệ thống phải thay đổi như thế nào, hãy nhìn vào bài toán hiển thị bảng tin (home timeline) của mạng xã hội. Hành trình kiến trúc thực tế của Twitter (nay là X) là ví dụ kinh điển.

Twitter có 2 thao tác nghiệp vụ cốt lõi:
1. **Đăng tweet (Post tweet)**: Người dùng xuất bản bài viết mới (trung bình 5,000 tweets/giây, giờ cao điểm hơn 12,000 tweets/giây).
2. **Xem trang chủ (Read home timeline)**: Người dùng tải bảng tin gồm các bài viết mới nhất từ những người họ theo dõi (khoảng 300,000 lượt đọc/giây).

Hãy chú ý sự bất đối xứng kinh khủng này: **Lượt đọc nhiều gấp hơn 50 lần lượt ghi**.

<NfrReadWriteRatio />

### 1. Fan-out on read: JOIN mỗi khi mở feed
Cách đơn giản nhất là lưu thông tin users, follows (theo dõi) và tweets vào các bảng cơ sở dữ liệu quan hệ. Khi ai đó đăng bài, việc ghi diễn ra rất nhanh trong một câu lệnh INSERT:

```sql
INSERT INTO tweets (user_id, text, timestamp) VALUES (:me, :text, NOW());
```

Tuy nhiên, mỗi khi một người dùng mở app để xem bảng tin, cơ sở dữ liệu phải tìm toàn bộ những người mà họ đang theo dõi, lấy bài viết mới nhất và sắp xếp giảm dần theo thời gian:

```sql
SELECT tweets.* FROM tweets
JOIN follows ON follows.followee_id = tweets.user_id
WHERE follows.follower_id = :current_user
ORDER BY tweets.timestamp DESC
LIMIT 800;
```

<NfrJoinExample />

Với **300,000 lượt đọc mỗi giây**, cách làm này làm tê liệt hoàn toàn database. Bộ nhớ đệm buffer pool bị đảo lộn liên tục, ổ đĩa cạn kiệt IOPS, và CPU chạm trần 100%. Độ trễ truy vấn tụt dốc từ vài mili-giây lên tới hàng chục giây.

### 2. Fan-out on write: tính sẵn hộp thư cho từng người
Để bảo vệ luồng đọc, Twitter đã đảo ngược mô hình: **chấp nhận tốn công lúc ghi để luồng đọc đạt tốc độ tối đa**.

Mỗi người dùng được cấp một hộp thư bảng tin tính toán trước trên bộ nhớ đệm (danh sách ID tweet trên Redis). Khi bạn mở ứng dụng, việc lấy bảng tin chỉ là một thao tác đọc Redis siêu nhẹ:

```text
LRANGE timeline:user_12345 0 50
```

Thao tác đọc này hoàn thành trong chưa đầy 2 mili-giây!

**Cạm bẫy chết người:** Điều gì xảy ra khi có người đăng tweet? Một cụm worker chạy ngầm sẽ tra cứu đồ thị theo dõi của tác giả, rồi lặp qua từng người theo dõi để chèn ID bài viết vào hộp thư Redis của họ.

Trong những sự kiện lớn (như chung kết World Cup hay giao thừa), các bài tweet của người nổi tiếng làm hàng đợi thông điệp bùng nổ. Cụm worker bị nghẽn tới vài phút, và Twitter liên tục sập với hình ảnh chú cá voi "Fail Whale" huyền thoại.

### 3. Kiểu lai (hybrid) chạy thật trên production
Twitter nhận ra rằng việc áp dụng cùng một cơ chế xử lý cho mọi tài khoản là sai lầm cốt lõi. Sự phân bố người theo dõi tuân theo định luật lũy thừa (Pareto): 99.9% người dùng có lượng bạn bè vừa phải, trong khi chỉ một số rất ít có hàng triệu người theo dõi.

Giải pháp là **Mô hình Hybrid (Lai)**:
- **Người dùng thông thường (< 20,000 người theo dõi)**: Tiếp tục dùng **Fan-Out on Write**. Bài viết của họ được đẩy sẵn vào hộp thư Redis của bạn bè.
- **Người nổi tiếng (> 1,000,000 người theo dõi)**: **Tuyệt đối không fan-out lúc ghi!** Bài viết của họ chỉ được ghi một lần duy nhất vào một bảng lưu trữ bài viết riêng biệt.
- **Khi người dùng mở ứng dụng**: Bộ hợp nhất bảng tin (Timeline Merger) sẽ đọc hộp thư Redis của họ (bài viết từ bạn bè thường) và truy vấn song song bài mới nhất của những người nổi tiếng mà họ theo dõi, sau đó ghép hai mảng đã sắp xếp ngay trong RAM chỉ mất dưới 5 mili-giây.

- **Home timeline (feed)**: danh sách bài mới của tất cả những người bạn theo dõi, mới nhất ở trên.
- **Fan-out**: một hành động tỏa ra thành rất nhiều hành động. Một tweet "fan-out" vào timeline của từng follower.
- **Fan-out on read / on write**: làm việc tỏa ra đó lúc có người đọc (ghép feed khi cần) hoặc lúc có người đăng (gửi trước bản sao cho từng follower).
- **JOIN**: phép SQL ghép các dòng của hai bảng qua một cột chung, ví dụ ghép bảng `tweets` với bảng `follows`.
- **Buffer pool & thrashing**: buffer pool là vùng RAM database dùng để giữ dữ liệu hay dùng. Thrashing là khi nó liên tục đẩy dữ liệu ra rồi nạp lại, mất hết thời gian xáo dữ liệu thay vì trả lời truy vấn.
- **IOPS**: số thao tác đọc/ghi mỗi giây mà ổ đĩa xử lý được.
- **Power law (phân phối lệch)**: đa số người dùng có ít follower, một số rất ít có hàng triệu. Con số trung bình che mất những trường hợp cực đoan này.
- **Load parameters (tham số tải)**: các con số mô tả tải của hệ thống, như số request mỗi giây, tỉ lệ đọc/ghi, số follower mỗi người.

</Concepts>

## Vì sao số trung bình che mất độ trễ đuôi (tail latency)

Khi đánh giá hiệu năng hệ thống, các đội ngũ kỹ thuật thường có thói quen nhìn vào **độ trễ trung bình (Mean / Average latency)**. Trong hệ thống phân tán, tin vào số trung bình là một cái bẫy chết người.

Giả sử hệ thống xử lý 100 yêu cầu: 99 yêu cầu chạy cực nhanh trong 10 mili-giây, nhưng có đúng 1 yêu cầu bị treo mất 1,000 mili-giây (1 giây). Số trung bình số học sẽ là:

```text
Số trung bình = (99 * 10ms + 1 * 1,000ms) / 100 = 19.9ms
```

Con số 19.9ms hiển thị trên màn hình giám sát trông rất đẹp. Nhưng nó đã che giấu hoàn toàn sự thật rằng có người dùng đã phải chịu đựng độ trễ 1 giây. Nếu có sự cố khiến 2% request bị đứng 30 giây, số trung bình chỉ nhích lên một chút, ru ngủ đội ngũ vận hành trong khi khách hàng đang bỏ đi.

<PercentileStrip />

### Phân vị (percentile) phản ánh đúng trải nghiệm
Để nắm bắt chính xác trải nghiệm người dùng, các kỹ sư sắp xếp toàn bộ thời gian phản hồi từ nhanh nhất đến chậm nhất và tính các phân vị:

- **p50 (Trung vị - Median)**: Đúng 50% yêu cầu có tốc độ nhanh hơn ngưỡng này. Đây là trải nghiệm điển hình của người dùng thông thường.
- **p95 & p99**: 95% hoặc 99% yêu cầu nhanh hơn con số này. Nó phản ánh những người dùng không may gặp phải hiện tượng nghẽn hàng đợi nhỏ, mạng chập chờn, hoặc dừng gom rác bộ nhớ (GC pause).
- **p99.9 (Độ trễ đuôi - The Tail)**: Đúng 1 trong mỗi 1,000 yêu cầu bị chậm hơn mốc này.

<NfrSortedRequests />

### Vì sao Amazon quan tâm tới p99.9
Trong bài báo kinh điển về cơ sở dữ liệu Dynamo, các kỹ sư Amazon đã giải thích lý do họ đặt ra các cam kết dịch vụ (SLA) nghiêm ngặt xoay quanh **p99.9** chứ không phải số trung bình hay p50.

Nghiên cứu của Amazon chỉ ra rằng cứ mỗi 100 mili-giây độ trễ tăng thêm sẽ làm sụt giảm 1% doanh số. Quan trọng hơn cả: những khách hàng rơi vào nhóm p99.9 chịu độ trễ tệ nhất **lại chính là những khách hàng VIP giá trị nhất của Amazon**. 

Một người mua một quyển sách chỉ tạo ra một request nhẹ với một lệnh đọc database. Nhưng một khách hàng mua buôn hoặc người dùng có giỏ hàng hàng trăm món đồ sẽ đòi hỏi hàng trăm truy vấn kiểm tra kho, tính giá và gợi ý sản phẩm. Nếu bạn bỏ qua độ trễ đuôi, bạn đang trực tiếp làm nản lòng những người đem lại nhiều doanh thu nhất.

### Dean và Barroso: fan-out làm độ trễ đuôi tệ hơn
Năm 2013, hai kỹ sư huyền thoại của Google là Jeffrey Dean và Luiz André Barroso đã công bố công trình nổi tiếng trên tạp chí *CACM* mang tên **"The Tail at Scale"**. Họ đã chứng minh bằng toán học tại sao kiến trúc microservices lại làm cho độ trễ đuôi trở nên nguy hiểm gấp bội.

Trong một ứng dụng hiện đại, để hiển thị một trang web hoàn chỉnh, một API Gateway trung tâm thường phải gọi song song đến hàng chục hoặc hàng trăm microservices phía sau (giá cả, bình luận, gợi ý, giỏ hàng, quảng cáo, tồn kho).

Tổng thời gian người dùng phải chờ đợi bị giới hạn bởi **service phản hồi chậm nhất**.

Giả sử một microservice riêng lẻ có hiệu năng cực kỳ ấn tượng:
- 99% request hoàn thành chỉ trong 10 mili-giây.
- Chỉ có đúng 1% request (p99) bị chậm 1 giây (do dừng gom rác JVM, tranh chấp luồng CPU hoặc nghẽn ổ đĩa).

Nếu một trang web gọi đồng thời **100 microservices** như vậy, xác suất để người dùng phải chịu độ trễ 1 giây là bao nhiêu?

```text
P(toàn bộ 100 nhanh)    = 0.99^100 ≈ 0.366 (36.6%)
P(ít nhất 1 service chậm) = 1 - 0.99^100 = 1 - 0.366 = 63.4%
```

| Số lượng gọi Backend (N) | Xác suất đuôi của 1 service (p) | Tỷ lệ người dùng bị chậm thực tế |
|---|---|---|
| **1 call** | 1% (0.01) | **1.0%** |
| **10 calls** | 1% (0.01) | **9.6%** |
| **50 calls** | 1% (0.01) | **39.5%** |
| **100 calls** | 1% (0.01) | **63.4%** |
| **200 calls** | 1% (0.01) | **86.6%** |

Hãy nhìn vào nghịch lý này: **Dù 99% thao tác của từng server backend đều chạy mượt mà, thì có tới gần hai phần ba (63.4%) người dùng cuối phải chịu cảnh chờ đợi hơn 1 giây!**

<Figure src={tailChart} alt="Biểu đồ xác suất một request chậm hơn một giây khi số server tăng, với server chậm 1 trên 100, 1 trên 1,000 và 1 trên 10,000; đường 1 trên 100 đạt 0.63 ở 100 server" caption="Biểu đồ của chính Google cho hiệu ứng này: nếu 1 server trên 100 hay chậm, xác suất trang bị chậm là 0.63 khi có 100 server và còn tăng tiếp." sourceTitle="The Tail at Scale, Communications of the ACM (Dean và Barroso)" sourceUrl="https://www.barroso.org/publications/TheTailAtScale.pdf" />

<Callout type="note" title="Vậy làm sao bớt độ trễ đuôi?">
Như Dean và Barroso chỉ ra, hệ thống quy mô lớn không thể trông chờ vào việc ép mọi server phải phản hồi hoàn hảo 100%. Thay vào đó, kiến trúc phải dùng kỹ thuật **Hedged Requests** (tự động bắn một request dự phòng sang bản sao replica thứ hai nếu replica thứ nhất chậm quá ngưỡng p95) và **Tied Requests** (hai replica phối hợp để hủy tác vụ của bên còn lại khi một bên bắt đầu xử lý).
</Callout>

### Ca thực tế: hedged request khi đọc BigTable trên 100 server
Dean và Barroso thử kỹ thuật này trên một benchmark của Google: đọc 1,000 key từ một bảng BigTable trải trên 100 server. Một lần đọc chạm tới mọi server, nên server chậm nhất quyết định thời gian trả lời, cùng hiệu ứng 63% ở trên.

<NfrBigtableRead />

Cách sửa rất rẻ. Client gửi request tới một replica. Nếu 10ms không có phản hồi, nó gửi cùng request đó sang replica thứ hai và dùng câu trả lời nào về trước. Theo số liệu trong bài báo, độ trễ p99.9 để lấy đủ 1,000 giá trị giảm từ 1,800ms xuống 74ms, mà chỉ gửi thêm 2% request. Nó hiệu quả vì độ trễ thường do nhiễu quanh một server (hàng đợi, một lần pause), không phải do bản thân request, nên server thứ hai gần như chắc chắn ổn.

<NfrHedgeResult />

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Latency (độ trễ)**: thời gian một request mất từ lúc gửi đi tới lúc nhận được câu trả lời.
- **Mean vs. median**: mean (trung bình) là tổng ÷ số lượng, nên vài request rất chậm có thể bị giấu trong đó. Median (p50) là giá trị ở giữa sau khi xếp tất cả request theo thứ tự.
- **Percentile (p95, p99, p99.9)**: "p99 = 200ms" nghĩa là 99% request xong trong 200ms, còn 1% chậm hơn.
- **Tail latency (độ trễ đuôi)**: phần chậm nhất ở cuối danh sách đã xếp: các request p99, p99.9.
- **SLO (Service Level Objective)**: mục tiêu hiệu năng đội cam kết, ví dụ "p99.9 dưới 300ms".
- **GC pause (dừng để dọn bộ nhớ)**: trong Java và các ngôn ngữ tương tự, runtime dừng chương trình một chút để dọn vùng nhớ không dùng. Request đang chạy phải đợi.
- **Replica (bản sao)**: một bản giống hệt của server hoặc dữ liệu, giữ để chạy nhanh hơn hoặc an toàn hơn.
- **Hedged / tied request**: hedged: nếu câu trả lời chậm, gửi lại y hệt request đó sang replica thứ hai và lấy kết quả nào về trước. Tied: gửi cho hai replica cùng lúc, replica nào bắt đầu làm trước sẽ báo replica kia hủy.

</Concepts>

## Fault, failure và lỗi do con người

Dù bản vẽ kiến trúc của bạn có hoàn hảo đến đâu, phần mềm khi chạy thật vẫn phải dựa trên phần cứng vật lý. Và đồ vật lý thì chắc chắn sẽ hỏng.

### Hỏng một phần (fault) và sập cả hệ thống (failure)
Các kỹ sư phân biệt rạch ròi giữa hai khái niệm:
- **Fault (Sai sót / Lỗi linh kiện)**: Một linh kiện riêng lẻ hoạt động lệch khỏi thiết kế (ổ cứng bị bad sector, dây cáp mạng chập chờn, một thanh RAM bị đảo bit, server mất điện).
- **Failure (Hệ thống sụp đổ)**: Toàn bộ hệ thống ngừng cung cấp dịch vụ cho người dùng.

Mục tiêu của tính tin cậy (Reliability) chính là **khả năng chịu lỗi (fault tolerance)**: thiết kế hệ thống sao cho những hỏng hóc cục bộ của linh kiện được cô lập và hấp thụ hoàn toàn, không bao giờ lan rộng thành sự sụp đổ của cả dịch vụ.

<FaultVsFailure />

### Lỗi đến từ ba nguồn

<NfrFaultSources />

1. **Lỗi phần cứng (Hardware Faults)**:
   Một ổ cứng có thời gian trung bình giữa các lần hỏng (MTBF) khoảng 10–50 năm. Nhưng khi quy mô lớn thì khác: 10.000 ổ cứng hỏng với tốc độ 10.000 ÷ (MTBF theo năm × 365) mỗi ngày, tức khoảng 0,5 đến 2,7 ổ mỗi ngày, nên trong một trung tâm dữ liệu bạn phải thay một ổ cứng chết **gần như mỗi ngày**. Các giải pháp dự phòng phần cứng (RAID, nguồn điện kép, cụm đa vùng Availability Zone) sinh ra để giải quyết bài toán này.

<DiskFailures />

2. **Lỗi phần mềm có hệ thống (Software Faults)**:
   Lỗi phần cứng thường độc lập: một ổ cứng chết không làm các ổ cứng bên cạnh chết theo. Ngược lại, lỗi phần mềm thường mang tính hệ thống và lây lan dây chuyền:
   - Một giây nhuận (leap second) làm CPU trên hàng ngàn máy chủ Linux tăng vọt 100%.
   - Một truy vấn nặng làm một node database bị tràn bộ nhớ và chết, khiến toàn bộ lưu lượng dồn sang node thứ hai và làm node này chết tiếp theo (**hiệu ứng thác lũ - cascading failure**).
   - Hiện tượng bầy đàn tranh chấp (thundering herd) khi một khóa cache hết hạn và hàng chục ngàn request cùng ùa vào đánh sập cơ sở dữ liệu gốc.

3. **Sai lầm của con người (Thủ phạm số một)**:
   Một nghiên cứu của Oppenheimer, Ganapathi và Patterson trên ba dịch vụ internet lớn chỉ ra một quy luật phũ phàng: **lỗi của người vận hành gây ra phần lớn nhất các vụ sập ở hai trong ba dịch vụ**, mất nhiều thời gian sửa hơn các lỗi khác, và lỗi cấu hình là loại lỗi vận hành lớn nhất.

Lỗi dây chuyền ở mục thứ hai là loại hay làm người ta bất ngờ, vì từng bước trông đều hợp lý:

<NfrCascade />

### Thiết kế để chịu được lỗi do người
Vì con người chắc chắn sẽ có lúc sơ suất, các hệ thống tin cậy luôn được thiết kế theo hướng phòng thủ:

- **Môi trường Sandbox độc lập**: Cho phép kỹ sư thử nghiệm an toàn trên môi trường mô phỏng mà không lo ảnh hưởng đến dữ liệu người dùng thật.
- **Phát hành theo đợt (Canary Rollouts)**: Triển khai cấu hình hoặc code mới dần dần trên một tỷ lệ nhỏ người dùng (1% &rarr; 10% &rarr; 100%) kèm hệ thống giám sát tự động bắt lỗi.
- **Khả năng hoàn tác tự động (Automated Rollbacks)**: Khi chỉ số lỗi vượt ngưỡng, hệ thống tự động quay về phiên bản cũ ngay lập tức mà không cần chờ con người can thiệp.
- **Kỹ thuật hỗn loạn (Chaos Engineering)**: Tiêu biểu là công cụ *Chaos Monkey* của Netflix, chủ động giả lập việc ngắt ngẫu nhiên các máy chủ đang chạy trong giờ làm việc để chứng minh năng lực tự chữa lành của hệ thống trước khi sự cố thật ập đến.

<NfrSafetyNet />

<CanaryRollout />

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Fault vs. failure**: fault là một bộ phận hỏng (một ổ đĩa, một sợi cáp, một tiến trình). Failure là cả dịch vụ ngừng phục vụ người dùng. Thiết kế tốt cho phép fault xảy ra mà không thành failure.
- **Fault tolerance (chịu lỗi)**: khả năng vẫn chạy đúng khi có vài bộ phận đang hỏng.
- **MTBF (Mean Time Between Failures)**: thời gian trung bình một linh kiện chạy được trước khi hỏng.
- **Redundancy & RAID**: giữ bản dự phòng để một bộ phận hỏng không làm mất dữ liệu hay dừng dịch vụ. RAID chia dữ liệu ra nhiều ổ đĩa để một ổ chết vẫn an toàn.
- **Cascading failure (sập dây chuyền)**: một bộ phận quá tải rồi sập, tải của nó dồn sang bộ phận kế tiếp, bộ phận đó cũng sập, như domino đổ.
- **Thundering herd**: một đám đông request cùng lao vào backend một lúc, ví dụ ngay khi một mục cache được dùng nhiều vừa hết hạn.
- **Canary rollout**: phát hành thay đổi cho một nhóm nhỏ người dùng trước, theo dõi tỉ lệ lỗi, rồi mới mở rộng dần.
- **Rollback**: quay về phiên bản gần nhất còn chạy tốt.
- **Chaos engineering**: cố ý làm hỏng hệ thống một cách có kiểm soát để chứng minh nó thật sự tự phục hồi được.

</Concepts>

## Khả năng bảo trì và cái bẫy độ phức tạp

Phần lớn chi phí và thời gian của vòng đời phần mềm không nằm ở giai đoạn viết mới; nó nằm ở giai đoạn **bảo trì**: sửa lỗi phát sinh, cập nhật thư viện, đào tạo kỹ sư mới, và bổ sung tính năng theo yêu cầu kinh doanh.

Khả năng bảo trì dựa trên 3 nguyên tắc nền tảng:

### 1. Dễ vận hành (operability)
Một hệ thống có khả năng vận hành tốt khi đội ngũ SRE có thể dễ dàng nắm bắt sức khỏe hệ thống, triển khai an toàn và khôi phục nhanh khi có biến cố. Điều này đòi hỏi:
- Cung cấp đầy đủ chỉ số đo đạc (metrics), nhật ký (logs) và dấu vết phân tán (distributed tracing).
- Có hành vi mặc định an toàn và khả năng tự phục hồi rõ ràng.
- Hạn chế tối đa các tài liệu hướng dẫn chạy tay (manual runbooks) để chuyển sang tự động hóa khai báo.

<NfrOperability />

### 2. Đơn giản: bớt phức tạp thừa (accidental complexity)
Độ phức tạp chính là kẻ thù số một của bảo trì phần mềm. Nó dẫn đến các phụ thuộc ngầm, gắn kết chặt chẽ (tight coupling) và khiến việc sửa đổi trở nên rủi ro.

Kỹ sư chia độ phức tạp làm hai loại:
- **Độ phức tạp bản chất (Essential Complexity)**: Độ khó bắt buộc của chính bài toán nghiệp vụ (ví dụ: công thức tính thuế phức tạp hoặc khớp lệnh sàn chứng khoán).
- **Độ phức tạp ngẫu nhiên (Accidental Complexity)**: Độ phức tạp tự chuốc lấy do quyết định cài đặt vụng về, trừu tượng hóa cẩu thả hoặc lạm dụng công nghệ quá mức cần thiết.

Vũ khí mạnh nhất để chống lại độ phức tạp ngẫu nhiên là **những tầng trừu tượng sạch sẽ (clean abstractions)**. Một tầng trừu tượng tốt giấu đi hàng ngàn chi tiết kỹ thuật phức tạp bên dưới một giao diện trực quan và dễ hiểu (tương tự cách LSM-tree hay B-tree ẩn giấu các sector đĩa thô đằng sau một API key-value đơn giản).

<NfrAbstraction />

### 3. Dễ thay đổi (evolvability)
Yêu cầu nghiệp vụ luôn thay đổi theo thời gian. Một hệ thống xây dựng trên những giả định cứng nhắc sẽ rất khó thích nghi. Khả năng tiến hóa đồng nghĩa với việc giữ cho các module có tính liên kết lỏng (loose coupling), giao ước API rõ ràng và cơ chế tuần tự hóa dữ liệu hỗ trợ tương thích ngược/xuôi (như Protocol Buffers hay Avro) để từng thành phần có thể nâng cấp độc lập.

<NfrCompat />

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Operability (khả năng vận hành)**: hệ thống dễ đến đâu với người vận hành nó: theo dõi, triển khai, xử lý sự cố.
- **Telemetry (metrics, logs, traces)**: dữ liệu hệ thống tự báo cáo về mình: các con số theo thời gian, dòng ghi lại sự kiện, và đường đi của một request qua các service.
- **Runbook**: tài liệu hướng dẫn từng bước cho người vận hành, ví dụ "nếu ổ đĩa đầy thì làm X".
- **Essential vs. accidental complexity**: độ phức tạp cốt lõi đến từ chính bài toán. Độ phức tạp ngẫu nhiên đến từ cách ta chọn xây giải pháp.
- **Abstraction (trừu tượng hóa)**: một giao diện đơn giản che đi chi tiết rối rắm, như API key-value che đi cách byte nằm trên đĩa.
- **B-tree / LSM-tree**: hai cách phổ biến để database sắp xếp dữ liệu trên đĩa sao cho tra cứu vẫn nhanh. Mỗi thứ đều đủ sâu để thành một chủ đề riêng.
- **Loose coupling (liên kết lỏng)**: các phần phụ thuộc vào nhau ít nhất có thể, để sửa một phần không làm vỡ phần khác.
- **Backward / forward compatibility**: backward: code mới đọc được dữ liệu cũ. Forward: code cũ vẫn đọc được dữ liệu do code mới ghi ra.
- **Protocol Buffers / Avro**: các định dạng mã hóa dữ liệu để gửi hoặc lưu, thiết kế để cấu trúc dữ liệu (schema) đổi được an toàn theo thời gian.

</Concepts>

## Điểm cốt lõi cần nhớ

- **Đừng tin vào số trung bình**: Tuyệt đối không đánh giá hiệu năng hệ thống bằng độ trễ trung bình số học. Luôn soi xét các phân vị (**p50, p95, p99, p99.9**) để thấy đúng trải nghiệm của người dùng thực tế.
- **Hiệu ứng khuếch đại độ trễ đuôi là có thật**: Khi một request phải gọi song song 100 microservices, xác suất chậm 1% (p99) của từng máy chủ sẽ thổi bùng thành **63.4% khả năng** người dùng cuối bị đơ máy.
- **Dữ liệu lệch pha làm vỡ kiến trúc đồng nhất**: Một bài đăng của người nổi tiếng có thể gây ra hàng triệu lệnh ghi. Các hệ thống lớn luôn dùng kiến trúc Hybrid để phân luồng tải hợp lý.
- **Độ tin cậy là sống chung với lỗi**: Chấp nhận rằng phần cứng sẽ hỏng và con người sẽ thao tác nhầm. Thiết kế hệ thống với cơ chế canary release, tự động rollback và khả năng tự chữa lành.
- **Chiến đấu với độ phức tạp ngẫu nhiên**: Tuổi thọ của một hệ thống phần mềm phụ thuộc vào những tầng trừu tượng sạch sẽ giúp kỹ sư tương lai tự tin thay đổi mà không sợ làm sập hệ thống.
