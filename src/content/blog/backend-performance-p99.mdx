### The hook: one log line, 30 ms

In August 2026 SoundCloud engineers wrote up a small Python service on their ad-serving path. For each listening session it answers one question: play an ad pod, or not. Its p99 sat at about 48 ms, and "it never dipped below 40ms at any point, at any volume". A validation check logged a structured warning and bumped four metrics on every request from callers that send no "posteriors" by design. For those fixed-policy callers, that was nearly all the traffic.

The fix was one line: the guard went from `if missing_actions:` to `if missing_actions and request.posteriors:`. The p99 fell to about 18 ms. What I like is how honest they are about getting there. The team's first hypothesis was string formatting, and they write "We never isolated it with a benchmark, and we should be honest about that". The cost was the synchronous write of the log line, inside the request. Their summary: "the best hour of the old service was worse than the worst hour of the new one".

<BeP11LogLine />

Your FastAPI service probably has a line like that, and nothing in code review will say which one. It has a second weakness too: nothing says "no" when work arrives faster than it can be done. This post is about the single-service half of latency: measure the tail, profile before you rewrite, bound what you wait for, and refuse early. Why a whole *fleet* of services turns timeouts and retries into outages is a different problem, and the [distributed systems post](/blog/trouble-with-distributed-systems-networks-clocks-fencing/) owns it. Why averages hide the tail is explained in the [first post on reliability](/blog/reliable-scalable-maintainable-data-systems/); here I only use p50, p95 and p99 as numbers we read off real runs.

All numbers below come from one laptop (Apple M2, macOS 26.4.1, Python 3.13) that was also running other things. Run them again and yours will differ. Where a number is noisy, I say so.

## 1. Measure the tail

Start with a service that looks fine. `p11_upstream.py` stands in for evidence-lab, the second service from the [observability post](/blog/backend-observability/). It is quick almost always, and one call in 40 is slow (a garbage-collection pause, a cold cache, a noisy neighbour: pick your cause). `demo/p11_upstream.py`:

```python
@app.get("/analyze/{case_id}")
async def analyze(case_id: str) -> dict:
    n = next(calls)
    # A GC pause, a cold cache, a noisy neighbour: 1 call in 40 takes 0.8 s.
    await asyncio.sleep(0.8 if n % 40 == 0 else 0.02)
    return {"case_id": case_id, "score": 0.87}
```

clue.api's report route calls it. The client is an `httpx.AsyncClient`, and note what is missing from the line that creates it (`demo/p11_naive.py`):

```python
lab = httpx.AsyncClient(base_url=LAB)  # no timeout= argument: httpx's default applies
```

```python
@app.get("/cases/{case_id}/report")
async def report(case_id: str) -> dict:
    analysis = (await lab.get(f"/analyze/{case_id}")).json()
    return {"case_id": case_id, "analysis": analysis}
```

To get percentiles you need many requests, not one `curl`. `demo/p11_measure.py` fires N requests with C in flight and sorts the results. The only maths is the nearest-rank rule: p99 is the smallest value that 99% of the samples sit at or below.

```python
def pct(sorted_ms: list[float], p: float) -> float:
    """Nearest-rank percentile: the smallest value with p% of samples at or below."""
    return sorted_ms[max(0, math.ceil(p / 100 * len(sorted_ms)) - 1)]
```

<BeP11Percentiles />

Why p99 and not p95? Because of simple counting. Ten of the 400 requests (one in 40, 2.5%) landed on a slow call. The slowest 1% of 400 is 4 requests, and all four are slow calls. If the slow rate were under 1%, p99 would look healthy and the tail would still exist at p99.9.

<BeP11OneInForty />

Read p99 as a rate. "Our p99 is 817 ms" means one user in a hundred waits that long, and users who make ten requests per page meet that user often.

<Concepts>
- **Percentile (p50, p95, p99)**: sort all the response times; p99 is the value that 99% of them are at or below.
- **Tail latency**: the slowest few percent of requests. It is usually caused by something rare, not by the typical path.
- **In flight**: requests the server has accepted and not yet answered.
</Concepts>

## 2. One blocked loop slows every route

A different tail comes from inside the service. In an `async def` endpoint, the event loop runs everything on one thread, and it only switches between requests when your code hits an `await`. Code that never awaits keeps the thread. The [async post](/blog/backend-async-concurrency-workers/) explains this in depth; here is what it costs in percentiles.

`demo/p11_hotspot.py` has a route that scores a case by counting distinct clues, and a `/health` route that does nothing. The scoring is plain Python, with no `await` in it:

```python
@app.get("/cases/{case_id}/score")
async def case_score(case_id: str) -> dict:
    evidence = [f"clue-{i % 2500}" for i in range(10000)]
    return {"case_id": case_id, "distinct_clues": score(evidence)}
```

<BeP11Blocked />

Run four `/score` requests at once and probe `/health` while they are in flight. First alone, then under that load:

Its median is still 1 ms, so a dashboard of averages or medians shows green. Only the tail shows that it waited behind /score.">

`/score` itself went from a median of 65 ms alone to 267 ms with four at once, because the four take turns on the one thread. The blocked loop makes the *neighbours* slow, which is why the slow route is not always the one users complain about. The trap with AI code is that it will happily put a blocking call (`requests.get`, `time.sleep`, a big loop) inside `async def`, and the demo passes because nobody tested two requests together.

<Concepts>
- **Event loop**: the single thread that runs all `async def` code, switching between requests only at an `await`.
- **Blocking call**: code that holds the thread without awaiting: CPU work, `time.sleep`, a synchronous HTTP client.
</Concepts>

## 3. Profile before you rewrite

Now that `/score` is slow, where do you look? The instinct is to read the code and guess: maybe the list comprehension, maybe the JSON. Do not guess, and do not start with a rewrite: SoundCloud's team guessed string formatting first, and by their own account never confirmed it. One question decides which tool to use.

<BeP11WhereFirst />

Here the CPU is busy, so a profiler fits. I wanted `py-spy` first: it attaches to a running process from outside and costs nothing to the service. On macOS it refuses to start without root:

`pyinstrument` is a sampling profiler you start and stop in your own code, so it works anywhere Python does. The middleware in `demo/p11_hotspot.py` turns it on for one request when the URL has `?profile=1`, and returns the report instead of the response:

```python
@app.middleware("http")
async def profile_on_request(request: Request, call_next):
    if request.query_params.get("profile") != "1":
        return await call_next(request)
    profiler = Profiler(async_mode="enabled")
    profiler.start()
    await call_next(request)
    profiler.stop()
    text = profiler.output_text(
        unicode=False, color=False, processor_options={"hide_regex": r".*site-packages.*"}
    )
    return PlainTextResponse(text)
```

`async_mode="enabled"` makes it follow the request across `await`s. The `hide_regex` option folds framework frames, so the report shows our code. Ask for the profile of one slow request:

The report answers with a function and a line: `dedupe`, `p11_hotspot.py:29`. Not the JSON, not the list comprehension. Here is the function:

```python
def dedupe(items: list[str]) -> list[str]:
    seen: list[str] = []
    for item in items:
        if item not in seen:
            seen.append(item)
    return seen
```

`item not in seen` scans a list, so each lookup is a walk. With 2,500 distinct clues the loop does millions of comparisons. Python's `dict` keeps insertion order and finds a key in one step, so `dict.fromkeys(items)` removes duplicates in one pass. Rather than editing the file, `demo/p11_hotfix.py` swaps the function, the way the observability post swapped `_trace`:

```python
p11_hotspot.dedupe = lambda items: list(dict.fromkeys(items))  # one pass, O(n)
app = p11_hotspot.app
```

Profiling first paid twice. It found a cause nobody would have guessed from reading the route, and it fixed an unrelated route too. Had I "optimised" the response model or moved to a thread pool, I would have spent a day and saved nothing.

<Callout type="warning" title="The AI habit to break">
Ask an assistant "make this endpoint faster" and you usually get a rewrite: caching, `asyncio.gather`, a different JSON library. All plausible, none measured. Ask for the profile first, paste the report, and only then ask for a change to the function it names.
</Callout>

<Concepts>
- **Profiler**: a tool that records where a program spends its time, by function and line.
- **Sampling profiler**: looks at the call stack many times a second instead of tracing every call, so it is cheap enough to leave on for one request.
- **Hot spot**: the one function or loop where most of the time goes.
</Concepts>

## 4. Put a deadline on every outbound call

Back to the slow dependency from section 1. With no deadline in the code, the answer to "how long will clue.api wait for evidence-lab?" is whatever the library default is. `httpx` does have one:

<TerminalOutput command="python -c &quot;import httpx; print(httpx.AsyncClient().timeout)&quot;" label="Python 3.13 · httpx 0.28.1 · captured Nov 2026" caption="httpx waits up to 5 seconds, per phase. That is far above a user's patience, and some other clients (requests, for one) wait forever unless you pass a timeout.">
```text
Timeout(timeout=5.0)
```
</TerminalOutput>

Five seconds is a choice somebody else made. Make your own, from what the route is for. The report is worth waiting a quarter of a second for. After that the caller is better served by a clear failure it can retry. `demo/p11_timeout.py`:

```python
lab = httpx.AsyncClient(base_url=LAB, timeout=httpx.Timeout(0.25))
```

```python
@app.get("/cases/{case_id}/report")
async def report(case_id: str) -> dict:
    try:
        analysis = (await lab.get(f"/analyze/{case_id}")).json()
    except httpx.TimeoutException:
        raise HTTPException(status_code=504, detail="evidence-lab: no answer in 0.25 s")
    return {"case_id": case_id, "analysis": analysis}
```

`httpx.Timeout(0.25)` sets connect, read, write and pool waits to 0.25 s each. `httpx.TimeoutException` is the common parent of all four, so one `except` catches the lot. The route answers **504 Gateway Timeout**, the status that means "I asked someone else and they did not answer in time".

Without it, every slow call holds a connection, a task and memory for as long as it lasts.

<Concepts>
- **Timeout**: the longest you will wait for something before giving up.
- **504 Gateway Timeout**: the status for "a service I depend on did not answer in time".
- **Deadline**: the point in time by which the whole request must be done; a timeout is a deadline for one step.
</Concepts>

## 5. Say no early: backpressure

Timeouts bound one call. Bounding the service as a whole needs a different tool. Every service has something scarce: database connections, CPU, a worker pool. `demo/p11_shed.py` models it as four slots, each job holding a slot for 50 ms. That is 4 / 0.05 = 80 jobs per second at most. Send 40 clients at it with no limit, and everybody queues for the slots:

<TerminalOutput command="MAX_IN_FLIGHT=1000 uvicorn p11_shed:app, then p11_measure.py ... /cases/C-1/report 400 40" label="Python 3.13 · FastAPI 0.165.0 · uvicorn 0.54.0 · Apple M2 · captured Nov 2026" caption="Every request succeeds, and every request takes half a second, for work that needs 50 ms. Forty users on four slots: ten per slot, each waiting for nine others.">
```text
/cases/C-1/report  n=400 in-flight=40  wall=5.4s  statuses={200: 400}
  200 only: mean=509ms  p50=526ms  p95=554ms  p99=562ms  max=574ms
```
</TerminalOutput>

Nothing here returns an error, which is why nothing alerts. It is just slow, and the slowness grows with the queue. The fix is a gate: allow a bounded number of requests inside, and answer the rest immediately with **503 Service Unavailable** and a `Retry-After` header that tells a well-behaved client when to come back.

```python
MAX_IN_FLIGHT = int(os.environ.get("MAX_IN_FLIGHT", "8"))
slots = asyncio.Semaphore(4)  # the scarce thing: 4 jobs can run at once
in_flight = 0
app = FastAPI(title="clue.api", version="0.11.3")
```

```python
@app.get("/cases/{case_id}/report")
async def report(case_id: str):
    global in_flight
    if in_flight >= MAX_IN_FLIGHT:
        return JSONResponse(
            status_code=503,
            headers={"Retry-After": "1"},
            content={"detail": "busy, retry in 1 s"},
        )
    in_flight += 1
    try:
        async with slots:
            await asyncio.sleep(0.05)  # the work: 50 ms of a slot
            return {"case_id": case_id, "report": "ready"}
    finally:
        in_flight -= 1
```

`asyncio.Semaphore(4)` is the scarce resource. `in_flight` counts requests inside, running or waiting. The check and the increment have no `await` between them, so on one event loop no two requests can both pass at 7. Eight is four running plus four waiting; a longer queue only adds delay.

<BeP11ShedCompare />

The median fell from 526 ms to 105 ms. This only works if clients cooperate. A client that retries instantly turns your 503 into more load, so say how long to wait in `Retry-After`, and have callers add jitter (a random delay) to their retries.

<Callout type="note" title="Where the limit really belongs">
This gate lives in one process. Behind a load balancer with several workers, each worker has its own counter, so the real limit is eight times the number of workers. In production the same idea is usually set at the edge (a reverse proxy, an API gateway) and again at the scarce resource itself, such as a database connection pool.
</Callout>

<Concepts>
- **Backpressure**: a signal from an overloaded part of the system telling upstream parts to slow down or stop sending.
- **Load shedding**: refusing some work on purpose so the work you accept still finishes quickly.
- **`Retry-After`**: a response header saying how many seconds a client should wait before trying again.
- **Semaphore**: a counter of free slots; `async with` takes one and gives it back.
</Concepts>

## 6. Load test it with locust

Everything so far used a driver I wrote. For a real test you want users who behave like users: they wait between clicks, there are many of them, they arrive gradually. `locust` does that. A user is a Python class:

```python
class Detective(HttpUser):
    wait_time = between(0.05, 0.15)  # think time between two requests of one user

    @task
    def report(self) -> None:
        self.client.get("/cases/C-1/report", name="/cases/{id}/report")
```

`wait_time` is the pause between one user's requests, and `name=` groups URLs with ids under one row in the report. Run it headless against the version with no gate, ramping 2 new users per second up to 40. `uv run --with locust` fetches it for this run only:

A checklist for the next AI-written service, one line each:

| It wrote | Ask | Fix in this post |

### Mở đầu: một dòng log, 30 ms

Tháng 8/2026, các kỹ sư SoundCloud kể lại chuyện về một service Python nhỏ nằm trên đường phục vụ quảng cáo. Với mỗi phiên nghe, nó trả lời một câu hỏi: phát một cụm quảng cáo hay không. P99 của nó nằm ở khoảng 48 ms, và "it never dipped below 40ms at any point, at any volume" (chưa bao giờ xuống dưới 40 ms, ở bất kỳ lưu lượng nào). Một đoạn kiểm tra ghi một warning có cấu trúc và tăng bốn metric cho mọi request từ những caller vốn không gửi "posteriors" theo thiết kế. Với các caller dùng chính sách cố định, đó là gần như toàn bộ traffic.

Cách sửa chỉ một dòng: điều kiện đi từ `if missing_actions:` thành `if missing_actions and request.posteriors:`. P99 rơi xuống còn khoảng 18 ms. Điều mình thích là họ kể thật về đoạn đường đi tới đó. Giả thuyết đầu của đội là format chuỗi, và họ viết "We never isolated it with a benchmark, and we should be honest about that" (chúng tôi chưa bao giờ cô lập nó bằng benchmark, và nên thành thật về điều đó). Cái tốn thật là việc ghi dòng log đồng bộ, ngay trong request. Họ tóm tắt: "the best hour of the old service was worse than the worst hour of the new one" (giờ tốt nhất của service cũ còn tệ hơn giờ tệ nhất của service mới).

<BeP11LogLine />

Service FastAPI của bạn rất có thể có một dòng như vậy, và code review sẽ không chỉ ra dòng nào. Nó còn một điểm yếu nữa: không có gì nói "không" khi việc đến nhanh hơn khả năng làm. Bài này nói về nửa "một service" của độ trễ: đo cái đuôi, profile trước khi viết lại, giới hạn thứ mình chờ, và từ chối sớm. Còn chuyện vì sao cả một *đội* service khiến timeout và retry thành sự cố thì là bài toán khác, mình để [bài hệ thống phân tán](/blog/trouble-with-distributed-systems-networks-clocks-fencing/) lo. Vì sao trung bình che mất cái đuôi thì mình đã giải thích trong [bài đầu về độ tin cậy](/blog/reliable-scalable-maintainable-data-systems/); ở đây mình chỉ dùng p50, p95, p99 như những con số đọc ra từ các lần chạy thật.

Mọi con số bên dưới đo trên một laptop (Apple M2, macOS 26.4.1, Python 3.13), lúc máy còn đang chạy việc khác. Bạn chạy lại sẽ ra số khác. Chỗ nào số nhiễu, mình nói rõ.

## 1. Đo cái đuôi

Bắt đầu với một service trông vẫn ổn. `p11_upstream.py` đóng vai evidence-lab, service thứ hai từ [bài observability](/blog/backend-observability/). Nó gần như lúc nào cũng nhanh, và cứ 40 lời gọi có một lời gọi chậm (GC pause, cache nguội, hàng xóm ồn ào: chọn nguyên nhân tùy bạn). `demo/p11_upstream.py`:

```python
@app.get("/analyze/{case_id}")
async def analyze(case_id: str) -> dict:
    n = next(calls)
    # A GC pause, a cold cache, a noisy neighbour: 1 call in 40 takes 0.8 s.
    await asyncio.sleep(0.8 if n % 40 == 0 else 0.02)
    return {"case_id": case_id, "score": 0.87}
```

Route report của clue.api gọi sang nó. Client là một `httpx.AsyncClient`, và để ý dòng tạo nó thiếu cái gì (`demo/p11_naive.py`):

```python
lab = httpx.AsyncClient(base_url=LAB)  # no timeout= argument: httpx's default applies
```

```python
@app.get("/cases/{case_id}/report")
async def report(case_id: str) -> dict:
    analysis = (await lab.get(f"/analyze/{case_id}")).json()
    return {"case_id": case_id, "analysis": analysis}
```

Muốn có percentile thì cần nhiều request, không phải một lần `curl`. `demo/p11_measure.py` bắn N request với C request cùng lúc rồi sắp xếp kết quả. Phép toán duy nhất là quy tắc nearest-rank: p99 là giá trị nhỏ nhất mà 99% mẫu nằm ở hoặc dưới nó.

```python
def pct(sorted_ms: list[float], p: float) -> float:
    """Nearest-rank percentile: the smallest value with p% of samples at or below."""
    return sorted_ms[max(0, math.ceil(p / 100 * len(sorted_ms)) - 1)]
```

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">
- **Percentile (p50, p95, p99)**: sắp xếp mọi thời gian phản hồi; p99 là giá trị mà 99% số đó nằm ở hoặc dưới nó.

- **In flight (đang bay)**: request server đã nhận và chưa trả lời.
</Concepts>

## 2. Một loop bị chặn làm chậm mọi route

Một kiểu đuôi khác đến từ bên trong service. Trong endpoint `async def`, event loop chạy mọi thứ trên một thread, và chỉ chuyển qua lại giữa các request khi code gặp một `await`. Code không bao giờ await sẽ giữ luôn thread. [Bài async](/blog/backend-async-concurrency-workers/) giải thích kỹ chuyện này; ở đây là cái giá của nó tính bằng percentile.

`demo/p11_hotspot.py` có một route chấm điểm case bằng cách đếm số manh mối khác nhau, và một route `/health` không làm gì cả. Phần chấm điểm là Python thuần, không có `await` nào:

```python
@app.get("/cases/{case_id}/score")
async def case_score(case_id: str) -> dict:
    evidence = [f"clue-{i % 2500}" for i in range(10000)]
    return {"case_id": case_id, "distinct_clues": score(evidence)}
```

```python
def dedupe(items: list[str]) -> list[str]:
    seen: list[str] = []
    for item in items:
        if item not in seen:
            seen.append(item)
    return seen
```

`item not in seen` quét cả một list, nên mỗi lần tra là một lần đi bộ. p11_hotspot.dedupe = lambda items: list(dict.fromkeys(items))  # one pass, O(n)

Profile trước có lợi hai lần: nó chỉ ra một nguyên nhân mà đọc route thì không ai đoán nổi, và nó sửa luôn cả một route không liên quan. Nếu mình "tối ưu" response model hay chuyển sang thread pool, mình đã mất một ngày mà chẳng được gì.

<Callout type="warning" title="Thói quen AI cần bỏ">
Bảo trợ lý "làm endpoint này nhanh hơn" thì thường nhận về một bản viết lại: cache, `asyncio.gather`, thư viện JSON khác. Cái nào cũng hợp lý, không cái nào được đo. Hãy xin profile trước, dán báo cáo vào, rồi mới nhờ sửa đúng hàm nó chỉ ra.
</Callout>

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">
- **Profiler**: công cụ ghi lại chương trình tốn thời gian ở đâu, theo hàm và theo dòng.
- **Sampling profiler**: nhìn call stack nhiều lần mỗi giây thay vì theo dõi từng lời gọi, nên đủ rẻ để bật cho một request.
- **Hot spot (điểm nóng)**: một hàm hoặc vòng lặp chiếm phần lớn thời gian.
</Concepts>

## 4. Đặt deadline cho mọi lời gọi ra ngoài

Quay lại dependency chậm ở mục 1. Không có deadline trong code thì câu trả lời cho "clue.api sẽ chờ evidence-lab bao lâu?" là giá trị mặc định của thư viện. `httpx` có một giá trị như vậy:

<TerminalOutput command="python -c &quot;import httpx; print(httpx.AsyncClient().timeout)&quot;" label="Python 3.13 · httpx 0.28.1 · captured Nov 2026" caption="httpx chờ tối đa 5 giây, cho mỗi giai đoạn. Con số đó vượt xa sự kiên nhẫn của người dùng, và vài client khác (như requests) chờ mãi mãi nếu bạn không truyền timeout.">
```text

```
</TerminalOutput>

Năm giây là lựa chọn của người khác. Hãy tự chọn, dựa vào mục đích của route. Report đáng để chờ một phần tư giây. Sau đó, người gọi được phục vụ tốt hơn bằng một lỗi rõ ràng mà nó có thể thử lại. `demo/p11_timeout.py`:

```python
lab = httpx.AsyncClient(base_url=LAB, timeout=httpx.Timeout(0.25))
```

```python
@app.get("/cases/{case_id}/report")
async def report(case_id: str) -> dict:
    try:
        analysis = (await lab.get(f"/analyze/{case_id}")).json()
    except httpx.TimeoutException:
        raise HTTPException(status_code=504, detail="evidence-lab: no answer in 0.25 s")
    return {"case_id": case_id, "analysis": analysis}
```

`httpx.Timeout(0.25)` đặt thời gian chờ connect, read, write và pool đều là 0,25 s. `httpx.TimeoutException` là lớp cha chung của cả bốn, nên một `except` bắt hết. Route trả **504 Gateway Timeout**, status có nghĩa "mình hỏi người khác và họ không trả lời kịp".

## 5. Từ chối sớm: backpressure

Timeout giới hạn một lời gọi. Giới hạn cả service cần công cụ khác. Service nào cũng có thứ khan hiếm: connection database, CPU, một worker pool. `demo/p11_shed.py` mô hình hóa nó bằng bốn slot, mỗi job giữ một slot 50 ms. Tức tối đa 4 / 0,05 = 80 job mỗi giây. Cho 40 client dồn vào mà không giới hạn, mọi người xếp hàng chờ slot:

<TerminalOutput command="MAX_IN_FLIGHT=1000 uvicorn p11_shed:app, then p11_measure.py ... /cases/C-1/report 400 40" label="Python 3.13 · FastAPI 0.165.0 · uvicorn 0.54.0 · Apple M2 · captured Nov 2026" caption="Request nào cũng thành công, và request nào cũng mất nửa giây cho việc chỉ cần 50 ms. Bốn mươi người dùng trên bốn slot: mười người mỗi slot, mỗi người chờ chín người khác.">
```text
/cases/C-1/report  n=400 in-flight=40  wall=5.4s  statuses={200: 400}
  200 only: mean=509ms  p50=526ms  p95=554ms  p99=562ms  max=574ms
```
</TerminalOutput>

Không có lỗi nào trả về nên cũng không có gì báo động. Nó chỉ chậm, và độ chậm lớn lên theo hàng đợi. Cách sửa là một cái cổng: cho một số request giới hạn vào trong, trả lời ngay phần còn lại bằng **503 Service Unavailable** kèm header `Retry-After` báo cho client biết khi nào quay lại.

```python
MAX_IN_FLIGHT = int(os.environ.get("MAX_IN_FLIGHT", "8"))
slots = asyncio.Semaphore(4)  # the scarce thing: 4 jobs can run at once
in_flight = 0
app = FastAPI(title="clue.api", version="0.11.3")
```

```python
@app.get("/cases/{case_id}/report")
async def report(case_id: str):
    global in_flight
    if in_flight >= MAX_IN_FLIGHT:
        return JSONResponse(
            status_code=503,
            headers={"Retry-After": "1"},
            content={"detail": "busy, retry in 1 s"},
        )
    in_flight += 1
    try:
        async with slots:
            await asyncio.sleep(0.05)  # the work: 50 ms of a slot
            return {"case_id": case_id, "report": "ready"}
    finally:
        in_flight -= 1
```

`asyncio.Semaphore(4)` là tài nguyên khan hiếm. `in_flight` đếm số request bên trong, đang chạy hay đang chờ. Việc kiểm tra và tăng biến không có `await` ở giữa, nên trên một event loop không có hai request nào cùng qua được khi đếm đang là 7. Tám là bốn đang chạy cộng bốn đang chờ; hàng đợi dài hơn chỉ thêm độ trễ.

<Callout type="note" title="Giới hạn thật sự nên đặt ở đâu">

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">
- **Backpressure (áp lực ngược)**: tín hiệu từ phần đang quá tải bảo các phần phía trước chậm lại hoặc ngừng gửi.
- **Load shedding (từ chối bớt tải)**: cố ý từ chối một phần việc để phần việc nhận vào vẫn xong nhanh.
- **`Retry-After`**: header phản hồi nói client nên chờ bao nhiêu giây trước khi thử lại.
- **Semaphore**: bộ đếm slot trống; `async with` lấy một slot và trả lại.
</Concepts>

## 6. Load test bằng locust

Đến giờ mọi thứ dùng driver do mình tự viết. Một bài test thật cần những người dùng cư xử như người dùng: họ chờ giữa các lần bấm, có rất nhiều người, và họ đến dần dần. `locust` làm được việc đó. Một người dùng là một class Python:

```python
class Detective(HttpUser):
    wait_time = between(0.05, 0.15)  # think time between two requests of one user

    @task
    def report(self) -> None:
        self.client.get("/cases/C-1/report", name="/cases/{id}/report")
```

`wait_time` là khoảng nghỉ giữa các request của một người dùng, và `name=` gom các URL có id vào một dòng trong báo cáo. Chạy headless vào bản không có cổng, tăng 2 người dùng mới mỗi giây đến 40. `uv run --with locust` tải nó chỉ cho lần chạy này:
