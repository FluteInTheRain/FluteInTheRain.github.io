### A rocket, a number that did not fit

On 4 June 1996 the first Ariane 5 rocket left the pad in French Guiana. It veered off course and was destroyed 37 seconds after launch. The inquiry traced it to one line of guidance software: a 64-bit floating-point number was converted to a 16-bit signed integer, the value was too big for 16 bits, and the conversion overflowed. The flight computer then read an error message as if it were flight data.

You will probably never write rocket software. But the same bug is one innocent line away in any language where a number has a fixed size. Go is such a language, and it will not warn you. This post covers the basic building blocks you need before anything else in Go makes sense:

1. **Variables and zero values**: how to declare things, and why Go has no "undefined".
2. **Types, constants and conversions**: why `int32 + int64` does not compile, and what happens when a number overflows.
3. **Functions**: multiple return values, and named results (use them rarely).
4. **Pointers, `defer` and the `:=` trap**: what "everything is passed by value" really means, when to pass a pointer, and the first bug most newcomers hit.

<Callout type="note" title="TL;DR">
Go gives every variable a type and a zero value, converts between number types only when you ask, and wraps integers around silently when they overflow. Functions can return several values. Every argument is a copy: pass a pointer when the function must change the caller's variable. `defer` runs a call when the function ends, in reverse order, with its arguments fixed at the `defer` line. And `:=` inside a block creates a new variable, which can hide the one you meant to set.
</Callout>

If you have not run a Go program yet, start with [Go basics](/blog/go-first-program-modules-packages/). This post assumes you can `go run` a file.

### Coming from Java, Python or JavaScript

| Topic | Java | Python | JavaScript | Go |
| :--- | :--- | :--- | :--- | :--- |
| Declare a variable | `int x = 1;` | `x = 1` | `let x = 1` | `x := 1` or `var x int` |
| Declared, no value given | field: `0`/`null`; local: compile error | name does not exist yet | `undefined` | the type's zero value |
| Size of `int` | always 32 bits | unlimited | not an int, a 64-bit float | 64 bits on a 64-bit machine |
| Mixing number types | widens automatically | automatic | automatic | never, you convert |
| Integer overflow | wraps silently | the number just grows | precision lost past 2^53 | wraps silently |
| Several return values | return an object | return a tuple | return an array or object | built in |
| Passing arguments | copy (objects: copy of the reference) | reference to the object | same as Python | always a copy |
| Cleanup at exit | `try`/`finally` | `with` | `try`/`finally` | `defer` |

<Concepts>

- **Zero value**: the value a variable has when you declare it without giving one. Each type has its own: `0`, `""`, `false`, `nil`.
- **Compile error**: a mistake the compiler catches before the program runs. Go reports many of them that other languages let through.
- **Pass by value**: handing a function a copy of the argument, so the function cannot change your original.

</Concepts>

## Variables and zero values

A variable is a named box that holds one value of one type. Go has two ways to make one. `var count int` says "a box called `count` that holds an `int`". `city := "Hanoi"` says "make a box called `city` and put this value in it", and Go works out the type itself. The short form `:=` is what you will write most of the time, but it only works inside functions.

The part that feels new is what is in the box when you do not say. In Go it is always the **zero value** of the type, so a variable is never "undefined" and never holds leftover garbage:

```go
var count int
var name string
var ok bool
var price float64
var p *int      // a pointer, covered below
var items []string
var o Order     // a struct with ID int and Total float64

city := "Hanoi"      // := declares and assigns
var temp = 31.5      // type worked out from the value
a, b := 1, "two"     // several at once
a, c := 3, "new"     // fine: c is new, so := is allowed
```

<TerminalOutput command="go run ./vars" label="Apple M2 · Go 1.27" caption="Every variable starts at its zero value. %T prints the type Go picked.">
```text
int=0 string="" bool=false float64=0
pointer=<nil> slice=[] (nil? true) struct={ID:0 Total:0}
Hanoi string, 31.5 float64
3 two new
```
</TerminalOutput>

| Type | Zero value |
| :--- | :--- |
| `int`, `float64` and the other numbers | `0` |
| `string` | `""` (empty, never `nil`) |
| `bool` | `false` |
| pointer (`*T`) | `nil` |
| slice, map | `nil` (see [Go collections](/blog/go-slices-maps-strings/)) |
| struct | each field at its own zero value |

Zero values are why Go code often skips setup code. A struct you just declared is usable, and a counter starts at 0 without you writing `= 0`.

Go is also strict about leftovers. A variable you declare and never use is a compile error, and so is an unused import. Efficient Go points out that this surprises newcomers but keeps code clean. If you really want to ignore a value, say so with the blank name `_`.

<TerminalOutput command="go build ./unused" label="Apple M2 · Go 1.27" caption="An unused variable stops the build. The compiler names the variable.">
```text
# demo/unused
unused/main.go:4:2: declared and not used: count
```
</TerminalOutput>

Two more rules about `:=`. It needs at least one new name on the left, which is why `a, c := 3, "new"` above is legal even though `a` already exists. And it cannot be used outside a function; at the top of a file you must write `var`.

<Concepts>

- **`var` and `:=`**: `var x T` declares a variable of type `T`. `x := v` declares and assigns in one step and infers the type, but only inside functions.
- **`nil`**: Go's name for "points at nothing". It is the zero value of pointers, slices, maps and a few other types.
- **Blank identifier `_`**: a write-only name. Assigning to it tells the compiler you are ignoring that value on purpose.

</Concepts>

## Types, constants and conversions

Go's number types have fixed sizes, and the name says the size: `int8`, `int16`, `int32`, `int64` and their unsigned twins `uint8` to `uint64`. Plain `int` and `uint` are the exceptions: they match the machine, so 64 bits on a 64-bit computer. Use `int` unless you have a reason to pick a size. Floating-point numbers are `float32` and `float64` (use `float64`). A `byte` is another name for `uint8`.

The rule that surprises people: **Go never converts between number types for you.** Adding an `int32` to an `int64` is a compile error, even though nothing would be lost.

<TerminalOutput command="go build ./bad" label="Apple M2 · Go 1.27" caption="Mixing int32 and int64 in one expression does not compile.">
```text
# demo/bad
bad/main.go:6:11: invalid operation: small + big (mismatched types int32 and int64)
```
</TerminalOutput>

You convert on purpose, by writing the target type like a function: `int64(small) + big`. This is also where data gets lost, so the conversion is where you should look when you review code. Converting a float to an int cuts off the decimals, it does not round.

```go
total := int64(small) + big
f := 9.99
fmt.Println(int(f)) // 9
```

### Constants and iota

A `const` is a name for a value fixed at compile time. Constants without a declared type are **untyped**, and the spec says numeric constants are exact values of arbitrary precision that do not overflow. That is why `const half = 0.5` can be multiplied with a `float64` or added to an integer expression without a conversion.

For a numbered list of related constants, Go has `iota`: inside one `const ( ... )` block it counts 0, 1, 2 and so on, one step per line.

```go
type Weekday int

const (
	Sunday Weekday = iota // 0
	Monday                // 1
	Tuesday               // 2
)

const (
	_  = iota             // skip 0
	KB = 1 << (10 * iota) // 1024
	MB                    // 1048576
	GB                    // 1073741824
)
```

This is Go's version of an enum. There is no `enum` keyword, only a named type plus constants.

### The octal trap

Here is a bug that compiles, runs and gives a plausible answer. A number written with a leading zero is **octal** (base 8), so `010` is 8.

```go
fmt.Println(100 + 010)  // 108, not 110
fmt.Println(100 + 0o10) // 108, but now it says "octal" out loud
fmt.Printf("755 as octal digits: %o\n", 755)
```

The same mistake hides in file permissions. The Unix permission `rwxr-xr-x` is written `0o755`, and the decimal number `755` is a completely different set of permission bits:

<TerminalOutput command="go run ./types" label="Apple M2 · Go 1.27" caption="0o755 is the permission you meant. Decimal 755 is something else entirely.">
```text
1000007
9
0 1 2 1024 1048576 1073741824
108
108
755 as octal digits: 1363
-rwxr-xr-x --wxrw--wx
1.5 3 3.5
```
</TerminalOutput>

Write octal with the `0o` prefix, as 100 Go Mistakes recommends, so the next reader does not have to guess. Go also accepts `0b` for binary, `0x` for hex and `_` as a digit separator, so `1_000_000` is a million.

The last line of that output shows one more thing. `7/2` is `3` because both sides are integers, and `7/2.0` is `3.5`. The type of the operands decides the kind of division.

<Concepts>

- **Untyped constant**: a constant written as a bare number like `0.5` or `1000`. It takes a type only where it is used, so it fits into whichever number type you combine it with.
- **`iota`**: a counter that starts at 0 in each `const` block and goes up by one per line. Used to build enum-like lists.
- **Conversion**: writing `T(value)` to turn a value into type `T`. Go requires it between different number types.
- **Octal**: base 8. In Go a literal starting with `0` is octal; `0o` makes that explicit.

</Concepts>

## Overflow and floating point

An integer has a fixed number of bits, so it has a largest value. Add one to it and the number **wraps around** to the smallest value. Go does this silently at run time: no panic, no error. (If the compiler can see the overflow in a constant, it refuses to build, as in `var c int32 = math.MaxInt32 + 1`.)

```go
var counter int32 = math.MaxInt32
counter++

var small uint8 = 255
small++

var big int64 = 40000
fmt.Println(int16(big))
```

<TerminalOutput command="go run ./overflow" label="Apple M2 · Go 1.27" caption="Three silent wrap-arounds. The last one is the Ariane 5 kind of bug: a conversion to a narrower type.">
```text
int32 after max+1: -2147483648
uint8 after 255+1: 0
int16(40000): -25536
```
</TerminalOutput>

<TerminalOutput command="go build ./constovf" label="Apple M2 · Go 1.27" caption="When the overflow is visible at compile time, Go refuses to build.">
```text
# demo/constovf
constovf/main.go:9:22: cannot use math.MaxInt32 + 1 (untyped int constant 2147483648) as int32 value in variable declaration (overflows)
```
</TerminalOutput>

That last `int16(40000)` is the shape of the Ariane 5 failure: a wide number squeezed into a narrower slot. The value that overflowed was the rocket's horizontal bias, which on Ariane 5 grew larger than the Ariane 4 design had expected. Go would have let the same conversion through without a sound.

Most of the time you do not need to worry. A request counter in an `int` will not reach 2^63. Check for overflow when you use small integer types, handle very large numbers, or convert from a wide type to a narrow one. The check is a plain comparison before the operation: for an addition, `a > math.MaxInt-b` tells you the sum would overflow.

### Floats are approximations

`float64` stores numbers in binary, and most decimal fractions such as `0.1` have no exact binary form. The result is tiny errors. Here is a twist worth seeing once: the same expression gives two different answers depending on whether the numbers are constants or variables.

```go
fmt.Println("0.1+0.2 == 0.3?", 0.1+0.2 == 0.3)  // constants
a, b := 0.1, 0.2
fmt.Println(a+b, a+b == 0.3, math.Abs(a+b-0.3) < 1e-9)  // variables
```

<TerminalOutput command="go run ./overflow" label="Apple M2 · Go 1.27" caption="Constants are computed exactly by the compiler, so the first line is true. Variables use float64, so they are off by a hair.">
```text
0.1+0.2 == 0.3? true
0.30000000000000004 false true
+Inf -Inf NaN
false true
```
</TerminalOutput>

So never compare floats with `==`. Compare the difference with a small tolerance, as the third value does. Dividing a float by zero does not panic, it gives `+Inf`, `-Inf` or `NaN` ("not a number"), and `NaN` is not even equal to itself, so use `math.IsNaN`. For money, store whole cents in an integer instead of dollars in a float.

<Concepts>

- **Overflow (wrap-around)**: a result too big for the type. Go's integers wrap to the other end of their range instead of failing.
- **Floating point**: how computers store fractional numbers using a fixed number of bits. The result is close to, not exactly, the true value.
- **`NaN` and `Inf`**: special float values for "not a number" and "infinity". They come from operations like `0/0` and `1/0`.

</Concepts>

## Functions

A function says its inputs and outputs in the signature: `func divide(a, b int) (int, error)`. Types come after the names, and neighbours of the same type can share one: `a, b int`. A function can return **more than one value**, and Go uses this everywhere. The usual shape is "the result, plus an error", and the caller checks the error right away.

```go
func divide(a, b int) (int, error) {
	if b == 0 {
		return 0, errors.New("divide by zero")
	}
	return a / b, nil
}

q, err := divide(7, 2)
```

There are no exceptions to catch here: an error is just a value you receive. That idea has its own post, [Go errors](/blog/go-errors-defer-panic/).

### Keep the happy path on the left

Because Go makes you check errors at every step, a function can easily turn into a staircase of nested `if`/`else`. The fix is to return early and keep the normal flow in one straight column. Mat Ryer put it as "Align the happy path to the left", and 100 Go Mistakes uses the line to make the same point.

```go
func join(s1, s2 string, max int) (string, error) {
	if s1 == "" {
		return "", errors.New("s1 is empty")
	}
	if s2 == "" {
		return "", errors.New("s2 is empty")
	}
	concat, err := concatenate(s1, s2)
	if err != nil {
		return "", err
	}
	if len(concat) > max {
		return concat[:max], nil
	}
	return concat, nil
}
```

Every `if` that returns needs no `else`. Read down the left edge and you see the success path; the indented lines are the ways it can fail.

### Named results, and when not to use them

You can give the return values names: `func minMax(xs []int) (lo, hi int)`. The names become variables, already set to their zero values, and a bare `return` sends back whatever they hold now. Two good uses: the names document which `int` is which, and they save a line or two in a short function.

The danger is that a named result that you forget to set quietly stays at its zero value. Here the author meant to return the context's error, but returns `err`, a result variable nobody assigned:

```go
func check(ctx context.Context, ok bool) (n int, err error) {
	if !ok {
		return 0, errors.New("invalid")
	}
	if ctx.Err() != nil {
		return 0, err // err is still nil here!
	}
	return 1, nil
}
```

It compiles, because `err` exists (named results are always declared). Without the names it would be a compile error. The fix is to return the real error:

```go
if err := ctx.Err(); err != nil {
	return 0, err
}
```

<TerminalOutput command="go run ./funcs" label="Apple M2 · Go 1.27" caption="The buggy version cancels the context and still reports no error. The fixed one reports context canceled.">
```text
3 <nil>
divide by zero
-2 9
buggy: <nil> true
fixed: context canceled
```
</TerminalOutput>

My rule of thumb, following 100 Go Mistakes: name the results when it makes a signature clearer (`(lat, lng float32, err error)` beats `(float32, float32, error)`), and avoid bare `return` outside very short functions. If you cannot say why the names help, leave them out.

<Concepts>

- **Multiple return values**: a function can hand back several results at once. By convention the last one is an `error`.
- **Happy path**: the sequence of steps when nothing goes wrong. Keeping it unindented makes a function easy to scan.
- **Named result**: a return value with a name, pre-set to its zero value. A bare `return` sends the current values back.

</Concepts>

## Pointers and pass by value

In Go, a function call **copies every argument** into the function's own variables. That is the whole rule, and the Go FAQ states it flatly: a function always gets a copy of the thing passed, as if the value had been assigned to the parameter. If you change the copy, the original does not change.

A pointer is how you let a function change the original. `&x` means "the address of `x`", and `*p` means "the thing `p` points at". Passing `&x` still copies, but what gets copied is the address, so the function reaches your variable through it. Play with the three cases below before reading on.

<GoPassByValueStepper />

Here is the same experiment as a real program. The `%p` verb prints the memory address, so you can see the copy living somewhere else:

```go
func bumpByValue(v int)    { v += 50 }
func bumpByPointer(p *int) { if p != nil { *p += 50 } }
```

<TerminalOutput command="go run ./ptr" label="Apple M2 · Go 1.27" caption="v is a copy at a different address, so x stays 10. The pointer version writes through the address and x becomes 60. Your addresses will differ.">
```text
main: x=10 at 0x4e44bc396020
  inside bumpByValue: v=60 at 0x4e44bc396040
after value: 10
  inside bumpByPointer: p=0x4e44bc396020 *p=60
after pointer: 60
```
</TerminalOutput>

### When to pass a pointer

Default to passing plain values. Reach for `*T` in these cases:

| Pass a pointer when | Why |
| :--- | :--- |
| the function must change the caller's variable | a copy cannot do that |
| the value is large | copying a pointer is cheaper; when unsure how large is large, benchmark |
| the type must not be copied (for example locks from the `sync` package) | a copy would break it, see [Context and locks](/blog/go-context-timeouts-mutexes/) |
| `nil` should mean "no value" | only pointers can be `nil` |

### Pointers are small and safe

A pointer in Go cannot be moved around. Writing `p++` to step to the next memory cell, as you can in C, does not compile. The Go FAQ gives the reason in one word, safety: without pointer arithmetic the language can never produce an illegal address.

<TerminalOutput command="go build ./ptrarith" label="Apple M2 · Go 1.27" caption="There is no p++ on a pointer.">
```text
# demo/ptrarith
ptrarith/main.go:6:2: invalid operation: p++ (non-numeric type *int)
```
</TerminalOutput>

You still can crash by following a pointer that points at nothing. The zero value of a pointer is `nil`, and `*np` on a `nil` pointer panics. So check `p != nil` when a pointer could be absent.

<TerminalOutput command="go run ./ptr" label="Apple M2 · Go 1.27" caption="Following a nil pointer stops the program with a panic.">
```text
panic: runtime error: invalid memory address or nil pointer dereference
[signal SIGSEGV: segmentation violation code=0x2 addr=0x0 pc=0x100c04fdc]
```
</TerminalOutput>

### The same choice for methods

A method can take its receiver (the value before the method name) by value or by pointer, and the rule is the one above. A value receiver works on a copy. A pointer receiver changes the original. Structs and methods get a full post in [Go structs and interfaces](/blog/go-structs-methods-interfaces/); here is only the effect:

```go
func (a Account) AddValue(v float64)    { a.Balance += v }
func (a *Account) AddPointer(v float64) { a.Balance += v }
```

<TerminalOutput command="go run ./ptr" label="Apple M2 · Go 1.27" caption="Starting from 100: the value receiver adds to a copy and loses it. The pointer receiver keeps the 50.">
```text
value receiver: 100.00
pointer receiver: 150.00
```
</TerminalOutput>

Use a pointer receiver if the method changes the receiver or the type holds something that must not be copied. Use a value receiver for small, naturally immutable types such as `time.Time`. If one method of a type needs a pointer, make them all pointer receivers so the type stays consistent.

<Concepts>

- **Pointer**: a variable that holds the memory address of another variable. `&x` takes an address, `*p` follows one.
- **Dereference**: following a pointer to the value it points at, written `*p`.
- **Receiver**: the extra parameter written before a method's name. It decides which type the method belongs to.
- **Panic**: a run-time crash that unwinds the program. A nil dereference causes one.

</Concepts>

## defer

Cleanup is where bugs hide: you open a file, then there are four places to return early, and you must close it in all of them. `defer` solves that. `defer someCall()` does not run the call now. It puts the call on a list, and Go runs the list when the **surrounding function returns**, even through an early return or a panic. Open and `defer Close()` on the next line, and you cannot forget.

The Go blog's article on defer gives the rules in three sentences. Calls are pushed on a list. They run in **last in, first out** order after the function returns. And arguments are evaluated when the `defer` statement runs, not later.

```go
for i := 1; i <= 3; i++ {
	defer fmt.Println("deferred", i)
}
fmt.Println("function body done")
```

<TerminalOutput command="go run ./deferd" label="Apple M2 · Go 1.27" caption="Reverse order: the last defer registered is the first to run.">
```text
function body done
deferred 3
deferred 2
deferred 1
```
</TerminalOutput>

Reverse order is deliberate. Things opened first usually depend on each other in layers, like a connection and then a transaction on it, so they must be closed from the inside out.

### Arguments are fixed at the defer line

This one catches people, and 100 Go Mistakes gives it a whole entry. The arguments of a deferred call are computed immediately, so a later change to the variable does not reach them. A closure behaves differently: it holds a link to the variable and reads it when it finally runs.

```go
x := 10
defer fmt.Println("defer arg captured x =", x)
defer func() { fmt.Println("closure sees x =", x) }()
x = 99
```

The stepper above has a third tab that walks through exactly this. Here is the real output, and a more realistic case, where a status string is reported on the way out:

```go
func broken(fail bool) {
	var status string
	defer notify(status)   // status is "" right now, and that "" is what gets saved
	status = "success"
	if fail {
		status = "error"
	}
}

func fixedClosure(fail bool) {
	var status string
	defer func() { notify(status) }() // reads status when the function ends
	// ... same body
}
```

<TerminalOutput command="go run ./deferd" label="Apple M2 · Go 1.27" caption="The closure sees 99, the plain argument kept 10. In the status example the broken version always reports an empty string.">
```text
closure sees x = 99
defer arg captured x = 10
broken:
  notify("")
fixed:
  notify("error")
```
</TerminalOutput>

The two fixes are the closure above, or passing a pointer (`defer notify(&status)`), because the pointer's address is fixed even when the value it points at changes. The closure is usually simpler.

Two related things have their own home: what happens with `defer` inside a loop, and `panic` with `recover`. Both are in [Go errors](/blog/go-errors-defer-panic/).

<Concepts>

- **`defer`**: schedules a call to run when the current function ends, however it ends.
- **LIFO (last in, first out)**: like a stack of plates: the most recently added is the first taken off.
- **Closure**: a function written inline that can read and change variables from the function around it.

</Concepts>

## Shadowing, the first trap

Now that you know `:=`, here is how it bites. Every `{ ... }` block (an `if`, a `for`, a plain pair of braces) is its own **scope**: names declared inside live only until the closing brace. If you write `x := ...` inside a block, and `x` already exists outside, Go does not set the outer `x`. It makes a brand-new `x` that **shadows** the outer one.

This is the example from 100 Go Mistakes, trimmed to the point. The outer `client` stays `nil`, because `client, err := ...` inside the `if` declared two new variables:

```go
func buggy(tracing bool) *Client {
	var client *Client
	if tracing {
		client, err := newTraced() // new client AND new err, only inside this block
		if err != nil {
			return nil
		}
		fmt.Println("inside block:", client.Name)
	}
	return client // the outer client was never touched
}

func fixed(tracing bool) *Client {
	var client *Client
	var err error
	if tracing {
		client, err = newTraced() // plain =, assigns to the outer variables
	} else {
		client, err = newDefault()
	}
	if err != nil {
		return nil
	}
	return client
}
```

<TerminalOutput command="go run ./shadow" label="Apple M2 · Go 1.27" caption="The block used its own client and printed fine, but the function still returned nil. The fix assigns with = to variables declared once, outside.">
```text
inside block: traced
buggy returns nil? true
fixed returns nil? false
```
</TerminalOutput>

The compiler accepts it because the inner `client` is used (it is printed). The two fixes are: declare the variables first and use plain `=` inside the block, or use a temporary name and assign it out. Reusing a name like `err` in a block is sometimes handy, so there is no blanket ban, but whenever a value "goes missing" after an `if` block, look for a `:=` that quietly made a second variable.

<Concepts>

- **Scope**: the region of code where a name is valid. Each pair of braces opens a new one.
- **Shadowing**: declaring a name in an inner scope that already exists in an outer scope, so the inner one hides the outer one.

</Concepts>

## Two small habits

**`init` functions.** A function named `init` with no arguments runs automatically, before `main`, once per package. Package-level `var` initializers run first, then every `init` in the order the source reads, then `main`. You can have more than one in a file.

```go
var a = func() int { fmt.Println("var"); return 0 }()
func init() { fmt.Println("init 1") }
func init() { fmt.Println("init 2") }
func main() { fmt.Println("main") }
```

<TerminalOutput command="go run ./initd" label="Apple M2 · Go 1.27" caption="Package variables first, then each init in source order, then main.">
```text
var
init 1
init 2
main
```
</TerminalOutput>

The catch is that `init` cannot return an error, and it runs before you control anything, so failing there means panicking or hiding the failure. It also makes the order in which things happen harder to follow. 100 Go Mistakes advises against using it for real setup. Prefer an explicit function you call from `main` and can test. How packages trigger each other's `init` is covered in [Go basics](/blog/go-first-program-modules-packages/).

**Getters and setters.** In Java you would write `getBalance()` and `setBalance()` by reflex. Go does not need them. If a field is exported (starts with a capital letter), people just read `customer.Balance`. Add accessors only when they do something: validate, compute, or guard with a lock. When you do, the getter is named `Balance()`, without a `Get` prefix, and the setter is `SetBalance()`. How structs and exported fields work is in [Go structs and interfaces](/blog/go-structs-methods-interfaces/).

<Concepts>

- **`init` function**: a special function Go calls automatically at startup, before `main`.
- **Exported name**: a name starting with a capital letter, visible to other packages. Lowercase names stay private to the package.

</Concepts>

## Key takeaways

- **Variables never start undefined.** Every type has a zero value, so a freshly declared variable is safe to use, and an unused variable is a compile error.
- **Convert numbers on purpose, and treat every conversion as a risk.** Go never mixes number types silently, but it wraps integers around silently, which is what brought down Ariane 5.
- **Return early and keep the happy path on the left**, and use named results only when they make a signature clearer.
- **Everything is a copy.** Pass a pointer when a function must change your variable, the value is large, or `nil` should mean absent. Otherwise pass the value.
- **`defer` fixes its arguments at the `defer` line**; use a closure to read the latest value, and remember `:=` in an inner block creates a new variable.

### Một quả tên lửa và con số không vừa ô

Ngày 4/6/1996, tên lửa Ariane 5 đầu tiên rời bệ phóng ở Guiana thuộc Pháp. Nó lệch hướng và bị phá hủy sau 37 giây kể từ lúc phóng. Hội đồng điều tra lần ra một dòng trong phần mềm dẫn đường: một số thực 64 bit bị ép sang số nguyên có dấu 16 bit, giá trị quá lớn so với 16 bit nên phép ép kiểu bị tràn. Máy tính bay sau đó đọc thông báo lỗi như thể đó là dữ liệu chuyến bay.

Bạn chắc không viết phần mềm tên lửa. Nhưng lỗi y hệt chỉ cách một dòng vô tội ở bất kỳ ngôn ngữ nào có kiểu số kích thước cố định. Go là một ngôn ngữ như thế, và nó sẽ không cảnh báo gì. Bài này đi qua các viên gạch cơ bản bạn cần trước khi mọi thứ khác trong Go có nghĩa:

1. **Biến và zero value**: khai báo thế nào, và vì sao Go không có "undefined".
2. **Kiểu, hằng số và ép kiểu**: vì sao `int32 + int64` không biên dịch được, và chuyện gì xảy ra khi số bị tràn.
3. **Hàm**: nhiều giá trị trả về, và kết quả có tên (ít khi nên dùng).
4. **Con trỏ, `defer` và bẫy `:=`**: "mọi thứ truyền theo giá trị" thật sự nghĩa là gì, khi nào truyền con trỏ, và lỗi đầu tiên người mới hay dính.

<Callout type="note" title="Tóm tắt nhanh">
Go gán cho mọi biến một kiểu và một zero value, chỉ đổi giữa các kiểu số khi bạn yêu cầu, và để số nguyên tràn vòng lại một cách âm thầm. Hàm có thể trả về nhiều giá trị. Mọi đối số đều là bản sao: muốn hàm sửa biến của bên gọi thì truyền con trỏ. `defer` chạy một lời gọi khi hàm kết thúc, theo thứ tự ngược, với đối số đã chốt tại dòng `defer`. Còn `:=` trong một khối sẽ tạo biến mới, có thể che mất biến bạn định gán.
</Callout>

Nếu bạn chưa chạy chương trình Go nào, hãy đọc [Go cơ bản](/blog/go-first-program-modules-packages/) trước. Bài này giả định bạn đã biết `go run` một file.

## Biến và zero value

Biến là một ô nhớ có tên, chứa một giá trị thuộc một kiểu. Go có hai cách tạo biến. `var count int` nghĩa là "một ô tên `count` chứa `int`". `city := "Hanoi"` nghĩa là "tạo ô tên `city` và bỏ giá trị này vào", Go tự suy ra kiểu. Dạng ngắn `:=` là thứ bạn viết nhiều nhất, nhưng chỉ dùng được bên trong hàm.

Điều mới mẻ là trong ô có gì khi bạn không nói. Ở Go luôn là **zero value** của kiểu đó, nên biến không bao giờ "undefined" và không bao giờ chứa rác còn sót lại:

```go
var count int
var name string
var ok bool
var price float64
var p *int      // con trỏ, phần dưới sẽ nói
var items []string
var o Order     // struct có ID int và Total float64

city := "Hanoi"      // := vừa khai báo vừa gán
var temp = 31.5      // kiểu suy ra từ giá trị
a, b := 1, "two"     // nhiều biến một lúc
a, c := 3, "new"     // hợp lệ: c là tên mới nên được dùng :=
```

</TerminalOutput>

| Kiểu | Zero value |
| :--- | :--- |
| `int`, `float64` và các kiểu số khác | `0` |
| `string` | `""` (rỗng, không bao giờ là `nil`) |
| `bool` | `false` |
| con trỏ (`*T`) | `nil` |
| slice, map | `nil` (xem [Go collections](/blog/go-slices-maps-strings/)) |
| struct | từng field mang zero value của nó |

Nhờ zero value mà code Go thường bỏ được bước khởi tạo. Struct vừa khai báo dùng được ngay, bộ đếm bắt đầu từ 0 mà bạn không cần viết `= 0`.

Go cũng khắt khe với đồ thừa. Biến khai báo mà không dùng là lỗi biên dịch, import không dùng cũng vậy. Efficient Go nhận xét điều này làm người mới ngạc nhiên nhưng giữ code gọn. Nếu thật sự muốn bỏ qua một giá trị, hãy nói rõ bằng tên trống `_`.

<TerminalOutput command="go build ./unused" label="Apple M2 · Go 1.27" caption="Biến không dùng làm build thất bại. Trình biên dịch gọi đúng tên biến.">
```text

```
</TerminalOutput>

Thêm hai quy tắc về `:=`. Vế trái phải có ít nhất một tên mới, nên `a, c := 3, "new"` ở trên hợp lệ dù `a` đã có. Và không dùng được ngoài hàm; ở đầu file bạn phải viết `var`.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **`var` và `:=`**: `var x T` khai báo biến kiểu `T`. `x := v` khai báo và gán một bước, tự suy ra kiểu, nhưng chỉ dùng trong hàm.
- **`nil`**: cách Go nói "không trỏ vào đâu". Là zero value của con trỏ, slice, map và vài kiểu khác.
- **Tên trống `_` (blank identifier)**: tên chỉ để ghi, không đọc lại được. Gán vào nó là báo trình biên dịch rằng bạn cố ý bỏ qua giá trị đó.

</Concepts>

## Kiểu, hằng số và ép kiểu

Các kiểu số của Go có kích thước cố định, và tên kiểu nói luôn kích thước: `int8`, `int16`, `int32`, `int64` cùng bản không dấu `uint8` đến `uint64`. `int` và `uint` trơn là ngoại lệ: chúng theo máy, tức 64 bit trên máy 64 bit. Cứ dùng `int` trừ khi có lý do chọn cỡ khác. Số thực là `float32` và `float64` (dùng `float64`). `byte` là tên khác của `uint8`.

Quy tắc hay làm người ta bất ngờ: **Go không bao giờ tự đổi kiểu số giúp bạn.** Cộng `int32` với `int64` là lỗi biên dịch, dù chẳng mất thông tin gì.

<TerminalOutput command="go build ./bad" label="Apple M2 · Go 1.27" caption="Trộn int32 và int64 trong một biểu thức thì không biên dịch được.">
```text

bad/main.go:6:11: invalid operation: small + big (mismatched types int32 and int64)
```
</TerminalOutput>

Bạn ép kiểu có chủ đích bằng cách viết tên kiểu đích như một hàm: `int64(small) + big`. Đây cũng là chỗ dữ liệu bị mất, nên khi review code hãy nhìn vào các phép ép kiểu. Ép số thực sang số nguyên là cắt bỏ phần thập phân, không làm tròn.

```go
total := int64(small) + big
f := 9.99
fmt.Println(int(f)) // 9
```

### Hằng số và iota

`const` là tên cho một giá trị cố định từ lúc biên dịch. Hằng số không khai báo kiểu là **untyped** (chưa gắn kiểu), và spec nói hằng số là giá trị chính xác với độ chính xác tùy ý, không bao giờ tràn. Vì vậy `const half = 0.5` nhân được với `float64` hay cộng được vào biểu thức số nguyên mà không cần ép kiểu.

Với một dãy hằng số liên quan, Go có `iota`: trong một khối `const ( ... )` nó đếm 0, 1, 2... mỗi dòng một bước.

```go
type Weekday int

const (
	Sunday Weekday = iota // 0
	Monday                // 1
	Tuesday               // 2
)

const (
	_  = iota             // bỏ số 0
	KB = 1 << (10 * iota) // 1024
	MB                    // 1048576
	GB                    // 1073741824
)
```

Đây là cách Go làm enum. Không có từ khóa `enum`, chỉ có một kiểu đặt tên cộng với các hằng số.

### Bẫy số bát phân

Đây là lỗi biên dịch được, chạy được và cho ra đáp án nghe hợp lý. Số viết với số 0 đứng đầu là **bát phân** (cơ số 8), nên `010` bằng 8.

```go
fmt.Println(100 + 010)  // 108, không phải 110
fmt.Println(100 + 0o10) // 108, nhưng giờ code nói rõ là bát phân
fmt.Printf("755 as octal digits: %o\n", 755)
```

Cùng một lỗi này còn nấp trong quyền file. Quyền Unix `rwxr-xr-x` viết là `0o755`, còn số thập phân `755` là một bộ quyền hoàn toàn khác:

<TerminalOutput command="go run ./types" label="Apple M2 · Go 1.27" caption="0o755 là quyền bạn định ghi. Số thập phân 755 là thứ khác hẳn.">

```text
108
```

Hãy viết bát phân với tiền tố `0o`, đúng như 100 Go Mistakes khuyên, để người đọc sau khỏi phải đoán. Go cũng nhận `0b` cho nhị phân, `0x` cho thập lục phân và `_` làm dấu ngăn chữ số, nên `1_000_000` là một triệu.

Dòng cuối của output cho thấy thêm một điều. `7/2` ra `3` vì hai vế đều là số nguyên, còn `7/2.0` ra `3.5`. Kiểu của toán hạng quyết định kiểu phép chia.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Hằng số chưa gắn kiểu (untyped constant)**: hằng số viết trơn như `0.5` hay `1000`. Nó chỉ nhận kiểu ở chỗ được dùng, nên khớp với kiểu số nào bạn kết hợp.
- **`iota`**: bộ đếm bắt đầu từ 0 trong mỗi khối `const` và tăng một sau mỗi dòng. Dùng để làm danh sách kiểu enum.
- **Ép kiểu (conversion)**: viết `T(value)` để đổi giá trị sang kiểu `T`. Go bắt buộc làm vậy giữa các kiểu số khác nhau.
- **Bát phân (octal)**: cơ số 8. Trong Go, số bắt đầu bằng `0` là bát phân; `0o` làm rõ điều đó.

</Concepts>

## Tràn số và số thực

Số nguyên có số bit cố định, nên có giá trị lớn nhất. Cộng thêm một thì số **quay vòng** về giá trị nhỏ nhất. Go làm vậy âm thầm lúc chạy: không panic, không lỗi. (Nếu trình biên dịch thấy tràn ngay trong một hằng số, nó từ chối build, như `var c int32 = math.MaxInt32 + 1`.)

```go
var counter int32 = math.MaxInt32
counter++

var small uint8 = 255
small++

var big int64 = 40000
fmt.Println(int16(big))
```

<TerminalOutput command="go run ./overflow" label="Apple M2 · Go 1.27" caption="Ba lần quay vòng âm thầm. Lần cuối là kiểu lỗi của Ariane 5: ép sang kiểu hẹp hơn.">

</TerminalOutput>

<TerminalOutput command="go build ./constovf" label="Apple M2 · Go 1.27" caption="Khi chỗ tràn thấy được lúc biên dịch, Go từ chối build.">

Dòng `int16(40000)` kia chính là hình dạng của vụ Ariane 5: nhét một số rộng vào ô hẹp hơn. Giá trị bị tràn là độ lệch ngang (horizontal bias) của tên lửa, trên Ariane 5 nó lớn hơn mức thiết kế Ariane 4 đã dự tính. Go sẽ để phép ép kiểu y hệt đó đi qua mà không một tiếng động.

Phần lớn thời gian bạn không cần lo. Bộ đếm request trong một `int` sẽ không chạm tới 2^63. Hãy kiểm tra tràn khi dùng kiểu số nguyên nhỏ, xử lý số rất lớn, hoặc ép từ kiểu rộng sang kiểu hẹp. Cách kiểm tra là một phép so sánh trước khi tính: với phép cộng, `a > math.MaxInt-b` cho biết tổng sẽ tràn.

### Số thực là số xấp xỉ

`float64` lưu số ở dạng nhị phân, và đa số phân số thập phân như `0.1` không có dạng nhị phân chính xác. Kết quả là sai số rất nhỏ. Có một điểm lắt léo đáng xem một lần: cùng một biểu thức cho hai đáp án khác nhau tùy các số là hằng số hay biến.

```go
fmt.Println("0.1+0.2 == 0.3?", 0.1+0.2 == 0.3)  // hằng số
a, b := 0.1, 0.2
fmt.Println(a+b, a+b == 0.3, math.Abs(a+b-0.3) < 1e-9)  // biến
```

Vì vậy đừng bao giờ so sánh số thực bằng `==`. Hãy so hiệu của chúng với một ngưỡng nhỏ, như giá trị thứ ba. Chia số thực cho 0 không panic mà cho `+Inf`, `-Inf` hoặc `NaN` ("không phải số"), và `NaN` còn không bằng chính nó, nên dùng `math.IsNaN`. Với tiền, hãy lưu số xu nguyên trong một số nguyên thay vì đô la trong số thực.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Tràn số (overflow, quay vòng)**: kết quả quá lớn so với kiểu. Số nguyên của Go quay sang đầu bên kia của dải giá trị thay vì báo lỗi.
- **Số thực dấu phẩy động (floating point)**: cách máy tính lưu số có phần thập phân bằng số bit cố định. Kết quả gần đúng chứ không chính xác tuyệt đối.
- **`NaN` và `Inf`**: các giá trị thực đặc biệt cho "không phải số" và "vô cực". Chúng đến từ các phép như `0/0` và `1/0`.

</Concepts>

## Hàm

Hàm nói rõ đầu vào và đầu ra ngay trong chữ ký: `func divide(a, b int) (int, error)`. Kiểu viết sau tên, và các tham số cạnh nhau cùng kiểu có thể dùng chung một kiểu: `a, b int`. Hàm có thể trả về **nhiều giá trị**, và Go dùng điều này khắp nơi. Dạng quen thuộc là "kết quả, cộng một error", và bên gọi kiểm tra error ngay.

```go
func divide(a, b int) (int, error) {
	if b == 0 {
		return 0, errors.New("divide by zero")
	}
	return a / b, nil
}

q, err := divide(7, 2)
```

Ở đây không có exception để bắt: error chỉ là một giá trị bạn nhận về. Ý tưởng này có bài riêng, [Go errors](/blog/go-errors-defer-panic/).

### Giữ đường chạy chính ở bên trái

Vì Go bắt bạn kiểm tra lỗi ở từng bước, hàm rất dễ biến thành cầu thang `if`/`else` lồng nhau. Cách sửa là return sớm và giữ luồng bình thường thẳng một cột. Mat Ryer diễn đạt là "Align the happy path to the left" (dồn đường chạy thuận về bên trái), và 100 Go Mistakes dùng câu này để nói cùng ý.

```go
func join(s1, s2 string, max int) (string, error) {
	if s1 == "" {
		return "", errors.New("s1 is empty")
	}
	if s2 == "" {
		return "", errors.New("s2 is empty")
	}
	concat, err := concatenate(s1, s2)
	if err != nil {
		return "", err
	}
	if len(concat) > max {
		return concat[:max], nil
	}
	return concat, nil
}
```

Mỗi `if` có return thì không cần `else`. Đọc dọc mép trái là thấy đường thành công; các dòng thụt vào là những cách nó có thể hỏng.

### Kết quả có tên, và khi nào không nên dùng

Bạn có thể đặt tên cho giá trị trả về: `func minMax(xs []int) (lo, hi int)`. Các tên trở thành biến, đã đặt sẵn zero value, và một `return` trần sẽ trả về những gì chúng đang giữ. Hai chỗ dùng tốt: tên giúp ghi rõ `int` nào là cái nào, và tiết kiệm một hai dòng trong hàm ngắn.

Nguy hiểm là một kết quả có tên mà bạn quên gán sẽ lặng lẽ giữ zero value. Ở đây tác giả định trả về lỗi của context, nhưng lại trả `err`, một biến kết quả không ai gán:

```go
func check(ctx context.Context, ok bool) (n int, err error) {
	if !ok {
		return 0, errors.New("invalid")
	}
	if ctx.Err() != nil {
		return 0, err // err vẫn là nil ở đây!
	}
	return 1, nil
}
```

Nó biên dịch được vì `err` tồn tại (kết quả có tên luôn được khai báo). Nếu không đặt tên thì đây là lỗi biên dịch. Cách sửa là trả về lỗi thật:

```go
if err := ctx.Err(); err != nil {
	return 0, err
}
```

<TerminalOutput command="go run ./funcs" label="Apple M2 · Go 1.27" caption="Bản lỗi hủy context rồi vẫn báo không có error. Bản đã sửa báo context canceled.">
```text
3 <nil>
divide by zero
-2 9
buggy: <nil> true
fixed: context canceled
```
</TerminalOutput>

Quy tắc của mình, theo 100 Go Mistakes: đặt tên kết quả khi nó làm chữ ký rõ hơn (`(lat, lng float32, err error)` dễ đọc hơn `(float32, float32, error)`), và tránh `return` trần ngoài những hàm rất ngắn. Nếu không nói được tên giúp được gì, thì bỏ đi.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Nhiều giá trị trả về (multiple return values)**: hàm trả về nhiều kết quả cùng lúc. Theo quy ước, giá trị cuối là `error`.
- **Đường chạy chính (happy path)**: chuỗi bước khi mọi thứ suôn sẻ. Giữ nó không thụt vào giúp hàm dễ lướt đọc.
- **Kết quả có tên (named result)**: giá trị trả về có tên, đặt sẵn zero value. `return` trần trả về các giá trị hiện tại.

</Concepts>

## Con trỏ và truyền theo giá trị

Trong Go, mỗi lời gọi hàm **chép mọi đối số** vào các biến riêng của hàm. Đó là toàn bộ quy tắc, và Go FAQ nói thẳng: hàm luôn nhận một bản sao của thứ được truyền, như thể giá trị được gán vào tham số. Sửa bản sao thì bản gốc không đổi.

Con trỏ là cách để hàm sửa được bản gốc. `&x` nghĩa là "địa chỉ của `x`", còn `*p` nghĩa là "thứ mà `p` trỏ tới". Truyền `&x` vẫn là chép, nhưng thứ được chép là địa chỉ, nên hàm với tay tới biến của bạn qua nó. Hãy thử cả ba trường hợp bên dưới rồi đọc tiếp.

<GoPassByValueStepper />

Đây là cùng thí nghiệm dưới dạng chương trình thật. Verb `%p` in địa chỉ bộ nhớ, nên bạn thấy bản sao nằm ở chỗ khác:

```go
func bumpByValue(v int)    { v += 50 }
func bumpByPointer(p *int) { if p != nil { *p += 50 } }
```


### Khi nào truyền con trỏ

Mặc định truyền giá trị trơn. Chỉ dùng `*T` trong các trường hợp này:

| Truyền con trỏ khi | Vì sao |
| :--- | :--- |
| hàm phải sửa biến của bên gọi | bản sao không làm được |
| giá trị lớn | chép một con trỏ rẻ hơn; chưa chắc "lớn" là bao nhiêu thì benchmark |
| kiểu không được chép (ví dụ khóa trong package `sync`) | chép sẽ làm hỏng nó, xem [Context và khóa](/blog/go-context-timeouts-mutexes/) |
| `nil` nên nghĩa là "không có giá trị" | chỉ con trỏ mới có thể là `nil` |

### Con trỏ nhỏ và an toàn

Con trỏ trong Go không dịch đi được. Viết `p++` để nhảy sang ô nhớ kế tiếp như trong C thì không biên dịch. Go FAQ giải thích bằng một từ: an toàn, vì không có số học con trỏ thì ngôn ngữ không bao giờ tạo ra một địa chỉ bất hợp lệ.

### Cùng lựa chọn đó cho method

Method có thể nhận receiver (giá trị đứng trước tên method) theo giá trị hoặc theo con trỏ, và quy tắc giống như trên. Receiver giá trị làm việc trên bản sao. Receiver con trỏ sửa bản gốc. Struct và method có bài riêng, [Go structs và interface](/blog/go-structs-methods-interfaces/); ở đây chỉ xem hiệu ứng:

```go
func (a Account) AddValue(v float64)    { a.Balance += v }
func (a *Account) AddPointer(v float64) { a.Balance += v }
```

<TerminalOutput command="go run ./ptr" label="Apple M2 · Go 1.27" caption="Xuất phát từ 100: receiver giá trị cộng vào bản sao rồi mất. Receiver con trỏ giữ được 50.">
```text

pointer receiver: 150.00
```

</TerminalOutput>

Dùng receiver con trỏ nếu method sửa receiver hoặc kiểu chứa thứ không được chép. Dùng receiver giá trị cho kiểu nhỏ, tự nhiên bất biến như `time.Time`. Nếu một method của kiểu cần con trỏ, hãy cho tất cả method dùng receiver con trỏ để kiểu nhất quán.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Con trỏ (pointer)**: biến giữ địa chỉ bộ nhớ của một biến khác. `&x` lấy địa chỉ, `*p` đi theo địa chỉ.
- **Dereference (giải tham chiếu)**: đi theo con trỏ tới giá trị nó trỏ vào, viết là `*p`.
- **Receiver**: tham số phụ viết trước tên method. Nó quyết định method thuộc về kiểu nào.
- **Panic**: sự cố lúc chạy làm chương trình sập dần. Truy cập qua con trỏ nil gây ra panic.

</Concepts>

## defer

Dọn dẹp là nơi lỗi hay ẩn: bạn mở một file, rồi có bốn chỗ có thể return sớm, và phải đóng file ở cả bốn. `defer` giải quyết chuyện này. `defer someCall()` không chạy lời gọi ngay. Nó đặt lời gọi vào một danh sách, và Go chạy danh sách đó khi **hàm bao quanh return**, kể cả khi return sớm hay panic. Mở file rồi `defer Close()` ở dòng kế tiếp thì bạn không thể quên.

Bài của blog Go về defer nêu quy tắc trong ba câu. Các lời gọi được đẩy vào danh sách. Chúng chạy theo thứ tự **vào sau ra trước (LIFO)** sau khi hàm return. Và đối số được tính khi câu lệnh `defer` chạy, không phải sau đó.

```go
for i := 1; i <= 3; i++ {
	defer fmt.Println("deferred", i)
}
fmt.Println("function body done")
```

<TerminalOutput command="go run ./deferd" label="Apple M2 · Go 1.27" caption="Thứ tự ngược: defer đăng ký cuối cùng chạy đầu tiên.">
```text
function body done

deferred 2
deferred 1
```
</TerminalOutput>

Thứ tự ngược là có chủ ý. Thứ mở trước thường là nền cho thứ mở sau, như một kết nối rồi một transaction trên đó, nên phải đóng từ trong ra ngoài.

### Đối số được chốt tại dòng defer

Cái này làm nhiều người vấp, và 100 Go Mistakes dành hẳn một mục. Đối số của lời gọi defer được tính ngay lập tức, nên việc biến đổi giá trị sau đó không ảnh hưởng tới chúng. Closure thì khác: nó giữ liên kết tới biến và đọc khi nó thực sự chạy.

```go
x := 10
defer fmt.Println("defer arg captured x =", x)
defer func() { fmt.Println("closure sees x =", x) }()
x = 99
```

Bộ mô phỏng ở trên có tab thứ ba đi qua đúng trường hợp này. Đây là output thật, cùng một ví dụ thực tế hơn, khi một chuỗi trạng thái được báo cáo lúc thoát hàm:

```go
func broken(fail bool) {
	var status string
	defer notify(status)   // status đang là "" và chính "" này được lưu lại
	status = "success"
	if fail {
		status = "error"
	}
}

func fixedClosure(fail bool) {
	var status string
	defer func() { notify(status) }() // đọc status khi hàm kết thúc
	// ... thân hàm giống trên
}
```

```text

defer arg captured x = 10
broken:
  notify("")

  notify("error")
```
</TerminalOutput>

Hai cách sửa là closure ở trên, hoặc truyền con trỏ (`defer notify(&status)`), vì địa chỉ của con trỏ không đổi dù giá trị nó trỏ tới thay đổi. Closure thường đơn giản hơn.

Hai chuyện liên quan có chỗ riêng: `defer` trong vòng lặp, và `panic` với `recover`. Cả hai nằm ở [Go errors](/blog/go-errors-defer-panic/).

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **`defer`**: hẹn một lời gọi chạy khi hàm hiện tại kết thúc, bất kể kết thúc kiểu nào.
- **LIFO (vào sau ra trước)**: như chồng đĩa: cái đặt lên sau cùng là cái được lấy ra đầu tiên.
- **Closure**: hàm viết ngay tại chỗ, đọc và sửa được các biến của hàm bao quanh.

</Concepts>

## Che biến, cái bẫy đầu tiên

Giờ bạn đã biết `:=`, đây là cách nó cắn. Mỗi khối `{ ... }` (một `if`, một `for`, hay cặp ngoặc trơn) là một **scope** riêng: tên khai báo bên trong chỉ sống tới dấu đóng ngoặc. Nếu bạn viết `x := ...` trong khối mà `x` đã có bên ngoài, Go không gán cho `x` bên ngoài. Nó tạo một `x` hoàn toàn mới **che (shadow)** cái bên ngoài.

Đây là ví dụ trong 100 Go Mistakes, rút gọn cho đúng ý. `client` bên ngoài vẫn là `nil`, vì `client, err := ...` trong `if` khai báo hai biến mới:

```go
func buggy(tracing bool) *Client {
	var client *Client
	if tracing {
		client, err := newTraced() // client VÀ err mới, chỉ trong khối này
		if err != nil {
			return nil
		}
		fmt.Println("inside block:", client.Name)
	}
	return client // client bên ngoài chưa hề bị đụng tới
}

func fixed(tracing bool) *Client {
	var client *Client
	var err error
	if tracing {
		client, err = newTraced() // dấu = trơn, gán vào biến bên ngoài
	} else {
		client, err = newDefault()
	}
	if err != nil {
		return nil
	}
	return client
}
```

<TerminalOutput command="go run ./shadow" label="Apple M2 · Go 1.27" caption="Khối lệnh dùng client riêng và in ra bình thường, nhưng hàm vẫn trả về nil. Bản sửa gán bằng = vào các biến khai báo một lần ở ngoài.">
```text
inside block: traced
buggy returns nil? true
fixed returns nil? false
```
</TerminalOutput>

Trình biên dịch chấp nhận vì `client` bên trong có được dùng (nó được in ra). Hai cách sửa: khai báo biến trước rồi dùng `=` trơn trong khối, hoặc dùng một tên tạm rồi gán ra ngoài. Dùng lại tên như `err` trong khối đôi khi tiện, nên không có lệnh cấm tuyệt đối, nhưng hễ một giá trị "biến mất" sau khối `if`, hãy tìm xem có `:=` nào lặng lẽ tạo biến thứ hai không.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Scope (phạm vi)**: vùng code mà một tên còn hiệu lực. Mỗi cặp ngoặc nhọn mở một scope mới.
- **Che biến (shadowing)**: khai báo ở scope trong một tên đã có ở scope ngoài, khiến tên trong che mất tên ngoài.

</Concepts>

## Hai thói quen nhỏ

**Hàm `init`.** Hàm tên `init` không có đối số sẽ tự chạy, trước `main`, một lần cho mỗi package. Các biến khai báo ở mức package được khởi tạo trước, rồi mọi `init` theo thứ tự xuất hiện trong source, rồi tới `main`. Một file có thể có nhiều `init`.

```go
var a = func() int { fmt.Println("var"); return 0 }()
func init() { fmt.Println("init 1") }
func init() { fmt.Println("init 2") }
func main() { fmt.Println("main") }
```

Cái khó là `init` không trả về error được, và nó chạy trước khi bạn kiểm soát được gì, nên thất bại ở đó nghĩa là panic hoặc giấu lỗi. Nó cũng làm trình tự mọi thứ diễn ra khó theo dõi hơn. 100 Go Mistakes khuyên đừng dùng nó cho việc khởi tạo thật. Hãy ưu tiên một hàm tường minh mà bạn gọi từ `main` và test được. Cách các package kích hoạt `init` của nhau có trong [Go cơ bản](/blog/go-first-program-modules-packages/).

**Getter và setter.** Ở Java bạn viết `getBalance()` và `setBalance()` theo phản xạ. Go không cần. Nếu field được export (chữ cái đầu viết hoa), người ta cứ đọc thẳng `customer.Balance`. Chỉ thêm accessor khi chúng làm gì đó: kiểm tra hợp lệ, tính toán, hoặc bảo vệ bằng khóa. Khi làm vậy, getter tên là `Balance()`, không có tiền tố `Get`, còn setter là `SetBalance()`. Struct và field export hoạt động thế nào có trong [Go structs và interface](/blog/go-structs-methods-interfaces/).

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Hàm `init`**: hàm đặc biệt Go tự gọi lúc khởi động, trước `main`.
- **Tên export (exported name)**: tên bắt đầu bằng chữ hoa, package khác nhìn thấy được. Tên chữ thường chỉ dùng riêng trong package.

## Điểm rút ra (Key takeaways)

- **Biến không bao giờ bắt đầu ở trạng thái undefined.** Mỗi kiểu có zero value, nên biến vừa khai báo dùng được ngay, và biến không dùng là lỗi biên dịch.
- **Ép kiểu số có chủ đích, và coi mỗi phép ép là một rủi ro.** Go không bao giờ trộn kiểu số âm thầm, nhưng nó quay vòng số nguyên âm thầm, chính thứ đã làm Ariane 5 hỏng.
- **Return sớm và giữ đường chạy chính ở bên trái**, chỉ dùng kết quả có tên khi nó làm chữ ký rõ hơn.
- **Mọi thứ là bản sao.** Truyền con trỏ khi hàm phải sửa biến của bạn, giá trị lớn, hoặc `nil` nên nghĩa là vắng mặt. Còn lại truyền giá trị.
- **`defer` chốt đối số tại dòng `defer`**; dùng closure để đọc giá trị mới nhất, và nhớ `:=` trong khối trong tạo biến mới.

## Câu hỏi ôn tập (Review questions)

2. `int16(40000)` in ra gì, và vì sao Go không ngăn bạn? (Tràn số và số thực)
3. Một hàm nhận `v int` và làm `v += 50`. Vì sao biến của bên gọi không đổi, và đổi gì để nó cập nhật? (Con trỏ và truyền theo giá trị)
4. Đoạn này in ra gì, và vì sao: `x := 1; defer fmt.Println(x); x = 2`? Làm sao để nó in 2? (defer)
5. Sau một khối `if`, `client` bên ngoài vẫn là `nil` dù khối đã gọi `client, err := create()` thành công. Chuyện gì đã xảy ra? (Che biến, cái bẫy đầu tiên)
