### The hook: two hours of guessing

On 18 November 2025 a large part of the internet returned errors for hours. Cloudflare's own post-mortem is blunt about how it started. A database permissions change made a query return duplicate column metadata, which doubled the size of a configuration file for their Bot Management feature. The proxy software had a hard limit of 200 features, about 60 were in use, and the oversized file crashed it. Cloudflare dates the start of the incident to 11:20 UTC.

What I find useful is what the team did next. They "initially wrongly suspected" a "hyper-scale DDoS attack". A fair guess: the symptoms looked like one. A coincidental outage of their status page, which is hosted off their own infrastructure, made the attack story stronger. And the errors came and went, because every five minutes the system generated either a good or a bad file: "This fluctuation made it unclear what was happening as the entire system would recover and then fail again." By 13:37 the team was working on rolling back the Bot Management file, more than two hours in. New file propagation stopped at 14:24, core traffic was mostly normal at 14:30, everything by 17:06. The post-mortem even notes that the debugging and observability systems themselves burned large amounts of CPU while enriching errors.

<BeP10Timeline />

I am not saying Cloudflare had no dashboards. I am saying the gap between "something is failing" and "this file, this limit" was crossed by guessing first and reading evidence second, on the worst day. Your service will have a smaller version of that gap. The size of it is decided long before the incident, by what each request leaves behind.

AI-written FastAPI services leave very little. The generated endpoint works, passes the demo, and logs `print("here")`. This post builds the wall of dials instead, on the series' clue.api, in five questions:

1. **Why `print()` is not a log**, and what one useful log line looks like.
2. **How one request id follows a request across services**, and how to keep secrets out of what you log.
3. **What a metric is for** — counts and buckets, and why an average lies.
4. **What a trace adds** — the request's own timeline, across the database and the next service.
5. **How to debug by evidence** — one deliberately slow request, found and explained in three steps.

Post 1's `trace_demo.py` was the first, hand-rolled trace: a middleware that printed the dispatch chain of one request. This post is its production-grade descendant. It builds on the layers from [post 4](/blog/backend-layered-architecture/) and the SQLAlchemy layer from [post 5](/blog/backend-database-access-layer/).

## 1. A print is not a log

Here is what debugging looks like when the only tool is `print()`. One endpoint, one print before the work, one in the middle, one at the end:

```python
@app.get("/cases/{case_id}/close")
async def close(case_id: str) -> dict:
    print("closing case")  # which case? which request? how long?
    await asyncio.sleep(0.2 if case_id == "C-1" else 0.05)
    print("rule check passed")
    await asyncio.sleep(0.1)
    print("done")
    return {"closed": case_id}
```

Everything a print could have said was thrown away because it was a string for a human in front of a terminal. The fix is the standard library's `logging`, with one change: the output is data, not prose. One JSON object per line, with the same fields on every line, so a machine can filter it and a person can still read it.

`logging` has three parts you will meet everywhere. A **logger** is what code calls (`log.info(...)`). A **handler** decides where the line goes (stdout here). A **formatter** decides what it looks like. A **filter** can add or change fields on every record that passes. The JSON formatter below is about twenty lines (`demo/p10_logs.py`, the whole class):

<BeP10LogParts />

```python
class JsonFormatter(logging.Formatter):
    def __init__(self, service: str) -> None:
        super().__init__()
        self.service = service

    def format(self, record: logging.LogRecord) -> str:
        line = {
            "ts": self.formatTime(record, "%H:%M:%S") + f".{int(record.msecs):03d}",
            "level": record.levelname,
            "service": self.service,
            "logger": record.name,
            "request_id": getattr(record, "request_id", "-"),
            "msg": record.getMessage(),
        }
        line.update({k: v for k, v in vars(record).items() if k not in _STANDARD})
        if record.exc_info:
            line["exc"] = self.formatException(record.exc_info)
        return json.dumps(line, default=str)
```

Two details matter. `extra={...}` on a log call becomes attributes on the record, and the loop over `vars(record)` copies every one that is not a standard attribute into the JSON, so `log.info("request", extra={"status": 201})` gives you a `status` field you can filter on. And `configure()` turns off uvicorn's own access log, otherwise every request gets a second, unstructured line:

```python
def configure(service: str) -> None:
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(JsonFormatter(service))
    handler.addFilter(RequestIdFilter())
    handler.addFilter(RedactFilter())
    root = logging.getLogger()
    root.handlers[:] = [handler]
    root.setLevel(logging.INFO)
    # uvicorn's own access log would be a second, unstructured line per request.
    logging.getLogger("uvicorn.access").disabled = True
```

The line that matters most is the access line, one per request, written by a middleware. FastAPI's `@app.middleware("http")` wraps every request: code before `call_next` runs on the way in, code after it runs on the way out (post 1's middleware did exactly this to print). `demo/p10_middleware.py`, the whole file:

```python
import logging
import time
import uuid

from fastapi import FastAPI, Request

from p10_logs import request_id_var

log = logging.getLogger("clue.access")


def install(app: FastAPI) -> None:
    @app.middleware("http")
    async def request_context(request: Request, call_next):
        # Trust a caller's id (so one id spans services), or mint our own.
        rid = request.headers.get("x-request-id") or uuid.uuid4().hex[:8]
        token = request_id_var.set(rid)
        started = time.perf_counter()
        status = 500  # if call_next raises, this is what we really answered
        try:
            response = await call_next(request)
            status = response.status_code
            response.headers["X-Request-ID"] = rid
            return response
        finally:
            log.info(
                "request",
                extra={
                    "method": request.method,
                    "path": request.url.path,
                    "status": status,
                    "duration_ms": round((time.perf_counter() - started) * 1000, 1),
                },
            )
            request_id_var.reset(token)
```

Read it in three beats. It takes the id from the caller's `X-Request-ID` header or mints a short one, and stores it in a `ContextVar` (more on that in a moment). It times the call. And the `finally` block writes the line even when the handler raised, which is why `status` starts at 500: if `call_next` throws, the 500 is what the client got.

## 2. One id across every service

Look at the `clue.service` lines above. Post 4's `CaseService` has no idea there is a web request: it takes a case id and a detective name. Yet its lines carry `a6d3d33e`, the id of the request it ran inside. The mechanism is a `ContextVar`, Python's per-task variable. The middleware sets it once; a logging filter reads it on every record:

```python
request_id_var: ContextVar[str] = ContextVar("request_id", default="-")
```

```python
class RequestIdFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        ctx = trace.get_current_span().get_span_context()
        if ctx.is_valid:  # only when tracing is on and a span is open
            record.trace_id = format(ctx.trace_id, "032x")
        return True
```

Because the value lives in the context of the running request, the service layer never receives a `request` argument just to log. FastAPI runs a plain `def` endpoint in a worker thread and copies the context into it, so the id survives there too (post 6 covers why sync endpoints run in threads). The catch: a new `threading.Thread` or a separate process starts with an empty context on Python 3.13, so code you hand off that way logs the id as `-`.

<BeP10Context />

The same series' `layered_service.py` says what it is doing with `print()`, through a small `_trace` helper. Rather than edit it, `p10_app.py` swaps that helper for a logger. One assignment turns every one of those prints into a structured line with the request id:

```python
layered_service._trace = lambda msg: log.info(msg)
```

Now the part that makes it a *correlation* id: it has to cross the network. clue.api's `/cases/{case_id}/report` calls a second service, evidence-lab, over HTTP. An `httpx` event hook stamps the id on every outgoing request, so no endpoint can forget:

```python
def stamp_request_id(request: httpx.Request) -> None:
    """Forward the correlation id on every outgoing call, so nobody forgets."""
    request.headers["X-Request-ID"] = p10_logs.request_id_var.get()


lab = httpx.Client(base_url=LAB, event_hooks={"request": [stamp_request_id]})
```

```python
@app.get("/cases/{case_id}/report")

    case = service.get_case(case_id)
    analysis = lab.get(f"/analyze/{case_id}", timeout=5).json()
    return {"case": vars(case), "analysis": analysis}
```

If the caller sends no id, the middleware mints one and returns it in the response's `X-Request-ID`, which is the id a user quotes in a bug report. Mind the trust: an id from the outside is a label, never an identity, so do not build anything that grants access from it.

### What never reaches a log

Logs are copied, indexed, shipped to a vendor and kept for months. Whatever a log line holds is now in all of those places. An assistant debugging a login bug writes this:

```python
token = "eyJhbGciOi.demo.signature"
user = {"name": "holmes", "password": "hunter2"}

# 1) The line an assistant writes while debugging a login problem.
plain = logging.StreamHandler(sys.stdout)
plain.setFormatter(p10_logs.JsonFormatter("clue-api"))
log = logging.getLogger("clue.auth")
log.addHandler(plain)
log.setLevel(logging.INFO)
log.info(f"login failed for {user} token={token}")
```

An f-string builds the final message before logging sees it, so the secret is already inside the text. The fix is a filter on the handler, the last line of defence, in the same file as the formatter (`demo/p10_logs.py`):

```python
# Catches token=abc, 'password': 'hunter2' and "api_key": "abc" alike.
_SECRET = re.compile(
    r"""(?i)(password|token|authorization|api[_-]?key)(['"]?\s*[=:]\s*)['"]?[^\s,'"})]+['"]?"""
)
```

```python
class RedactFilter(logging.Filter):
    """Last line of defence: scrub secrets from the message and from extras."""

    def filter(self, record: logging.LogRecord) -> bool:
        record.msg = _SECRET.sub(r"\1\2[REDACTED]", record.getMessage())
        record.args = None
        for key in ("password", "token", "authorization"):
            if key in record.__dict__:
                record.__dict__[key] = "[REDACTED]"
        return True
```

<BeP10Redact />

A regex catches what it was written for and nothing else: it will miss a secret in a shape you did not anticipate. Treat it as the net under the trapeze. The habit is to log identifiers (`case_id`, the user's id), never the object, never a token, a password or a full request body. [Post 7](/blog/backend-auth-oauth2-jwt/) is where those tokens come from.

## 3. Metrics: count, bucket, never average

Logs answer "what happened to this request". They cannot answer "how is the service doing", because nobody reads 10,000 lines. For that you want numbers that are cheap to keep: **metrics**. A metric is a name, a few labels, and a value that a scraper (Prometheus, for example) reads from `/metrics` every few seconds.

Two metric types cover most backends. A **counter** only goes up: requests served. A **histogram** counts observations into buckets: how many requests took up to 10 ms, up to 50 ms, up to 100 ms. `prometheus_client` provides both, and the middleware in `demo/p10_metrics.py` feeds them:

```python
REQUESTS = Counter(
    "http_requests_total", "Requests served", ["method", "route", "status"]
)
LATENCY = Histogram(
    "http_request_duration_seconds",
    "Request latency",
    ["route"],
    buckets=(0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5),
)
```

The histogram's buckets are chosen up front: the boundaries are the only resolution you will ever get back. These run from 10 ms to 2.5 s. A middleware records every request into both:

```python
    @app.middleware("http")
    async def measure(request: Request, call_next):
        started = time.perf_counter()
        status = 500
        try:
            response = await call_next(request)
            status = response.status_code
            return response
        finally:
            # The route TEMPLATE ("/cases/{case_id}"), never the raw path:
            # the raw path would mint one time series per case id.
            route = request.scope.get("route")
            label = route.path if route else "unmatched"
            REQUESTS.labels(request.method, label, str(status)).inc()
            LATENCY.labels(label).observe(time.perf_counter() - started)
```

Mind the comment inside: the label is the route *template* (`/cases/{case_id}/report`), read from `request.scope["route"]` after the router has matched, and never the raw path. The raw path contains the case id, and every distinct value would become its own time series; the end of this section shows what that costs. Average latency is 200 ms, and not one request took 200 ms. Thirty-five were under 100 ms and five were over a second. A latency alert on the average would be quiet (200 ms looks healthy), while one request in eight is unusable. A histogram keeps the shape: you can ask for the 95th or 99th percentile, you can add histograms from several workers together (you cannot average averages), and you can see two humps instead of one number between them. The trap for AI-written code is that `time.time()` around a handler and one `avg_latency` gauge is the first thing it produces.

<BeP10Cardinality />

Prometheus's own naming guide says it plainly: "Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses, or other unbounded sets of values." Metrics stay cheap because they aggregate; a label that grows with your users removes exactly that property. Who asked for which case belongs in a log line (searchable, per request) or a trace attribute. Labels are for small, fixed sets: the route template, the method, the status class.

## 4. Traces: the request's own timeline

Metrics tell you a route is slow. Logs tell you which request. Neither shows where the time went *inside* a request that touched a database and another service. A **trace** does: it is the tree of **spans** a single request produced. Each span has a name, a start and an end, a `trace_id` shared by the whole tree, and a `parent_id` pointing at the span that caused it.

<BeP10Signals />

**OpenTelemetry** is the vendor-neutral standard for producing them. In Python that is three kinds of piece: the SDK (creates and exports spans), an exporter (where they go), and instrumentation packages that wrap a library so you write no span code. `demo/p10_tracing.py` wires all of it in one function:

```python
def setup(app: FastAPI, service: str, engine=None) -> None:
    provider = TracerProvider(resource=Resource.create({"service.name": service}))
    # Console exporter: no collector needed. Production would use a
    # BatchSpanProcessor + OTLP exporter instead of printing each span.
    provider.add_span_processor(SimpleSpanProcessor(ConsoleSpanExporter()))
    trace.set_tracer_provider(provider)

    FastAPIInstrumentor.instrument_app(app)
    HTTPXClientInstrumentor().instrument()  # also injects the traceparent header
    if engine is not None:
        SQLAlchemyInstrumentor().instrument(engine=engine)
```

Each line does one job. `FastAPIInstrumentor.instrument_app(app)` opens a span for every request. `HTTPXClientInstrumentor` opens a span for every outgoing call and also injects a `traceparent` header (the W3C Trace Context format) carrying the trace id, so evidence-lab's span joins the same trace instead of starting its own. `SQLAlchemyInstrumentor` gives post 5's engine a span per SQL statement. The exporter here is `ConsoleSpanExporter`, which prints spans, so no collector is needed to try this. In production you would swap in a `BatchSpanProcessor` and an OTLP exporter: the simple processor exports each span synchronously on the request's own thread, fine for a demo and a cost you do not want on every request.

Custom spans are one `with` away. The service layer from post 4 gets a span around its moves, without touching `layered_service.py`:

```python
class ObservedCaseService(CaseService):
    """post 4's service, unchanged, plus a span around each move."""

    def get_case(self, case_id: str) -> CaseRecord:
        with tracer.start_as_current_span("CaseService.get_case"):
            return super().get_case(case_id)

    def assign(self, case_id: str, detective: str) -> CaseRecord:
        with tracer.start_as_current_span("CaseService.assign"):
            return super().assign(case_id, detective)
```

## 5. Debug by evidence

Here is the whole thing in use, on a fault I built into the demo: evidence-lab is slow for one case, C-7 (it has a huge evidence set). Nobody told the dashboard. A user says "the report page is sometimes slow".

The guesses come first, because they always do: the database, a missing index, the thread pool, the new deploy. Any of them can be true and each one takes a half hour to rule in or out with a code change. Skip them. Use the three signals in order, each narrowing what the next one has to answer.

<BeP10Walk />

**Step 1, metrics: is it real, and how often?** The histogram from section 3: 5 of 40 report requests took over a second. It is real, it is the report route, and it is a minority. That is a different bug from "everything is slow" and already rules out most global causes.

**Step 2, logs: which requests?** Filter the access lines for slow ones, take one request id, and search both services' logs for it:

<Callout type="note" title="Observability has a price">
Cloudflare's post-mortem notes that large amounts of CPU went to its debugging and observability systems while the incident was under way. Everything in this post costs something: JSON formatting on the request path, a counter increment per request, a span per SQL statement, a log line that blocks if stdout is slow. Keep the per-request work small, export in batches, and make sure the thing you add to find a fault cannot become one.
</Callout>

### The review habit

A checklist for the next AI-written service, one line each:

| It wrote | Ask | Fix in this post |
|---|---|---|
| `print()` or `logging.info(f"...")` in endpoints | Can I filter these by request, status and duration? | JSON formatter + the access middleware (section 1) |
| Logs that name the user, a token or a body | Would I be comfortable seeing this in a vendor's index? | `RedactFilter`, log ids not objects (section 2) |
| A call to another service | Does it forward the request id and `traceparent`? | `httpx` hook + `HTTPXClientInstrumentor` (sections 2, 4) |
| `avg_latency` or a single timer | Can it show a tail? | Histogram with explicit buckets (section 3) |
| A label like `user_id` or the raw path | How many distinct values can this take? | Route template, fixed small sets (section 3) |
| A trace exporter set to print | What does it cost on every request? | `BatchSpanProcessor` + OTLP in production (section 4) |

<Concepts>
- **Structured log**: one machine-readable record per event (JSON here) with the same fields every time, so tools can filter and count it.
- **Correlation id (request id)**: a value stamped on every log line of one request and forwarded to every service it calls, so separate logs can be joined.
- **`ContextVar`**: a Python variable whose value belongs to the current task or request context, so deep code can read it without a parameter.
- **Counter / histogram**: a number that only goes up, and a set of bucket counts that keeps the shape of a distribution, respectively.
- **Cardinality**: how many distinct values a label can take. Each one is a separate time series, so unbounded labels grow memory without limit.
- **Trace / span**: a trace is everything one request caused; a span is one timed step in it, with a `parent_id` pointing at the step that caused it.
</Concepts>

`logging` có ba mảnh bạn sẽ gặp ở mọi nơi. **Logger** là thứ code gọi (`log.info(...)`). **Handler** quyết định dòng log đi đâu (ở đây là stdout). **Formatter** quyết định nó trông thế nào. Thêm **filter** có thể gắn thêm hoặc sửa trường trên mọi record đi qua. Formatter JSON bên dưới dài chừng hai chục dòng (`demo/p10_logs.py`, nguyên class):

<BeP10LogParts />

```python
class JsonFormatter(logging.Formatter):
    def __init__(self, service: str) -> None:
        super().__init__()
        self.service = service

    def format(self, record: logging.LogRecord) -> str:
        line = {
            "ts": self.formatTime(record, "%H:%M:%S") + f".{int(record.msecs):03d}",
            "level": record.levelname,
            "service": self.service,
            "logger": record.name,
            "request_id": getattr(record, "request_id", "-"),
            "msg": record.getMessage(),
        }
        line.update({k: v for k, v in vars(record).items() if k not in _STANDARD})
        if record.exc_info:
            line["exc"] = self.formatException(record.exc_info)
        return json.dumps(line, default=str)
```

Hai chi tiết đáng chú ý. `extra={...}` trong lời gọi log thành attribute của record, và vòng lặp trên `vars(record)` chép mọi attribute không chuẩn vào JSON, nên `log.info("request", extra={"status": 201})` cho bạn một trường `status` để lọc. Còn `configure()` tắt access log của uvicorn, không thì mỗi request có thêm một dòng thứ hai không có cấu trúc:

```python
def configure(service: str) -> None:
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(JsonFormatter(service))
    handler.addFilter(RequestIdFilter())
    handler.addFilter(RedactFilter())
    root = logging.getLogger()
    root.handlers[:] = [handler]
    root.setLevel(logging.INFO)
    # uvicorn's own access log would be a second, unstructured line per request.
    logging.getLogger("uvicorn.access").disabled = True
```

Dòng quan trọng nhất là dòng access, mỗi request một dòng, do middleware ghi. `@app.middleware("http")` của FastAPI bọc quanh mỗi request: code trước `call_next` chạy lúc vào, code sau nó chạy lúc ra (middleware ở bài 1 làm đúng việc này để in). `demo/p10_middleware.py`, nguyên file:

```python
import logging
import time
import uuid

from fastapi import FastAPI, Request

from p10_logs import request_id_var

log = logging.getLogger("clue.access")


def install(app: FastAPI) -> None:
    @app.middleware("http")
    async def request_context(request: Request, call_next):
        # Trust a caller's id (so one id spans services), or mint our own.
        rid = request.headers.get("x-request-id") or uuid.uuid4().hex[:8]
        token = request_id_var.set(rid)
        started = time.perf_counter()
        status = 500  # if call_next raises, this is what we really answered
        try:
            response = await call_next(request)
            status = response.status_code
            response.headers["X-Request-ID"] = rid
            return response
        finally:
            log.info(
                "request",
                extra={
                    "method": request.method,
                    "path": request.url.path,
                    "status": status,
                    "duration_ms": round((time.perf_counter() - started) * 1000, 1),
                },
            )
            request_id_var.reset(token)
```

Đọc nó theo ba nhịp. Nó lấy id từ header `X-Request-ID` của caller hoặc tự sinh một id ngắn, rồi cất vào một `ContextVar` (lát nữa nói thêm). Nó bấm giờ lời gọi. Và khối `finally` ghi dòng log kể cả khi handler ném lỗi, nên `status` khởi đầu là 500: nếu `call_next` ném exception thì 500 là thứ client nhận được.

## 2. Một id đi qua mọi service

Nhìn các dòng `clue.service` ở trên. `CaseService` của bài 4 không biết có request web nào: nó nhận một case id và tên thám tử. Vậy mà dòng log của nó mang `a6d3d33e`, id của request nó chạy bên trong. Cơ chế là `ContextVar`, biến riêng theo từng task của Python. Middleware đặt nó một lần; một filter của logging đọc nó trên mọi record:

```python
request_id_var: ContextVar[str] = ContextVar("request_id", default="-")
```

```python
class RequestIdFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        ctx = trace.get_current_span().get_span_context()
        if ctx.is_valid:  # only when tracing is on and a span is open
            record.trace_id = format(ctx.trace_id, "032x")
        return True
```

Vì giá trị nằm trong context của request đang chạy, tầng service không phải nhận thêm tham số `request` chỉ để log. FastAPI chạy endpoint `def` thường trong một worker thread và chép context sang đó, nên id vẫn còn (bài 6 giải thích vì sao endpoint sync chạy trong thread). Một cái bẫy: `threading.Thread` mới hoặc process riêng khởi đầu với context rỗng trên Python 3.13, nên code bạn đẩy sang đó sẽ log id là `-`.

<BeP10Context />

`layered_service.py` của series nói nó đang làm gì bằng `print()`, qua một helper `_trace` nhỏ. Thay vì sửa file đó, `p10_app.py` đổi helper ấy thành logger. Một phép gán biến mọi dòng print thành dòng log có cấu trúc kèm request id:

```python
layered_service._trace = lambda msg: log.info(msg)
```

Log bị chép, bị index, bị đẩy lên vendor và giữ hàng tháng. Cái gì nằm trong một dòng log là đã nằm ở tất cả những chỗ đó. Một trợ lý đang debug lỗi đăng nhập sẽ viết thế này:

```python
# Catches token=abc, 'password': 'hunter2' and "api_key": "abc" alike.
_SECRET = re.compile(
    r"""(?i)(password|token|authorization|api[_-]?key)(['"]?\s*[=:]\s*)['"]?[^\s,'"})]+['"]?"""
)
```

```python
class RedactFilter(logging.Filter):
    """Last line of defence: scrub secrets from the message and from extras."""

    def filter(self, record: logging.LogRecord) -> bool:
        record.msg = _SECRET.sub(r"\1\2[REDACTED]", record.getMessage())
        record.args = None
        for key in ("password", "token", "authorization"):
            if key in record.__dict__:
                record.__dict__[key] = "[REDACTED]"
        return True
```

## 3. Metric: đếm, chia bucket, đừng lấy trung bình

Log trả lời "request này đã xảy ra chuyện gì". Nó không trả lời được "service đang khỏe không", vì không ai đọc nổi 10.000 dòng. Muốn vậy bạn cần những con số rẻ để giữ: **metric**. Một metric gồm một cái tên, vài label và một giá trị mà scraper (ví dụ Prometheus) đọc từ `/metrics` vài giây một lần.

Hai loại metric phủ phần lớn backend. **Counter** chỉ tăng: số request đã phục vụ. **Histogram** đếm quan sát vào các bucket: bao nhiêu request mất tới 10 ms, tới 50 ms, tới 100 ms. `prometheus_client` có cả hai, và middleware trong `demo/p10_metrics.py` nạp dữ liệu cho chúng:

```python
REQUESTS = Counter(
    "http_requests_total", "Requests served", ["method", "route", "status"]
)
LATENCY = Histogram(
    "http_request_duration_seconds",
    "Request latency",
    ["route"],
    buckets=(0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5),
)
```

Các bucket của histogram phải chọn trước: ranh giới là độ phân giải duy nhất bạn nhận lại được. Ở đây chúng chạy từ 10 ms đến 2,5 s. Một middleware ghi mỗi request vào cả hai:

```python
    @app.middleware("http")
    async def measure(request: Request, call_next):
        started = time.perf_counter()
        status = 500
        try:
            response = await call_next(request)
            status = response.status_code
            return response
        finally:
            # The route TEMPLATE ("/cases/{case_id}"), never the raw path:
            # the raw path would mint one time series per case id.
            route = request.scope.get("route")
            label = route.path if route else "unmatched"
            REQUESTS.labels(request.method, label, str(status)).inc()
            LATENCY.labels(label).observe(time.perf_counter() - started)
```

Để ý comment bên trong: label là *template* của route (`/cases/{case_id}/report`), lấy từ `request.scope["route"]` sau khi router đã khớp, không bao giờ là path thô. Path thô chứa case id, và mỗi giá trị khác nhau sẽ thành một time series riêng; cuối mục này cho thấy cái giá. Giờ gửi bốn mươi request report (một trong tám case bị chậm) rồi scrape:

## 4. Trace: dòng thời gian của chính request

Metric cho biết một route chậm. Log cho biết request nào. Cả hai đều không chỉ ra thời gian đi đâu *bên trong* một request đã chạm database và một service khác. **Trace** làm được việc đó: nó là cây các **span** mà một request sinh ra. Mỗi span có tên, thời điểm bắt đầu và kết thúc, một `trace_id` chung cho cả cây, và một `parent_id` trỏ tới span đã gây ra nó.

<BeP10Signals />

**OpenTelemetry** là chuẩn trung lập với vendor để sinh ra chúng. Ở Python có ba loại mảnh: SDK (tạo và export span), exporter (span đi đâu), và các gói instrumentation bọc quanh một thư viện để bạn khỏi tự viết code tạo span. `demo/p10_tracing.py` nối tất cả trong một hàm:

```python
def setup(app: FastAPI, service: str, engine=None) -> None:
    provider = TracerProvider(resource=Resource.create({"service.name": service}))
    # Console exporter: no collector needed. Production would use a
    # BatchSpanProcessor + OTLP exporter instead of printing each span.
    provider.add_span_processor(SimpleSpanProcessor(ConsoleSpanExporter()))
    trace.set_tracer_provider(provider)

    FastAPIInstrumentor.instrument_app(app)
    HTTPXClientInstrumentor().instrument()  # also injects the traceparent header
    if engine is not None:
        SQLAlchemyInstrumentor().instrument(engine=engine)
```

Mỗi dòng làm một việc. `FastAPIInstrumentor.instrument_app(app)` mở một span cho mỗi request. `HTTPXClientInstrumentor` mở một span cho mỗi lời gọi đi ra, và gắn thêm header `traceparent` (định dạng W3C Trace Context) mang trace id, để span của evidence-lab nhập vào cùng trace thay vì tự mở trace mới. `SQLAlchemyInstrumentor` cho engine của bài 5 một span cho mỗi câu SQL. Exporter ở đây là `ConsoleSpanExporter`, chỉ in span ra, nên thử không cần collector. Ở production bạn đổi sang `BatchSpanProcessor` và exporter OTLP: processor đơn giản export từng span ngay trên thread của request, ổn cho demo nhưng là chi phí bạn không muốn trả ở mọi request.

Span tự viết chỉ cách một câu `with`. Tầng service của bài 4 có thêm span quanh mỗi nước đi mà không cần đụng `layered_service.py`:

```python
class ObservedCaseService(CaseService):
    """post 4's service, unchanged, plus a span around each move."""

    def get_case(self, case_id: str) -> CaseRecord:
        with tracer.start_as_current_span("CaseService.get_case"):
            return super().get_case(case_id)

    def assign(self, case_id: str, detective: str) -> CaseRecord:
        with tracer.start_as_current_span("CaseService.assign"):
            return super().assign(case_id, detective)
```

## 5. Debug bằng bằng chứng

Đây là cả bộ đồ nghề dùng thật, trên một lỗi mình cài sẵn vào demo: evidence-lab chậm với một case, C-7 (bộ chứng cứ của nó rất lớn). Không ai báo cho dashboard. Một người dùng nói "trang report thỉnh thoảng chậm".

### Thói quen review

Checklist cho service AI viết tiếp theo, mỗi mục một dòng:

| Nó viết | Hỏi | Cách sửa trong bài |
|---|---|---|
| `print()` hoặc `logging.info(f"...")` trong endpoint | Lọc được theo request, status và thời lượng không? | JSON formatter + middleware access (mục 1) |
| Log có tên user, token hay body | Mình có chịu được cảnh thấy cái này trong index của vendor không? | `RedactFilter`, log id thay vì object (mục 2) |
| Một lời gọi sang service khác | Có chuyển tiếp request id và `traceparent` không? | hook `httpx` + `HTTPXClientInstrumentor` (mục 2, 4) |
| `avg_latency` hay một cái timer đơn | Nó có cho thấy cái đuôi không? | Histogram với bucket tường minh (mục 3) |
| Label kiểu `user_id` hay path thô | Label này nhận được bao nhiêu giá trị khác nhau? | Template route, tập nhỏ cố định (mục 3) |
| Exporter của trace đặt chế độ in ra | Nó tốn gì trên mỗi request? | `BatchSpanProcessor` + OTLP ở production (mục 4) |

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">
- **Structured log (log có cấu trúc)**: mỗi sự kiện một bản ghi máy đọc được (ở đây là JSON) với các trường giống nhau, để công cụ lọc và đếm được.
- **Correlation id (request id)**: giá trị đóng dấu lên mọi dòng log của một request và được chuyển tiếp tới mọi service nó gọi, để nối được các bản log rời nhau.
- **`ContextVar`**: biến Python mà giá trị thuộc về task hay request context hiện tại, nên code nằm sâu đọc được mà không cần tham số.
- **Counter / histogram**: lần lượt là con số chỉ tăng, và tập số đếm theo bucket giữ được hình dạng của một phân phối.
- **Cardinality (số lượng giá trị phân biệt)**: một label nhận được bao nhiêu giá trị khác nhau. Mỗi giá trị là một time series riêng, nên label không giới hạn làm bộ nhớ phình mãi.
- **Trace / span**: trace là mọi thứ một request gây ra; span là một bước có bấm giờ trong đó, với `parent_id` trỏ tới bước đã gây ra nó.
</Concepts>
