### When a cluster node stops moving without crashing

In 2020, a production `etcd` node froze during snapshot recovery (`etcd-io/etcd#11817`). `store.Restore` took `s.mu.Lock()`, closed its shutdown channel `s.stopc`, and called `s.fifoSched.Stop()` to wait for background compaction jobs to finish. One compaction worker on `fifoSched`, running `compactBarrier`, tried to acquire `s.mu.Lock()` before checking `<-s.stopc`—so `Restore` held the lock waiting for the worker, while the worker blocked on the lock waiting for `Restore`.

In another `etcd` incident (`etcd-io/etcd#10492`), `lessor.Renew` held `le.mu.Lock()` while synchronously writing a lease checkpoint entry through Raft and waiting for it to apply; applying that entry called `le.Checkpoint`, which needed `le.mu.Lock()`. Both bugs compiled, passed unit tests, and had zero data races—yet wedged the server under specific interleavings.

Once you know how to launch goroutines, use channels, and guard state with mutexes, the real bugs move one layer deeper. This post explains four runtime mechanisms behind classic Go concurrency failures:

1. **The GMP scheduler and workload sizing**: how Go maps goroutines onto OS threads, why spawning too many slows down merge sort by `3.7x`, and how to size pools for CPU vs. I/O work.
2. **Data races, race conditions, and the Go Memory Model**: why a clean `go test -race` run still leaves non-deterministic bugs and why buffered vs. unbuffered channels give opposite synchronization guarantees.
3. **Loop variables, `select` randomness, `nil` channels, and `sync.Cond`**: how Go 1.22 changed loop variable capture, why `select` picks ready cases at random, how `ch = nil` stops a 100% CPU spin, and when to broadcast with `sync.Cond`.
4. **Hidden `append` races, `fmt.Sprintf` traps, and lock-ordering deadlocks**: why concurrent `append` can corrupt memory only when capacity has room left, how `String()` deadlocks a mutex, and how `etcd` fixed both races and deadlocks.

<Callout type="note" title="TL;DR">
Go multiplexes cheap goroutines (`G`) across `GOMAXPROCS` logical processors (`P`) and OS threads (`M`), so spawning goroutines around tiny work adds scheduling overhead that loses to plain sequential code. Passing `go test -race` rules out unsynchronized memory writes, not ordering-dependent race conditions or deadlocks. Keep loop-captured variables safe across module versions, disable closed `select` branches by assigning `nil`, use `sync.Cond` for repeated broadcasts, never `append` concurrently to a slice with spare capacity, and never hold a mutex while calling `fmt.Sprintf` on self-locking types or waiting on worker queues that take that mutex.
</Callout>

## Inside the GMP scheduler

Every operating system manages threads in kernel space, where switching from one thread to another saves full CPU registers and jumps between kernel and user mode. Go adds a lighter scheduling layer in user space on top of those OS threads, multiplexing thousands of goroutines without asking the OS kernel for thousands of threads.

Think of a busy shipping depot. The physical loading bays are CPU cores, the licensed truck drivers are OS threads (`M`), and the freight carts packed in the yard are goroutines (`G`). Instead of hiring a new truck driver for every single box, the depot uses `GOMAXPROCS` dispatchers (`P`), each holding a local queue of carts ready to roll onto whatever driver is parked at their bay.

In runtime terminology, three letters run the entire show:

- **G (goroutine)**: the task itself, carrying its instruction pointer and a resizable stack starting around `2 KiB` (versus `1–8 MiB` for a typical OS thread stack). Switching goroutines happens in user space in roughly `200 ns`—about `80–90%` faster than an OS thread context switch.
- **M (machine)**: an actual OS kernel thread managed by the host operating system.
- **P (processor)**: a logical scheduling slot holding a local `[256]G` ring queue and memory cache. By default, `GOMAXPROCS` sets the number of `P`s to the CPU cores visible to the process.

<GoP13GmpScheduler />

Watching how `G`, `M`, and `P` react to I/O explains why a Go server handles tens of thousands of open HTTP connections on a handful of OS threads:

| Event inside running goroutine `G` (on `P0` + `M0`) | What happens to OS thread `M0` | What happens to logical `P0` | Where `G` waits until ready |
| :--- | :--- | :--- | :--- |
| **Network socket wait** (`net.Conn.Read` gets `EAGAIN`) | `M0` stays free and grabs the next `G` from `P0`'s queue | `P0` stays attached to `M0` | `G` parks in the OS `netpoller` (`epoll` / `kqueue`) using `0` OS threads |
| **Blocking disk or Cgo syscall** (`os.ReadFile`) | `M0` sleeps inside the OS kernel waiting on disk | Runtime detaches `P0` (`handoffp`) onto another idle or new `M2` | `G` stays parked with `M0` until the syscall returns |
| **`P1`'s local queue runs empty** | Checks global queue every `61` ticks to avoid starvation, then `netpoller` | **Work stealing**: `P1` steals half of `P0`'s local queue | Stolen goroutines run immediately on `P1`'s core |
| **CPU-heavy loop hits ~`10 ms`** | Preemptive signal interrupts the running `G` (since Go 1.14) | Scheduler puts `G` back on the run queue | Other runnable goroutines get a fair turn |

### Why more goroutines can run slower

Cheap is not free. Spawning a goroutine still allocates closure state, initializes a stack, schedules `G` onto a queue, and wakes `sync.WaitGroup` when done. If the work inside each goroutine finishes in a few microseconds, coordination costs far more than the computation itself.

Parallel merge sort makes the trade-off obvious. Splitting a slice recursively down to single elements creates thousands of tiny goroutines just to compare two numbers, whereas stopping parallel splits below a threshold (`2048` elements) lets sequential code run fast in local CPU cache:

```go
func parallelMergesortUnbounded(s []int) {
	if len(s) <= 1 {
		return
	}
	mid := len(s) / 2
	var wg sync.WaitGroup
	wg.Add(1)
	go func() {
		defer wg.Done()
		parallelMergesortUnbounded(s[:mid])
	}()
	parallelMergesortUnbounded(s[mid:])
	wg.Wait()
	merge(s, mid)
}

func parallelMergesortBounded(s []int) {
	if len(s) <= 2048 {
		sequentialMergesort(s)
		return
	}
	mid := len(s) / 2
	var wg sync.WaitGroup
	wg.Add(1)
	go func() {
		defer wg.Done()
		parallelMergesortBounded(s[:mid])
	}()
	parallelMergesortBounded(s[mid:])
	wg.Wait()
	merge(s, mid)
}
```

### Size concurrency by workload type

Choosing how many workers to run—say, in a background job on the `Todo` service—depends on what limits the task:

- **CPU-bound work** (sorting, hashing, compression, JSON marshaling): bound workers near `GOMAXPROCS` (`runtime.GOMAXPROCS(0)`). Prefer `GOMAXPROCS` over `runtime.NumCPU()` because containers or config flags may restrict `GOMAXPROCS` below physical cores; spawning more CPU workers than `P`s just adds goroutine switching overhead.
- **I/O-bound work** (database queries, webhook calls, object storage): workers spend most of their time parked in the `netpoller`, so you can exceed `GOMAXPROCS`. Size the pool to match downstream capacity—like your PostgreSQL connection pool limit or an external API's rate limit—rather than raw core count.

Wait until you run Go in Kubernetes before assuming `GOMAXPROCS` automatically detects container CPU quotas—[Go in production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/) covers container CPU limits and CFS throttling in detail.

<Concepts>

- **Work stealing**: scheduler behavior where an idle logical processor `P` takes half the runnable goroutines from a busy peer's local `[256]G` queue instead of sitting empty.
- **Syscall handoff (`handoffp`)**: detaching a `P` from an `M` blocked on a synchronous OS syscall and attaching it to another `M` so remaining goroutines keep using CPU cores.
- **CPU-bound vs. I/O-bound**: tasks bottlenecked by processor cycles (benefiting from `GOMAXPROCS`-sized worker pools) versus tasks bottlenecked by waiting on network or disk responses.

</Concepts>

## Data races, race conditions, and the memory model

For when to reach for a channel versus a `sync.Mutex`, see [Context and locks](/blog/go-context-timeouts-mutexes/), and for running the race detector in tests, see [Go testing](/blog/go-testing-table-tests/). Here we focus on why a race-free program can still produce wrong results—and what the Go runtime actually guarantees about memory visibility across goroutines.

Think of two cashiers updating a shared paper ledger. If both grab the pen and write over the same line at the exact same moment, the ink smears into garbage—that is a **data race**. If they take turns holding the only pen, every line stays legible, yet the final balance still depends on who got to the desk first—that is a **race condition**.

In Go, a **data race** occurs when two or more goroutines access the same memory address concurrently, at least one access is a write, and no synchronization separates them. Even `i++` compiles down to read, increment, and write steps, so two goroutines running `i++` can both read `0` and overwrite `1`:

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	i := 0
	var wg sync.WaitGroup
	wg.Add(2)
	go func() {
		defer wg.Done()
		i++
	}()
	go func() {
		defer wg.Done()
		i++
	}()
	wg.Wait()
	fmt.Println(i)
}
```

Now guard both writes with `sync.Mutex`, changing the operations to assignments `i = 1` and `i = 2`:

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	i := 0
	var wg sync.WaitGroup
	wg.Add(2)
	go func() {
		defer wg.Done()
		mu.Lock()
		i = 1
		mu.Unlock()
	}()
	go func() {
		defer wg.Done()
		mu.Lock()
		i = 2
		mu.Unlock()
	}()
	wg.Wait()
	fmt.Println(i)
}
```

Running `go run -race main.go` prints `1` or `2` with exit status `0` and zero warnings. Every memory access is serialized behind `mu`, so there is no data race—yet a **race condition** remains because correctness depends on uncontrollable goroutine scheduling order. If your `Todo` service updates a shared task status inside separate critical sections without enforcing step order, `-race` stays completely silent while state transitions occasionally flip backward.

### Happens-before guarantees in the Go Memory Model

Compilers and CPUs reorder instructions and buffer writes in core-local caches. The [Go Memory Model](https://go.dev/ref/mem) defines the exact **happens-before** edges (`A < B`) that force writes from one goroutine to become visible to reads in another:

1. **Goroutine launch vs. exit**: starting `go fn()` happens-before `fn` begins executing, so reading a variable before `go` does not race with writes inside `fn`—but a goroutine exiting creates *no* happens-before edge unless you wait on a channel, `WaitGroup`, or mutex.
2. **Channel send and close**: a send on a channel happens-before the corresponding receive completes, and `close(ch)` happens-before a receive returning the zero value because the channel closed.
3. **Unbuffered vs. buffered receive**: on an **unbuffered** channel (`make(chan struct{})`), a receive happens-before the send on that channel *completes*. On a **buffered** channel (`make(chan struct{}, 1)`), the send completes immediately into the buffer without waiting for the receiver!

Look at how swapping `make(chan struct{}, 1)` for `make(chan struct{})` breaks synchronization even though the code looks nearly identical:

```go
package main

import "fmt"

func main() {
	i := 0
	ch := make(chan struct{}, 1) // buffered: send returns before child receives!
	go func() {
		i = 1
		<-ch
	}()
	ch <- struct{}{}
	fmt.Println(i)
}
```

<Concepts>

- **Happens-before**: a formal ordering guarantee in the Go Memory Model ensuring writes performed before event A are visible to reads occurring after event B.
- **Critical section**: the block of code between `Lock()` and `Unlock()` where only one goroutine may touch shared state at a time.

</Concepts>

## Loop variables in goroutines

For over a decade, Go's `for` loop had one notorious surprise for concurrent code: the loop variable was allocated once outside the iterations and overwritten in place on every step. Spawning a closure goroutine inside a loop meant every goroutine captured the *address* of that single variable, reading whatever final value sat there when the scheduler finally ran them.

Think of handing three couriers the same sticky note on your desk while you cross out the address on it three times. By the time the couriers walk over to read the note, all three see only the last address you wrote.

In [Go 1.22](https://go.dev/blog/loopvar-preview), Go changed `for` loop scoping so each iteration gets its own variable storage whenever a closure captures it—*when* your module's `go.mod` specifies `go 1.22` or higher.

<GoP13LoopVarCapture />

We can verify both behaviors directly on Go 1.27.1 by running the exact same `main.go` with `go 1.21` vs. `go 1.27.1` in `go.mod` and printing both the value and `&v`:

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	items := []int{1, 2, 3}
	var wg sync.WaitGroup
	for _, v := range items {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Printf("%d(%p) ", v, &v)
		}()
	}
	wg.Wait()
	fmt.Println()
}
```

Look at the hex addresses in the real runs: under `go 1.21`, all three goroutines printed `0x6da053d9c030` and failed `-race`; under `go 1.27.1`, each goroutine saw a distinct 8-byte-spaced address (`...030`, `...038`, `...040`) and printed `1`, `2`, `3` cleanly.

Watch out for two traps that **still** bite even in Go 1.22+:

1. **Declaring the loop variable outside the `for` header**: writing `var v int; for _, v = range items` forces one shared variable outside the loop even in Go 1.27.1 (`go run -race .` immediately reports `WARNING: DATA RACE` and prints `3 3 3`).
2. **Legacy `go 1.21` modules**: Go honors the `go` directive in `go.mod` per module so old codebases keep old semantics until upgraded—pass `v` as a goroutine parameter (`go func(id int) { ... }(v)`) or shadow with `v := v` if you still maintain pre-1.22 modules.

<Concepts>

- **Variable capture**: when an inline function literal (closure) binds to a variable from an outer scope rather than copying its value at creation time.
- **Per-iteration scoping**: Go 1.22+ rule that gives variables declared inside a `for` header a fresh instance per loop iteration whenever captured or referenced by address.

</Concepts>

## `select` randomness, `nil` channels, and `sync.Cond`

For channel basics and `select` syntax, see [Goroutines and channels](/blog/go-goroutines-channels-select/); for canceling goroutines cleanly with `context.Context` and `r.Context()`, see [Context and locks](/blog/go-context-timeouts-mutexes/); and for structured worker pools and `errgroup`, see [Go concurrency patterns](/blog/go-concurrency-patterns-worker-pools-pipelines/). Here we cover three subtle behaviors where `select`, channel states, and `sync.Cond` trip up experienced Go teams.

### `select` chooses ready cases uniformly at random

Unlike `switch`, which evaluates cases top-to-bottom, the [Go Language Specification](https://go.dev/ref/spec#Select_statements) guarantees that when multiple `select` cases can proceed at once, Go picks one via **uniform pseudo-random selection**. That prevents a busy upper branch from starving lower channels forever—but breaks any code assuming `case v := <-messageCh` always drains before `case <-disconnectCh`.

Watch what happens when 10 buffered messages and a disconnect signal are already queued:

```go
package main

import "fmt"

### Disabling closed `select` branches with `nil` channels

Reading from a closed channel never blocks—it returns the zero value and `ok == false` immediately on every iteration. Leave a closed channel active inside a `for { select { ... } }` loop merging two streams, and the closed case matches millions of times per second, pinning a CPU core at 100%.

Assigning `nil` to that channel variable flips its behavior completely: sending to or receiving from a `nil` channel **blocks forever**, which tells `select` to skip that branch cleanly while the remaining open channels keep flowing:

```go
package main

import "fmt"

func merge(ch1, ch2 <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for ch1 != nil || ch2 != nil {
			select {
			case v, ok := <-ch1:
				if !ok {
					ch1 = nil
					continue
				}
				out <- v
			case v, ok := <-ch2:
				if !ok {
					ch2 = nil
					continue
				}
				out <- v
			}
		}
	}()
	return out
}

func main() {
	a := make(chan int, 2)
	b := make(chan int, 2)
	a <- 1
	close(a)
	b <- 10
	b <- 20
	close(b)
	for v := range merge(a, b) {
		fmt.Print(v, " ")
	}
	fmt.Println()
}
```

### Repeated broadcasts with `sync.Cond`

Channel closure broadcasts to every waiting goroutine—but only **once** in a channel's lifetime. A normal channel send (`ch <- val`), by contrast, delivers each message to just *one* waiting receiver at a time, splitting updates across listeners.

Suppose two listeners wait on a donation balance—one watching for `$10`, another watching for `$15`—while an updater increments the balance dollar by dollar. If both listeners read from one shared channel, listener 1 may receive `$1, $3, $5, $7, $9, $11` while listener 2 receives `$10`, causing listener 1 to miss `$10` completely!

`sync.Cond` solves repeated multi-listener broadcasts cleanly. It pairs a `sync.Locker` (usually `&sync.Mutex{}`) with a waiter queue:

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type Donation struct {
	cond    *sync.Cond
	balance int
}

func main() {
	d := &Donation{cond: sync.NewCond(&sync.Mutex{})}
	var wg sync.WaitGroup

	listen := func(goal int) {
		defer wg.Done()
		d.cond.L.Lock()
		for d.balance < goal {
			d.cond.Wait()
		}
		fmt.Printf("$%d goal reached (balance=$%d)\n", goal, d.balance)
		d.cond.L.Unlock()
	}

	wg.Add(2)
	go listen(10)
	go listen(15)

	for range 15 {
		time.Sleep(time.Millisecond)
		d.cond.L.Lock()
		d.balance++
		d.cond.L.Unlock()
		d.cond.Broadcast()
	}
	wg.Wait()
}
```

<TerminalOutput command="go run -race main.go" label="Go 1.27.1">
```text
$10 goal reached (balance=$10)
$15 goal reached (balance=$15)
```
</TerminalOutput>

Keep two habits when using `sync.Cond`:

1. **Always wrap `cond.Wait()` in a `for !condition` loop while holding `cond.L.Lock()`**: `Wait()` atomically unlocks `L`, suspends the goroutine, and re-acquires `L` before returning—so looping re-checks `d.balance < goal` safely if multiple waiters wake up at once.
2. **Remember missed broadcasts**: unlike a buffered channel, `Broadcast()` (wake all waiters) and `Signal()` (wake one waiter) do not buffer notifications. If a listener has not entered `Wait()` yet when `Broadcast()` fires, that wakeup is gone—which is why checking the protected state (`d.balance < goal`) *before* calling `Wait()` matters.

<Concepts>

- **Nil channel**: an uninitialized or reassigned `nil` channel value whose send and receive operations block forever, disabling its branch inside `select`.
- **Busy-waiting**: polling or reading a non-blocking closed channel in a tight loop, burning 100% of a CPU core without doing real work.
- **Condition variable (`sync.Cond`)**: a rendezvous point guarding shared state with a `Locker`, letting goroutines sleep via `Wait()` and wake one (`Signal()`) or all (`Broadcast()`) when state changes.

</Concepts>

## `append` races, string formatting, and `etcd` deadlocks

Before diving into `append` races, remember two habits covered earlier: [Go memory](/blog/go-memory-data-types-slices-maps-strings/) explains the 24-byte slice header (`ptr`, `len`, `cap`), and [Context and locks](/blog/go-context-timeouts-mutexes/) shows why you must never copy `sync` types by value and must call `wg.Add` before `go`.

### Hidden data races inside `append`

Calling `append` on a slice looks functional—it returns a new slice header `s1` without changing `s`'s `len`. Yet whether `append` is safe across goroutines depends silently on spare capacity:

```go
// Case 1: len=1, cap=1 (full) -> each goroutine allocates its own backing array
s := make([]int, 1)
go func() { s1 := append(s, 10); fmt.Println("g1:", s1) }()
go func() { s2 := append(s, 20); fmt.Println("g2:", s2) }()

// Case 2: len=0, cap=1 (spare capacity) -> BOTH write backing[0] at once!
s := make([]int, 0, 1)
go func() { s1 := append(s, 10); fmt.Println("g1:", s1) }()
go func() { s2 := append(s, 20); fmt.Println("g2:", s2) }()
```

### Side effects of `fmt.Sprintf` and `String()`

Formatting strings looks read-only, yet calling `fmt.Sprintf` or `fmt.Errorf` under concurrency can trigger both data races and deadlocks:

- **The `etcd` `fmt.Sprintf` context data race (`etcd-io/etcd#7816`)**: `clientv3.(*watcher).Watch` built a map key using `fmt.Sprintf("%v", ctx)`. Formatting a `context.Context` walked its wrapped `WithValue` chain via `String()` and `reflect`, reading mutable trace values (`x/net/trace`) at the same time another goroutine wrote to them—triggering a `DATA RACE` failure in `TestV3ElectionObserve` (`#7811`). The fix wrapped the watch context in a `blankContext` whose `String()` returned a constant string instead of inspecting mutable values.
- **Self-deadlock via `fmt.Stringer` (`Customer` trap)**: Go's `sync.Mutex` and `sync.RWMutex` are **not reentrant**. Look at what happens when `UpdateAge` holds `c.mu.Lock()` and formats `c` with `%v`:

```go
package main

import (
	"fmt"
	"sync"
)

type Customer struct {
	mu  sync.RWMutex
	id  string
	age int
}

func (c *Customer) UpdateAge(age int) error {
	c.mu.Lock()
	defer c.mu.Unlock()
	if age < 0 {
		return fmt.Errorf("negative age for %v", c) // calls c.String() while locked!
	}
	c.age = age
	return nil
}

func (c *Customer) String() string {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return fmt.Sprintf("id=%s age=%d", c.id, c.age)
}

func main() {
	c := &Customer{id: "cust-42", age: 30}
	fmt.Println(c.UpdateAge(-5))
}
```

### Lock-ordering deadlocks in `etcd`

<Figure src={signalBox} alt="Mechanical railway signal box levers at Quorn and Woodhouse" caption="Mechanical interlocking keeps conflicting track levers from locking out of order—just as consistent lock boundaries prevent goroutine deadlock cycles." sourceTitle="Wikimedia Commons: Quorn & Woodhouse signal box" sourceUrl="https://commons.wikimedia.org/wiki/File:Great_Central_Railway_-_signal_box_Quorn_%5E_Woodhouse_-_geograph.org.uk_-_3916232.jpg" />

Both `etcd` deadlocks from the start of this post trace back to the same rule: **never hold a lock across a blocking wait on work that might need the same lock**.

In `etcd-io/etcd#11817`, `store.Restore` held `s.mu.Lock()`, closed `s.stopc`, and blocked inside `s.fifoSched.Stop()` waiting for active workers to drain. Meanwhile, a running compaction task inside `fifoSched` called `compactBarrier`, which attempted `s.mu.Lock()` *before* checking `select { case <-s.stopc: ... }`. Moving `s.mu.Lock()` *inside* the `default:` branch let shutdown workers exit immediately without touching `s.mu`.

Similarly, in `etcd-io/etcd#10492`, `lessor.Renew` stopped holding `le.mu.Lock()` across a synchronous Raft `Checkpoint` call and released `le.mu` before sending the checkpoint to Raft.

| Synchronization tool | Best fit | Main trap to check in review |
| :--- | :--- | :--- |
| **`sync.Mutex`** | Protecting shared structs/maps with frequent writes | Holding lock across `fmt.Sprintf`, Raft/RPC waits, or blocking queues |
| **`sync.RWMutex`** | Read-heavy state (rare writes) | Calling `RLock()` twice on the same goroutine while a writer waits (deadlocks!) |
| **`sync.Cond`** | Repeated 1-to-many broadcasts on changing state | Forgetting the `for !cond` loop or missing wakeups sent before `Wait()` |
| **`sync/atomic`** | Single counters, flags, or pointer swaps | Splitting invariants across *two* independent atomic variables |
| **Channels / `nil` `select`** | Ownership transfer, orchestration, merging streams | Leaving closed channels non-`nil` in `select` (100% CPU spin) |

- **Full slice expression (`s[:len:len]`)**: reslicing syntax that pins capacity to `len`, forcing `append` to allocate a fresh array rather than writing into shared spare capacity.
- **Lock-order inversion**: two goroutines acquiring locks (or waiting on a lock and a queue) in opposite orders, forming a permanent cycle where neither can advance.

## Key takeaways

- **Measure before adding goroutines**: the GMP scheduler handles tens of thousands of network-bound goroutines via `netpoller`, yet spawning goroutines around microsecond work (like single-element merge sort) slows execution by `3.7x`. Size CPU pools near `GOMAXPROCS` and I/O pools to downstream capacity.
- **Never stop checking after `go test -race` passes**: `-race` catches unsynchronized concurrent memory writes (including `append` into shared spare capacity and `make(chan T, 1)` misuse), not logic-level race conditions or deadlocks.
- **Mind loop capture and `select` semantics**: Go 1.22+ gives per-iteration loop variables only inside `for` headers of `go 1.22+` modules; `select` chooses ready branches randomly (drain with an inner `default` loop), and assigning `ch = nil` disables closed branches without spinning CPU.
- **Reach for `sync.Cond` only for repeated broadcasts**: channels broadcast only once via `close(ch)`; `sync.Cond.Broadcast()` wakes all waiting goroutines inside a `for !predicate` loop protected by `cond.L`.
- **Keep blocking waits and `fmt.Sprintf` outside locks**: Go mutexes are non-reentrant—never log `%v` on a locking `Stringer` inside `mu.Lock()`, and never hold a mutex while waiting on Raft or worker schedulers (`etcd#11817`, `etcd#10492`).

### Khi một node cluster đứng im mà không hề crash

Năm 2020, một node `etcd` chạy thật bị treo cứng trong lúc khôi phục snapshot (`etcd-io/etcd#11817`). Hàm `store.Restore` khóa `s.mu.Lock()`, đóng kênh dừng `s.stopc`, rồi gọi `s.fifoSched.Stop()` để đợi các tác vụ compaction đang chạy thoát hết. Ở phía bên kia, chính một worker đang chạy `compactBarrier` trên `fifoSched` lại gọi `s.mu.Lock()` trước khi kiểm tra `<-s.stopc` — thế là `Restore` giữ khóa đợi worker thoát, còn worker đứng đợi khóa của `Restore`.

## Bên trong bộ lập lịch GMP

Mỗi hệ điều hành quản lý thread trong nhân OS (kernel space), nơi việc đổi từ thread này sang thread khác phải lưu toàn bộ thanh ghi CPU và chuyển chế độ qua lại rất tốn công. Go đặt thêm một tầng điều phối nhẹ hơn ở user space ngay phía trên OS thread, ghép hàng chục ngàn goroutine lên vài thread thay vì bắt hệ điều hành gánh hàng chục ngàn thread.

Cứ hình dung một kho hàng bận rộn. Các cửa bốc dỡ là nhân CPU, tài xế xe tải là OS thread (`M`), còn các xe đẩy hàng ngoài sân là goroutine (`G`). Thay vì thuê thêm một tài xế cho mỗi kiện hàng nhỏ, kho chỉ bố trí `GOMAXPROCS` điều phối viên (`P`), mỗi người cầm một hàng đợi cục bộ để đẩy xe hàng lên bất kỳ tài xế nào đang trống ở cửa kho.

Bên trong Go runtime, ba chữ cái điều khiển toàn bộ luồng chạy:

- **G (goroutine)**: tác vụ đang chạy, mang con trỏ lệnh và stack co giãn khởi đầu khoảng `2 KiB` (so với `1–8 MiB` của một OS thread). Việc tráo goroutine diễn ra ở user space hết khoảng `200 ns` — nhanh hơn `80–90%` so với chuyển ngữ cảnh OS thread.
- **M (machine)**: OS thread thật sự do hệ điều hành cấp.
- **P (processor)**: bộ xử lý logic giữ hàng đợi vòng cục bộ `[256]G` và bộ đệm cấp phát bộ nhớ. Mặc định `GOMAXPROCS` đặt số lượng `P` đúng bằng số nhân CPU mà process nhìn thấy.

<GoP13GmpScheduler />

Theo dõi `G`, `M` và `P` trong hai kiểu chờ I/O khác nhau sẽ lý giải vì sao một server Go mở hàng chục ngàn kết nối mạng mà số OS thread vẫn nhỏ gọn:

| Sự kiện trong goroutine `G` (trên `P0` + `M0`) | Chuyện xảy ra với OS thread `M0` | Chuyện xảy ra với `P0` | `G` nằm chờ ở đâu tới lượt? |
| :--- | :--- | :--- | :--- |
| **Chờ socket mạng** (`net.Conn.Read` gặp `EAGAIN`) | `M0` rảnh ngay và bốc `G` tiếp theo trong hàng đợi của `P0` | `P0` giữ nguyên gắn với `M0` | `G` ngủ gọn trong `netpoller` của OS (`epoll` / `kqueue`), tốn `0` OS thread |
| **Syscall đọc đĩa / Cgo chặn đồng bộ** (`os.ReadFile`) | `M0` ngủ thật trong kernel chờ ổ đĩa trả dữ liệu | Runtime tách `P0` (`handoffp`) sang một `M2` rảnh hoặc tạo `M2` mới | `G` chờ cùng `M0` tới khi syscall trả về |
| **Hàng đợi cục bộ của `P1` cạn sạch** | Kiểm tra hàng đợi toàn cục mỗi `61` nhịp để tránh bỏ đói, rồi hỏi `netpoller` | **Trộm việc (work stealing)**: `P1` lấy một nửa số `G` trong hàng đợi của `P0` | Các `G` vừa chuyển sang chạy ngay trên nhân của `P1` |
| **Vòng lặp nặng CPU chạy quá ~`10 ms`** | Tín hiệu ngắt chủ động (preemption, từ Go 1.14) dừng tạm `G` | Bộ lập lịch đẩy `G` về hàng đợi chạy | Các goroutine khác có cơ hội chia sẻ CPU |

### Vì sao tạo thêm goroutine có thể chạy chậm hơn

Nhẹ không có nghĩa là miễn phí. Mở một goroutine vẫn phải cấp phát biến closure, khởi tạo stack, đẩy `G` vào hàng đợi và đánh thức `sync.WaitGroup` khi xong. Nếu việc bên trong chạy hết vài micro giây, tiền công điều phối sẽ lớn hơn hẳn tiền công tính toán.

Bài toán merge sort song song cho thấy rất rõ cái giá đó. Tách đệ quy bằng goroutine xuống tận từng phần tử lẻ sinh ra hàng chục ngàn goroutine chỉ để so sánh hai số, trong khi dừng tách song song dưới ngưỡng `2048` phần tử giúp CPU chạy liền mạch trên cache:

```go
func parallelMergesortUnbounded(s []int) {
	if len(s) <= 1 {
		return
	}
	mid := len(s) / 2
	var wg sync.WaitGroup
	wg.Add(1)
	go func() {
		defer wg.Done()
		parallelMergesortUnbounded(s[:mid])
	}()
	parallelMergesortUnbounded(s[mid:])
	wg.Wait()
	merge(s, mid)
}

func parallelMergesortBounded(s []int) {
	if len(s) <= 2048 {
		sequentialMergesort(s)
		return
	}
	mid := len(s) / 2
	var wg sync.WaitGroup
	wg.Add(1)
	go func() {
		defer wg.Done()
		parallelMergesortBounded(s[:mid])
	}()
	parallelMergesortBounded(s[mid:])
	wg.Wait()
	merge(s, mid)
}
```

### Chỉnh số worker theo đúng loại công việc

Khi mở worker chạy nền — chẳng hạn cho một tác vụ nền trong service `Todo` — hãy dựa vào điểm nghẽn thực tế của tác vụ:

- **Việc nặng CPU (CPU-bound)** (sắp xếp, băm dữ liệu, nén, encode JSON): giữ số worker quanh `GOMAXPROCS` (`runtime.GOMAXPROCS(0)`). Nên lấy `GOMAXPROCS` thay vì `runtime.NumCPU()` vì container hoặc biến môi trường có thể giới hạn `GOMAXPROCS` thấp hơn số nhân vật lý; mở thừa worker chỉ làm các goroutine chen nhau chuyển ngữ cảnh.
- **Việc nặng I/O (I/O-bound)** (truy vấn DB, gọi webhook, đọc S3): đa số thời gian worker nằm chờ trong `netpoller`, nên bạn có thể mở nhiều hơn `GOMAXPROCS`. Hãy chỉnh số worker theo sức chịu tải của hệ thống đích — như giới hạn connection pool của PostgreSQL hay rate limit bên đối tác — thay vì số nhân CPU.

Khi đưa Go vào Kubernetes, đừng mặc định `GOMAXPROCS` tự biết quota CPU của container — bài [Go in production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/) giải thích kỹ phần giới hạn CPU container và hiện tượng CFS throttling.

<Concepts title="Mấy thuật ngữ ở mục này">

- **Trộm việc (work stealing)**: cơ chế một bộ xử lý logic `P` đang rảnh tự lấy một nửa số goroutine trong hàng đợi cục bộ `[256]G` của `P` khác đang bận để giữ CPU luôn chạy đều.
- **Chuyển giao lúc syscall (`handoffp`)**: tách `P` ra khỏi `M` đang kẹt trong syscall đồng bộ của hệ điều hành và gắn sang một `M` khác để các goroutine còn lại không bị đứng chờ theo.
- **CPU-bound vs. I/O-bound**: việc bị chặn bởi tốc độ tính toán của vi xử lý (chỉnh pool theo `GOMAXPROCS`) khác với việc bị chặn bởi thời gian chờ phản hồi từ mạng hay ổ đĩa.

</Concepts>

## Data race, race condition và mô hình bộ nhớ

Để biết khi nào nên chọn channel hay `sync.Mutex`, bạn xem lại bài [Context and locks](/blog/go-context-timeouts-mutexes/), còn cách bật race detector trong test nằm ở bài [Go testing](/blog/go-testing-table-tests/). Ở đây mình tập trung vào lý do một chương trình không có data race vẫn ra kết quả sai — và quy ước đồng bộ bộ nhớ thật sự của Go runtime.

Hãy nghĩ tới hai thu ngân cùng ghi vào một cuốn sổ giấy. Nếu cả hai cùng cầm bút đè lên đúng một dòng tại cùng một lúc, nét chữ nhòe hết không đọc nổi — đó là **data race**. Nếu cả hai biết chuyền nhau đúng một cây bút, chữ viết ra luôn rõ ràng, nhưng tổng kết cuối ngày vẫn phụ thuộc vào việc ai bước tới bàn trước — đó là **race condition**.

Trong Go, **data race** xảy ra khi hai hoặc nhiều goroutine cùng truy cập một ô nhớ, ít nhất một bên ghi, mà không có điểm đồng bộ nào ngăn giữa. Ngay cả phép `i++` cũng tách thành đọc, cộng thêm 1 rồi ghi lại, nên hai goroutine chạy `i++` có thể cùng đọc `0` và cùng ghi đè số `1`:

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	i := 0
	var wg sync.WaitGroup
	wg.Add(2)
	go func() {
		defer wg.Done()
		i++
	}()
	go func() {
		defer wg.Done()
		i++
	}()
	wg.Wait()
	fmt.Println(i)
}
```

		mu.Lock()

Nếu service `Todo` của bạn cập nhật trạng thái một công việc ở hai vùng khóa tách rời mà không ép thứ tự bước, cờ `-race` vẫn báo xanh trong khi dữ liệu thỉnh thoảng nhảy ngược trạng thái.

### Cam kết happens-before trong Go Memory Model

Trình biên dịch và CPU thường đảo thứ tự lệnh hoặc giữ dữ liệu trong cache riêng từng nhân. Tài liệu [Go Memory Model](https://go.dev/ref/mem) quy định rõ các quan hệ **happens-before** (`A < B`) đảm bảo dữ liệu một goroutine ghi ra sẽ nhìn thấy được bên goroutine kia:

1. **Khởi tạo so với thoát goroutine**: lệnh `go fn()` diễn ra trước (happens-before) lúc `fn` bắt đầu chạy, nên đọc biến trước `go` không race với việc ghi trong `fn` — nhưng lúc goroutine thoát thì *không* tạo sẵn quan hệ happens-before nào nếu bạn không đợi qua channel, `WaitGroup` hay mutex.
2. **Gửi và đóng channel**: thao tác gửi vào channel diễn ra trước lúc lệnh nhận tương ứng hoàn tất, và `close(ch)` diễn ra trước lúc lệnh nhận đọc ra zero value do đóng kênh.
3. **Nhận trên unbuffered vs. buffered channel**: trên **unbuffered channel** (`make(chan struct{})`), thao tác nhận diễn ra trước lúc lệnh gửi *hoàn tất*. Ngược lại trên **buffered channel** (`make(chan struct{}, 1)`), lệnh gửi ghi vào buffer xong là trả về ngay không đợi bên nhận!

Hãy xem chỉ việc đổi `make(chan struct{})` thành `make(chan struct{}, 1)` làm hỏng đồng bộ ra sao dù hai đoạn code trông gần giống hệt nhau:

```go
package main

import "fmt"

func main() {
	i := 0
	ch := make(chan struct{}, 1) // có buffer: lệnh gửi xong trước khi goroutine con nhận!
	go func() {
		i = 1
		<-ch
	}()
	ch <- struct{}{}
	fmt.Println(i)
}
```

- **Happens-before**: quy tắc thứ tự trong Go Memory Model bảo đảm mọi thay đổi bộ nhớ làm trước sự kiện A đều hiển thị đầy đủ cho các lệnh đọc sau sự kiện B.

## Biến vòng lặp trong goroutine

Hơn một thập kỷ qua, vòng lặp `for` của Go giữ một cái bẫy kinh điển cho code chạy song song: biến vòng lặp chỉ được cấp phát một chỗ duy nhất và bị ghi đè qua từng lượt. Mở goroutine dùng closure bên trong vòng lặp khiến toàn bộ goroutine giữ chung *địa chỉ* của đúng một biến đó, và lúc chúng chạy thật thì đọc trúng giá trị cuối cùng còn sót lại.

Giống như đưa cho ba người giao hàng xem cùng một tờ giấy ghi chú trên bàn trong khi bạn gạch xóa địa chỉ trên tờ giấy tới ba lần. Lúc cả ba nhìn xuống đọc, ai cũng chỉ thấy mỗi địa chỉ cuối cùng vừa viết.

Từ [Go 1.22](https://go.dev/blog/loopvar-preview), Go đổi phạm vi biến vòng lặp `for` để mỗi lượt lặp có một ô nhớ riêng mỗi khi closure bắt biến đó — *với điều kiện* file `go.mod` của module khai báo `go 1.22` trở lên.

<GoP13LoopVarCapture />

Mình kiểm chứng ngay hai hành vi này trên Go 1.27.1 bằng cách chạy đúng một file `main.go` dưới `go 1.21` rồi đổi sang `go 1.27.1` trong `go.mod`, đồng thời in cả giá trị lẫn địa chỉ `&v`:

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	items := []int{1, 2, 3}
	var wg sync.WaitGroup
	for _, v := range items {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Printf("%d(%p) ", v, &v)
		}()
	}
	wg.Wait()
	fmt.Println()
}
```

- **Bắt biến (variable capture)**: hiện tượng hàm ẩn danh (closure) giữ tham chiếu tới biến ở phạm vi bên ngoài thay vì chụp bản sao giá trị tại thời điểm khởi tạo.
- **Phạm vi từng lượt lặp (per-iteration scoping)**: quy tắc từ Go 1.22 cấp một ô nhớ riêng cho biến khai báo ở đầu câu lệnh `for` ở mỗi vòng lặp nếu biến đó bị closure bắt lại hoặc lấy địa chỉ.

</Concepts>

## Tính ngẫu nhiên của `select`, `nil` channel và `sync.Cond`

Phần cơ bản về channel và `select` nằm ở bài [Goroutines and channels](/blog/go-goroutines-channels-select/); hủy tác vụ qua `context.Context` và `r.Context()` nằm ở bài [Context and locks](/blog/go-context-timeouts-mutexes/); còn worker pool và `errgroup` nằm ở bài [Go concurrency patterns](/blog/go-concurrency-patterns-worker-pools-pipelines/). Dưới đây là ba hành vi dễ gây nhầm lẫn nhất của `select`, channel đóng và `sync.Cond`.

### `select` chọn ngẫu nhiên khi nhiều nhánh cùng sẵn sàng

Khác với `switch` xét từ trên xuống dưới, [đặc tả ngôn ngữ Go](https://go.dev/ref/spec#Select_statements) quy định khi có nhiều nhánh `select` cùng chạy được một lúc, Go sẽ **chọn ngẫu nhiên đều** một nhánh. Cách này tránh cho một nhánh gửi nhanh bỏ đói vĩnh viễn các nhánh bên dưới — nhưng phá hỏng mọi đoạn code tưởng rằng đặt `case v := <-messageCh` lên trên `case <-disconnectCh` sẽ giúp xả hết tin nhắn trước khi thoát.

Thử chạy kịch bản hàng đợi đã chứa sẵn 10 tin nhắn cùng một tín hiệu ngắt:

```go
package main

import "fmt"

func main() {
	messageCh := make(chan int, 10)
	disconnectCh := make(chan struct{}, 1)
	for i := range 10 {
		messageCh <- i
	}
	disconnectCh <- struct{}{}

	for {
		select {
		case v := <-messageCh:
			fmt.Print(v, " ")
		case <-disconnectCh:
			fmt.Println("\ndisconnected")
			return
		}
	}
}
```

Nếu chỉ có một bên gửi, bạn có thể bỏ buffer của `messageCh` hoặc gộp chung tin nhắn và tín hiệu đóng vào một channel để giữ thứ tự FIFO. Nếu nhiều goroutine cùng gửi, hãy đặt một vòng lặp `select` phụ có nhánh `default` bên trong `case <-disconnectCh` để vét sạch tin còn lại trong buffer rồi mới thoát:

```go
case <-disconnectCh:
	for {
		select {
		case v := <-messageCh:
			fmt.Print(v, " ")
		default:
			fmt.Println("\ndisconnected")
			return
		}
	}
```

### Tắt nhánh `select` đã đóng bằng `nil` channel

Đọc từ một channel đã đóng không bao giờ block — nó lập tức trả về zero value kèm `ok == false` ở mỗi lượt lặp. Nếu bạn giữ nguyên một channel đã đóng trong vòng lặp `for { select { ... } }` gộp hai luồng dữ liệu, nhánh đã đóng đó luôn ở trạng thái sẵn sàng và quay hàng triệu vòng mỗi giây, đốt cứng 100% một nhân CPU.

Gán `nil` cho biến channel đổi ngược hoàn toàn chuyện này: gửi hoặc nhận trên `nil` channel sẽ **block vĩnh viễn**, nhờ vậy `select` tự động bỏ qua nhánh đó và ngủ chờ gọn trên các channel còn lại:

```go
package main

import "fmt"

func merge(ch1, ch2 <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for ch1 != nil || ch2 != nil {
			select {
			case v, ok := <-ch1:
				if !ok {
					ch1 = nil
					continue
				}
				out <- v
			case v, ok := <-ch2:
				if !ok {
					ch2 = nil
					continue
				}
				out <- v
			}
		}
	}()
	return out
}

func main() {
	a := make(chan int, 2)
	b := make(chan int, 2)
	a <- 1
	close(a)
	b <- 10
	b <- 20
	close(b)
	for v := range merge(a, b) {
		fmt.Print(v, " ")
	}
	fmt.Println()
}
```

### Phát tín hiệu lặp lại nhiều lần với `sync.Cond`

Đóng channel (`close(ch)`) phát tín hiệu tới toàn bộ goroutine đang chờ — nhưng chỉ phát được **đúng một lần** trong vòng đời channel. Còn gửi qua channel bình thường (`ch <- val`) thì mỗi tin chỉ rơi vào tay *một* goroutine nhận theo lượt, làm các bên nghe chia nhau tin nhắn.

Hãy xét bài toán hai listener cùng theo dõi số tiền quyên góp: một bên đợi mốc `$10`, bên kia đợi mốc `$15`, trong khi updater tăng số dư lên từng đô một. Nếu hai listener cùng đọc chung một channel, bên 1 rất dễ bốc trúng `$1, $3, $5, $7, $9, $11` còn bên 2 bốc trúng `$10` — khiến bên 1 lỡ mất đúng mốc `$10`!

`sync.Cond` sinh ra cho nhu cầu phát tín hiệu lặp đi lặp lại tới nhiều bên chờ. Nó ghép một `sync.Locker` (thường là `&sync.Mutex{}`) với hàng đợi các goroutine đang ngủ chờ trạng thái đổi:

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type Donation struct {
	cond    *sync.Cond
	balance int
}

func main() {
	d := &Donation{cond: sync.NewCond(&sync.Mutex{})}
	var wg sync.WaitGroup

	listen := func(goal int) {
		defer wg.Done()
		d.cond.L.Lock()
		for d.balance < goal {
			d.cond.Wait()
		}
		fmt.Printf("$%d goal reached (balance=$%d)\n", goal, d.balance)
		d.cond.L.Unlock()
	}

	wg.Add(2)
	go listen(10)
	go listen(15)

	for range 15 {
		time.Sleep(time.Millisecond)
		d.cond.L.Lock()
		d.balance++
		d.cond.L.Unlock()
		d.cond.Broadcast()
	}
	wg.Wait()
}
```

<TerminalOutput command="go run -race main.go" label="Go 1.27.1">
```text
$10 goal reached (balance=$10)
$15 goal reached (balance=$15)
```
</TerminalOutput>

Khi dùng `sync.Cond`, nhớ hai thói quen này:

1. **Luôn bọc `cond.Wait()` trong vòng lặp `for !dieuKien` khi đang giữ `cond.L.Lock()`**: hàm `Wait()` tự động nhả khóa `L`, cho goroutine đi ngủ, rồi xin lại khóa `L` trước khi trả về — nên vòng `for` đảm bảo kiểm tra lại `d.balance < goal` mỗi khi được đánh thức.
2. **Lưu ý thông báo không được lưu đệm**: khác với buffered channel, cả `Broadcast()` (đánh thức toàn bộ) lẫn `Signal()` (đánh thức một bên) đều trôi mất nếu lúc gọi chưa có goroutine nào đang đứng ở `Wait()`. Nhờ kiểm tra trạng thái thật (`d.balance < goal`) *trước* khi ngủ, listener sẽ không bỏ lỡ điều kiện đã đạt từ trước.

<Concepts title="Mấy thuật ngữ ở mục này">

- **Nil channel**: biến channel chưa cấp phát hoặc được gán lại bằng `nil`; mọi thao tác gửi và nhận trên nó đều block vĩnh viễn, giúp vô hiệu hóa nhánh tương ứng trong `select`.
- **Quay rỗng (busy-waiting)**: vòng lặp đọc liên tục từ channel đã đóng mà không ngủ, đốt 100% một nhân CPU mà không làm việc hữu ích.
- **Biến điều kiện (`sync.Cond`)**: điểm hẹn gắn với một khóa `Locker`, cho phép goroutine ngủ chờ qua `Wait()` và được gọi dậy một bên (`Signal()`) hoặc tất cả (`Broadcast()`) khi dữ liệu thay đổi.

</Concepts>

## Race khi `append`, bẫy `fmt.Sprintf` và deadlock ở `etcd`

Trước khi đi vào các ca lỗi dưới đây, nhớ lại hai nền tảng đã học ở các bài trước: bài [Go memory](/blog/go-memory-data-types-slices-maps-strings/) giải thích cấu trúc header 24 byte của slice (`ptr`, `len`, `cap`), còn bài [Context and locks](/blog/go-context-timeouts-mutexes/) nhắc quy tắc tuyệt đối không copy các kiểu `sync` theo giá trị và phải gọi `wg.Add` trước `go`.

### Data race ẩn bên trong `append`

Gọi `append` trên một slice nhìn rất vô hại vì nó trả về header slice mới mà không sửa `len` của biến `s` gốc. Nhưng thao tác này có race khi chạy đồng thời hay không lại phụ thuộc ngầm vào việc mảng nền còn chỗ trống hay đã đầy:

```go
// Trường hợp 1: len=1, cap=1 (đầy) -> mỗi goroutine tự cấp phát mảng nền mới
s := make([]int, 1)
go func() { s1 := append(s, 10); fmt.Println("g1:", s1) }()
go func() { s2 := append(s, 20); fmt.Println("g2:", s2) }()

// Trường hợp 2: len=0, cap=1 (còn chỗ trống) -> CẢ HAI ghi đè vào backing[0]!
s := make([]int, 0, 1)
go func() { s1 := append(s, 10); fmt.Println("g1:", s1) }()
go func() { s2 := append(s, 20); fmt.Println("g2:", s2) }()
```

### Tác dụng phụ của `fmt.Sprintf` và `String()`

Format chuỗi trông có vẻ chỉ đọc, nhưng gọi `fmt.Sprintf` hay `fmt.Errorf` trong code chạy song song có thể châm ngòi cho cả data race lẫn deadlock:

- **Ca data race vì `fmt.Sprintf` của `etcd` (`etcd-io/etcd#7816`)**: hàm `clientv3.(*watcher).Watch` ghép key cho map bằng `fmt.Sprintf("%v", ctx)`. Khi format một `context.Context`, gói `fmt` đi dọc chuỗi `WithValue` qua `String()` và `reflect`, đọc nhầm dữ liệu trace có thể thay đổi (`x/net/trace`) đúng lúc một goroutine khác đang cập nhật nó — gây lỗi `DATA RACE` trong `TestV3ElectionObserve` (`#7811`). Bản vá bọc thêm một `blankContext` có `String()` trả về chuỗi cố định thay vì duyệt toàn bộ giá trị trong context.
- **Tự khóa chết vì `fmt.Stringer` (mẫu `Customer`)**: cả `sync.Mutex` lẫn `sync.RWMutex` của Go đều **không khóa lồng lại được**. Hãy xem chuyện gì xảy ra khi `UpdateAge` đang giữ `c.mu.Lock()` rồi format `c` bằng `%v`:

```go
package main

import (
	"fmt"
	"sync"
)

type Customer struct {
	mu  sync.RWMutex
	id  string
	age int
}

func (c *Customer) UpdateAge(age int) error {
	c.mu.Lock()
	defer c.mu.Unlock()
	if age < 0 {
		return fmt.Errorf("negative age for %v", c) // gọi ngầm c.String() khi đang giữ khóa!
	}
	c.age = age
	return nil
}

func (c *Customer) String() string {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return fmt.Sprintf("id=%s age=%d", c.id, c.age)
}

func main() {
	c := &Customer{id: "cust-42", age: 30}
	fmt.Println(c.UpdateAge(-5))
}
```

### Deadlock đảo ngược thứ tự khóa trong `etcd`

<Figure src={signalBox} alt="Trạm gác ghi đường sắt Quorn & Woodhouse điều khiển cần gạt tránh xung đột đường ray" caption="Khóa cơ khí trên trạm ghi không cho hai cần gạt xung đột kéo sai thứ tự — cũng giống kỷ luật ranh giới khóa để tránh vòng deadlock giữa các goroutine." sourceTitle="Wikimedia Commons: Quorn & Woodhouse signal box" sourceUrl="https://commons.wikimedia.org/wiki/File:Great_Central_Railway_-_signal_box_Quorn_%5E_Woodhouse_-_geograph.org.uk_-_3916232.jpg" />

Quay lại hai sự cố `etcd` ở đầu bài, nguyên nhân gốc hoàn toàn giống nhau: **không bao giờ giữ mutex trong lúc đứng đợi một tác vụ chặn có khả năng xin lại chính mutex đó**.

Trong `etcd-io/etcd#11817`, hàm `store.Restore` khóa `s.mu.Lock()`, đóng `s.stopc`, rồi đứng đợi `s.fifoSched.Stop()` cho tới khi mọi job đang chạy kết thúc. Cùng lúc đó, tác vụ compaction chạy bên trong `fifoSched` gọi `compactBarrier` và lại xin `s.mu.Lock()` *trước* khi kiểm tra `select { case <-s.stopc: ... }`. Khi bản vá đưa `s.mu.Lock()` vào sâu trong nhánh `default:` sau bước kiểm tra `<-s.stopc`, worker thoát ngay khi thấy `stopc` đóng mà không đụng tới `s.mu`.

Tương tự trong `etcd-io/etcd#10492`, hàm `lessor.Renew` phải nhả `le.mu` trước khi gửi entry `Checkpoint` sang Raft thay vì ôm khóa đứng đợi vòng apply.

- **Biểu thức cắt lát đầy đủ (full slice expression, `s[:len:len]`)**: cú pháp cắt slice ép `cap` bằng đúng `len`, buộc lệnh `append` tiếp theo phải cấp phát mảng mới thay vì ghi vào phần sức chứa còn thừa.
- **Đảo ngược thứ tự khóa (lock-order inversion)**: tình huống hai goroutine lấy khóa (hoặc một bên giữ khóa đợi hàng đợi, bên trong hàng đợi lại xin khóa) theo chiều ngược nhau, tạo vòng chờ chết đứng cả hai.

## Điểm rút ra (Key takeaways)

- **Đo trước khi tách goroutine**: bộ lập lịch GMP gánh nhẹ nhàng hàng chục ngàn goroutine chờ mạng qua `netpoller`, nhưng rải goroutine cho công việc vài micro giây (như merge sort từng phần tử) khiến bản song song chậm hơn `3.7` lần. Hãy chỉnh pool CPU quanh `GOMAXPROCS` và pool I/O theo sức tải hệ thống đích.
- **Đừng chủ quan khi `go test -race` báo xanh**: cờ `-race` chỉ bắt lỗi ghi đè ô nhớ thiếu đồng bộ (kể cả `append` vào slice còn dư `cap` hay dùng nhầm `make(chan T, 1)`), chứ không phát hiện được race condition ở tầng logic hay deadlock.
- **Để ý biến vòng lặp và hành vi `select`**: cơ chế cấp biến riêng mỗi vòng lặp từ Go 1.22 chỉ áp dụng cho biến khai báo trong đầu `for` của module `go 1.22+`; `select` chọn ngẫu nhiên các nhánh sẵn sàng (cần vòng `select` phụ có `default` để xả hết tin), và gán `ch = nil` là cách tắt gọn nhánh đã đóng mà không tốn CPU.
- **Dùng `sync.Cond` cho phát tin lặp lại nhiều lần**: đóng channel chỉ phát được đúng một lần; `sync.Cond.Broadcast()` đánh thức toàn bộ goroutine đang nằm chờ trong vòng lặp `for !dieuKien` dưới sự bảo vệ của `cond.L`.
- **Đẩy tác vụ chặn và `fmt.Sprintf` ra ngoài vùng khóa**: mutex của Go không khóa lồng lại được — tránh log `%v` lên struct có `String()` khi đang giữ `mu.Lock()`, và đừng ôm mutex đứng đợi Raft hay hàng đợi worker (`etcd#11817`, `etcd#10492`).
