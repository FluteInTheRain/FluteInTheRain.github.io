### A short function that allocates four times the size of its file

*Efficient Go* works one small function through every idea in this post. `Sum` reads a file of integers, one per line, and adds them up. It looks harmless. On a 7.4 MB file with 1,000,000 lines, my first version takes 52 ms and allocates 29.9 MiB per call, about four times the size of the file it reads.

By the end of the post the same job takes 14 ms and 8 KiB on one core, and 4 ms on four cores. Every speed-up below is a [`benchstat`](/blog/go-observability-metrics-microbenchmarks-benchstat/) comparison from real runs on Go 1.27.1, Apple M2. For each step you get what changed, why it helped, and what it cost.

<Callout type="note" title="TL;DR">
Ask "can we skip this work?" before anything else, then walk the Three Rs in order: **Reduce** allocations, **Reuse** memory you own, and only then **Recycle** with `sync.Pool`. A streaming reader with one 8 KiB buffer kept the speed of reading the whole file and cut memory from 7.0 MiB to 8.2 KiB, whatever the file size. To use four cores, give each worker its own byte range of the file; sending every line through one channel made the same job about 9 times slower than one core. `sync.Pool` saved 97.8% of the bytes allocated in this case study and only 2.4% of the time, so measure before you add one.
</Callout>

## Do less work first, then the Three Rs

Every allocation costs twice. You pay when the memory is handed out, and you pay again when the garbage collector has to trace it and free it (post 16 shows how). So the cheapest allocation is the one you never make, and the cheapest work is the work you skip.

*Efficient Go* puts this in an order. Start with **do less work**: remove steps nobody needs. Then the **Three Rs** for memory, as *Efficient Go* tells it, from a FOSDEM 2018 talk by Bryan Boreham: **Reduce** how much you allocate, **Reuse** memory you already hold, **Recycle** what is left through a shared pool or the garbage collector. Each step is riskier than the one before it, which is why the order matters.

<GoP19ThreeRs />

Here is what each step usually looks like in Go code. Pre-sizing a slice with `make([]T, 0, n)` when you know `n` is a **Reduce** move; the [slice header post](/blog/go-memory-data-types-slices-maps-strings/) explains why `append` otherwise keeps reallocating.

| Step | Plain meaning | Typical Go move |
| :--- | :--- | :--- |
| 0. Do less work | Skip work no one needs | Drop a check you never use; do not build a list you only loop over once |
| 1. Reduce | Allocate less | `make([]T, 0, n)` when `n` is known; take a `[]byte` or an `io.Reader` instead of returning a new slice; avoid needless `string(b)` conversions |
| 2. Reuse | One buffer serves many calls | A buffer the caller passes in and owns; `buf = buf[:0]` between uses |
| 3. Recycle | A shared pool of interchangeable objects | `sync.Pool` |

*Efficient Go* also lists garbage-collector help under Recycle: fewer pointers in your structs, and `GOGC` and `GOMEMLIMIT` tuning. Those are in [Go hardware and GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/). This post covers the pool.

<Concepts>

- **Three Rs (Reduce, Reuse, Recycle)**: an order for cutting memory waste. Reduce means allocate less, Reuse means keep and refill one object, Recycle means hand objects back to a shared pool. Try them in that order because each step is riskier than the last.
- **Do less work**: before making work cheaper, ask whether the work is needed at all. It is the only step that has no downside.

</Concepts>

## Set a goal, then build the test and the benchmark

Optimizing without a goal never ends, so write the goals first (post 15 calls them RAER). `Sum` gets three, scaled to this machine:

1. **Time:** at most 20 ns per line on one CPU. For 1,000,000 lines that is 20 ms.
2. **Memory:** the same speed, with at most 10 KB allocated on the heap for any file size.
3. **Four cores:** at most 6 ns per line with four CPUs available.

Here is the first version, `Sum1`. It reads the whole file, splits it into lines with `bytes.Split`, and parses each line with `strconv.ParseInt`:

```go
func Sum1(fileName string) (ret int64, _ error) {
	b, err := os.ReadFile(fileName)
	if err != nil {
		return 0, err
	}
	for _, line := range bytes.Split(b, []byte("\n")) {
		if len(line) == 0 {
			continue
		}
		num, err := strconv.ParseInt(string(line), 10, 64)
		if err != nil {
			return 0, err
		}
		ret += num
	}
	return ret, nil
}
```

`os.ReadFile` returns the whole file as one `[]byte`. `bytes.Split(b, sep)` cuts it at every `sep` and returns a `[][]byte`, one slice per line. `strconv.ParseInt(s, 10, 64)` turns text into an `int64`, in base 10, fitting 64 bits.

Before any speed work comes a test. Every version must give the same answer as a number computed while the input file is written. `TestMain` (about 15 lines, not shown) writes 1,000,000 random integers between −1,000,000 and 999,999, one per line, to a temporary file of 7,389,110 bytes, and keeps their sum in `want`. A small test calls each version and compares it with `want`. The benchmark checks it again on every iteration, so a "faster" version that is wrong cannot sneak through:

```go
func BenchmarkSum(b *testing.B) {
	impls := []struct {
		name string
		fn   func(string) (int64, error)
	}{
		{"Sum1", Sum1}, {"Sum2", Sum2}, {"Sum3", Sum3},
		{"Sum4", Sum4}, {"Sum5", Sum5}, {"Sum6", Sum6}, {"Sum6Pool", Sum6Pool},
	}
	for _, impl := range impls {
		b.Run("impl="+impl.name, func(b *testing.B) {
			for b.Loop() {
				got, err := impl.fn(file)
				if err != nil || got != want {
					b.Fatal(got, err)
				}
			}
		})
	}
}
```

`b.Run` makes a sub-benchmark per version, named `impl=Sum1` and so on. `b.Loop()` is the loop from [Go benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/). I ran the sequential versions with `-cpu 1`, which sets `GOMAXPROCS` to 1 so the garbage collector cannot hide cost on other cores, and `-count 10` so `benchstat` has ten samples per version:

```text
go test -run '^$' -bench 'BenchmarkSum$' -benchmem -count 10 -cpu 1 > seq.txt
```

The file is in the operating system's cache after the first run, so these numbers measure CPU and memory work, not the disk. A cold disk would add a cost that none of these steps can remove.

## From Sum1 to Sum4: remove work, one step at a time

Start from a profile (how to take one is in [Go profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/)). A 3-second CPU profile of `Sum1` says where the time goes: `bytes.Split` takes 36%, `strconv.ParseInt` takes 32%, and the write barrier the garbage collector needs (`gcWriteBarrier`) takes 14%. `bytes.Split` is the biggest piece, so change one thing: the split.

**`Sum1` to `Sum2`: stop building a list of lines.** `bytes.Split` handles any separator and returns 1,000,000 slice headers (24 bytes each, about 22.9 MiB) just so we can loop over them once. We only split on `\n`, so walk the bytes ourselves and parse each line where it sits:

```go
func Sum2(fileName string) (ret int64, _ error) {
	b, err := os.ReadFile(fileName)
	if err != nil {
		return 0, err
	}
	var last int // where the current line starts
	for i := 0; i < len(b); i++ {
		if b[i] != '\n' {
			continue
		}
		num, err := strconv.ParseInt(string(b[last:i]), 10, 64)
		if err != nil {
			return 0, err
		}
		ret += num
		last = i + 1
	}
	return ret, nil
}
```

**`Sum2` to `Sum3`: stop copying each line into a string.** `string(b[last:i])` copies the bytes. The profile of `Sum2` shows `runtime.slicebytetostring` at 9.5%. The table below says 5 allocations per call, not a million, so the copy does not hit the heap: asking the compiler with `-gcflags=-m` prints `string(b[last:i]) does not escape`, which means the copy lives on the stack. It is still a copy. Go 1.20 added `unsafe.String(ptr, len)`, which builds a string that points at the same bytes without copying:

```go
line := b[last:i]
num, err := strconv.ParseInt(unsafe.String(unsafe.SliceData(line), len(line)), 10, 64)
```

`unsafe.SliceData(line)` is a pointer to the first byte. This is a deliberate trade: the string and the slice now share memory, so changing `b` later would change the string too. It is safe here because `b` is never touched after it is read. It is also the kind of code you should be able to justify in a review.

**`Sum3` to `Sum4`: write the parser you need.** The profile of `Sum3` puts `strconv.ParseInt` at 49%. It supports bases 2 to 36, signs, overflow checks and several error cases. We only need base 10 and `int64`. Write that, and parse straight from the bytes, which removes `unsafe` too:

```go
var errSyntax = errors.New("not a valid integer")

// ParseInt parses a base-10 int64 straight from bytes.
func ParseInt(input []byte) (n int64, _ error) {
	factor := int64(1)
	k := 0
	if input[0] == '-' {
		factor *= -1
		k++
	}
	for i := len(input) - 1; i >= k; i-- {
		if input[i] < '0' || input[i] > '9' {
			return 0, errSyntax
		}
		n += factor * int64(input[i]-'0')
		factor *= 10
	}
	return n, nil
}
```

`Sum4` is `Sum2` with `num, err := ParseInt(b[last:i])` in the loop. Here are the four versions side by side. `benchstat` writes `~` when it cannot tell two results apart, and shows the spread (`± 10%`) next to each median. In the command, `benchstat` stands for `go run golang.org/x/perf/cmd/benchstat@latest`:

Read it from left to right. Dropping the split cut time by 55% and memory by 76%. Skipping the string copy added another 11%, with no change in memory. The tailored parser added 32% more and deleted the `unsafe` call, so the final code is both faster and safer than `Sum3`. On the test machine in *Efficient Go* the same four versions took 101, 50, 25 and 14 ms for 2,000,000 lines. The numbers differ, the shape does not.

Goal 1 asked for 20 ms. `Sum2` (23.55 ms) and `Sum3` (21.02 ms) miss it, `Sum4` (14.36 ms) meets it. **Stop there.** More tuning would cost readability for no requirement.

Be honest about what `Sum4` gave up; *Efficient Go* is. `strconv.ParseInt` handles cases our `ParseInt` does not. An empty line makes ours panic with `index out of range [0] with length 0`; `+5` is rejected as a syntax error, where `strconv` accepts it; and `99999999999999999999` overflows silently into `7766279631452241919`, where `strconv` returns an out-of-range error (I ran all three). That is fine when you control the input and wrong when you do not. This is the "trade features for speed" pattern from *Efficient Go*: the cheapest speed-up is often a feature you can live without.

<Concepts>

- **Tailored helper**: a small function that does only what your input needs. Standard-library functions are built for every case (any separator, any base), so on a proven hot path a narrower version can win; elsewhere keep the standard one.
- **`unsafe.String`**: builds a `string` that points at existing bytes without copying them. Fast, but you promise the bytes will not change while the string is alive.
- **`-gcflags=-m`**: asks the compiler to print its escape-analysis decisions, for example `does not escape` for values that stay on the stack (see post 16).

</Concepts>

## Streaming: memory that does not grow with the file

Goal 2 says at most 10 KB on the heap, for any file. `Sum4` allocates 7.0 MiB because `os.ReadFile` loads the whole file. A separate run at 100,000, 1,000,000 and 10,000,000 lines gave `Sum4` 745,864, 7,389,576 and 73,892,232 bytes per call: memory grows with the file. The fix is to read a piece, use it, and read the next piece into the same space. That is **streaming**.

The standard library's way is `bufio.Scanner`, which hands you one line at a time. `Sum5` is the same function with the file opened and read through it:

```go
func Sum5(fileName string) (ret int64, err error) {
	f, err := os.Open(fileName)
	if err != nil {
		return 0, err
	}
	defer f.Close()
	scanner := bufio.NewScanner(f)
	for scanner.Scan() {
		num, err := ParseInt(scanner.Bytes())
		if err != nil {
			return 0, err
		}
		ret += num
	}
	return ret, scanner.Err()
}
```

Its memory is only 4.2 KiB, but it is slower. Writing the loop by hand gets both. `Sum6Reader` reads into a buffer the caller supplies:

```go
func Sum6(fileName string) (ret int64, err error) {
	f, err := os.Open(fileName)
	if err != nil {
		return 0, err
	}
	defer f.Close()
	buf := make([]byte, 8*1024)
	return Sum6Reader(f, buf)
}

func Sum6Reader(r io.Reader, buf []byte) (ret int64, err error) {
	var offset, n int
	for err != io.EOF {
		n, err = r.Read(buf[offset:])
		if err != nil && err != io.EOF {
			return 0, err
		}
		n += offset

		var last int
		for i := range buf[:n] {
			if buf[i] != '\n' {
				continue
			}
			num, err := ParseInt(buf[last:i])
			if err != nil {
				return 0, err
			}
			ret += num
			last = i + 1
		}

		offset = n - last
		if offset > 0 {
			_ = copy(buf, buf[last:n])
		}
	}
	return ret, nil
}
```

`io.Reader` is any value with a `Read(p []byte) (n int, err error)` method; `*os.File` and `strings.Reader` both have one. `Read` fills `p` with up to `len(p)` bytes and says how many it put there. At the end of the input it returns `io.EOF`, which is not a failure here, so the loop treats it as "process what you have, then stop".

The hard part is the end of the buffer. A read stops wherever the buffer is full, which is usually in the middle of a number. The code keeps the unfinished tail: `offset = n - last` is how many bytes follow the last newline, and `copy(buf, buf[last:n])` moves them to the front. The next `Read` writes after them, so the number arrives whole:

<GoP19StreamWindow />

You can watch this with a buffer much smaller than 8 KiB. Same function, a 10-byte buffer, and an input whose numbers do not line up with the buffer. This is a test in the same package as `Sum6Reader`:

```go
func TestSmallBuffer(t *testing.T) {
	sum, err := Sum6Reader(strings.NewReader("12\n345\n6789\n10\n"), make([]byte, 10))
	fmt.Println(sum, err)
}
```

```text
7156 <nil>
```

12 + 345 + 6789 + 10 is 7156, the same answer as reading the whole input at once. The test of every `Sum` version against `want` is what proves the stitching right on the real file.

Now the numbers. `Sum6` reuses a buffer whose size we chose: 8 KiB is small enough to stay in the CPU cache and leaves room under the 10 KB goal.

Streaming costs you something, too. The buffer must be bigger than the longest line, or the loop never finishes. I tried a 4-byte buffer with the input `123456` and the call never returned (the test hit its 5-second timeout), because `buf[offset:]` was empty and `Read` kept returning 0 bytes. `Sum6Reader` assumes no number is longer than about 8,000 digits. State an assumption like that where the next reader will see it.

Passing the buffer in also decides who owns it. `Sum6Reader(r, buf)` allocates nothing itself, so a caller that sums many files can reuse one buffer for all of them. That is the **Reuse** step.

<Concepts>

- **Streaming**: processing input in fixed-size pieces instead of loading it all. Memory stays constant, whatever the input size, as long as each piece can be handled on its own.
- **`io.Reader`**: the interface behind files, network connections and in-memory text. `Read(p)` fills `p` and returns how many bytes it wrote; `io.EOF` means the input ended normally.
- **Chunk boundary**: the place where one read ends and the next begins. Anything that can be cut there, such as a number or a line, must be carried over to the next read.

</Concepts>

## Four cores: sharding beats a worker pool

Goal 3 asks for 6 ns per line with four CPUs. Adding numbers does not care about order: the sum of the first half plus the sum of the second half is the sum of everything. So the work can be split. The question is how. I tried three ways on four cores (`-cpu 4`), each starting from the sequential `Sum4` or `Sum6` code.

**One goroutine per line.** Easy to write, because a goroutine costs little (post 7):

```go
var wg sync.WaitGroup
var last int
for i := 0; i < len(b); i++ {
	if b[i] != '\n' {
		continue
	}
	wg.Add(1)
	go func(line []byte) {
		defer wg.Done()
		num, err := ParseInt(line)
		if err != nil {
			return
		}
		atomic.AddInt64(&ret, num) // add to the shared total without a lock
	}(b[last:i])
	last = i + 1
}
wg.Wait()
```

**A fixed pool fed through one channel.** The pool from [Go concurrency patterns](/blog/go-concurrency-patterns-worker-pools-pipelines/): 4 workers, a feeder that sends every line over a channel, and each worker adding up its own total:

```go
func ConcurrentSum2(fileName string, workers int) (ret int64, _ error) {
	b, err := os.ReadFile(fileName)
	if err != nil {
		return 0, err
	}
	var wg sync.WaitGroup
	workCh := make(chan []byte, 10)
	wg.Add(workers + 1)
	go func() { // the feeder
		var last int
		for i := 0; i < len(b); i++ {
			if b[i] != '\n' {
				continue
			}
			workCh <- b[last:i]
			last = i + 1
		}
		close(workCh)
		wg.Done()
	}()
	for i := 0; i < workers; i++ {
		go func() {
			var sum int64
			for line := range workCh {
				num, err := ParseInt(line)
				if err != nil {
					continue
				}
				sum += num
			}
			atomic.AddInt64(&ret, sum)
			wg.Done()
		}()
	}
	wg.Wait()
	return ret, nil
}
```

**Sharding.** Cut the file into four byte ranges, give each worker one range, and let each worker run the same `Sum6Reader` loop on its own range, with its own 8 KiB buffer. Nothing is shared while they work, and each worker sends one number at the end. The tool is `io.NewSectionReader(r, off, n)`: it returns a reader that sees only `n` bytes of `r` starting at `off`. `r` must be an `io.ReaderAt` (it has `ReadAt(p, off)`, which reads at a position and leaves no shared "current offset"), and `*os.File` is one, so four workers can read different places in the same file at once.

The one subtlety is the cut. Splitting at `size/4` would cut a line in two, so each cut moves forward to the next line start:

```go
// boundary returns the first line start at or after pos.
func boundary(r io.ReaderAt, pos, size int64) int64 {
	if pos <= 0 {
		return 0
	}
	if pos >= size {
		return size
	}
	var one [1]byte
	for p := pos - 1; p < size; p++ {
		if _, err := r.ReadAt(one[:], p); err != nil {
			return size
		}
		if one[0] == '\n' {
			return p + 1
		}
	}
	return size
}

func ConcurrentSum4(fileName string, workers int) (ret int64, err error) {
	f, err := os.Open(fileName)
	if err != nil {
		return 0, err
	}
	defer f.Close()
	s, err := f.Stat()
	if err != nil {
		return 0, err
	}
	size := s.Size()
	per := size / int64(workers)
	resultCh := make(chan int64)
	for i := 0; i < workers; i++ {
		go func(i int) {
			begin := boundary(f, int64(i)*per, size)
			end := size
			if i != workers-1 {
				end = boundary(f, int64(i+1)*per, size)
			}
			r := io.NewSectionReader(f, begin, end-begin)
			sum, _ := Sum6Reader(r, make([]byte, 8*1024))
			resultCh <- sum
		}(i)
	}
	for i := 0; i < workers; i++ {
		ret += <-resultCh
	}
	return ret, nil
}
```

The shown code leaves out two things to keep the idea visible: an error from a worker's `Sum6Reader` is dropped (`sum, _ :=`), and a file that does not end in a newline loses its last line. Real code returns the error through the channel.

The other two lose badly, and the reason is the same: **the work per item is smaller than the cost of coordinating it.** Parsing one line takes about 14 ns. Starting a goroutine, or sending a value through a channel and waking a worker to receive it, costs more than that. A CPU profile of the channel version shows it: the time is in `runtime.schedule`, `runtime.chanrecv` and `runtime.chansend`, and `ParseInt` is not among the top entries. The goroutine-per-line version also allocates about two objects per line (2,000,008 per call).

This does not make worker pools wrong. The pool from post 9 is the right tool when each job is expensive, like an HTTP call or a database query. It is the wrong tool when a job is a few nanoseconds. For cheap work, split the **data** up front and give each worker a large, independent piece. This is what *Efficient Go* calls a coordination-free algorithm, and it needs no lock, no channel per item and no scheduler traffic while the workers run.

Two limits before you copy it. Sharding only helped here because the file was already in the page cache and parsing was the cost; on a cold disk, reading dominates and four workers will mostly wait together. And it only works for work whose pieces really are independent. The sum does not care about order; a running average that needs the previous line would not shard.

<Concepts>

- **Sharding**: splitting the input into independent ranges up front, one per worker, so workers never talk to each other until they report a final result.
- **`io.SectionReader`**: a reader that exposes only a window `[off, off+n)` of an `io.ReaderAt`. Several of them can read different parts of one file at the same time.
- **`io.ReaderAt`**: an interface with `ReadAt(p, off)`, a read at an explicit position. Unlike `Read`, it does not move a shared position, so it is safe to call from several goroutines.
- **Coordination cost**: the time spent handing work to a goroutine (scheduling, locking, waking), which has to be smaller than the work itself for concurrency to pay.

</Concepts>

## sync.Pool: when recycling pays and when it hurts

Everything so far was Reduce and Reuse. The last R is the one people reach for first, which is the problem. The [basic mechanism of `sync.Pool`](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/#three-practical-ways-to-cut-allocations-96) is in post 16: a per-processor cache of interchangeable temporary objects, which you pool as pointers. This section is about its costs.

### A real case: a pool that kept a huge buffer alive

In December 2017 Joe Tsai opened [golang/go issue 23199](https://github.com/golang/go/issues/23199), titled "sync: Pool example suggests incorrect usage". His point was that a pool assumes every entry costs about the same, but the `bytes.Buffer` in the documentation's example can hold anything from a few bytes to hundreds of megabytes. One large request grows a buffer; the buffer goes back to the pool; small requests keep picking it up, and the big allocation stays pinned. As of today the issue is still open.

The standard library takes the point. In Go 1.27.1, `fmt` pools its printer state, and `(*pp).free` in `src/fmt/print.go` (lines 155 to 166) refuses to put back a printer whose buffer grew past 64 KiB, with a comment that names issue 23199. Here is the same idea as a function of your own:

```go
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

func render(w io.Writer, name string) error {
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset() // clear what the last user left behind
	defer func() {
		if buf.Cap() <= 64<<10 { // like fmt: do not keep a huge buffer
			bufPool.Put(buf)
		}
	}()
	fmt.Fprintf(buf, "hello, %s\n", name)
	_, err := w.Write(buf.Bytes())
	return err
}
```

`buf.Reset()` empties the buffer but keeps its memory. Skipping it means the next caller sees the previous caller's bytes. `buf.Cap()` is the size of the memory behind it. Calling `render` twice with a `strings.Builder` as the writer prints:

```text
hello, gopher
hello, pool
```

### Three ways a pool lets you down

**1. You added it, and nothing changed.** The easiest slip is to grow a pooled slice and forget to store the bigger one back, so the pool keeps handing out the small original and every call regrows. I benchmarked a function that appends 1,000,000 bytes: with no reuse, with one static buffer, with a correct pool, and with a pool where the grown slice is not stored back:

```go
var pool = sync.Pool{New: func() any { b := make([]byte, 0, 1<<20); return &b }}

// forgetful: grows the slice but never stores it back in the pool entry.
var poolSmall = sync.Pool{New: func() any { b := make([]byte, 0, 64); return &b }}

func fill(buf []byte) []byte {
	buf = buf[:0]
	for i := 0; i < 1_000_000; i++ {
		buf = append(buf, 'a')
	}
	return buf
}

func BenchmarkFill(b *testing.B) {
	b.Run("impl=alloc", func(b *testing.B) {
		for b.Loop() {
			sink = len(fill(nil))
		}
	})
	b.Run("impl=static", func(b *testing.B) {
		buf := make([]byte, 0, 1<<20)
		for b.Loop() {
			sink = len(fill(buf))
		}
	})
	b.Run("impl=pool", func(b *testing.B) {
		for b.Loop() {
			bp := pool.Get().(*[]byte)
			*bp = fill(*bp) // store the grown slice back
			sink = len(*bp)
			pool.Put(bp)
		}
	})
	b.Run("impl=pool-forgot-store", func(b *testing.B) {
		for b.Loop() {
			bp := poolSmall.Get().(*[]byte)
			buf := fill(*bp) // grows, but *bp still points at the small array
			sink = len(buf)
			poolSmall.Put(bp)
		}
	})
}
```

(`sink` is a package-level `int` that keeps the compiler from deleting the work, as in post 17.)

**2. The pool empties itself.** The pool may drop anything at any time. After a garbage collection, entries move to a second tier (the "victim" cache); after the next one, they are gone. One processor makes this deterministic, so the program sets `GOMAXPROCS(1)` and counts how often the pool has to make a new buffer:

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	runtime.GOMAXPROCS(1) // one P, so Get always looks in the same place

	created := 0
	pool := sync.Pool{New: func() any {
		created++
		return new([64]byte)
	}}

	a := pool.Get() // pool is empty: New runs
	pool.Put(a)
	b := pool.Get()
	fmt.Println("no GC:        same buffer:", a == b, " New calls:", created)

	pool.Put(b)
	runtime.GC()
	c := pool.Get()
	fmt.Println("after 1 GC:   same buffer:", b == c, " New calls:", created)

	pool.Put(c)
	runtime.GC()
	runtime.GC()
	d := pool.Get()
	fmt.Println("after 2 GCs:  same buffer:", c == d, " New calls:", created)
}
```

```text
no GC:        same buffer: true  New calls: 1
after 1 GC:   same buffer: true  New calls: 1
after 2 GCs:  same buffer: false  New calls: 2
```

I ran it five times and got these three lines every time. With more than one processor, a goroutine can move to another one between `Put` and `Get`, and the buffer may be missed even after one GC, so do not build on the survival of a pooled object: the same program without the `GOMAXPROCS(1)` line printed `false` after one GC in 8 of 10 runs. A microbenchmark never sees this, because it never lets a GC happen between two uses. A real service does. **3. It saved allocations, not time or peak memory.** Apply the pool to the streaming sum. `Sum6Pool` is `Sum6` with the 8 KiB buffer borrowed from a `sync.Pool` of `*[]byte` instead of made on each call:

```go
var sumBufPool = sync.Pool{New: func() any { b := make([]byte, 8*1024); return &b }}

func Sum6Pool(fileName string) (ret int64, err error) {
	f, err := os.Open(fileName)
	if err != nil {
		return 0, err
	}
	defer f.Close()
	bp := sumBufPool.Get().(*[]byte)
	defer sumBufPool.Put(bp)
	return Sum6Reader(f, *bp)
}
```

The bytes allocated fell by almost 98%, and the time barely moved. The 8 KiB buffer was never what made `Sum6` slow: the reads and the parsing are. Pooling it also adds a `Get`, a `Put`, and a pointer type to keep right. *Efficient Go* ran the same experiment at larger scale: a service that sums files of 10 and 100 million lines, tested for five minutes under load with four buffering designs. The version with `sync.Pool` allocated far less in total (about 0.5 GB against 3.3 GB without buffering), yet the version with no buffering had the lowest peak heap, because the garbage collector ran more often. I did not reproduce that load test; I quote its result. The lesson is the one in this case study: pooling cuts allocation work, not necessarily memory, and only a macrobenchmark tells you whether your service gains.

By *Efficient Go*'s account, the pool earns its keep when all four of these hold:

- You reuse large or very many objects, so allocation itself is the cost.
- You do not care about the contents, only about the memory block.
- Several goroutines reuse them, in a number that changes.
- The reuse happens between quick computations, at most one GC cycle apart.

The standard library meets all four: `fmt` formats text in many goroutines, every call is short, every buffer is the same kind. In the HTTP service from [post 10](/blog/go-http-service-net-http-json-middleware/), `writeJSON` should not get a pool until a profile shows its allocations are the cost.

<Concepts>

- **Victim cache**: a second tier inside `sync.Pool`. At each garbage collection the pool's entries move into it, and the next collection discards them. This gives idle buffers one more cycle to be reused before they are freed.
- **Pooling vs caching**: a pool holds interchangeable blocks, and you do not care which one you get. A cache maps keys to specific values and keeps them. Never use a `sync.Pool` for something that must survive, such as a connection or a login session.
- **Static buffer**: a buffer your code owns for a fixed number of users. When the count of users is known, it is simpler than a pool and cannot disappear.

</Concepts>

## Key takeaways

- **Do less work before anything else.** Cutting the list of lines (`Sum2`) and the generic parser (`Sum4`) took the job from 52.07 ms to 14.36 ms with no concurrency and no pool.
- **Profile, change one thing, compare.** Each step above came from the biggest entry in a profile and a `benchstat` table; the unsafe step gave 11% and was deleted by the next one.
- **Tailored code has a price.** `Sum4` panics on an empty line and `Sum6Reader` loops forever on a line longer than its buffer. Write those assumptions down.
- **Stream to get constant memory.** One caller-owned 8 KiB buffer kept the speed of `Sum4` and used 8,376 bytes per call at 100,000 and at 10,000,000 lines.
- **Shard cheap work; do not queue it.** One goroutine per line was 1686% slower and a channel-fed pool 787% slower than one core, because the work per line (about 14 ns) is smaller than the coordination. Four independent byte ranges were about 3 times faster.
- **A pool saves allocations, not always time or peak memory.** `Sum6Pool` cut allocated bytes 97.8% and time 2.4%. Reset what you borrow, cap what you return, and never rely on an object surviving a GC.

## Làm ít việc trước, rồi mới tới Three Rs

Mỗi lần cấp phát tốn hai lần. Bạn trả khi vùng nhớ được cấp ra, rồi trả lần nữa khi garbage collector phải duyệt và giải phóng nó (bài 16 cho thấy cách). Nên cấp phát rẻ nhất là cái bạn không làm, và việc rẻ nhất là việc bạn bỏ qua.

*Efficient Go* xếp những ý này theo thứ tự. Bắt đầu bằng **do less work** (làm ít việc hơn): bỏ những bước không ai cần. Rồi tới **Three Rs** cho bộ nhớ, theo lời sách kể về bài nói của Bryan Boreham ở FOSDEM 2018: **Reduce** lượng bạn cấp phát, **Reuse** vùng nhớ bạn đang giữ, **Recycle** phần còn lại qua một pool dùng chung hoặc qua garbage collector. Bước sau rủi ro hơn bước trước, nên thứ tự quan trọng.

<GoP19ThreeRs />

Mỗi bước thường trông thế này trong code Go. Chuẩn bị sẵn dung lượng slice bằng `make([]T, 0, n)` khi biết `n` là một nước **Reduce**; [bài về slice header](/blog/go-memory-data-types-slices-maps-strings/) giải thích vì sao nếu không thì `append` cứ phải cấp phát lại.

| Bước | Nghĩa đơn giản | Nước đi thường gặp trong Go |
| :--- | :--- | :--- |
| 0. Do less work | Bỏ việc không ai cần | Bỏ một phép kiểm tra không dùng; đừng dựng danh sách chỉ để duyệt một lần |
| 1. Reduce | Cấp phát ít hơn | `make([]T, 0, n)` khi biết `n`; nhận `[]byte` hoặc `io.Reader` thay vì trả về slice mới; tránh `string(b)` thừa |
| 2. Reuse | Một buffer phục vụ nhiều lần gọi | Buffer do bên gọi truyền vào và sở hữu; `buf = buf[:0]` giữa các lần dùng |
| 3. Recycle | Pool dùng chung các object hoán đổi được | `sync.Pool` |

*Efficient Go* cũng xếp việc giúp garbage collector vào Recycle: ít con trỏ hơn trong struct, chỉnh `GOGC` và `GOMEMLIMIT`. Phần đó nằm ở [Go hardware and GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/). Bài này nói về pool.

<Concepts>

- **Three Rs (Reduce, Reuse, Recycle)**: một thứ tự để giảm lãng phí bộ nhớ. Reduce là cấp phát ít hơn, Reuse là giữ và nạp lại một object, Recycle là trả object về pool dùng chung. Thử theo thứ tự đó vì bước sau rủi ro hơn bước trước.
- **Do less work**: trước khi làm một việc rẻ đi, hãy hỏi việc đó có cần không. Đây là bước duy nhất không có mặt trái.

</Concepts>

## Đặt mục tiêu, rồi dựng test và benchmark

Tối ưu mà không có mục tiêu thì không bao giờ dừng, nên viết mục tiêu trước (bài 15 gọi là RAER). `Sum` có ba mục tiêu, tính theo máy này:

1. **Thời gian:** tối đa 20 ns mỗi dòng trên một CPU. Với 1.000.000 dòng là 20 ms.
2. **Bộ nhớ:** cùng tốc độ đó, và cấp phát tối đa 10 KB trên heap cho mọi cỡ file.
3. **Bốn nhân:** tối đa 6 ns mỗi dòng khi có bốn CPU.

Đây là phiên bản đầu, `Sum1`. Nó đọc cả file, cắt thành dòng bằng `bytes.Split`, rồi parse từng dòng bằng `strconv.ParseInt`:

```go
func Sum1(fileName string) (ret int64, _ error) {
	b, err := os.ReadFile(fileName)
	if err != nil {
		return 0, err
	}
	for _, line := range bytes.Split(b, []byte("\n")) {
		if len(line) == 0 {
			continue
		}
		num, err := strconv.ParseInt(string(line), 10, 64)
		if err != nil {
			return 0, err
		}
		ret += num
	}
	return ret, nil
}
```

`os.ReadFile` trả cả file thành một `[]byte`. `bytes.Split(b, sep)` cắt nó ở mỗi `sep` và trả về một `[][]byte`, mỗi dòng một slice. `strconv.ParseInt(s, 10, 64)` đổi chữ thành `int64`, hệ thập phân, vừa 64 bit.

Trước khi tăng tốc là phải có test. Mọi phiên bản phải cho đúng đáp án như con số được tính lúc ghi file đầu vào. `TestMain` (khoảng 15 dòng, không hiển thị) ghi 1.000.000 số nguyên ngẫu nhiên từ −1.000.000 đến 999.999, mỗi dòng một số, vào một file tạm 7.389.110 byte, và giữ tổng của chúng trong `want`. Một test nhỏ gọi từng phiên bản và so với `want`. Benchmark kiểm tra lại ở mỗi vòng lặp, nên một bản "nhanh hơn" mà sai thì không lọt được:

```go
func BenchmarkSum(b *testing.B) {
	impls := []struct {
		name string
		fn   func(string) (int64, error)
	}{
		{"Sum1", Sum1}, {"Sum2", Sum2}, {"Sum3", Sum3},
		{"Sum4", Sum4}, {"Sum5", Sum5}, {"Sum6", Sum6}, {"Sum6Pool", Sum6Pool},
	}
	for _, impl := range impls {
		b.Run("impl="+impl.name, func(b *testing.B) {
			for b.Loop() {
				got, err := impl.fn(file)
				if err != nil || got != want {
					b.Fatal(got, err)
				}
			}
		})
	}
}
```

`b.Run` tạo một sub-benchmark cho mỗi phiên bản, tên `impl=Sum1` v.v. `b.Loop()` là vòng lặp trong [Go benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/). Mình chạy các bản tuần tự với `-cpu 1`, đặt `GOMAXPROCS` bằng 1 để garbage collector không giấu chi phí sang các nhân khác, và `-count 10` để `benchstat` có mười mẫu cho mỗi phiên bản:

```text
go test -run '^$' -bench 'BenchmarkSum$' -benchmem -count 10 -cpu 1 > seq.txt
```

Sau lần chạy đầu, file nằm trong cache của hệ điều hành, nên các số này đo công việc của CPU và bộ nhớ, không đo ổ đĩa. Ổ đĩa lạnh sẽ thêm một chi phí mà không bước nào ở đây bỏ được.

## Từ Sum1 đến Sum4: bỏ việc, từng bước một

Bắt đầu từ profile (cách lấy profile ở [Go profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/)). Một CPU profile 3 giây của `Sum1` cho biết thời gian đi đâu: `bytes.Split` chiếm 36%, `strconv.ParseInt` chiếm 32%, và write barrier mà garbage collector cần (`gcWriteBarrier`) chiếm 14%. `bytes.Split` là phần lớn nhất, nên chỉ đổi một thứ: việc cắt.

**`Sum1` sang `Sum2`: thôi dựng danh sách các dòng.** `bytes.Split` xử lý mọi dấu ngăn cách và trả về 1.000.000 slice header (24 byte mỗi cái, khoảng 22,9 MiB) chỉ để ta duyệt qua một lần. Ta chỉ cắt ở `\n`, nên tự đi qua từng byte và parse mỗi dòng tại chỗ:

```go
func Sum2(fileName string) (ret int64, _ error) {
	b, err := os.ReadFile(fileName)
	if err != nil {
		return 0, err
	}
	var last int // where the current line starts
	for i := 0; i < len(b); i++ {
		if b[i] != '\n' {
			continue
		}
		num, err := strconv.ParseInt(string(b[last:i]), 10, 64)
		if err != nil {
			return 0, err
		}
		ret += num
		last = i + 1
	}
	return ret, nil
}
```

**`Sum2` sang `Sum3`: thôi chép mỗi dòng thành string.** `string(b[last:i])` chép các byte. Profile của `Sum2` cho thấy `runtime.slicebytetostring` chiếm 9,5%. Bảng bên dưới ghi 5 lần cấp phát mỗi lần gọi, không phải một triệu, nên bản chép không chạm tới heap: hỏi compiler bằng `-gcflags=-m` ra dòng `string(b[last:i]) does not escape`, nghĩa là bản chép nằm trên stack. Nhưng nó vẫn là một lần chép. Go 1.20 thêm `unsafe.String(ptr, len)`, tạo một string trỏ vào đúng các byte đó mà không chép:

```go
line := b[last:i]
num, err := strconv.ParseInt(unsafe.String(unsafe.SliceData(line), len(line)), 10, 64)
```

`unsafe.SliceData(line)` là con trỏ tới byte đầu tiên. Đây là một đánh đổi có chủ ý: string và slice giờ dùng chung vùng nhớ, nên nếu sau này sửa `b` thì string cũng đổi theo. Ở đây an toàn vì `b` không bị đụng tới sau khi đọc. Đó cũng là loại code mà bạn phải biện minh được khi review.

**`Sum3` sang `Sum4`: viết bộ parse đúng cái bạn cần.** Profile của `Sum3` đặt `strconv.ParseInt` ở mức 49%. Nó hỗ trợ hệ cơ số từ 2 đến 36, dấu, kiểm tra tràn số và nhiều trường hợp lỗi. Ta chỉ cần hệ thập phân và `int64`. Viết đúng cái đó, parse thẳng từ byte, và `unsafe` cũng biến mất:

```go
var errSyntax = errors.New("not a valid integer")

// ParseInt parses a base-10 int64 straight from bytes.
func ParseInt(input []byte) (n int64, _ error) {
	factor := int64(1)
	k := 0
	if input[0] == '-' {
		factor *= -1
		k++
	}
	for i := len(input) - 1; i >= k; i-- {
		if input[i] < '0' || input[i] > '9' {
			return 0, errSyntax
		}
		n += factor * int64(input[i]-'0')
		factor *= 10
	}
	return n, nil
}
```

`Sum4` là `Sum2` với dòng `num, err := ParseInt(b[last:i])` trong vòng lặp. Đây là bốn phiên bản cạnh nhau. `benchstat` in `~` khi không phân biệt được hai kết quả, và hiện độ dao động (`± 10%`) cạnh mỗi trung vị. Trong lệnh, `benchstat` là cách viết gọn của `go run golang.org/x/perf/cmd/benchstat@latest`:

- **`unsafe.String`**: tạo một `string` trỏ vào các byte có sẵn mà không chép. Nhanh, nhưng bạn hứa là các byte đó không đổi khi string còn sống.
- **`-gcflags=-m`**: yêu cầu compiler in các quyết định escape analysis, ví dụ `does not escape` cho giá trị ở lại trên stack (xem bài 16).

## Streaming: bộ nhớ không lớn theo file

Mục tiêu 2 nói tối đa 10 KB trên heap, với mọi file. `Sum4` cấp phát 7,0 MiB vì `os.ReadFile` nạp cả file. Một lần chạy riêng ở 100.000, 1.000.000 và 10.000.000 dòng cho `Sum4` lần lượt 745.864, 7.389.576 và 73.892.232 byte mỗi lần gọi: bộ nhớ lớn theo file. Cách sửa là đọc một đoạn, dùng nó, rồi đọc đoạn kế vào cùng chỗ đó. Đó là **streaming**.

Cách của thư viện chuẩn là `bufio.Scanner`, đưa bạn từng dòng một. `Sum5` là cùng hàm đó, mở file và đọc qua nó:

```go
func Sum5(fileName string) (ret int64, err error) {
	f, err := os.Open(fileName)
	if err != nil {
		return 0, err
	}
	defer f.Close()
	scanner := bufio.NewScanner(f)
	for scanner.Scan() {
		num, err := ParseInt(scanner.Bytes())
		if err != nil {
			return 0, err
		}
		ret += num
	}
	return ret, scanner.Err()
}
```

Bộ nhớ của nó chỉ 4,2 KiB nhưng chậm hơn. Tự viết vòng lặp thì được cả hai. `Sum6Reader` đọc vào một buffer do bên gọi cấp:

```go
func Sum6(fileName string) (ret int64, err error) {
	f, err := os.Open(fileName)
	if err != nil {
		return 0, err
	}
	defer f.Close()
	buf := make([]byte, 8*1024)
	return Sum6Reader(f, buf)
}

func Sum6Reader(r io.Reader, buf []byte) (ret int64, err error) {
	var offset, n int
	for err != io.EOF {
		n, err = r.Read(buf[offset:])
		if err != nil && err != io.EOF {
			return 0, err
		}
		n += offset

		var last int
		for i := range buf[:n] {
			if buf[i] != '\n' {
				continue
			}
			num, err := ParseInt(buf[last:i])
			if err != nil {
				return 0, err
			}
			ret += num
			last = i + 1
		}

		offset = n - last
		if offset > 0 {
			_ = copy(buf, buf[last:n])
		}
	}
	return ret, nil
}
```

`io.Reader` là mọi giá trị có phương thức `Read(p []byte) (n int, err error)`; `*os.File` và `strings.Reader` đều có. `Read` điền vào `p` tối đa `len(p)` byte và cho biết đã ghi bao nhiêu. Hết đầu vào thì nó trả `io.EOF`, ở đây không phải lỗi, nên vòng lặp hiểu là "xử lý phần đang có rồi dừng".

Phần khó là cuối buffer. Một lần đọc dừng ở chỗ buffer đầy, thường là giữa một con số. Code giữ lại phần đuôi chưa xong: `offset = n - last` là số byte nằm sau dấu xuống dòng cuối, và `copy(buf, buf[last:n])` dời chúng lên đầu. Lần `Read` kế ghi vào ngay sau chúng, nên con số đến đủ:

<Concepts>

- **Chunk boundary (ranh giới mảnh)**: chỗ một lần đọc kết thúc và lần kế bắt đầu. Thứ gì có thể bị cắt ở đó, như một số hay một dòng, phải được mang sang lần đọc kế.

## Bốn nhân: chia khúc thắng worker pool

Mục tiêu 3 đòi 6 ns mỗi dòng khi có bốn CPU. Phép cộng không quan tâm thứ tự: tổng nửa đầu cộng tổng nửa sau bằng tổng của tất cả. Nên việc này chia được. Câu hỏi là chia thế nào. Mình thử ba cách trên bốn nhân (`-cpu 4`), mỗi cách xuất phát từ code tuần tự `Sum4` hoặc `Sum6`.

**Một goroutine cho mỗi dòng.** Dễ viết, vì goroutine rẻ (bài 7):

```go
var wg sync.WaitGroup
var last int
for i := 0; i < len(b); i++ {
	if b[i] != '\n' {
		continue
	}
	wg.Add(1)
	go func(line []byte) {
		defer wg.Done()
		num, err := ParseInt(line)
		if err != nil {
			return
		}
		atomic.AddInt64(&ret, num) // add to the shared total without a lock
	}(b[last:i])
	last = i + 1
}
wg.Wait()
```

**Một pool cố định cấp việc qua một channel.** Pool từ [Go concurrency patterns](/blog/go-concurrency-patterns-worker-pools-pipelines/): 4 worker, một goroutine cấp việc gửi mọi dòng qua channel, và mỗi worker tự cộng tổng của nó:

```go
func ConcurrentSum2(fileName string, workers int) (ret int64, _ error) {
	b, err := os.ReadFile(fileName)
	if err != nil {
		return 0, err
	}
	var wg sync.WaitGroup
	workCh := make(chan []byte, 10)
	wg.Add(workers + 1)
	go func() { // the feeder
		var last int
		for i := 0; i < len(b); i++ {
			if b[i] != '\n' {
				continue
			}
			workCh <- b[last:i]
			last = i + 1
		}
		close(workCh)
		wg.Done()
	}()
	for i := 0; i < workers; i++ {
		go func() {
			var sum int64
			for line := range workCh {
				num, err := ParseInt(line)
				if err != nil {
					continue
				}
				sum += num
			}
			atomic.AddInt64(&ret, sum)
			wg.Done()
		}()
	}
	wg.Wait()
	return ret, nil
}
```

**Chia khúc (sharding).** Cắt file thành bốn đoạn byte, cho mỗi worker một đoạn, và để mỗi worker chạy cùng vòng lặp `Sum6Reader` trên đoạn của nó, với buffer 8 KiB riêng. Lúc chạy không có gì dùng chung, và mỗi worker chỉ gửi một con số ở cuối. Công cụ là `io.NewSectionReader(r, off, n)`: nó trả về một reader chỉ nhìn thấy `n` byte của `r` bắt đầu từ `off`. `r` phải là một `io.ReaderAt` (có `ReadAt(p, off)`, đọc tại một vị trí và không để lại "vị trí hiện tại" dùng chung), mà `*os.File` là một ReaderAt, nên bốn worker đọc được bốn chỗ khác nhau của cùng một file cùng lúc.

Điểm tinh tế duy nhất là chỗ cắt. Cắt ở `size/4` sẽ chặt một dòng làm đôi, nên mỗi chỗ cắt dời tới đầu dòng kế tiếp:

```go
// boundary returns the first line start at or after pos.
func boundary(r io.ReaderAt, pos, size int64) int64 {
	if pos <= 0 {
		return 0
	}
	if pos >= size {
		return size
	}
	var one [1]byte
	for p := pos - 1; p < size; p++ {
		if _, err := r.ReadAt(one[:], p); err != nil {
			return size
		}
		if one[0] == '\n' {
			return p + 1
		}
	}
	return size
}

func ConcurrentSum4(fileName string, workers int) (ret int64, err error) {
	f, err := os.Open(fileName)
	if err != nil {
		return 0, err
	}
	defer f.Close()
	s, err := f.Stat()
	if err != nil {
		return 0, err
	}
	size := s.Size()
	per := size / int64(workers)
	resultCh := make(chan int64)
	for i := 0; i < workers; i++ {
		go func(i int) {
			begin := boundary(f, int64(i)*per, size)
			end := size
			if i != workers-1 {
				end = boundary(f, int64(i+1)*per, size)
			}
			r := io.NewSectionReader(f, begin, end-begin)
			sum, _ := Sum6Reader(r, make([]byte, 8*1024))
			resultCh <- sum
		}(i)
	}
	for i := 0; i < workers; i++ {
		ret += <-resultCh
	}
	return ret, nil
}
```

Code ở trên bỏ qua hai thứ để ý tưởng dễ thấy: lỗi từ `Sum6Reader` của worker bị bỏ (`sum, _ :=`), và file không kết thúc bằng xuống dòng sẽ mất dòng cuối. Code thật trả lỗi về qua channel.

Điều này không có nghĩa worker pool là sai. Pool ở bài 9 là công cụ đúng khi mỗi job đắt, như một lời gọi HTTP hay một truy vấn database. Nó là công cụ sai khi một job chỉ tốn vài nano giây. Với việc rẻ, hãy chia **dữ liệu** từ trước và giao mỗi worker một mảnh lớn, độc lập. Đây là cái *Efficient Go* gọi là thuật toán không cần điều phối (coordination-free), và nó không cần lock, không cần channel cho từng phần tử, không có lưu lượng của scheduler trong lúc các worker chạy.

Hai giới hạn trước khi bạn chép lại. Chia khúc chỉ có ích ở đây vì file đã nằm trong page cache và chi phí là parse; với ổ đĩa lạnh thì việc đọc chiếm phần lớn và bốn worker phần nhiều sẽ cùng chờ. Và nó chỉ dùng được cho việc mà các mảnh thực sự độc lập. Phép cộng không quan tâm thứ tự; một trung bình trượt cần dòng trước sẽ không chia khúc được.

<Concepts>

- **Sharding (chia khúc)**: chia đầu vào từ trước thành các đoạn độc lập, mỗi worker một đoạn, để các worker không nói chuyện với nhau cho tới khi báo kết quả cuối.
- **`io.SectionReader`**: reader chỉ để lộ một cửa sổ `[off, off+n)` của một `io.ReaderAt`. Nhiều cái có thể đọc các phần khác nhau của cùng một file cùng lúc.
- **`io.ReaderAt`**: interface có `ReadAt(p, off)`, đọc tại một vị trí chỉ định. Khác với `Read`, nó không dời vị trí dùng chung, nên gọi từ nhiều goroutine là an toàn.
- **Coordination cost (chi phí điều phối)**: thời gian bỏ ra để giao việc cho goroutine (lập lịch, khoá, đánh thức), phải nhỏ hơn bản thân việc thì chạy đồng thời mới có lời.

</Concepts>

## sync.Pool: khi nào tái chế có lợi và khi nào có hại

Đến giờ tất cả mới là Reduce và Reuse. R cuối là cái người ta với tới đầu tiên, và đó chính là vấn đề. [Cơ chế cơ bản của `sync.Pool`](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/#three-practical-ways-to-cut-allocations-96) nằm ở bài 16: một cache theo từng processor chứa các object tạm hoán đổi được, và bạn đưa vào pool bằng con trỏ. Phần này nói về cái giá của nó.

### Một ca thật: pool giữ một buffer khổng lồ sống mãi

Tháng 12 năm 2017, Joe Tsai mở [golang/go issue 23199](https://github.com/golang/go/issues/23199) với tựa "sync: Pool example suggests incorrect usage". Ý của anh là pool giả định mọi phần tử tốn cỡ như nhau, nhưng `bytes.Buffer` trong ví dụ của tài liệu có thể chứa từ vài byte đến hàng trăm megabyte. Một request lớn làm buffer phình ra; buffer được trả về pool; các request nhỏ cứ nhặt lại nó, và vùng cấp phát lớn đó bị ghim lại. Tính đến hôm nay issue vẫn còn mở.

Thư viện chuẩn đã nhận ý đó. Trong Go 1.27.1, `fmt` dùng pool cho trạng thái printer, và `(*pp).free` trong `src/fmt/print.go` (dòng 155 đến 166) từ chối trả về một printer có buffer đã lớn quá 64 KiB, kèm chú thích nêu tên issue 23199. Đây là cùng ý đó thành một hàm của riêng bạn:

```go
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

func render(w io.Writer, name string) error {
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset() // clear what the last user left behind
	defer func() {
		if buf.Cap() <= 64<<10 { // like fmt: do not keep a huge buffer
			bufPool.Put(buf)
		}
	}()
	fmt.Fprintf(buf, "hello, %s\n", name)
	_, err := w.Write(buf.Bytes())
	return err
}
```

`buf.Reset()` làm rỗng buffer nhưng giữ lại vùng nhớ. Bỏ nó thì người dùng sau sẽ thấy các byte của người dùng trước. `buf.Cap()` là cỡ vùng nhớ phía sau. Gọi `render` hai lần với một `strings.Builder` làm writer thì in ra:

```text
hello, gopher
hello, pool
```

### Ba cách pool làm bạn thất vọng

**1. Bạn thêm nó vào mà chẳng có gì đổi.** Lỗi dễ mắc nhất là làm một slice lấy từ pool phình ra rồi quên cất slice lớn hơn trở lại, nên pool cứ đưa ra bản nhỏ ban đầu và mỗi lần gọi lại phải phình lại. Mình benchmark một hàm append 1.000.000 byte: không dùng lại gì, dùng một buffer tĩnh, dùng pool đúng, và dùng pool mà slice đã phình không được cất lại:

```go
var pool = sync.Pool{New: func() any { b := make([]byte, 0, 1<<20); return &b }}

// forgetful: grows the slice but never stores it back in the pool entry.
var poolSmall = sync.Pool{New: func() any { b := make([]byte, 0, 64); return &b }}

	buf = buf[:0]
	for i := 0; i < 1_000_000; i++ {
		buf = append(buf, 'a')
	}
	return buf

		}

		buf := make([]byte, 0, 1<<20)
		for b.Loop() {
			sink = len(fill(buf))
		}
	})
	b.Run("impl=pool", func(b *testing.B) {
		for b.Loop() {
			bp := pool.Get().(*[]byte)
			*bp = fill(*bp) // store the grown slice back
			sink = len(*bp)
			pool.Put(bp)
		}
	})
	b.Run("impl=pool-forgot-store", func(b *testing.B) {
		for b.Loop() {
			bp := poolSmall.Get().(*[]byte)
			buf := fill(*bp) // grows, but *bp still points at the small array
			sink = len(buf)
			poolSmall.Put(bp)
		}
	})
}
```

**2. Pool tự rỗng.** Pool có thể bỏ bất cứ thứ gì, bất cứ lúc nào. Sau một lần garbage collection, các phần tử chuyển sang tầng thứ hai ("victim" cache); sau lần kế tiếp thì mất. Một processor làm điều này xác định được, nên chương trình đặt `GOMAXPROCS(1)` và đếm số lần pool phải tạo buffer mới:

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	runtime.GOMAXPROCS(1) // one P, so Get always looks in the same place

	created := 0
	pool := sync.Pool{New: func() any {
		created++
		return new([64]byte)
	}}

	a := pool.Get() // pool is empty: New runs
	pool.Put(a)
	b := pool.Get()
	fmt.Println("no GC:        same buffer:", a == b, " New calls:", created)

	pool.Put(b)
	runtime.GC()
	c := pool.Get()
	fmt.Println("after 1 GC:   same buffer:", b == c, " New calls:", created)

	pool.Put(c)
	runtime.GC()
	runtime.GC()
	d := pool.Get()
	fmt.Println("after 2 GCs:  same buffer:", c == d, " New calls:", created)
}
```

```text
no GC:        same buffer: true  New calls: 1
after 1 GC:   same buffer: true  New calls: 1
after 2 GCs:  same buffer: false  New calls: 2
```

Mình chạy năm lần và lần nào cũng ra ba dòng này. Khi có nhiều hơn một processor, một goroutine có thể chuyển sang processor khác giữa `Put` và `Get`, và buffer có thể bị lỡ ngay cả sau một lần GC, nên đừng xây gì trên việc object trong pool còn sống: cũng chương trình đó nhưng bỏ dòng `GOMAXPROCS(1)` in `false` sau một lần GC ở 8 trong 10 lần chạy. Microbenchmark không bao giờ thấy điều này, vì nó không để GC xảy ra giữa hai lần dùng. Một service thật thì có. Hãy bấm qua ba trường hợp bên dưới: trúng ô private của processor, tầng victim qua hai lần GC, và một buffer được trả về mà không `Reset`.

**3. Nó tiết kiệm cấp phát, không phải thời gian hay bộ nhớ đỉnh.** Áp pool vào phép cộng streaming. `Sum6Pool` là `Sum6` với buffer 8 KiB mượn từ một `sync.Pool` các `*[]byte` thay vì tạo ở mỗi lần gọi:

```go
var sumBufPool = sync.Pool{New: func() any { b := make([]byte, 8*1024); return &b }}

func Sum6Pool(fileName string) (ret int64, err error) {
	f, err := os.Open(fileName)
	if err != nil {
		return 0, err
	}
	defer f.Close()
	bp := sumBufPool.Get().(*[]byte)
	defer sumBufPool.Put(bp)
	return Sum6Reader(f, *bp)
}
```

Dùng pool còn thêm một `Get`, một `Put` và một kiểu con trỏ phải giữ cho đúng. *Efficient Go* chạy cùng thí nghiệm ở quy mô lớn hơn: một service cộng các file 10 và 100 triệu dòng, thử năm phút dưới tải với bốn cách làm buffer. Bản dùng `sync.Pool` cấp phát tổng cộng ít hơn nhiều (khoảng 0,5 GB so với 3,3 GB của bản không buffer), nhưng bản không buffer lại có heap đỉnh thấp nhất, vì garbage collector chạy thường hơn. Mình không tái hiện bài kiểm tra tải đó; mình trích kết quả của nó. Bài học giống bài học của ca này: pool giảm công cấp phát, chưa chắc giảm bộ nhớ, và chỉ macrobenchmark mới cho biết service của bạn có lời không.

Theo lời sách, pool đáng giá khi cả bốn điều sau cùng đúng:

- Bạn dùng lại object lớn hoặc rất nhiều object, nên bản thân việc cấp phát là chi phí.
- Bạn không quan tâm nội dung, chỉ quan tâm khối nhớ.
- Nhiều goroutine dùng lại chúng, với số lượng thay đổi.
- Việc dùng lại xảy ra giữa các phép tính nhanh, cách nhau tối đa một chu kỳ GC.

Thư viện chuẩn thoả cả bốn: `fmt` định dạng chữ trong nhiều goroutine, mỗi lời gọi ngắn, mọi buffer cùng một loại. Trong HTTP service ở [bài 10](/blog/go-http-service-net-http-json-middleware/), `writeJSON` không nên có pool cho tới khi profile cho thấy cấp phát của nó là chi phí.

<Concepts>

- **Victim cache**: tầng thứ hai bên trong `sync.Pool`. Mỗi lần garbage collection, các phần tử của pool chuyển vào đó, và lần collection kế tiếp bỏ chúng đi. Nhờ vậy buffer nhàn rỗi có thêm một chu kỳ để được dùng lại trước khi bị giải phóng.
- **Pooling và caching**: pool chứa các khối hoán đổi được, bạn không quan tâm lấy cái nào. Cache ánh xạ khoá tới giá trị cụ thể và giữ chúng. Đừng bao giờ dùng `sync.Pool` cho thứ phải sống sót, như một connection hay một phiên đăng nhập.
- **Static buffer (buffer tĩnh)**: buffer do code của bạn sở hữu cho một số người dùng cố định. Khi biết số người dùng, nó đơn giản hơn pool và không biến mất.

</Concepts>

## Điểm rút ra (Key takeaways)

- **Làm ít việc trước mọi thứ khác.** Bỏ danh sách các dòng (`Sum2`) và bộ parse tổng quát (`Sum4`) đưa việc từ 52,07 ms xuống 14,36 ms mà không cần chạy đồng thời hay pool.
- **Profile, đổi một thứ, so sánh.** Mỗi bước ở trên đến từ mục lớn nhất trong profile và một bảng `benchstat`; bước unsafe cho 11% và bị bước sau xoá đi.
- **Code may đo có giá.** `Sum4` panic với dòng trống và `Sum6Reader` lặp mãi với dòng dài hơn buffer. Hãy ghi những giả định đó ra.
- **Streaming để bộ nhớ không đổi.** Một buffer 8 KiB do bên gọi sở hữu giữ tốc độ của `Sum4` và dùng 8.376 byte mỗi lần gọi ở 100.000 lẫn 10.000.000 dòng.
- **Chia khúc việc rẻ; đừng xếp hàng nó.** Một goroutine mỗi dòng chậm hơn 1686% và pool qua channel chậm hơn 787% so với một nhân, vì việc cho mỗi dòng (khoảng 14 ns) nhỏ hơn chi phí điều phối. Bốn đoạn byte độc lập nhanh hơn khoảng 3 lần.
- **Pool tiết kiệm cấp phát, không phải lúc nào cũng thời gian hay bộ nhớ đỉnh.** `Sum6Pool` giảm 97,8% byte cấp phát và 2,4% thời gian. Hãy Reset thứ bạn mượn, giới hạn thứ bạn trả, và đừng bao giờ tin object sống qua một lần GC.
