### A program went from 25 seconds to 2.3

In 2011 Russ Cox took a loop-finding benchmark written in Go that ran in 25.20 seconds and used 1,302 MB. He did not rewrite it from a hunch. He captured a profile, fixed the biggest line it showed, captured again, and repeated. The final version ran in 2.29 seconds and used 351 MB: [11 times faster](https://go.dev/blog/pprof), with the same algorithm.

That is the habit this post teaches. When something is slow, your first guess is usually wrong, because the slow part is rarely the part that looks complicated. A **profile** is a table that says which functions the program was running, and how often. You read it, fix the top line, and measure again.

We will profile the `Todo` service from Post 10 under load, in this order:

1. what a profile contains, and how to expose the profiler without opening a hole;
2. the CPU profile: reading the `Top` table and a flame graph (`Flat` against `Cum`);
3. the heap profile: bytes allocated against bytes still alive;
4. waiting time that a CPU profile cannot see, with `fgprof`;
5. comparing two profiles with `-diff_base`, and keeping profiles running all the time.

## What a profile is

A profiler answers one question: while the program ran, which code was it in? Timing every function call would slow the program down a lot. So Go profiles by **sampling**: it interrupts the program about 100 times per second of CPU time, writes down the **call stack** at that instant (the chain of functions that led to the running one), and moves on. After a few seconds you have hundreds of stacks. Count them and you know where the time goes.

<GoP18Sampling />

Two counts come out of every stack, and the rest of the post leans on them:

- **`Flat`**: samples where the function was the one on top of the stack, doing the work itself.
- **`Cum`** (cumulative): samples where the function appeared anywhere in the stack, so its own work plus everything it called.

A function that only calls others has a large `Cum` and a `Flat` near zero. A function that does real work has `Flat` close to its `Cum`.

Go ships several profiles. They share one file format and one tool, `go tool pprof`, so what you learn about reading one carries over to the rest ([Efficient Go](https://www.efficientgo.dev/), Ch. 9; [100 Go Mistakes](https://100go.co/) #98):

| Profile | Answers | Costs / default |
|---|---|---|
| `profile` (CPU) | Which code burns CPU time? | Runs only while you capture it; 30 seconds by default |
| `heap` (and `allocs`) | Which code allocates memory? | Always on, one sample per 512 KB allocated on average |
| `goroutine` | What are all goroutines doing right now? | A snapshot of every goroutine, no sampling |
| `block` | Where do goroutines wait on locks and channels? | Off until you set a rate |
| `mutex` | Which locks are contended? | Off until you set a fraction |

<Concepts>

- **Profile**: a set of sampled call stacks with a number attached to each (CPU time, bytes, wait time).
- **Sampling**: recording a stack every so often instead of timing every call, so the cost stays small enough for a live service.
- **Call stack**: the list of functions currently active, from `main` down to the one running now.
- **`Flat` and `Cum`**: self time of a function, and self time plus everything it called.

</Concepts>

## Expose pprof safely

The `net/http/pprof` package serves the profiles over HTTP. The quick way is a **blank import**, `import _ "net/http/pprof"`. The `_` means "import this package only for its side effects": its `init` function registers handlers on `http.DefaultServeMux`, the global default router. That is fine on a laptop. It is a problem the day some server in your program serves `DefaultServeMux` on a public port, because then anyone can ask for `/debug/pprof/profile?seconds=30` and make your service burn CPU for half a minute.

The fix is to be explicit: build a separate mux with exactly the handlers you want, and serve it on a second listener bound to `127.0.0.1` (the machine itself). Efficient Go recommends the same, an empty mux instead of the global one. We also register `fgprof`, a profiler we use later:

```go
package main

import (
	"log/slog"
	"net/http"
	"net/http/pprof"
	"time"

	"github.com/felixge/fgprof"
)

// serveDebug exposes the profiling endpoints on their own listener.
// The public mux in routes() never sees them.
func serveDebug(log *slog.Logger, addr string) {
	mux := http.NewServeMux()
	mux.HandleFunc("/debug/pprof/", pprof.Index)
	mux.HandleFunc("/debug/pprof/profile", pprof.Profile)
	mux.Handle("/debug/fgprof", fgprof.Handler())

	srv := &http.Server{Addr: addr, Handler: mux, ReadHeaderTimeout: 5 * time.Second}
	log.Info("debug listening", "addr", addr)
	if err := srv.ListenAndServe(); err != nil {
		log.Error("debug server stopped", "err", err)
	}
}
```

Two details. There is no `WriteTimeout` on this server, because a 30-second CPU capture would be cut off by the 10-second timeout from Post 10. And `ReadHeaderTimeout` stays, for the same slow-client reason Post 10 gave.

`fgprof` is a third-party package, so run `go get github.com/felixge/fgprof` once. Then start the debug server from `run()` in Post 10's `main.go`, right after the `srv := &http.Server{...}` block. `getenv` is Post 10's helper for "read an environment variable, or use a default":

```go
go serveDebug(logger, getenv("DEBUG_ADDR", "127.0.0.1:6060"))
```

Build, start, and ask both ports for the pprof index page. `-w "%{http_code}"` tells `curl` to print only the HTTP status:

## Put the Todo service under load

A profile of an idle service is empty. You need traffic that looks like real use. Post 17 showed a load driver for this service; here is the same idea as a complete small program. It sends up to 2,000 requests per second from 8 workers (about 1,400 per second achieved, because the 4 ms ticker drops ticks while a worker is stuck in the 20 ms `/report`). The rate matters for later: when we change the code and profile again, both runs do the same amount of work (16,924 requests against 16,920), so any difference is the code and not the load.

The service needs two small additions first. A `/report` route stands in for a handler that waits on something slow (a database, say). It sleeps for 20 ms. Add the route line inside `routes()` and the handler anywhere in the file:

```go
mux.HandleFunc("GET /report", s.report)

// report stands in for a handler that waits on a slow dependency (a database, say).
func (s *server) report(w http.ResponseWriter, r *http.Request) {
	time.Sleep(20 * time.Millisecond)
	writeJSON(w, http.StatusOK, map[string]string{"status": "ready"})
}
```

The driver first creates 2,000 todos, so `GET /todos` has something real to encode. Then each worker uses a `time.NewTicker` (a channel that delivers one value every 4 ms; `<-tick.C` waits for the next one) to pace itself: 8 workers times 250 requests per second is 2,000 at most. The mix is 10% `POST /todos`, 30% `GET /todos`, 10% `GET /report` and 50% `GET /todos/{id}`:

```go
// Command load drives the Todo service: 8 workers, a fixed duration.
package main

import (
	"bytes"
	"fmt"
	"io"
	"net/http"
	"sort"
	"sync"
	"time"
)

func main() {
	const base = "http://127.0.0.1:8080"
	client := &http.Client{Transport: &http.Transport{MaxIdleConnsPerHost: 8}}

	// Seed 2000 todos so GET /todos has something to encode.
	for i := range 2000 {
		body := fmt.Sprintf(`{"title":"todo number %d"}`, i)
		resp, err := client.Post(base+"/todos", "application/json", bytes.NewReader([]byte(body)))
		if err != nil {
			panic(err)
		}
		io.Copy(io.Discard, resp.Body)
		resp.Body.Close()
	}

	deadline := time.Now().Add(12 * time.Second)
	var mu sync.Mutex
	var lats []time.Duration
	var wg sync.WaitGroup
	for w := range 8 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			var mine []time.Duration
			tick := time.NewTicker(4 * time.Millisecond) // 8 workers x 250/s = 2000 requests/s at most
			defer tick.Stop()
			for i := 0; time.Now().Before(deadline); i++ {
				<-tick.C
				t0 := time.Now()
				var resp *http.Response
				var err error
				switch i % 10 {
				case 0:
					resp, err = client.Post(base+"/todos", "application/json", bytes.NewReader([]byte(`{"title":"load"}`)))
				case 1, 2, 3:
					resp, err = client.Get(base + "/todos")
				case 4:
					resp, err = client.Get(base + "/report")
				default:
					resp, err = client.Get(fmt.Sprintf("%s/todos/%d", base, (i+w)%2000+1))
				}
				if err != nil {
					panic(err)
				}
				io.Copy(io.Discard, resp.Body)
				resp.Body.Close()
				mine = append(mine, time.Since(t0))
			}
			mu.Lock()
			lats = append(lats, mine...)
			mu.Unlock()
		}()
	}
	wg.Wait()
	sort.Slice(lats, func(i, j int) bool { return lats[i] < lats[j] })
	p := func(q float64) time.Duration { return lats[int(float64(len(lats)-1)*q)] }
	fmt.Printf("requests=%d p50=%v p99=%v\n", len(lats), p(0.50), p(0.99))
}
```

Terminal 1 runs the service (`go build -o todo . && ./todo > server.log`). Terminal 2 runs the driver:

<TerminalOutput command="./loadgen" label="Apple M2 · Go 1.27.1" caption="One real run on a laptop where client and server share the CPUs. Numbers move a little on every run.">
```text
requests=16924 p50=404.5µs p99=21.395167ms
```
</TerminalOutput>

`sort.Slice` sorts the latencies so `p(0.99)` can pick the value that 99% of requests were faster than; that value is `p99`, and `p50` is the median. Remember that `p99` of about 21 ms. The service answers most requests in well under a millisecond, so something takes 20 ms or more for about one request in ten. We will find it, and the CPU profile will not be the tool that does.

### Flame graphs

The same data as a picture. `go tool pprof -http=127.0.0.1:8099 cpu-v1.pb.gz` starts a small web server with a viewer; pick **View → Flame Graph**.

<Figure src={todoFlame} alt="The pprof web viewer showing a flame graph of the Todo service CPU profile, with wide boxes for the HTTP serving code and the JSON encoder" caption="The Flame Graph view of cpu-v1.pb.gz in go tool pprof -http. The viewer draws the root at the top and each box's callees below it." />

How to read it:

- **Width is the share of samples**, the `Cum` of that function. The root spans the whole width.
- **Left to right is not time.** A box on the left did not run before a box on the right. Width is all that carries meaning.
- **Callees hang below their caller.** A box with no box below it is where the CPU is spent: its `Flat` is its whole width.
- Look for wide boxes with little below them, not for tall narrow stacks. Depth only means a long chain of calls.

## Heap: allocated or alive?

Memory has two different questions, and the heap profile answers both. Each sample is a stack where memory was allocated. A heap profile stores four numbers per stack, and `-sample_index` picks which one to show:

- `alloc_space` and `alloc_objects`: everything allocated since the process started, even what the garbage collector has already freed.
- `inuse_space` and `inuse_objects`: only what is still alive, as of the last garbage collection.

A number that keeps growing between captures is the signature of a goroutine leak, the problem from [Goroutines and channels](/blog/go-goroutines-channels-select/). `?debug=2` prints every stack in full.

The **block** and **mutex** profiles are off until you turn them on, because they cost extra. Add these two lines to `run()`, before `go serveDebug(...)`, and import `runtime`:

```go
runtime.SetBlockProfileRate(1)     // record every blocking event
runtime.SetMutexProfileFraction(5) // record 1 in 5 lock contentions
```

## Compare profiles, and keep them

A profile you cannot compare is a one-off. Compare two and you can prove a change worked. Back to the `GET /todos` finding: a handler returning 2,000 items on every call is a design choice, and the usual fix is paging. Here is a version that returns the first 100 only (`min` is a built-in that returns the smaller of two numbers):

```go
func (s *store) list() []Todo {
	s.mu.Lock()
	defer s.mu.Unlock()
	n := min(len(s.todos), 100) // first page only
	out := make([]Todo, n)      // a copy, and [] (not null) when empty
	copy(out, s.todos[:n])
	return out
}
```

### Keep profiles running

Everything so far needs you to be there at the right moment. Incidents do not wait for you: a container is killed for using too much memory, the orchestrator starts a fresh one, and the heap you wanted to inspect is gone. **Continuous profiling** captures profiles on a schedule and stores them, so you can go back to the minute before the problem. Efficient Go points to Google-Wide Profiling (2010) as the origin, and to open-source tools such as Parca for the same job. Płotka runs it always on at work with a one-minute interval, keeping a few days of data.

The idea needs no special tool to try. This loop saves a heap profile every minute, using only the endpoint we already built (I ran it with a 2-second sleep to check it writes files):

```text
while true; do
  curl -s -o "heap-$(date +%H%M%S).pb.gz" http://127.0.0.1:6060/debug/pprof/heap
  sleep 60
done
```

Real tools add storage, a UI to pick two points in time and diff them, and often one-click comparison. Watch the overhead: Efficient Go says the standard Go profilers aim to stay under 5% CPU for one process. If that is too much, profile only one replica of many.

<Concepts>

- **`-diff_base`**: show profile B minus profile A as signed numbers, to prove a change helped and did not just move the cost.
- **Delta heap profile**: `/debug/pprof/heap?seconds=N` returns only the allocations made during those N seconds.
- **Continuous profiling**: capturing profiles on a schedule and storing them, so a restart does not erase the evidence.

</Concepts>

## Key takeaways

- **Profile before you change code.** The slow line is rarely the one that looks complicated.
- **Keep `/debug/pprof` off the public port.** Use a separate mux on `127.0.0.1`, and no `WriteTimeout` on it.
- **`Cum` finds the handler, `Flat` finds the line.** A flame graph shows the same thing by width, not by time.
- **`alloc_space` is churn, `inuse_space` is what stays.** Large allocation with a small live heap is a GC cost, not a leak.
- **A CPU profile is blind to waiting.** Use `fgprof` or tracing when latency is high and CPU is low.
- **Prove fixes with `-diff_base`, and keep snapshots.** Compare under the same load, and read latency next to CPU.

### Một chương trình từ 25 giây xuống 2,3 giây

Năm 2011, Russ Cox lấy một benchmark tìm vòng lặp viết bằng Go. Nó chạy mất 25,20 giây và dùng 1.302 MB. Anh không viết lại theo linh cảm. Anh chụp một profile, sửa dòng nặng nhất nó chỉ ra, chụp lại, rồi lặp lại. Bản cuối chạy trong 2,29 giây và dùng 351 MB: [nhanh gấp 11 lần](https://go.dev/blog/pprof), thuật toán vẫn giữ nguyên.

Đó chính là thói quen bài này muốn bạn có. Khi code chậm, đoán thường sai, vì chỗ chậm hiếm khi là chỗ trông phức tạp. **Profile** là một bảng cho biết chương trình đang chạy hàm nào và bao nhiêu lần. Bạn đọc nó, sửa dòng đứng đầu, rồi đo lại.

Mình sẽ profile `Todo` service của Bài 10 khi chịu tải, theo thứ tự này:

1. profile chứa gì, và cách mở profiler mà không mở toang cửa sau;
2. CPU profile: đọc bảng `Top` và flame graph (`Flat` so với `Cum`);
3. heap profile: byte đã cấp phát so với byte còn sống;
4. thời gian chờ mà CPU profile không thấy, bằng `fgprof`;
5. so hai profile bằng `-diff_base`, và để profile chạy liên tục.

## Profile là gì

Profiler trả lời một câu hỏi: trong lúc chạy, chương trình đang ở đoạn code nào? Bấm giờ từng lần gọi hàm sẽ làm chương trình chậm đi đáng kể. Vì vậy Go dùng **lấy mẫu (sampling)**: khoảng 100 lần mỗi giây CPU, runtime ngắt chương trình, ghi lại **call stack** tại khoảnh khắc đó (chuỗi hàm dẫn tới hàm đang chạy), rồi chạy tiếp. Sau vài giây bạn có hàng trăm stack. Đếm chúng là biết thời gian đi đâu.

<GoP18Sampling />

Từ mỗi stack có hai phép đếm, và cả bài dựa vào chúng:

- **`Flat`**: số mẫu mà hàm nằm trên cùng stack, tức tự nó đang làm việc.
- **`Cum`** (cộng dồn): số mẫu mà hàm xuất hiện ở bất kỳ vị trí nào trong stack, tức việc của chính nó cộng mọi thứ nó gọi.

Hàm chỉ gọi hàm khác thì `Cum` lớn còn `Flat` gần bằng không. Hàm làm việc thật thì `Flat` gần bằng `Cum`.

Go có sẵn nhiều profile. Chúng dùng chung một định dạng file và một công cụ, `go tool pprof`, nên cách đọc một profile áp dụng được cho các profile còn lại ([Efficient Go](https://www.efficientgo.dev/), Ch. 9; [100 Go Mistakes](https://100go.co/) #98):

| Profile | Trả lời | Chi phí / mặc định |
|---|---|---|
| `profile` (CPU) | Code nào đốt thời gian CPU? | Chỉ chạy lúc bạn xin capture; mặc định 30 giây |
| `heap` (và `allocs`) | Code nào cấp phát bộ nhớ? | Luôn bật, trung bình một mẫu cho mỗi 512 KB cấp phát |
| `goroutine` | Mọi goroutine đang làm gì lúc này? | Ảnh chụp mọi goroutine, không lấy mẫu |
| `block` | Goroutine chờ lock và channel ở đâu? | Tắt cho tới khi bạn đặt rate |
| `mutex` | Lock nào bị tranh chấp? | Tắt cho tới khi bạn đặt fraction |

<Concepts>

- **Profile**: tập các call stack được lấy mẫu, mỗi stack kèm một con số (thời gian CPU, byte, thời gian chờ).
- **Lấy mẫu (sampling)**: thỉnh thoảng ghi lại một stack thay vì bấm giờ mọi lần gọi, nên chi phí đủ nhỏ để chạy trên service đang sống.
- **Call stack**: danh sách các hàm đang hoạt động, từ `main` xuống hàm đang chạy.
- **`Flat` và `Cum`**: thời gian riêng của hàm, và thời gian riêng cộng mọi thứ nó đã gọi.

</Concepts>

## Mở pprof an toàn

Package `net/http/pprof` phục vụ các profile qua HTTP. Cách nhanh là **blank import**: `import _ "net/http/pprof"`. Dấu `_` nghĩa là "import package này chỉ vì tác dụng phụ": hàm `init` của nó đăng ký handler vào `http.DefaultServeMux`, router mặc định toàn cục. Trên laptop thì ổn. Nhưng nếu một ngày nào đó có server trong chương trình phục vụ `DefaultServeMux` trên cổng public, ai cũng gọi được `/debug/pprof/profile?seconds=30` và bắt service của bạn đốt CPU nửa phút.

Cách sửa là nói rõ: tạo một mux riêng chỉ chứa đúng handler bạn muốn, rồi phục vụ nó trên listener thứ hai gắn với `127.0.0.1` (chính cái máy đó). Efficient Go cũng khuyên vậy, dùng mux rỗng thay vì mux toàn cục. Mình đăng ký luôn `fgprof`, profiler sẽ dùng ở phần sau:

```go
package main

import (
	"log/slog"
	"net/http"
	"net/http/pprof"
	"time"

	"github.com/felixge/fgprof"
)

// serveDebug exposes the profiling endpoints on their own listener.
// The public mux in routes() never sees them.
func serveDebug(log *slog.Logger, addr string) {
	mux := http.NewServeMux()
	mux.HandleFunc("/debug/pprof/", pprof.Index)
	mux.HandleFunc("/debug/pprof/profile", pprof.Profile)
	mux.Handle("/debug/fgprof", fgprof.Handler())

	srv := &http.Server{Addr: addr, Handler: mux, ReadHeaderTimeout: 5 * time.Second}
	log.Info("debug listening", "addr", addr)
	if err := srv.ListenAndServe(); err != nil {
		log.Error("debug server stopped", "err", err)
	}
}
```

## Cho Todo service chịu tải

Profile của service đang nhàn rỗi thì trống trơn. Bạn cần traffic giống dùng thật. Bài 17 có một load driver cho service này; đây là cùng ý tưởng dưới dạng một chương trình nhỏ hoàn chỉnh. Nó gửi tối đa 2.000 request mỗi giây từ 8 worker (thực tế đạt khoảng 1.400 mỗi giây, vì ticker 4 ms bỏ bớt nhịp khi một worker đang kẹt ở `/report` 20 ms). Tốc độ này quan trọng cho phần sau: khi đổi code và profile lại, cả hai lần chạy làm cùng một lượng việc (16.924 request so với 16.920), nên mọi khác biệt đến từ code chứ không phải từ tải.

Trước hết service cần thêm hai thứ nhỏ. Route `/report` đóng vai handler phải chờ thứ gì đó chậm (ví dụ database). Nó ngủ 20 ms. Thêm dòng route vào `routes()` và handler vào chỗ nào trong file cũng được:

```go
mux.HandleFunc("GET /report", s.report)

// report stands in for a handler that waits on a slow dependency (a database, say).
func (s *server) report(w http.ResponseWriter, r *http.Request) {
	time.Sleep(20 * time.Millisecond)
	writeJSON(w, http.StatusOK, map[string]string{"status": "ready"})
}
```

Driver tạo trước 2.000 todo để `GET /todos` có dữ liệu thật mà encode. Sau đó mỗi worker dùng `time.NewTicker` (một channel gửi ra một giá trị sau mỗi 4 ms; `<-tick.C` chờ giá trị tiếp theo) để tự giữ nhịp: 8 worker nhân 250 request mỗi giây là tối đa 2.000. Tỉ lệ request: 10% `POST /todos`, 30% `GET /todos`, 10% `GET /report` và 50% `GET /todos/{id}`:

```go
// Command load drives the Todo service: 8 workers, a fixed duration.
package main

import (
	"bytes"
	"fmt"
	"io"
	"net/http"
	"sort"
	"sync"
	"time"
)

func main() {
	const base = "http://127.0.0.1:8080"
	client := &http.Client{Transport: &http.Transport{MaxIdleConnsPerHost: 8}}

	// Seed 2000 todos so GET /todos has something to encode.
	for i := range 2000 {
		body := fmt.Sprintf(`{"title":"todo number %d"}`, i)
		resp, err := client.Post(base+"/todos", "application/json", bytes.NewReader([]byte(body)))
		if err != nil {
			panic(err)
		}
		io.Copy(io.Discard, resp.Body)
		resp.Body.Close()
	}

	deadline := time.Now().Add(12 * time.Second)
	var mu sync.Mutex
	var lats []time.Duration
	var wg sync.WaitGroup
	for w := range 8 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			var mine []time.Duration
			tick := time.NewTicker(4 * time.Millisecond) // 8 workers x 250/s = 2000 requests/s at most
			defer tick.Stop()
			for i := 0; time.Now().Before(deadline); i++ {
				<-tick.C
				t0 := time.Now()
				var resp *http.Response
				var err error
				switch i % 10 {
				case 0:
					resp, err = client.Post(base+"/todos", "application/json", bytes.NewReader([]byte(`{"title":"load"}`)))
				case 1, 2, 3:
					resp, err = client.Get(base + "/todos")
				case 4:
					resp, err = client.Get(base + "/report")
				default:
					resp, err = client.Get(fmt.Sprintf("%s/todos/%d", base, (i+w)%2000+1))
				}
				if err != nil {
					panic(err)
				}
				io.Copy(io.Discard, resp.Body)
				resp.Body.Close()
				mine = append(mine, time.Since(t0))
			}
			mu.Lock()
			lats = append(lats, mine...)
			mu.Unlock()
		}()
	}
	wg.Wait()
	sort.Slice(lats, func(i, j int) bool { return lats[i] < lats[j] })
	p := func(q float64) time.Duration { return lats[int(float64(len(lats)-1)*q)] }
	fmt.Printf("requests=%d p50=%v p99=%v\n", len(lats), p(0.50), p(0.99))
}
```

## Heap: đã cấp phát hay đang sống?

Bộ nhớ có hai câu hỏi khác nhau, và heap profile trả lời cả hai. Mỗi mẫu là một stack nơi bộ nhớ được cấp phát. Heap profile lưu bốn con số cho mỗi stack, và `-sample_index` chọn con số nào để hiện:

## So sánh profile, và giữ lại chúng

Profile không so sánh được thì chỉ dùng một lần. So hai profile với nhau bạn mới chứng minh được bản sửa có tác dụng. Quay lại phát hiện về `GET /todos`: handler trả 2.000 phần tử mỗi lần gọi là một lựa chọn thiết kế, và cách sửa thường là phân trang. Đây là bản chỉ trả 100 phần tử đầu (`min` là hàm có sẵn, trả về số nhỏ hơn trong hai số):

```go
func (s *store) list() []Todo {
	s.mu.Lock()
	defer s.mu.Unlock()
	n := min(len(s.todos), 100) // first page only
	out := make([]Todo, n)      // a copy, and [] (not null) when empty
	copy(out, s.todos[:n])
	return out
}
```

### Cho profiler chạy liên tục

Mọi thứ ở trên đều cần bạn có mặt đúng lúc. Sự cố thì không chờ bạn: container bị kill vì dùng quá nhiều bộ nhớ, orchestrator bật một cái mới, và cái heap bạn muốn soi đã biến mất. **Continuous profiling** capture profile theo lịch và lưu lại, để bạn quay về phút trước khi sự cố xảy ra. Efficient Go nhắc tới Google-Wide Profiling (2010) như nguồn gốc, và các công cụ mã nguồn mở như Parca cho cùng mục đích. Płotka bật nó thường trực ở chỗ làm với chu kỳ một phút, giữ dữ liệu vài ngày.

Ý tưởng này không cần công cụ đặc biệt để thử. Vòng lặp dưới đây lưu một heap profile mỗi phút, chỉ dùng endpoint ta đã dựng (mình đã chạy nó với `sleep 2` để kiểm tra rằng nó ghi ra file):

```text
while true; do
  curl -s -o "heap-$(date +%H%M%S).pb.gz" http://127.0.0.1:6060/debug/pprof/heap
  sleep 60
done
```

Công cụ thật bổ sung chỗ lưu trữ, giao diện để chọn hai thời điểm rồi diff, và thường có nút so sánh một cú bấm. Hãy để ý chi phí: Efficient Go nói các profiler chuẩn của Go nhắm giữ dưới 5% CPU cho một tiến trình. Nếu vẫn nhiều, chỉ profile một replica trong số nhiều replica.

<Concepts>

- **`-diff_base`**: hiện profile B trừ profile A dưới dạng số có dấu, để chứng minh thay đổi có ích chứ không chỉ chuyển chi phí đi chỗ khác.
- **Heap profile delta**: `/debug/pprof/heap?seconds=N` chỉ trả về các lần cấp phát trong N giây đó.
- **Continuous profiling**: capture profile theo lịch và lưu lại, để khởi động lại không xóa bằng chứng.

</Concepts>

## Điểm rút ra (Key takeaways)

- **Profile trước khi sửa code.** Dòng chậm hiếm khi là dòng trông phức tạp.
- **Giữ `/debug/pprof` khỏi cổng public.** Dùng mux riêng trên `127.0.0.1`, và không đặt `WriteTimeout` cho nó.
- **`Cum` tìm handler, `Flat` tìm dòng code.** Flame graph thể hiện cùng thông tin bằng chiều rộng, không phải bằng thời gian.
- **`alloc_space` là churn, `inuse_space` là phần ở lại.** Cấp phát lớn mà heap sống nhỏ là chi phí GC, không phải rò rỉ.
- **CPU profile mù trước thời gian chờ.** Dùng `fgprof` hoặc tracing khi độ trễ cao mà CPU thấp.
- **Chứng minh bản sửa bằng `-diff_base`, và giữ snapshot.** So sánh dưới cùng một tải, và đọc độ trễ bên cạnh CPU.
