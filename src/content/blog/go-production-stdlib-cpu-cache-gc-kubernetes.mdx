### The service passed every test and still stalled

In August 2019 a Go user opened issue #33803 on the Go repository. Their setup was ordinary: each container had a CPU quota of 4, and the containers ran on machines with 32 processors. Go looked at the machine, saw 32 processors, and started its runtime as if it owned all of them. The container could only use 4 processors' worth of time, so the kernel kept pausing it. Latency suffered, and the issue says the effect was visible in the main body of the latency distribution, not only in the tail. The fix shipped in Go 1.25, in August 2025.

That story is the shape of everything in this post. Your service works on a laptop, where the network is instant, the database is next door and nothing has a CPU limit. In production the network is slow, the database is shared and the container has a ceiling. Go's standard library is friendly on a laptop, and a few of its defaults turn into outages elsewhere.

We will use the `Todo` service from [Build a Go HTTP service](/blog/go-http-service-net-http-json-middleware/) as the running example, and go through six traps.

| Trap | What goes wrong | Where |
|---|---|---|
| A call or a server with no timeout | A goroutine waits for ever on one stuck peer | [section 1](#1-waiting-for-ever-timeouts) |
| A body, rows or file never closed | Connections and file handles run out | [section 2](#2-close-what-you-open) |
| `time.After` in a loop, bare numbers as durations | Memory grows (older Go), or a sleep is a million times too short | [section 3](#3-time-bare-numbers-and-timers) |
| JSON that quietly drops or rounds data | Missing fields, wrong comparisons, rounded IDs | [section 4](#4-json-three-surprises) |
| `database/sql` is a pool, not a connection | Requests queue behind connections nobody returned | [section 5](#5-databasesql-is-a-pool) |
| A container with a CPU limit | The kernel pauses the whole process | [section 6](#6-go-in-containers) |

<Callout type="note" title="TL;DR">
Set a timeout on every client and server: `http.DefaultClient` and `http.ListenAndServe` have none. Read the rest of a response body and close it, close `sql.Rows`, and put `return` after `http.Error`. An embedded `time.Time` takes over a struct's JSON, and numbers decoded into `any` become `float64`. `sql.Open` makes a pool and connects to nothing. In a container, check the `go` line in `go.mod`: from Go 1.25 `GOMAXPROCS` follows the CPU limit, but a CPU limit can still throttle the process.
</Callout>

## 1. Waiting for ever: timeouts

A *timeout* is a limit on how long your code waits for something outside it: a connection, an answer, a client that is slow to send. Go has no hidden global timeout. If you set none, the wait has no end. That is fine on a laptop and dangerous when one upstream service hangs, because each waiting call keeps a goroutine, a socket and some memory alive.

### The default client never gives up

The `net/http` package ships a ready-made client, `http.DefaultClient`, and shortcuts such as `http.Get` that use it. Here is its definition in Go's own source:

<GitHubCode repo="golang/go" path="src/net/http/client.go" lines="L58-L125" url="https://github.com/golang/go/blob/074522c96ce70350453c164ecb17904881106b6a/src/net/http/client.go#L58-L125" caption="http.DefaultClient is just &Client{}. Its Timeout field is zero, and the comment says what that means.">
```go
	// A Timeout of zero means no timeout.
	Timeout time.Duration
}

// DefaultClient is the default [Client] and is used by [Get], [Head], and [Post].
var DefaultClient = &Client{}
```
</GitHubCode>

So `http.Get(url)` waits as long as the other side likes. The program below starts a test server that accepts a request and then sleeps for 3 seconds. `httptest.NewServer` (from [post 10](/blog/go-http-service-net-http-json-middleware/)) gives us that server without any network setup. First we call it with `http.Get` in a goroutine and give up watching after 1 second. Then we call it with our own client that has a `Timeout`.

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func main() {
	// A server that accepts the request and then never answers (it sleeps 3s).
	slow := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(3 * time.Second)
	}))
	defer slow.Close()

	// 1. http.Get uses http.DefaultClient, whose Timeout is 0: wait forever.
	done := make(chan error, 1)
	go func() {
		_, err := http.Get(slow.URL)
		done <- err
	}()
	select {
	case err := <-done:
		fmt.Println("default client returned:", err)
	case <-time.After(1 * time.Second):
		fmt.Println("default client: no answer after 1s, still waiting")
	}

	// 2. Our own client with a deadline for the whole call.
	client := &http.Client{Timeout: 500 * time.Millisecond}
	start := time.Now()
	_, err := client.Get(slow.URL)
	fmt.Printf("own client gave up after %v\n%v\n", time.Since(start).Round(100*time.Millisecond), err)
}
```

`Client.Timeout` is one deadline for the whole call, from connecting to reading the body. For finer control, the client's `Transport` (the part that owns connections) has its own limits. This is the client to use in production:

```go
client := &http.Client{
	Timeout: 5 * time.Second, // the whole call, body included
	Transport: &http.Transport{
		DialContext:           (&net.Dialer{Timeout: 1 * time.Second}).DialContext, // opening the connection
		TLSHandshakeTimeout:   1 * time.Second,
		ResponseHeaderTimeout: 2 * time.Second, // from sending the request to the first response header
		IdleConnTimeout:       90 * time.Second, // how long an unused connection may stay in the pool
	},
}
```

<GoP14ClientTimeouts />

A `Dialer` is the part that opens a network connection, so `Dialer.Timeout` limits how long that takes. Make one client like this at start-up and share it: clients are safe for many goroutines, and sharing one is also what lets connections be reused (next section). If the `Todo` service called a webhook after every `createTodo`, this is the client that call would use. You can also stop a single request early with a `context`, as [post 8](/blog/go-context-timeouts-mutexes/) shows.

### The server side: the same trap on the other end

A server has the mirror problem. A client can connect and then send its headers one byte at a time, or never finish them, and a server with no limit keeps that connection open. [Post 10](/blog/go-http-service-net-http-json-middleware/) builds the `Todo` server with `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` and `IdleTimeout` and explains each one. Here is the difference they make. The program connects with a raw TCP socket, sends half a request header and waits to see whether the server hangs up.

```go
package main

import (
	"fmt"
	"net"
	"net/http"
	"net/http/httptest"
	"time"
)

// trickle opens a connection, sends half a request header, then waits to see
// whether the server hangs up.
func trickle(addr string) string {
	conn, err := net.Dial("tcp", addr)
	if err != nil {
		return err.Error()
	}
	defer conn.Close()
	fmt.Fprint(conn, "GET / HTTP/1.1\r\nHost: example\r\n") // no blank line: the header never ends
	start := time.Now()
	conn.SetReadDeadline(time.Now().Add(3 * time.Second))
	buf := make([]byte, 512)
	n, err := conn.Read(buf)
	waited := time.Since(start).Round(100 * time.Millisecond)
	if err != nil {
		return fmt.Sprintf("after %v: %v", waited, err)
	}
	return fmt.Sprintf("after %v the server answered: %q", waited, string(buf[:n]))
}

func main() {
	h := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {})

	bare := httptest.NewServer(h) // no timeouts, like http.ListenAndServe
	defer bare.Close()
	fmt.Println("no timeouts:        ", trickle(bare.Listener.Addr().String()))

	guarded := httptest.NewUnstartedServer(h)
	guarded.Config.ReadHeaderTimeout = 1 * time.Second
	guarded.Start()
	defer guarded.Close()
	fmt.Println("ReadHeaderTimeout 1s:", trickle(guarded.Listener.Addr().String()))
}
```

<TerminalOutput command="go run ." label="Apple M2 · Go 1.27.1" caption="The first line is our own 3-second read deadline firing: the server without timeouts was still holding the half-finished request when we gave up. The second line is the server hanging up after 1 second (EOF).">
```text
no timeouts:         after 3s: read tcp 127.0.0.1:55471->127.0.0.1:55470: i/o timeout
ReadHeaderTimeout 1s: after 1s: EOF
```
</TerminalOutput>

One slow client costs a goroutine and a socket. A few thousand of them can use up your file descriptors. That is why `http.ListenAndServe(addr, h)` is fine for a demo and wrong for a service: it builds a server with every timeout at zero and gives you no way to change that. Build the `http.Server` yourself, as post 10 does.

| Setting | Default | What it risks | A starting point |
|---|---|---|---|
| `http.Client.Timeout` | `0`, no limit | a stuck upstream pins a goroutine for ever | `5 * time.Second`, plus the `Transport` limits above |
| `http.Server.ReadHeaderTimeout` | `0`, no limit | clients that never finish their headers | a few seconds |
| `http.Transport.MaxIdleConnsPerHost` | `2` (`http.DefaultMaxIdleConnsPerHost`) | at high request rates most connections are closed and opened again | raise it to the number of calls you make in parallel to one host |
| `sql.DB` `SetMaxOpenConns` | `0`, no limit | a burst opens as many database connections as it asks for | a number your database can serve ([section 5](#5-databasesql-is-a-pool)) |

<Concepts>

- **Timeout**: a limit on how long to wait. Go sets none by default for clients and servers built from the defaults.
- **`Transport` and `Dialer`**: the `Transport` is the part of an `http.Client` that owns connections and the pool of idle ones. The `Dialer` is the part that opens a network connection.
- **Slow-client attack**: a client that opens connections and sends data very slowly, or not at all, so the server's resources stay tied up.

</Concepts>

## 2. Close what you open

Some values hold an operating-system resource until you close them: an HTTP response body, the rows of a database query, an open file. Forgetting to close them is the quiet kind of leak, because nothing crashes. The resource count just creeps up until a call fails. Go gives you `defer` for this ([post 5](/blog/go-errors-defer-panic/)). Two details are easy to miss.

### Response bodies: close, and read to the end

Every `http.Get` that succeeds returns a `resp` whose `Body` you must close. Closing is also not quite enough. An HTTP connection can serve many requests one after another (this is called *keep-alive*), and the client keeps finished connections in an idle pool to reuse them. A connection goes back to that pool only if the whole body was read. If you close early, the client throws the connection away, and the next request pays for a new TCP connection and TLS handshake.

```go
func fetch(client *http.Client, url string) error {
	resp, err := client.Get(url)
	if err != nil {
		return err
	}
	defer resp.Body.Close() // runs when fetch returns
	// ... decode the body here ...
	_, err = io.Copy(io.Discard, io.LimitReader(resp.Body, 1<<20)) // read what is left, at most 1 MiB
	return err
}
```

`io.Discard` is a writer that throws everything away, so `io.Copy` into it reads and ignores the rest. `io.LimitReader` stops after 1 MiB (`1<<20` bytes), so a huge answer cannot make this call run for ever. The `defer` goes right after the error check: when `err` is not `nil`, `resp` is `nil` and there is nothing to close.

How much does it matter? The program below makes 5 requests to a local server, with and without reading the rest, for three body sizes. It counts the connections the server accepted.

```go
package main

import (
	"fmt"
	"io"
	"net"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync/atomic"
)

func main() {
	for _, size := range []int{1_000, 100_000, 5_000_000} {
		for _, drain := range []bool{false, true} {
			var conns atomic.Int32
			srv := httptest.NewUnstartedServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
				io.WriteString(w, strings.Repeat("x", size))
			}))
			srv.Config.ConnState = func(_ net.Conn, s http.ConnState) {
				if s == http.StateNew {
					conns.Add(1)
				}
			}
			srv.Start()
			client := &http.Client{Transport: &http.Transport{}}
			for i := 0; i < 5; i++ {
				resp, err := client.Get(srv.URL)
				if err != nil {
					panic(err)
				}
				if drain {
					io.Copy(io.Discard, resp.Body)
				}
				resp.Body.Close()
			}
			fmt.Printf("body %7d bytes, drain=%-5v: 5 requests used %d connection(s)\n", size, drain, conns.Load())
			srv.Close()
		}
	}
}
```

### `http.Error` does not stop the handler

`http.Error(w, message, code)` writes a status line and a text body. It does not return from your handler. The function you wrote keeps running, and anything it writes afterwards is appended to the same response. The program below is a trimmed `getTodo` from post 10, with the `return` missing after the first `http.Error`. The handler gets `abc` as the id, which is not a number.

```go
package main

import (
	"fmt"
	"io"
	"log"
	"net/http"
	"net/http/httptest"
	"os"
	"strconv"
)

var titles = []string{"write post"} // todo 1 is titles[0]

func getTodo(w http.ResponseWriter, r *http.Request) {
	id, err := strconv.Atoi(r.PathValue("id"))
	if err != nil {
		http.Error(w, "id must be a number", http.StatusBadRequest)
		// no return here
	}
	if id < 1 || id > len(titles) {
		http.Error(w, "todo not found", http.StatusNotFound)
		return
	}
	fmt.Fprintln(w, titles[id-1])
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /todos/{id}", getTodo)
	srv := httptest.NewUnstartedServer(mux)
	srv.Config.ErrorLog = log.New(os.Stdout, "server log: ", 0) // show the server's own log here
	srv.Start()
	defer srv.Close()

	resp, _ := http.Get(srv.URL + "/todos/abc")
	body, _ := io.ReadAll(resp.Body)
	fmt.Printf("status %d\nbody %q\n", resp.StatusCode, body)
}
```

<TerminalOutput command="go run ." label="Apple M2 · Go 1.27.1" caption="Real run. The server's own log points at line 22 of the file above, the second http.Error call.">
```text

status 400

```
</TerminalOutput>

<GoP14MissingReturn />

When `Atoi` fails, `id` is `0`, so the next check also fails and writes a second error. The status was already sent, so the second one is ignored (and logged as "superfluous"), but its text is still appended to the body. In a bigger handler the code after the missing `return` might write to a database. The fix is one word, `return`, right after every `http.Error` and every `writeError` call.

### Rows and files

`sql.Rows` from a query holds a database connection until you call `rows.Close()`, and a file holds a file descriptor until `f.Close()`. Both follow the same `defer` pattern. The rows version appears in [section 5](#5-databasesql-is-a-pool). For files you write to, check the error from `Close` too, as [post 5](/blog/go-errors-defer-panic/) explains.

<Concepts>

- **Keep-alive and the idle pool**: an HTTP connection that can carry several requests. The client keeps finished connections ready in a pool and reuses them, but only if the response body was read to the end.
- **`io.Discard`**: a writer that drops everything written to it. Copying into it is the standard way to read and ignore data.

</Concepts>

## 3. Time: bare numbers and timers

### A bare number is nanoseconds

`time.Duration` counts nanoseconds. Constants like `time.Second` are just big numbers of them, so a literal without a unit means something very small.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	fmt.Println(time.Duration(1000))
	fmt.Println(1000 * time.Millisecond)
	start := time.Now()
	time.Sleep(1000) // meant: one second
	fmt.Println("slept for", time.Since(start).Round(time.Microsecond) < 100*time.Microsecond)
}
```

Always write the unit: `5 * time.Second`, `time.Duration(n) * time.Millisecond`.

### `time.After` in a loop

`time.After(d)` returns a channel and starts a timer that sends on it after `d`. It is the usual way to write "wait for an event, but give up after a minute" inside a `select`. Put it in a `for` loop and every iteration starts a new timer. For years the advice was that those timers stay in memory until they fire, so a busy loop with a long timeout could use gigabytes.

I measured it. The program reads from a channel that always has a value ready, with a one-minute `time.After` as the other `select` case, a million times, and prints the live heap before and after.

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// heapMB forces a collection and returns the live heap in megabytes.
func heapMB() float64 {
	var m runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m)
	return float64(m.HeapAlloc) / (1 << 20)
}

func main() {
	events := make(chan int)
	go func() {
		for i := 0; ; i++ {
			events <- i
		}
	}()

	before := heapMB()
	for i := 0; i < 1_000_000; i++ {
		select {
		case <-events:
		case <-time.After(time.Minute): // a new timer every iteration
		}
	}
	fmt.Printf("live heap: %.1f MB before, %.1f MB after 1,000,000 loops\n", before, heapMB())
}
```

On Go 1.22 the million unfired timers hold about 199 MB. On Go 1.27 they hold nothing. The [Go 1.23 release notes](https://go.dev/doc/go1.23) explain: timers that the program no longer refers to can now be garbage-collected immediately, even if they were not stopped. So the leak the advice warns about is gone on current Go. It is still alive if you build with an older toolchain, so if you meet this pattern in old code, or have to support an old Go, create one timer outside the loop and reuse it:

```go
timer := time.NewTimer(time.Minute) // one timer for the whole loop
defer timer.Stop()
for i := 0; i < 1_000_000; i++ {
	timer.Reset(time.Minute) // restart the countdown each time
	select {
	case <-events:
	case <-timer.C:
	}
}
```

Dropped into the same program, this loop kept the heap at 0.1 MB after a million iterations on Go 1.22.12 and 0.2 MB on Go 1.27.1. On Go 1.23 and newer, `time.After` in a loop is fine for memory.

## 4. JSON: three surprises

`encoding/json` turns Go values into JSON and back. The `Todo` service uses it in every handler, through `json.NewEncoder` and `json.NewDecoder`. Three behaviours catch people out, and the program below shows all three. It needs two small types: `Event`, which embeds a `time.Time` (embedding is from [post 4](/blog/go-structs-methods-interfaces/): the embedded type's fields and methods are promoted to the outer struct), and `Fixed`, which holds the same time in a named field.

```go
package main

import (
	"encoding/json"
	"fmt"
	"strings"
	"time"
)

type Todo struct {
	ID    int    `json:"id"`
	Title string `json:"title"`
}

// Event is a todo change. time.Time is embedded, so its methods are promoted.
type Event struct {
	Todo
	time.Time
}

// Fixed is the same data with the time under a name.
type Fixed struct {
	Todo
	At time.Time `json:"at"`
}

func main() {
	at := time.Date(2026, 11, 23, 9, 30, 0, 0, time.UTC)
	todo := Todo{ID: 7, Title: "write post"}

	b, _ := json.Marshal(Event{todo, at})
	fmt.Println("embedded: ", string(b))
	b, _ = json.Marshal(Fixed{todo, at})
	fmt.Println("named:    ", string(b))

	// The monotonic clock does not survive JSON.
	t1 := time.Now()
	raw, _ := json.Marshal(t1)
	var t2 time.Time
	json.Unmarshal(raw, &t2)
	fmt.Println("t1 == t2:", t1 == t2, " t1.Equal(t2):", t1.Equal(t2))

	// Numbers decoded into any are float64.
	var m map[string]any
	json.Unmarshal([]byte(`{"id": 9007199254740993}`), &m)
	fmt.Printf("map[string]any: %v (%T)\n", m["id"], m["id"])
	fmt.Printf("as %%.0f:        %.0f\n", m["id"])

	dec := json.NewDecoder(strings.NewReader(`{"id": 9007199254740993}`))
	dec.UseNumber()
	var m2 map[string]any
	dec.Decode(&m2)
	fmt.Printf("with UseNumber: %v (%T)\n", m2["id"], m2["id"])
}
```

### An embedded `time.Time` takes over the JSON (#77)

`Event{todo, at}` should print an object with `id` and `title`, and it prints only the time. `time.Time` has a method `MarshalJSON`, the hook `encoding/json` calls for a type that wants to encode itself (the interface is `json.Marshaler`). Because `time.Time` is embedded, that method is promoted to `Event`, so `Event` now encodes itself as a time and `json.Marshal` never looks at the other fields. Decoding has the same problem the other way round.

<GoP14EmbeddedTime />

The fix in `Fixed` is to give the time a name. Embedding is a convenient way to reuse methods, and this is its cost: it can make your struct satisfy an interface you never meant to implement.

### The monotonic clock does not survive JSON

<Figure src={clockEscapement} alt="Historic engraving of Mr. R. Mays detached clock escapement mechanism showing paired timing wheels" caption="Two clocks in one struct: a time.Time returned by time.Now carries a wall-clock reading and a monotonic tick count. JSON keeps only the wall-clock half." sourceTitle="Wikimedia Commons: Mays detached escapement (Wellcome Collection)" sourceUrl="https://commons.wikimedia.org/wiki/File:Clocks;_an_escapement_mechanism._Engraving_by_W._Kelsall_aft_Wellcome_V0023849EL.jpg" />

A computer keeps two kinds of time. The *wall clock* is the date and time of day; it can jump when the machine syncs with a time server. The *monotonic clock* only counts forward, so it is the right thing to measure how long something took. `time.Now()` returns both in one `time.Time`. When you encode a time to JSON, only the wall-clock reading is written, so after decoding `t1` and `t2` show the same instant but are different values. `==` compares every part of the struct, including the monotonic reading, and says `false`. `t1.Equal(t2)` compares the instant and says `true`. Compare times with `Equal` (or `Before` and `After`), not with `==`.

### Numbers decoded into `any` are `float64`

If you decode into `map[string]any`, the compiler does not know your structure, so every JSON number becomes a `float64`. A `float64` holds whole numbers exactly only up to 2^53, which is 9007199254740992. The program decodes 9007199254740993, one more than that, and gets back ...992. An ID that big would be silently changed, and this is how a big database ID gets rounded on its way through a generic handler. Two fixes: decode into a struct with an `int64` field, or call `UseNumber()` on the decoder, which keeps the digits as a `json.Number` you can turn into an `int64` yourself.

<Concepts>

- **Method promotion**: when a struct embeds a type, the embedded type's methods can be called on the outer struct, and the outer struct satisfies the same interfaces.
- **Wall clock and monotonic clock**: the wall clock tells the date and can jump; the monotonic clock only moves forward and is meant for measuring durations. A `time.Time` from `time.Now()` holds both.
- **`float64` precision**: a 64-bit float stores integers exactly only up to 2^53. Larger whole numbers are rounded.

</Concepts>

## 5. `database/sql` is a pool

The standard `database/sql` package gives you one type for talking to a database, `*sql.DB`. Despite the name, it is not one connection. It is a *pool*: a set of connections that the package opens when needed, hands to one caller at a time and takes back for the next caller. The `Todo` service keeps its data in memory, but a real one would hold a `*sql.DB` the same way it holds its `store`. The real driver you import (for PostgreSQL, MySQL and so on) matters little here, so the program below uses a fake driver that only counts how many connections were opened. That lets us see the pool without a database.

```go
package main

import (
	"context"
	"database/sql"
	"database/sql/driver"
	"errors"
	"fmt"
	"sync/atomic"
	"time"
)

// fakeDriver stands in for a real database driver (such as pgx). It only
// counts how many connections were opened.
type fakeDriver struct{ opened atomic.Int32 }

func (d *fakeDriver) Open(name string) (driver.Conn, error) {
	d.opened.Add(1)
	return fakeConn{}, nil
}

type fakeConn struct{}

func (fakeConn) Prepare(string) (driver.Stmt, error) { return nil, errors.New("not needed") }
func (fakeConn) Close() error                         { return nil }
func (fakeConn) Begin() (driver.Tx, error)            { return nil, errors.New("not needed") }

func main() {
	d := &fakeDriver{}
	sql.Register("fake", d)

	db, err := sql.Open("fake", "host=db")
	fmt.Println("sql.Open error:", err, "| connections opened:", d.opened.Load())

	ctx := context.Background()
	fmt.Println("Ping error:", db.PingContext(ctx), "| connections opened:", d.opened.Load())

	db.SetMaxOpenConns(2)
	c1, _ := db.Conn(ctx) // takes connection 1 and keeps it
	c2, _ := db.Conn(ctx) // takes connection 2 and keeps it
	fmt.Println("holding 2 of 2 connections")

	waitCtx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
	defer cancel()
	_, err = db.Conn(waitCtx) // a third caller has to queue
	fmt.Println("third caller:", err)
	fmt.Printf("stats: open=%d inUse=%d waitCount=%d\n",
		db.Stats().OpenConnections, db.Stats().InUse, db.Stats().WaitCount)

	c1.Close() // hand one back
	c3, err := db.Conn(ctx)
	fmt.Println("after releasing one:", err, "| connections opened:", d.opened.Load())
	c2.Close()
	c3.Close()
}
```

```text

Ping error: <nil> | connections opened: 1
holding 2 of 2 connections
```

<GoP14SqlPool />

Read the output top to bottom.

1. `sql.Open` returned no error and **opened 0 connections** (#78). It checks its arguments and builds the pool. With a real driver it would also succeed if the database were down. Call `db.PingContext(ctx)` at start-up to find out early; the ping is what opened the first connection.
2. With `SetMaxOpenConns(2)`, two callers hold both connections. A third caller does not fail. It waits in line, and only the `context` timeout got it out after 200 ms. This is the same shape as the missing timeout in section 1: without a context deadline, that caller would wait until someone returns a connection.
3. When `c1` was handed back, the next caller reused it instead of opening a third connection.

What holds a connection in a real service is usually a query result you forgot to close. This is the shape of a function that reads rows. It needs a real driver, so it is only a sketch:

```go
func names(ctx context.Context, db *sql.DB) ([]string, error) {
	rows, err := db.QueryContext(ctx, "SELECT title FROM todos")
	if err != nil {
		return nil, err
	}
	defer rows.Close() // gives the connection back to the pool
	var out []string
	for rows.Next() {
		var title string
		if err := rows.Scan(&title); err != nil {
			return nil, err
		}
		out = append(out, title)
	}
	return out, rows.Err() // Next() also returns false when something went wrong
}
```

`rows.Next()` returns `false` both when the rows have run out and when an error stopped the read, so after the loop you must check `rows.Err()`. The `defer rows.Close()` is what puts the connection back; if one code path forgets it, the pool shrinks by one every time it runs.

The pool has four settings. The defaults come from `go doc`:

| Setting | Default | What it controls |
|---|---|---|
| `SetMaxOpenConns(n)` | `0`, unlimited | most connections open at once; the rest queue |
| `SetMaxIdleConns(n)` | `2` | connections kept ready when idle |
| `SetConnMaxLifetime(d)` | no limit | how long a connection may be reused before it is replaced |
| `SetConnMaxIdleTime(d)` | no limit | how long a connection may sit idle before it is closed |

Unlimited open connections means a burst of traffic can open more connections than your database allows. Set `SetMaxOpenConns` to a number the database can serve, and give connections a lifetime so a firewall or load balancer that quietly drops old ones cannot leave you with dead ones.

<Concepts>

- **Connection pool**: a set of ready connections shared by many callers. A caller takes one, uses it and gives it back.
- **`sql.Open` vs `Ping`**: `sql.Open` builds the pool without necessarily connecting; `PingContext` forces a connection and proves the database is reachable.

</Concepts>

## 6. Go in containers

A container runs your program with limits the program cannot see directly. The one that matters here is CPU. In Kubernetes, `limits.cpu: "2"` on a pod becomes a kernel setting for the container, and the Linux scheduler that enforces it is called CFS (the Completely Fair Scheduler). To understand what goes wrong, you first need `GOMAXPROCS`.

`GOMAXPROCS` is how many goroutines the Go runtime lets run at the same moment, one per logical processor (`P`), as [post 13](/blog/go-concurrency-scheduler-channels-context-mutexes/) explains. It is also the number of threads that can burn CPU at once.

### The Kubernetes CFS throttling trap (`#100`)

CFS gives a container a *quota* of CPU time per *period* of 100 ms. A limit of 2 CPUs is a quota of 200 ms of CPU time in every 100 ms. When the container's threads together use up the quota, the kernel pauses all of them until the next period starts. This is *throttling*. It is not a crash and not an error. The process just stops for a while, which shows up as latency.

Before Go 1.25, `GOMAXPROCS` defaulted to the number of CPUs on the machine, whatever the container's limit was. On a 6-CPU machine with a limit of 2, Go runs 6 threads at once, and 6 busy threads use 200 ms of CPU in about 33 ms. Then everything waits for the rest of the window.

<GoP14CfsWindow />

I ran this, not only calculated it. The program below prints the container's quota (the file `cpu.max`), the CPU count and `GOMAXPROCS`. It then burns CPU on every `P` for 3 seconds. In the meantime it asks to sleep 1 ms again and again and records how late it wakes up at worst, and at the end it reads how many 100 ms periods were throttled from the container's `cpu.stat`.

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"strings"
	"time"
)

func cgroupFile(name string) string {
	b, err := os.ReadFile("/sys/fs/cgroup/" + name)
	if err != nil {
		return err.Error()
	}
	return strings.TrimSpace(string(b))
}

// throttled pulls two counters out of the cgroup's cpu.stat file.
func throttled() (periods, count string) {
	for _, line := range strings.Split(cgroupFile("cpu.stat"), "\n") {
		f := strings.Fields(line)
		switch f[0] {
		case "nr_periods":
			periods = f[1]
		case "nr_throttled":
			count = f[1]
		}
	}
	return
}

func main() {
	fmt.Println("cpu.max (quota period):", cgroupFile("cpu.max"))
	fmt.Println("NumCPU:", runtime.NumCPU(), " GOMAXPROCS:", runtime.GOMAXPROCS(0))

	// Burn CPU on every P for 3 seconds, and watch how late a 1 ms sleeper wakes up.
	stop := time.Now().Add(3 * time.Second)
	for i := 0; i < runtime.GOMAXPROCS(0); i++ {
		go func() {
			for time.Now().Before(stop) {
			}
		}()
	}
	var worst time.Duration
	for time.Now().Before(stop) {
		t := time.Now()
		time.Sleep(time.Millisecond)
		if late := time.Since(t) - time.Millisecond; late > worst {
			worst = late
		}
	}
	p, n := throttled()
	fmt.Printf("periods: %s, throttled periods: %s, worst wake-up delay: %v\n", p, n, worst.Round(time.Millisecond))
}
```

I built it for Linux with Go 1.27.1 and ran it in a container limited to 2 CPUs on a 6-CPU machine, twice, once with the default and once with `GOMAXPROCS=6` in the environment, which is what the old default would have chosen. The container runtime was OrbStack. It sets the same `cpu.max` file that Kubernetes writes for a CPU limit, but this was not a Kubernetes cluster.

With 6 threads, almost every period was throttled and a 1 ms sleep woke up as much as 103 ms late. With 2 it was far better, but not clean. The worst delay was still about 45 ms, and some periods were throttled anyway. That is because Go has threads other than the 2 running goroutines (the garbage collector and the runtime's own helpers), and they also spend quota. A CPU limit can still throttle a well-behaved Go program. Go 1.25 shrank the problem; it did not remove it.

What Go 1.25 changed is the default. [The release notes](https://go.dev/doc/go1.25) say that on Linux the runtime now reads the cgroup's CPU limit, and if it is lower than the number of logical CPUs it becomes the default `GOMAXPROCS`. It uses the *limit* and ignores the *request* in Kubernetes terms. `go doc runtime.GOMAXPROCS` adds that the runtime keeps updating the value if the limit changes. I also tried fractional limits on the same machine: `--cpus=1.5` gave `GOMAXPROCS` 2, `--cpus=2.5` gave 3 and `--cpus=0.5` gave 2, so it rounds up and never goes below 2.

There is one more catch, and it is in `go.mod`. The new default is tied to the language version in the module's `go` line. `go doc` says `containermaxprocs=0` is the default for language version 1.24 and below. I took the same program, set `go 1.24` in `go.mod` and built it with Go 1.27.1:

<TerminalOutput command="go build -o gmp-old . (go.mod says go 1.24), then docker run --cpus=2" label="Go 1.27.1 toolchain · go 1.24 in go.mod · 2 CPUs" caption="A new toolchain does not help while the go line is old.">

So upgrading the compiler is not enough: raise the `go` line too, or set `GOMAXPROCS` yourself (an environment variable or a call to `runtime.GOMAXPROCS`; either one turns off the automatic behaviour). On a Go older than 1.25, the usual fix is the `go.uber.org/automaxprocs` package.

How do you know it is happening? Throttling does not show up as high CPU. A pod can look idle on average and still be paused in bursts. Kubernetes exposes `container_cpu_cfs_throttled_seconds_total`, and [Go observability](/blog/go-observability-metrics-microbenchmarks-benchstat/) shows how to read it next to CPU usage.

<Concepts>

- **CFS quota and throttling**: the Linux scheduler gives a container a CPU-time budget per 100 ms period. When the container's threads spend it all, the kernel pauses them until the next period.
- **`GOMAXPROCS`**: how many goroutines run at the same moment. From Go 1.25, with a `go` line of 1.25 or newer, its default follows the container's CPU limit, rounded up, with a minimum of 2.
- **CPU limit and CPU request**: in Kubernetes the limit is the ceiling that causes throttling. The request is a scheduling hint, and Go does not read it.

</Concepts>

## Key takeaways

- **Set a timeout on everything that waits.** `http.DefaultClient`, `http.Get` and `http.ListenAndServe` have none. Build your own `http.Client` with `Timeout` and Transport limits, and your own `http.Server` with its timeouts.
- **Read the rest of a response body, then close it.** An unread body makes the client drop the connection; five requests with a 5,000,000-byte body used five connections instead of one.
- **Put `return` after `http.Error`.** The handler keeps running otherwise, and what it writes next is appended to the response.
- **A bare number is nanoseconds.** `time.Sleep(1000)` is 1 microsecond. `time.After` in a loop leaked about 199 MB per million iterations on Go 1.22.12 and nothing on Go 1.27.1.
- **Do not trust JSON round trips blindly.** An embedded `time.Time` replaces the struct's JSON, `==` on times can be `false` for the same instant, and numbers decoded into `any` are `float64`.
- **`sql.Open` makes a pool and does not connect.** Ping at start-up, close every `sql.Rows`, check `rows.Err()`, and bound the pool.
- **In a container, check the `go` line and watch throttling.** Go 1.25 and a `go` line of 1.25 or newer make `GOMAXPROCS` follow the CPU limit, yet a limit can still throttle you: 4 to 11 of 31 periods in my runs, against 30 of 31 with `GOMAXPROCS=6`.

## 1. Chờ mãi: timeout

*Timeout* là giới hạn thời gian code chờ một thứ nằm ngoài nó: một connection, một câu trả lời, một client gửi chậm. Go không có timeout toàn cục ngầm. Nếu mình không đặt, việc chờ không có điểm dừng. Trên laptop thì không sao, nhưng khi một service phía sau treo thì nguy hiểm, vì mỗi lời gọi đang chờ giữ lại một goroutine, một socket và ít bộ nhớ.

### Client mặc định không bao giờ bỏ cuộc

Package `net/http` có sẵn một client, `http.DefaultClient`, và các hàm tắt như `http.Get` dùng nó. Định nghĩa của nó trong mã nguồn Go:

```go
	Timeout time.Duration
```

Vậy `http.Get(url)` chờ bao lâu tuỳ đầu bên kia. Chương trình dưới dựng một server thử nhận request rồi ngủ 3 giây. `httptest.NewServer` (từ [bài 10](/blog/go-http-service-net-http-json-middleware/)) cho mình server đó mà không cần cấu hình mạng. Đầu tiên gọi bằng `http.Get` trong một goroutine và ngừng xem sau 1 giây. Sau đó gọi bằng client của mình có `Timeout`.

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func main() {
	// A server that accepts the request and then never answers (it sleeps 3s).
	slow := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(3 * time.Second)
	}))
	defer slow.Close()

	// 1. http.Get uses http.DefaultClient, whose Timeout is 0: wait forever.
	done := make(chan error, 1)
	go func() {
		_, err := http.Get(slow.URL)
		done <- err
	}()
	select {
	case err := <-done:
		fmt.Println("default client returned:", err)
	case <-time.After(1 * time.Second):
		fmt.Println("default client: no answer after 1s, still waiting")
	}

	// 2. Our own client with a deadline for the whole call.
	client := &http.Client{Timeout: 500 * time.Millisecond}
	start := time.Now()
	_, err := client.Get(slow.URL)
	fmt.Printf("own client gave up after %v\n%v\n", time.Since(start).Round(100*time.Millisecond), err)
}
```

`Client.Timeout` là một hạn chót cho cả lời gọi, từ lúc kết nối đến lúc đọc xong body. Muốn chia nhỏ hơn thì `Transport` của client (phần giữ các connection) có giới hạn riêng. Đây là client nên dùng trên production:

```go
client := &http.Client{
	Timeout: 5 * time.Second, // the whole call, body included
	Transport: &http.Transport{
		DialContext:           (&net.Dialer{Timeout: 1 * time.Second}).DialContext, // opening the connection
		TLSHandshakeTimeout:   1 * time.Second,
		ResponseHeaderTimeout: 2 * time.Second, // from sending the request to the first response header

	},
}
```

`Dialer` là phần mở một connection mạng, nên `Dialer.Timeout` giới hạn việc đó mất bao lâu. Hãy tạo một client như vậy lúc khởi động và dùng chung: client an toàn với nhiều goroutine, và dùng chung cũng là điều cho phép tái sử dụng connection (mục sau). Nếu service `Todo` gọi một webhook sau mỗi `createTodo`, đây là client lời gọi đó sẽ dùng. Mình cũng có thể dừng một request riêng lẻ bằng `context`, như [bài 8](/blog/go-context-timeouts-mutexes/) đã chỉ.

### Phía server: cùng một cái bẫy ở đầu kia

Server gặp đúng vấn đề đối xứng. Một client có thể kết nối rồi gửi header từng byte một, hoặc không bao giờ gửi xong, và server không có giới hạn sẽ giữ connection đó mở mãi. [Bài 10](/blog/go-http-service-net-http-json-middleware/) dựng server `Todo` với `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` và `IdleTimeout` và giải thích từng cái. Đây là khác biệt chúng tạo ra. Chương trình kết nối bằng một socket TCP thô, gửi nửa header của request rồi chờ xem server có tự ngắt không.

```go
package main

import (
	"fmt"
	"net"
	"net/http"
	"net/http/httptest"
	"time"
)

// trickle opens a connection, sends half a request header, then waits to see
// whether the server hangs up.
func trickle(addr string) string {
	conn, err := net.Dial("tcp", addr)
	if err != nil {
		return err.Error()
	}
	defer conn.Close()
	fmt.Fprint(conn, "GET / HTTP/1.1\r\nHost: example\r\n") // no blank line: the header never ends
	start := time.Now()
	conn.SetReadDeadline(time.Now().Add(3 * time.Second))
	buf := make([]byte, 512)
	n, err := conn.Read(buf)
	waited := time.Since(start).Round(100 * time.Millisecond)
	if err != nil {
		return fmt.Sprintf("after %v: %v", waited, err)
	}
	return fmt.Sprintf("after %v the server answered: %q", waited, string(buf[:n]))
}

func main() {
	h := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {})

	bare := httptest.NewServer(h) // no timeouts, like http.ListenAndServe
	defer bare.Close()
	fmt.Println("no timeouts:        ", trickle(bare.Listener.Addr().String()))

	guarded := httptest.NewUnstartedServer(h)
	guarded.Config.ReadHeaderTimeout = 1 * time.Second
	guarded.Start()
	defer guarded.Close()
	fmt.Println("ReadHeaderTimeout 1s:", trickle(guarded.Listener.Addr().String()))
}
```

<Concepts title="Mấy khái niệm ở mục này">

- **Timeout**: giới hạn thời gian chờ. Go mặc định không đặt cái nào cho client và server dựng từ giá trị mặc định.
- **`Transport` và `Dialer`**: `Transport` là phần của `http.Client` giữ các connection và pool connection đang rảnh. `Dialer` là phần mở một connection mạng.
- **Tấn công client chậm**: client mở connection rồi gửi dữ liệu rất chậm, hoặc không gửi gì, để tài nguyên server bị giữ chặt.

</Concepts>

## 2. Đã mở thì phải đóng

Có những giá trị giữ tài nguyên của hệ điều hành cho đến khi mình đóng chúng: body của HTTP response, các dòng kết quả của một câu query, một file đang mở. Quên đóng là kiểu rò rỉ âm thầm, vì không có gì crash. Chỉ là số tài nguyên cứ nhích lên cho đến khi một lời gọi hỏng. Go có `defer` cho việc này ([bài 5](/blog/go-errors-defer-panic/)). Có hai chi tiết dễ sót.

### Response body: đóng, và đọc đến hết

Mỗi `http.Get` thành công trả về `resp` mà mình phải đóng `Body` của nó. Chỉ đóng cũng chưa đủ. Một connection HTTP có thể phục vụ nhiều request nối tiếp nhau (gọi là *keep-alive*), và client giữ các connection đã xong trong một pool rảnh để dùng lại. Connection chỉ quay về pool nếu body đã được đọc hết. Đóng sớm thì client vứt connection đi, và request sau phải trả giá cho một connection TCP mới cộng một lần bắt tay TLS.

```go
func fetch(client *http.Client, url string) error {
	resp, err := client.Get(url)
	if err != nil {
		return err
	}
	defer resp.Body.Close() // runs when fetch returns
	// ... decode the body here ...
	_, err = io.Copy(io.Discard, io.LimitReader(resp.Body, 1<<20)) // read what is left, at most 1 MiB
	return err
}
```

`io.Discard` là một writer vứt hết mọi thứ ghi vào, nên `io.Copy` vào đó là đọc và bỏ phần còn lại. `io.LimitReader` dừng sau 1 MiB (`1<<20` byte), nên một câu trả lời khổng lồ không thể làm lời gọi này chạy mãi. `defer` đặt ngay sau chỗ kiểm tra lỗi: khi `err` khác `nil` thì `resp` là `nil` và không có gì để đóng.

Chuyện này quan trọng cỡ nào? Chương trình dưới gửi 5 request tới một server local, có và không đọc phần còn lại, với ba cỡ body. Nó đếm số connection mà server đã nhận.

```go
package main

import (
	"fmt"
	"io"
	"net"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync/atomic"
)

func main() {
	for _, size := range []int{1_000, 100_000, 5_000_000} {
		for _, drain := range []bool{false, true} {
			var conns atomic.Int32
			srv := httptest.NewUnstartedServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
				io.WriteString(w, strings.Repeat("x", size))
			}))
			srv.Config.ConnState = func(_ net.Conn, s http.ConnState) {
				if s == http.StateNew {
					conns.Add(1)
				}
			}
			srv.Start()
			client := &http.Client{Transport: &http.Transport{}}
			for i := 0; i < 5; i++ {
				resp, err := client.Get(srv.URL)
				if err != nil {
					panic(err)
				}
				if drain {
					io.Copy(io.Discard, resp.Body)
				}
				resp.Body.Close()
			}
			fmt.Printf("body %7d bytes, drain=%-5v: 5 requests used %d connection(s)\n", size, drain, conns.Load())
			srv.Close()
		}
	}
}
```

### `http.Error` không dừng handler

`http.Error(w, message, code)` ghi một dòng status và một body chữ. Nó không thoát khỏi handler của mình. Hàm bạn viết vẫn chạy tiếp, và mọi thứ nó ghi sau đó được nối vào cùng một response. Chương trình dưới là một `getTodo` rút gọn từ bài 10, thiếu `return` sau lần `http.Error` đầu tiên. Handler nhận `abc` làm id, không phải số.

```go
package main

import (
	"fmt"
	"io"
	"log"
	"net/http"
	"net/http/httptest"
	"os"
	"strconv"
)

var titles = []string{"write post"} // todo 1 is titles[0]

func getTodo(w http.ResponseWriter, r *http.Request) {
	id, err := strconv.Atoi(r.PathValue("id"))
	if err != nil {
		http.Error(w, "id must be a number", http.StatusBadRequest)
		// no return here
	}
	if id < 1 || id > len(titles) {
		http.Error(w, "todo not found", http.StatusNotFound)
		return
	}
	fmt.Fprintln(w, titles[id-1])
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /todos/{id}", getTodo)
	srv := httptest.NewUnstartedServer(mux)
	srv.Config.ErrorLog = log.New(os.Stdout, "server log: ", 0) // show the server's own log here
	srv.Start()
	defer srv.Close()

	resp, _ := http.Get(srv.URL + "/todos/abc")
	body, _ := io.ReadAll(resp.Body)
	fmt.Printf("status %d\nbody %q\n", resp.StatusCode, body)
}
```

Trong một handler lớn hơn, đoạn code sau chỗ thiếu `return` có thể ghi vào database. Cách sửa chỉ một từ, `return`, ngay sau mỗi lời gọi `http.Error` và `writeError`.

### Rows và file

`sql.Rows` từ một câu query giữ một connection database cho đến khi gọi `rows.Close()`, và một file giữ một file descriptor cho đến khi `f.Close()`. Cả hai theo cùng khuôn `defer`. Bản của rows nằm ở [mục 5](#5-databasesql-là-một-pool). Với file mình ghi vào, nhớ kiểm tra lỗi từ `Close` nữa, như [bài 5](/blog/go-errors-defer-panic/) giải thích.

<Concepts title="Mấy khái niệm ở mục này">

- **Keep-alive và pool rảnh**: một connection HTTP chở được nhiều request. Client giữ sẵn các connection đã xong trong pool và dùng lại, nhưng chỉ khi response body đã được đọc đến hết.
- **`io.Discard`**: một writer bỏ hết mọi thứ ghi vào. Copy vào nó là cách chuẩn để đọc và bỏ dữ liệu.

</Concepts>

## 3. Time: số trần và timer

### Số trần là nano giây

`time.Duration` đếm bằng nano giây. Các hằng như `time.Second` chỉ là những con số lớn của đơn vị đó, nên một số viết không kèm đơn vị có nghĩa là một khoảng rất nhỏ.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	fmt.Println(time.Duration(1000))
	fmt.Println(1000 * time.Millisecond)
	start := time.Now()
	time.Sleep(1000) // meant: one second
	fmt.Println("slept for", time.Since(start).Round(time.Microsecond) < 100*time.Microsecond)
}
```

### `time.After` trong vòng lặp

`time.After(d)` trả về một channel và bật một timer gửi vào đó sau `d`. Đây là cách quen thuộc để viết "chờ một sự kiện, nhưng bỏ cuộc sau một phút" trong `select`. Đặt nó trong vòng `for` thì mỗi vòng bật một timer mới. Nhiều năm lời khuyên là các timer đó nằm trong bộ nhớ cho đến khi chúng nổ, nên một vòng lặp bận với timeout dài có thể ngốn hàng gigabyte.

Mình đã đo. Chương trình đọc từ một channel lúc nào cũng có sẵn giá trị, với `time.After` một phút là nhánh `select` còn lại, một triệu lần, rồi in heap đang sống trước và sau.

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// heapMB forces a collection and returns the live heap in megabytes.
func heapMB() float64 {
	var m runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m)
	return float64(m.HeapAlloc) / (1 << 20)
}

func main() {
	events := make(chan int)
	go func() {
		for i := 0; ; i++ {
			events <- i
		}
	}()

	before := heapMB()
	for i := 0; i < 1_000_000; i++ {
		select {
		case <-events:
		case <-time.After(time.Minute): // a new timer every iteration
		}
	}
	fmt.Printf("live heap: %.1f MB before, %.1f MB after 1,000,000 loops\n", before, heapMB())
}
```

```go
timer := time.NewTimer(time.Minute) // one timer for the whole loop

	}
```

## 4. JSON: ba điều bất ngờ

`encoding/json` biến giá trị Go thành JSON và ngược lại. Service `Todo` dùng nó trong mọi handler, qua `json.NewEncoder` và `json.NewDecoder`. Ba hành vi hay làm người ta vấp, và chương trình dưới cho thấy cả ba. Nó cần hai kiểu nhỏ: `Event`, nhúng một `time.Time` (nhúng là chuyện của [bài 4](/blog/go-structs-methods-interfaces/): field và method của kiểu được nhúng được đưa lên struct ngoài), và `Fixed`, giữ cùng thời điểm đó trong một field có tên.

```go
package main

import (
	"encoding/json"
	"fmt"
	"strings"
	"time"
)

type Todo struct {
	ID    int    `json:"id"`
	Title string `json:"title"`
}

// Event is a todo change. time.Time is embedded, so its methods are promoted.
type Event struct {
	Todo
	time.Time
}

// Fixed is the same data with the time under a name.
type Fixed struct {
	Todo
	At time.Time `json:"at"`
}

func main() {
	at := time.Date(2026, 11, 23, 9, 30, 0, 0, time.UTC)
	todo := Todo{ID: 7, Title: "write post"}

	b, _ := json.Marshal(Event{todo, at})
	fmt.Println("embedded: ", string(b))
	b, _ = json.Marshal(Fixed{todo, at})
	fmt.Println("named:    ", string(b))

	// The monotonic clock does not survive JSON.
	t1 := time.Now()
	raw, _ := json.Marshal(t1)
	var t2 time.Time
	json.Unmarshal(raw, &t2)
	fmt.Println("t1 == t2:", t1 == t2, " t1.Equal(t2):", t1.Equal(t2))

	// Numbers decoded into any are float64.
	var m map[string]any
	json.Unmarshal([]byte(`{"id": 9007199254740993}`), &m)
	fmt.Printf("map[string]any: %v (%T)\n", m["id"], m["id"])
	fmt.Printf("as %%.0f:        %.0f\n", m["id"])

	dec := json.NewDecoder(strings.NewReader(`{"id": 9007199254740993}`))
	dec.UseNumber()
	var m2 map[string]any
	dec.Decode(&m2)
	fmt.Printf("with UseNumber: %v (%T)\n", m2["id"], m2["id"])
}
```

### `time.Time` nhúng sẵn chiếm luôn phần JSON (#77)

`Event{todo, at}` lẽ ra in một object có `id` và `title`, nhưng nó chỉ in mỗi thời điểm. `time.Time` có method `MarshalJSON`, cái móc mà `encoding/json` gọi cho kiểu muốn tự encode (interface đó là `json.Marshaler`). Vì `time.Time` được nhúng, method đó được đưa lên `Event`, nên `Event` giờ tự encode mình như một thời điểm và `json.Marshal` không bao giờ nhìn tới các field còn lại. Decode cũng bị y như vậy theo chiều ngược lại.

Cách sửa trong `Fixed` là đặt tên cho field thời gian. Nhúng là cách tiện để dùng lại method, và đây là cái giá: nó có thể khiến struct của bạn thoả một interface mà bạn chưa hề định cài đặt.

### Đồng hồ đơn điệu không sống sót qua JSON

JSON chỉ giữ nửa đồng hồ treo tường." sourceTitle="Wikimedia Commons: Mays detached escapement (Wellcome Collection)" sourceUrl="https://commons.wikimedia.org/wiki/File:Clocks;_an_escapement_mechanism._Engraving_by_W._Kelsall_aft_Wellcome_V0023849EL.jpg" />

Máy tính giữ hai loại thời gian. *Đồng hồ treo tường* (wall clock) cho ngày giờ; nó có thể nhảy khi máy đồng bộ với máy chủ thời gian. *Đồng hồ đơn điệu* (monotonic clock) chỉ đếm tiến, nên là thứ đúng để đo một việc mất bao lâu. `time.Now()` trả về cả hai trong một `time.Time`. Khi encode một thời điểm ra JSON, chỉ số đọc của đồng hồ treo tường được ghi ra, nên sau khi decode, `t1` và `t2` cùng một thời điểm nhưng là hai giá trị khác nhau. `==` so sánh mọi phần của struct, kể cả số đọc đơn điệu, và cho `false`. `t1.Equal(t2)` so sánh thời điểm và cho `true`. Hãy so sánh thời gian bằng `Equal` (hoặc `Before` và `After`), đừng dùng `==`.

### Số decode vào `any` là `float64`

Nếu decode vào `map[string]any`, compiler không biết cấu trúc của mình, nên mọi số JSON đều thành `float64`. Một `float64` chỉ giữ chính xác số nguyên tới 2^53, tức 9007199254740992. Chương trình decode 9007199254740993, lớn hơn đúng một đơn vị, và nhận lại ...992. Một ID lớn như vậy bị đổi âm thầm, và đó là cách một ID database lớn bị làm tròn khi đi qua một handler tổng quát. Hai cách sửa: decode vào struct có field `int64`, hoặc gọi `UseNumber()` trên decoder, giữ nguyên các chữ số dưới dạng `json.Number` để mình tự đổi sang `int64`.

<Concepts title="Mấy khái niệm ở mục này">

- **Method promotion (đưa method lên)**: khi một struct nhúng một kiểu, method của kiểu được nhúng gọi được trên struct ngoài, và struct ngoài thoả cùng các interface.
- **Wall clock và monotonic clock**: wall clock cho biết ngày giờ và có thể nhảy; monotonic clock chỉ chạy tiến và dùng để đo khoảng thời gian. `time.Time` từ `time.Now()` giữ cả hai.
- **Độ chính xác của `float64`**: số thực 64-bit chỉ lưu chính xác số nguyên tới 2^53. Số nguyên lớn hơn bị làm tròn.

</Concepts>

## 5. `database/sql` là một pool

Package chuẩn `database/sql` cho mình một kiểu duy nhất để nói chuyện với database, `*sql.DB`. Dù tên vậy, nó không phải một connection. Nó là một *pool*: một tập các connection mà package mở khi cần, giao cho từng người gọi một lúc và nhận lại cho người kế tiếp. Service `Todo` giữ dữ liệu trong bộ nhớ, nhưng một service thật sẽ giữ một `*sql.DB` giống cách nó giữ `store`. Driver thật mà bạn import (cho PostgreSQL, MySQL...) ở đây không quan trọng lắm, nên chương trình dưới dùng một driver giả chỉ đếm số connection đã mở. Nhờ vậy mình thấy được pool mà không cần database.

```go
package main

import (
	"context"
	"database/sql"
	"database/sql/driver"
	"errors"
	"fmt"
	"sync/atomic"
	"time"
)

// fakeDriver stands in for a real database driver (such as pgx). It only
// counts how many connections were opened.
type fakeDriver struct{ opened atomic.Int32 }

func (d *fakeDriver) Open(name string) (driver.Conn, error) {
	d.opened.Add(1)
	return fakeConn{}, nil
}

type fakeConn struct{}

func (fakeConn) Prepare(string) (driver.Stmt, error) { return nil, errors.New("not needed") }
func (fakeConn) Close() error                         { return nil }
func (fakeConn) Begin() (driver.Tx, error)            { return nil, errors.New("not needed") }

func main() {
	d := &fakeDriver{}
	sql.Register("fake", d)

	db, err := sql.Open("fake", "host=db")
	fmt.Println("sql.Open error:", err, "| connections opened:", d.opened.Load())

	ctx := context.Background()
	fmt.Println("Ping error:", db.PingContext(ctx), "| connections opened:", d.opened.Load())

	db.SetMaxOpenConns(2)
	c1, _ := db.Conn(ctx) // takes connection 1 and keeps it
	c2, _ := db.Conn(ctx) // takes connection 2 and keeps it
	fmt.Println("holding 2 of 2 connections")

	waitCtx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
	defer cancel()
	_, err = db.Conn(waitCtx) // a third caller has to queue
	fmt.Println("third caller:", err)
	fmt.Printf("stats: open=%d inUse=%d waitCount=%d\n",
		db.Stats().OpenConnections, db.Stats().InUse, db.Stats().WaitCount)

	c1.Close() // hand one back
	c3, err := db.Conn(ctx)
	fmt.Println("after releasing one:", err, "| connections opened:", d.opened.Load())
	c2.Close()
	c3.Close()
}
```

1. `sql.Open` không trả lỗi và **mở 0 connection** (#78). Nó chỉ kiểm tra tham số và dựng pool. Với driver thật nó cũng thành công dù database đang sập. Hãy gọi `db.PingContext(ctx)` lúc khởi động để biết sớm; chính lần ping đã mở connection đầu tiên.
2. Với `SetMaxOpenConns(2)`, hai người gọi giữ hết cả hai connection. Người gọi thứ ba không bị lỗi. Nó xếp hàng chờ, và chỉ timeout của `context` mới đưa nó ra sau 200 ms. Hình dạng này giống chuyện thiếu timeout ở mục 1: không có hạn chót của context thì người gọi đó chờ cho tới khi có ai trả connection.
3. Khi `c1` được trả lại, người gọi kế tiếp dùng lại nó chứ không mở connection thứ ba.

Thứ giữ connection trong một service thật thường là kết quả query mà bạn quên đóng. Đây là dạng của một hàm đọc rows. Nó cần driver thật, nên chỉ là bản phác:

```go
func names(ctx context.Context, db *sql.DB) ([]string, error) {
	rows, err := db.QueryContext(ctx, "SELECT title FROM todos")
	if err != nil {
		return nil, err
	}
	defer rows.Close() // gives the connection back to the pool
	var out []string
	for rows.Next() {
		var title string
		if err := rows.Scan(&title); err != nil {
			return nil, err
		}
		out = append(out, title)
	}
	return out, rows.Err() // Next() also returns false when something went wrong
}
```

`rows.Next()` trả `false` cả khi hết dòng lẫn khi có lỗi làm dừng việc đọc, nên sau vòng lặp bạn phải kiểm tra `rows.Err()`. Chính `defer rows.Close()` trả connection về pool; nếu một nhánh code quên nó, pool nhỏ đi một connection mỗi lần nhánh đó chạy.

Pool có bốn thông số. Mặc định lấy từ `go doc`:

| Thông số | Mặc định | Điều khiển gì |
|---|---|---|
| `SetMaxOpenConns(n)` | `0`, không giới hạn | số connection mở tối đa cùng lúc; phần còn lại xếp hàng |
| `SetMaxIdleConns(n)` | `2` | số connection giữ sẵn khi rảnh |
| `SetConnMaxLifetime(d)` | không giới hạn | một connection được dùng lại bao lâu trước khi bị thay |
| `SetConnMaxIdleTime(d)` | không giới hạn | một connection được rảnh bao lâu trước khi bị đóng |

Không giới hạn số connection mở nghĩa là một đợt tải có thể mở nhiều connection hơn database cho phép. Hãy đặt `SetMaxOpenConns` bằng con số database phục vụ nổi, và cho connection một tuổi thọ để firewall hay load balancer âm thầm cắt connection cũ không để lại cho bạn những connection chết.

<Concepts title="Mấy khái niệm ở mục này">

- **Connection pool**: một tập connection sẵn sàng dùng chung cho nhiều người gọi. Người gọi lấy một cái, dùng và trả lại.
- **`sql.Open` và `Ping`**: `sql.Open` dựng pool mà không nhất thiết kết nối; `PingContext` ép kết nối và chứng minh database với tới được.

</Concepts>

## 6. Go trong container

Container chạy chương trình của mình với những giới hạn mà chương trình không thấy trực tiếp. Giới hạn quan trọng ở đây là CPU. Trong Kubernetes, `limits.cpu: "2"` trên một pod trở thành một thiết lập kernel cho container, và bộ lập lịch Linux thực thi nó gọi là CFS (Completely Fair Scheduler). Để hiểu cái gì hỏng, trước hết cần hiểu `GOMAXPROCS`.

`GOMAXPROCS` là số goroutine mà runtime của Go cho chạy cùng một lúc, mỗi cái trên một logical processor (`P`), như [bài 13](/blog/go-concurrency-scheduler-channels-context-mutexes/) giải thích. Nó cũng là số thread có thể đốt CPU cùng lúc.

### Cái bẫy CFS Throttling trên Kubernetes (`#100`)

CFS cấp cho container một *quota* thời gian CPU trên mỗi *chu kỳ* 100 ms. Giới hạn 2 CPU là quota 200 ms thời gian CPU trong mỗi 100 ms. Khi các thread của container cộng lại dùng hết quota, kernel dừng tất cả chúng cho đến khi chu kỳ mới bắt đầu. Đó là *throttling* (bị bóp). Nó không phải crash, cũng không phải lỗi. Process chỉ đứng lại một lúc, và biểu hiện ra ngoài là độ trễ.

Trước Go 1.25, `GOMAXPROCS` mặc định bằng số CPU của máy, bất kể giới hạn của container. Trên máy 6 CPU với giới hạn 2, Go chạy 6 thread cùng lúc, và 6 thread bận dùng hết 200 ms CPU chỉ trong khoảng 33 ms. Sau đó mọi thứ chờ hết phần còn lại của chu kỳ.

<GoP14CfsWindow />

Mình đã chạy thật chứ không chỉ tính. Chương trình dưới in quota của container (file `cpu.max`), số CPU và `GOMAXPROCS`. Rồi nó đốt CPU trên mọi `P` trong 3 giây. Trong lúc đó nó liên tục xin ngủ 1 ms và ghi lại lần thức dậy trễ nhất, và cuối cùng đọc từ `cpu.stat` của container xem bao nhiêu chu kỳ 100 ms đã bị bóp.

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"strings"
	"time"
)

func cgroupFile(name string) string {
	b, err := os.ReadFile("/sys/fs/cgroup/" + name)
	if err != nil {
		return err.Error()
	}
	return strings.TrimSpace(string(b))
}

// throttled pulls two counters out of the cgroup's cpu.stat file.
func throttled() (periods, count string) {
	for _, line := range strings.Split(cgroupFile("cpu.stat"), "\n") {
		f := strings.Fields(line)
		switch f[0] {
		case "nr_periods":
			periods = f[1]
		case "nr_throttled":
			count = f[1]
		}
	}
	return
}

func main() {
	fmt.Println("cpu.max (quota period):", cgroupFile("cpu.max"))
	fmt.Println("NumCPU:", runtime.NumCPU(), " GOMAXPROCS:", runtime.GOMAXPROCS(0))

	// Burn CPU on every P for 3 seconds, and watch how late a 1 ms sleeper wakes up.
	stop := time.Now().Add(3 * time.Second)
	for i := 0; i < runtime.GOMAXPROCS(0); i++ {
		go func() {
			for time.Now().Before(stop) {
			}
		}()
	}
	var worst time.Duration
	for time.Now().Before(stop) {
		t := time.Now()
		time.Sleep(time.Millisecond)
		if late := time.Since(t) - time.Millisecond; late > worst {
			worst = late
		}
	}
	p, n := throttled()
	fmt.Printf("periods: %s, throttled periods: %s, worst wake-up delay: %v\n", p, n, worst.Round(time.Millisecond))
}
```

Mình build cho Linux bằng Go 1.27.1 và chạy trong container giới hạn 2 CPU trên máy 6 CPU, hai lần, một lần với mặc định và một lần với `GOMAXPROCS=6` trong môi trường, là giá trị mà mặc định cũ sẽ chọn. Runtime container là OrbStack. Nó đặt cùng file `cpu.max` mà Kubernetes ghi cho một giới hạn CPU, nhưng đây không phải một cluster Kubernetes.

|---|---|---|---|
| mặc định, lần 1 | 2 | 11 trên 31 | 46 ms |
| mặc định, lần 2 | 2 | 4 trên 31 | 45 ms |
| `GOMAXPROCS=6`, lần 1 | 6 | 30 trên 31 | 103 ms |
| `GOMAXPROCS=6`, lần 2 | 6 | 30 trên 31 | 93 ms |

Với 6 thread, gần như chu kỳ nào cũng bị bóp và một lệnh ngủ 1 ms thức dậy trễ tới 103 ms. Với 2 thì tốt hơn nhiều, nhưng chưa sạch. Độ trễ tệ nhất vẫn khoảng 45 ms, và vài chu kỳ vẫn bị bóp. Đó là vì Go còn có các thread khác ngoài 2 goroutine đang chạy (garbage collector và các helper của runtime), và chúng cũng tiêu quota. Giới hạn CPU vẫn có thể bóp một chương trình Go cư xử tử tế. Go 1.25 làm vấn đề nhỏ lại; nó không xoá hẳn.

Cái Go 1.25 đổi là giá trị mặc định. [Ghi chú phát hành](https://go.dev/doc/go1.25) nói rằng trên Linux runtime giờ đọc giới hạn CPU của cgroup, và nếu nó thấp hơn số logical CPU thì nó thành `GOMAXPROCS` mặc định. Nó dùng *limit* và bỏ qua *request* theo cách gọi của Kubernetes. `go doc runtime.GOMAXPROCS` nói thêm rằng runtime tiếp tục cập nhật giá trị nếu giới hạn đổi. Mình cũng thử giới hạn lẻ trên cùng máy: `--cpus=1.5` cho `GOMAXPROCS` 2, `--cpus=2.5` cho 3 và `--cpus=0.5` cho 2, nghĩa là nó làm tròn lên và không bao giờ xuống dưới 2.

Còn một cái bẫy nữa, và nó nằm trong `go.mod`. Mặc định mới gắn với phiên bản ngôn ngữ ở dòng `go` của module. `go doc` nói `containermaxprocs=0` là mặc định cho phiên bản ngôn ngữ 1.24 trở xuống. Mình lấy cùng chương trình, đặt `go 1.24` trong `go.mod` và build bằng Go 1.27.1:

<TerminalOutput command="go build -o gmp-old . (go.mod ghi go 1.24), rồi docker run --cpus=2" label="Toolchain Go 1.27.1 · go 1.24 trong go.mod · 2 CPU" caption="Toolchain mới cũng không giúp được khi dòng go còn cũ.">
```text

NumCPU: 6  GOMAXPROCS: 6
periods: 31, throttled periods: 30, worst wake-up delay: 90ms
```

Vậy nâng compiler chưa đủ: hãy nâng cả dòng `go`, hoặc tự đặt `GOMAXPROCS` (biến môi trường hoặc gọi `runtime.GOMAXPROCS`; cái nào cũng tắt hành vi tự động). Với Go cũ hơn 1.25, cách sửa thường dùng là package `go.uber.org/automaxprocs`.

Làm sao biết nó đang xảy ra? Throttling không hiện ra là CPU cao. Một pod có thể trông rảnh theo trung bình mà vẫn bị dừng từng đợt. Kubernetes cung cấp `container_cpu_cfs_throttled_seconds_total`, và [Go observability](/blog/go-observability-metrics-microbenchmarks-benchstat/) chỉ cách đọc nó bên cạnh mức dùng CPU.

<Concepts title="Mấy khái niệm ở mục này">

- **CFS quota và throttling**: bộ lập lịch Linux cấp cho container một ngân sách thời gian CPU trên mỗi chu kỳ 100 ms. Khi các thread của container tiêu hết, kernel dừng chúng cho tới chu kỳ sau.
- **`GOMAXPROCS`**: số goroutine chạy cùng một lúc. Từ Go 1.25, với dòng `go` là 1.25 trở lên, giá trị mặc định theo giới hạn CPU của container, làm tròn lên, tối thiểu là 2.
- **CPU limit và CPU request**: trong Kubernetes, limit là cái trần gây ra throttling. Request là gợi ý để xếp lịch, và Go không đọc nó.

</Concepts>

## Điểm rút ra (Key takeaways)

- **Đặt timeout cho mọi thứ phải chờ.** `http.DefaultClient`, `http.Get` và `http.ListenAndServe` không có cái nào. Tự dựng `http.Client` với `Timeout` và các giới hạn Transport, và tự dựng `http.Server` với timeout của nó.
- **Đọc nốt response body rồi mới đóng.** Body chưa đọc làm client bỏ connection; năm request với body 5.000.000 byte dùng năm connection thay vì một.
- **Đặt `return` sau `http.Error`.** Không thì handler chạy tiếp, và thứ nó ghi sau đó bị nối vào response.
- **Số trần là nano giây.** `time.Sleep(1000)` là 1 micro giây. `time.After` trong vòng lặp rò khoảng 199 MB cho mỗi triệu vòng trên Go 1.22.12 và không rò gì trên Go 1.27.1.
- **Đừng tin mù quáng vào việc đi qua JSON rồi quay về.** `time.Time` nhúng sẵn thay JSON của struct, `==` trên thời gian có thể `false` cho cùng một thời điểm, và số decode vào `any` là `float64`.
- **`sql.Open` tạo pool và không kết nối.** Ping lúc khởi động, đóng mọi `sql.Rows`, kiểm tra `rows.Err()` và giới hạn pool.
- **Trong container, xem dòng `go` và theo dõi throttling.** Go 1.25 cùng dòng `go` từ 1.25 trở lên làm `GOMAXPROCS` theo giới hạn CPU, nhưng một giới hạn vẫn có thể bóp bạn: 4 đến 11 trên 31 chu kỳ trong các lần chạy của mình, so với 30 trên 31 khi `GOMAXPROCS=6`.
