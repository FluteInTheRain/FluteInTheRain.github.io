### A nil pointer that broke TLS handshakes

In May 2026, a Go developer filed [issue #79392](https://github.com/golang/go/issues/79392) after TLS handshakes in their HTTP client failed with a bare `invalid argument` error. They had written a small helper, `getKeyLogWriter() *os.File`, that returned `nil` when debug key logging was turned off, and assigned its result to `tls.Config.KeyLogWriter`. Even though `getKeyLogWriter()` returned `nil`, every HTTPS request aborted.

Inside Go's standard library (`src/crypto/tls/common.go`), `writeKeyLog` starts with `if c.KeyLogWriter == nil { return nil }`. Because `KeyLogWriter` has interface type `io.Writer` and received a typed `*os.File` nil pointer instead of an untyped `nil`, that check evaluated to `false`. The TLS stack went ahead and called `Write` on a `nil` `*os.File`, which returned `os.ErrInvalid`.

<GoP12KeyLogTrap />

Reproducing that bug locally on Go 1.27.1 against a test TLS server shows the exact error. In Go 1.27, the TLS package added a `"tls: KeyLogWriter: "` prefix to help point callers to the culprit, yet the handshake still fails:

```go
package main

import (
	"crypto/tls"
	"fmt"
	"net/http"
	"net/http/httptest"
	"os"
)

var debug = false

func getKeyLogWriter() *os.File {
	if !debug {
		return nil
	}
	return os.Stdout
}

func main() {
	srv := httptest.NewTLSServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	}))
	defer srv.Close()

	client := &http.Client{
		Transport: &http.Transport{
			TLSClientConfig: &tls.Config{
				InsecureSkipVerify: true,
				KeyLogWriter:       getKeyLogWriter(),
			},
		},
	}

	resp, err := client.Get(srv.URL)
	if err != nil {
		fmt.Printf("ERROR: %v\n", err)
		return
	}
	defer resp.Body.Close()
	fmt.Printf("OK: status=%d\n", resp.StatusCode)
}
```

That single failure exposes the mechanical rules behind Go's abstractions. This post examines five areas where everyday habits trip on how Go implements interfaces, generics, and initialization:

1. **Runtime interface headers and the typed-nil trap**: how `runtime.iface` and `eface` store `(type, data)`, and why returning a nil concrete pointer as `error` or `io.Writer` fails `== nil` checks.
2. **Consumer-side interfaces and `io.Reader` inputs**: why producers return concrete structs, why callers declare minimal interfaces, and why `any` erases compile-time safety.
3. **Generic types and when generics fit**: building `Stack[T]` step by step, using `slices` and `maps`, and choosing between type parameters and interfaces.
4. **Type-embedding hazards**: how anonymous embedding leaks mutex locks, breaks JSON marshaling, and keeps the inner receiver.
5. **Functional options, `init()`, and accessors**: configuring optional server fields cleanly without zero-value ambiguity, avoiding hidden side effects in `init()`, and naming Go getters and setters.

<Callout type="note" title="TL;DR">
A Go interface value holds two words, a type descriptor and a data pointer, so a typed nil pointer makes the interface non-nil. Define small interfaces in the consumer package, accept `io.Reader` instead of filenames, and return concrete structs from producers. Reach for generics such as `Stack[T]`, `slices`, and `maps` when the same algorithm spans multiple types, keep `sync.Mutex` and `time.Time` as named fields rather than embedded ones, configure optional parameters with functional options, and replace stateful `init()` blocks with explicit constructors.
</Callout>

<Concepts>

- **`iface` and `eface`**: Go's two-word runtime structs for non-empty interfaces (`tab` + `data`) and empty `any` interfaces (`_type` + `data`).
- **Typed `nil`**: a `nil` pointer of a concrete type (such as `(*os.File)(nil)`) stored inside an interface, leaving the interface's type word non-nil.
- **Consumer-side interface**: an interface declared in the package that calls a dependency rather than the package that implements it.
- **Type embedding**: declaring a struct or interface field without a field name so its methods and fields are promoted onto the outer type.
- **Functional options**: variadic option functions (`func(*options) error`) passed to a constructor to validate and override defaults cleanly.

</Concepts>

## Runtime interface headers and the typed-nil trap

An `error` or `io.Writer` variable in Go is a two-word header, not a single pointer. One word records the concrete type inside the box, and the second word points to the value itself. Think of a labeled shipping box: even if you put nothing inside the box, sticking a `*os.File` label on the outside means the box is no longer empty when someone checks `box == nil`.

Go's runtime defines both interface layouts directly in `src/runtime/runtime2.go`:

<GitHubCode repo="golang/go" path="src/runtime/runtime2.go" lines="L184-L192" url="https://github.com/golang/go/blob/go1.27.1/src/runtime/runtime2.go#L184-L192" caption="Exact runtime representation of iface (interfaces with methods) and eface (any) in Go 1.27.1.">
```go
type iface struct {
	tab  *itab
	data unsafe.Pointer
}

type eface struct {
	_type *_type
	data  unsafe.Pointer
}
```
</GitHubCode>

An `iface` (`tab`, `data`) represents any interface with at least one method, such as `error` or `io.Reader`. The `tab` field points to an `itab` table computed by the compiler and cached at runtime, linking the interface type to the concrete type's method pointers. An `eface` (`_type`, `data`) represents `any` (`interface{}`), which has zero methods and only needs the concrete type descriptor.

Go considers an interface value equal to `nil` only when **both** words (`tab`/`_type` and `data`) are zero. That rule interacts with another Go feature: calling a method on a `nil` pointer receiver is valid. A method in Go is syntactic sugar for a function whose first argument is the receiver, so if a method never dereferences a field (or guards against `nil`), calling it on a nil pointer runs without panicking.

```go
package main

import (
	"fmt"
	"os"
)

type Greeter struct{}

func (g *Greeter) Hello() string {
	return "hello from nil receiver"
}

func main() {
	var g *Greeter
	fmt.Println(g.Hello())

	var f *os.File
	_, err := f.Write([]byte("secret\n"))
	fmt.Println("nil *os.File Write err:", err)
}
```

```text
hello from nil receiver
nil *os.File Write err: invalid argument
```
</TerminalOutput>

That exact mechanism causes the typed-`nil` `error` bug. If a method builds a `*MultiError` pointer and returns it as `error` on the happy path when the pointer is still `nil`, Go packs `tab = *itab(error, *MultiError)` and `data = nil`. Because `tab` is non-zero, `err == nil` is `false` even though `fmt.Println(err)` prints `<nil>`.

```go
package main

import (
	"errors"
	"fmt"
	"strings"
)

type MultiError struct {
	errs []string
}

func (m *MultiError) Add(err error) {
	m.errs = append(m.errs, err.Error())
}

func (m *MultiError) Error() string {
	return strings.Join(m.errs, "; ")
}

type Customer struct {
	Age  int
	Name string
}

func (c Customer) ValidateBuggy() error {
	var m *MultiError
	if c.Age < 0 {
		m = &MultiError{}
		m.Add(errors.New("age is negative"))
	}
	if c.Name == "" {
		if m == nil {
			m = &MultiError{}
		}
		m.Add(errors.New("name is empty"))
	}
	return m // boxes (*MultiError)(nil) into a non-nil error interface
}

func (c Customer) ValidateFixed() error {
	var m *MultiError
	if c.Age < 0 {
		m = &MultiError{}
		m.Add(errors.New("age is negative"))
	}
	if c.Name == "" {
		if m == nil {
			m = &MultiError{}
		}
		m.Add(errors.New("name is empty"))
	}
	if m != nil {
		return m
	}
	return nil // leaves both tab and data zeroed
}

func main() {
	c := Customer{Age: 33, Name: "Lan"}

	err1 := c.ValidateBuggy()
	fmt.Printf("buggy: err == nil -> %v, type=%T, val=%v\n", err1 == nil, err1, err1)

	err2 := c.ValidateFixed()
	fmt.Printf("fixed: err == nil -> %v, type=%T, val=%v\n", err2 == nil, err2, err2)
}
```

<TerminalOutput command="go run typed_nil.go" label="Go 1.27.1 · darwin/arm64" caption="ValidateBuggy returns a non-nil error holding type *main.MultiError and nil pointer data; ValidateFixed returns an untyped nil.">
```text
buggy: err == nil -> false, type=*main.MultiError, val=<nil>
fixed: err == nil -> true, type=<nil>, val=<nil>
```
</TerminalOutput>

To prevent this across your codebase, never assign or return a concrete pointer variable when the function returns `error` or another interface unless you guard `if ptr != nil` first and `return nil` explicitly on the success branch. You can trace how `iface.tab` and `iface.data` change in the first tab of the playground below (the second tab reviews error wrapping with `%w` vs. `%v`).

<GoArchInterfaceErrorDemo />

How to wrap errors with `%w`, inspect chains with `errors.Is` and `errors.As`, and handle each error once is covered in [Go errors](/blog/go-errors-defer-panic/).

<Concepts>

- **`itab` descriptor**: the runtime table pairing an interface type with a concrete type and storing direct function pointers for its methods.
- **Nil pointer receiver**: a `nil` pointer passed as a method's receiver parameter; valid in Go as long as the method checks for `nil` before dereferencing fields.
- **Typed `nil` interface**: an interface whose `tab` or `_type` word is populated while `data` is `nil`, making `iface != nil` evaluate to `true`.

</Concepts>

## Consumer-side interfaces, any, and io.Reader inputs

Developers arriving from Java or C# often write an interface beside every struct and inject it everywhere from day one. In Go, that habit creates **interface pollution**: extra layers of indirection with only one concrete type behind them, making code harder to trace without adding real flexibility.

<Figure src={bellSwitch} alt="Telephone switchboard operators plugging patch cords into modular jack interfaces in 1950" caption="Each plug defines only the minimal jack contract it expects, so the wiring behind the board can change without rewriting callers." sourceTitle="Wikimedia Commons: Bell telephone magazine (1950)" sourceUrl="https://commons.wikimedia.org/wiki/File:Bell_telephone_magazine_(1950)_(14755092795).jpg" />

In Go, abstractions work best when callers discover them as a concrete need appears. Three situations justify creating an interface:

- **Factoring out common behavior**: multiple types already perform the same operation, such as `sort.Interface` (`Len`, `Less`, `Swap`) or `io.Reader`.
- **Decoupling at a boundary**: a service needs to talk to storage (`store`) during production and an in-memory double in unit tests.
- **Restricting capabilities**: a consumer receives a read-write struct like `IntConfig` (`Get` and `Set`) and accepts a one-method `intConfigGetter` (`Get() int`) so callers inside that module cannot mutate config accidentally.

Rob Pike explains why keeping interfaces small (one or two methods) makes them far easier to compose:

<YouTube id="PAAkCSZUG1c" title="Go Proverbs with Rob Pike — Interface Design Philosophy" start={318} end={386} caption="Between 5:18 and 6:26, Rob Pike explains why 'the bigger the interface, the weaker the abstraction' and how tiny contracts compose." sourceTitle="The Go Programming Language — Gopherfest 2015" />

Where you place the interface matters just as much as its size. Put interfaces on the **consumer side** (in the calling package) and return **concrete structs** from the **producer side** (the implementing package). Because Go interfaces are satisfied implicitly, a producer package like `store` returns `*Store` without importing any caller, while `billing` defines a one-method `customerGetter` and `reporting` defines `customerLister`.

```go
// Producer package: return the concrete struct, not an interface
package store

func New() *Store { return &Store{} }
func (s *Store) Get(id string) (Customer, error) { /* ... */ }
func (s *Store) ListAll() ([]Customer, error)    { /* ... */ }

// Consumer package: declare only the method billing actually calls
package billing

type customerGetter interface {
	Get(id string) (store.Customer, error)
}
```

If `store` instead declared a six-method `CustomerStorage` interface, every consumer test would have to stub all six methods even when it only called one. Worse, if `store.New()` tried to return a `billing.CustomerGetter` interface owned by the consumer, `store` would have to import `billing`, triggering a Go compile-time import cycle.

<GoP12ConsumerDeps />

Returning concrete structs while accepting interfaces follows Postel's Law ("be conservative in what you send, be liberal in what you accept"). There are two deliberate standard-library exceptions where an interface is known up front: `error` itself, and combinators like `io.LimitReader(r Reader, n int64) Reader` inside `io`, where the contract (`io.Reader`) is universal across the ecosystem.

### Accept io.Reader instead of a filename

Functions that parse logs, CSV uploads, or config files often take `filename string` and call `os.Open(filename)` inside. That forces every unit test to write temporary files on disk and blocks you from reusing the parser on an HTTP request body (such as `r.Body` in our [HTTP service](/blog/go-http-service-net-http-json-middleware/)).

Accept `io.Reader` instead. Callers can pass an `*os.File` in production, `r.Body` in an HTTP handler, or `strings.NewReader(...)` directly inside a fast unit test:

```go
package main

import (
	"bufio"
	"fmt"
	"io"
	"strings"
)

func countEmptyLines(r io.Reader) (int, error) {
	scanner := bufio.NewScanner(r)
	empty := 0
	for scanner.Scan() {
		if strings.TrimSpace(scanner.Text()) == "" {
			empty++
		}
	}
	return empty, scanner.Err()
}

func main() {
	input := "todo: buy milk\n\ntodo: write tests\n   \ndone\n"
	n, err := countEmptyLines(strings.NewReader(input))
	fmt.Printf("empty=%d err=%v\n", n, err)
}
```

### Avoid any when static types fit

The predeclared `any` identifier (an alias for `interface{}`) accepts every Go value, which removes all compile-time constraints. If you design a store API with `Set(id string, v any) error` and `Get(id string) (any, error)`, callers can pass an `int` where a `Customer` was expected and only discover the mismatch at runtime via a type assertion.

Prefer explicit typed methods such as `GetCustomer`, `SetCustomer`, `GetContract`, and `SetContract`, or use generic type parameters when the container logic truly stays identical across types. Keep `any` strictly for genuinely open-ended APIs like `encoding/json.Marshal(v any)`, `fmt.Println(a ...any)`, or SQL query arguments in `database/sql`.

| Abstraction tool | Best used when | Runtime / compile trade-off | Common misuse |
| :--- | :--- | :--- | :--- |
| Concrete struct (`*Store`) | Single implementation or constructor return | Zero indirection; callers see all methods | Creating matching `StoreInterface` beside it |
| Small consumer interface (1–2 methods) | I/O boundaries (`io.Reader`), test doubles, read-only views | Static `*itab` lookup, one indirect call | Fat 10-method producer interfaces |
| Generics (`[T any]`) | Reusable containers (`Stack[T]`), `slices`/`maps` helpers | Type-checked at compile time; zero `any` boxing | Wrapping `io.Writer` in `[T io.Writer]` |
| `any` (`interface{}`) | Codecs (`json.Marshal`), formatting, SQL args | Boxes scalars into `eface`, loses compile checks | Using `any` instead of a typed signature or `[T]` |

<Concepts>

- **Interface pollution**: adding premature interfaces where only one implementation exists and callers gain no decoupling.
- **Postel's law in Go**: accept narrow interfaces at function boundaries, return concrete structs from constructors.
- **`any`**: Go's alias for `interface{}`; carries no methods and conveys no static contract to callers or the compiler.

</Concepts>

## Generic types, slices, maps, and when generics fit

In [Go structs and interfaces](/blog/go-structs-methods-interfaces/), we used generic functions like `Max[T cmp.Ordered]` for comparisons across numbers and strings. Type parameters also work on structs and container types, letting you write one type-safe data structure instead of falling back to `[]any` and runtime type assertions.

<QuoteCard author="Ian Lance Taylor" role="Go Generics Co-Designer" sourceTitle="When To Use Generics (Go Blog)" sourceUrl="https://go.dev/blog/when-generics">
Write Go code cleanly by calling methods directly or through tiny interfaces first, and introduce type parameters only when you find yourself copying identical algorithm bodies over multiple distinct types.
</QuoteCard>

Suppose you want a last-in, first-out `Stack` that works for integers, strings, or `Todo` items from our [HTTP service](/blog/go-http-service-net-http-json-middleware/). Declare the type parameter `[T any]` on the struct, then repeat `[T]` on each method's receiver (`(s *Stack[T])`). When the stack is empty, `var zero T` produces the zero value of whatever type `T` stands for:

```go
package main

import (
	"cmp"
	"fmt"
	"maps"
	"slices"
)

type Stack[T any] struct {
	items []T
}

func (s *Stack[T]) Push(v T) {
	s.items = append(s.items, v)
}

func (s *Stack[T]) Pop() (T, bool) {
	if len(s.items) == 0 {
		var zero T
		return zero, false
	}
	top := s.items[len(s.items)-1]
	s.items = s.items[:len(s.items)-1]
	return top, true
}

func (s *Stack[T]) Len() int {
	return len(s.items)
}

type Todo struct {
	ID    int
	Title string
}

func main() {
	var nums Stack[int]
	nums.Push(10)
	nums.Push(20)
	top, ok := nums.Pop()
	fmt.Printf("pop=%d ok=%v len=%d\n", top, ok, nums.Len())

	todos := []Todo{
		{ID: 3, Title: "deploy"},
		{ID: 1, Title: "write tests"},
		{ID: 2, Title: "review PR"},
	}
	slices.SortFunc(todos, func(a, b Todo) int {
		return cmp.Compare(a.ID, b.ID)
	})
	fmt.Println("sorted:", todos)

	counts := map[string]int{"open": 2, "done": 5, "blocked": 1}
	keys := slices.Sorted(maps.Keys(counts))
	fmt.Println("keys:", keys)
}
```

<TerminalOutput command="go run stack.go" label="Go 1.27.1 · darwin/arm64" caption="Stack[int] pops an int without type assertions, while standard library packages slices and maps handle struct sorting and sorted map key extraction.">
```text
pop=20 ok=true len=1
sorted: [{1 write tests} {2 review PR} {3 deploy}]
keys: [blocked done open]
```
</TerminalOutput>

Notice the standard library packages `slices` and `maps` right in `main`: before writing a loop to sort structs, clone a map, or collect sorted keys from a map, reach for `slices.SortFunc`, `maps.Clone`, `maps.Keys`, and `slices.Sorted`. One detail: `maps.Keys` does not return a slice. It returns an iterator (`iter.Seq[string]`, Go 1.23+) that hands out keys one at a time, and `slices.Sorted` collects them into a new sorted slice.

### Constraints, `comparable`, and `~`

A **constraint** is an interface that restricts which types can instantiate a type parameter:

- **`any`**: permits every type, suitable when you only store or move values (`Stack[T any]`).
- **`comparable`**: permits types supporting `==` and `!=`, which you need for map keys (`K comparable` in `map[K]V`) or equality checks like `slices.Contains`.
- **Type unions and `~`**: writing `int | string` allows exact `int` and `string` types, whereas `~int | ~string` matches any defined type whose *underlying* type is `int` or `string` (such as `type UserID int`). Without `~`, passing `UserID` fails to compile:

```go
type stringerInt interface {
	int
	String() string
}

type UserID int

func (id UserID) String() string { return strconv.Itoa(int(id)) }

func format[T stringerInt](v T) string { return v.String() }
```

### Generic methods vs. interface methods

Since Go 1.27, concrete methods can declare their own method-level type parameters (`func (c *Cache) Get[V any](k string)`), whereas **interface methods cannot declare type parameters**. Attempting `type Getter interface { Get[T any](k string) T }` fails immediately at compile time (`interface method must have no type parameters`), and generic methods on concrete types cannot satisfy interface requirements.

<GoP12StackGenerics />

The decision rule between generics and interfaces stays simple:
- **Use generics** for data structures (`Stack[T]`, trees, caches), slice/map/channel utilities (`slices`, `maps`, `merge[T any](ch1, ch2 <-chan T)`), or factoring out pure algorithmic boilerplate across types.
- **Use an interface** whenever behavior varies across implementations or when a function only needs to call a method on its argument. Writing `func save[T io.Writer](w T)` adds zero clarity or capability over `func save(w io.Writer)`.

Go does not compile one copy of a generic function per type. It groups types by their GC shape (how they look in memory to the garbage collector): all pointer types such as `*A` and `*B` share one compiled body, and a small static dictionary (`.dict`) tells that body which real type it is working with. Step through it below, compared with `eface` boxing and plain interfaces:

<GoGenericsStencilDemo />

<Concepts>

- **Generic type instantiation**: supplying a concrete type argument (such as `Stack[int]`) so the compiler checks operations and specializes code for that type.
- **`comparable`**: built-in constraint satisfied by every Go type that supports `==` and `!=` (required for map keys).
- **Underlying type operator (`~`)**: constraint prefix (`~int`) matching both `int` and any custom type defined on top of `int`.
- **GCShape stenciling**: Go's compiler strategy where pointer types share one compiled generic function body guided by a tiny static `.dict` type dictionary.

</Concepts>

## Type-embedding hazards and receiver identity

Go lets you declare a field inside a struct without giving it a name (`type Service struct { Logger }`). That **embedding** promotes the inner type's exported fields and methods onto the outer struct, which is handy for delegating work, yet creates three traps when used just to save keystrokes.

The first hazard is **leaking internal locks**. If you embed `sync.Mutex` without a field name inside a struct, both `Lock()` and `Unlock()` become part of the outer struct's exported API, so any caller can lock the struct and accidentally deadlock it.

The second hazard is **accidentally implementing an interface via promoted methods**. If you embed `time.Time` inside an `Event` struct (`ID`, `Name`), `Event` inherits `time.Time.MarshalJSON()`. When you pass `Event` to `json.Marshal`, `encoding/json` calls the promoted `MarshalJSON` method and outputs only the timestamp string, silently dropping `ID` and `Name`.

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type BadCache struct {
	sync.Mutex
	items map[string]string
}

type Event struct {
	time.Time
	ID   int
	Name string
}

type Logger struct {
	Prefix string
}

func (l Logger) Name() string     { return "Logger" }
func (l Logger) Describe() string { return "I am " + l.Name() }

type Service struct {
	Logger
	Port int
}

func (s Service) Name() string { return "Service" }

func main() {
	c := BadCache{items: map[string]string{"a": "1"}}
	c.Lock() // compiles: Lock() leaked onto BadCache's public API
	c.items["b"] = "2"
	c.Unlock()
	fmt.Println("cache len:", len(c.items))

	ev := Event{
		Time: time.Date(2026, 11, 23, 9, 0, 0, 0, time.UTC),
		ID:   42,
		Name: "deploy",
	}
	b, _ := json.Marshal(ev)
	fmt.Println("json:", string(b))

	s := Service{Logger: Logger{Prefix: "[svc]"}, Port: 8080}
	fmt.Println("s.Name():", s.Name())
	fmt.Println("s.Describe():", s.Describe())
}
```

<TerminalOutput command="go run embedding.go" label="Go 1.27.1 · darwin/arm64" caption="BadCache exposes Lock() publicly, Event loses ID and Name during json.Marshal, and s.Describe() prints Logger instead of Service.">
```text
cache len: 2
json: "2026-11-23T09:00:00Z"
s.Name(): Service
s.Describe(): I am Logger
```
</TerminalOutput>

Look at the last two lines too: **embedding is composition, not OOP subclassing**. When `s.Describe()` runs, `Describe` belongs to `Logger`, so its receiver is `s.Logger`, not `s`. Inside `Describe`, calling `l.Name()` invokes `Logger.Name`, returning `"I am Logger"` even though `Service` defines its own `Name()` method.

The third hazard is **ambiguous promotion**. If a struct embeds two types `A` and `B` that both define `Ping()`, calling `c.Ping()` refuses to compile (`ambiguous selector c.Ping`), forcing callers to qualify `c.A.Ping()` or `c.B.Ping()`.

<GoP12EmbeddingPromo />

Keep embedding narrow and intentional:
- **Never embed** just to shorten `s.At` vs. `s.Time`, and never embed `sync.Mutex` or `sync.RWMutex` (give them an unexported field name like `mu sync.Mutex`, as our [HTTP service](/blog/go-http-service-net-http-json-middleware/) store does).
- **Do embed** when you genuinely want the outer type to expose and satisfy an inner behavior without writing forwarding boilerplate (for example, wrapping an `io.WriteCloser` so `Write` and `Close` promote onto a custom audit writer, or composing `io.ReadWriter` from `io.Reader` and `io.Writer`).

<Concepts>

- **Method promotion**: exposing an embedded field's exported methods directly on the enclosing struct so callers can invoke `outer.Method()`.
- **Receiver identity**: an embedded method always receives the embedded field as its receiver, never the outer enclosing struct.
- **Ambiguous selector**: compile error raised when two embedded fields at the same depth promote methods or fields with identical names.

</Concepts>

## Functional options for extensible constructors

Suppose you are building a reusable `NewServer` constructor for an HTTP service like the one in [Build a Go HTTP service](/blog/go-http-service-net-http-json-middleware/). `addr` is required, while `port` and `readTimeout` should be optional with clean rules: if the caller omits the port, default to `8080`; if they pass `0`, bind a random ephemeral port; if they pass a negative number, return a validation error.

Go has no default parameter values or function overloading. Putting optional fields into a plain `Config{Port int}` struct fails immediately: an omitted `Port` initializes to its zero value `0`, making `Config{}` indistinguishable from `Config{Port: 0}`. Switching to `Port *int` forces callers to allocate integer variables just to take their address, and passing an empty `Config{}` at every default call site adds noise. A GoF-style `ConfigBuilder` fixes pointer ergonomics, yet forces error checks to wait until `.Build()`.

Rob Pike and Dave Cheney popularized the **functional options** pattern to solve all three constraints cleanly:

1. Store settings in an unexported `options` struct (`port *int`, `readTimeout time.Duration`).
2. Define `type Option func(*options) error`.
3. Provide exported `With...` helpers that return closures validating and setting one field.
4. Accept `opts ...Option` variadically in `NewServer(addr string, opts ...Option)`.

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

type Server struct {
	addr        string
	port        int
	readTimeout time.Duration
}

type options struct {
	port        *int
	readTimeout time.Duration
}

type Option func(*options) error

func WithPort(port int) Option {
	return func(o *options) error {
		if port < 0 {
			return errors.New("port must not be negative")
		}
		o.port = &port
		return nil
	}
}

func WithReadTimeout(d time.Duration) Option {
	return func(o *options) error {
		if d <= 0 {
			return errors.New("read timeout must be positive")
		}
		o.readTimeout = d
		return nil
	}
}

func NewServer(addr string, opts ...Option) (*Server, error) {
	cfg := options{
		readTimeout: 10 * time.Second,
	}
	for _, opt := range opts {
		if err := opt(&cfg); err != nil {
			return nil, err
		}
	}

	port := 8080
	if cfg.port != nil {
		if *cfg.port == 0 {
			port = 54321
		} else {
			port = *cfg.port
		}
	}

	return &Server{addr: addr, port: port, readTimeout: cfg.readTimeout}, nil
}

func main() {
	s1, _ := NewServer("127.0.0.1")
	s2, _ := NewServer("127.0.0.1", WithPort(0), WithReadTimeout(5*time.Second))
	_, err := NewServer("127.0.0.1", WithPort(-1))

	fmt.Printf("default: addr=%s port=%d readTimeout=%s\n", s1.addr, s1.port, s1.readTimeout)
	fmt.Printf("custom:  addr=%s port=%d readTimeout=%s\n", s2.addr, s2.port, s2.readTimeout)
	fmt.Printf("invalid: %v\n", err)
}
```

<TerminalOutput command="go run options.go" label="Go 1.27.1 · darwin/arm64" caption="Calling NewServer with no options uses defaults; WithPort(0) distinguishes explicit 0 from omitted, and WithPort(-1) returns an error immediately.">
```text
default: addr=127.0.0.1 port=8080 readTimeout=10s
custom:  addr=127.0.0.1 port=54321 readTimeout=5s
invalid: port must not be negative
```
</TerminalOutput>

<GoP12FunctionalOptions />

Callers who want defaults simply write `NewServer("127.0.0.1")` without a dummy config struct, and adding a future `WithTLS(...)` option breaks zero existing call sites. When constructors or cleanup helpers schedule work with `defer`, remember that `defer` captures its arguments on the `defer` line and waits for the enclosing function to return (covered in [Go types and functions](/blog/go-variables-types-pointers-functions/) and [Go errors](/blog/go-errors-defer-panic/)).

<Concepts>

- **Variadic parameter (`opts ...Option`)**: syntax allowing callers to pass zero, one, or many `Option` values, received inside the function as `[]Option`.
- **Closure**: an anonymous function returned by `WithPort` that keeps access to the `port` variable after `WithPort` returns.
- **Zero-value ambiguity**: inability to distinguish an omitted struct field from one explicitly set to `0`, `""`, or `false` without pointers or options.

</Concepts>

## Package initialization with init() and struct accessors

Two patterns carry strong habits from Java and Spring into Go codebases: running setup logic automatically in `init()`, and generating `GetX`/`SetX` methods on every struct field.

### How `init()` runs and when to avoid it

An `init()` function takes no arguments, returns nothing (`func init()`), and runs automatically when a package is imported, before `main()` starts. Go initializes packages in a strict order: imported dependencies initialize recursively first (including blank imports like `_ "pkg"` used solely for side effects), then package-level constants and variables, then `init()` functions (sorted alphabetically by file name, then top-to-bottom within a file), and finally `main()`.

```go
package main

import "fmt"

var configReady = func() bool {
	fmt.Println("1. package var")
	return true
}()

func init() {
	fmt.Println("2. first init")
}

func init() {
	fmt.Println("3. second init")
}

func main() {
	fmt.Println("4. main, configReady =", configReady)
}
```

<TerminalOutput command="go run init_order.go" label="Go 1.27.1 · darwin/arm64" caption="Package-level variable initializers execute before init() functions, which run in source order before main().">
```text
1. package var
2. first init
3. second init
4. main, configReady = true
```
</TerminalOutput>

You also cannot invoke `init()` manually from your own code: trying `init()` inside `main()` fails with `undefined: init`.

<GoP12InitOrder />

Avoid putting database pools, HTTP clients, or config loading inside `init()` for three reasons:
1. **Broken error handling**: `init()` cannot return an `error`, leaving `panic` as the only escape hatch instead of letting callers retry or pick a fallback.
2. **Coupled unit tests**: Go runs every `init()` in a package before running `go test`, forcing pure unit tests in that package to open external connections.
3. **Global state**: anything `init()` opens must live in a package-level global variable that any function can mutate and tests struggle to isolate.

Replace stateful `init()` blocks with explicit constructors (`openDB(dsn string) (*sql.DB, error)`), keeping `init()` strictly for static, failure-free registration that creates no globals (such as registering static HTTP routes or image decoders). For how to organize packages cleanly and control symbol visibility with `internal/`, see [Go basics](/blog/go-first-program-modules-packages/).

### Getters and setters in Go

Unlike Java, Go has no generated properties and does not expect `GetX`/`SetX` boilerplate around ordinary struct fields. The standard library itself exposes struct fields directly: for instance, `time.Timer` exposes `timer.C` as a public field rather than hiding it behind `GetC()`.

Add accessor methods only when you gain concrete value: validating writes, guarding reads with a mutex, computing a derived value, or preserving forward compatibility if an internal representation might change. When you do write them, follow Go's naming rule: omit the `Get` prefix on the getter (`Balance()`, not `GetBalance()`), and use `Set` on the setter (`SetBalance`):

```go
package main

import "fmt"

type Customer struct {
	balance int
}

func (c *Customer) Balance() int {
	return c.balance
}

func (c *Customer) SetBalance(amount int) {
	if amount < 0 {
		c.balance = 0
		return
	}
	c.balance = amount
}

func main() {
	var c Customer
	c.SetBalance(-50)
	fmt.Println("clamped:", c.Balance())
	c.SetBalance(120)
	fmt.Println("updated:", c.Balance())
}
```

<TerminalOutput command="go run getters.go" label="Go 1.27.1 · darwin/arm64" caption="Write Balance() without a Get prefix and SetBalance() when encapsulation enforces an invariant such as clamping negative balances.">
```text
clamped: 0
updated: 120
```
</TerminalOutput>

<Concepts>

- **`init()` function**: zero-argument, zero-return hook executed automatically once per package during startup, before `main()` or tests.
- **Blank import (`_ "pkg"`)**: importing a package solely to trigger its `var` initializers and `init()` side effects without referencing its exported symbols.
- **Go accessor naming**: getter methods drop the `Get` prefix (`Balance()`), while mutating setters keep `Set` (`SetBalance()`).

</Concepts>

## Key takeaways

- **Never return a typed `nil` pointer when the signature is an interface**: a `(*MyError)(nil)` or `(*os.File)(nil)` fills `iface.tab`, making `val == nil` return `false`; return literal untyped `nil` explicitly.
- **Discover interfaces on the consumer side and return concrete structs**: accept narrow inputs like `io.Reader` instead of filenames, avoid `any` when types are known, and let callers define 1–2 method interfaces where they need decoupling.
- **Use generics for shared data structures and algorithms, not behavior variation**: build containers like `Stack[T]` and use `slices`/`maps` to avoid `any` boxing, while keeping I/O contracts as plain interfaces.
- **Guard what type embedding promotes**: never embed `sync.Mutex` or `time.Time` merely as a shortcut, and remember promoted methods bind to the inner field's receiver rather than the outer struct.
- **Use functional options for optional constructor config, avoid stateful `init()`, and skip empty getters/setters**: keep initialization error-returning and explicit, and name getters without `Get` when invariants justify encapsulation.

### Con trỏ nil làm gãy cả phiên bắt tay TLS

Tháng 5/2026, một lập trình viên Go gửi [issue #79392](https://github.com/golang/go/issues/79392) khi mọi kết nối TLS từ HTTP client của họ đều gãy với một câu lỗi cộc lốc: `invalid argument`. Họ viết một hàm phụ trợ `getKeyLogWriter() *os.File` trả về `nil` mỗi khi tắt chế độ debug, rồi gán thẳng kết quả vào trường `tls.Config.KeyLogWriter`. Dù hàm trả về `nil`, toàn bộ request HTTPS vẫn hỏng.

Bên trong thư viện chuẩn Go (`src/crypto/tls/common.go`), hàm `writeKeyLog` mở đầu bằng `if c.KeyLogWriter == nil { return nil }`. Vì `KeyLogWriter` có kiểu interface `io.Writer` và nhận vào một con trỏ typed `*os.File` đang `nil` thay vì `nil` thuần, phép kiểm tra đó cho ra `false`. Tầng TLS vẫn gọi `Write` lên con trỏ `*os.File` bằng `nil`, và hàm đó trả về lỗi `os.ErrInvalid`.

<GoP12KeyLogTrap />

Chạy thử lại tình huống đó ngay trên máy với Go 1.27.1 và server TLS test để xem đúng thông báo lỗi. Từ Go 1.27, gói `crypto/tls` đã bọc thêm tiền tố `"tls: KeyLogWriter: "` để người gọi dễ lần ra chỗ sai, nhưng kết nối vẫn bị ngắt như thường:

```go
package main

import (
	"crypto/tls"
	"fmt"
	"net/http"
	"net/http/httptest"
	"os"
)

var debug = false

func getKeyLogWriter() *os.File {
	if !debug {
		return nil
	}
	return os.Stdout
}

func main() {
	srv := httptest.NewTLSServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	}))
	defer srv.Close()

	client := &http.Client{
		Transport: &http.Transport{
			TLSClientConfig: &tls.Config{
				InsecureSkipVerify: true,
				KeyLogWriter:       getKeyLogWriter(),
			},
		},
	}

	resp, err := client.Get(srv.URL)
	if err != nil {
		fmt.Printf("ERROR: %v\n", err)
		return
	}
	defer resp.Body.Close()
	fmt.Printf("OK: status=%d\n", resp.StatusCode)
}
```

1. **Cấu trúc interface dưới runtime và bẫy typed nil**: cách `runtime.iface` và `eface` lưu cặp `(type, data)`, và lý do con trỏ `nil` có kiểu cụ thể phá hỏng phép kiểm tra `== nil`.
2. **Interface phía người gọi và đầu vào `io.Reader`**: vì sao bên cung cấp nên trả struct cụ thể, bên gọi tự khai báo interface nhỏ, và vì sao `any` làm mất kiểm tra tĩnh.
3. **Kiểu generic và ranh giới dùng generics**: xây dựng từng bước `Stack[T]`, tận dụng `slices` và `maps`, rồi phân định khi nào chọn generics thay cho interface.
4. **Bẫy khi nhúng kiểu (type embedding)**: nhúng ẩn danh làm rò rỉ khóa mutex, làm mất dữ liệu khi `json.Marshal`, và giữ nguyên receiver của struct bên trong.
5. **Functional options, `init()` và getter/setter**: cấu hình tham số tùy chọn mà không vướng nhập nhằng zero value, loại bỏ tác dụng phụ ngầm trong `init()`, và cách đặt tên hàm truy cập chuẩn Go.

<Callout type="note" title="Tóm tắt nhanh (TL;DR)">
Một biến interface trong Go gồm hai phần: mô tả kiểu và con trỏ dữ liệu, nên con trỏ typed nil vẫn làm biến interface khác nil. Hãy đặt interface nhỏ ngay ở package sử dụng, nhận `io.Reader` thay cho đường dẫn file, và trả struct cụ thể từ package cung cấp. Dùng generics như `Stack[T]`, `slices`, `maps` khi cùng một logic áp dụng cho nhiều kiểu dữ liệu, đặt tên trường rõ ràng cho `sync.Mutex` và `time.Time` thay vì nhúng ẩn danh, cấu hình tham số tùy chọn qua functional options, và thay hàm `init()` chứa trạng thái bằng hàm tạo tường minh.
</Callout>

</Callout>

<Concepts title="Giải thích nhanh mấy khái niệm mở đầu">

- **`iface` và `eface`**: hai cấu trúc hai ngăn của Go runtime cho interface có method (`tab` + `data`) và interface rỗng `any` (`_type` + `data`).
- **Typed `nil`**: một con trỏ `nil` mang kiểu cụ thể (ví dụ `(*os.File)(nil)`) được gói vào interface, khiến ngăn kiểu của interface không còn trống.
- **Consumer-side interface (interface phía người gọi)**: interface khai báo ngay trong package sử dụng phụ thuộc thay vì đặt trong package cài đặt phụ thuộc đó.
- **Type embedding (nhúng kiểu)**: khai báo trường trong struct hoặc interface mà không đặt tên, giúp đẩy các trường và method bên trong ra kiểu bọc ngoài.
- **Functional options**: mẫu truyền các hàm tùy chọn biến thiên (`func(*options) error`) vào hàm tạo để kiểm tra hợp lệ và ghi đè giá trị mặc định.

</Concepts>

## Cấu trúc interface dưới runtime và bẫy typed-nil

Biến kiểu `error` hay `io.Writer` trong Go là một cặp hai trường, không phải một con trỏ đơn. Một ngăn ghi loại dữ liệu thực sự nằm bên trong, ngăn kia trỏ tới dữ liệu đó. Bạn có thể hình dung một thùng hàng dán nhãn: dù bên trong thùng rỗng hoàn toàn, hễ bên ngoài đã dán nhãn `*os.File` thì phép kiểm tra `thùng == nil` không còn đúng nữa.

Trong mã nguồn runtime của Go (`src/runtime/runtime2.go`), hai cấu trúc này được khai báo ngay sát nhau:

<GitHubCode repo="golang/go" path="src/runtime/runtime2.go" lines="L184-L192" url="https://github.com/golang/go/blob/go1.27.1/src/runtime/runtime2.go#L184-L192" caption="Cấu trúc runtime chính xác của iface (interface có method) và eface (any) trong Go 1.27.1.">
```go
type iface struct {
	tab  *itab
	data unsafe.Pointer
}

type eface struct {
	_type *_type
	data  unsafe.Pointer
}
```
</GitHubCode>

`iface` (`tab`, `data`) đại diện cho mọi interface có ít nhất một method, như `error` hay `io.Reader`. Trường `tab` trỏ tới bảng `itab` do compiler dựng sẵn và cache lúc chạy, nối kiểu interface với địa chỉ các method của kiểu cụ thể. Còn `eface` (`_type`, `data`) dùng riêng cho `any` (`interface{}`), vì không có method nào nên chỉ cần mô tả kiểu `_type`.

Go chỉ coi một biến interface bằng `nil` khi **cả hai** ngăn (`tab`/`_type` và `data`) đều bằng không. Quy tắc này kết hợp với một đặc điểm khác của Go: gọi method trên con trỏ `nil` là hợp lệ. Method trong Go thực chất chỉ là hàm nhận receiver làm tham số đầu tiên, nên chừng nào thân hàm không đọc trường qua con trỏ `nil` (hoặc tự kiểm tra `nil` trước), lời gọi vẫn chạy bình thường.

```go
package main

import (
	"fmt"
	"os"
)

type Greeter struct{}

func (g *Greeter) Hello() string {
	return "hello from nil receiver"
}

func main() {
	var g *Greeter
	fmt.Println(g.Hello())

	var f *os.File
	_, err := f.Write([]byte("secret\n"))
	fmt.Println("nil *os.File Write err:", err)
}
```

```text
hello from nil receiver
nil *os.File Write err: invalid argument
```
</TerminalOutput>

Chính cơ chế đó tạo ra bẫy `error` kiểu typed `nil`. Khi hàm khởi tạo một biến con trỏ `*MultiError` ở đầu hàm, mọi điều kiện đều hợp lệ nên biến vẫn là `nil`, rồi cuối hàm viết `return m` với chữ ký trả về `error`, Go tự gói `tab = *itab(error, *MultiError)` và `data = nil`. Vì `tab` khác không, `err == nil` cho ra `false` dù `fmt.Println(err)` in ra `<nil>`.

```go
package main

import (
	"errors"
	"fmt"
	"strings"
)

type MultiError struct {
	errs []string
}

func (m *MultiError) Add(err error) {
	m.errs = append(m.errs, err.Error())
}

func (m *MultiError) Error() string {
	return strings.Join(m.errs, "; ")
}

type Customer struct {
	Age  int
	Name string
}

func (c Customer) ValidateBuggy() error {
	var m *MultiError
	if c.Age < 0 {
		m = &MultiError{}
		m.Add(errors.New("age is negative"))
	}
	if c.Name == "" {
		if m == nil {
			m = &MultiError{}
		}
		m.Add(errors.New("name is empty"))
	}
	return m // đóng gói (*MultiError)(nil) thành error interface khác nil
}

func (c Customer) ValidateFixed() error {
	var m *MultiError
	if c.Age < 0 {
		m = &MultiError{}
		m.Add(errors.New("age is negative"))
	}
	if c.Name == "" {
		if m == nil {
			m = &MultiError{}
		}
		m.Add(errors.New("name is empty"))
	}
	if m != nil {
		return m
	}
	return nil // giữ cả tab lẫn data đều bằng 0
}

func main() {
	c := Customer{Age: 33, Name: "Lan"}

	err1 := c.ValidateBuggy()
	fmt.Printf("buggy: err == nil -> %v, type=%T, val=%v\n", err1 == nil, err1, err1)

	err2 := c.ValidateFixed()
	fmt.Printf("fixed: err == nil -> %v, type=%T, val=%v\n", err2 == nil, err2, err2)
}
```

<TerminalOutput command="go run typed_nil.go" label="Go 1.27.1 · darwin/arm64" caption="ValidateBuggy trả về error khác nil giữ kiểu *main.MultiError và dữ liệu nil; ValidateFixed trả về nil thuần.">
```text
buggy: err == nil -> false, type=*main.MultiError, val=<nil>
fixed: err == nil -> true, type=<nil>, val=<nil>
```
</TerminalOutput>

Để tránh bẫy này, đừng bao giờ trả thẳng biến con trỏ cụ thể khi chữ ký hàm trả về `error` hay một interface khác: hãy kiểm tra `if ptr != nil` rồi `return nil` tường minh ở nhánh thành công. Bạn có thể bấm thử tab đầu trong mô phỏng bên dưới để xem hai ngăn `iface.tab` và `iface.data` đổi ra sao (tab thứ hai ôn lại bọc lỗi `%w` với `%v`).

<GoArchInterfaceErrorDemo />

Cách bọc lỗi với `%w`, kiểm tra chuỗi bằng `errors.Is` và `errors.As`, cũng như quy tắc xử lý lỗi đúng một lần đã được trình bày riêng trong [Lỗi trong Go](/blog/go-errors-defer-panic/).

<Concepts title="Giải thích nhanh mấy thuật ngữ ở mục này">

- **Bảng `itab`**: cấu trúc runtime nối giữa một interface với một kiểu dữ liệu cụ thể, kèm danh sách con trỏ hàm của các method khớp với interface đó.
- **Nil pointer receiver**: con trỏ `nil` được truyền vào làm receiver cho method; hoàn toàn hợp lệ miễn method tự kiểm tra `nil` trước khi truy cập trường.
- **Typed `nil` interface**: biến interface có ngăn `tab` hoặc `_type` khác trống trong khi ngăn `data` bằng `nil`, làm phép so sánh `!= nil` trả về `true`.

</Concepts>

## Interface phía người gọi, any và đầu vào io.Reader

Người mới chuyển từ Java hay C# hay giữ thói quen tạo sẵn một interface đứng cạnh mọi struct rồi truyền vòng qua khắp nơi. Trong Go, thói quen đó gây **interface pollution (lạm dụng interface)**: sinh ra nhiều lớp gọi gián tiếp khi mới chỉ có đúng một bản cài đặt thật, làm code rối khi đọc mà không mang lại lợi ích tách rời nào.

<Figure src={bellSwitch} alt="Các nữ tổng đài viên năm 1950 cắm dây nối vào bảng giắc tổng đài điện thoại" caption="Mỗi đầu cắm chỉ quy định chuẩn giắc tối thiểu nó cần, nên cách đi dây phía sau đổi thế nào cũng không làm gãy bên gọi." sourceTitle="Wikimedia Commons: Bell telephone magazine (1950)" sourceUrl="https://commons.wikimedia.org/wiki/File:Bell_telephone_magazine_(1950)_(14755092795).jpg" />

Trong Go, trừu tượng nên được rút ra khi xuất hiện nhu cầu thực tế. Có ba tình huống đáng để định nghĩa một interface:

- **Gom hành vi chung**: nhiều kiểu đã làm cùng một việc, như `sort.Interface` (`Len`, `Less`, `Swap`) hay `io.Reader`.
- **Tách phụ thuộc ở ranh giới**: một tầng nghiệp vụ cần chạy với database thật (`store`) khi lên production nhưng lại muốn dùng bản giả lập trong bộ nhớ lúc chạy unit test.
- **Giới hạn quyền thao tác**: một module nhận struct cấu hình `IntConfig` (có cả `Get` lẫn `Set`) nhưng chỉ khai báo interface một hàm `intConfigGetter` (`Get() int`) để đảm bảo code trong module đó không thể sửa nhầm cấu hình.

Rob Pike giải thích vì sao interface càng ít method (một đến hai hàm) thì càng dễ ghép nối:

<YouTube id="PAAkCSZUG1c" title="Go Proverbs với Rob Pike — Triết lý thiết kế Interface" start={318} end={386} caption="Từ 5:18 đến 6:26, Rob Pike giải thích câu 'the bigger the interface, the weaker the abstraction' và lý do interface nhỏ dễ kết hợp." sourceTitle="The Go Programming Language — Gopherfest 2015" />

Vị trí đặt interface quan trọng ngang với số lượng method của nó. Hãy đặt interface ở **phía người gọi (consumer)** và cho **phía cung cấp (producer)** trả về struct cụ thể. Nhờ cơ chế khớp ngầm định của Go, package `store` chỉ cần trả về `*Store` mà không biết sự tồn tại của bất kỳ package gọi nào, còn `billing` tự khai báo `customerGetter` và `reporting` tự khai báo `customerLister`.

```go
// Bên cung cấp: trả về struct cụ thể, không ép interface sớm
package store

func New() *Store { return &Store{} }
func (s *Store) Get(id string) (Customer, error) { /* ... */ }
func (s *Store) ListAll() ([]Customer, error)    { /* ... */ }

// Bên gọi: chỉ khai báo đúng method mà billing cần dùng
package billing

type customerGetter interface {
	Get(id string) (store.Customer, error)
}
```

Nếu `store` tự định nghĩa sẵn `CustomerStorage` gồm sáu method, mọi bài test bên `billing` đều phải giả lập đủ cả sáu method dù chỉ gọi đúng `Get`. Còn nếu `store.New()` lại trả về kiểu interface `billing.CustomerGetter` nằm bên `billing`, `store` buộc phải import `billing` và trình biên dịch sẽ chặn ngay lỗi import vòng tròn (import cycle).

<GoP12ConsumerDeps />

Nhận interface và trả về struct cụ thể chính là nguyên tắc Postel ("chặt chẽ ở đầu ra, rộng rãi ở đầu vào") trong Go. Thư viện chuẩn chỉ phá lệ ở vài chỗ mà mức trừu tượng đã chắc chắn ngay từ đầu: bản thân kiểu `error`, và các hàm ghép nối trong gói `io` như `io.LimitReader(r Reader, n int64) Reader`.

### Nhận `io.Reader` thay cho tên file

Những hàm đọc log, file CSV hay file cấu hình hay nhận `filename string` rồi tự gọi `os.Open(filename)` bên trong. Cách viết đó ép mọi unit test phải tạo hàng loạt file nháp trên ổ cứng và khiến hàm không thể dùng lại cho luồng byte từ mạng (như `r.Body` trong [bài dịch vụ HTTP](/blog/go-http-service-net-http-json-middleware/)).

Thay vì nhận tên file, hãy nhận `io.Reader`. Lúc chạy thật bạn truyền `*os.File` hay `r.Body`, còn trong unit test bạn truyền thẳng `strings.NewReader(...)`:

```go
package main

import (
	"bufio"
	"fmt"
	"io"
	"strings"
)

func countEmptyLines(r io.Reader) (int, error) {
	scanner := bufio.NewScanner(r)
	empty := 0
	for scanner.Scan() {
		if strings.TrimSpace(scanner.Text()) == "" {
			empty++
		}
	}
	return empty, scanner.Err()
}

func main() {
	input := "todo: buy milk\n\ntodo: write tests\n   \ndone\n"
	n, err := countEmptyLines(strings.NewReader(input))
	fmt.Printf("empty=%d err=%v\n", n, err)
}
```

### Hạn chế `any` khi đã biết rõ kiểu

Từ khóa `any` (tên gọi khác của `interface{}`) nhận mọi giá trị, đồng nghĩa với việc bỏ qua toàn bộ kiểm tra kiểu lúc biên dịch. Nếu bạn thiết kế kho lưu trữ với `Set(id string, v any) error` và `Get(id string) (any, error)`, người gọi hoàn toàn có thể truyền nhầm một số `int` vào chỗ đáng lẽ cần `Customer` và chỉ phát hiện lỗi khi chạy thật qua phép ép kiểu.

Hãy viết thẳng các hàm mang kiểu rõ ràng như `GetCustomer`, `SetCustomer`, `GetContract`, `SetContract`, hoặc dùng generics khi cấu trúc dữ liệu thật sự dùng chung cho mọi kiểu. Chỉ giữ `any` ở những nơi thực sự nhận đầu vào tùy ý như `encoding/json.Marshal(v any)`, `fmt.Println(a ...any)`, hay danh sách tham số câu truy vấn trong `database/sql`.

| Công cụ trừu tượng | Dùng đúng lúc khi | Đánh đổi lúc biên dịch / chạy | Lỗi hay gặp |
| :--- | :--- | :--- | :--- |
| Struct cụ thể (`*Store`) | Chỉ có 1 bản cài đặt hoặc trả về từ hàm tạo | Không tốn nhảy gián tiếp; thấy hết method | Tạo dư `StoreInterface` đứng cạnh |
| Interface nhỏ phía gọi (1–2 hàm) | Biên I/O (`io.Reader`), viết test giả lập, giới hạn quyền | Tra `*itab` tĩnh, tốn một lần gọi gián tiếp | Ôm cả chục method bên package cung cấp |
| Generics (`[T any]`) | Cấu trúc dữ liệu (`Stack[T]`), hàm `slices`/`maps` | Kiểm kiểu lúc biên dịch; 0 đóng hộp `any` | Bọc `io.Writer` vào `[T io.Writer]` |
| `any` (`interface{}`) | Encoder (`json.Marshal`), format chuỗi, tham số SQL | Đóng hộp giá trị vào `eface`, mất kiểm tra tĩnh | Thay thế hàm có kiểu cụ thể hoặc `[T]` |

<Concepts title="Giải thích nhanh mấy thuật ngữ ở mục này">

- **Interface pollution (lạm dụng interface)**: tạo sẵn hàng loạt interface khi mới chỉ có một kiểu cài đặt và chưa cần tách phụ thuộc.
- **Nguyên tắc Postel trong Go**: đầu vào nhận interface hẹp nhất có thể, đầu ra trả về struct cụ thể.
- **`any`**: tên gọi khác của `interface{}`; không yêu cầu method nào và không mang lại kiểm tra kiểu tĩnh ở lúc biên dịch.

</Concepts>

## Kiểu generic, slices, maps và ranh giới sử dụng

Ở [Struct và interface trong Go](/blog/go-structs-methods-interfaces/), mình đã dùng hàm generic `Max[T cmp.Ordered]` để so sánh số và chuỗi. Tham số kiểu cũng gắn được vào định nghĩa struct để tạo các cấu trúc dữ liệu dùng chung cho nhiều kiểu mà không cần ép mọi phần tử vào `[]any` rồi kiểm tra kiểu thủ công lúc chạy.

<QuoteCard author="Ian Lance Taylor" role="Đồng tác giả Go Generics" sourceTitle="When To Use Generics (Go Blog)" sourceUrl="https://go.dev/blog/when-generics">
Hãy viết code Go theo cách tự nhiên nhất bằng struct và interface nhỏ trước, và chỉ đưa tham số kiểu vào đúng lúc bạn thấy mình đang phải sao chép nguyên logic thuật toán giống hệt nhau cho nhiều kiểu khác nhau.
</QuoteCard>

Giả sử bạn cần một ngăn xếp `Stack` vào sau ra trước cho số nguyên, chuỗi, hoặc struct `Todo` từ [bài dịch vụ HTTP](/blog/go-http-service-net-http-json-middleware/). Bạn đặt tham số kiểu `[T any]` ngay sau tên struct, rồi lặp lại `[T]` ở receiver của từng method (`(s *Stack[T])`). Khi ngăn xếp rỗng, câu lệnh `var zero T` tạo ra đúng giá trị mặc định (zero value) của kiểu `T`:

```go
package main

import (
	"cmp"
	"fmt"
	"maps"
	"slices"
)

type Stack[T any] struct {
	items []T
}

func (s *Stack[T]) Push(v T) {
	s.items = append(s.items, v)
}

func (s *Stack[T]) Pop() (T, bool) {
	if len(s.items) == 0 {
		var zero T
		return zero, false
	}
	top := s.items[len(s.items)-1]
	s.items = s.items[:len(s.items)-1]
	return top, true
}

func (s *Stack[T]) Len() int {
	return len(s.items)
}

type Todo struct {
	ID    int
	Title string
}

func main() {
	var nums Stack[int]
	nums.Push(10)
	nums.Push(20)
	top, ok := nums.Pop()
	fmt.Printf("pop=%d ok=%v len=%d\n", top, ok, nums.Len())

	todos := []Todo{
		{ID: 3, Title: "deploy"},
		{ID: 1, Title: "write tests"},
		{ID: 2, Title: "review PR"},
	}
	slices.SortFunc(todos, func(a, b Todo) int {
		return cmp.Compare(a.ID, b.ID)
	})
	fmt.Println("sorted:", todos)

	counts := map[string]int{"open": 2, "done": 5, "blocked": 1}
	keys := slices.Sorted(maps.Keys(counts))
	fmt.Println("keys:", keys)
}
```

<TerminalOutput command="go run stack.go" label="Go 1.27.1 · darwin/arm64" caption="Stack[int] lấy ra trực tiếp kiểu int mà không cần ép kiểu, còn gói slices và maps trong thư viện chuẩn lo sẵn việc sắp xếp struct và lấy khóa của map theo thứ tự.">
```text
pop=20 ok=true len=1
sorted: [{1 write tests} {2 review PR} {3 deploy}]
keys: [blocked done open]
```

Lưu ý hai gói `slices` và `maps` ngay trong `main`: trước khi tự viết vòng lặp sắp xếp slice struct, nhân bản map hay gom key rồi sort, hãy kiểm tra `slices.SortFunc`, `maps.Clone`, `maps.Keys` và `slices.Sorted`. Một chi tiết: `maps.Keys` không trả về slice. Nó trả về một iterator (`iter.Seq[string]`, Go 1.23+) đưa ra từng key một, và `slices.Sorted` gom chúng vào một slice mới đã sắp xếp.

### Ràng buộc kiểu (constraint), `comparable` và dấu `~`

Một **constraint (ràng buộc kiểu)** thực chất là một interface giới hạn tập kiểu mà tham số generic được phép nhận:

- **`any`**: nhận mọi kiểu, phù hợp khi cấu trúc chỉ lưu và di chuyển phần tử (`Stack[T any]`).
- **`comparable`**: chỉ nhận những kiểu hỗ trợ phép `==` và `!=`, bắt buộc dùng cho key của map (`K comparable` trong `map[K]V`) hoặc các phép tìm kiếm như `slices.Contains`.
- **Hợp kiểu `|` và dấu `~`**: viết `int | string` chỉ cho phép đúng hai kiểu gốc `int` và `string`, còn `~int | ~string` khớp với mọi kiểu tự định nghĩa có kiểu nền là `int` hoặc `string` (chẳng hạn `type UserID int`). Thiếu dấu `~`, trình biên dịch sẽ từ chối `UserID`:

```go
type stringerInt interface {
	int
	String() string
}

type UserID int

func (id UserID) String() string { return strconv.Itoa(int(id)) }

func format[T stringerInt](v T) string { return v.String() }
```

### Method generic vs. method trong interface

Từ Go 1.27, method trên kiểu cụ thể đã được phép khai báo tham số kiểu riêng (`func (c *Cache) Get[V any](k string)`), nhưng **method bên trong interface vẫn không được phép có tham số kiểu**. Khai báo `type Getter interface { Get[T any](k string) T }` sẽ bị chặn ngay lúc biên dịch (`interface method must have no type parameters`), và một method generic cũng không thể dùng để thỏa mãn method của interface.

<GoP12StackGenerics />

Quy tắc chọn giữa generics và interface vẫn rất gọn:
- **Dùng generics** cho cấu trúc dữ liệu (`Stack[T]`, cây, cache), hàm tiện ích trên slice/map/channel (`slices`, `maps`, `merge[T any](ch1, ch2 <-chan T)`), hoặc gom thuật toán thuần chạy trên nhiều kiểu.
- **Dùng interface** khi hành vi thay đổi theo từng bản cài đặt, hoặc hàm chỉ gọi một method trên tham số nhận vào. Viết `func save[T io.Writer](w T)` không mang lại thêm tính năng hay tốc độ nào so với `func save(w io.Writer)`.

Go không biên dịch riêng một bản hàm generic cho mỗi kiểu. Nó gom các kiểu theo GC shape (hình dạng trong bộ nhớ dưới mắt bộ gom rác): mọi kiểu con trỏ như `*A` và `*B` dùng chung một bản mã đã biên dịch, và một từ điển tĩnh nhỏ (`.dict`) cho bản mã đó biết nó đang làm việc với kiểu thật nào. Bạn bấm qua từng bước ở mô phỏng dưới đây, so với chi phí đóng hộp `eface` của `any`:

<GoGenericsStencilDemo />

<Concepts title="Giải thích nhanh mấy thuật ngữ ở mục này">

- **Khởi tạo kiểu generic (instantiation)**: truyền kiểu cụ thể vào tham số kiểu (như `Stack[int]`) để trình biên dịch kiểm tra hợp lệ và sinh mã tương ứng.
- **`comparable`**: ràng buộc có sẵn đại diện cho mọi kiểu so sánh được bằng `==` và `!=`, cần thiết cho key của `map`.
- **Dấu kiểu nền (`~`)**: tiền tố trong constraint (`~int`) cho phép nhận cả `int` lẫn các kiểu mới định nghĩa dựa trên `int`.
- **GCShape stenciling**: cách compiler Go gộp các kiểu con trỏ dùng chung một bản mã máy rồi truyền kèm bảng tra `.dict` tĩnh ở lúc chạy.

</Concepts>

## Bẫy type embedding và danh tính receiver

Go cho phép khai báo một trường trong struct mà không đặt tên (`type Service struct { Logger }`). Kiểu **nhúng (embedding)** này tự động đẩy các trường và method public của kiểu bên trong lên struct bọc ngoài, rất tiện khi chuyển tiếp lời gọi, nhưng dễ tạo ba lỗi ngầm nếu lạm dụng để gõ cho ngắn.

Bẫy đầu tiên là **làm rò rỉ khóa nội bộ**. Nếu bạn nhúng `sync.Mutex` không đặt tên trường vào struct, cả `Lock()` lẫn `Unlock()` đều lộ ra thành API công khai của struct đó, khiến code bên ngoài có thể tự ý gọi khóa và gây kẹt deadlock.

Bẫy thứ hai là **vô tình thỏa mãn một interface thông qua method được đẩy lên**. Nếu bạn nhúng `time.Time` vào struct `Event` (chứa thêm `ID`, `Name`), `Event` thừa hưởng luôn method `time.Time.MarshalJSON()`. Khi gọi `json.Marshal(ev)`, gói `encoding/json` gọi thẳng `MarshalJSON` của `time.Time` và chỉ xuất ra mỗi chuỗi thời gian, làm rơi sạch `ID` lẫn `Name`.

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type BadCache struct {
	sync.Mutex
	items map[string]string
}

type Event struct {
	time.Time
	ID   int
	Name string
}

type Logger struct {
	Prefix string
}

func (l Logger) Name() string     { return "Logger" }
func (l Logger) Describe() string { return "I am " + l.Name() }

type Service struct {
	Logger
	Port int
}

func (s Service) Name() string { return "Service" }

func main() {
	c := BadCache{items: map[string]string{"a": "1"}}
	c.Lock() // biên dịch bình thường: Lock() bị lộ ra API công khai của BadCache
	c.items["b"] = "2"
	c.Unlock()
	fmt.Println("cache len:", len(c.items))

	ev := Event{
		Time: time.Date(2026, 11, 23, 9, 0, 0, 0, time.UTC),
		ID:   42,
		Name: "deploy",
	}
	b, _ := json.Marshal(ev)
	fmt.Println("json:", string(b))

	s := Service{Logger: Logger{Prefix: "[svc]"}, Port: 8080}
	fmt.Println("s.Name():", s.Name())
	fmt.Println("s.Describe():", s.Describe())
}
```

<TerminalOutput command="go run embedding.go" label="Go 1.27.1 · darwin/arm64" caption="BadCache làm lộ Lock() ra bên ngoài, Event mất sạch ID và Name khi json.Marshal, còn s.Describe() vẫn in Logger thay vì Service.">
```text
cache len: 2
json: "2026-11-23T09:00:00Z"
s.Name(): Service
s.Describe(): I am Logger
```
</TerminalOutput>

Hai dòng cuối cho thấy thêm một điểm dễ nhầm: **embedding là ghép thành phần (composition), không phải kế thừa class của OOP**. Khi gọi `s.Describe()`, hàm `Describe` vẫn thuộc về `Logger` và chạy với receiver `s.Logger`, không phải `s`. Bên trong `Describe`, lời gọi `l.Name()` luôn chạy `Logger.Name` và trả về `"I am Logger"` dù `Service` có định nghĩa `Name()` riêng.

Bẫy thứ ba là **trùng tên method từ nhiều kiểu nhúng**. Nếu struct nhúng cả `A` lẫn `B` cùng có method `Ping()`, lời gọi `c.Ping()` bị chặn lúc biên dịch (`ambiguous selector c.Ping`), buộc bạn phải ghi rõ `c.A.Ping()` hoặc `c.B.Ping()`.

<GoP12EmbeddingPromo />

Chỉ dùng embedding khi thật sự có chủ đích:
- **Không nhúng** chỉ để rút gọn `s.Time` hay cho `sync.Mutex` / `sync.RWMutex`: hãy đặt tên trường viết thường như `mu sync.Mutex` giống cấu trúc `store` trong [bài dịch vụ HTTP](/blog/go-http-service-net-http-json-middleware/).
- **Nên nhúng** khi bạn thực sự muốn struct ngoài lộ và thỏa mãn hành vi của kiểu bên trong mà khỏi phải viết lại các hàm chuyển tiếp lặp đi lặp lại (ví dụ nhúng `io.WriteCloser` để struct log tự có `Write` và `Close`, hoặc ghép `io.ReadWriter` từ `io.Reader` và `io.Writer`).

<Concepts title="Giải thích nhanh mấy thuật ngữ ở mục này">

- **Method promotion (đẩy method lên ngoài)**: cơ chế đưa các method public của trường nhúng ẩn danh thành method gọi trực tiếp được trên struct bọc ngoài.
- **Receiver identity (danh tính receiver)**: method được đẩy lên vẫn giữ receiver là trường bên trong chứ không chuyển thành struct bọc ngoài.
- **Ambiguous selector (lỗi chọn mơ hồ)**: lỗi biên dịch khi hai trường nhúng cùng cấp định nghĩa trùng tên method hoặc trường dữ liệu.

</Concepts>

## Functional options cho hàm tạo dễ mở rộng

Giả sử bạn viết một hàm tạo `NewServer` dùng lại cho dịch vụ HTTP như trong [bài dịch vụ HTTP](/blog/go-http-service-net-http-json-middleware/). Tham số `addr` là bắt buộc, còn `port` và `readTimeout` là tùy chọn với quy tắc rõ: bỏ trống `port` thì lấy mặc định `8080`, truyền `0` thì xin một cổng ngẫu nhiên, còn truyền số âm thì báo lỗi ngay.

Go không có giá trị mặc định cho tham số hàm và cũng không hỗ trợ nạp chồng hàm (overloading). Nếu gom các tham số tùy chọn vào struct `Config{Port int}`, bạn đụng ngay điểm nghẽn: trường `Port` không truyền vào sẽ tự nhận zero value `0`, khiến `Config{}` giống hệt `Config{Port: 0}`. Đổi sang con trỏ `Port *int` buộc bên gọi phải tạo biến tạm mới lấy được địa chỉ và lúc dùng mặc định vẫn phải gõ `Config{}`. Dùng Builder kiểu GoF đỡ vụ con trỏ nhưng lại đẩy việc kiểm tra lỗi lùi tận xuống bước `.Build()`.

Rob Pike và Dave Cheney phổ biến mẫu **functional options** để giải quyết gọn cả ba điểm đó:

1. Gom cấu hình vào một struct nội bộ không export tên là `options` (`port *int`, `readTimeout time.Duration`).
2. Định nghĩa `type Option func(*options) error`.
3. Tạo các hàm `With...` trả về closure kiểm tra hợp lệ và gán đúng một trường.
4. Cho `NewServer(addr string, opts ...Option)` nhận danh sách tùy chọn biến thiên.

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

type Server struct {
	addr        string
	port        int
	readTimeout time.Duration
}

type options struct {
	port        *int
	readTimeout time.Duration
}

type Option func(*options) error

func WithPort(port int) Option {
	return func(o *options) error {
		if port < 0 {
			return errors.New("port must not be negative")
		}
		o.port = &port
		return nil
	}
}

func WithReadTimeout(d time.Duration) Option {
	return func(o *options) error {
		if d <= 0 {
			return errors.New("read timeout must be positive")
		}
		o.readTimeout = d
		return nil
	}
}

func NewServer(addr string, opts ...Option) (*Server, error) {
	cfg := options{
		readTimeout: 10 * time.Second,
	}
	for _, opt := range opts {
		if err := opt(&cfg); err != nil {
			return nil, err
		}
	}

	port := 8080
	if cfg.port != nil {
		if *cfg.port == 0 {
			port = 54321
		} else {
			port = *cfg.port
		}
	}

	return &Server{addr: addr, port: port, readTimeout: cfg.readTimeout}, nil
}

func main() {
	s1, _ := NewServer("127.0.0.1")
	s2, _ := NewServer("127.0.0.1", WithPort(0), WithReadTimeout(5*time.Second))
	_, err := NewServer("127.0.0.1", WithPort(-1))

	fmt.Printf("default: addr=%s port=%d readTimeout=%s\n", s1.addr, s1.port, s1.readTimeout)
	fmt.Printf("custom:  addr=%s port=%d readTimeout=%s\n", s2.addr, s2.port, s2.readTimeout)
	fmt.Printf("invalid: %v\n", err)
}
```

<TerminalOutput command="go run options.go" label="Go 1.27.1 · darwin/arm64" caption="Gọi NewServer không kèm tùy chọn sẽ lấy mặc định; WithPort(0) tách bạch số 0 cố ý với trường bỏ trống, còn WithPort(-1) trả lỗi ngay lập tức.">
```text
default: addr=127.0.0.1 port=8080 readTimeout=10s
custom:  addr=127.0.0.1 port=54321 readTimeout=5s
invalid: port must not be negative
```
</TerminalOutput>

<GoP12FunctionalOptions />

Khi dùng mặc định, bên gọi chỉ viết ngắn gọn `NewServer("127.0.0.1")` mà không cần tạo struct rỗng, và sau này có thêm `WithTLS(...)` cũng không làm vỡ bất kỳ chỗ gọi cũ nào. Nếu trong hàm tạo hoặc hàm dọn dẹp có hẹn giờ bằng `defer`, hãy nhớ `defer` chụp tham số ngay tại dòng khai báo và chờ tới lúc hàm bọc ngoài thoát ra mới chạy (xem lại chi tiết trong [Kiểu dữ liệu và hàm trong Go](/blog/go-variables-types-pointers-functions/) và [Lỗi trong Go](/blog/go-errors-defer-panic/)).

<Concepts title="Giải thích nhanh mấy thuật ngữ ở mục này">

- **Tham số biến thiên (`opts ...Option`)**: cú pháp cho phép truyền không, một hoặc nhiều giá trị `Option`, bên trong hàm nhận thành một slice `[]Option`.
- **Closure**: hàm ẩn danh do `WithPort` trả về, vẫn giữ quyền đọc biến `port` sau khi hàm `WithPort` đã kết thúc.
- **Nhập nhằng zero value**: tình trạng không phân biệt được một trường struct cố tình đặt bằng `0`, `""`, `false` với trường bị bỏ trống nếu không dùng con trỏ hoặc options.

</Concepts>

## Khởi tạo gói bằng init() và hàm getter/setter

Hai thói quen mang từ Java và Spring sang Go dễ làm code nặng nề hơn mức cần thiết là đặt code khởi tạo kết nối vào hàm `init()` và viết sẵn cặp `GetX`/`SetX` cho mọi trường của struct.

### Thứ tự chạy của `init()` và lúc nào nên tránh

Hàm `init()` không nhận tham số và không trả kết quả (`func init()`), tự động chạy một lần khi package được import, trước khi `main()` bắt đầu. Go khởi tạo các gói theo thứ tự cố định: chạy đệ quy các package được import trước (kể cả import ẩn danh `_ "pkg"` chỉ để kích hoạt side effect), sau đó tính các hằng số và biến cấp package, tiếp tới chạy các hàm `init()` (theo thứ tự tên file tăng dần rồi từ trên xuống dưới trong file), cuối cùng mới vào `main()`.

```go
package main

import "fmt"

var configReady = func() bool {
	fmt.Println("1. package var")
	return true
}()

func init() {
	fmt.Println("2. first init")
}

func init() {
	fmt.Println("3. second init")
}

func main() {
	fmt.Println("4. main, configReady =", configReady)
}
```

<TerminalOutput command="go run init_order.go" label="Go 1.27.1 · darwin/arm64" caption="Biến cấp package chạy xong trước các hàm init(), và các hàm init() chạy theo đúng thứ tự xuất hiện trước khi vào main().">
```text
1. package var
2. first init
3. second init
4. main, configReady = true
```
</TerminalOutput>

Bạn cũng không thể gọi `init()` trực tiếp từ code: gọi `init()` bên trong `main()` sẽ bị trình biên dịch báo lỗi `undefined: init`.

<GoP12InitOrder />

Tránh mở pool kết nối database, tạo HTTP client hay đọc file cấu hình bên trong `init()` vì ba lý do:
1. **Không xử lý lỗi tử tế được**: `init()` không trả về được `error`, nên hễ gặp lỗi chỉ còn cách `panic` làm sập chương trình thay vì để bên gọi thử lại hay dùng phương án dự phòng.
2. **Làm vướng unit test**: `go test` tự động kích hoạt toàn bộ `init()` của package trước khi chạy từng test case, ép cả những bài test thuần logic phải kéo theo kết nối mạng hoặc đĩa.
3. **Ép dùng biến toàn cục**: tài nguyên mở ra trong `init()` buộc phải gán vào biến cấp package, khiến mọi hàm trong gói đều sửa được và khó cô lập khi test song song.

Hãy thay phần khởi tạo có trạng thái bằng hàm tạo rõ ràng (`openDB(dsn string) (*sql.DB, error)`), chỉ giữ `init()` cho các đăng ký tĩnh không thể lỗi và không sinh biến toàn cục (ví dụ đăng ký bộ giải mã ảnh hoặc route tĩnh). Về cách tổ chức package sạch sẽ và ẩn chi tiết bằng thư mục `internal/`, xem thêm trong [Go cơ bản](/blog/go-first-program-modules-packages/).

### Getter và setter trong Go

Khác với Java, Go không sinh sẵn property và không coi việc bọc mọi trường bằng `GetX`/`SetX` là chuẩn mực. Ngay trong thư viện chuẩn, struct `time.Timer` mở công khai thẳng trường `timer.C` cho người dùng đọc thay vì giấu sau hàm `GetC()`.

Chỉ nên viết getter và setter khi thật sự mang lại giá trị: kiểm tra ràng buộc lúc ghi, bọc khóa mutex khi đọc/ghi, tính ra giá trị suy diễn, hoặc giữ tương thích API khi cấu trúc lưu trữ bên trong có thể thay đổi sau này. Nếu cần viết, hãy theo quy ước đặt tên của Go: getter bỏ tiền tố `Get` (`Balance()`, không phải `GetBalance()`), còn setter giữ tiền tố `Set` (`SetBalance`):

```go
package main

import "fmt"

type Customer struct {
	balance int
}

func (c *Customer) Balance() int {
	return c.balance
}

func (c *Customer) SetBalance(amount int) {
	if amount < 0 {
		c.balance = 0
		return
	}
	c.balance = amount
}

func main() {
	var c Customer
	c.SetBalance(-50)
	fmt.Println("clamped:", c.Balance())
	c.SetBalance(120)
	fmt.Println("updated:", c.Balance())
}
```

<TerminalOutput command="go run getters.go" label="Go 1.27.1 · darwin/arm64" caption="Đặt tên Balance() không có chữ Get, và dùng SetBalance() ở nơi cần giữ bất biến như chặn số dư âm.">
```text
clamped: 0
updated: 120
```
</TerminalOutput>

<Concepts title="Giải thích nhanh mấy thuật ngữ ở mục này">

- **Hàm `init()`**: hàm không tham số, không giá trị trả về, tự động chạy một lần khi package được import trước lúc `main()` hoặc test bắt đầu.
- **Blank import (`_ "pkg"`)**: import một package chỉ để chạy phần khởi tạo biến và hàm `init()` của nó mà không dùng trực tiếp symbol nào bên trong.
- **Quy ước đặt tên accessor**: method đọc giá trị bỏ chữ `Get` (`Balance()`), còn method cập nhật giữ chữ `Set` (`SetBalance()`).

</Concepts>

## Điểm rút ra (Key takeaways)

- **Đừng bao giờ trả về con trỏ typed `nil` khi hàm khai báo trả về interface**: giá trị `(*MyError)(nil)` hay `(*os.File)(nil)` vẫn lấp đầy ngăn `iface.tab`, làm `val == nil` cho kết quả `false`; hãy `return nil` tường minh ở nhánh thành công.
- **Đặt interface nhỏ ở phía người gọi và trả về struct cụ thể từ phía cung cấp**: nhận đầu vào tổng quát như `io.Reader` thay cho tên file, hạn chế `any` khi biết rõ kiểu, và chỉ tách interface 1–2 method ngay chỗ sử dụng.
- **Dùng generics cho cấu trúc dữ liệu và thuật toán lặp kiểu, dùng interface khi hành vi thay đổi**: xây container như `Stack[T]` kết hợp `slices`/`maps` để tránh đóng hộp `any`, còn với ranh giới I/O thì giữ interface thuần cho gọn.
- **Kiểm soát kỹ những gì type embedding đẩy ra ngoài**: tránh nhúng ẩn `sync.Mutex` hay `time.Time` chỉ cho đỡ gõ, và luôn nhớ method được đẩy lên vẫn chạy với receiver là trường bên trong chứ không phải struct ngoài.
- **Dùng functional options cho tham số tùy chọn, tránh nhồi I/O vào `init()` và bỏ getter/setter thừa**: giữ hàm khởi tạo có trả về `error`, và bỏ tiền tố `Get` khi thật sự cần viết method đọc trường.
