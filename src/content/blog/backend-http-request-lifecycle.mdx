### The hook: hours with no requests

On October 4, 2021, Facebook did not have a code problem. A routine maintenance command took down all the connections in Facebook's backbone, so its data centers could no longer talk to each other. Facebook's DNS servers saw they could not reach those data centers and, by design, withdrew their own BGP advertisements — and with them, Facebook's authoritative DNS servers disappeared from the internet map. Every app went dark for hours, and the loss of DNS broke many of the internal tools engineers needed to fix it. Not one line of their code ran badly that day: **no request ever arrived** ([Janardhan, Meta Engineering](https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/)).

<BeP01OutageTimeline />

That is the first thing to understand about backend: before your Python runs, a request crosses a chain of stations you do not own. Most incidents are boring — a slow DNS lookup, a TLS handshake retry, a dropped connection — and none of them show up in your profiler. This post walks one request through every station, live, and answers four questions:

1. **The stations before your code**: DNS, TCP, TLS, HTTP — what each does, and what it costs you.
2. **Where your code begins**: what uvicorn actually owns, and what ASGI hands you.
3. **The pipe back**: why the second request on a connection is far cheaper than the first.
4. **The habit**: which one trace tells you which station ate the time.

Line by line:

**DNS turns a name into an address.** `fastapi.tiangolo.com` became `172.66.46.235`. Your resolver asks around — cache, router, then the hierarchy — and each answer is cached for its TTL. In the Facebook outage, this is exactly the station that died: the resolver could not reach Facebook's nameservers at all.

The asking order never changes:

<BeP01DnsWalk />

**TCP opens the pipe.** One round trip for the three-way handshake (`SYN`, `SYN-ACK`, `ACK`), then bytes can flow both ways. If the address is wrong or filtered, the request stalls here — your app logs nothing at all.

The three packets, in order:

<BeP01TcpHandshake />

**TLS makes the pipe private.** One round trip in TLS 1.3 (two in TLS 1.2) to agree keys and check the certificate — that's the `CN=fastapi.tiangolo.com` and `SSL certificate verify ok` above. Every HTTPS request pays this before the first HTTP byte.

**HTTP is the message inside the pipe.** `GET / HTTP/2` with a few headers. Notice `cf-ray: ...-SIN` in the response: Cloudflare's Singapore edge answered. Your request's station list depends on geography, not on your code.

You can pay each station yourself, with nothing but the standard library — this is `demo/station_timing.py`:

```python
import socket
import ssl
import time

HOST = "fastapi.tiangolo.com"


def ms(since: float) -> float:
    return (time.perf_counter() - since) * 1000


# Station 1: DNS — a name becomes an address.
t = time.perf_counter()
addr = socket.getaddrinfo(HOST, 443, proto=socket.IPPROTO_TCP)[0][4][0]
print(f"DNS   {ms(t):7.1f} ms   {HOST} -> {addr}")

# Station 2: TCP — the three-way handshake opens the pipe.
t = time.perf_counter()
sock = socket.create_connection((HOST, 443))
print(f"TCP   {ms(t):7.1f} ms   connected to {addr}:443")

# Station 3: TLS — keys agreed, certificate checked.
t = time.perf_counter()
tls = ssl.create_default_context().wrap_socket(sock, server_hostname=HOST)
print(f"TLS   {ms(t):7.1f} ms   {tls.version()}")

# Station 4 + 5: HTTP is the letter inside the pipe; the first bytes back
# are one more round trip. This is the only station your profiler ever sees.
t = time.perf_counter()
tls.sendall(
    b"GET / HTTP/1.1\r\n"
    + f"Host: {HOST}\r\n".encode()
    + b"User-Agent: station-timing\r\n"
    + b"Accept: */*\r\n"
    + b"Connection: close\r\n\r\n"
)
status = tls.recv(256).split(b"\r\n")[0].decode()
print(f"HTTP  {ms(t):7.1f} ms   {status}")
tls.close()
```

<Concepts>
- **DNS (Domain Name System)**: the internet's phone book — turns names into IP addresses, with caching at every level.
- **TCP handshake**: the three-packet ritual (`SYN`, `SYN-ACK`, `ACK`) that opens a reliable, ordered pipe between two IPs.
- **TLS (Transport Layer Security)**: the handshake that checks the server's certificate and agrees encryption keys; TLS 1.3 takes one round trip.
- **RTT (round-trip time)**: the time for a packet to cross and an answer to come back. Handshakes are paid in RTTs, not in milliseconds of your code.
- **HTTP/2**: a binary, multiplexed version of HTTP — many requests share one connection without queueing behind each other.
</Concepts>

## 2. The red box: where your code begins

Everything above happens before your process is involved. What does "running the server" actually mean for a Python app?

uvicorn owns the socket. It parses bytes, closes handshakes, decodes HTTP — and calls one thing of yours: an ASGI app. The whole ASGI contract is one callable: `async def app(scope, receive, send)`. A request arrives as a `scope` dict; you read the body by awaiting `receive()`; you push the response by awaiting `send()`. FastAPI is a very large, very organized version of that callable, with routing, validation and docs riding on top.

To see how small that contract is, here is an app with no framework at all (`demo/p01_raw_asgi.py`). uvicorn calls it once per request, and it answers with two `send()` calls: one for the status line and headers, one for the body.

```python
async def app(scope, receive, send):
    if scope["type"] != "http":
        return  # lifespan etc.: this toy app only speaks HTTP
    print("scope keys:", sorted(scope))
    body = f"{scope['method']} {scope['path']}".encode()
    await send(
        {
            "type": "http.response.start",
            "status": 200,
            "headers": [(b"content-type", b"text/plain")],
        }
    )
    await send({"type": "http.response.body", "body": body})
```

Nothing here routes `/cases/42` anywhere, parses `?x=1`, or checks types. You would have to write all of that by hand, for every endpoint. FastAPI is the same callable with that work done for you. Two lines of the demo service (`demo/trace_demo.py`) show how: `app = FastAPI(title="clue.api", version="0.1.0")` creates the ASGI callable uvicorn will call, and a decorator registers a path operation on it:

```python
@app.get("/cases/{case_id}")
async def get_case(case_id: int) -> dict:
    return {"case_id": case_id, "status": "open"}
```

`@app.get("/cases/{case_id}")` tells the router "GET requests to this path come here", and the `{case_id}` piece of the path is captured. The annotation `case_id: int` is not decoration: FastAPI reads it, converts the text `"42"` to the integer `42` before your function runs, and rejects anything else. Send `/cases/abc` and your function is never called:

<BeP01CaseIdCheck />

The trap here is typing the parameter as `str` (or leaving it untyped) and calling `int(case_id)` by hand. A bad id then raises `ValueError` inside your code and the client gets a 500 for what was its own mistake. Let the annotation do the checking: bad input is a 4xx, a 500 means your code broke.

The service also registers one middleware with `@app.middleware("http")`. A middleware wraps every request: the code before `await call_next(request)` runs on the way in, the code after it runs on the way out, so it is the natural place to trace a request. Here it prints what it sees:

```python
@app.middleware("http")
async def trace_middleware(request: Request, call_next):
    scope = request.scope
    print(
        f"ASGI scope: type={scope['type']} scheme={scope['scheme']}"
        f" http_version={scope.get('http_version')}"
    )
    print(f"app -> router -> endpoint: {request.method} {request.url.path}")
    started = time.perf_counter()
    response = await call_next(request)
    elapsed_ms = (time.perf_counter() - started) * 1000
    print(
        f"endpoint returned, response back through the stack:"
        f" {response.status_code} in {elapsed_ms:.2f} ms"
    )
    return response
```

That red box is the only thing you own. It explains two facts that bite AI-written services constantly:

- If latency is added **outside** the red box — DNS, TLS retries, a proxy — your profiler will show a fast, healthy endpoint and unhappy users at the same time.
- If a request **blocks inside** the red box (a slow database call in a sync def), the whole worker stalls with it. Later posts in this series take that apart properly.

<Callout type="warning" title="The AI habit to break">
Generated code starts measuring at the endpoint and treats the network as instant. When users report "the app is slow," the station that ate the time is outside your process as often as inside it — and `curl -v` finds it in seconds, while a profiler finds nothing.
</Callout>

## 3. One pipe, both ways

The response rides the same TCP connection back: your code hands bytes to `send()`, uvicorn writes them to the socket, TLS encrypts, TCP carries them. There is no second magic pipe.

But look at the last line of the curl trace: `Connection #0 ... left intact`. The expensive part — DNS, TCP, TLS — is connection setup, and it is reusable. A second request on that connection skips the handshake stations almost entirely. That is what keep-alive buys. On the server side it is a uvicorn setting: `--timeout-keep-alive` (default 5 seconds) is how long uvicorn holds an idle connection open waiting for the next request, so a client that pauses longer pays the handshake again. It is also why:

- A **benchmark of one request** measures mostly setup. Six stations of tax, one request of value.
- A **load test** that reuses connections and one that doesn't can disagree wildly about the same service.
- HTTP/2 goes further: many requests in flight over one connection, so the "second request" cost shrinks again.

<BeP01KeepAlive />

Keep this in your head as a budget: the first request on a fresh connection pays roughly 1 RTT for DNS (cached often), 1 for TCP, 1 for TLS 1.3 — before the server has received a single byte. On a 40 ms RTT link, your "2 ms endpoint" is a ~122 ms experience for the first request. The number you brag about is rarely the number users feel.

That budget, drawn to scale:

<BeP01ReuseCost />

Run the pair yourself — this is `demo/reuse_timing.py`:

```python
import time

import httpx

URL = "https://fastapi.tiangolo.com/"


def ms(since: float) -> float:
    return (time.perf_counter() - since) * 1000


with httpx.Client() as client:
    t = time.perf_counter()
    client.get(URL)
    first = ms(t)

    t = time.perf_counter()
    client.get(URL)
    second = ms(t)

print(f"first request:  {first:7.1f} ms   (fresh connection)")
print(f"second request:  {second:7.1f} ms   (connection reused)")
```

## 4. Trace first, guess never

When something is slow, walk the stations in order — one tool per station, two minutes total:

1. `curl -v` — where does the trace pause? Resolution, connect, TLS, or time-to-first-byte after the request was sent?
2. The server's access log — did the request even arrive, and how long did your box take? That's the red box's receipt.
3. Only then open a profiler, if the receipt says the time is yours.

The whole habit on one line:

<BeP01TraceFirst />

The Facebook outage is the extreme case: countless requests never arrived, and no amount of endpoint profiling would have found a BGP route withdrawal. Your cases will be smaller — a flaky resolver, an expired certificate, a proxy timeout — but the discipline is identical: **find the station first, then fix the right box.**

</En>

### Mở đầu: nhiều giờ không một request

Ngày 4 tháng 10 năm 2021, Facebook không hề có lỗi code. Một lệnh bảo trì định kỳ làm đứt toàn bộ kết nối backbone của Facebook, các data center không còn nói chuyện được với nhau. Các DNS server của họ thấy mình không với tới data center, nên theo thiết kế tự rút luôn quảng bá BGP của chính mình, và DNS authoritative biến mất khỏi bản đồ internet. App tắt hàng giờ. Mất DNS còn làm hỏng nhiều tool nội bộ mà kỹ sư cần để sửa. Không một dòng code nào của họ chạy sai hôm đó: **không request nào tới được chỗ code** ([Janardhan, Meta Engineering](https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/)).

<BeP01OutageTimeline />

Đó là bài học đầu tiên về backend: trước khi Python của bạn chạy, request phải băng qua một chuỗi trạm mà bạn không sở hữu cái nào. Đa số sự cố nhàm chán lắm — DNS tra chậm một nhịp, TLS handshake retry một lần, một connection rớt giữa đường — và chẳng cái nào lộ mặt trong profiler của bạn. Mình sẽ đi theo một request qua từng trạm, bằng capture thật, và trả lời bốn câu:

1. **Các trạm trước code của bạn**: DNS, TCP, TLS, HTTP — từng trạm làm gì, và đắt cỡ nào.
2. **Code của bạn bắt đầu từ đâu**: uvicorn thực sự nắm những gì, và ASGI nhét gì vào tay bạn.
3. **Con ống quay lại**: vì sao request thứ hai trên cùng một connection rẻ hơn request đầu nhiều lần.
4. **Thói quen**: một trace duy nhất cho biết trạm nào ăn mất thời gian.

Toàn bộ trace, vẽ thành một dòng:

<BeP01Stations />

Từng dòng một:

**DNS biến tên thành địa chỉ.** `fastapi.tiangolo.com` trở thành `172.66.46.235`. Resolver của bạn đi hỏi vòng — cache trước, router kế tiếp, rồi lên cả cây hệ thống — và câu trả lời nào cũng được lưu lại theo TTL riêng của nó. Trong sự cố Facebook, trạm chết chính là trạm này: resolver có muốn cũng không với tới nameserver của Facebook.

Thứ tự hỏi không bao giờ đổi:

<BeP01DnsWalk />

**TCP mở ống.** Một round trip cho bộ bắt tay ba bước (`SYN`, `SYN-ACK`, `ACK`), rồi byte chạy thoải mái cả hai chiều. Địa chỉ sai hoặc bị chặn thì request kẹt ngay tại đây — và app của bạn không log được lấy một dòng.

Ba gói tin, theo thứ tự:

<BeP01TcpHandshake />

**TLS biến ống thành kênh riêng.** TLS 1.3 tốn một round trip (TLS 1.2 tốn hai) để trao khoá và đối chiếu chứng chỉ — chính là mấy dòng `CN=fastapi.tiangolo.com` và `SSL certificate verify ok` bạn thấy phía trên. Mọi request HTTPS đều trả khoản này trước byte HTTP đầu tiên.

**HTTP là lá thư bỏ trong ống.** `GET / HTTP/2` kèm vài header. Để ý dòng `cf-ray: ...-SIN` trong response: edge của Cloudflare ở Singapore trả lời bạn đấy. Request đi qua những trạm nào tuỳ vào bạn đứng ở đâu trên bản đồ, chứ không tuỳ code của bạn.

Bạn có thể tự tay trả tiền từng trạm, không cần framework nào ngoài standard library — đây là `demo/station_timing.py`:

```python
import socket
import ssl
import time

HOST = "fastapi.tiangolo.com"


def ms(since: float) -> float:
    return (time.perf_counter() - since) * 1000


# Station 1: DNS — a name becomes an address.
t = time.perf_counter()
addr = socket.getaddrinfo(HOST, 443, proto=socket.IPPROTO_TCP)[0][4][0]
print(f"DNS   {ms(t):7.1f} ms   {HOST} -> {addr}")

# Station 2: TCP — the three-way handshake opens the pipe.
t = time.perf_counter()
sock = socket.create_connection((HOST, 443))
print(f"TCP   {ms(t):7.1f} ms   connected to {addr}:443")

# Station 3: TLS — keys agreed, certificate checked.
t = time.perf_counter()
tls = ssl.create_default_context().wrap_socket(sock, server_hostname=HOST)
print(f"TLS   {ms(t):7.1f} ms   {tls.version()}")

# Station 4 + 5: HTTP is the letter inside the pipe; the first bytes back
# are one more round trip. This is the only station your profiler ever sees.
t = time.perf_counter()
tls.sendall(
    b"GET / HTTP/1.1\r\n"
    + f"Host: {HOST}\r\n".encode()
    + b"User-Agent: station-timing\r\n"
    + b"Accept: */*\r\n"
    + b"Connection: close\r\n\r\n"
)
status = tls.recv(256).split(b"\r\n")[0].decode()
print(f"HTTP  {ms(t):7.1f} ms   {status}")
tls.close()
```

<Concepts title="Mấy thuật ngữ phía trên, nói dễ hiểu">
- **DNS (Domain Name System)**: danh bạ của internet — biến tên miền thành địa chỉ IP, cache ở mọi tầng.
- **TCP handshake**: nghi thức ba gói (`SYN`, `SYN-ACK`, `ACK`) để mở một ống đáng tin, có thứ tự, giữa hai địa chỉ IP.
- **TLS (Transport Layer Security)**: bước bắt tay đối chiếu chứng chỉ server và trao khoá mã hoá; TLS 1.3 chỉ tốn một round trip.
- **RTT (round-trip time)**: thời gian gói đi qua và câu trả lời quay về. Handshake trả bằng RTT, không phải bằng mili-giây code của bạn.
- **HTTP/2**: bản HTTP nhị phân, multiplex — nhiều request chung một connection không phải xếp hàng chờ nhau.

## 2. Ô đỏ: code của bạn bắt đầu từ đâu

Tất cả những gì phía trên diễn ra khi process của bạn còn chưa được kéo vào câu chuyện. Vậy "chạy server" thực ra nghĩa là gì với một app Python?

uvicorn nắm socket. Nó parse byte, đóng các handshake, giải mã HTTP — rồi gọi đúng một thứ của bạn thôi: một app ASGI. Cả giao diện ASGI gói gọn trong một callable: `async def app(scope, receive, send)`. Request tới dưới dạng dict `scope`; muốn đọc body thì await `receive()`; muốn đẩy response thì await `send()`. FastAPI, suy cho cùng, cũng chỉ là một phiên bản cực lớn và cực có tổ chức của đúng callable đó — routing, validation, docs cài sẵn phía trên.

Để thấy hợp đồng đó nhỏ đến đâu, đây là một app không dùng framework nào (`demo/p01_raw_asgi.py`). uvicorn gọi nó một lần cho mỗi request, và nó trả lời bằng hai lần `send()`: một cho status line cùng header, một cho body.

```python
async def app(scope, receive, send):
    if scope["type"] != "http":
        return  # lifespan etc.: this toy app only speaks HTTP
    print("scope keys:", sorted(scope))
    body = f"{scope['method']} {scope['path']}".encode()
    await send(
        {
            "type": "http.response.start",
            "status": 200,
            "headers": [(b"content-type", b"text/plain")],
        }
    )
    await send({"type": "http.response.body", "body": body})
```

Hai dòng trong demo service (`demo/trace_demo.py`) cho thấy cách: `app = FastAPI(title="clue.api", version="0.1.0")` tạo ra callable ASGI mà uvicorn sẽ gọi, còn một decorator đăng ký một path operation lên nó:

```python
@app.get("/cases/{case_id}")
async def get_case(case_id: int) -> dict:
    return {"case_id": case_id, "status": "open"}
```

`@app.get("/cases/{case_id}")` nói với router "request GET tới path này thì vào đây", và phần `{case_id}` của path được bắt lại. Annotation `case_id: int` không phải để trang trí: FastAPI đọc nó, đổi chuỗi `"42"` thành số nguyên `42` trước khi hàm của bạn chạy, và từ chối mọi giá trị khác. Cái bẫy: khai báo tham số là `str` (hoặc không khai báo kiểu) rồi tự gọi `int(case_id)`. Khi đó id sai làm code bạn ném `ValueError`, và client nhận 500 cho lỗi do chính nó gây ra. Hãy để annotation kiểm tra: đầu vào sai là 4xx, còn 500 nghĩa là code của bạn hỏng.

Service còn đăng ký một middleware bằng `@app.middleware("http")`. Middleware bọc mọi request: code trước `await call_next(request)` chạy lúc request đi vào, code sau nó chạy lúc response đi ra, nên đây là chỗ tự nhiên để truy vết một request. Ở đây nó in ra những gì nó nhìn thấy:

```python
@app.middleware("http")
async def trace_middleware(request: Request, call_next):
    scope = request.scope
    print(
        f"ASGI scope: type={scope['type']} scheme={scope['scheme']}"
        f" http_version={scope.get('http_version')}"
    )
    print(f"app -> router -> endpoint: {request.method} {request.url.path}")
    started = time.perf_counter()
    response = await call_next(request)
    elapsed_ms = (time.perf_counter() - started) * 1000
    print(
        f"endpoint returned, response back through the stack:"
        f" {response.status_code} in {elapsed_ms:.2f} ms"
    )
    return response
```

## 3. Một con ống, cả hai chiều

Response đi ngược lại đúng connection đó: code bạn đưa byte cho `send()`, uvicorn ghi vào socket, TLS mã hoá, TCP chở đi. Không có con ống thần kỳ thứ hai.

Nhưng nhìn dòng cuối của trace curl: `Connection #0 ... left intact`. Phần đắt đỏ — DNS, TCP, TLS — là chi phí mở kết nối, và nó dùng lại được. Request thứ hai trên cùng connection gần như bỏ qua các trạm handshake. Đó là thứ keep-alive mua cho bạn. Phía server, nó là một setting của uvicorn: `--timeout-keep-alive` (mặc định 5 giây) là thời gian uvicorn giữ một connection rảnh để chờ request kế tiếp, nên client nghỉ lâu hơn mức đó sẽ phải trả lại chi phí handshake. Đó cũng là vì sao:

- Một **benchmark chạy đúng một request** đo toàn tiền setup. Sáu trạm thuế, một request giá trị.
- Một **load test** tái dùng connection và một load test không tái dùng có thể chênh nhau xa trên cùng một service.
- HTTP/2 đi xa hơn nữa: nhiều request cùng chạy trên một connection, nên chi phí "request thứ hai" lại co nhỏ thêm lần nữa.

<BeP01KeepAlive />

Giữ cái ngân sách này trong đầu: request đầu tiên trên một connection mới trả chừng 1 RTT cho DNS (nếu cache trống), 1 cho TCP, 1 cho TLS 1.3 — tất cả trước khi server nhận được một byte nào. Trên đường RTT 40 ms, "endpoint 2 ms" của bạn là trải nghiệm ~122 ms cho request đầu tiên. Con số bạn khoe hiếm khi là con số user cảm nhận.

Ngân sách đó, vẽ đúng tỉ lệ:

<BeP01ReuseCost />

Chạy thử cặp này ngay — đây là `demo/reuse_timing.py`:

```python
import time

import httpx

URL = "https://fastapi.tiangolo.com/"


def ms(since: float) -> float:
    return (time.perf_counter() - since) * 1000


with httpx.Client() as client:
    t = time.perf_counter()
    client.get(URL)
    first = ms(t)

    t = time.perf_counter()
    client.get(URL)
    second = ms(t)

print(f"first request:  {first:7.1f} ms   (fresh connection)")
print(f"second request:  {second:7.1f} ms   (connection reused)")
```

## 4. Trace trước, đừng đoán

Khi có thứ gì đó chậm, đi qua từng trạm theo thứ tự — một tool mỗi trạm, tổng cộng hai phút:

1. `curl -v` — trace dừng ở đâu? Tra địa chỉ, kết nối, TLS, hay time-to-first-byte sau khi request đã gửi?
2. Access log của server — request có tới nơi không, và ô đỏ của bạn mất bao lâu? Đó là biên lai của phần code bạn.
3. Mở profiler sau cùng, nếu biên lai nói thời gian nằm ở phần của bạn.
