### The hook: two correct halves

On 23 September 1999, NASA's Mars Climate Orbiter reached Mars and was lost. The Mishap Investigation Board's report names the root cause in one sentence: "the failure to use metric units in the coding of a ground software file." The thruster data that the ground software produced was in pound-force seconds. The navigation software read the same file as newton-seconds. The software on the spacecraft itself used metric units and was correct, and the trajectory modelers "assumed the data was provided in metric units per the requirements." By the time of Mars insertion the spacecraft was about 170 kilometers lower than planned.

Each half was consistent with its own assumption. The mistake lived in the join between them, and the board says what was missing there: "End-to-end testing to validate the small forces ground software performance and its applicability to the specification did not appear to be accomplished."

<BeP09Orbiter />

Your backend has the same joins: service and database, handler and caller, your code and the token library. A test suite is how you check them cheaply and often. It has to be able to fail when a join is wrong, and AI-written suites are good at the opposite. They go green in seconds, because they were written to match the code beside them. Two habits do most of the damage: **mocking the very thing under test**, and **asserting only that the status was 200**.

This post builds a real suite for the series' clue.api and counts what it costs. Four questions:

1. **What does the pyramid look like in a real suite?** Counts and seconds, not a diagram from a textbook.
2. **Why a fake beats a mock** for the thing you own, and how to write the fake.
3. **How do you test the real app in-process?** Overrides, a database per test, a real token.
4. **Which two checks sit beside the pyramid?** A contract snapshot and a tiny load check.

## 1. The pyramid, counted

First the vocabulary, since the words get used loosely. A **unit test** runs a small piece of your code by calling it directly: no web server, no database. An **API test** (many people say "integration test") runs the real application, routes and handlers and dependency wiring included, but inside the test process and usually against a stand-in for the slow parts. An **end-to-end test** starts the thing the way production does and talks to it over a real socket. The **test pyramid** is the advice to have many of the first, fewer of the second and very few of the third, because each step up is slower and breaks for more reasons.

Here is the suite for this post, measured. It lives in `demo/tests_p09/`, and `demo/pytest.ini` tells pytest where to look and registers four markers. `conftest.py` tags every test with its layer from its file name, so `pytest -m unit` runs one layer at a time.

<Concepts>
- **Unit test**: calls your code directly. Here, the service rules with a fake repository. It tells you which rule broke.
- **API test**: the real FastAPI app, in-process, through `TestClient` or an async client. It tells you the wiring still works.
- **End-to-end test**: a real server process, a real socket, a real login. It tells you the whole thing starts and holds together.
- **Fake**: a working implementation that is not durable, such as a repository backed by a dict. **Mock**: an object that records calls and answers what you told it to.
</Concepts>

## 2. Unit tests: the rules, a fake, no framework

Post 4 split clue.api so that `layered_service.py` imports no FastAPI and talks to storage through the `CaseRepository` protocol. That seam is the reason the base of the pyramid is cheap: any object with `add`, `get` and `save` can stand in for the database.

<BeP09Seam />

The stand-in is `demo/tests_p09/fakes.py`. It is a real implementation, just not a durable one:

```python
class FakeCaseRepository:
    def __init__(self) -> None:
        self.rows: dict[str, CaseRecord] = {}

    def add(self, record: CaseRecord) -> None:
        self.rows[record.case_id] = replace(record)

    def get(self, case_id: str) -> CaseRecord | None:
        row = self.rows.get(case_id)
        return replace(row) if row else None

    def save(self, record: CaseRecord) -> None:
        self.rows[record.case_id] = replace(record)
```

The `replace(...)` calls are the point of the file. A dict that stores the very object you pass in would hide a class of bugs, because the caller and the "database" would share one object. A real database does not do that: it copies on write and hands you a fresh object on read. The fake copies in both directions, so a change you forget to save stays forgotten, exactly as it would in production. (Post 4's `p04_override.py` used a simpler fake that stored the objects themselves; that is fine for showing the seam, and it is the fake that the next section's bug would sail through.)

<BeP09FakeCopy />

Two fixtures in `conftest.py` hand it out: `fake_repo`, and `service`, a `CaseService` built on it. A test then reads like the rule it protects:

```python
def test_close_is_persisted(service, fake_repo):
    service.open_case("gnome")
    service.assign("C-1", "wren")
    service.close("C-1", "found in the pond")
    stored = fake_repo.rows["C-1"]
    assert (stored.status, stored.resolution) == ("closed", "found in the pond")


def test_cannot_close_without_a_detective(service, fake_repo):
    service.open_case("gnome")
    with pytest.raises(CaseRuleError, match="unassigned"):
        service.close("C-1", "x")
    assert fake_repo.rows["C-1"].status == "open"  # and nothing was half-written
```

Note what the first test asserts. It does not check that `save` was called, it checks what ended up stored: status `closed`, resolution recorded. And the second test checks two things on purpose: the rule fired, and nothing was half-written when it did. That is the habit that makes a test able to fail for the right reason.

Rules with many combinations want a table. The whole rulebook for `assign` and `close` fits in six rows, and `pytest.mark.parametrize` turns each row into its own test:

```python
# The whole rulebook as a table: (status, detective, move) -> what the rules say.
MOVES = {
    "assign": lambda s: s.assign("C-1", "kite"),
    "close": lambda s: s.close("C-1", "done"),
}


@pytest.mark.parametrize(
    "status, detective, move, refused",
    [
        ("open", None, "assign", False),
        ("open", "wren", "assign", False),
        ("closed", "wren", "assign", True),
        ("open", None, "close", True),
        ("open", "wren", "close", False),
        ("closed", "wren", "close", False),
    ],
)
def test_rulebook(service, fake_repo, status, detective, move, refused):
    fake_repo.add(CaseRecord("C-1", "gnome", status, detective))
    if refused:
        with pytest.raises(CaseRuleError):
            MOVES[move](service)
    else:
        MOVES[move](service)
```

## 3. A mock agrees with you; a fake can disagree

Now the trap. Suppose AI "refactors" `close` and the diff looks harmless. `demo/p09_buggy_service.py`:

```python
class BuggyCaseService(CaseService):
    def close(self, case_id: str, resolution: str) -> CaseRecord:
        case = self._require(case_id)
        if case.detective is None:
            raise CaseRuleError("an unassigned case cannot be closed")
        self._repo.save(case)  # saved too early: status is still "open" here
        case.status = "closed"
        case.resolution = resolution
        return case
```

It saves first and sets the status afterwards. Against the in-memory repository from post 4 this works, because the repository holds the very same object and the late assignments show up anyway. Against a database row it silently loses the close: `save` copied the fields while the status was still `open`. This is Mars Climate Orbiter in miniature, two parts that each look right.

Here is the test an AI assistant writes for it, with `unittest.mock`, and the same check written against the fake. Both run against the correct service and the buggy one:

```python
@pytest.mark.parametrize("service_cls", ALL)
def test_close_with_a_mock(service_cls):
    repo = MagicMock()
    repo.get.return_value = CaseRecord("C-1", "gnome", "open", detective="wren")

    service_cls(repo).close("C-1", "found")

    repo.save.assert_called_once()  # "save was called": true for both classes


@pytest.mark.parametrize("service_cls", SERVICES)
def test_close_with_a_fake(service_cls, fake_repo):
    fake_repo.add(CaseRecord("C-1", "gnome", "open", detective="wren"))

    service_cls(fake_repo).close("C-1", "found")

    assert fake_repo.get("C-1").status == "closed"  # what storage really holds
```

A `MagicMock` accepts any call and answers what you configured, so it has no way to disagree with the code. The mock test can only assert *what the code did* (`save` was called once), never *what storage now holds*. The fake test asks the question that matters.

<Callout type="warning" title="The AI habit to break">
Ask an assistant for tests and it will often reach for `MagicMock` first, because a mock needs no setup and always goes green. A mock is the right tool at a boundary you do not own and cannot run: a payment provider, an email API. For your own repository, write the fake once, put it in `fakes.py`, and let every test share it. The rule of thumb: **never mock the thing under test, and be suspicious of mocking anything you can write a fake for in twenty lines.**
</Callout>

## 4. API tests: the real app, in-process

Unit tests cover the rules. They say nothing about whether the route parses `?resolution=`, whether the exception handler turns `CaseRuleError` into a 409, or whether `Depends` wires what you think. For that you call the app itself.

FastAPI's `TestClient` calls the ASGI app in-process, so there is no port and no server to start, and `app.dependency_overrides` swaps one dependency for another. This is post 4's idea, grown into fixtures. The fake goes in through `get_repo`, and the real routes, handlers and `CaseService` run on top of it:

```python
@pytest.fixture
def client(fake_repo):
    app.dependency_overrides[get_repo] = lambda: fake_repo
    yield TestClient(app)
    app.dependency_overrides.clear()  # the app object is module-global: always clean up


def test_open_returns_201_and_the_case(client, fake_repo):
    response = client.post("/cases", params={"title": "The missing gnome"})
    assert response.status_code == 201
    assert response.json() == {
        "case_id": "C-1",
        "title": "The missing gnome",
        "status": "open",
        "detective": None,
        "resolution": None,
    }
    assert fake_repo.rows["C-1"].title == "The missing gnome"
```

The cleanup line is not optional. `app` is a module-level object that every test in the process shares, so an override that is never cleared leaks into the next test, and you get a failure that depends on test order. Put the cleanup after the `yield` of a fixture and it runs even when the test fails.

<BeP09OverrideLeak />

`TestClient` is synchronous and drives the app from its own thread. When a test itself needs to be `async`, or needs to share an event loop with something else, use `httpx.AsyncClient` with `ASGITransport` instead. It reaches the same app, still without a network:

```python
@pytest.mark.anyio
async def test_same_app_through_an_async_client(fake_repo):
    app.dependency_overrides[get_repo] = lambda: fake_repo
    try:
        transport = httpx.ASGITransport(app=app)
        async with httpx.AsyncClient(transport=transport, base_url="http://test") as ac:
            response = await ac.post("/cases", params={"title": "async"})
    finally:
        app.dependency_overrides.clear()
    assert response.status_code == 201
```

`@pytest.mark.anyio` comes from the `anyio` plugin that ships with Starlette's dependencies, and the `anyio_backend` fixture in `conftest.py` picks asyncio. Reach for it when the test body itself needs `await`, for instance to call async code of your own next to the request.

### A database per test

A fake cannot tell you whether your SQL, your session handling or your commit really work. For that you want a real database, and SQLite makes it cheap: **one fresh file per test.** Post 5 gave the app a `get_session` dependency with a commit-on-success, rollback-on-error rule, and that rule is exactly what we want to test, so we must not override `get_session`. We change only the thing it builds sessions from:

```python
@pytest.fixture
def sql_sessions(tmp_path, monkeypatch):
    """A brand-new SQLite file per test, wired in where p05_db builds sessions."""
    engine = create_engine(
        f"sqlite:///{tmp_path / 'test.db'}", connect_args={"check_same_thread": False}
    )
    p05_db.Base.metadata.create_all(engine)
    factory = sessionmaker(engine, expire_on_commit=False)
    # get_session() stays the real one (its commit/rollback is under test);
    # only the factory it opens sessions from is swapped.
    monkeypatch.setattr(p05_db, "SessionLocal", factory)
    yield factory
    engine.dispose()
```

`tmp_path` is pytest's own per-test temporary folder, so the file is new for every test, and pytest cleans up old ones. `monkeypatch.setattr` swaps `p05_db.SessionLocal` and puts it back when the test ends. A second, quieter trap sits at the top of `conftest.py`: `p05_db` reads `DATABASE_URL` the moment it is imported, so the environment variable is set *before* any demo module is imported. Without it, merely importing `p05_app` would create a `clue.db` in whatever folder you ran pytest from.

<BeP09DbPerTest />

```python
@pytest.fixture
def client(sql_sessions):
    # raise_server_exceptions=False: a crash in the app is a 500 we can assert on.
    return TestClient(app, raise_server_exceptions=False)


def test_ids_are_unique_across_requests(client):
    # The post-5 bug (a counter reset per request) lives only in the database:
    # a dict-backed fake would never have produced the duplicate key.
    first = client.post("/cases", params={"title": "one"})
    second = client.post("/cases", params={"title": "two"})
    assert (first.status_code, second.status_code) == (201, 201)
    assert second.json()["case_id"] == "C-2"


def test_each_test_starts_empty(client):
    assert client.get("/stats").json() == {"cases": 0}  # no leftovers from other tests


def test_batch_with_a_blank_title_opens_nothing(client):
    response = client.post("/cases/batch", json=["one", "two", "  "])
    assert response.status_code == 500
    assert client.get("/stats").json() == {"cases": 0}  # rolled back, all or nothing
```

Each test here is one the fake cannot write. The first pins post 5's bug, a counter that reset on every request: a dict would simply overwrite `C-1`, while the database refuses the duplicate key. The third checks the all-or-nothing batch: the blank title raises, the session rolls back, and `/stats` still counts zero. That is a transaction guarantee, and only a real database has transactions. `raise_server_exceptions=False` tells `TestClient` to give us the 500 response instead of re-raising the exception into the test.

## 5. Auth in tests: the override that removes the guard

Post 7 put a guard in front of the routes: `get_current_user` decodes the token, checks the signature and expiry, and checks the scopes. Testing a route behind it tempts you to override it, and for one purpose that is right: to test the *owner rule* ("is this your case?") without minting tokens. For another purpose it is wrong, and the test below shows the difference.

```python
def bearer(user: str, scopes: list[str]) -> dict:
    return {"Authorization": f"Bearer {sec.make_token(user, scopes)}"}
```

`bearer` builds a real token with post 7's own `make_token`, which is cheap because it only signs a few claims. With real tokens you can test what the guard does:

```python
def test_missing_scope_is_403_with_the_scope_named():
    response = client.post("/purge", headers=bearer("bob", ["cases:read"]))
    assert response.status_code == 403
    assert "cases:write" in response.json()["detail"]


@pytest.fixture
def as_bob():
```

## 6. Contract: pin what callers see

Some changes break no rule and no route, and still break a caller. Rename `title` to `name` in the request body and every unit and API test that goes through your own code passes, because your code agrees with itself. The client sending `title` is the one that gets a 422. FastAPI already writes down what the API promises: the OpenAPI document at `/openapi.json`, the same one Swagger UI renders on this post's cover. A **contract check** commits a copy of that document and fails when the generated one differs.

```python
SNAPSHOT = Path(__file__).with_name("openapi.snapshot.json")


def as_lines(document: dict) -> list[str]:
    return json.dumps(document, indent=2, sort_keys=True).splitlines()


def test_openapi_matches_the_committed_snapshot():
    committed = as_lines(json.loads(SNAPSHOT.read_text()))
    generated = as_lines(app.openapi())
    diff = list(difflib.unified_diff(committed, generated, "committed", "generated", lineterm="", n=1))
    if diff:
        pytest.fail("the API contract changed:\n" + "\n".join(diff), pytrace=False)
```

`demo/p09_snapshot.py` writes `openapi.snapshot.json` from `app.openapi()`. The test compares the two as sorted, indented lines and fails with a unified diff, so the failure message is the change itself. To prove it works we ran it against a copy of the demo where `OpenBody.title` was renamed to `name`:

## 7. Load as a check

A load test is a measurement, but a very small one can also be a check: send a few hundred requests, compute p95 (the time that 95 percent of requests beat), and fail the build when it crosses a bound. It will not tell you your capacity. It will tell you that a change made an endpoint several times slower. `demo/p09_burst.py` does it with httpx:

```python
async def one(client: httpx.AsyncClient, path: str, gate: asyncio.Semaphore) -> float:
    async with gate:  # at most `concurrency` requests in flight
        started = time.perf_counter()
        response = await client.get(path)
        response.raise_for_status()
        return (time.perf_counter() - started) * 1000


async def main(base: str, path: str, n: int, concurrency: int, bound_ms: float) -> int:
    gate = asyncio.Semaphore(concurrency)
    async with httpx.AsyncClient(base_url=base, timeout=60) as client:
        await client.get(path)  # warm-up: first request pays connection and import costs
        started = time.perf_counter()
        times = sorted(await asyncio.gather(*(one(client, path, gate) for _ in range(n))))
        wall = time.perf_counter() - started
    p50 = statistics.median(times)
    p95 = times[int(len(times) * 0.95) - 1]
    verdict = "ok" if p95 <= bound_ms else "FAIL"
    print(
        f"GET {path} x{n} at {concurrency}: {n / wall:.0f} req/s | "
        f"p50 {p50:.1f} ms | p95 {p95:.1f} ms | max {times[-1]:.1f} ms | "
        f"bound {bound_ms:.0f} ms -> {verdict}"
    )
    return 0 if p95 <= bound_ms else 1
```

`asyncio.Semaphore` caps how many requests are in flight at once, which is what "5 at a time" means. The first request is a warm-up that pays for connection setup and first-call costs, and `sys.exit(1)` when the bound breaks lets any CI step treat it as a plain command. We pointed it at post 5's two endpoints: `/lazy`, which runs 101 queries for 100 cases (the N+1 problem), and `/eager`, the one-line fix that runs 2.

## 8. Who tests the tests?

You now have a suite that goes green. The question that matters is whether it can go red. When AI writes the tests, ask it by breaking the code on purpose: delete one rule and see which tests notice. `demo/p09_weak_tests.py` holds two tests of the kind assistants write by default:

<Callout type="note" title="Do not chase the pyramid for its own sake">
Seven layers of tests on a weekend project is as much ceremony as seven layers of code. Start with the unit tests of your rules and one or two end-to-end tests of the paths that earn money or hold data. Add API tests where wiring bites you, a contract snapshot when you have a caller you do not control, and a load check when you have a performance promise. The shape follows what has actually broken.
</Callout>

The review habit, one line: **for every AI-written test, ask what change to the code would make it fail, and if the answer is "nothing realistic", delete it or rewrite it.** Is the repository a fake that copies, or a mock that nods? Does the assertion read what is stored, or only what was called? Did an override remove the very thing the test claims to cover? Those three questions catch most of what goes green and means nothing.

### Mở đầu: hai nửa đều đúng

Ngày 23/09/1999, tàu Mars Climate Orbiter của NASA tới sao Hỏa rồi mất. Backend của bạn cũng đầy những chỗ nối như vậy: service với database, handler với bên gọi, code của bạn với thư viện token. Bộ test là cách rẻ và thường xuyên để kiểm các chỗ nối đó. 1. **Kim tự tháp test trong một bộ test thật trông thế nào?** Số test và số giây, không phải hình minh họa trong sách giáo khoa.
2. **Vì sao fake thắng mock** với thứ do chính bạn viết, và viết fake ra sao.
3. **Test app thật trong cùng process thế nào?** Override, một database cho mỗi test, một token thật.
4. **Hai check nào nằm cạnh kim tự tháp?** Contract snapshot và một load check nhỏ xíu.

## 2. Unit test: luật, một fake, không framework

Bài 4 tách clue.api sao cho `layered_service.py` không import FastAPI và nói chuyện với kho lưu trữ qua protocol `CaseRepository`. Chỗ nối đó là lý do đáy kim tự tháp rẻ: bất kỳ đối tượng nào có `add`, `get`, `save` đều thế được chỗ database.

<BeP09Seam />

Đồ thế chỗ là `demo/tests_p09/fakes.py`. Nó là bản cài đặt thật, chỉ không bền:

```python
class FakeCaseRepository:
    def __init__(self) -> None:
        self.rows: dict[str, CaseRecord] = {}

    def add(self, record: CaseRecord) -> None:
        self.rows[record.case_id] = replace(record)

    def get(self, case_id: str) -> CaseRecord | None:
        row = self.rows.get(case_id)
        return replace(row) if row else None

    def save(self, record: CaseRecord) -> None:
        self.rows[record.case_id] = replace(record)
```

Mấy lời gọi `replace(...)` là điểm mấu chốt của file. Một cái dict lưu đúng đối tượng bạn đưa vào sẽ che mất cả một loại bug, vì bên gọi và "database" dùng chung một đối tượng. ## 3. Mock gật đầu, fake thì có thể cãi

Giờ tới cái bẫy. Giả sử AI "refactor" hàm `close` và diff trông vô hại. `demo/p09_buggy_service.py`:

```python
class BuggyCaseService(CaseService):
    def close(self, case_id: str, resolution: str) -> CaseRecord:
        case = self._require(case_id)
        if case.detective is None:
            raise CaseRuleError("an unassigned case cannot be closed")
        self._repo.save(case)  # saved too early: status is still "open" here
```

## 4. API test: app thật, trong cùng process

Unit test lo phần luật. Chúng không nói gì về việc route có parse được `?resolution=` không, exception handler có đổi `CaseRuleError` thành 409 không, hay `Depends` có nối đúng thứ bạn nghĩ không. Muốn biết thì phải gọi chính app.

`TestClient` của FastAPI gọi app ASGI ngay trong process, nên không port, không server nào phải bật, còn `app.dependency_overrides` đổi dependency này lấy dependency khác. Đây là ý tưởng của bài 4, lớn thêm thành fixture. Fake đi vào qua `get_repo`, còn route, handler và `CaseService` thật chạy trên nó:

Dòng dọn dẹp không phải tùy chọn. `app` là object cấp module mà mọi test trong process dùng chung, nên một override không được xóa sẽ rò sang test kế tiếp, và bạn gặp kiểu fail phụ thuộc thứ tự chạy. Đặt dọn dẹp sau `yield` của fixture thì nó chạy kể cả khi test fail.

`TestClient` là đồng bộ và chạy app từ một thread riêng. Khi chính test cần là `async`, hoặc cần dùng chung event loop với thứ khác, hãy dùng `httpx.AsyncClient` với `ASGITransport`. Nó tới cùng app đó, vẫn không qua mạng:

`@pytest.mark.anyio` đến từ plugin `anyio` đi kèm các dependency của Starlette, và fixture `anyio_backend` trong `conftest.py` chọn asyncio. Dùng nó khi chính thân test cần `await`, ví dụ để gọi code async của bạn ngay cạnh request.

### Một database cho mỗi test

Fake không cho bạn biết SQL, cách xử lý session hay commit của bạn có chạy thật không. Muốn vậy cần database thật, và SQLite làm chuyện này rẻ: **một file mới cho mỗi test.** Bài 5 cho app dependency `get_session` với luật commit khi thành công, rollback khi lỗi, và đó chính là luật ta muốn test, nên không được override `get_session`. Ta chỉ đổi thứ nó dùng để tạo session:

```python
@pytest.fixture
def sql_sessions(tmp_path, monkeypatch):
    """A brand-new SQLite file per test, wired in where p05_db builds sessions."""
    engine = create_engine(
        f"sqlite:///{tmp_path / 'test.db'}", connect_args={"check_same_thread": False}
    )
    p05_db.Base.metadata.create_all(engine)
    factory = sessionmaker(engine, expire_on_commit=False)
    # get_session() stays the real one (its commit/rollback is under test);
    # only the factory it opens sessions from is swapped.
    monkeypatch.setattr(p05_db, "SessionLocal", factory)
    yield factory
    engine.dispose()
```

`tmp_path` là thư mục tạm riêng cho từng test của pytest, nên file mới tinh cho mỗi test, và pytest tự dọn những thư mục cũ. `monkeypatch.setattr` đổi `p05_db.SessionLocal` rồi trả lại khi test kết thúc. Còn một cái bẫy âm thầm hơn ở đầu `conftest.py`: `p05_db` đọc `DATABASE_URL` ngay lúc được import, nên biến môi trường phải đặt *trước* mọi lần import module demo. Không có nó, chỉ riêng việc import `p05_app` cũng đẻ ra một `clue.db` trong thư mục bạn chạy pytest.

```python
def login(base_url: str, user: str, password: str) -> dict:
    form = {"username": user, "password": password, "scope": "cases:read"}
    token = httpx.post(f"{base_url}/token", data=form).json()["access_token"]
    return {"Authorization": f"Bearer {token}"}


def test_login_then_read_own_case(base_url):
    headers = login(base_url, "alice", "alice-demo-pw")
    response = httpx.get(f"{base_url}/cases/C-1", headers=headers)
    assert response.status_code == 200


def test_a_valid_login_still_cannot_read_someone_elses_case(base_url):
    headers = login(base_url, "bob", "bob-demo-pw")
    assert httpx.get(f"{base_url}/cases/C-1", headers=headers).status_code == 404
```

`scope="module"` bật server một lần cho cả file, và `finally` bảo đảm nó được tắt kể cả khi test fail. Test thứ hai là cái đáng có: một lần đăng nhập *hợp lệ* của bob vẫn nhận 404 với case của alice. Hai test là con số hợp lý. Mỗi test end-to-end thêm vào lại phải trả phí khởi động, hoặc chia sẻ trạng thái với các test khác.

## 6. Contract: ghim lại thứ bên gọi nhìn thấy

Có những thay đổi không phá luật nào, không phá route nào, mà vẫn phá bên gọi. Đổi `title` thành `name` trong body request, và mọi unit test lẫn API test đi qua code của bạn vẫn pass, vì code của bạn thống nhất với chính nó. Client đang gửi `title` mới là bên nhận 422. SNAPSHOT = Path(__file__).with_name("openapi.snapshot.json")


```python
def as_lines(document: dict) -> list[str]:
    return json.dumps(document, indent=2, sort_keys=True).splitlines()


def test_openapi_matches_the_committed_snapshot():
    committed = as_lines(json.loads(SNAPSHOT.read_text()))
    generated = as_lines(app.openapi())
    diff = list(difflib.unified_diff(committed, generated, "committed", "generated", lineterm="", n=1))
    if diff:
        pytest.fail("the API contract changed:\n" + "\n".join(diff), pytrace=False)
```

## 7. Load như một lần kiểm tra

Load test là một phép đo, nhưng một phiên bản rất nhỏ cũng làm được vai trò check: gửi vài trăm request, tính p95 (mốc thời gian mà 95 phần trăm request nhanh hơn), và fail build khi vượt ngưỡng. Nó không cho bạn biết sức chịu tải. Nó cho bạn biết một thay đổi vừa làm endpoint chậm đi nhiều lần. `demo/p09_burst.py` làm việc đó bằng httpx:

```python
async def one(client: httpx.AsyncClient, path: str, gate: asyncio.Semaphore) -> float:
    async with gate:  # at most `concurrency` requests in flight
        started = time.perf_counter()
        response = await client.get(path)
        response.raise_for_status()
        return (time.perf_counter() - started) * 1000


async def main(base: str, path: str, n: int, concurrency: int, bound_ms: float) -> int:
    gate = asyncio.Semaphore(concurrency)
    async with httpx.AsyncClient(base_url=base, timeout=60) as client:
        await client.get(path)  # warm-up: first request pays connection and import costs
        started = time.perf_counter()
        times = sorted(await asyncio.gather(*(one(client, path, gate) for _ in range(n))))
        wall = time.perf_counter() - started
    p50 = statistics.median(times)
    p95 = times[int(len(times) * 0.95) - 1]
    verdict = "ok" if p95 <= bound_ms else "FAIL"
    print(
        f"GET {path} x{n} at {concurrency}: {n / wall:.0f} req/s | "
        f"p50 {p50:.1f} ms | p95 {p95:.1f} ms | max {times[-1]:.1f} ms | "
        f"bound {bound_ms:.0f} ms -> {verdict}"
    )
    return 0 if p95 <= bound_ms else 1
```

`asyncio.Semaphore` giới hạn số request bay cùng lúc, chính là nghĩa của "5 cái một lúc". Request đầu là lượt khởi động, trả giá cho việc dựng kết nối và chi phí lần gọi đầu, còn `sys.exit(1)` khi vượt ngưỡng cho phép bất kỳ bước CI nào coi nó như một lệnh thường. Mình trỏ nó vào hai endpoint của bài 5: `/lazy`, chạy 101 query cho 100 case (bài toán N+1), và `/eager`, bản sửa một dòng chạy 2 query.

## 8. Ai test cái test?

Giờ bạn có một bộ test xanh. Câu hỏi quan trọng là nó có đỏ được không. Khi AI viết test, hãy hỏi bằng cách phá code có chủ ý: xóa một luật và xem test nào nhận ra. `demo/p09_weak_tests.py` chứa hai test kiểu trợ lý hay viết mặc định:

```python
def test_close_returns_ok():
    service = MagicMock()  # replaces the very thing the endpoint exists to call
    service.close.return_value = CaseRecord("C-1", "gnome", "closed", "wren", "found")
    app.dependency_overrides[get_service] = lambda: service
    try:
        response = client.post("/cases/C-1/close", params={"resolution": "found"})
    finally:
        app.dependency_overrides.clear()
    assert response.status_code == 200
    service.close.assert_called_once()


def test_open_returns_201():
    response = client.post("/cases", params={"title": "The missing gnome"})
    assert response.status_code == 201  # the body, the id, the status: never looked at
```

Test đầu mock service, đúng thứ mà endpoint sinh ra để gọi, rồi assert 200 và assert mock đã được gọi. Test thứ hai assert 201 và không bao giờ nhìn vào body. Giờ xóa luật "an unassigned case cannot be closed" khỏi một bản copy của `layered_service.py` và chạy cả hai bộ:

<Callout type="note" title="Đừng đuổi theo kim tự tháp vì chính nó">
Bảy tầng test cho một dự án cuối tuần cũng là nghi thức như bảy tầng code. Bắt đầu bằng unit test cho các luật và một hai test end-to-end cho những đường đi sinh ra tiền hoặc giữ dữ liệu. Thêm API test ở chỗ việc nối dây hay cắn bạn, contract snapshot khi có bên gọi bạn không kiểm soát, và load check khi có lời hứa về hiệu năng. Hình dạng đi theo những gì thực sự đã hỏng.
</Callout>

Thói quen duyệt code, gói trong một dòng: **với mỗi test AI viết, hỏi xem đổi code thế nào thì nó fail, và nếu câu trả lời là "không có thay đổi nào thực tế" thì xóa hoặc viết lại.** Repository ở đây là fake biết copy hay mock chỉ biết gật? Assertion đọc thứ đã lưu hay chỉ đọc thứ đã gọi? Có override nào gỡ mất chính thứ test tuyên bố bao phủ không? Ba câu hỏi đó bắt được phần lớn những test xanh mà vô nghĩa.
