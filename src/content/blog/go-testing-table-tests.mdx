### A test that fails for no reason is worse than no test

Google measured its own test suite and found that about 1.5% of all test runs report a "flaky" result: the same code both passes and fails. Almost 16% of its tests are flaky at some level, and about 84% of the pass-to-fail changes its build system saw involved a flaky test. People learn to ignore a test that cries wolf, and then they ignore the real failure too.

Go's answer is small. Testing is built into the language tools: no framework to install, no assertion library, no runner config. You write ordinary Go in a file ending in `_test.go` and run `go test`. This post shows the habits that keep those tests fast, readable and not flaky.

<Callout type="note" title="TL;DR">
Put tests in `_test.go` files next to the code and run them with `go test`. Write many cases as one table-driven test with `t.Run` subtests, so adding a case costs one line. Keep tests fast and repeatable: pass the time in instead of calling `time.Now()`, never wait with `time.Sleep`, and fence off slow tests with `-short` or a build tag. Use `httptest` to test HTTP handlers in memory, and run `go test -race` to catch data races.
</Callout>

## Coming from Java, Python or JavaScript

Here is how the test tools you know map to Go.

| You know | Java | Python | JavaScript | Go |
|---|---|---|---|---|
| Test framework | JUnit | pytest | Jest | `testing` (standard library) |
| Where tests live | `src/test/java` | `test_*.py` | `*.test.js` | `*_test.go`, same folder |
| A test is | `@Test` method | `test_` function | `test("...", fn)` | `func TestXxx(t *testing.T)` |
| Assertion | `assertEquals` | `assert a == b` | `expect(a).toBe(b)` | plain `if got != want` and `t.Errorf` |
| Parameterized test | `@ParameterizedTest` | `@pytest.mark.parametrize` | `test.each` | table-driven test + `t.Run` |
| Run | `mvn test` | `pytest` | `npm test` | `go test ./...` |
| Mocks | Mockito | `unittest.mock` | `jest.mock` | small interfaces and hand-written fakes |

Two differences matter most. Go has no `assert` function: you write the `if` and decide the message yourself. And there is no test runner to configure, because `go test` is part of the `go` command you already use.

## Your first test

We need something to test. This function turns text like `"8080"` into a TCP port number, and returns an error for bad input. If errors are new to you, they have their own post: [Go errors, defer and panic](/blog/go-errors-defer-panic/). Here you only need to know that a function can return an `error` next to its result, and that `nil` means "no error".

```go
// port.go
package port

import (
	"fmt"
	"strconv"
)

// Parse turns text like "8080" into a TCP port number.
func Parse(s string) (int, error) {
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("port %q is not a number", s)
	}
	if n < 1 || n > 65535 {
		return 0, fmt.Errorf("port %d is out of range 1-65535", n)
	}
	return n, nil
}
```

A test goes in a file whose name ends in `_test.go`, in the same folder. The `go` command compiles these files only when you run tests, so they never end up in your program. A test is a function named `TestSomething` that takes one `*testing.T`. That `t` is your handle to the test: you use it to report failures.

<GoP06Files />

```go
// port_test.go
package port

import "testing"

func TestParseValid(t *testing.T) {
	got, err := Parse("8080")
	if err != nil {
		t.Fatalf("Parse(\"8080\") returned error: %v", err)
	}
	if got != 8080 {
		t.Errorf("Parse(\"8080\") = %d, want 8080", got)
	}
}
```

There are two ways to fail. `t.Errorf` marks the test failed and keeps going, so you see every problem at once. `t.Fatalf` marks it failed and stops this test right there; use it when the next lines would be meaningless, like checking `got` after an error. The `%q`, `%d` and `%v` are format verbs: the table in [Go variables, types, pointers and functions](/blog/go-variables-types-pointers-functions/) lists them.

<TerminalOutput command="go test -v" label="Go 1.27.1 · darwin/arm64" caption="-v lists every test. Without it, a passing package prints only PASS and the package line.">
```text
=== RUN   TestParseValid
--- PASS: TestParseValid (0.00s)
PASS
ok  	example.com/port	0.217s
```
</TerminalOutput>

<Concepts>

- **`_test.go` file**: a file the `go` command compiles only for `go test`. Tests sit next to the code they check.
- **`*testing.T`**: the value every test receives. Its methods (`Errorf`, `Fatalf`, `Run`, `Helper`...) report results.
- **`t.Errorf` vs `t.Fatalf`**: both fail the test; `Fatalf` also stops it immediately.

</Concepts>

## Table-driven tests

Writing one test function per case copies the same four steps again and again: call, expect, compare, report. Go's habit is to write that logic once and put the cases in a table, a slice where each element is one case. Adding a case then costs one line.

Two pieces of syntax are used here. The table's element type is a struct (a bundle of named fields, covered in [Go structs, methods and interfaces](/blog/go-structs-methods-interfaces/)) declared inline without a name. And `t.Run(name, func(t *testing.T) { ... })` runs a subtest: the function literal is a closure, explained in [Go errors, defer and panic](/blog/go-errors-defer-panic/). All you need now is that each case runs as its own named test. Read `[]struct{...}{...}` as: a slice whose elements are an unnamed struct type, followed by the elements themselves.

```go
package port

import "testing"

func TestParse(t *testing.T) {
	tests := []struct {
		name    string
		input   string
		want    int
		wantErr bool
	}{
		{"normal port", "8080", 8080, false},
		{"lowest port", "1", 1, false},
		{"highest port", "65535", 65535, false},
		{"zero", "0", 0, true},
		{"too big", "65536", 0, true},
		{"not a number", "http", 0, true},
		{"empty", "", 0, true},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got, err := Parse(tc.input)
			if (err != nil) != tc.wantErr {
				t.Fatalf("Parse(%q) error = %v, wantErr %v", tc.input, err, tc.wantErr)
			}
			if got != tc.want {
				t.Errorf("Parse(%q) = %d, want %d", tc.input, got, tc.want)
			}
		})
	}
}
```

<GoTableTestDemo />

The line `if (err != nil) != tc.wantErr` compares two true/false values: "did we get an error?" and "did we expect one?". It is true, and the test fails, only when the two disagree.

Each case shows up as its own line in the output, named after its `name` field with spaces turned into underscores. That is why good case names matter: they are what you read when something breaks.

<Concepts>

- **Table-driven test**: one test function with a slice of cases and one loop that runs the same checks on each.
- **Subtest**: a named test started with `t.Run` inside another test. It reports, filters and fails on its own.
- **`-run`**: a `go test` flag that runs only tests whose names match a pattern.

</Concepts>

## Helpers and fixtures

Some checks repeat across tests, so you move them into a helper function. Call `t.Helper()` on its first line. Without it, a failure is reported at the line inside the helper; with it, Go reports the line that called the helper, which is where you want to look.

This test file also uses `package port_test` instead of `package port`. A test file may live in a separate `_test` package: it can then only use what the package exports, the way real callers do, so it checks your public API rather than your internals.

```go
package port_test

import (
	"testing"

	"example.com/port"
)

func wantPort(t *testing.T, input string, want int) {
	t.Helper()
	got, err := port.Parse(input)
	if err != nil {
		t.Fatalf("Parse(%q): %v", input, err)
	}
	if got != want {
		t.Errorf("Parse(%q) = %d, want %d", input, got, want)
	}
}

func TestHelpers(t *testing.T) {
	wantPort(t, "8080", 8080)
	wantPort(t, "443", 80)
}
```

For files and other set-up, the `testing` package has two tools. `t.TempDir()` gives you a fresh folder that Go deletes when the test ends. `t.Cleanup(fn)` registers a function to run after the test, like a `defer` that also covers subtests. Fixed input files belong in a folder named `testdata`, which the `go` tool ignores when it builds packages.

```go
package port_test

import (
	"os"
	"path/filepath"
	"testing"
)

func TestReadConfig(t *testing.T) {
	dir := t.TempDir() // a fresh folder, deleted when the test ends
	path := filepath.Join(dir, "port.txt")
	if err := os.WriteFile(path, []byte("8080\n"), 0o600); err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() { t.Log("cleanup runs last") })

	data, err := os.ReadFile(path)
	if err != nil {
		t.Fatal(err)
	}
	t.Logf("read %q", data)
}
```


<Concepts>

- **Helper function**: a function that takes `t` and does a repeated check. `t.Helper()` makes failures point at its caller.
- **`package x_test`**: a test file in a separate package that can use only the exported names of `x`.
- **`testdata/`**: a folder for fixture files (fixed sample inputs). The `go` tool skips it when building.
- **`t.TempDir`, `t.Cleanup`**: a throwaway folder for the test, and a function to run when the test ends.

</Concepts>

## Running tests: flags that find bugs

`go test ./...` runs every package under the current folder. A few flags change how the tests run, and they find real bugs. The full list is in the `go` command docs (see sources).

| Flag | What it does | Why you want it |
|---|---|---|
| `-v` | print every test and subtest | see what ran |
| `-run <pattern>` | run only matching tests | iterate on one case |
| `-count=1` | ignore the result cache | rerun tests that read files or the network |
| `-short` | skip tests that call `testing.Short()` | fast loop (see "Slow tests") |

When you run a list of packages such as `./...`, Go caches passing results, so an unchanged package prints `(cached)` the next time. Use `-count=1` when you want a real rerun.

Two more flags, one line each. Calling `t.Parallel()` at the top of a test lets it run alongside other parallel tests; that is faster only when the tests share nothing (no file, global variable or database row). `-shuffle=on` runs tests in random order and prints the seed, so a failing order can be replayed with `-shuffle=<seed>`; it exposes tests that depend on each other. `-parallel N` caps how many parallel tests run at once.

<Concepts>

- **Test cache**: when you run a package list like `./...`, Go remembers a passing result and prints `(cached)` when nothing changed. `-count=1` turns it off.
- **`t.Parallel()`**: lets this test run at the same time as other parallel tests.
- **`-shuffle`**: runs tests in a random order to expose hidden dependencies between them.

</Concepts>

## Slow tests: `-short`, build tags, environment

A pyramid is the usual picture of test types: many fast unit tests at the bottom, fewer slow integration tests (a real database, a real network) above them. Go has three simple ways to keep the slow ones from blocking everyone.

1. **`-short`.** A slow test checks `testing.Short()` and skips itself. `go test -short` is then your fast loop.
2. **A build tag.** A first line `//go:build integration` keeps the file out unless you ask: `go test -tags=integration`.
3. **An environment variable.** The test reads `os.Getenv("...")` and skips if it is not set. Use it for things like a database address.

```go
package session

import (
	"testing"
	"time"
)

func TestSlowDatabase(t *testing.T) {
	if testing.Short() {
		t.Skip("skipping in short mode")
	}
	time.Sleep(2 * time.Second) // stand-in for a slow real database call
}
```

```go
//go:build integration

package session

import "testing"

func TestAgainstRealDatabase(t *testing.T) {
	t.Log("talking to the real database")
}
```

## Time without `time.Sleep`

A test that sleeps is guessing how long the work takes. Sleep 100 ms and it passes on your laptop and fails on a busy CI machine; sleep 5 seconds and the whole suite crawls. The fix depends on why you were waiting.

If the code you test reads the clock, do not let it read the clock. Pass the time in. `Expired` below takes `now` as a parameter instead of calling `time.Now()` inside, so a test can pick any moment it likes, and it runs in microseconds.

```go
package session

import "time"

// Expired reports whether a session created at `created` is too old at time `now`.
func Expired(created, now time.Time, ttl time.Duration) bool {
	return now.Sub(created) > ttl
}
```

```go
package session

import (
	"testing"
	"time"
)

func TestExpired(t *testing.T) {
	created := time.Date(2026, 11, 23, 9, 0, 0, 0, time.UTC)
	ttl := 30 * time.Minute

	tests := []struct {
		name string
		now  time.Time
		want bool
	}{
		{"just created", created, false},
		{"29 minutes later", created.Add(29 * time.Minute), false},
		{"31 minutes later", created.Add(31 * time.Minute), true},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			if got := Expired(created, tc.now, ttl); got != tc.want {
				t.Errorf("Expired(...) = %v, want %v", got, tc.want)
			}
		})
	}
}
```

<TerminalOutput command="go test -v -run TestExpired" label="Go 1.27.1 · darwin/arm64" caption="Three moments in time, none of them waited for. 31 minutes passes in no time at all.">
```text
=== RUN   TestExpired
=== RUN   TestExpired/just_created
=== RUN   TestExpired/29_minutes_later
=== RUN   TestExpired/31_minutes_later
--- PASS: TestExpired (0.00s)
    --- PASS: TestExpired/just_created (0.00s)
    --- PASS: TestExpired/29_minutes_later (0.00s)
    --- PASS: TestExpired/31_minutes_later (0.00s)
```
</TerminalOutput>

<GoP06Time />

The other reason to sleep is waiting for work running in the background, a goroutine (you will meet them in [Go goroutines, channels and select](/blog/go-goroutines-channels-select/)). The rule there is the same in spirit: wait for a signal that the work is done, such as a channel or a `sync.WaitGroup`, not for a clock. When you have no signal to wait on, poll the condition in a loop with a deadline instead of one long sleep.

<Concepts>

- **Flaky test**: a test that sometimes passes and sometimes fails with no code change. Sleeping for a fixed time is a common cause.
- **Pass the time in**: take `now` as a parameter so a test can control it, instead of calling `time.Now()` inside the function.

</Concepts>

## Testing HTTP handlers

A Go web handler is a function that gets a request and a response writer. The `net/http/httptest` package, part of the standard library, lets you call that function directly, with no network port and no server. `httptest.NewRequest` builds a request. `httptest.NewRecorder` stands in for the response writer and remembers the status, headers and body for you to check.

```go
package ht

import (
	"fmt"
	"net/http"
)

// Hello greets the name in the ?name= query parameter.
func Hello(w http.ResponseWriter, r *http.Request) {
	name := r.URL.Query().Get("name")
	if name == "" {
		http.Error(w, "name is required", http.StatusBadRequest)
		return
	}
	fmt.Fprintf(w, "hello, %s", name)
}
```

```go
package ht

import (
	"net/http"
	"net/http/httptest"
	"testing"
)

func TestHello(t *testing.T) {
	tests := []struct {
		name       string
		url        string
		wantStatus int
		wantBody   string
	}{
		{"with a name", "/hello?name=Linh", http.StatusOK, "hello, Linh"},
		{"missing name", "/hello", http.StatusBadRequest, "name is required\n"},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			req := httptest.NewRequest(http.MethodGet, tc.url, nil)
			rec := httptest.NewRecorder()

			Hello(rec, req)

			if rec.Code != tc.wantStatus {
				t.Errorf("status = %d, want %d", rec.Code, tc.wantStatus)
			}
			if rec.Body.String() != tc.wantBody {
				t.Errorf("body = %q, want %q", rec.Body.String(), tc.wantBody)
			}
		})
	}
}
```

To test code that is an HTTP client, `httptest.NewServer` starts a real server on a free local port and gives you its URL, so you can point the client at it. Its sibling package `testing/iotest` has readers that fail on purpose, to test code that reads streams.

<Concepts>

- **`httptest.NewRecorder`**: a fake response writer that records the status code, headers and body.
- **`httptest.NewRequest`**: builds an HTTP request in memory, without any network.
- **`httptest.NewServer`**: starts a real temporary local server, for testing HTTP clients.

</Concepts>

## `-race`: a first look

A data race happens when two goroutines touch the same variable at the same time and at least one of them writes. These bugs pass most test runs and then fail in production, so you cannot find them by running a test again. Go can instrument the program to watch memory accesses: add `-race`.

The Go team added the race detector in 2012. Its announcement says it had found 42 races in the standard library by then, and that it became part of Go's own continuous build. Add `go test -race ./...` to your CI from day one; it makes tests slower, but it is the cheapest way to find this kind of bug.

<QuoteCard author="Dmitry Vyukov and Andrew Gerrand" role="The Go Blog" sourceTitle="Introducing the Go Race Detector" sourceUrl="https://go.dev/blog/race-detector">
The technology was integrated with Go in September 2012; since then it has detected 42 races in the standard library. It is now part of our continuous build process, where it continues to catch race conditions as they arise.
</QuoteCard>

In a test where two goroutines (functions running at the same time as the rest of the program; post 7 explains them) both add to one counter, plain `go test` prints PASS, while `go test -race` prints `WARNING: DATA RACE`, then the read, the previous write, the goroutine for each and the file and line of each access.

How the detector works, and how to fix a race, is in [Go concurrency: scheduler, channels, context and mutexes](/blog/go-concurrency-scheduler-channels-context-mutexes/).

<Concepts>

- **Data race**: two goroutines access one variable at once and at least one writes. The result depends on timing.
- **`-race`**: a flag that builds the program with checks that report data races as they happen. Slower, but it finds bugs plain runs miss.

</Concepts>

## Key takeaways

- Tests are plain Go in `_test.go` files, run by `go test`; there is no framework, and failures are reported with `t.Errorf` and `t.Fatalf`.
- Put many cases in one table and run each with `t.Run`, so adding a case is one line and a failure names its case.
- Make time an input and wait for signals, not clocks, so tests are fast and do not flake.
- Fence off slow tests with `-short`, a build tag or an environment variable, and run `-shuffle=on` and `-race` regularly.
- Use `httptest` to test handlers in memory, and read `-cover` as a map of untested code, not a score.

Cách Go giải quyết khá gọn. Công cụ test có sẵn trong ngôn ngữ: không cần cài framework, không cần thư viện assert, không cần cấu hình runner. Bạn viết Go bình thường trong file có đuôi `_test.go` rồi chạy `go test`. Bài này chỉ ra những thói quen giúp test nhanh, dễ đọc và không flaky.

## Nếu bạn đến từ Java, Python hay JavaScript

Bảng dưới ánh xạ công cụ test bạn quen sang Go.

| Bạn đã biết | Java | Python | JavaScript | Go |
|---|---|---|---|---|
| Framework test | JUnit | pytest | Jest | `testing` (thư viện chuẩn) |
| Test nằm ở đâu | `src/test/java` | `test_*.py` | `*.test.js` | `*_test.go`, cùng thư mục |
| Một test là | method `@Test` | hàm `test_` | `test("...", fn)` | `func TestXxx(t *testing.T)` |
| Assertion | `assertEquals` | `assert a == b` | `expect(a).toBe(b)` | `if got != want` thường và `t.Errorf` |
| Test tham số hóa | `@ParameterizedTest` | `@pytest.mark.parametrize` | `test.each` | table-driven test + `t.Run` |
| Chạy | `mvn test` | `pytest` | `npm test` | `go test ./...` |
| Mock | Mockito | `unittest.mock` | `jest.mock` | interface nhỏ và fake tự viết |

Hai khác biệt quan trọng nhất. Go không có hàm `assert`: bạn tự viết `if` và tự chọn thông báo lỗi. Và không có runner nào để cấu hình, vì `go test` là một phần của lệnh `go` bạn đã dùng.

## Test đầu tiên

Cần có thứ gì đó để test. Hàm này đổi chuỗi như `"8080"` thành số cổng TCP, và trả về lỗi nếu đầu vào sai. Nếu lỗi còn mới với bạn, đã có bài riêng: [Go errors, defer and panic](/blog/go-errors-defer-panic/). Ở đây chỉ cần biết một hàm có thể trả về `error` bên cạnh kết quả, và `nil` nghĩa là "không có lỗi".

```go
// port.go
package port

import (
	"fmt"
	"strconv"
)

// Parse turns text like "8080" into a TCP port number.
func Parse(s string) (int, error) {
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("port %q is not a number", s)
	}
	if n < 1 || n > 65535 {
		return 0, fmt.Errorf("port %d is out of range 1-65535", n)
	}
	return n, nil
}
```

Test nằm trong file có tên kết thúc bằng `_test.go`, cùng thư mục. Lệnh `go` chỉ biên dịch các file này khi chạy test, nên chúng không bao giờ lọt vào chương trình của bạn. Một test là hàm tên `TestSomething` nhận một `*testing.T`. Biến `t` là tay nắm của bạn với test: dùng nó để báo lỗi.

<GoP06Files />

```go
// port_test.go
package port

import "testing"

func TestParseValid(t *testing.T) {
	got, err := Parse("8080")
	if err != nil {
		t.Fatalf("Parse(\"8080\") returned error: %v", err)
	}
	if got != 8080 {
		t.Errorf("Parse(\"8080\") = %d, want 8080", got)
	}
}
```

Có hai cách báo lỗi. `t.Errorf` đánh dấu test fail nhưng vẫn chạy tiếp, nên bạn thấy hết các vấn đề một lượt. `t.Fatalf` đánh dấu fail và dừng test ngay tại đó; dùng khi các dòng sau vô nghĩa, ví dụ kiểm tra `got` sau khi đã có lỗi. `%q`, `%d`, `%v` là các verb định dạng: bảng trong [Go variables, types, pointers and functions](/blog/go-variables-types-pointers-functions/) liệt kê hết.

<TerminalOutput command="go test -v" label="Go 1.27.1 · darwin/arm64" caption="-v liệt kê từng test. Không có nó, package pass chỉ in PASS và dòng tên package.">
```text
=== RUN   TestParseValid
--- PASS: TestParseValid (0.00s)
PASS
ok  	example.com/port	0.217s
```
</TerminalOutput>

<Concepts>

- **File `_test.go`**: file mà lệnh `go` chỉ biên dịch khi chạy `go test`. Test nằm cạnh code mà nó kiểm tra.
- **`*testing.T`**: giá trị mà mọi test nhận được. Các method của nó (`Errorf`, `Fatalf`, `Run`, `Helper`...) báo kết quả.
- **`t.Errorf` và `t.Fatalf`**: cả hai đều làm test fail; `Fatalf` còn dừng test ngay.

</Concepts>

## Table-driven test

Viết mỗi case một hàm test sẽ chép đi chép lại cùng bốn bước: gọi, đặt kỳ vọng, so sánh, báo lỗi. Thói quen của Go là viết logic đó một lần và để các case vào một bảng, tức một slice mà mỗi phần tử là một case. Thêm case chỉ tốn một dòng.

Đoạn code dùng hai cú pháp. Kiểu phần tử của bảng là một struct (nhóm các field có tên, xem [Go structs, methods and interfaces](/blog/go-structs-methods-interfaces/)) khai báo ngay tại chỗ, không đặt tên. Và `t.Run(name, func(t *testing.T) { ... })` chạy một subtest: hàm literal đó là closure, giải thích trong [Go errors, defer and panic](/blog/go-errors-defer-panic/). Lúc này chỉ cần biết mỗi case chạy như một test riêng có tên. Đọc `[]struct{...}{...}` như sau: một slice mà phần tử là struct không tên, theo sau là chính các phần tử đó.

```go
package port

import "testing"

func TestParse(t *testing.T) {
	tests := []struct {
		name    string
		input   string
		want    int
		wantErr bool
	}{
		{"normal port", "8080", 8080, false},
		{"lowest port", "1", 1, false},
		{"highest port", "65535", 65535, false},
		{"zero", "0", 0, true},
		{"too big", "65536", 0, true},
		{"not a number", "http", 0, true},
		{"empty", "", 0, true},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got, err := Parse(tc.input)
			if (err != nil) != tc.wantErr {
				t.Fatalf("Parse(%q) error = %v, wantErr %v", tc.input, err, tc.wantErr)
			}
			if got != tc.want {
				t.Errorf("Parse(%q) = %d, want %d", tc.input, got, tc.want)
			}
		})
	}
}
```

<GoTableTestDemo />

Dòng `if (err != nil) != tc.wantErr` so sánh hai giá trị đúng/sai: "có nhận được lỗi không?" và "có mong đợi lỗi không?". Nó đúng, và test fail, chỉ khi hai giá trị này khác nhau.

Mỗi case hiện thành một dòng riêng trong kết quả, lấy tên từ field `name` với dấu cách đổi thành gạch dưới. Vì vậy tên case rất quan trọng: đó là thứ bạn đọc khi có gì đó hỏng.

- **`-run`**: cờ của `go test` chỉ chạy các test có tên khớp pattern.

## Helper và fixture

Có những bước kiểm tra lặp lại giữa nhiều test, nên bạn chuyển chúng vào một hàm helper. Gọi `t.Helper()` ở dòng đầu tiên của nó. Không có dòng này, lỗi được báo tại dòng bên trong helper; có nó, Go báo dòng đã gọi helper, đúng chỗ bạn cần xem.

File test này còn dùng `package port_test` thay vì `package port`. Một file test có thể nằm trong package `_test` riêng: khi đó nó chỉ dùng được những gì package xuất ra, giống người dùng thật, nên nó kiểm tra API công khai chứ không phải phần bên trong.

```go
package port_test

import (
	"testing"

	"example.com/port"
)

func wantPort(t *testing.T, input string, want int) {
	t.Helper()
	got, err := port.Parse(input)
	if err != nil {
		t.Fatalf("Parse(%q): %v", input, err)
	}
	if got != want {
		t.Errorf("Parse(%q) = %d, want %d", input, got, want)
	}
}

func TestHelpers(t *testing.T) {
	wantPort(t, "8080", 8080)
	wantPort(t, "443", 80)
}
```

Với file và các bước chuẩn bị khác, package `testing` có hai công cụ. `t.TempDir()` cho bạn một thư mục mới mà Go xóa khi test kết thúc. `t.Cleanup(fn)` đăng ký một hàm chạy sau khi test xong, giống `defer` nhưng bao cả subtest. File đầu vào cố định nên để trong thư mục tên `testdata`, thư mục mà công cụ `go` bỏ qua khi build package.

```go
package port_test

import (
	"os"
	"path/filepath"
	"testing"
)

func TestReadConfig(t *testing.T) {
	dir := t.TempDir() // a fresh folder, deleted when the test ends
	path := filepath.Join(dir, "port.txt")
	if err := os.WriteFile(path, []byte("8080\n"), 0o600); err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() { t.Log("cleanup runs last") })

	data, err := os.ReadFile(path)
	if err != nil {
		t.Fatal(err)
	}
	t.Logf("read %q", data)
}
```

- **Hàm helper**: hàm nhận `t` và làm một bước kiểm tra lặp lại. `t.Helper()` làm lỗi chỉ về nơi gọi nó.
- **`package x_test`**: file test nằm trong package riêng, chỉ dùng được các tên được xuất của `x`.
- **`testdata/`**: thư mục chứa file fixture (đầu vào mẫu cố định). Công cụ `go` bỏ qua nó khi build.
- **`t.TempDir`, `t.Cleanup`**: thư mục dùng một lần cho test, và hàm chạy khi test kết thúc.

</Concepts>

## Chạy test: các cờ giúp tìm lỗi

`go test ./...` chạy mọi package dưới thư mục hiện tại. Một vài cờ đổi cách chạy test, và chúng tìm ra lỗi thật. Danh sách đầy đủ nằm trong tài liệu lệnh `go` (xem phần nguồn).

| Cờ | Tác dụng | Vì sao nên dùng |
|---|---|---|
| `-v` | in từng test và subtest | thấy cái gì đã chạy |
| `-run <pattern>` | chỉ chạy test khớp | lặp nhanh trên một case |
| `-count=1` | bỏ qua cache kết quả | chạy lại test đọc file hoặc mạng |
| `-short` | bỏ qua test gọi `testing.Short()` | vòng lặp nhanh (xem "Test chậm") |

Khi chạy một danh sách package như `./...`, Go cache kết quả pass, nên package không đổi sẽ in `(cached)` ở lần sau. Dùng `-count=1` khi bạn muốn chạy lại thật.

Thêm hai cờ nữa, mỗi cờ một dòng. Gọi `t.Parallel()` ở đầu một test cho phép nó chạy cùng các test song song khác; chỉ nhanh hơn khi các test không dùng chung gì (không file, biến toàn cục hay dòng database). `-shuffle=on` chạy test theo thứ tự ngẫu nhiên và in ra seed, để chạy lại đúng thứ tự gây lỗi bằng `-shuffle=<seed>`; nó lộ ra các test phụ thuộc lẫn nhau. `-parallel N` giới hạn số test song song chạy cùng lúc.

<Concepts>

- **Test cache**: khi chạy danh sách package như `./...`, Go nhớ kết quả pass và in `(cached)` khi không có gì đổi. `-count=1` tắt nó đi.
- **`t.Parallel()`**: cho phép test này chạy cùng lúc với các test song song khác.
- **`-shuffle`**: chạy test theo thứ tự ngẫu nhiên để lộ ra những phụ thuộc ngầm giữa chúng.

</Concepts>

## Test chậm: `-short`, build tag, biến môi trường

Hình kim tự tháp là cách vẽ quen thuộc cho các loại test: nhiều unit test nhanh ở đáy, ít integration test chậm hơn ở trên (database thật, mạng thật). Go có ba cách đơn giản để test chậm không làm cả nhóm phải chờ.

1. **`-short`.** Test chậm kiểm tra `testing.Short()` và tự bỏ qua. `go test -short` khi đó là vòng lặp nhanh của bạn.
2. **Build tag.** Dòng đầu `//go:build integration` giữ file ngoài cuộc trừ khi bạn yêu cầu: `go test -tags=integration`.
3. **Biến môi trường.** Test đọc `os.Getenv("...")` và bỏ qua nếu chưa đặt. Dùng cho những thứ như địa chỉ database.

```go
package session

import (
	"testing"
	"time"
)

func TestSlowDatabase(t *testing.T) {
	if testing.Short() {
		t.Skip("skipping in short mode")
	}
	time.Sleep(2 * time.Second) // stand-in for a slow real database call
}
```

```go
//go:build integration

package session

import "testing"

func TestAgainstRealDatabase(t *testing.T) {
	t.Log("talking to the real database")
}
```

## Thời gian mà không cần `time.Sleep`

Test có sleep là test đang đoán. Sleep 100 ms thì chạy ổn trên laptop nhưng fail trên máy CI đang bận; sleep 5 giây thì cả bộ test chạy lê thê. Cách sửa tùy vào lý do bạn phải chờ.

Nếu code cần test đọc đồng hồ, đừng để nó đọc đồng hồ. Hãy truyền thời gian vào. `Expired` bên dưới nhận `now` làm tham số thay vì gọi `time.Now()` bên trong, nên test chọn được bất kỳ thời điểm nào nó muốn và chạy trong vài micro giây.

```go
package session

import "time"

// Expired reports whether a session created at `created` is too old at time `now`.
func Expired(created, now time.Time, ttl time.Duration) bool {
	return now.Sub(created) > ttl
}
```

```go
package session

import (
	"testing"
	"time"
)

func TestExpired(t *testing.T) {
	created := time.Date(2026, 11, 23, 9, 0, 0, 0, time.UTC)
	ttl := 30 * time.Minute

	tests := []struct {
		name string
		now  time.Time
		want bool
	}{
		{"just created", created, false},
		{"29 minutes later", created.Add(29 * time.Minute), false},
		{"31 minutes later", created.Add(31 * time.Minute), true},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			if got := Expired(created, tc.now, ttl); got != tc.want {
				t.Errorf("Expired(...) = %v, want %v", got, tc.want)
			}
		})
	}
}
```

```text

=== RUN   TestExpired/29_minutes_later
=== RUN   TestExpired/31_minutes_later
--- PASS: TestExpired (0.00s)
```

<GoP06Time />

Lý do khác để sleep là chờ công việc chạy nền, một goroutine (bạn sẽ gặp chúng trong [Go goroutines, channels and select](/blog/go-goroutines-channels-select/)). Nguyên tắc ở đó cùng tinh thần: chờ một tín hiệu báo việc đã xong, như channel hoặc `sync.WaitGroup`, đừng chờ theo đồng hồ. Khi không có tín hiệu nào để chờ, hãy kiểm tra điều kiện trong một vòng lặp có hạn chót thay vì một lần sleep dài.

<Concepts>

- **Flaky test**: test lúc pass lúc fail dù code không đổi. Sleep một khoảng cố định là nguyên nhân thường gặp.
- **Truyền thời gian vào**: nhận `now` làm tham số để test điều khiển được, thay vì gọi `time.Now()` bên trong hàm.

</Concepts>

## Test HTTP handler

HTTP handler trong Go là một hàm nhận request và một response writer. Package `net/http/httptest` của thư viện chuẩn cho phép bạn gọi thẳng hàm đó, không cần mở cổng mạng hay server. `httptest.NewRequest` dựng một request. `httptest.NewRecorder` đóng vai response writer và ghi nhớ status, header và body để bạn kiểm tra.

```go
package ht

import (
	"fmt"
	"net/http"
)

// Hello greets the name in the ?name= query parameter.
func Hello(w http.ResponseWriter, r *http.Request) {
	name := r.URL.Query().Get("name")
	if name == "" {
		http.Error(w, "name is required", http.StatusBadRequest)
		return
	}
	fmt.Fprintf(w, "hello, %s", name)
}
```

```go
package ht

import (
	"net/http"
	"net/http/httptest"
	"testing"
)

func TestHello(t *testing.T) {
	tests := []struct {
		name       string
		url        string
		wantStatus int
		wantBody   string
	}{
		{"with a name", "/hello?name=Linh", http.StatusOK, "hello, Linh"},
		{"missing name", "/hello", http.StatusBadRequest, "name is required\n"},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			req := httptest.NewRequest(http.MethodGet, tc.url, nil)
			rec := httptest.NewRecorder()

			Hello(rec, req)

			if rec.Code != tc.wantStatus {
				t.Errorf("status = %d, want %d", rec.Code, tc.wantStatus)
			}
			if rec.Body.String() != tc.wantBody {
				t.Errorf("body = %q, want %q", rec.Body.String(), tc.wantBody)
			}
		})
	}
}
```

<TerminalOutput command="go test -v" label="Go 1.27.1 · darwin/arm64" caption="Một table test bình thường. Handler chạy trong bộ nhớ, cả file mất chưa tới một giây.">
```text
=== RUN   TestHello
=== RUN   TestHello/with_a_name
=== RUN   TestHello/missing_name
--- PASS: TestHello (0.00s)
    --- PASS: TestHello/with_a_name (0.00s)
    --- PASS: TestHello/missing_name (0.00s)

```

Để test code là một HTTP client, `httptest.NewServer` khởi động một server thật trên một cổng cục bộ còn trống và đưa bạn URL của nó, để bạn trỏ client vào. Package anh em `testing/iotest` có các reader cố tình lỗi, dùng để test code đọc luồng dữ liệu.

<Concepts>

- **`httptest.NewRecorder`**: response writer giả, ghi lại status code, header và body.
- **`httptest.NewRequest`**: dựng một HTTP request trong bộ nhớ, không cần mạng.
- **`httptest.NewServer`**: khởi động một server cục bộ thật và tạm thời, để test HTTP client.

</Concepts>

## `-race`: làm quen

Data race xảy ra khi hai goroutine cùng chạm vào một biến cùng lúc và ít nhất một bên ghi. Loại lỗi này qua được hầu hết các lần chạy test rồi mới hỏng ở production, nên chạy lại test không tìm ra nó. Go có thể gắn thêm mã theo dõi truy cập bộ nhớ vào chương trình: thêm `-race`.

Nhóm Go thêm race detector năm 2012. Bài giới thiệu nói đến lúc đó nó đã tìm ra 42 race trong thư viện chuẩn, và nó trở thành một phần của quá trình build liên tục của Go. Hãy thêm `go test -race ./...` vào CI ngay từ đầu; test sẽ chậm hơn, nhưng đây là cách rẻ nhất để bắt loại lỗi này.

<QuoteCard author="Dmitry Vyukov and Andrew Gerrand" role="The Go Blog" sourceTitle="Introducing the Go Race Detector" sourceUrl="https://go.dev/blog/race-detector">
The technology was integrated with Go in September 2012; since then it has detected 42 races in the standard library. It is now part of our continuous build process, where it continues to catch race conditions as they arise.
</QuoteCard>

Trong một test mà hai goroutine (hàm chạy cùng lúc với phần còn lại của chương trình; bài 7 giải thích) cùng cộng vào một biến đếm, `go test` thường in PASS, còn `go test -race` in `WARNING: DATA RACE`, rồi đến lần đọc, lần ghi trước đó, goroutine của từng lần và file cùng dòng của mỗi lần truy cập.

Cách detector hoạt động và cách sửa một race nằm ở [Go concurrency: scheduler, channels, context and mutexes](/blog/go-concurrency-scheduler-channels-context-mutexes/).

<Concepts>

- **Data race**: hai goroutine cùng truy cập một biến và ít nhất một bên ghi. Kết quả phụ thuộc vào thời điểm.
- **`-race`**: cờ build chương trình kèm các kiểm tra báo data race ngay khi nó xảy ra. Chậm hơn, nhưng tìm ra lỗi mà lần chạy thường bỏ sót.

</Concepts>

## Điểm rút ra (Key takeaways)

- Test là Go thường trong file `_test.go`, chạy bằng `go test`; không có framework, và lỗi được báo bằng `t.Errorf` và `t.Fatalf`.
- Gom nhiều case vào một bảng và chạy từng case bằng `t.Run`: thêm case chỉ một dòng, và khi fail thì biết ngay case nào.
- Biến thời gian thành đầu vào và chờ tín hiệu thay vì chờ đồng hồ, để test nhanh và không flaky.
- Tách test chậm bằng `-short`, build tag hoặc biến môi trường, và chạy `-shuffle=on` cùng `-race` thường xuyên.
- Dùng `httptest` để test handler trong bộ nhớ, và đọc `-cover` như bản đồ code chưa được test, không phải điểm số.
