### Why fast benchmarks still ship slow code

In [Go issue #14813](https://github.com/golang/go/issues/14813), a benchmark comparing two bit-counting (`popcnt`) implementations looked blazing fast: Go's Static Single Assignment (SSA) compiler inlined the pure helper, saw that nobody used its return value, and deleted the entire calculation. The loop still ran `1,000,000,000` times and printed `PASS`, except it was timing an empty loop counter. Years later, that same class of `b.N` compiler and timer mistakes pushed the Go team to design `testing.B.Loop` for Go 1.24.

Functional tests give you a clear pass or fail because `2 + 2` returns `4` even if your laptop fan is spinning or Slack is syncing. Performance numbers have no such shield. Averages smear away p99 pauses, container OOM kills watch OS pages that Go's heap counters miss, CPU thermal boost swings single benchmark runs by double digits, and a microbenchmark of one isolated function sees zero TCP sockets or mutex contention.

<Callout type="note" title="TL;DR">
Instrument services with **RED** (Rate, Errors, Duration histograms) and resources with **USE** (Utilization, Saturation, Errors), compare container `working_set` RAM against Go `runtime/metrics` heap counters, guard microbenchmarks against setup leaks, dead-code elimination, and cache warming with `for b.Loop()` (Go 1.24+), demand `p < 0.05` across `-count=10` runs in `benchstat`, and validate service-level tail latency with macrobenchmarks.
</Callout>

## Efficiency signals: RED, USE and histograms

Before touching a benchmark file, you need to know what is slow in the running service. Watching a server by printing a debug log line on every HTTP call often creates the very bottleneck you are hunting, because formatting and shipping strings steals CPU and heap allocations on every request.

Think of observability signals like instruments in a car compared with a dashcam. A speedometer and fuel gauge (**metrics**) update cheap numbers continuously; a trip timeline (**tracing**) records one journey across turns; **logging** keeps rare incident snapshots; and **continuous profiling** (covered in [Go profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/)) inspects which engine part is burning fuel line by line.

<Figure src={promArch} alt="Official Prometheus architecture showing target discovery, metrics pulling, TSDB storage, PromQL querying, and Grafana/Alertmanager outputs" caption="Prometheus scrapes pre-aggregated atomic counters from a Go process over HTTP instead of forcing the service to ship raw per-request logs." sourceTitle="Prometheus Documentation — Overview" sourceUrl="https://prometheus.io/docs/introduction/overview/" />

For Go services, two small checklists keep dashboards consistent without drowning in metrics:

- **RED** (Tom Wilkie's method for request-driven APIs): track **R**ate (requests/s), **E**rrors (failed requests/s), and **D**uration (request latency distribution). In the [Todo HTTP service](/blog/go-http-service-net-http-json-middleware/), you wrap `statusRecorder` inside a middleware right next to `logging` so every route records its status code and elapsed seconds.
- **USE** (Brendan Gregg's method for hardware and runtime pools): for CPU cores, memory, disks, or connection pools, watch **U**tilization (% busy), **S**aturation (work queued waiting for a turn), and **E**rrors (dropped packets, OOM kills).

<GoP17RedVsUse />

Notice why **Duration** must be a **Histogram**, never a plain average or a Prometheus **Summary**. Suppose 99 `GET /todos` calls finish in `5 ms` and 1 call stalls for `705 ms` waiting on a lock: the arithmetic mean reports a calm `12 ms`, hiding the outlier completely. Worse, a `Summary` computes percentiles locally inside each pod—averaging `p99 = 12 ms` from a busy pod and `p99 = 820 ms` from an idle pod gives nonsense (`416 ms`), whereas a classic **Histogram** (`_bucket{le="..."}`)—or modern Prometheus native histograms—counts bucket hits per pod so PromQL can sum them cleanly across your cluster:

```go
// Add RED middleware alongside statusRecorder from the Todo service (Post 10).
httpDur := prometheus.NewHistogramVec(prometheus.HistogramOpts{
	Name:    "http_request_duration_seconds",
	Help:    "Request duration per route pattern and status class.",
	Buckets: []float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.5, 2.0},
}, []string{"route", "code"})

func metricsMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
		start := time.Now()
		next.ServeHTTP(rec, r)
		// Normalize route ("GET /todos/{id}"), never raw "/todos/98123", to prevent cardinality explosion.
		httpDur.WithLabelValues(r.Pattern, strconv.Itoa(rec.status)).Observe(time.Since(start).Seconds())
	})
}
```

Watch the label trap inside `metricsMiddleware` above: never stick raw IDs, user emails, or unconstrained error strings into metric labels. Every unique label combination creates a separate time series in both your Go process memory and Prometheus TSDB—turning one route metric into millions of series if traffic hits random `/todos/991823` URLs. Use `r.Pattern` (added on Go 1.22+ `ServeMux`) and keep raw request IDs in logs or sampled traces.

| Metric type | What it stores | Safe across pods? | Where it fits in Go |
| :--- | :--- | :--- | :--- |
| **`Counter`** | Monotonically rising total (`+1`) | Wrap with `rate()` | Request counts, 5xx errors, allocated bytes total |
| **`Gauge`** | Current point-in-time level (`+1 / -1`) | Read `max` or `avg` | Active goroutines, queue depth, `HeapInuse` |
| **`Histogram`** | Cumulative `le` bucket counts (or native sparse buckets) | Yes, `sum by (le)` | Cluster-wide `histogram_quantile(0.99, ...)` |
| **`Summary`** | Client-side sliding quantiles | Never average across pods | Single-process local stats only |

<Concepts>

- **RED vs. USE**: RED measures what callers experience on an API boundary (**R**ate, **E**rrors, **D**uration); USE measures pressure inside a resource (**U**tilization, **S**aturation, **E**rrors).
- **Tail latency (`p90` / `p99`)**: the latency ceiling below which 90% or 99% of requests complete, exposing slow outliers that averages erase.
- **Prometheus Histogram (`le` buckets)**: counters tracking how many observations fell at or below each threshold (`le="0.01"`), allowing valid cluster-wide quantiles via PromQL.
- **Label cardinality**: the number of distinct time series produced by label combinations; unbounded IDs as labels can OOM-kill exporters and Prometheus.

</Concepts>

## Container vs runtime CPU and memory

Grafana panels routinely fool Go engineers in two places: cumulative CPU counters and the gap between what Go thinks its heap uses versus what the Linux kernel counts before killing the pod.

First, Linux cgroups and Go runtime exporters publish **cumulative CPU seconds** consumed since process start (`process_cpu_seconds_total` and `container_cpu_usage_seconds_total`), never instant CPU percentages. Wrapping them in `rate(container_cpu_usage_seconds_total[1m])` gives the average CPU cores used per second—and pairing that with `rate(container_cpu_cfs_throttled_seconds_total[1m])` catches Linux CFS quota throttling even when 1-minute average CPU looks low (see [Go in production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/#the-kubernetes-cfs-throttling-trap-100) for how cgroup 100 ms quota windows and container-aware `GOMAXPROCS` interact).

Second, Kubernetes OOM-kills pods based on `container_memory_working_set_bytes` (cAdvisor's estimate of active anonymous RSS plus non-inactive OS page cache), not Go's `HeapAlloc`. Think of it like your monthly apartment bill versus the furniture inside one bedroom: Go only weighs the furniture (`HeapAlloc`), while Kubernetes adds the empty crates waiting for pickup (`HeapInuse` / un-released spans), hallway clutter (goroutine stacks, Cgo/`mmap`), and kitchen deliveries cached by the building (OS page cache).

<GoP17MemoryLayers />

Inside Go itself, prefer the `runtime/metrics` package (introduced in Go 1.16) over `runtime.ReadMemStats` in hot diagnostic paths: `runtime.ReadMemStats` triggers a brief Stop-The-World pause to snapshot every stat at once, whereas `runtime/metrics` reads individual runtime counters cheaply. Here is a real Go 1.27.1 comparison after allocating `20 MiB` of live byte slices and running one `runtime.GC()`:

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/metrics"
)

var hold [][]byte

func main() {
	for range 20 {
		hold = append(hold, make([]byte, 1<<20)) // allocate 20 MiB live
	}
	runtime.GC()

	samples := []metrics.Sample{
		{Name: "/gc/heap/allocs:bytes"},
		{Name: "/memory/classes/heap/objects:bytes"},
		{Name: "/memory/classes/heap/free:bytes"},
		{Name: "/memory/classes/heap/released:bytes"},
	}
	metrics.Read(samples)

	var m runtime.MemStats
	runtime.ReadMemStats(&m)

	fmt.Printf("runtime/metrics allocs=%d MiB objects=%d MiB free=%d MiB released=%d MiB\n",
		samples[0].Value.Uint64()>>20,
		samples[1].Value.Uint64()>>20,
		samples[2].Value.Uint64()>>20,
		samples[3].Value.Uint64()>>20,
	)
	fmt.Printf("MemStats        HeapAlloc=%d MiB HeapInuse=%d MiB HeapSys=%d MiB HeapReleased=%d MiB\n",
		m.HeapAlloc>>20, m.HeapInuse>>20, m.HeapSys>>20, m.HeapReleased>>20,
	)
}
```

Notice how checking both layers saves hours during an outage. If `container_memory_working_set_bytes` climbs past `900 MiB` while `go_memstats_heap_alloc_bytes` reads `40 MiB`, hunting through your Go structs wastes time: the RAM sits off-heap in leaked goroutine stacks, Cgo buffers, explicit `mmap` files, or OS file page cache. Conversely, if `HeapInuse` is far larger than `HeapAlloc`, objects fragmented across many 8 KiB spans are pinning memory until those spans empty and the background scavenger calls `madvise` (covered in [Go hardware and GC](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/), alongside sizing `GOMEMLIMIT` below the container ceiling).

| Memory metric | Source | What it measures | Production signal |
| :--- | :--- | :--- | :--- |
| **`HeapAlloc`** / `heap/objects` | `MemStats` / `runtime/metrics` | Live reachable heap objects | Rising floor across GC cycles means a live Go leak |
| **`HeapInuse`** | `runtime.MemStats` | Active 8 KiB runtime spans | Much higher than `HeapAlloc` exposes span fragmentation |
| **`HeapSys - HeapReleased`** | `runtime.MemStats` | Virtual heap spans currently backed by RAM | Shrinks lazily as the background scavenger runs |
| **`container_memory_working_set_bytes`** | Linux cgroup (cAdvisor) | Active RSS + non-inactive OS page cache | Reaching pod limit triggers kernel OOMKill |

Keep these three PromQL queries ready when triaging a pod under memory or latency pressure:

```text
# 1. Catch CPU throttling over 100 ms cgroup windows even when average CPU looks idle
rate(container_cpu_cfs_throttled_seconds_total{pod=~"todo-api-.*"}[1m])

# 2. Compute cluster-wide p99 duration from Histogram buckets (never average Summaries)
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# 3. Spot span fragmentation inside Go's heap vs off-heap growth in container RSS
go_memstats_heap_inuse_bytes - go_memstats_heap_alloc_bytes
```

<Concepts>

- **`rate()` on cumulative counters**: converts monotonically increasing totals (`cpu_seconds_total`) into per-second rates so restarts and scrape intervals stay accurate.
- **`runtime/metrics`**: Go's modern, non-STW telemetry API (`metrics.Read`) exposing granular heap, GC, and scheduler metrics without pausing all goroutines.
- **Working set vs. `HeapInuse`**: `working_set` is the container-level RAM cAdvisor tracks for OOM eviction (including stacks, Cgo, and file cache), whereas `HeapInuse` measures only Go's active 8 KiB heap spans.

</Concepts>

## Microbenchmarks that do not lie

Unit tests check correctness on edge cases; **microbenchmarks** (`func BenchmarkX(b *testing.B)`) measure how fast and how much heap memory a single isolated function spends on typical inputs. Measuring nanoseconds on a live laptop is like timing a mechanical watch escapement on a moving ship: background OS tasks, CPU frequency scaling, warm L1 caches, and compiler optimizations all tilt the reading unless you isolate them.

<Figure src={chronometerImg} alt="Brass marine chronometer suspended inside its gimbaled wooden box" caption="Marine chronometers rode inside gimbaled rings to stay level against rolling seas—microbenchmarks need the same discipline around timers, sinks, and machine stability." sourceTitle="Wikimedia Commons: Marine chronometer, Joseph Sewill (Liverpool, c. 1870)" sourceUrl="https://commons.wikimedia.org/wiki/File:Marine_chronometer,_Joseph_Sewill,_Liverpool_(c._1870).JPG" />

Every Go microbenchmark lives in a `*_test.go` file, takes `*testing.B`, and runs via `go test`. Always pass `-run '^$'` so functional unit tests do not run and pollute output, and pass `-benchmem` (or call `b.ReportAllocs()`) so heap bytes (`B/op`) and allocation counts (`allocs/op`) print beside latency (`ns/op`). Just as importantly, check errors inside your benchmark (`if err != nil { b.Fatal(err) }`): benchmarking an error path that returns early in 20 ns because a fixture path was misspelled is a fast way to celebrate a fake speedup.

Even with `-benchmem` on and errors checked, four classic mistakes (`#89` in *100 Go Mistakes*) silently turn `go test -bench` into fiction.

<GoP17BenchTraps />

### 1. Letting setup leak into the timer

Suppose you want to measure how fast a single lookup in a 100,000-entry `Todo` index runs. Building that index inside the benchmark without resetting the clock mixes 3 milliseconds of map allocation into early calibration iterations:

```go
var LookupSink string

func BenchmarkLookupNoReset(b *testing.B) {
	b.ReportAllocs()
	idx := buildTodoIndex(100_000) // counted in timer and allocs!
	var v string
	for i := 0; i < b.N; i++ {
		v = idx[i%100_000]
	}
	LookupSink = v
}

func BenchmarkLookupResetTimer(b *testing.B) {
	b.ReportAllocs()
	idx := buildTodoIndex(100_000)
	b.ResetTimer() // clears setup elapsed time and alloc counters
	var v string
	for i := 0; i < b.N; i++ {
		v = idx[i%100_000]
	}
	LookupSink = v
}

func BenchmarkLookupBLoop(b *testing.B) {
	b.ReportAllocs()
	idx := buildTodoIndex(100_000)
	i := 0
	for b.Loop() { // Go 1.24+: automatically resets timer on iteration 0
		_ = idx[i%100_000]
		i++
	}
}
```

Look at Run 1 of `BenchmarkLookupNoReset-8`: Go first calls the benchmark with `b.N=1` to guess how many iterations fit in `-benchtime`. Because `buildTodoIndex` ran inside the active timer, Go thought one lookup took milliseconds, picked `b.N=874`, and reported `25,382 ns/op` and `6,736 B/op` instead of `12 ns/op` and `0 B/op`.

What if setup must happen on *every* iteration? You can wrap per-iteration setup with `b.StopTimer()` and `b.StartTimer()`, as long as the measured work takes far longer than the ~30–50 ns timer toggle overhead—otherwise wall-clock runtime stretches well past `-benchtime` while timer overhead swamps fast functions.

### 2. Compiler dead-code elimination vs `for b.Loop()`

Come back to Go issue #14813's `popcnt` bit-counter. Under `for i := 0; i < b.N; i++`, calling a pure inlineable function without using its result lets Go's SSA compiler prove the loop body has zero observable side effects and strip it down to an empty loop counter:

```go
var GlobalSink uint64

func BenchmarkPopcntIgnored(b *testing.B) {
	for i := 0; i < b.N; i++ {
		popcnt(uint64(i)) // result unused -> compiler deletes call
	}
}

func BenchmarkPopcntSink(b *testing.B) {
	var acc uint64
	for i := 0; i < b.N; i++ {
		acc += popcnt(uint64(i))
	}
	GlobalSink = acc // one package-level write after the loop
}

func BenchmarkPopcntBLoop(b *testing.B) {
	x := uint64(0xdeadbeefcafebabe)
	for b.Loop() { // Go 1.24+: compiler keeps arguments and results alive
		popcnt(x)
		x++
	}
}
```

Inspecting ARM64 assembly (`go test -c -gcflags='-S'`) confirms what happened: `BenchmarkPopcntIgnored` compiled down to `ADD $1; CMP; BLT`—zero `LSR`/`AND`/`MUL` instructions—and hit Go's `1,000,000,000` maximum iteration cap, a red flag that a benchmark is measuring empty loop overhead. Meanwhile, `BenchmarkPopcntSink` kept the work alive via one post-loop write to `GlobalSink` (never write to a package global on every iteration, which adds memory store cost inside the hot loop).

Go 1.24's **`for b.Loop()`** replaces both `b.ResetTimer()` and manual sink boilerplate for almost all benchmarks. Look straight into Go 1.27.1's `src/testing/benchmark.go` to see its contract:

<GitHubCode repo="golang/go" path="src/testing/benchmark.go" lines="L475-L487" url="https://github.com/golang/go/blob/go1.27.1/src/testing/benchmark.go#L475-L487" caption="Inside Go 1.27.1's testing package: b.Loop() resets the timer on entry, stops it at exit, and wraps body variables in runtime.KeepAlive intrinsics.">
```go
// Loop resets the benchmark timer the first time it is called in a benchmark,
// so any setup performed prior to starting the benchmark loop does not count
// toward the benchmark measurement. Likewise, when it returns false, it stops
// the timer so cleanup code is not measured.
//
// Within the body of a "for b.Loop() { ... }" loop, arguments to and
// results from function calls and assigned variables within the loop are kept
// alive, preventing the compiler from fully optimizing away the loop body.
// Currently, this is implemented as a compiler transformation that wraps such
// variables with a runtime.KeepAlive intrinsic call. This applies only to
// statements syntactically between the curly braces of the loop, and the loop
// condition must be written exactly as "b.Loop()".
```
</GitHubCode>

Two details in Go 1.27.1 are worth noticing in the numbers above. First, `b.Loop()` adds ~1.4 ns of stack spill and loop-check overhead compared with `GlobalSink` on sub-nanosecond functions, which vanishes once a benchmarked operation takes tens of nanoseconds or more. Second, `for b.Loop()` blocks dead-code elimination of the call's *result*, yet if you pass a local constant right above the loop (`x := 0xdeadbeef; for b.Loop() { popcnt(x) }`), Go's SSA pass can still constant-fold `popcnt(x)` to `46` before `runtime.KeepAlive` runs; vary the input (`x++`) or read it from a package variable when testing pure arithmetic.

### 4. Machine noise, run order, and input scaling

Power-saving modes, CPU thermal throttling, background browser tabs, and noisy cloud neighbors (or shared CI runners) routinely move nanosecond benchmarks by 10–30%, and simply swapping the order of two benchmarks in a file can flip which one looks faster. Before running serious numbers: plug the laptop into wall power, close heavy apps, use sub-benchmarks (`b.Run`) across realistic input sizes to check how scaling behaves ([Go efficiency workflow](/blog/go-efficiency-workflow-raer-tfbo-hardware-memory/) contrasts Big-O growth vs. constant factors), lengthen noisy runs with `-benchtime=2s` or `-cpu=4`, and repeat every run with `-count=10`.

## Statistical proof with benchstat

A single `-count=1` benchmark number tells you almost nothing, because a background OS task or CPU clock boost can shift any single sample by 15%. Collecting `-count=10` samples into text files (`old.txt` and `new.txt`) and feeding them to Go's **`benchstat`** CLI turns raw runs into statistical evidence.

Under the hood, `benchstat` computes each benchmark's **median** and **95% confidence interval** (`± X%`) rather than assuming a clean bell curve. When comparing two files, it runs a two-sample **Mann-Whitney U test** (non-parametric rank comparison) to compute a `p-value`—the probability that the gap between `old` and `new` appeared purely by chance. If `p >= 0.05` (the default `-alpha`), `benchstat` refuses to declare a delta and prints `~` (noisy / inconclusive). When a suite contains multiple sub-benchmarks, the bottom **`geomean`** row summarizes proportional change across the set so one slow case does not skew an arithmetic average.

## Macrobenchmarks: testing the whole service

Even a flawless `benchstat` win on one function can disappoint in production. A microbenchmark runs inside `go test` on one goroutine with zero network sockets, no concurrent mutex lock contention, and no sustained heap pressure triggering GC cycles.

<YouTube id="wv97cPiqYSU" title="P99 CONF 2023 | The Art of Macro Benchmarking by Bartłomiej Płotka" start={382} end={450} caption="From 6:22 to 7:30, Bartłomiej Płotka contrasts microbenchmarks, macrobenchmarks, and production benchmarking—and why end-to-end realism exposes bottlenecks unit benchmarks miss." sourceTitle="ScyllaDB P99 CONF — Bartłomiej Płotka" />

**Macrobenchmarks** treat the entire compiled service binary (ideally inside a container with realistic cgroup CPU/RAM limits and dependencies, the model behind `efficientgo/e2e`) as a closed system and drive HTTP or gRPC traffic from outside:

- **`k6` (Grafana Labs)**: Go-powered load generator scripted in JavaScript, ideal for multi-step flows (`POST /todos` -> `GET /todos` -> `GET /todos/{id}`), warmup stages, status assertions, and CI p99 thresholds.
- **`vegeta`**: Go CLI and library focused on constant arrival-rate (`RPS`) HTTP attacks so server stalls cannot slow down the client's sending pace (avoiding *coordinated omission* in closed-loop VU tests).
- **`ghz`**: purpose-built Go CLI for gRPC load testing with protobuf reflection and gRPC status histograms.

<GoP17MicroVsMacro />

To prove how much a macrobenchmark reveals on code you already know, let's fire a 4,000-request mixed workload (`10% POST /todos`, `20% GET /todos`, `70% GET /todos/{id}`) from 8 concurrent HTTP workers against Post 10's `Todo` mux on Go 1.27.1 after a 200-request warmup:

```go
// Snippet of the loopback load driver against Post 10's Todo routes (full run: 8 workers x 500 reqs)
for i := range perWorker {
	t0 := time.Now()

	case 0:

	_, _ = io.Copy(io.Discard, resp.Body)
	resp.Body.Close()

		badStatus.Add(1)
	}
	lats = append(lats, time.Since(t0))
}
```

When running `k6` or `vegeta` against containers in staging, enforce five habits so your macrobenchmark stays honest:

```javascript
// todo-load.js — minimal k6 script with warmup, realistic read/write mix, and status checks
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',
      rate: 200, timeUnit: '1s', duration: '3m', preAllocatedVUs: 20,
    },
  },
  thresholds: { http_req_duration: ['p(99)<50'], http_req_failed: ['rate<0.01'] },
};

export default function () {
  const res = http.get('http://todo-api:8080/todos');
  check(res, { 'status 200': (r) => r.status === 200, 'json array': (r) => r.body.startsWith('[') });
}
```

1. **Warm up first, measure second**: exclude connection handshakes, initial cache fills, and span growth before recording percentiles.
2. **Use realistic traffic mix and arrival rate**: open-loop (`constant-arrival-rate` in `k6`, or `vegeta -rate`) keeps firing at target RPS even when the server slows down, exposing real queue buildup.
3. **Assert status codes and payload shape**: `check()` ensures an endpoint returning `500` in `0.2 ms` never looks like a throughput record.
4. **Watch the load generator itself**: check client CPU, file descriptors (`ulimit -n`), and ephemeral ports so you do not benchmark a starved client.
5. **Run long enough for GC and Prometheus scrapes**: run multi-minute tests rather than milliseconds so `15s` scrapes and steady-state GC cycles appear in your RED/USE dashboards.

Once a microbenchmark or macrobenchmark proves *which* path violates your budget, the next step is finding the exact lines burning CPU or heap—covered next in [Go profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/).

<Concepts>

- **Closed-loop vs. open-loop load**: closed-loop VUs wait for each reply before sending the next (hiding queueing stalls); open-loop constant arrival rate (`vegeta`, `k6` `constant-arrival-rate`) keeps sending at target RPS even during stalls.
- **Warmup window**: an unmeasured ramp period letting TCP pools, OS caches, and Go heap spans settle before collecting percentiles.
- **Coordinated omission**: load-test bias where slow server replies cause the test client to pause sending, under-reporting tail latency.

</Concepts>

## Key takeaways

- **Measure services with RED and resources with USE**: capture HTTP `Rate`, `Errors`, and `Duration` with Prometheus Histograms (`sum by (le)`), never raw averages or cross-pod Summaries, and keep dynamic IDs out of label values.
- **Watch both OS working set and Go runtime heap**: apply `rate()` to cumulative CPU counters and compare `container_memory_working_set_bytes` against `runtime/metrics` (`HeapAlloc`, `HeapInuse`, `HeapReleased`) to tell Go leaks and span fragmentation apart from off-heap growth.
- **Guard `testing.B` with `for b.Loop()` (Go 1.24+)**: prefer `for b.Loop()` to auto-reset setup timers and block dead-code elimination, assert non-nil errors with `b.Fatal`, vary constant inputs, and beware warm-cache observer effects.
- **Require `benchstat` `p < 0.05` across `-count=10` runs**: ignore single `-count=1` wins and anything flagged `~`, inspect all three tables (`sec/op`, `B/op`, `allocs/op`), and read `geomean` across input sizes.
- **Close the loop with macrobenchmarks**: drive realistic, warmed-up traffic with status checks (`k6`, `vegeta`, `ghz`) to expose mutex contention, GC cycles, TCP churn, and cgroup limits invisible to microbenchmarks.

### Vì sao benchmark nhìn nhanh mà lên server vẫn chậm?

Trong [Go issue #14813](https://github.com/golang/go/issues/14813), một bài benchmark so sánh hai hàm đếm bit (`popcnt`) cho ra tốc độ nhanh đến mức khó tin: trình biên dịch SSA của Go đã nội tuyến (inline) hàm thuần túy đó, thấy chẳng ai dùng giá trị trả về, và cắt phăng toàn bộ phép tính. ## Tín hiệu đo lường: RED, USE và histogram

Trước khi viết bất kỳ file benchmark nào, mình cần nhìn thấy chỗ chậm thật trên service đang chạy. Kiểu đo hay gặp của người mới là nhét `log.Debug` ở mọi bước xử lý request, rồi chính tiền ép chuỗi JSON và đẩy log đi lại ngốn sạch CPU của service.

Hãy hình dung bốn tín hiệu quan sát hệ thống (observability signals) như đồng hồ táp-lô trên xe và camera hành trình. Đồng hồ tốc độ hay mức xăng (**metrics**) chỉ là mấy con số đếm cực nhẹ cập nhật liên tục; lịch sử một chuyến đi (**tracing**) ghi lại dòng thời gian qua từng ngã rẽ; **logging** giữ lại vài sự cố hiếm; còn **continuous profiling** (xem kỹ ở [Profiling trong Go](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/)) soi từng chi tiết máy đang đốt xăng ở dòng code nào.

- **RED** (phương pháp của Tom Wilkie cho dịch vụ theo request): đo **R**ate (tần suất request/giây), **E**rrors (lỗi/giây) và **D**uration (phân bố độ trễ). Với [Todo HTTP service](/blog/go-http-service-net-http-json-middleware/), mình bọc `statusRecorder` trong một middleware ngay cạnh `logging` để ghi nhận mã HTTP và thời gian xử lý của mọi route.
- **USE** (phương pháp của Brendan Gregg cho tài nguyên phần cứng/pool): với CPU, RAM, ổ đĩa hay connection pool, soi **U**tilization (% thời gian bận), **S**aturation (hàng đợi đang nghẽn) và **E**rrors (rớt gói, OOMKill).

<GoP17RedVsUse />

Chỗ dễ sập bẫy nhất là cách đo **Duration**: luôn phải dùng **Histogram**, tuyệt đối đừng dùng trung bình cộng hay Prometheus **Summary**. Giả sử 99 request `GET /todos` chạy hết `5 ms` và 1 request kẹt khóa mất `705 ms`: trung bình cộng vẫn báo đẹp `12 ms`, che sạch cú khựng của khách. Tệ hơn nữa, `Summary` tự tính phân vị cục bộ trên từng pod — đem `p99 = 12 ms` ở pod bận cộng chia trung bình với `p99 = 820 ms` ở pod rảnh ra `416 ms` là sai bét. Ngược lại, **Histogram** (`_bucket{le="..."}` — hoặc native histogram mới của Prometheus) đếm số request lọt vào từng xô theo từng pod nên PromQL cộng gộp chuẩn trên cả cụm:

```go
// Gắn middleware RED cùng statusRecorder từ Todo service (Bài 10).
httpDur := prometheus.NewHistogramVec(prometheus.HistogramOpts{
	Name:    "http_request_duration_seconds",
	Help:    "Đo độ trễ theo pattern route và mã HTTP.",
	Buckets: []float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.5, 2.0},
}, []string{"route", "code"})

func metricsMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
		start := time.Now()
		next.ServeHTTP(rec, r)
		// Dùng r.Pattern ("GET /todos/{id}"), cấm gắn path thô "/todos/98123" kẻo nổ cardinality.
		httpDur.WithLabelValues(r.Pattern, strconv.Itoa(rec.status)).Observe(time.Since(start).Seconds())
	})
}
```

Để ý dòng `r.Pattern` ở trên: tuyệt đối đừng nhét ID ngẫu nhiên, email hay chuỗi lỗi thô làm nhãn (label) cho metric. Mỗi giá trị label mới đẻ ra một chuỗi time-series mới nằm lì trong RAM của cả app Go lẫn Prometheus TSDB — đủ để kéo sập exporter nếu traffic gọi hàng triệu `/todos/991823` khác nhau. Hãy gom theo `r.Pattern` (có từ `ServeMux` Go 1.22+) và để ID chi tiết cho log hoặc trace đã lấy mẫu.

| Kiểu metric | Bản chất lưu trữ | Cộng gộp nhiều pod? | Dùng chuẩn ở đâu |
| :--- | :--- | :--- | :--- |
| **`Counter`** | Chỉ tăng cộng dồn (`+1`) | Luôn bọc `rate()` | Số request, số lỗi 5xx, tổng byte cấp phát |
| **`Gauge`** | Giá trị tức thời (`+1 / -1`) | Đọc `max` hoặc `avg` | Số goroutine đang chạy, độ dài queue, `HeapInuse` |
| **`Histogram`** | Các xô đếm `le` (hoặc native bucket) | Có, `sum by (le)` | Tính `histogram_quantile(0.99, ...)` toàn cụm |
| **`Summary`** | Client tự tính phân vị sẵn | Cấm lấy trung bình giữa pod | Chỉ dùng nội bộ một máy lẻ |

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **RED vs. USE**: RED soi trải nghiệm người gọi ngay ở cửa API (**R**ate, **E**rrors, **D**uration); USE soi độ căng thẳng tài nguyên bên trong (**U**tilization, **S**aturation, **E**rrors).
- **Tail latency (độ trễ đuôi `p90` / `p99`)**: ngưỡng thời gian mà 90% hoặc 99% request hoàn thành dưới mức đó, phơi bày những cú chậm hiếm gặp bị số trung bình che khuất.
- **Prometheus Histogram (xô `le`)**: bộ đếm số lần đo nhỏ hơn hoặc bằng từng mốc (`le="0.01"`), cho phép cộng dồn chuẩn xác qua nhiều pod trước khi tính phân vị.
- **Label cardinality**: số chuỗi time-series phân biệt sinh ra từ các tổ hợp label; gắn ID không giới hạn dễ làm OOMKill cả exporter lẫn Prometheus.

</Concepts>

## Đọc đúng CPU và RAM: container và Go runtime

Mở Grafana lên soi sự cố, anh em hay vấp ngay hai chỗ: bộ đếm CPU cộng dồn và độ vênh giữa RAM mà Go báo với RAM mà Linux đếm để OOMKill pod.

Thứ nhất, cả cgroup Linux lẫn Go runtime đều xuất **tổng số giây CPU cộng dồn** từ lúc khởi động (`process_cpu_seconds_total` và `container_cpu_usage_seconds_total`), chứ không phải % CPU tức thời. Phải bọc `rate(container_cpu_usage_seconds_total[1m])` mới ra số nhân CPU trung bình đang ăn mỗi giây — và phải nhìn kèm `rate(container_cpu_cfs_throttled_seconds_total[1m])` để bắt pod bị Linux CFS bóp nhịp 100 ms dù tải trung bình nhìn rất nhàn (chi tiết về cơ chế bóp quota và `GOMAXPROCS` theo cgroup mình đã tách riêng ở [Go trong production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/#c%C3%A1i-b%E1%BA%ABy-cfs-throttling-tr%C3%AAn-kubernetes-100)).

Thứ hai, Kubernetes giết pod (OOMKill) dựa trên `container_memory_working_set_bytes` (ước lượng RAM vật lý RSS cộng page cache còn dùng của cAdvisor), chứ không dựa vào `HeapAlloc` của Go. Hãy ví nó như tiền hóa đơn chung cư so với cân nặng đồ đạc trong một phòng ngủ: Go chỉ cân số đồ đạc (`HeapAlloc`), còn Kubernetes tính luôn đống thùng rỗng chưa kịp dọn (`HeapInuse` / span chờ trả OS), đồ ngoài hành lang (stack goroutine, Cgo/`mmap`) và hàng giao tạm ở sảnh (OS page cache).

<GoP17MemoryLayers />

Bên trong Go, hãy ưu tiên gói `runtime/metrics` (có từ Go 1.16) thay vì gọi `runtime.ReadMemStats` ở đường nóng: `ReadMemStats` buộc dừng mọi goroutine (STW) một nhịp ngắn để chụp ảnh toàn bộ thống kê, còn `runtime/metrics` đọc từng chỉ số rất nhẹ. Đây là kết quả chạy thật trên Go 1.27.1 sau khi cấp phát `20 MiB` byte slice sống và gọi một lượt `runtime.GC()`:

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/metrics"
)

var hold [][]byte

func main() {
	for range 20 {
		hold = append(hold, make([]byte, 1<<20)) // giữ 20 MiB đang sống
	}
	runtime.GC()

	samples := []metrics.Sample{
		{Name: "/gc/heap/allocs:bytes"},
		{Name: "/memory/classes/heap/objects:bytes"},
		{Name: "/memory/classes/heap/free:bytes"},
		{Name: "/memory/classes/heap/released:bytes"},
	}
	metrics.Read(samples)

	var m runtime.MemStats
	runtime.ReadMemStats(&m)

	fmt.Printf("runtime/metrics allocs=%d MiB objects=%d MiB free=%d MiB released=%d MiB\n",
		samples[0].Value.Uint64()>>20,
		samples[1].Value.Uint64()>>20,
		samples[2].Value.Uint64()>>20,
		samples[3].Value.Uint64()>>20,
	)
	fmt.Printf("MemStats        HeapAlloc=%d MiB HeapInuse=%d MiB HeapSys=%d MiB HeapReleased=%d MiB\n",
		m.HeapAlloc>>20, m.HeapInuse>>20, m.HeapSys>>20, m.HeapReleased>>20,
	)
}
```

Nếu `container_memory_working_set_bytes` vọt qua `900 MiB` trong khi `go_memstats_heap_alloc_bytes` chỉ quanh quẩn `40 MiB`, đừng mất công soi struct Go — thủ phạm đang nằm ngoài heap ở stack các goroutine bị rò, buffer Cgo, `mmap` hoặc OS page cache. Ngược lại, khi `HeapInuse` lớn hơn hẳn `HeapAlloc`, các object nằm rải rác đang ghim nhiều span 8 KiB khiến RAM chưa giải phóng được tới khi scavenger gọi `madvise` (xem cơ chế trả RAM và đặt ngưỡng `GOMEMLIMIT` ở [Phần cứng và GC trong Go](/blog/go-hardware-cpu-caches-virtual-memory-gc-allocator/)).

| Chỉ số RAM | Nguồn lấy | Đo cái gì thật sự | Dấu hiệu bệnh production |
| :--- | :--- | :--- | :--- |
| **`HeapAlloc`** / `heap/objects` | `MemStats` / `runtime/metrics` | Object Go đang còn sống | Đáy sau mỗi vòng GC tăng dần là rò heap thật |
| **`HeapInuse`** | `runtime.MemStats` | Các span 8 KiB đang mở | Cao hơn nhiều so với `HeapAlloc` là phân mảnh span |
| **`HeapSys - HeapReleased`** | `runtime.MemStats` | Span ảo còn giữ trang RAM vật lý | Co lại từ từ khi scavenger chạy nền |
| **`container_memory_working_set_bytes`** | Linux cgroup (cAdvisor) | RSS đang dùng + OS page cache nóng | Chạm limit pod là bị kernel OOMKill ngay |

Thủ sẵn ba câu truy vấn PromQL này khi điều tra một pod đang phình RAM hoặc giật độ trễ:

```text
# 1. Bắt pod bị bóp CFS theo chu kỳ 100 ms dù CPU trung bình trông còn rảnh
rate(container_cpu_cfs_throttled_seconds_total{pod=~"todo-api-.*"}[1m])

# 2. Tính p99 toàn cụm từ Histogram (tuyệt đối không cộng trung bình Summary)
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# 3. Soi khoảng trống phân mảnh span trong Go heap vs phần ngoài heap trên container RSS
go_memstats_heap_inuse_bytes - go_memstats_heap_alloc_bytes
```

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **`rate()` trên bộ đếm cộng dồn**: biến tổng giây CPU chỉ tăng đều (`cpu_seconds_total`) thành tốc độ ăn nhân CPU mỗi giây, không bị hỏng khi pod restart.
- **`runtime/metrics`**: API đo lường hiện đại của Go (`metrics.Read`), đọc số liệu heap, GC và scheduler mà không phải dừng toàn bộ goroutine như `ReadMemStats`.
- **`working_set` vs. `HeapInuse`**: `working_set` là phần RAM cấp container cAdvisor tính để OOMKill (gồm cả stack, Cgo, file cache), còn `HeapInuse` chỉ đếm các span 8 KiB của Go heap.

</Concepts>

## Viết microbenchmark sao cho không tự lừa mình

Unit test trả lời hàm có chạy đúng với các ca biên hay không; **microbenchmark** (`func BenchmarkX(b *testing.B)`) đo xem một hàm đơn lẻ mất bao nhiêu nano-giây và cấp phát bao nhiêu byte trên dữ liệu tiêu biểu. Đo tới từng nano-giây trên laptop cũng giống canh nhịp đồng hồ cơ hàng hải trên boong tàu đang lắc: tiến trình nền, hạ xung nhiệt, L1 cache ấm sẵn và các pha tối ưu của trình biên dịch đều làm kim đo lệch nếu bạn không giữ thăng bằng.

### 1. Để phần chuẩn bị dữ liệu lọt vào đồng hồ đo

Giả sử mình muốn đo tốc độ tra cứu 1 khóa trong bảng chỉ mục 100.000 mục `Todo`. Nếu dựng bảng chỉ mục trước vòng lặp mà quên reset đồng hồ, 3 mili-giây dựng map sẽ tràn thẳng vào các lượt đo đầu tiên:

```go
var LookupSink string

	idx := buildTodoIndex(100_000) // bị tính cả vào đồng hồ và B/op!

	for i := 0; i < b.N; i++ {

	}
	LookupSink = v
}

	b.ReportAllocs()
	idx := buildTodoIndex(100_000)

		v = idx[i%100_000]

func BenchmarkLookupBLoop(b *testing.B) {
	b.ReportAllocs()
	idx := buildTodoIndex(100_000)
	i := 0
	for b.Loop() { // Go 1.24+: tự reset timer ngay vòng lặp đầu tiên
		_ = idx[i%100_000]
```

### 2. Trình biên dịch xóa code chết (dead-code elimination) vs `for b.Loop()`

Quay lại ví dụ `popcnt` của issue #14813. Với vòng lặp kiểu cũ `for i := 0; i < b.N; i++`, hễ hàm thuần túy được inline mà kết quả không ai đọc, pha tối ưu SSA kết luận thân vòng lặp không có tác dụng phụ và xóa sạch toàn bộ phép tính:

```go
var GlobalSink uint64

func BenchmarkPopcntIgnored(b *testing.B) {
	for i := 0; i < b.N; i++ {
		popcnt(uint64(i)) // bỏ quên giá trị trả về -> compiler xóa mất
	}
}

func BenchmarkPopcntSink(b *testing.B) {
	var acc uint64
	for i := 0; i < b.N; i++ {
		acc += popcnt(uint64(i))
	}
	GlobalSink = acc // ghi đúng một lần ra biến package sau vòng lặp
}

func BenchmarkPopcntBLoop(b *testing.B) {
	x := uint64(0xdeadbeefcafebabe)
	for b.Loop() { // Go 1.24+: compiler tự giữ tham số và kết quả còn sống
		popcnt(x)
		x++
	}
}
```

Trong khi đó `BenchmarkPopcntSink` giữ được phép tính nhờ dồn vào biến cục bộ rồi mới gán ra `GlobalSink` một lần sau vòng lặp (đừng gán thẳng ra biến toàn cục mỗi vòng lặp kẻo tốn thêm chi phí ghi bộ nhớ vào điểm nóng).

Từ Go 1.24+, **`for b.Loop()`** giải quyết gọn cả hai chuyện `b.ResetTimer()` lẫn bẫy xóa code chết. Nhìn thẳng vào cam kết của nó trong mã nguồn chuẩn Go 1.27.1 (`src/testing/benchmark.go`):

<GitHubCode repo="golang/go" path="src/testing/benchmark.go" lines="L475-L487" url="https://github.com/golang/go/blob/go1.27.1/src/testing/benchmark.go#L475-L487" caption="Bên trong gói testing của Go 1.27.1: b.Loop() tự reset đồng hồ ở đầu, dừng trước cleanup và bọc các biến trong thân vòng lặp bằng intrinsic runtime.KeepAlive.">
```go
// Loop resets the benchmark timer the first time it is called in a benchmark,
// so any setup performed prior to starting the benchmark loop does not count
// toward the benchmark measurement. Likewise, when it returns false, it stops
// the timer so cleanup code is not measured.
//
// Within the body of a "for b.Loop() { ... }" loop, arguments to and
// results from function calls and assigned variables within the loop are kept
// alive, preventing the compiler from fully optimizing away the loop body.
// Currently, this is implemented as a compiler transformation that wraps such
// variables with a runtime.KeepAlive intrinsic call. This applies only to
// statements syntactically between the curly braces of the loop, and the loop
// condition must be written exactly as "b.Loop()".
```
</GitHubCode>

Có hai chi tiết nhỏ trên Go 1.27.1 đáng lưu ý từ bảng đo trên. Thứ nhất, `b.Loop()` thêm khoảng ~1,4 ns chi phí spill stack và kiểm tra điều kiện lặp so với `GlobalSink` trên các hàm siêu nhỏ dưới 5 ns — với hàm thực tế vài chục nano-giây trở lên thì mức này không đáng kể. Thứ hai, `for b.Loop()` bảo vệ *kết quả* không bị xóa, nhưng nếu bạn truyền hẳn một hằng số cục bộ ngay trước vòng lặp (`x := 0xdeadbeef; for b.Loop() { popcnt(x) }`), compiler vẫn có thể tính gộp trước `popcnt(x)` thành `46` (constant folding) trước khi `KeepAlive` giữ số `46` đó lại; hãy cho biến đầu vào thay đổi (`x++`) hoặc đọc từ biến package khi đo các hàm số học thuần túy.

## Chứng minh bằng thống kê với benchstat

Chạy benchmark đúng một lần (`-count=1`) gần như không chứng minh được gì vì chỉ một tác vụ nền hay nhịp đổi xung CPU là kết quả đã lệch 15%. Gom `-count=10` lượt vào hai file (`old.txt` và `new.txt`) rồi so bằng **`benchstat`** mới biến cảm giác thành bằng chứng thống kê.

Phiên bản `benchstat` hiện đại tính **số trung vị (median)** kèm **khoảng tin cậy 95%** (`± X%`) cho từng bản, không giả định số liệu phải tuân theo phân phối chuẩn hình chuông. Khi so sánh hai file, nó chạy kiểm định phi tham số **Mann-Whitney U** để tính giá trị **`p-value`** (xác suất chênh lệch giữa bản cũ và mới chỉ do hên xui/nhiễu nền). Nếu `p >= 0.05` (ngưỡng mặc định `-alpha`), `benchstat` từ chối kết luận và in dấu `~`. Khi có từ hai sub-benchmark trở lên, dòng **`geomean`** (trung bình nhân) ở cuối bảng tổng hợp tỷ lệ thay đổi chung mà không bị một ca quá chậm kéo lệch toàn bảng.

Xem thử hai lần chạy thật trên Go 1.27.1 (Apple M2). Trước tiên là so `atomic.StoreInt32` với `atomic.StoreInt64` (từ `#89`) qua `-count=10` lượt:

## Macrobenchmark: đo toàn bộ service khi chạy thật

Ngay cả khi `benchstat` xanh rì trên một hàm, đẩy lên server vẫn có thể chậm. Microbenchmark chạy trong `go test` trên một goroutine lẻ, không có TCP socket, không có tranh chấp khóa giữa các request đồng thời, và không phản ánh đúng nhịp GC khi heap giữ dữ liệu sống thật.

<YouTube id="wv97cPiqYSU" title="P99 CONF 2023 | The Art of Macro Benchmarking — Bartłomiej Płotka" start={382} end={450} caption="Từ 6:22 đến 7:30, Bartłomiej Płotka phân biệt microbenchmark, macrobenchmark và production benchmark — vì sao thử nghiệm toàn hệ thống mới lộ ra những điểm nghẽn mà microbenchmark bỏ sót." sourceTitle="ScyllaDB P99 CONF — Bartłomiej Płotka" />

**Macrobenchmark** chạy nguyên binary service hoàn chỉnh (tốt nhất nằm trong container có giới hạn CPU/RAM giống thật, như tư duy của bộ `efficientgo/e2e`) rồi bắn tải HTTP hoặc gRPC từ bên ngoài vào:

- **`k6` (Grafana Labs)**: công cụ viết bằng Go cho phép kịch bản tải bằng JavaScript, rất hợp kiểm tra luồng nhiều bước (`POST /todos` -> `GET /todos` -> `GET /todos/{id}`), chia pha warmup, kiểm tra nội dung trả về và gắn ngưỡng fail cho CI.
- **`vegeta`**: công cụ CLI/thư viện Go chuyên bắn tải HTTP ở tốc độ RPS cố định, giúp giữ nhịp bắn ngay cả khi server bị chậm (tránh lỗi sai số *coordinated omission* của tải vòng kín).
- **`ghz`**: phiên bản chuyên trị gRPC viết bằng Go, hỗ trợ protobuf reflection và xuất phân bố độ trễ theo mã trạng thái gRPC.

Để thấy rõ macrobenchmark phơi bày được những gì mà microbenchmark bó tay, mình bắn thử 4.000 request trộn (`10% POST /todos`, `20% GET /todos`, `70% GET /todos/{id}`) từ 8 luồng HTTP đồng thời vào bộ router `Todo` của Bài 10 trên Go 1.27.1 sau một nhịp warmup 200 request:

```go
// Đoạn driver bắn tải qua loopback vào các route Todo của Bài 10 (8 luồng x 500 request)
for i := range perWorker {
	t0 := time.Now()

	case 0:
		resp, err = client.Post(srv.URL+"/todos", "application/json", bytes.NewReader(payload))
	case 1, 2:

	default:
		resp, err = client.Get(fmt.Sprintf("%s/todos/%d", srv.URL, (i%200)+1))
	}

	_, _ = io.Copy(io.Discard, resp.Body)
	resp.Body.Close()
	if resp.StatusCode >= 400 {
		badStatus.Add(1)
	}
	lats = append(lats, time.Since(t0))
}
```

Khi dựng bài bắn tải `k6` hoặc `vegeta` trong container staging, giữ năm thói quen sau để số liệu đừng đánh lừa bạn:

```javascript
// todo-load.js — kịch bản k6 tối thiểu có bắn tốc độ đều và kiểm tra phản hồi
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',
      rate: 200, timeUnit: '1s', duration: '3m', preAllocatedVUs: 20,
    },
  },
  thresholds: { http_req_duration: ['p(99)<50'], http_req_failed: ['rate<0.01'] },
};

export default function () {
  const res = http.get('http://todo-api:8080/todos');
  check(res, { 'status 200': (r) => r.status === 200, 'json array': (r) => r.body.startsWith('[') });
}
```

1. **Làm ấm (warmup) trước, tính số liệu sau**: loại bỏ pha mở pool TCP, làm đầy cache và nở span ban đầu khỏi bảng phân vị.
2. **Dùng tải vòng hở (open-loop) theo RPS mục tiêu**: dùng `constant-arrival-rate` trong `k6` hoặc `vegeta -rate` để client tiếp tục gửi đúng nhịp ngay cả khi server bị khựng, lộ đúng độ dồn hàng đợi.
3. **Bắt buộc kiểm tra mã HTTP và payload**: không có `check()`, một endpoint lỗi `500` trả lời trong `0,2 ms` sẽ trông như kỷ lục tốc độ!
4. **Đừng để chính máy bắn tải bị nghẽn**: kiểm tra CPU máy bắn tải, giới hạn file descriptor (`ulimit -n`) và cổng ephemeral trước khi đổ lỗi cho server.
5. **Chạy đủ lâu để GC và Prometheus kịp ghi nhận**: chạy vài phút thay vì vài trăm mili-giây để quét qua nhiều chu kỳ scrape `15s` và nhìn thấy nhịp GC ổn định trên biểu đồ RED/USE.

Một khi microbenchmark hoặc macrobenchmark đã chứng minh rõ luồng nào đang vượt ngân sách hiệu năng, bước tiếp theo là soi thẳng tới đúng dòng code đốt CPU hay cấp phát heap — mình sẽ đi chi tiết ở bài sau [Profiling trong Go](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/).

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Tải vòng kín (closed-loop) vs. vòng hở (open-loop)**: tải vòng kín bắt mỗi user ảo đợi phản hồi xong mới gửi tiếp (vô tình che bớt độ trễ xếp hàng); tải vòng hở bắn theo RPS cố định bất kể server chậm đi.
- **Warmup window (pha làm ấm)**: khoảng chạy khởi động không tính vào số đo cuối để kết nối TCP, cache và heap span ổn định.
- **Coordinated omission**: sai số thống kê kinh điển khi máy bắn tải bị chậm lây theo server, làm kết quả phân vị đuôi thấp hơn thực tế.

</Concepts>

## Điểm rút ra (Key takeaways)

- **Đo service bằng RED và tài nguyên bằng USE**: dùng Prometheus Histogram (`sum by (le)`) để tính chuẩn độ trễ đuôi cụm pod, tuyệt đối tránh dùng trung bình cộng hay Summary liên pod, và giữ label route sạch không nhét ID động.
- **Soi song song `working_set` container với Go heap**: bọc `rate()` quanh bộ đếm CPU cộng dồn và đối chiếu `container_memory_working_set_bytes` với `runtime/metrics` (`HeapAlloc`, `HeapInuse`, `HeapReleased`) để phân biệt rò Go heap, phân mảnh span và rò bộ nhớ ngoài heap.
- **Viết benchmark chống số ảo bằng `for b.Loop()` (Go 1.24+)**: tận dụng `b.Loop()` để tự reset timer và giữ biến qua `runtime.KeepAlive`, kiểm tra lỗi bằng `b.Fatal`, thay đổi đầu vào hằng số, và để ý hiệu ứng cache ấm ảo.
- **Luôn kiểm định qua `benchstat` với `-count=10` và `p < 0,05`**: bỏ qua số đo 1 lần hoặc kết quả gắn dấu `~`, đọc đủ cả ba bảng (`sec/op`, `B/op`, `allocs/op`) cùng dòng `geomean`.
- **Khép vòng kiểm chứng bằng macrobenchmark**: bắn tải có kiểm tra phản hồi bằng `k6`, `vegeta` hoặc `ghz` để bắt tranh chấp mutex, chu kỳ GC, nghẽn socket và giới hạn cgroup mà microbenchmark không thấy.
