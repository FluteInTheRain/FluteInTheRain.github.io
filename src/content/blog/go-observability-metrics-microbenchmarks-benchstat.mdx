### Why fast-looking Go benchmarks still ship regressions

Every Go engineer has seen a triumphant pull request comment: *"Refactored parser — 4x faster!"* accompanied by a single `-count=1` benchmark line pasted from a noisy laptop. Two days later, latency in Kubernetes climbs higher than before, or heap allocations double under real payloads.

Measuring software performance accurately—building directly on the hardware cache and allocator mechanics just covered—is fundamentally harder than running unit tests: compiler optimizers silently delete unused loops, averages hide p99 stalls, OS page caches skew second runs, and single-function microbenchmarks ignore whole-system concurrency and network pools. This guide covers four skills to build trustworthy numbers in Go:

1. **The four observability signals**: matching Logging, Tracing, Prometheus Histograms (RED/USE), and Profiling to each efficiency question.
2. **Reading CPU &amp; memory metrics properly**: avoiding cumulative CPU counter traps and separating `HeapAlloc`, `HeapInuse`, `HeapSys`, and Container Working Set (`RSS`).
3. **Writing Go microbenchmarks that don't lie**: beating setup contamination, dead-code elimination, and Big O assumptions.
4. **Statistical proof &amp; Macrobenchmarks**: reading `benchstat` p-values and spinning up full Go `e2e` + `k6` environments.

<Callout type="note" title="TL;DR">
Watch **RED** (Rate, Errors, Duration) and **USE** (Utilization, Saturation, Errors) with Prometheus **Histograms**—never plain averages—to spot tail latency. Measure CPU time in seconds per interval via `rate()`, check **both** `go_memstats_heap_inuse_bytes` and container `working_set` RSS, always keep setup out of `testing.B` timers, assign outputs to package-level `Sink` variables (or `b.Loop()`), and demand `p &lt; 0.05` across `-count=6..10` runs in **`benchstat`**.
</Callout>

<Concepts>

- **RED vs. USE methods**: **RED** tracks request-driven workloads (Rate, Errors, Duration), while **USE** monitors hardware/resource bottlenecks (Utilization, Saturation queue depth, Errors).
- **Histogram (`le` buckets)**: metric counting how many requests fell below each duration bucket threshold (`0.01s`, `0.05s`, `0.5s`), letting Prometheus estimate p90/p99 percentiles accurately.
- **Big O complexity**: worst-case growth rate relative to input size `N` (`O(1)`, `O(N)`, `O(N log N)`), useful for eliminating catastrophic scaling yet insufficient alone due to constant-factor hardware costs.
- **Dead-code elimination**: compiler pass that drops computations whose results are never read—making broken microbenchmarks report sub-nanosecond speeds falsely.
- **Statistical p-value (`benchstat`)**: probability that an observed before/after difference happened purely by random noise (`p &lt; 0.05` marks genuine change; `~` means noisy uncertainty).

</Concepts>

## 1. Efficiency observability: Logs, Traces, Metrics &amp; RED/USE

Newcomers often reach straight for heavyweight debug logging on every request, then wonder why logging JSON serialization itself consumes 30% of service CPU. Observability relies on four complementary signals ordered by collection overhead:

<Figure src={promArch} alt="Official Prometheus architecture showing target discovery, metrics pulling, TSDB storage, PromQL querying, and Grafana/Alertmanager outputs" caption="Pull-based Metrics pipelines like Prometheus aggregate millions of fast counters locally in RAM, turning costly per-request telemetry into cheap time-series scrapes." sourceTitle="Prometheus Documentation — Overview" sourceUrl="https://prometheus.io/docs/introduction/overview/" />

- **Metrics (Prometheus)** collect tiny aggregated atomic counters per process at minimal CPU cost—always start here with **RED** for APIs/workers and **USE** for CPU/RAM/disk pools. Crucially, replace raw sums/averages with **Prometheus Histograms** (`histogram_quantile(0.99, ...)`), because 99 fast 5 ms calls plus 1 stalled 705 ms call averages to a deceptive "12 ms"!
- **Tracing** records single-request span timelines across HTTP, gRPC, and SQL boundaries (sampled via head or tail sampling so trace exports do not saturate network bandwidth).
- **Logging** belongs strictly to low-volume errors or startup events; calling `log.Debug` inside tight request paths burns CPU allocations even when formatted conditionally unless guarded properly.
- **Continuous Profiling** attributes CPU nanoseconds and Heap allocations straight down to exact Go function lines (covered in Part 11).
- And track latency distribution accurately via Prometheus Histogram:

```go
// Track latency distribution accurately via Prometheus Histogram
httpDur := prometheus.NewHistogramVec(prometheus.HistogramOpts{
	Name:    "http_request_duration_seconds",
	Help:    "Request duration broken down cleanly into p90/p99 quantiles.",
	Buckets: []float64{0.005, 0.01, 0.025, 0.1, 0.5, 2.0},
}, []string{"route", "code"})

// Measure inside middleware without adding heavy JSON debug logs per call:
start := time.Now()
next.ServeHTTP(w, r)
httpDur.WithLabelValues(route, status).Observe(time.Since(start).Seconds())
```

<GoObsFourSignalsMap />

Also beware Prometheus label **cardinality explosions**: attaching high-cardinality fields such as `user_id`, `request_id`, or unnormalized raw paths (`GET /users/991823/profile`) turns one harmless metric into millions of active time-series inside memory and TSDB indexes, frequently OOM-killing either your Go exporter or Prometheus itself! Always bucket dynamic parameters into clean route patterns (`/users/:id/profile`).

| Metric Type | Cumulative / Snapshot | Safe Across Scrapes? | Go Benchmark / Prometheus Choice |
| :--- | :--- | :--- | :--- |
| **`Counter`** | Monotonically rising (`+1`) | Always wrap with `rate()` | HTTP request counts, 5xx errors, bytes sent |
| **`Gauge`** | Current instant value (`+1 / -1`) | Read directly | Active goroutines, queue depth, `HeapInuse` |
| **`Histogram`** | Cumulative buckets (`le="..."`) | **Mergeable across replicas!** | Aggregating cluster-wide `histogram_quantile(0.99, ...)` |
| **`Summary`** | Client-computed quantiles | Never average across pods! | Single-node summaries only; prefer Histograms |

<Concepts>

- **Tail latency (p90 / p99)**: duration below which 90% or 99% of requests finish—what users actually experience during traffic bursts rather than smoothed means.
- **Head vs. tail sampling**: deciding at request start (e.g., trace 1% randomly) versus keeping all traces after a slow `p99` outlier or `500` error finishes.

</Concepts>

## 2. Reading CPU time and Container vs. Go Memory metrics cleanly

Once Grafana graphs load, engineers frequently misread two standard metrics:

1. **CPU seconds vs. percentage**: Linux and Go runtime expose **cumulative CPU seconds** consumed (`process_cpu_seconds_total` and `container_cpu_usage_seconds_total`), never instant percentages. Apply `rate(metric[1m])` to turn cumulative counters into fractional CPU cores actively used, and compare against Kubernetes cgroup throttled time (`container_cpu_cfs_throttled_seconds_total`) when requests stall despite low average utilization!
2. **Container RAM (`RSS` / `WorkingSet`) vs. Go Heap (`MemStats`)**: Kubernetes enforces OOM kills against container `working_set` (which combines Go Heap, Goroutine stacks, Cgo/explicit `mmap`, and un-reclaimed OS buffers). Meanwhile, `runtime.ReadMemStats` splits Go's heap into `HeapSys` (virtual arenas requested), `HeapInuse` (active 8 KB spans), and `HeapAlloc` (live reachable bytes).

```go
// Read internal Go heap vs. idle spans inside /metrics or diagnostics:
var m runtime.MemStats
runtime.ReadMemStats(&m)
fmt.Printf("HeapAlloc=%dMB HeapInuse=%dMB HeapSys=%dMB HeapReleased=%dMB\n",
	m.HeapAlloc>>20, m.HeapInuse>>20, m.HeapSys>>20, m.HeapReleased>>20)
```

<GoEffMemoryMetricsAnatomy />

Notice why checking both layers saves hours during incidents: if container `working_set` hits 950 MB while `HeapAlloc` reads only 40 MB, hunting inside Go structs misses the leak—the memory sits in leaked goroutine stacks, Cgo libraries, `mmap` files, or OS page cache!

| Memory Metric | Source | What It Actually Measures | When It Exposes a Production Bug |
| :--- | :--- | :--- | :--- |
| **`HeapAlloc`** | `runtime.MemStats` | Live reachable Go heap objects | Grows continuously across GC cycles -> genuine live Go leak |
| **`HeapInuse`** | `runtime.MemStats` | All active 8 KB runtime spans holding objects | Much larger than `HeapAlloc` -> heavy span fragmentation |
| **`HeapSys`** | `runtime.MemStats` | Virtual address spans reserved from OS | Stays high briefly; watch `HeapSys - HeapReleased` instead |
| **`container_memory_working_set_bytes`** | Linux cgroup (cAdvisor) | Active anonymous RSS + un-reclaimed OS file cache | Approaching pod RAM limit triggers kernel **OOMKill** regardless of GC! |

When paging through an incident, keep these four PromQL queries handy so Kubernetes CPU throttling or fragmented spans never masquerade as healthy dashboards:

```text
# 1. Catch micro-bursts hitting Linux CFS 100ms CPU quotas despite low 1m average
rate(container_cpu_cfs_throttled_seconds_total{pod=~"api-.*"}[1m])

# 2. Compute genuine request p99 latency across pods (requires histograms, never summaries!)
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# 3. Measure Go allocator span fragmentation gap waiting for scvg release
go_memstats_heap_inuse_bytes - go_memstats_heap_alloc_bytes
```

Think of Linux CFS throttling like a highway toll booth giving you **40 milliseconds of green light out of every 100 ms**: a sudden GC mark phase or JSON batch finishes in 40 ms cleanly, gets paused for 60 ms at the cgroup kernel boundary, and adds an inexplicable +60–180 ms tail spike even though average CPU sits calmly at `35%`.

<Concepts>

- **Cumulative Counter + `rate()`**: monotonically increasing total (`cpu_seconds_total`) requiring `rate()` per second so restarts or scrape intervals never corrupt metrics.
- **`HeapInuse` vs. `HeapAlloc`**: `HeapAlloc` sums live Go object bytes, whereas `HeapInuse` tracks whole 8 KB allocator spans—showing hidden memory fragmentation gaps.

</Concepts>

## 3. Writing Go microbenchmarks that don't lie

Functional unit tests ask a binary pass/fail question, whereas **microbenchmarks (`func BenchmarkX(b *testing.B)`)** act like high-precision marine chronometers trying to measure nanosecond physics through changing OS loads, CPU thermal throttling, and compiler tricks:

<Figure src={chronometerImg} alt="Brass marine chronometer preserved inside its gimbaled wooden box" caption="Harrison-era marine chronometers suspended brass escapements inside gimbaled cases to stay level on rolling seas—just as microbenchmarks require ResetTimer and exported sinks to resist compiler and OS noise." sourceTitle="Wikimedia Commons: Marine chronometer, Joseph Sewill (Liverpool, c. 1870)" sourceUrl="https://commons.wikimedia.org/wiki/File:Marine_chronometer,_Joseph_Sewill,_Liverpool_(c._1870).JPG" />

Three everyday traps turn Go benchmarks into fiction:

1. **Setup code inside the `b.N` timer**: creating temporary files or parsing inputs before setting `b.ResetTimer()` hides the cost of your algorithm behind I/O fixture setup (and pair with `b.StopTimer()` / `b.StartTimer()` sparingly, as excessive timer toggles add skew).
2. **Compiler dead-code elimination**: if an inlineable pure helper's output is ignored (`_ = fn(i)`), Go compiles away the body completely! Let's prove this live on Apple M2 Go 1.27—notice how discarding `computeMask` drops time to a single ~0.31 ns cycle:

<TerminalOutput command="go test -run '^$' -bench 'BenchmarkMask' -benchmem" label="Apple M2 · Go 1.27" caption="Live proof of compiler dead-code elimination: dropping the return value shrinks runtime artificially from 0.61 ns/op to 0.31 ns/op.">
```text
goos: darwin
goarch: arm64
pkg: effgobench
cpu: Apple M2
BenchmarkMaskEliminated-8   	1000000000	         0.3119 ns/op	       0 B/op	       0 allocs/op
BenchmarkMaskObserved-8     	1000000000	         0.6080 ns/op	       0 B/op	       0 allocs/op
```
</TerminalOutput>

3. **Unchecked assertions &amp; missing `-benchmem`**: never run benchmarks on broken functions that return errors silently (`b.Fatal(err)` on errors!), always enable `-benchmem` or `b.ReportAllocs()`, test multiple input sizes via sub-benchmarks (`for _, n := range sizes { b.Run(...) }`), and upgrade to Go 1.24's **`for b.Loop()`** when available so Go prevents dead-code elimination automatically.

```go
var globalResult uint64 // package-level sink blocks dead-code elimination

func BenchmarkComputeObserved(b *testing.B) {
	input := buildFixture(b, 100_000)
	b.ReportAllocs()
	b.ResetTimer() // ignore setup time above!
	var acc uint64
	for i := 0; i < b.N; i++ {
		acc += computeMask(input, uint64(i))
	}
	globalResult = acc
}
```

## 4. Statistical rigor with `benchstat` and `e2e` macrobenchmarks

Bartłomiej Płotka highlights a golden rule in his P99 CONF talk: **a single benchmark run proves almost nothing**. Even on a quiet machine, background daemons, CPU frequency scaling, and memory layout randomization create swings between runs:

<YouTube id="wv97cPiqYSU" title="P99 CONF 2023 | The Art of Macro Benchmarking by Bartłomiej Płotka" start={382} end={450} caption="From 6:22 to 7:30, Bartłomiej Płotka contrasts micro, macro, and production benchmarks and why environment realism matters alongside functional testing." sourceTitle="ScyllaDB P99 CONF — Bartłomiej Płotka" />

Follow this repeatable protocol from `efficientgo/examples`:

1. Run `-count=6` to `-count=10` iterations into versioned output files (`go test -run '^$' -bench '^BenchmarkSum$' -benchtime=5s -count=6 -cpu=4 -benchmem | tee v4.txt`).
2. Compare two runs with **`benchstat old.txt new.txt`** (the Mann-Whitney U statistical test). Look at a real Apple M2 Go 1.27 run comparing `Sum4` vs. streaming `Sum6`:

<TerminalOutput command="go run golang.org/x/perf/cmd/benchstat@latest v4.txt v6.txt" label="Apple M2 · Go 1.27" caption="Real benchstat output: ~ (p=0.240) honestly warns latency variance (±69%) is noisy, while p=0.002 proves a 99.98% heap cut.">
```text
      │    v4.txt    │            v6.txt             │
      │    sec/op    │    sec/op     vs base         │
Sum-8   1.801m ± 69%   2.089m ± 48%  ~ (p=0.240 n=6)

      │     v4.txt     │              v6.txt               │
      │      B/op      │    B/op     vs base               │
Sum-8   1401263.5 ± 0%   216.0 ± 0%  -99.98% (p=0.002 n=6)

      │   v4.txt   │              v6.txt               │
      │ allocs/op  │ allocs/op   vs base               │
Sum-8   5.000 ± 0%   3.000 ± 0%  -40.00% (p=0.002 n=6)
```
</TerminalOutput>

Look closely at that `~ (p=0.240 n=6)` line above—that tilde is your shield against false optimizations:

- Notice how `B/op` dropped `-99.98%` with zero variance (`± 0%`, `p=0.002`), proving the memory cut is rock-solid.
- Meanwhile `sec/op` jumped `± 69%` on laptop battery/background noise, so `benchstat` rightly refuses to crown a CPU winner (`p=0.240 > 0.05`). Increasing sample duration (`-benchtime=2s`), pinning GOMAXPROCS (`-cpu=4`), running `-count=10`, and closing background browsers tightens variance down under `± 5%` before deciding CPU impact.

If you want to evaluate latency or memory optimizations reliably, stop trusting single microbenchmark runs on noisy developer laptops—automate reproducible multi-sample runs and macrobenchmarks that mirror real garbage collection, caches, and OS limits.
</QuoteCard>

## Key takeaways

- **Lead with Histograms and RED/USE metrics**: track request `Rate`, `Errors`, and `Duration` percentiles via Prometheus buckets rather than logs in hot loops or misleading means.
- **Monitor both OS RSS and Go Heap internals**: apply `rate()` to cumulative CPU counters and compare container `working_set` against `HeapInuse` to spot off-heap memory growth.
- **Guard `testing.B` against silent falsehoods**: assert correctness, call `b.ResetTimer()`, pass outputs into exported sinks (or use `b.Loop()`), and always inspect `-benchmem`.
- **Insist on `benchstat` before claiming speedup**: run `-count=6..10` under steady CPU limits and ignore gains flagged `~` (`p >= 0.05`).
- **Promote major changes to Macrobenchmarks**: use containerized `e2e` + `k6` pipelines to catch real GC pacing, socket churn, and pooling regressions invisible in microbenchmarks.

### Vì sao benchmark thấy "nhanh gấp 4 lần" mà đẩy lên server vẫn chậm?

Anh em làm Go chắc chắn từng thấy ít nhất một PR ghi gọn lỏn: *"Đã tối ưu parser — chạy nhanh hơn 4x!"* kèm đúng một dòng `go test -bench` chạy thử một lần trên laptop đang mở Slack với Chrome. Hai ngày sau đưa lên Kubernetes, độ trễ p99 còn vọt cao hơn lúc chưa sửa.

Nối tiếp kiến thức phần cứng và GC vừa nắm ở bài trước, việc đo hiệu năng chuẩn xác vẫn khó hơn chạy unit test rất nhiều: trình biên dịch thấy hàm không dùng kết quả thì âm thầm xóa luôn cho ra `0,3 ns`, số trung bình che giấu sạch độ trễ đuôi p99, còn microbenchmark lẻ một hàm lại bỏ qua hoàn toàn GC, connection pool với mạng thật. Bài này gom lại bốn kỹ năng cốt lõi để lấy được số đo đáng tin:

1. **Bốn tín hiệu Observability**: biết lúc nào dùng Logs, Tracing, Metrics (RED/USE + Histogram) hay Profiling.
2. **Đọc đúng chỉ số CPU &amp; RAM**: cách biến bộ đếm tích lũy thành số core thật và phân biệt `HeapAlloc`, `HeapInuse`, `HeapSys` với `RSS` của container.
3. **Viết Go microbenchmark không ra số ảo**: né thời gian setup, né bẫy compiler xóa mất hàm (dead-code elimination) và hiểu đúng ý nghĩa `-benchmem`.
4. **Kiểm chứng thống kê với `benchstat` &amp; Macrobenchmark**: đọc chỉ số tin cậy `p-value` và dựng bài test tải thực tế (`e2e` + `k6`).

<Callout type="note" title="Tóm tắt nhanh (TL;DR)">
Theo dõi hệ thống bằng bộ chỉ số **RED** (Rate, Errors, Duration) và **USE** (Utilization, Saturation, Errors) qua **Prometheus Histogram** — đừng bao giờ tin con số trung bình. Đổi bộ đếm CPU bằng hàm `rate()`, đối chiếu **cả** `HeapInuse` trong Go lẫn `working_set` RSS của container, tách phần khởi tạo khỏi `b.ResetTimer()`, gán kết quả vào biến `Sink` (hoặc dùng `b.Loop()`), và luôn kiểm chứng `p &lt; 0,05` qua 6–10 lần chạy bằng **`benchstat`**.
</Callout>

<Concepts title="Giải thích nhanh mấy thuật ngữ cho người mới">

- **Mô hình RED vs. USE**: **RED** đo luồng xử lý request (*Rate* tần suất, *Errors* lỗi, *Duration* độ trễ); **USE** soi sức khỏe tài nguyên phần cứng (*Utilization* % bận, *Saturation* hàng đợi nghẽn, *Errors*).
- **Histogram (`le` buckets)**: bộ đếm phân loại thời gian xử lý vào từng ngưỡng (`0.01s`, `0.05s`, `0.5s`), giúp Prometheus tính chuẩn độ trễ p90/p99 thay vì lấy trung bình cộng.
- **Độ phức tạp Big O**: tốc độ phình tài nguyên theo kích thước đầu vào `N` (`O(1)`, `O(N)`, `O(N log N)`), cần để né thảm họa thuật toán nhưng chưa đủ nếu bỏ qua chi phí phần cứng trên mỗi bước.
- **Dead-code elimination**: tối ưu của compiler tự cắt bỏ đoạn tính toán không ai đọc kết quả — làm benchmark hỏng báo ảo chỉ tốn 1 chu kỳ CPU.
- **Độ tin cậy p-value (`benchstat`)**: xác suất chênh lệch giữa hai lần đo chỉ là do may rủi/nhiễu (`p &lt; 0,05` mới đáng tin; dấu `~` nghĩa là quá nhiễu chưa chốt được).

</Concepts>

## 1. Bốn tín hiệu đo lường: Logs, Traces, Metrics &amp; RED/USE

## 2. Đọc đúng chỉ số CPU và RAM của Container vs. Go Runtime

Tới lúc mở dashboard Grafana lên điều tra sự cố, có hai chỗ cực kỳ hay bị đọc nhầm:

1. **Bộ đếm CPU luôn là số cộng dồn (cumulative)**: Linux và Go chỉ xuất tổng số *giây CPU* đã chạy từ lúc bật (`process_cpu_seconds_total`, `container_cpu_usage_seconds_total`), chứ không xuất phần trăm tức thời. Phải bọc hàm `rate(metric[1m])` để biết trung bình một giây app đang ăn bao nhiêu nhân CPU — và nhớ nhìn kèm `container_cpu_cfs_throttled_seconds_total` để phát hiện pod bị bóp CPU dù tải trung bình nhìn còn rảnh!
2. **RAM Container (`RSS` / `WorkingSet`) khác Heap của Go (`MemStats`)**: Kubernetes giết pod (OOMKill) theo `working_set` tổng hợp của cả tiến trình (gồm Go Heap + stack các goroutine + thư viện Cgo / `mmap` riêng + buffer OS chưa nhả). Trong khi `runtime.ReadMemStats` chia riêng phần Heap của Go thành `HeapSys` (tổng vùng đã xin OS), `HeapInuse` (các span 8 KB đang chứa object) và `HeapAlloc` (số byte object còn sống thật sự).

```go
// Đọc nhanh chỉ số Heap bên trong Go runtime cho trang chẩn đoán / metrics:
var m runtime.MemStats
runtime.ReadMemStats(&m)
fmt.Printf("HeapAlloc=%dMB HeapInuse=%dMB HeapSys=%dMB HeapReleased=%dMB\n",
	m.HeapAlloc>>20, m.HeapInuse>>20, m.HeapSys>>20, m.HeapReleased>>20)
```

<GoEffMemoryMetricsAnatomy />

Đối chiếu hai lớp này tiết kiệm hàng giờ mò kim đáy bể: nếu container `working_set` vọt tới 950 MB trong lúc `HeapAlloc` chỉ báo 40 MB thì chắc chắn RAM không rò trong struct Go — thủ phạm nằm ở đống goroutine bị kẹt không thoát, `mmap` hoặc Cgo bên ngoài!

| Chỉ số RAM | Nguồn lấy | Ý nghĩa thật sự | Dấu hiệu bệnh production |
| :--- | :--- | :--- | :--- |
| **`HeapAlloc`** | `runtime.MemStats` | Tổng byte object Go đang sống | Tăng đều qua nhiều vòng GC -> rò rỉ biến Go thật sự |
| **`HeapInuse`** | `runtime.MemStats` | Các trang span 8 KB đang chứa ít nhất 1 object | Cao vượt `HeapAlloc` nhiều -> Heap bị phân mảnh nặng |
| **`HeapSys`** | `runtime.MemStats` | Dải bộ nhớ ảo đã xin OS | Cao sau đợt tải nhọn; theo dõi `HeapSys - HeapReleased` |
| **`container_memory_working_set_bytes`** | Linux cgroup (cAdvisor) | RAM vật lý RSS + OS file cache đang giữ | Chạm trần limit Kubernetes là nổ **OOMKill** ngay lập tức |

Lúc trực sự cố thực tế, cứ thủ sẵn ba câu query PromQL này để bắt ngay bệnh bóp CPU ngầm hoặc phân mảnh Heap mà biểu đồ trung bình hay che giấu:

```text
# 1. Bắt tình trạng pod bị bóp CFS từng nhịp 100ms dù tải trung bình còn thấp
rate(container_cpu_cfs_throttled_seconds_total{pod=~"api-.*"}[1m])

# 2. Tính độ trễ p99 chuẩn toàn cụm pod (bắt buộc dùng Histogram, cấm cộng Summary!)
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# 3. Đo độ rỗng phân mảnh trong các span 8 KB đang chờ scvg trả OS
go_memstats_heap_inuse_bytes - go_memstats_heap_alloc_bytes
```

Hãy tưởng tượng Linux CFS quota giống trạm gác cho xe qua **40 ms trong mỗi chu kỳ 100 ms**: khi một đợt GC hoặc parse JSON cần 45 ms liên tục, pod bị kernel nhấn nút tạm dừng hết 60 ms còn lại của chu kỳ đó, đẻ ra cú giật đuôi p99 `+60–180 ms` ngay cả khi đồ thị CPU trung bình mới báo `35%`.

<Concepts title="Mấy khái niệm ở mục này">

- **Cumulative counter + `rate()`**: bộ đếm chỉ tăng đều theo thời gian (`cpu_seconds_total`), buộc phải tính đạo hàm theo giây qua `rate()` mới thành mức tải hiện tại.
- **`HeapInuse` vs. `HeapAlloc`**: `HeapAlloc` chỉ đếm byte object đang sống, còn `HeapInuse` đếm trọn vẹn các span 8 KB đang giữ chỗ — giúp nhìn ra hiện tượng phân mảnh bộ nhớ.

</Concepts>

## 4. Kiểm chứng thống kê bằng `benchstat` và Macrobenchmark

Bartłomiej nhấn mạnh một nguyên tắc sống còn trong bài nói ở P99 CONF 2023: **một lần đo benchmark đơn lẻ hầu như không chứng minh được gì**. Ngay cả khi tắt hết app, xung nhịp CPU nhảy lên xuống và bố cục bộ nhớ ngẫu nhiên vẫn làm số đo xê dịch qua lại:

<YouTube id="wv97cPiqYSU" title="P99 CONF 2023 | The Art of Macro Benchmarking — Bartłomiej Płotka" start={382} end={450} caption="Từ 6:22 đến 7:30, Bartłomiej Płotka phân biệt microbenchmark, macrobenchmark và production benchmark — vì sao đo đúng môi trường thật lại quyết định." sourceTitle="ScyllaDB P99 CONF — Bartłomiej Płotka" />

Quy trình chuẩn từ bộ ví dụ `efficientgo/examples` gồm ba bước rõ ràng:

1. Chạy lặp `-count=6` tới `-count=10` lượt và xuất thẳng ra file theo từng phiên bản (`go test -run '^$' -bench '^BenchmarkSum$' -benchtime=5s -count=6 -cpu=4 -benchmem | tee v4.txt`).

## Điểm rút ra (Key takeaways)

- **Dùng Histogram và bộ chỉ số RED/USE**: theo dõi `Rate`, `Errors` và phân vị `Duration` (p90/p99) bằng bucket Prometheus thay vì tin con số trung bình hay in debug log tràn lan.
- **Đối chiếu cả OS RSS lẫn `HeapInuse` của Go**: biến bộ đếm CPU thành mức tải bằng `rate()` và soi song song `working_set` với `MemStats` để không tìm nhầm chỗ rò RAM.
- **Khóa chặt `testing.B` chống số ảo**: kiểm tra lỗi trước, tách setup qua `b.ResetTimer()`, đẩy kết quả ra biến `Sink` (hoặc `b.Loop()`) và bật `-benchmem`.
- **Chỉ tin `benchstat` có `p &lt; 0,05`**: lặp tối thiểu `-count=6..10` trên môi trường yên tĩnh, bỏ qua mọi "cải thiện" vẫn gắn dấu ngã `~`.
- **Dùng Macrobenchmark khi tối ưu cấp hệ thống**: `e2e` + `k6` phơi bày rõ ảnh hưởng thật của GC, connection churn và pool tài nguyên dưới tải nhiều người dùng.
