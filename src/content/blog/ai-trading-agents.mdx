### A chatbot made up a policy, and the company paid for it

In 2022 a passenger named Jake Moffatt asked Air Canada's website chatbot about bereavement fares after his grandmother died. The chatbot told him he could buy a full-price ticket and apply for the bereavement discount afterwards. Air Canada's real policy did not allow that. When he applied, the airline refused. He took it to a small-claims tribunal in British Columbia.

Air Canada's defence was that it could not be held liable for what its chatbot said. The tribunal disagreed. In February 2024 it ordered the airline to pay damages of just over C$650, plus the usual costs. The sum is small. The company still owned the sentence its model wrote.

A trading team will meet the same moment, with bigger numbers. An LLM reads a filing, writes "revenue grew 12%", and an analyst puts it in a note. Nobody checked the 12%. This post is about the machinery around the model that makes that check possible. It covers four things:

1. **What an agent is**: a loop, not a smarter model.
2. **Tools**: code the model can call, so it does not do arithmetic or recall prices from memory.
3. **Retrieval and memory**: what the model gets to see, and why it is never the whole filing.
4. **Evidence**: how errors pile up over steps, and how to test an agent without fooling yourself.

<Callout type="note" title="TL;DR">

An LLM agent is a model inside a loop: it picks a tool, reads the result, and picks again until it answers. Fixed workflows and agents differ in who chooses the next step, and the simplest one that works is the right one. Tools turn guesses into computed facts; retrieval hands the model a few pieces of a document (FinanceBench found GPT-4-Turbo with retrieval wrong or refusing on 81% of its questions). Errors multiply across steps: ten steps at 95% each finish only 59.9% of the time. Published agent trading results often rest on very short tests, and an LLM may have read the outcome in its training text. Nothing here is investment advice or a recommendation to trade.

</Callout>

<Concepts>

- **LLM (large language model)**: a model that predicts the next piece of text. It answers from the text it was trained on and the text you give it.
- **Agent**: an LLM that decides its own next step, uses tools, and repeats until the task is done.
- **Tool**: ordinary code the model can ask the program to run, such as a price lookup or a calculator.
- **Context**: all the text the model can see in one call: instructions, your question, tool results.

</Concepts>

## 1. An agent is a loop

Plain version first. A chat model takes text in and gives text out, once. An agent wraps that call in a loop. The model says "I want to run the tool `get_prices` with these arguments." The program runs it and pastes the result back into the model's context. The model reads the result and says what to do next, until it decides to answer.

Anthropic's "Building effective agents" draws the line this way: workflows are "systems where LLMs and tools are orchestrated through predefined code paths", while agents are "systems where LLMs dynamically direct their own processes and tool usage." The difference is who picks the next step. A research paper called ReAct (Yao et al., 2022) showed the pattern early: interleave a line of reasoning with an action, read what the action returned, reason again. On two interactive benchmarks, ALFWorld and WebShop, it beat imitation and reinforcement learning methods by 34% and 10% in absolute success rate.

<AtP21Loop />

The loop has a useful consequence. The model never touches the world. Everything it does goes through a tool, so everything it does can be limited, logged and tested by the code around it. The limits in the bottom box of the figure (step count, budget, human sign-off on anything that writes) are plain code. A prompt that says "please be careful" is not one of them.

Most tasks do not need the loop. Say you want a summary of one filing: one call does it. Say you want figures extracted, checked against a second source, then written up: a fixed chain does it, and you can test each link. A router that sends each headline to a handler is another fixed design. Anthropic's advice is to use the simplest one that works and add autonomy only when the number of steps cannot be known in advance.

<AtP21Spectrum />

<Concepts>

- **Workflow**: a system where your code decides the order of steps and the model fills in each one.
- **ReAct**: a pattern where the model alternates a short reasoning line with a tool action and reads each result before the next step.
- **Trace**: the recorded list of every step an agent took: each tool call, each result, each decision.

</Concepts>

## 2. Tools are the hands

A model that is asked "what is the HOSE price ceiling if yesterday's reference price was 95,000?" will often get it right, and sometimes will not. The rule is a daily band of 7% around the reference price for stocks, as set in a July 2021 HOSE trading regulation reported by Người Quan Sát. That gives 95,000 x 1.07 = 101,650 for the ceiling and 95,000 x 0.93 = 88,350 for the floor. A tool does this multiplication in code, the same way every time. The model's job shrinks to choosing the tool and reading the answer.

<AtP21Tools />

Split tools into two groups. Read-only tools (search the filings, fetch prices, compute a band) cannot hurt anything, so the agent may call them freely. Tools that write (place an order, send a report under your name) change the world, so each call waits for a person. The waiting must be code. Project Vend, which you will meet in section 4, had a tool that changed prices; the lesson was that nothing in code stopped a bad price.

Two details matter in practice. Tool descriptions are part of the prompt: a vague name or an unclear argument makes the model call it wrong, and Anthropic's guide says tool design deserves as much care as prompt design. And a tool result goes straight into the context, so a tool that returns 4,000 tokens of raw table costs the agent room to think. Return the five rows that matter.

<Concepts>

- **Tool call**: a structured request from the model to run a named function with given arguments. The program runs it, not the model.
- **Read-only vs write tool**: a read-only tool only looks; a write tool changes something outside the program, such as an order or an email.
- **Reference price**: the price a HOSE daily band is measured from; the ceiling and floor are 7% above and below it.

</Concepts>

## 3. What the model gets to see: retrieval and memory

An annual report runs tens of thousands of words. Say it is 60,000 words. At about 0.75 words per token that is roughly 80,000 tokens. A model reads only what is in its context, and that context has a size limit. So the usual design is retrieval-augmented generation, RAG, introduced by Lewis et al. in 2020: cut the document into chunks, find the chunks that match the question, and give the model those.

Say the chunks are 500 tokens, so the filing becomes 160 of them, and the search keeps the top five. The model now reads 2,500 tokens, 3.1% of the report. It answers well if the right chunk is among the five, and badly if not.

<AtP21Rag />

Three failures show up again and again. The right chunk ranks sixth. A table is cut in half, so a row of numbers loses the header that says whether it is in millions of dong or in billions. Or the model reads the chunks and answers from memory anyway. FinanceBench, a set of open-book questions about public companies, put numbers on it: the authors report that GPT-4-Turbo with a retrieval system answered incorrectly or refused 81% of the questions.

Retrieval can also overfill the window. Say the window holds 128,000 tokens. A 3,000-token system prompt, ten tool results of 4,000 tokens each, and the whole 80,000-token filing add up to 123,000. That leaves 5,000. The agent has no room to think and no room for the next tool result.

<AtP21Context />

Long jobs therefore keep memory outside the window. The agent writes findings to a notes file as it goes and re-reads them, and a separate store holds past reports that it searches when it needs them. This is context engineering in practice: decide what goes in, what stays out, and what is written down for later.

<Concepts>

- **RAG (retrieval-augmented generation)**: search a document store for passages that match the question, then give them to the model so it answers from them.
- **Chunk**: one piece of a document cut to a fixed size so it can be searched and fitted into the context.
- **Context window**: the maximum amount of text, counted in tokens, the model can read in one call.
- **Token**: a small piece of text, often a word or part of a word. Prices and limits are counted in tokens.

</Concepts>

## 4. Errors pile up over steps

A research agent that answers one question might take ten steps: search, read, search again, compute, compare, draft. Each step can go wrong in a small way. The trouble is that the steps multiply.

Say each step is right 95% of the time and the task needs ten steps in a row. The whole task is right 0.95 to the tenth power, which is 59.9% of the time. With twenty steps it is 35.8%. At 99% per step and twenty steps it is 81.8%. This is plain arithmetic and holds for any model: whatever the per-step rate, a long chain shrinks it.

A check after each step helps a lot. Say the check catches 80% of wrong steps and allows one retry. A step then succeeds with probability 0.95 + 0.05 x 0.8 x 0.95 = 0.988, and ten steps finish 88.6% of the time. Play with the numbers below.

<AtP21CompoundDemo />

Anthropic's Project Vend is a real record of what unchecked steps look like. In 2025 Anthropic and Andon Labs let Claude run a small shop in Anthropic's San Francisco office, with web search, email, a notes tool, Slack and the ability to change prices. It lost money. An employee's joke request for a tungsten cube started a run of orders for metal items, and Claude quoted prices without researching costs, so some sold below cost. When an employee questioned a 25% staff discount, Claude replied that "our customer base is indeed heavily concentrated among Anthropic employees", said it would drop the discount codes, and offered them again within days. On April 1 it said it would deliver in person, in a blue blazer and red tie. Anthropic's verdict: "we would not hire Claudius."

<AtP21Vend />

Each failure in the figure has an ordinary fix in code: a price floor in the price tool, discount rules the model can read but not edit, a trace review that flags a claim with no tool call behind it. None of them is a better prompt.

<Concepts>

- **Compounding error**: when each step has a small chance of failing, the chance that all steps succeed shrinks with every step added.
- **Verifier**: a check that looks at a step's output, either another model, a rule, or a person, and flags it before it moves on.
- **Guardrail**: a limit enforced in code around the model, such as a price floor, a step cap or an approval gate.

</Concepts>

## 5. Testing an agent without fooling yourself

Multi-agent trading papers look convincing. TradingAgents (Xiao, Sun, Luo and Wang, 2024) gives language-model agents the roles of a trading firm: analysts for fundamentals, sentiment and technicals; bull and bear researchers who debate; a trader; a risk team. The paper reports Sharpe ratios of 8.21 for Apple, 6.39 for Google and 5.60 for Amazon.

Read the test window before the table. The backtest ran from 1 January to 29 March 2024, about three months. A footnote says the authors benchmarked over three months because of the cost of running LLMs and tools. They also write that the top Sharpe ratio exceeds their expected range and put it down to few pullbacks in that period. Three months of a mostly rising market cannot separate a good method from a good quarter. The roles are a design, and the test does not show that the design works. The Statistics post in this series explains why a Sharpe ratio from a short window needs a wide error bar.

<AtP21TradingAgents />

There is a second trap that only language models have. A model trained on text up to a certain date has read what happened up to that date. Glasserman and Lin (2023) studied this for sentiment scores from GPT: when you backtest on headlines inside the training window, the model may already know how the story ended (look-ahead bias), and it may be distracted by what it knows about a named company. They compared strategies built on original headlines with strategies built on headlines with the company names removed. Within the training window the anonymised headlines did better, which they read as the distraction effect mattering more than look-ahead, especially for large companies. Out of sample, look-ahead is less of a worry, but they note distraction may still occur.

<AtP21LookAhead />

Lopez-Lira and Tang (2023) found GPT-4 headline scores predicted next-day-onwards drift, strongest for small stocks and for negative news, using headlines from after the model's knowledge cutoff. They also report that the strategy's returns fall as LLM adoption rises. That is the same decay you saw in Signals: once many people read the same headlines with the same tool, the edge thins.

<Concepts>

- **Look-ahead bias**: using information in a test that would not have been available at the time. For an LLM it includes what the model memorised in training.
- **Training cutoff**: the date after which the model has seen no text. A clean test uses only data after it.
- **Sharpe ratio**: average return divided by its volatility. A very high value over a short window is more likely luck than skill.

</Concepts>

## 6. Checking an agent in practice

Four checks, cheapest first, each catching something the others miss. Test each tool with plain unit tests: the price band should return 101,650 and 88,350 for a reference of 95,000, every time. Read the trace, not just the answer: did the agent call the tool, or did it type a number that looks like one? Run a fixed set of questions with known answers and have a person score them; FinanceBench is one such set for filings. Last, run it forward in time with timestamps after the model's cutoff, in paper trading, with no money at risk.

<AtP21Eval />

Passing the third check says the agent can answer questions whose answers are known. Only the fourth says anything about next month, and even that is one sample of one regime. Keep a person on every write.

Where does an agent fit on a Vietnamese research desk? Reading a stack of annual reports and surfacing the pages that matter, computing price bands and lot sizes with a tool, and drafting a first summary that a person then checks line by line. Placing the order, or sending the note to a client, stays with a person. The next post in the series, the Investment OS, puts several agents, data, risk limits and execution together and asks who is accountable for each decision.

## 7. Worked case: where to put one check

Say a desk wants an agent to answer one question from a Vietnamese company's annual report: "Did the gross margin move, and by how much?" The agent takes six steps. Nobody has measured it, so the rates below are my assumptions, not data. A person would set them by running the agent on twenty reports with known answers and scoring each step.

**What I would check first.** The weakest step, because a check costs time and money and should go where the failures are. The assumed rates: finding the filing 97%, picking the right page 90%, extracting the number 93%, computing the ratio 99.5% (a tool does it), comparing with last year 92%, drafting 96%. Multiply them and the whole run is right 71.3% of the time. Roughly three answers in ten are wrong even though no single step looks bad.

**The steps.** Say a check catches 80% of wrong steps, never flags a right one, and allows one retry. A step with a check succeeds with probability s + (1 - s) x 0.8 x s. Apply it to one step at a time and multiply again.

```python
steps = [
    ("search filings",      0.97),
    ("pick the right page", 0.90),
    ("extract the number",  0.93),
    ("compute the ratio",   0.995),  # done by a tool, not by the model
    ("compare with last year", 0.92),
    ("draft the summary",   0.96),
]
CATCH = 0.80

def with_check(s, catch=CATCH):
    # first try right, or wrong but caught and the retry is right
    return s + (1 - s) * catch * s

base = np.prod([s for _, s in steps])
print(f"no check: {base:.3f}")
for i, (name, s) in enumerate(steps):
    p = np.prod([with_check(t) if j == i else t for j, (_, t) in enumerate(steps)])
    print(f"check on '{name}': {p:.3f}  (+{p - base:.3f})")
print(f"check on all six: {np.prod([with_check(s) for _, s in steps]):.3f}")
```

**What the result tells you.** Page-picking is the weakest step (0.90), so a check there gains most: 5.7 points. Extracting the number (+4.0) and the year comparison (+4.6) come next. The ratio step gains almost nothing, because the tool had already removed that failure. A check should go where the per-step rate is lowest, and a step that code already makes right needs none. One check on one step still leaves 77%, so a person reads the cited page before the answer goes out.

**What would change my mind.** The 80% catch rate is the weak assumption. A checker that is the same model, reading the same page, often shares the mistake that fooled the first pass, and the gain shrinks. A rule that compares the extracted number with the text on the cited page does better. If a test on known questions shows the page-picking step is really at 97%, the best place moves to the number extraction. Measure the rates before you trust any of the percentages above.

## Key takeaways

- **An agent is a loop**: the model picks a tool, reads the result and picks again; the stop rules and the approvals are ordinary code around it. *(Section 1)*
- **Use the simplest design that works**: one call, a fixed chain or a router are easier to test; choose an agent only when the number of steps cannot be known. *(Section 1)*
- **Tools turn guesses into computed facts**: 95,000 gives 101,650 and 88,350 every time. Split tools into read-only and write, and put approval on writes in code. *(Section 2)*
- **The model sees only what you hand it**: 2,500 of 80,000 tokens in the RAG example; FinanceBench found 81% wrong or refused for GPT-4-Turbo with retrieval. *(Section 3)*
- **Errors multiply**: 95% per step over ten steps is 59.9%; a check that catches 80% lifts it to 88.6%. *(Section 4)*
- **Short tests prove little**: three months of a rising market cannot tell skill from luck, and a model may have read the outcome in training. *(Section 5)*
- **Check in layers**: tools, traces, known questions, then forward in time. *(Section 6)*
- **Put the check where the weak step is**: in a six-step example, one check on the 90% step lifts the run from 71.3% to 77.1%; on the 99.5% tool step it adds 0.3 points. *(Section 7)*

### Một chatbot bịa ra chính sách, và công ty phải trả tiền

Năm 2022, hành khách Jake Moffatt hỏi chatbot trên website Air Canada về vé giảm giá cho người đi viếng tang, sau khi bà của anh mất. Chatbot bảo anh cứ mua vé giá đầy đủ rồi xin giảm giá sau. Chính sách thật của Air Canada không cho phép việc đó. Khi anh nộp đơn, hãng từ chối. Anh đưa vụ việc ra tòa xử các khiếu nại nhỏ ở British Columbia.

Air Canada cãi rằng hãng không chịu trách nhiệm về lời chatbot nói. Tòa không đồng ý. Tháng 2/2024 tòa buộc hãng bồi thường hơn 650 đô la Canada, cộng các khoản phí thông thường. Số tiền nhỏ. Nhưng công ty vẫn phải nhận câu mà model của mình viết ra.

Một nhóm giao dịch sẽ gặp đúng khoảnh khắc này, với số tiền lớn hơn. Một LLM đọc báo cáo, viết "doanh thu tăng 12%", và một analyst chép vào ghi chú. Không ai kiểm con số 12%. Bài này nói về phần khung quanh model giúp việc kiểm tra đó làm được. Có bốn phần:

1. **Agent là gì**: một vòng lặp, không phải một model thông minh hơn.
2. **Tool**: code mà model có thể gọi, để nó khỏi tự tính toán hay nhớ giá từ trí nhớ.
3. **Truy xuất và bộ nhớ**: model được nhìn thấy gì, và vì sao không bao giờ là cả báo cáo.
4. **Bằng chứng**: lỗi dồn lại qua các bước ra sao, và cách kiểm thử agent mà không tự lừa mình.

<Callout type="note" title="Tóm tắt nhanh">

LLM agent là một model nằm trong vòng lặp: chọn tool, đọc kết quả, chọn tiếp cho tới khi trả lời. Workflow cố định và agent khác nhau ở chỗ ai chọn bước kế tiếp, và loại đơn giản nhất làm được việc là loại đúng. Tool biến phỏng đoán thành sự thật được tính ra; truy xuất đưa cho model vài mảnh của tài liệu (FinanceBench thấy GPT-4-Turbo kèm truy xuất trả lời sai hoặc từ chối 81% câu hỏi). Lỗi nhân lên qua các bước: mười bước, mỗi bước đúng 95%, chỉ xong đúng 59,9%. Kết quả giao dịch của agent trong các bài báo thường dựa trên bài test rất ngắn, và một LLM có thể đã đọc kết quả trong văn bản huấn luyện. Không điều gì ở đây là lời khuyên đầu tư hay khuyến nghị giao dịch.

</Callout>

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **LLM (mô hình ngôn ngữ lớn)**: model dự đoán đoạn chữ kế tiếp. Nó trả lời từ văn bản nó được huấn luyện và văn bản bạn đưa vào.
- **Agent**: một LLM tự quyết bước kế tiếp, dùng tool, và lặp lại cho tới khi xong việc.
- **Tool**: code thường mà model có thể nhờ chương trình chạy, như tra giá hay máy tính.
- **Context**: toàn bộ chữ model nhìn thấy trong một lần gọi: chỉ dẫn, câu hỏi của bạn, kết quả tool.

</Concepts>

## 1. Agent là một vòng lặp

Nói thẳng trước. Một model chat nhận chữ vào và trả chữ ra, đúng một lần. Agent bọc lần gọi đó trong một vòng lặp. Model nói "tôi muốn chạy tool `get_prices` với các tham số này." Chương trình chạy nó và dán kết quả trở lại context của model. Model đọc kết quả rồi nói làm gì tiếp, cho tới khi nó quyết định trả lời.

Bài "Building effective agents" của Anthropic vạch ranh giới như sau: workflow là "systems where LLMs and tools are orchestrated through predefined code paths", còn agent là "systems where LLMs dynamically direct their own processes and tool usage." Khác biệt là ai chọn bước kế tiếp. Một bài nghiên cứu tên ReAct (Yao và cộng sự, 2022) cho thấy mẫu này từ sớm: xen một dòng suy luận với một hành động, đọc kết quả hành động trả về, rồi suy luận tiếp. Trên hai benchmark tương tác, ALFWorld và WebShop, nó hơn các phương pháp imitation và reinforcement learning lần lượt 34% và 10% tỉ lệ thành công tuyệt đối.

<AtP21Loop />

Vòng lặp có một hệ quả hữu ích. Model không bao giờ chạm vào thế giới. Mọi việc nó làm đều đi qua một tool, nên mọi việc nó làm đều có thể bị code xung quanh giới hạn, ghi log và kiểm thử. Các giới hạn ở khung dưới của hình (số bước, ngân sách, người duyệt trước mọi thao tác ghi) là code thường. Một prompt viết "hãy cẩn thận" thì không phải.

Phần lớn việc không cần vòng lặp. Giả sử bạn muốn tóm tắt một báo cáo: một lần gọi là đủ. Giả sử bạn muốn trích số liệu, đối chiếu với nguồn thứ hai rồi viết lại: một chuỗi cố định làm được, và bạn kiểm thử được từng mắt xích. Một bộ định tuyến chuyển mỗi tiêu đề tới đúng bộ xử lý cũng là thiết kế cố định. Lời khuyên của Anthropic là dùng loại đơn giản nhất làm được việc và chỉ thêm tự chủ khi không thể biết trước số bước.

<AtP21Spectrum />

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Workflow**: hệ thống mà code của bạn quyết định thứ tự các bước còn model điền vào từng bước.
- **ReAct**: mẫu thiết kế trong đó model xen một dòng suy luận ngắn với một hành động tool và đọc từng kết quả trước bước kế tiếp.
- **Trace (vết chạy)**: danh sách ghi lại mọi bước agent đã làm: từng lần gọi tool, từng kết quả, từng quyết định.

</Concepts>

## 2. Tool là đôi tay

Hỏi một model "giá trần HOSE là bao nhiêu nếu giá tham chiếu hôm qua là 95.000?" thì nó thường đúng, và đôi khi không. Quy định là biên độ 7% quanh giá tham chiếu với cổ phiếu, theo quy chế giao dịch của HOSE tháng 7/2021 mà báo Người Quan Sát đưa tin. Vậy giá trần là 95.000 x 1,07 = 101.650 và giá sàn là 95.000 x 0,93 = 88.350. Một tool làm phép nhân này bằng code, lần nào cũng như lần nào. Việc của model thu lại còn chọn tool và đọc đáp án.

<AtP21Tools />

Chia tool làm hai nhóm. Tool chỉ đọc (tìm trong báo cáo, lấy giá, tính biên độ) không làm hỏng được gì, nên agent gọi thoải mái. Tool ghi (đặt lệnh, gửi báo cáo dưới tên bạn) thay đổi thế giới, nên mỗi lần gọi phải chờ một người. Việc chờ đó phải là code. Project Vend, mà bạn sẽ gặp ở mục 4, có một tool đổi giá; bài học là không có gì trong code chặn một mức giá tồi.

Hai chi tiết quan trọng trong thực tế. Mô tả tool là một phần của prompt: tên mơ hồ hay tham số khó hiểu khiến model gọi sai, và hướng dẫn của Anthropic nói thiết kế tool đáng được chăm chút như thiết kế prompt. Và kết quả tool đi thẳng vào context, nên một tool trả về 4.000 token bảng thô làm agent mất chỗ để nghĩ. Hãy trả về năm dòng cần thiết.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Tool call (lời gọi tool)**: yêu cầu có cấu trúc từ model để chạy một hàm có tên với các tham số cho trước. Chương trình chạy nó, không phải model.
- **Tool chỉ đọc và tool ghi**: tool chỉ đọc chỉ nhìn; tool ghi thay đổi thứ ở ngoài chương trình, như một lệnh hay một email.
- **Giá tham chiếu**: mức giá mà biên độ ngày của HOSE được đo từ đó; giá trần và giá sàn cách nó 7% lên và xuống.

</Concepts>

## 3. Model được nhìn thấy gì: truy xuất và bộ nhớ

Một báo cáo thường niên dài hàng chục nghìn từ. Giả sử là 60.000 từ. Với khoảng 0,75 từ mỗi token, đó là khoảng 80.000 token. Model chỉ đọc những gì có trong context, và context có giới hạn kích thước. Nên thiết kế thường gặp là retrieval-augmented generation, RAG, do Lewis và cộng sự đưa ra năm 2020: cắt tài liệu thành các đoạn, tìm các đoạn khớp với câu hỏi, và đưa chúng cho model.

Giả sử mỗi đoạn dài 500 token, vậy báo cáo thành 160 đoạn, và bước tìm kiếm giữ năm đoạn đầu. Model giờ đọc 2.500 token, bằng 3,1% báo cáo. Nó trả lời tốt nếu đoạn đúng nằm trong năm đoạn, và tệ nếu không.

<AtP21Rag />

Ba lỗi lặp đi lặp lại. Đoạn đúng xếp thứ sáu. Một bảng bị cắt đôi, nên một dòng số mất cái tiêu đề cho biết đơn vị là triệu đồng hay tỉ đồng. Hoặc model đọc các đoạn rồi vẫn trả lời theo trí nhớ. FinanceBench, một bộ câu hỏi mở sách về các công ty đại chúng, đưa ra con số: các tác giả báo cáo GPT-4-Turbo kèm hệ truy xuất trả lời sai hoặc từ chối 81% số câu hỏi.

Truy xuất cũng có thể làm tràn cửa sổ. Giả sử cửa sổ chứa 128.000 token. Một system prompt 3.000 token, mười kết quả tool mỗi cái 4.000 token, và cả báo cáo 80.000 token cộng lại là 123.000. Còn 5.000. Agent không còn chỗ để nghĩ và không còn chỗ cho kết quả tool kế tiếp.

<AtP21Context />

Vì vậy việc dài giữ bộ nhớ ngoài cửa sổ. Agent ghi kết quả vào một file ghi chú khi làm và đọc lại, còn một kho riêng chứa các báo cáo cũ để nó tìm khi cần. Đây là context engineering trong thực tế: quyết định cái gì được đưa vào, cái gì để ngoài, và cái gì được ghi lại cho lần sau.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **RAG (retrieval-augmented generation)**: tìm trong kho tài liệu các đoạn khớp câu hỏi, rồi đưa cho model để nó trả lời từ đó.
- **Chunk (đoạn)**: một mảnh tài liệu được cắt theo cỡ cố định để tìm kiếm được và nhét vừa context.
- **Context window (cửa sổ context)**: lượng chữ tối đa, tính bằng token, model đọc được trong một lần gọi.
- **Token**: một mẩu chữ nhỏ, thường là một từ hoặc một phần của từ. Giá và giới hạn tính theo token.

</Concepts>

## 4. Lỗi dồn lại qua các bước

Một agent nghiên cứu trả lời một câu hỏi có thể mất mười bước: tìm, đọc, tìm lại, tính, so sánh, viết nháp. Mỗi bước có thể sai nhẹ. Rắc rối là các bước nhân với nhau.

Giả sử mỗi bước đúng 95% và việc cần mười bước liên tiếp. Cả việc đúng 0,95 mũ mười, tức 59,9% số lần. Hai mươi bước thì là 35,8%. Với 99% mỗi bước và hai mươi bước thì là 81,8%. Đây là số học thuần túy, đúng với mọi model: tỉ lệ mỗi bước là bao nhiêu thì chuỗi dài cũng làm nó co lại.

Một bước kiểm sau mỗi bước giúp rất nhiều. Giả sử bước kiểm bắt được 80% bước sai và cho thử lại một lần. Khi đó một bước đúng với xác suất 0,95 + 0,05 x 0,8 x 0,95 = 0,988, và mười bước xong 88,6% số lần. Thử chỉnh số bên dưới.

<AtP21CompoundDemo />

Project Vend của Anthropic là một bản ghi thật về cảnh các bước không được kiểm. Năm 2025 Anthropic và Andon Labs để Claude điều hành một cửa hàng nhỏ ở văn phòng Anthropic tại San Francisco, với tìm web, email, công cụ ghi chú, Slack và khả năng đổi giá. Cửa hàng thua lỗ. Một nhân viên đùa xin một khối tungsten, rồi kéo theo một loạt đơn hàng kim loại, và Claude báo giá mà không tra giá vốn, nên có món bán dưới giá vốn. Khi một nhân viên hỏi về mức giảm 25% cho nhân viên, Claude đáp rằng "our customer base is indeed heavily concentrated among Anthropic employees", nói sẽ bỏ mã giảm giá, rồi vài ngày sau lại đưa ra. Ngày 1/4 nó nói sẽ giao hàng trực tiếp, mặc blazer xanh và cà vạt đỏ. Kết luận của Anthropic: "we would not hire Claudius."

<AtP21Vend />

Mỗi lỗi trong hình có cách sửa thông thường bằng code: giá sàn trong tool giá, quy tắc giảm giá mà model đọc được nhưng không sửa được, một lượt soát vết chạy gắn cờ lời khẳng định không có lần gọi tool nào đứng sau. Không cái nào là một prompt hay hơn.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Lỗi cộng dồn (compounding error)**: khi mỗi bước có một khả năng nhỏ sai, xác suất mọi bước đều đúng co lại với mỗi bước thêm vào.
- **Verifier (bước kiểm)**: một kiểm tra nhìn vào đầu ra của bước, có thể là model khác, một luật, hay một người, và gắn cờ trước khi nó đi tiếp.
- **Guardrail (hàng rào)**: giới hạn được ép bằng code quanh model, như giá sàn, trần số bước hay cổng duyệt.

</Concepts>

## 5. Kiểm thử agent mà không tự lừa mình

Các bài báo multi-agent giao dịch trông rất thuyết phục. TradingAgents (Xiao, Sun, Luo và Wang, 2024) cho các agent ngôn ngữ đóng vai một công ty giao dịch: analyst về cơ bản, tâm lý và kỹ thuật; nhóm bull và bear tranh luận; một trader; một nhóm rủi ro. Bài báo báo cáo Sharpe 8,21 cho Apple, 6,39 cho Google và 5,60 cho Amazon.

Hãy đọc cửa sổ test trước khi đọc bảng. Backtest chạy từ 1/1 đến 29/3/2024, khoảng ba tháng. Một chú thích nói các tác giả chỉ benchmark ba tháng vì chi phí chạy LLM và tool. Họ cũng viết rằng Sharpe cao nhất vượt mức họ kỳ vọng và quy cho việc giai đoạn đó ít nhịp giảm. Ba tháng của một thị trường chủ yếu đi lên không phân biệt được phương pháp tốt với một quý tốt. Các vai là một thiết kế, và bài test không chứng minh thiết kế đó hiệu quả. Bài Thống kê của series giải thích vì sao Sharpe từ một cửa sổ ngắn cần một khoảng sai số rộng.

<AtP21TradingAgents />

Có cái bẫy thứ hai mà chỉ model ngôn ngữ mới có. Một model huấn luyện trên văn bản tới một ngày nào đó đã đọc những gì xảy ra tới ngày đó. Glasserman và Lin (2023) nghiên cứu điều này với điểm tâm lý từ GPT: khi backtest trên các tiêu đề nằm trong cửa sổ huấn luyện, model có thể đã biết câu chuyện kết thúc ra sao (look-ahead bias), và có thể bị nhiễu bởi điều nó biết về một công ty có nêu tên. Họ so sánh chiến lược dựng trên tiêu đề gốc với chiến lược dựng trên tiêu đề đã bỏ tên công ty. Trong cửa sổ huấn luyện, tiêu đề ẩn danh làm tốt hơn, điều họ diễn giải là hiệu ứng nhiễu quan trọng hơn look-ahead, nhất là với công ty lớn. Ngoài mẫu, look-ahead ít đáng lo hơn, nhưng họ lưu ý nhiễu vẫn có thể xảy ra.

<AtP21LookAhead />

Lopez-Lira và Tang (2023) thấy điểm tiêu đề của GPT-4 dự đoán được độ trôi giá từ ngày kế tiếp trở đi, mạnh nhất ở cổ phiếu nhỏ và tin xấu, dùng các tiêu đề sau mốc kiến thức của model. Họ cũng báo cáo lợi suất của chiến lược giảm khi LLM được dùng nhiều hơn. Đó là cùng kiểu phân huỷ bạn đã thấy ở bài Tín hiệu: khi nhiều người đọc cùng tiêu đề với cùng công cụ, lợi thế mỏng đi.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Look-ahead bias**: dùng trong bài test thông tin mà lúc đó chưa có. Với LLM, nó gồm cả những gì model đã nhớ trong huấn luyện.
- **Training cutoff (mốc cắt huấn luyện)**: ngày sau đó model chưa thấy chữ nào. Một bài test sạch chỉ dùng dữ liệu sau mốc này.
- **Sharpe ratio**: lợi suất trung bình chia cho độ biến động của nó. Giá trị rất cao trong một cửa sổ ngắn thường là may mắn hơn là tay nghề.

</Concepts>

## 6. Kiểm tra agent trong thực tế

Bốn lần kiểm, rẻ nhất trước, mỗi lần bắt được thứ các lần khác bỏ sót. Kiểm thử từng tool bằng unit test thường: biên độ giá phải trả 101.650 và 88.350 với tham chiếu 95.000, lần nào cũng vậy. Đọc vết chạy, không chỉ câu trả lời: agent đã gọi tool, hay gõ ra một con số trông giống thế? Chạy một bộ câu hỏi cố định có đáp án sẵn và để người chấm; FinanceBench là một bộ như vậy cho báo cáo tài chính. Cuối cùng, chạy tiến theo thời gian với mốc sau mốc cắt của model, ở dạng giao dịch giả lập, không có tiền thật bị đặt vào.

## 7. Ca thực tế: đặt một bước kiểm ở đâu

Giả sử một nhóm muốn agent trả lời một câu hỏi từ báo cáo thường niên của một công ty Việt Nam: "Biên lợi nhuận gộp có đổi không, đổi bao nhiêu?". Agent đi sáu bước. Chưa ai đo, nên các tỷ lệ dưới đây là giả định của tôi, không phải số liệu. Người làm thật sẽ chạy agent trên hai chục báo cáo có đáp án sẵn và chấm từng bước.

**Tôi sẽ kiểm gì trước.** Bước yếu nhất, vì một bước kiểm tốn thời gian và tiền, nên đặt ở nơi lỗi hay xảy ra. Tỷ lệ giả định: tìm báo cáo 97%, chọn đúng trang 90%, trích số 93%, tính tỷ số 99,5% (do tool tính), so với năm trước 92%, viết tóm tắt 96%. Nhân lại thì cả lượt đúng 71,3%. Cứ mười câu trả lời có khoảng ba câu sai, dù không bước nào trông tệ.

**Các bước.** Giả sử bước kiểm bắt 80% bước sai, không bao giờ báo nhầm bước đúng, và cho thử lại một lần. Một bước có kiểm thành công với xác suất s + (1 - s) x 0,8 x s. Áp cho từng bước một rồi nhân lại.

```python
steps = [
    ("search filings",      0.97),
    ("pick the right page", 0.90),
    ("extract the number",  0.93),
    ("compute the ratio",   0.995),  # done by a tool, not by the model
    ("compare with last year", 0.92),
    ("draft the summary",   0.96),
]
CATCH = 0.80

def with_check(s, catch=CATCH):
    # first try right, or wrong but caught and the retry is right
    return s + (1 - s) * catch * s

base = np.prod([s for _, s in steps])
print(f"no check: {base:.3f}")
for i, (name, s) in enumerate(steps):
    p = np.prod([with_check(t) if j == i else t for j, (_, t) in enumerate(steps)])
    print(f"check on '{name}': {p:.3f}  (+{p - base:.3f})")
print(f"check on all six: {np.prod([with_check(s) for _, s in steps]):.3f}")
```

## Điểm rút ra (Key takeaways)

- **Agent là một vòng lặp**: model chọn tool, đọc kết quả và chọn tiếp; luật dừng và việc duyệt là code thường bọc quanh nó. *(Mục 1)*
- **Dùng thiết kế đơn giản nhất làm được việc**: một lần gọi, chuỗi cố định hay bộ định tuyến dễ kiểm thử hơn; chỉ chọn agent khi không thể biết trước số bước. *(Mục 1)*
- **Tool biến phỏng đoán thành sự thật được tính ra**: 95.000 cho 101.650 và 88.350 lần nào cũng vậy. Chia tool thành chỉ đọc và ghi, và đặt việc duyệt ở các tool ghi bằng code. *(Mục 2)*
- **Model chỉ thấy những gì bạn đưa**: 2.500 trên 80.000 token trong ví dụ RAG; FinanceBench thấy GPT-4-Turbo kèm truy xuất sai hoặc từ chối 81%. *(Mục 3)*
- **Lỗi nhân lên**: 95% mỗi bước qua mười bước là 59,9%; bước kiểm bắt 80% nâng lên 88,6%. *(Mục 4)*
- **Test ngắn chứng minh được ít**: ba tháng của một thị trường đang lên không phân biệt được tay nghề với may mắn, và model có thể đã đọc kết quả trong huấn luyện. *(Mục 5)*
- **Kiểm theo lớp**: tool, vết chạy, câu hỏi đã biết đáp án, rồi chạy tiến theo thời gian. *(Mục 6)*
- **Đặt bước kiểm ở khâu yếu**: trong ví dụ sáu bước, một bước kiểm ở khâu 90% nâng cả lượt từ 71,3% lên 77,1%; ở khâu tool 99,5% chỉ thêm 0,3 điểm. *(Mục 7)*
