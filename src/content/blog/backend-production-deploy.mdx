### The hook: seven out of eight

On 1 August 2012 the trading firm Knight Capital sent millions of unintended orders into the US stock market in about 45 minutes. The SEC's order says it ended with a realised loss of $460 million. The cause was a deploy. Starting on 27 July the team had been putting new code onto eight servers in stages, and one technician did not copy it to one of them. Seven servers ran the new code. The eighth still held an old routine called Power Peg, and the new code reused the flag that used to switch that routine on.

<BeP12Knight />

Two details from the order stay with me. First, nobody reviewed the deploy: "Knight did not have a second technician review this deployment", and no written procedure required one. Second, when people tried to fix it live, they uninstalled the new code from the seven good servers, and the order says plainly that "this action worsened the problem". The three ingredients are all deploy hygiene: a change you cannot verify per server, a flag whose meaning depends on which build reads it, and a rollback nobody had practised.

Your service will not trade stocks, but an assistant can write its Dockerfile in seconds, and the first draft runs. What it leaves out is what Knight lacked: a deploy that checks itself. This post builds that path on the series' clue.api, in six questions:

1. **Where config comes from**, and what stops the boot when a value is wrong.
2. **What a small, non-root image** looks like.
3. **How many processes** one container should run.
4. **What happens when the platform says stop**: signals, draining, the PID 1 trap.
5. **What the three probes ask**, and why one of them must stay dumb.
6. **What a rolling update drops**, with and without all of that, counted by a load loop.

It builds on [post 6](/blog/backend-async-concurrency-workers/) (the worker model) and [post 10](/blog/backend-observability/) (the log lines you will read here). Everything ran on my laptop: Docker 29.8.2 and a throwaway one-node kind cluster running Kubernetes 1.32.2. That is not a production cluster, so treat the absolute numbers as this setup's; the direction is what carries over.

## 1. Config comes from the environment

The code in your image is the same in every environment. What changes is small: the database address, the release name, a warm-up time. The twelve-factor rule for it is strict separation of config from code, with config stored in environment variables. Its litmus test is a good one: could the repository be open-sourced right now without leaking a credential?

`pydantic-settings` turns that into a class. A `BaseSettings` subclass reads its fields from the environment, converts the types, and validates them, so a bad value fails at the first line of the program and not on the first request that needs it. `demo/p12_settings.py`, the whole file:

```python
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    """Everything that changes between environments comes from the environment."""

    model_config = SettingsConfigDict(env_prefix="CLUE_")

    database_url: str  # required: no default, so a missing value stops the boot
    release: str = "dev"
    work_ms: int = Field(default=50, ge=0)
    slow_ms: int = Field(default=2000, ge=0)
    startup_delay_s: float = Field(default=0.0, ge=0)
```

`env_prefix="CLUE_"` means the field `database_url` is read from `CLUE_DATABASE_URL`. The fields with defaults are conveniences. `database_url` has no default on purpose: a secret with a fallback turns "forgot to set it" into "silently wrong". `Field(default=50, ge=0)` adds a rule, so a negative value is rejected too. `p12_app.py` builds `Settings()` at import, which is the point of no return. In Kubernetes the values arrive from two objects. A ConfigMap holds plain settings, a Secret holds the sensitive one, and the Deployment injects both as environment variables with `envFrom`. `demo/p12/k8s/config.yaml`, the whole file:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: clue-api-config
data:
  CLUE_WORK_MS: "50"
  CLUE_STARTUP_DELAY_S: "3"
---
apiVersion: v1
kind: Secret
metadata:
  name: clue-api-secret
type: Opaque
stringData:
  CLUE_DATABASE_URL: "sqlite:///demo-not-a-real-secret.db"
```

A Secret object is only base64 text in a manifest, not encryption, so the value here is a placeholder and a real one never goes into git. The settings object does not care where the variables came from, which is the benefit: the same image runs on a laptop, in CI and in the cluster.

<Callout type="warning" title="The AI habit to break">
Ask an assistant for a "production-ready config" and you often get `DATABASE_URL = "postgresql://admin:admin@localhost/app"` in a module, a `.env` committed with real keys, or `os.getenv("SECRET_KEY", "changeme")`. That last one is the quiet killer: a missing variable now boots the service with a known secret. When you review config, search for every default on a value that should never have one.
</Callout>

## 2. A small image

An image is a frozen folder: Python, your dependencies and your code, packed so it runs the same everywhere. Think of the standard shipping container. The ship, the truck and the crane never ask what is inside; they only need the box to be the agreed shape. A good image is a box of the right shape with nothing extra in it.

<Figure src={heroContainers} alt="A reach stacker lifting a shipping container in a stack at the Port of Onehunga, Auckland" caption="The standard box is the whole trick: any crane, any ship, any truck. An image gives your service the same property for any machine that runs containers." sourceTitle="Wikimedia Commons: Container Stacking, Port Of Onehunga (public domain, Ingolfson)" sourceUrl="https://commons.wikimedia.org/wiki/File:Container_Stacking,_Port_Of_Onehunga.jpg" />

The recipe is a Dockerfile. This one uses two stages: the first installs dependencies with `uv`, the second copies only the result. `demo/p12/Dockerfile`, the whole file:

```dockerfile
# Build the demo from the demo/ folder:  docker build -f p12/Dockerfile -t clue-api:p12 .

# ---- build stage: has uv and the resolver; never ships ----
FROM python:3.13-slim AS build
COPY --from=ghcr.io/astral-sh/uv:0.13.0 /uv /usr/local/bin/uv
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy
WORKDIR /app
COPY p12/pyproject.toml p12/uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project

# ---- runtime stage: Python, the venv, our two files ----
FROM python:3.13-slim
RUN useradd --system --uid 10001 --no-create-home app
WORKDIR /app
COPY --from=build /app/.venv /app/.venv
COPY p12_settings.py p12_app.py ./
ENV PATH="/app/.venv/bin:$PATH" PYTHONUNBUFFERED=1
USER 10001
EXPOSE 8000
# Exec form: uvicorn is PID 1 and receives SIGTERM itself.
CMD ["uvicorn", "p12_app:app", "--host", "0.0.0.0", "--port", "8000"]
```

Read it as five decisions. The build stage holds the `uv` binary and runs `uv sync --frozen --no-dev --no-install-project`: install exactly the versions in `uv.lock`, skip dev tools, and skip the project itself so this layer is cached until the lockfile changes. The runtime stage starts again from a clean `python:3.13-slim` and copies one folder, `/app/.venv`. Your two source files come last, so editing code does not invalidate the dependency layer. `useradd` plus `USER 10001` makes the process a non-root user, so a bug in the app cannot write to the system. And `CMD` is in exec form (a JSON list), a detail that decides whether shutdown works; section 4 shows why.

`clue-api:p12-fat` is the Dockerfile an assistant tends to write first. It works, and it is worth reading for what it does not do. `demo/p12/Dockerfile.fat`, the whole file:

```dockerfile
# The Dockerfile an assistant tends to write first. It works. Do not ship it.
FROM python:3.13
WORKDIR /app
COPY . .
RUN pip install fastapi==0.165.0 "uvicorn[standard]==0.54.0" pydantic-settings

```

The base is the full `python:3.13` image with compilers nobody needs at runtime. `COPY . .` copies the whole folder, including whatever is lying around next to the code, and puts it before the install so every code edit reinstalls everything. There is no `USER`, so it runs as root. And `CMD` is the shell form, which section 4 shows to be the dangerous one.

<Callout type="note" title="A smaller image is a faster deploy">
Every pod that starts on a new node pulls the image first. A rollout that waits on a 1.7 GB pull is a rollout where the new pod is not ready for longer, which is time the old pods have to cover.
</Callout>

## 3. One process per pod

Python runs your async code on one thread in one process. To use more than one core you run more than one process, and `uvicorn --workers 2` does that: a parent that starts and watches two worker processes sharing one listening socket. [Post 6](/blog/backend-async-concurrency-workers/) explains why the worker model matters; here the question is only where to put the processes.

The FastAPI docs answer for clusters: handle replication at the cluster level, with a single uvicorn process per container, because a second process manager inside the container adds complexity the orchestrator already provides. They keep `--workers` for a single server or Docker Compose without a cluster. The capture shows the other thing you pay for in-container workers: the split is not yours to control.

Replicas give you the same parallelism with extras: each pod has its own probes and its own restarts, a rolling update replaces them one at a time, and the Service spreads requests across pods. On a plain VM with no orchestrator, a process manager is the tool, and `gunicorn` supervising uvicorn workers is the usual one; I did not measure that setup here.

## 4. A shutdown is a budget of seconds

When a platform wants to stop your process it sends `SIGTERM`, a polite "please finish up", waits for a while, and then sends `SIGKILL`, which cannot be caught. Graceful shutdown is what you do between the two: stop taking new work, finish the work in hand, release what you hold, exit. Think of a restaurant at closing time. You lock the door, you serve the tables already seated, and then you turn off the lights.

uvicorn already behaves like this on `SIGTERM`. It closes its listening socket, waits for open requests to finish, and then lets FastAPI run the shutdown half of the `lifespan` function, the code after `yield`. `demo/p12_app.py`, the lifespan:

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup: warm things up (pool, caches). uvicorn does not listen until
    # this block finishes, and /readyz stays 503 until the flag is set.
    log.info("startup: warming up for %.1fs (release %s)", settings.startup_delay_s, settings.release)
    await asyncio.sleep(settings.startup_delay_s)
    app.state.ready = True
    log.info("startup: ready")
    yield
    # Shutdown: uvicorn has stopped accepting and waited for open requests.
    app.state.ready = False
    log.info("shutdown: in-flight requests left: %d", inflight)
```

The startup half warms up (a pool, a cache) and flips `app.state.ready`. The shutdown half runs only once uvicorn has drained, so the log line it writes, in-flight requests left, is evidence of how the drain went. To see it, the demo starts the real image, begins a two-second request, and sends the stop signal half a second later (`demo/p12_drain.py`):

### The PID 1 trap

In a container the first process is PID 1, and `SIGTERM` is delivered to it. If PID 1 is a shell that then starts uvicorn, the shell is the one that gets the signal, and a shell does not pass it on. ### In Kubernetes

The kubelet does three things in order: it runs the container's `preStop` hook, sends `SIGTERM` to PID 1, and after `terminationGracePeriodSeconds` (30 by default) sends `SIGKILL`. At the same moment, the control plane starts removing the pod from the Service's list of endpoints. Those two things run in parallel, so for a short window the Service can still send a request to a pod whose server has already stopped listening. A `preStop` sleep keeps the pod serving through that window. It is the first thing in the Deployment's `lifecycle`, shown in full in section 6.

## 5. Three probes, three questions

A probe is a check the kubelet runs on a container on a schedule. Kubernetes has three, and they are easy to mix up because they look the same in YAML: an HTTP path, a port, a period. What differs is what Kubernetes does when one fails. The startup probe says whether the app has finished booting, and until it succeeds the other two are not run. The readiness probe says whether traffic should come here right now. The liveness probe says whether the container is stuck and should be restarted.

The demo gives them two endpoints, and keeps each answer honest. `demo/p12_app.py`:

```python
@app.get("/livez")
async def livez() -> dict:
    # Liveness: "is this process stuck?" Never check dependencies here.
    return {"alive": True}


@app.get("/readyz")
async def readyz(response: Response) -> dict:
    # Readiness: "should traffic come here right now?"
    if not app.state.ready:
        response.status_code = 503
    return {"ready": app.state.ready}
```

`/livez` answers "the event loop can still run a function", and nothing else. `/readyz` reads the flag the lifespan set after warm-up. The Deployment wires them up (these lines are the end of `demo/p12/k8s/deploy-graceful.yaml`):

```yaml
          startupProbe:
            httpGet:
              path: /livez
              port: 8000
            periodSeconds: 1
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8000
            periodSeconds: 1
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /livez
              port: 8000
            periodSeconds: 10
            failureThreshold: 3
          lifecycle:
            preStop:
              sleep:
                seconds: 5
```

The startup probe uses `/livez` with a 30 second budget (`failureThreshold` times `periodSeconds`); it keeps the liveness check from killing a slow-booting pod. The readiness probe runs every second for the whole life of the pod. To see what each does, the demo has two buttons: `/debug/unready` flips the flag (a dependency "went away"), and `/debug/hang` blocks the event loop with a sleep.

The rule that follows is the one AI-written manifests break. Readiness may look at dependencies, because "not ready" only takes a pod out of rotation. Liveness must not, because "not alive" restarts it. If `/livez` checked the database, a short database outage would restart every pod at once, which turns a blip into an outage with a cold start in the middle.

## 6. Roll out and count

A rolling update replaces pods a few at a time. Whether it drops requests depends on when Kubernetes believes a new pod can take traffic, and when it believes an old one is gone. The demo measures it. `demo/p12_load.py` sends 20 requests per second, each on a new connection with a 3 second timeout, and counts what a caller would see. The function that does it:

```python
async def one(client: httpx.AsyncClient, url: str, t0: float, out: dict) -> None:
    second = int(time.monotonic() - t0)
    try:
        r = await client.get(url)
        if r.status_code == 200:
            out["ok"] += 1
            out["releases"][r.json()["release"]] += 1
        else:
            out["errors"][f"HTTP {r.status_code}"] += 1
            out["by_second"][second] += 1
    except httpx.HTTPError as exc:
        out["errors"][type(exc).__name__] += 1
        out["by_second"][second] += 1
```

While it runs, `demo/p12_rollout.py` changes the release with `kubectl set env`, which makes Kubernetes replace every pod. It refuses to run unless `KUBECONFIG` is set and the current context is `kind-p12`, so it can never touch another cluster. First the naive Deployment: no probes, no `preStop`, the default strategy.

## 7. The review habit

Knight's deploy had no check that said "this server is not like the others". Yours can have five, and each one is something this post measured. Run down them when an assistant hands you a Dockerfile and a manifest:

<BeP12Checklist />

| It wrote | Ask | Fix in this post |
|---|---|---|
| A default on a secret, or a config module with real values | What happens when the variable is missing? | `Settings` with a required field (section 1) |
| `FROM python:3.13`, `COPY . .`, no `USER` | How big, who is it running as? | Two stages, `USER 10001` (section 2) |
| `CMD uvicorn ...` or a shell wrapper | Does SIGTERM reach uvicorn? | Exec form, `exec` in scripts (section 4) |
| No probes, or one `/health` for everything | What does Kubernetes do when it fails? | `/livez` dumb, `/readyz` honest (section 5) |
| Default rollout, no `maxUnavailable: 0` | What does a deploy do to capacity? | Readiness + `maxUnavailable: 0` (section 6) |

<Concepts>
- **12-factor config**: settings that differ per environment live in environment variables, never in code, so one build runs everywhere.
- **Multi-stage build**: a Dockerfile with several `FROM` stages where only the last one is shipped, so build tools stay out of the image.
- **PID 1**: the first process in a container. It receives the stop signal, so it has to be the app, not a shell.
- **`SIGTERM` / `SIGKILL`**: a stop request the process can catch and handle, and a kill that it cannot.
- **Graceful shutdown**: stop accepting new work, finish the work in hand, release resources, exit.
- **Lifespan**: FastAPI's startup-and-shutdown function; the code before `yield` runs at boot, the code after it at exit.
- **Liveness / readiness / startup probe**: restart me if stuck; send me traffic only when ready; wait until I finish booting.
- **Rolling update**: replace pods a few at a time so some are always serving.
</Concepts>

## Key takeaways

- Load config from the environment into a validated `Settings` object, give secrets no default, and let a missing value stop the process before it listens.
- Build the image in two stages, run as a non-root user, and write `CMD` in exec form so the app is PID 1 and hears `SIGTERM`.
- In a cluster, scale with replicas, one uvicorn process per pod.
- A rolling update is only zero-downtime if readiness is true: in the demo it took failed requests from 67 to 0.
- Keep liveness dumb and readiness honest, and check them by breaking them on purpose.

3. Why can a liveness probe that checks the database turn a short outage into a long one? (section 5)
4. In the rollout captures, which single change took the failures to zero, and what did the preStop sleep change? (section 6)

## 1. Config đến từ môi trường

Code trong image của bạn giống nhau ở mọi môi trường. Thứ thay đổi chỉ là một ít: địa chỉ database, tên release, thời gian warm-up. Quy tắc twelve-factor cho việc này rất rõ: tách config khỏi code thật sạch, và lưu config trong biến môi trường (environment variable). Phép thử của họ rất hay: ngay lúc này có thể open-source repo mà không lộ credential nào không?

`pydantic-settings` biến quy tắc đó thành một class. Một lớp con của `BaseSettings` đọc field từ môi trường, ép kiểu và kiểm tra hợp lệ, nên giá trị sai sẽ làm chương trình hỏng ngay dòng đầu tiên, chứ không đợi tới request đầu tiên cần nó. `demo/p12_settings.py`, toàn bộ file:

```python
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    """Everything that changes between environments comes from the environment."""

    model_config = SettingsConfigDict(env_prefix="CLUE_")

    database_url: str  # required: no default, so a missing value stops the boot
    release: str = "dev"
    work_ms: int = Field(default=50, ge=0)
    slow_ms: int = Field(default=2000, ge=0)
    startup_delay_s: float = Field(default=0.0, ge=0)
```

`env_prefix="CLUE_"` nghĩa là field `database_url` được đọc từ `CLUE_DATABASE_URL`. Các field có default chỉ là tiện lợi. `database_url` cố tình không có default: một secret có giá trị dự phòng biến "quên đặt" thành "sai âm thầm". `Field(default=50, ge=0)` thêm một luật, nên giá trị âm cũng bị từ chối. `p12_app.py` tạo `Settings()` ngay lúc import, đó là điểm không quay lại. ## 2. Một image nhỏ

Image là một thư mục đóng băng: Python, dependency và code của bạn, đóng gói để chạy y hệt ở mọi nơi. Hãy nghĩ tới container vận chuyển tiêu chuẩn. Con tàu, chiếc xe tải, cái cần cẩu không bao giờ hỏi bên trong có gì; chúng chỉ cần cái thùng đúng kích cỡ thỏa thuận. Một image tốt là cái thùng đúng kích cỡ, bên trong không có gì thừa.

<Figure src={heroContainers} alt="Một xe nâng container đang nhấc một container trong bãi xếp ở cảng Onehunga, Auckland" caption="Cái thùng tiêu chuẩn là toàn bộ mẹo: cần cẩu nào, tàu nào, xe tải nào cũng dùng được. Công thức là một Dockerfile. File này có hai stage: stage đầu cài dependency bằng `uv`, stage sau chỉ copy kết quả. `demo/p12/Dockerfile`, toàn bộ file:

```dockerfile
# Build the demo from the demo/ folder:  docker build -f p12/Dockerfile -t clue-api:p12 .

# ---- build stage: has uv and the resolver; never ships ----
FROM python:3.13-slim AS build
COPY --from=ghcr.io/astral-sh/uv:0.13.0 /uv /usr/local/bin/uv
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy
WORKDIR /app
COPY p12/pyproject.toml p12/uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project

# ---- runtime stage: Python, the venv, our two files ----
FROM python:3.13-slim
RUN useradd --system --uid 10001 --no-create-home app
WORKDIR /app
COPY --from=build /app/.venv /app/.venv
COPY p12_settings.py p12_app.py ./
ENV PATH="/app/.venv/bin:$PATH" PYTHONUNBUFFERED=1
USER 10001
EXPOSE 8000
# Exec form: uvicorn is PID 1 and receives SIGTERM itself.
CMD ["uvicorn", "p12_app:app", "--host", "0.0.0.0", "--port", "8000"]
```

Đọc nó như năm quyết định. Stage build giữ binary `uv` và chạy `uv sync --frozen --no-dev --no-install-project`: cài đúng các phiên bản trong `uv.lock`, bỏ công cụ dev, và bỏ qua chính project để layer này được cache cho tới khi lockfile đổi. Stage runtime bắt đầu lại từ một `python:3.13-slim` sạch và chỉ copy một thư mục, `/app/.venv`. Hai file nguồn của bạn đặt cuối, nên sửa code không làm hỏng layer dependency. `useradd` cùng `USER 10001` biến process thành user không phải root, nên một lỗi trong app không thể ghi vào hệ thống. Còn `CMD` ở dạng exec (một list JSON), một chi tiết quyết định việc shutdown có chạy hay không; mục 4 sẽ cho thấy vì sao.

## 3. Mỗi pod một process

Python chạy code async của bạn trên một thread trong một process. Muốn dùng nhiều hơn một core thì chạy nhiều hơn một process, và `uvicorn --workers 2` làm đúng việc đó: một process cha khởi động và canh hai process worker dùng chung một socket đang listen. [Bài 6](/blog/backend-async-concurrency-workers/) giải thích vì sao mô hình worker quan trọng; ở đây câu hỏi chỉ là đặt các process ở đâu.

Tài liệu FastAPI trả lời cho cluster: để cluster lo việc nhân bản, mỗi container một process uvicorn, vì một process manager thứ hai bên trong container chỉ thêm phức tạp mà orchestrator đã có sẵn. Họ để dành `--workers` cho trường hợp một server đơn hoặc Docker Compose không có cluster. Capture dưới đây cho thấy cái giá khác của worker trong container: cách chia việc không do bạn quyết.

## 4. Shutdown là một ngân sách giây

Khi nền tảng muốn dừng process của bạn, nó gửi `SIGTERM`, một lời nhắc lịch sự "làm nốt rồi dừng đi", chờ một lúc, rồi gửi `SIGKILL`, thứ không thể bắt được. Graceful shutdown (thoát êm) là những gì bạn làm giữa hai mốc đó: ngừng nhận việc mới, làm nốt việc đang cầm, trả lại tài nguyên đang giữ, rồi thoát. Hãy nghĩ tới nhà hàng giờ đóng cửa. Bạn khóa cửa, phục vụ nốt các bàn đã ngồi, rồi mới tắt đèn.

uvicorn đã cư xử như vậy khi nhận `SIGTERM`. Nó đóng socket đang listen, chờ các request đang mở xong, rồi để FastAPI chạy nửa shutdown của hàm `lifespan`, phần code sau `yield`. `demo/p12_app.py`, hàm lifespan:

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup: warm things up (pool, caches). uvicorn does not listen until
    # this block finishes, and /readyz stays 503 until the flag is set.
    log.info("startup: warming up for %.1fs (release %s)", settings.startup_delay_s, settings.release)
    await asyncio.sleep(settings.startup_delay_s)
    app.state.ready = True
    log.info("startup: ready")
    yield
    # Shutdown: uvicorn has stopped accepting and waited for open requests.
    app.state.ready = False
    log.info("shutdown: in-flight requests left: %d", inflight)
```

Nửa startup làm warm-up (pool, cache) rồi bật `app.state.ready`. Nửa shutdown chỉ chạy khi uvicorn đã xả xong, nên dòng log nó ghi, số request còn dang dở, là bằng chứng cho việc xả diễn ra thế nào. Để xem, demo khởi động image thật, bắt đầu một request kéo dài hai giây, và nửa giây sau gửi lệnh dừng (`demo/p12_drain.py`):

## 5. Ba probe, ba câu hỏi

Probe là một phép kiểm tra kubelet chạy lên container theo lịch. Kubernetes có ba loại, và dễ nhầm vì trong YAML chúng trông y hệt: một đường dẫn HTTP, một port, một chu kỳ. Khác nhau ở chỗ Kubernetes làm gì khi một probe fail. Startup probe cho biết app đã boot xong chưa, và chừng nào nó chưa thành công thì hai loại kia chưa chạy. Readiness probe cho biết lúc này có nên gửi traffic vào đây không. Liveness probe cho biết container có đang kẹt và cần restart không.

Demo cho chúng hai endpoint, và giữ mỗi câu trả lời trung thực. `demo/p12_app.py`:

```python
@app.get("/livez")
async def livez() -> dict:
    # Liveness: "is this process stuck?" Never check dependencies here.
    return {"alive": True}


@app.get("/readyz")
async def readyz(response: Response) -> dict:
    # Readiness: "should traffic come here right now?"
    if not app.state.ready:
        response.status_code = 503
    return {"ready": app.state.ready}
```

`/livez` chỉ trả lời "event loop vẫn chạy được một hàm", và không gì hơn. `/readyz` đọc cái cờ mà lifespan bật sau warm-up. Deployment nối chúng lại (các dòng này là phần cuối của `demo/p12/k8s/deploy-graceful.yaml`):

```yaml
          startupProbe:
            httpGet:
              path: /livez
              port: 8000
            periodSeconds: 1
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8000
            periodSeconds: 1
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /livez
              port: 8000
            periodSeconds: 10
            failureThreshold: 3
          lifecycle:
            preStop:
              sleep:
                seconds: 5
```

Startup probe dùng `/livez` với ngân sách 30 giây (`failureThreshold` nhân `periodSeconds`); nó giữ cho liveness check không giết một pod boot chậm. Readiness probe chạy mỗi giây trong suốt đời pod. Để xem từng loại làm gì, demo có hai "nút bấm": `/debug/unready` lật cái cờ (một dependency "biến mất"), và `/debug/hang` chặn event loop bằng một lệnh sleep.

## 6. Rollout và đếm

Rolling update thay pod từng ít một. Nó có làm rớt request hay không phụ thuộc vào lúc nào Kubernetes tin rằng pod mới nhận được traffic, và lúc nào tin rằng pod cũ đã đi. Demo đo chính điều đó. `demo/p12_load.py` gửi 20 request mỗi giây, mỗi request một connection mới với timeout 3 giây, và đếm những gì người gọi sẽ thấy. Hàm làm việc đó:

```python
async def one(client: httpx.AsyncClient, url: str, t0: float, out: dict) -> None:
    second = int(time.monotonic() - t0)
    try:
        r = await client.get(url)
        if r.status_code == 200:
            out["ok"] += 1
            out["releases"][r.json()["release"]] += 1
        else:
            out["errors"][f"HTTP {r.status_code}"] += 1
            out["by_second"][second] += 1
    except httpx.HTTPError as exc:
        out["errors"][type(exc).__name__] += 1
        out["by_second"][second] += 1
```

Trong lúc nó chạy, `demo/p12_rollout.py` đổi release bằng `kubectl set env`, khiến Kubernetes thay mọi pod. Nó từ chối chạy trừ khi `KUBECONFIG` được đặt và context hiện tại là `kind-p12`, nên không bao giờ chạm vào cluster khác. ## 7. Thói quen review

Lần deploy của Knight không có phép kiểm tra nào nói được "server này không giống mấy server kia". Của bạn có thể có năm phép, và mỗi phép là thứ bài này đã đo. Hãy đi qua chúng khi AI đưa bạn một Dockerfile và một manifest:

| AI viết | Hãy hỏi | Cách sửa trong bài |
|---|---|---|
| Default trên một secret, hoặc module config chứa giá trị thật | Điều gì xảy ra khi biến bị thiếu? | `Settings` với field bắt buộc (mục 1) |
| `FROM python:3.13`, `COPY . .`, không có `USER` | Nặng bao nhiêu, chạy bằng user nào? | Hai stage, `USER 10001` (mục 2) |
| `CMD uvicorn ...` hoặc shell wrapper | SIGTERM có tới uvicorn không? | Dạng exec, `exec` trong script (mục 4) |
| Không có probe, hoặc một `/health` cho mọi thứ | Kubernetes làm gì khi nó fail? | `/livez` đơn giản, `/readyz` trung thực (mục 5) |
| Rollout mặc định, không có `maxUnavailable: 0` | Một lần deploy làm gì với công suất? | Readiness + `maxUnavailable: 0` (mục 6) |

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">
- **12-factor config**: các setting khác nhau theo môi trường nằm trong biến môi trường, không bao giờ trong code, để một bản build chạy ở mọi nơi.
- **Multi-stage build**: Dockerfile có nhiều stage `FROM` mà chỉ stage cuối được ship, để công cụ build không lọt vào image.
- **PID 1**: process đầu tiên trong container. Nó nhận signal dừng, nên phải là chính app chứ không phải shell.
- **`SIGTERM` / `SIGKILL`**: một yêu cầu dừng mà process bắt và xử lý được, và một lệnh kill mà nó không bắt được.
- **Graceful shutdown (thoát êm)**: ngừng nhận việc mới, làm nốt việc đang cầm, trả tài nguyên, rồi thoát.
- **Lifespan**: hàm startup-và-shutdown của FastAPI; code trước `yield` chạy lúc boot, code sau nó chạy lúc thoát.
- **Liveness / readiness / startup probe**: kẹt thì restart tôi; chỉ gửi traffic khi tôi sẵn sàng; chờ tôi boot xong.
- **Rolling update**: thay pod từng ít một để luôn có pod đang phục vụ.
</Concepts>

## Điểm rút ra (Key takeaways)

- Nạp config từ môi trường vào một object `Settings` có kiểm tra hợp lệ, không cho secret default nào, và để giá trị thiếu dừng process trước khi nó kịp listen.
- Build image hai stage, chạy bằng user không phải root, và viết `CMD` ở dạng exec để app là PID 1 và nghe được `SIGTERM`.
- Trong cluster, mở rộng bằng replica, mỗi pod một process uvicorn.
- Rolling update chỉ không downtime khi readiness nói thật: trong demo nó đưa số request lỗi từ 67 về 0.
- Giữ liveness đơn giản, readiness trung thực, và kiểm chứng chúng bằng cách cố tình phá.
