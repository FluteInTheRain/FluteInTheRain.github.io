### Why clean Go still hits hardware walls and GC spikes

High-level Go hides pointers, page tables, and garbage collection behind ordinary loops and struct values. Under light load that abstraction holds up, while real production traffic exposes where it bends:

- **Discord's two-minute latency spikes.** Discord's Read States service kept tens of millions of cached entries in an in-memory Go LRU cache. Because Go forces a garbage collection cycle at least every two minutes even when heap growth is small, scanning millions of live pointer-heavy cache entries caused predictable CPU and tail-latency spikes until Discord moved that service to Rust.
- **Uber reclaiming ~70,000 CPU cores across 30 services.** Microservices running with default `GOGC=100` inside containers with plenty of spare RAM burned up to 25% of total CPU inside `runtime.scanobject`. Dynamically scaling GC targets against container memory headroom recovered tens of thousands of cores, which helped motivate `GOMEMLIMIT` in Go 1.19.
- **Linux RSS surprises between Go 1.12 and Go 1.15.** When Go switched Linux memory release from `MADV_DONTNEED` to lazy `MADV_FREE`, freed heap spans stayed counted in process `RSS` until the kernel faced memory pressure. Kubernetes dashboards reported rising memory even while Go's heap sat mostly empty, so Go 1.16 restored `MADV_DONTNEED` as the default.

Five hardware and runtime layers sit between a Go loop and the container limits around it:

1. **CPU caches, false sharing, and instruction parallelism:** why memory layout and data dependencies govern loop speed before arithmetic does.
2. **Struct alignment and padding:** how field ordering shrinks memory footprint and cuts cache-line traffic.
3. **Stack vs. heap, escape analysis, inlining, and BCE:** reading `-gcflags="-m=2"` and `-d=ssa/check_bce/debug=1"` on real code, including our `Todo` service.
4. **Virtual memory (`VSS` vs. `RSS`), `madvise`, and Go's 3-tier allocator:** how `mcache`, `mcentral`, and `mheap` separate `scan` and `noscan` memory.
5. **Tri-color GC, `GOGC`, and `GOMEMLIMIT`:** how concurrent marking stays safe under mutation and how to size container limits without thrashing.

<Callout type="note" title="TL;DR">
Main DRAM is ~100x slower than L1 cache, so pack values contiguously in slices, sort struct fields from largest to smallest to remove padding, and separate per-core counters onto distinct cache lines. Run `go build -gcflags="-m=2 -d=ssa/check_bce/debug=1"` to verify heap escapes, inlining, and bounds checks. In Kubernetes, monitor resident memory (`RSS` via `MADV_DONTNEED`) instead of virtual `VSS`, pair raised `GOGC` with `GOMEMLIMIT` around 80-90% of pod RAM, and cut allocations rather than hugging the limit.
</Callout>

<Concepts>

- **Memory wall**: the widening gap between fast CPU cores and slow main DRAM (~80-100 ns per cold read), meaning tight loops often spend more time waiting for bytes than computing.
- **Cache line**: the fixed 64-byte (x86-64) or 128-byte (Apple Silicon) block copied from DRAM into CPU caches whenever your program reads even 1 byte.
- **Escape analysis**: the compile-time pass deciding whether a Go variable stays on a goroutine's private stack or must live on the shared heap.
- **VSS vs. RSS**: Virtual Set Size (`VSS`) is all address space a process reserved; Resident Set Size (`RSS`) is the physical RAM frames mapped right now.

</Concepts>

## 1. CPU caches, false sharing, and instruction parallelism

Modern CPUs run billions of instructions per second, yet pulling one uncached word from DRAM stalls a core for dozens of nanoseconds, long enough to finish hundreds of arithmetic instructions. Small on-die SRAM caches (`L1`, `L2`, `L3`) and a hardware prefetcher that predicts sequential strides hide most of that gap.

<Figure src={cpuDie} alt="Close-up silicon die photograph of an HP PA-RISC 7000 microprocessor" caption="Most surface area on a real processor die goes to SRAM caches and control logic feeding data to tiny execution units." sourceTitle="Wikimedia Commons: PA-RISC 7000 silicon die" sourceUrl="https://commons.wikimedia.org/wiki/File:HP-HP9000-PARISC-PA7000-CPU-Chip-Closeup-Project-Mustang.jpg" />

| Hardware or system tier | Approximate latency | Relative scale | What it means in Go |
| :--- | :--- | :--- | :--- |
| L1 cache hit (per core) | ~1 ns | 1x | Keep hot loops scanning compact `[]T` values linearly |
| L2 / L3 cache hit | ~4-15 ns | 4-15x | Smaller, tighter structs stay in on-chip cache longer |
| Main DRAM miss | ~80-100 ns | ~100x | Avoid pointer chains (`*A -> *B -> *C`) in tight loops |
| Same-AZ network RPC | ~500 µs - 2 ms | ~1,000,000x | Cut round-trips before micro-tuning nanoseconds |

Whenever Go reads `s[0]` and misses L1, the CPU fetches an entire **cache line** (64 bytes on typical x86-64 servers, 128 bytes on Apple Silicon), bringing neighboring elements along for free. That hardware behavior explains why **spatial locality** (`#91`) shifts throughput between loops that share the same Big-O count.

### Spatial locality, AoS vs. SoA, and unpredictable strides (`#91`)

Here are three comparisons on Go 1.27.1 (Apple M2): summing a `512×512` `int64` matrix row-by-row vs. column-by-column, storing structs as an array (`[]OrderAoS`) vs. separate field slices (`OrderSoA`), and walking a slice vs. chasing pointers down a linked list:

```go
// Row-major walks contiguous 8-byte steps; Col-major jumps 4,096 bytes per step
for r := range 512 {
	for c := range 512 {
		sum += mat[r][c]
	}
}

// Array of Structs (AoS): each 64B struct mixes hot amount with 56B cold metadata
type OrderAoS struct {
	amount int64
	meta   [56]byte
}

// Struct of Arrays (SoA): scanning amounts packs 8 int64 values per 64B line
type OrderSoA struct {
	amounts []int64
	metas   [][56]byte
}
```

Look at `BenchmarkStride_LinkedList-8` in that table: all `500,000` nodes came from one contiguous slice (`make([]listNode, 500_000)`), and Apple M2's wide out-of-order engine hid most of the gap (`661-972 µs` across runs vs. `637-647 µs` for the slice). Once linked-list nodes scatter across random heap pages, every `n = n.next` hop becomes a **non-unit stride** that breaks hardware prefetching and forces serial `~80-100 ns` DRAM waits.

Cache geometry brings hardware-specific surprises too. On a `32 KiB`, 8-way set-associative L1D cache (`64 sets × 64 B = 4 KiB`), stepping by `512` `int64` columns (`4,096 B`) hashes every row into the exact same cache set (**conflict misses** at a **critical stride**), whereas `513` columns spreads across sets. On Apple M2's larger L1 cache, `512` and `513` columns ran nearly identically (`~515 ns/op` vs. `~550 ns/op`), which is why microbenchmarks need verification on production hardware.

### False sharing across CPU cores (`#92`)

Because L1 and L2 belong to individual physical cores, two goroutines on different cores communicate cache updates through coherency protocols (such as MESI) at **cache-line granularity**, never variable granularity. When Goroutine 1 updates `c.a` while Goroutine 2 updates `c.b` on adjacent `atomic.Int64` fields in the same cache line, each write invalidates the other core's copy of that entire line even though there is zero Go data race.

```go
type CountersUnpadded struct {
	a atomic.Int64
	b atomic.Int64 // shares the same cache line as a
}

type CountersPad128 struct {
	a atomic.Int64
	_ [120]byte    // x86-64 64B line needs _ [56]byte; Apple Silicon uses 128B
	b atomic.Int64
}
```

### Instruction-level parallelism and data hazards (`#93`)

Modern cores are **superscalar**: they decode, reorder, and run multiple independent instructions in parallel each cycle. Two hazards stall those pipelines:
- **Control hazards (branches):** unpredictable `if` checks flush speculative pipelines (10-20 cycles lost), although Go's compiler emits branchless `CSEL`/`CMOV` machine instructions for simple conditional updates.
- **Data hazards (dependencies):** if instruction `B` reads what instruction `A` just wrote, the core has to serialize them.

Splitting one sum accumulator (`total += s[i]`) into two independent accumulators (`a += s[i]; b += s[i+1]`) breaks that read-after-write chain so the core runs both additions in parallel:

```go
func sumSingleAccum(s []int64) int64 {
	var total int64
	for i := range s {
		total += s[i] // every iteration waits on the previous total
	}
	return total
}

func sumDualAccum(s []int64) int64 {
	var a, b int64
	i := 0
	for ; i+1 < len(s); i += 2 {
		a += s[i]     // independent dependency chain 1
		b += s[i+1]   // independent dependency chain 2
	}
	if i < len(s) {
		a += s[i]
	}
	return a + b
}
```

<Concepts>

- **Spatial locality**: storing elements read together side by side (`[]T` or Structure of Arrays) so each cache-line fetch brings useful bytes into L1.
- **False sharing**: slowdowns caused when multiple cores write independent variables that share one physical cache line, forcing repeated invalidations.
- **Instruction-level parallelism (ILP)**: a superscalar CPU executing multiple independent instructions per clock cycle when data dependencies allow it.
- **Critical stride / conflict miss**: a stride matching a cache's set spacing so repeated accesses evict each other from the same cache set.

</Concepts>

## 2. Struct alignment and padding

A Go struct often takes more memory than the sum of its fields. On 64-bit CPUs, a 1-byte `bool` or `uint8` fits at any byte offset, a 4-byte `int32` starts on a 4-byte boundary, and an 8-byte `int64`, `float64`, or pointer starts on an 8-byte boundary. To keep every field aligned without splitting a read across two machine words, the compiler inserts hidden **padding** bytes, and **Go never reorders struct fields for you** (`#94`).

<GoP16StructPadding />

Running `unsafe.Sizeof` and `unsafe.Offsetof` on Go 1.27.1 shows how field order affects `Unpadded`, `Padded`, and Post 10's `Todo` struct if you later add an `Archived bool` field:

```go
type Unpadded struct {
	Active bool  // offset 0 (1B) + 7B padding
	ID     int64 // offset 8 (8B)
	Flag   uint8 // offset 16 (1B) + 7B trailing padding = 24 bytes
}

type Padded struct {
	ID     int64 // offset 0 (8B)
	Active bool  // offset 8 (1B)
	Flag   uint8 // offset 9 (1B) + 6B trailing padding = 16 bytes
}

type TodoBad struct {
	Done     bool   // 1B + 7B padding
	ID       int    // 8B
	Archived bool   // 1B + 7B padding
	Title    string // 16B = 40 bytes total
}

type TodoCompact struct {
	Title    string // 16B (header: 8B ptr + 8B len)
	ID       int    // 8B
	Done     bool   // 1B
	Archived bool   // 1B + 6B trailing padding = 32 bytes total
}
```

<Concepts>

- **Data alignment**: placing a $k$-byte field at a memory offset divisible by $k$ (capped at pointer width, 8 bytes on 64-bit CPUs) so the CPU fetches it in one read.
- **Struct padding**: empty bytes inserted by the Go compiler between fields and at the end of a struct to keep every field and adjacent slice item aligned.

</Concepts>

## 3. Stack, heap, escape analysis, inlining, and BCE

In C or C++, you explicitly separate stack locals from `malloc`. In Go, you write `&x` or values naturally and the compiler decides where each variable belongs (`#95`):

- **Goroutine stack:** each goroutine owns a private, contiguous stack (starting at `2 KiB` on 64-bit Linux and macOS) that grows or shrinks as needed. Pushing local variables subtracts from the CPU stack pointer (`SP`); returning moves `SP` back in one instruction with zero locks, zero GC tracking, and high L1 locality.
- **Shared heap:** a process-wide memory pool shared across goroutines (`runtime.mallocgc`). Objects that outlive their declaring frame sit on the heap, so the GC has to trace their pointers and sweep them later.

| Property | Goroutine stack frame | Shared Go heap |
| :--- | :--- | :--- |
| Allocation work | Pointer adjustment on `SP` | Size-class lookup + zeroing + pointer bitmap |
| Cleanup work | Immediate on `return` (`0` GC cost) | Marked & swept later by concurrent GC |
| Concurrency safety | Exclusive to one goroutine (no locks) | Shared across goroutines |
| Effect on GC frequency | Invisible to `GOGC` & `GOMEMLIMIT` | Counts directly toward heap target |

### Escape analysis (`-gcflags="-m=2"`)

Go's escape analyzer enforces two invariants documented in `src/cmd/compile/internal/escape/escape.go`:

<GitHubCode repo="golang/go" path="src/cmd/compile/internal/escape/escape.go" lines="L25-L30" url="https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/escape/escape.go#L25-L30" caption="Exact escape analysis contract in Go 1.27.1: stack allocation is safe only while pointers neither enter the heap nor outlive their frame.">
```go
// Here we analyze functions to determine which Go variables
// (including implicit allocations such as calls to "new" or "make",
// composite literals, etc.) can be allocated on the stack. The two
// key invariants we have to ensure are: (1) pointers to stack objects
// cannot be stored in the heap, and (2) pointers to a stack object
// cannot outlive that object (e.g., because the declaring function
// returned and destroyed the object's stack frame, or its space is
// reused across loop iterations for logically distinct variables).
```
</GitHubCode>

The practical rule is **sharing down stays on the stack; sharing up escapes to the heap**. Passing `&a` down into `sumDown(&a, &b)` keeps `a` and `b` on the caller's stack because the caller outlives `sumDown`. Returning `&z` up from `sumUp(a, b)` forces `z` onto the heap, making `BenchmarkStackVsHeap_Ptr` pay `8 B/op, 1 alloc/op` (`~8.6-11.2 ns/op` vs. `~2.8-3.5 ns/op` for returning `int` by value on Apple M2).

Other common escape triggers include:
- Storing a pointer (or value containing a pointer) in a global variable or sending it over a channel.
- Allocating a dynamic slice whose length is unknown at compile time (`make([]byte, n)`), exceeding the compiler's stack size cap, or overflowing capacity in `append`.
- Capturing a mutated variable in a closure or boxing a concrete value into an `any` / interface parameter.

That interface boxing behavior shows up right inside Post 10's `writeJSON(w http.ResponseWriter, status int, v any)` helper when a handler passes `Todo` by value:

```go
func writeJSON(w http.ResponseWriter, status int, v any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	_ = json.NewEncoder(w).Encode(v)
}

func writeTodo(w http.ResponseWriter, t Todo) {
	writeJSON(w, http.StatusOK, t) // t boxed into v any
}
```

### Inlining (`#97`) and Bounds Check Elimination (BCE)

The first two lines of that `-gcflags="-m=2"` trace show Go's **inlining cost budget of 80**. Small functions (`cost <= 80`) paste into the caller during compilation, dropping call overhead and often keeping values on the caller's stack. Since Go 1.9, **mid-stack inlining** allows inlining functions that call other functions. The standard library uses this via **fast-path / slow-path outlining** inside `internal/sync/mutex.go`:

<GitHubCode repo="golang/go" path="src/internal/sync/mutex.go" lines="L61-L71" url="https://github.com/golang/go/blob/go1.27.1/src/internal/sync/mutex.go#L61-L71" caption="Real Go 1.27.1 stdlib trick: Mutex.Lock outlines lockSlow() so the uncontended fast path stays under the 80-cost inlining budget.">
```go
func (m *Mutex) Lock() {
	// Fast path: grab unlocked mutex.
	if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
		if race.Enabled {
			race.Acquire(unsafe.Pointer(m))
		}
		return
	}
	// Slow path (outlined so that the fast path can be inlined)
	m.lockSlow()
}
```
</GitHubCode>

Adding `-d=ssa/check_bce/debug=1` exposes **Bounds Check Elimination (BCE)** at the same time. Go inserts bounds checks before slice accesses (`if idx >= len(s) { panic }`) unless the SSA optimizer proves the index stays in range. Reslicing a 4-element window and reading `_ = win[3]` once clears all four bounds checks inside the loop:

```go
package bce

func sumEveryFourth(s []int) int {
	var total int
	for i := 0; i+3 < len(s); i += 4 {
		total += s[i] + s[i+1] + s[i+2] + s[i+3] // 4 IsInBounds checks per step
	}
	return total
}

func sumWithBCEHint(s []int) int {
	if len(s) < 4 {
		return 0
	}
	var total int
	for i := 0; i < len(s)-3; i += 4 {
		win := s[i : i+4]
		_ = win[3] // proves length 4 up front -> 0 checks below
		total += win[0] + win[1] + win[2] + win[3]
	}
	return total
}
```

### Three practical ways to cut allocations (`#96`)

1. **Share down in APIs:** `io.Reader` accepts `Read(p []byte)` instead of returning a fresh `[]byte`, letting callers reuse one buffer across thousands of reads.
2. **Watch compiler lookup fast paths:** looking up a map with a `[]byte` longer than 32 bytes via `k := string(key); v = m[k]` allocates a heap string (`26.0 ns/op, 64 B/op, 1 alloc/op` on Go 1.27.1), whereas `v = m[string(key)]` inline triggers Go's zero-copy lookup (`8.1 ns/op, 0 B/op, 0 allocs/op`).
3. **Recycle buffers with `sync.Pool`:** pooling `*bytes.Buffer` pointers across calls cut a 1 KiB response build from `147.8 ns/op, 1024 B/op, 1 alloc/op` to `10.7 ns/op, 0 B/op, 0 allocs/op` on Go 1.27.1. Pool pointer types (`*bytes.Buffer`, because boxing a bare 24-byte `[]byte` header into `any` still allocates), reset buffers before `Put`, and keep in mind that GC clears idle pool items on collection. Full pooling and streaming patterns live in [Go optimization patterns](/blog/go-three-rs-optimization-patterns-streaming-pooling/).

<Concepts>

- **Bounds Check Elimination (BCE)**: an SSA compiler pass removing redundant `index out of range` checks once a dominating length check proves safety.
- **Mid-stack & fast-path inlining**: splitting complex error or contention paths into a separate helper so the tiny fast path fits under Go's 80-node inline budget.
- **`sync.Pool`**: a per-P temporary object cache safe for concurrent reuse that cuts allocation churn while letting GC reclaim entries under memory pressure.

</Concepts>

## 4. Virtual memory (`VSS` vs. `RSS`), `madvise`, and Go's allocator

Processes never touch raw physical DRAM addresses directly. Every Go binary runs inside its own **Virtual Address Space (`VSS`)**, divided into **4 KiB pages** mapped onto physical **DRAM frames (`RSS`)** by the CPU's Memory Management Unit (MMU) and Translation Lookaside Buffer (TLB).

Virtual memory works like airline overbooking: reserving address space via `mmap` assigns address ranges, while the kernel attaches real physical DRAM frames lazily through hardware **page faults** only when your code reads or writes inside each 4 KiB page. On Go 1.27.1, `syscall.Mmap` and `syscall.Getrusage` show that split directly:

<TerminalOutput command="go run vss_rss.go run_vss.go" label="Apple M2 · Go 1.27.1" caption="Reserving 256 MiB via anonymous mmap leaves physical RSS unchanged at 4.1 MiB; touching one byte per 4 KiB page across 64 MiB brings RSS to 68.1 MiB.">
```text

after256: MaxRSS=4.1 MiB  (virtual reserved 256 MiB, untouched)
touch64:  MaxRSS=68.1 MiB  (wrote 1 byte per 4 KiB page across 64 MiB)
```
</TerminalOutput>

Lazy paging explains two common container surprises:
1. **Ignore `VSS` when hunting memory leaks:** virtual reservations can exceed a node's physical RAM without spending a byte of DRAM.
2. **Why `RSS` stays high right after GC sweeps:** after a traffic spike pushes Go's heap to `420 MiB` and GC reclaims garbage back down to `90 MiB`, Go holds freed spans briefly for the next burst before its background **scavenger** goroutine issues **`madvise(MADV_DONTNEED)`** on Linux. That syscall lets the kernel drop backing physical frames right away so container `RSS` (`container_memory_working_set_bytes`) falls back down without shrinking `VSS`.

### Go's 3-tier TCMalloc allocator (`mcache` / `mcentral` / `mheap`)

Sitting atop OS virtual arenas is Go's 3-tier allocator (`src/runtime/malloc.go` and `src/internal/runtime/gc/sizeclasses.go`), built so goroutines rarely contend on a global heap lock:

<GitHubCode repo="golang/go" path="src/runtime/malloc.go" lines="L114-L120" url="https://github.com/golang/go/blob/go1.27.1/src/runtime/malloc.go#L114-L120" caption="Core sizing parameters in Go 1.27.1's src/runtime/malloc.go linking tiny objects, 67 small size classes (up to 32 KiB), 8 KiB runtime pages, and 64 MiB virtual arenas.">
```go

	maxTinySize   = _TinySize
	tinySizeClass = _TinySizeClass
	maxSmallSize  = gc.MaxSmallSize
	pageSize      = 1 << gc.PageShift
	pageMask      = pageSize - 1
```
</GitHubCode>

<GoP16ThreeTierAllocator />

Go splits small allocations into **67 size classes** (`8 B` up to `32 KiB`) across three tiers:
1. **`per-P mcache` (zero locks):** each logical processor `P` owns a private cache of spans for each size class, plus a tiny allocator packing pointer-free sub-16 B values together. Small allocations finish here with no mutexes.
2. **`mcentral` (per-size-class lock):** when `mcache` empties a span, it refills from `mcentral`, which separates **`scan` spans** (objects holding pointers) from **`noscan` spans** (raw data like `[]int64` or `[]byte`). Separating `noscan` spans lets the garbage collector skip tracing pointer-free buffers, which explains why flat value layouts avoid the pointer-graph scans that slowed Discord's LRU cache.
3. **`mheap` (global lock):** manages 8 KiB runtime pages carved from `64 MiB` OS virtual arenas on 64-bit Unix (`4 MiB` on 32-bit and Windows), and handles objects over `32 KiB` directly without touching `mcache`.

<Concepts>

- **On-demand paging (Page Fault)**: a hardware interrupt triggered the first time code reads or writes an unbacked 4 KiB virtual page, prompting the kernel to map a physical RAM frame.
- **`madvise(MADV_DONTNEED)`**: Linux syscall called by Go's background scavenger to release physical RAM frames from idle heap spans back to the OS right away.
- **`scan` vs. `noscan` spans**: allocator buckets keeping pointer-bearing structs apart from raw byte/number slabs so GC skips tracing pointer-free memory.

</Concepts>

## 5. Tri-color concurrent mark-sweep GC and the Hybrid Write Barrier

Go's garbage collector (`src/runtime/mgc.go`) is **concurrent, non-generational, and non-compacting**: it sweeps unused heap blocks while your goroutines keep running and leaves live objects at their original addresses. Think of clearing clutter from an office while staff keep walking between desks:

1. **Mark Setup (brief Stop-The-World):** Go pauses goroutines briefly, turns on the **Hybrid Write Barrier**, and shades root pointers on Stacks and Globals **Grey** (*alive, children not scanned yet*).
2. **Concurrent Marking (~25% background CPU):** application goroutines resume while background GC workers drain Grey objects, shade reachable children Grey, and mark finished objects **Black** (*kept*). If mutators allocate faster than workers can mark, Go triggers **Mark Assist**, forcing the allocating goroutine to scan a share of the heap before getting more memory.
   What if your code links a still-**White** object `D` onto an already-**Black** node (`A.Next = D`) mid-cycle? Because the collector won't revisit Black node `A`, it could sweep live `D` by mistake. Go's **Hybrid Write Barrier** shades both the overwritten target and newly written pointer Grey during marking so live objects stay reachable.
3. **Mark Termination (brief STW) & Lazy Sweep:** a second micro-pause disables the write barrier, and unused **White** slots sweep back to `mcache`/`mcentral` lazily as allocations request space.

<Concepts>

- **Stop-The-World (STW)**: brief synchronization pauses at Mark Setup and Mark Termination to toggle the write barrier safely across all `P`s.
- **Hybrid Write Barrier**: compiler-inserted pointer-write hook active only during concurrent GC marking, shading modified pointer targets Grey so live objects aren't missed.
- **Mark Assist**: backpressure forcing fast-allocating goroutines to perform marking work proportional to their allocations when background markers fall behind.

</Concepts>

## 6. Tuning `GOGC` and `GOMEMLIMIT` safely in Kubernetes

Go exposes two knobs to balance CPU against memory (`#99`):

1. **`GOGC` (default `100`, or `debug.SetGCPercent`):** sets the percentage of **new heap growth** allowed relative to surviving live heap (`HeapTarget = Live × (1 + GOGC/100)`). With `50 MiB` live and `GOGC=100`, Go collects at `100 MiB`. Raising `GOGC=200` raises the trigger to `150 MiB` and roughly halves GC frequency, which is why keeping `GOGC=100` in roomy containers wastes CPU (Uber's 70K-core win). Even with `GOGC=off`, Go forces a collection if two minutes pass without one, the exact two-minute heartbeat that hit Discord's Read States service.
2. **`GOMEMLIMIT` (Go 1.19+ soft limit, or `debug.SetMemoryLimit`):** caps total Go-managed runtime memory (`MemStats.Sys - MemStats.HeapReleased`: heap, stacks, and runtime metadata, excluding binary text, `cgo`, or manual `syscall.Mmap`). It lets you raise `GOGC` (even to `off`) without crossing your pod limit, up to a safeguard ceiling.

<QuoteCard author="Michael Knyszek" role="Go Runtime & GC Team" sourceTitle="Go runtime: 4 years later" sourceUrl="https://go.dev/blog/go1.19-runtime">
The runtime will limit the GC to 50% of total CPU time, even if this means exceeding the memory limit.
</QuoteCard>

Because `GOMEMLIMIT` caps GC at **50% of CPU** rather than stalling your service forever in an infinite collection loop (**GC thrashing**), keep `GOMEMLIMIT` 15-20% below your container's hard cgroup limit to leave room for OS page cache, runtime exclusions, and sudden bursts:

<GoP16GogcGomemlimit />

| Kubernetes pod memory limit | Suggested `GOMEMLIMIT` | `GOGC` strategy | Primary risk to watch |
| :--- | :--- | :--- | :--- |
| Tight (`<= 256 MiB`) | `200MiB` (~80%) | Keep `100` | Live heap >170 MiB causes GC CPU thrashing |
| Standard (`1 GiB`) | `850MiB` (~85%) | `100-200` | OS page cache spikes on heavy file I/O |
| High headroom (`4 GiB`, 200 MiB live) | `3400MiB` (~85%) | `300-500` or `off` | Sudden burst filling >3 GiB live data |

Plugging a `50 MiB` steady live heap inside a `512 MiB` pod into `Target = Live × (1 + GOGC/100)` shows the exact numbers:

| Setting (`Live = 50 MiB`, Pod = `512 MiB`) | Next GC target | Garbage allowed per cycle | Relative GC frequency |
| :--- | :--- | :--- | :--- |
| `GOGC=50`, no limit | `75 MiB` | `25 MiB` | 2x (twice as many cycles as default) |
| `GOGC=100` (default) | `100 MiB` | `50 MiB` | 1x baseline (leaves ~300 MiB unused) |
| `GOGC=400`, `GOMEMLIMIT=400MiB` | `250 MiB` | `200 MiB` | 0.25x (~4x fewer cycles than default) |
| `GOGC=off`, `GOMEMLIMIT=400MiB` | ~`400 MiB` total | ~`340 MiB` headroom | Minimum until live data spikes near limit |

Two container companions belong right next to GC tuning in Kubernetes: Go 1.25+ adjusts `GOMAXPROCS` for container quotas, though CPU limits still trigger Linux **CFS throttling** as covered in [Go in production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/). Once this hardware and GC picture is clear, measure speedups rigorously in [Go benchmarking](/blog/go-observability-metrics-microbenchmarks-benchstat/) and pinpoint hotspots with `pprof` in [Go profiling](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/).

<Concepts>

- **`GOGC`**: target heap growth percentage before the next GC runs (`100` triggers collection when new allocations match surviving live heap).
- **`GOMEMLIMIT`**: soft cap on Go-managed runtime memory (heap + stacks + metadata, excluding `cgo` and OS page cache) that forces earlier GCs near the limit, bounded at 50% CPU.
- **GC thrashing**: tight feedback loop when genuine live objects sit just under `GOMEMLIMIT`, forcing continuous back-to-back collections for tiny gains.

</Concepts>

## Key takeaways

- Keep hot data contiguous in value slices (`[]T` or SoA) and separate per-core counters by cache-line padding (64 B x86-64, 128 B Apple Silicon) or local accumulators so cores don't thrash each other's L1 cache.
- Sort large, high-volume struct fields from largest to smallest to remove interior padding; reordering two 1-byte flags cut `TodoBad` from 40 to 32 bytes and sped up a 2M-element `Unpadded` scan ~2.6x.
- Verify compiler placement with `go build -gcflags="-m=2 -d=ssa/check_bce/debug=1"`: share pointers down instead of returning `&x` up, watch `any` boxing like in `writeJSON`, and let fast-path outlining keep small functions under the 80-node inline budget.
- Measure container memory using physical `RSS` (`MADV_DONTNEED`, default on Linux since Go 1.16) rather than virtual `VSS`, and use `noscan` value types to minimize GC pointer scanning.
- Pair raised `GOGC` with `GOMEMLIMIT` at ~80-85% of pod RAM to trade idle memory for lower GC CPU, while fixing allocation churn before live data pushes GC into the 50% thrashing cap.

### Vì sao code Go gọn gàng vẫn vướng tường phần cứng và giật p99

Code Go bậc cao giấu con trỏ, bảng trang nhớ ảo và garbage collector đằng sau những vòng lặp và struct rất bình thường. Lúc ít tải lớp vỏ ấy chạy êm, nhưng tải production nhanh chóng kéo màn che đó xuống:

- **Cơn giật p99 theo chu kỳ 2 phút ở Discord.** Dịch vụ Read States của Discord giữ hàng chục triệu mục trong một LRU cache viết bằng Go. Vì Go ép chạy GC ít nhất 2 phút một lần kể cả khi heap ít tăng, mỗi đợt quét qua cây con trỏ khổng lồ ấy đều làm CPU và độ trễ đuôi vọt lên đều đặn, buộc họ chuyển dịch vụ đó sang Rust.
- **Uber thu hồi ~70.000 nhân CPU trên 30 microservice.** Chạy mặc định `GOGC=100` trong những container thừa mứa RAM khiến nhiều dịch vụ đốt tới 25% CPU trong `runtime.scanobject`. Khi tự điều chỉnh mục tiêu GC theo đúng phần RAM trống của container, Uber tiết kiệm hàng chục nghìn nhân, góp phần mở đường cho `GOMEMLIMIT` ở Go 1.19.
- **Bẫy RSS trên Linux từ Go 1.12 đến 1.15.** Khi Go chuyển từ `MADV_DONTNEED` sang `MADV_FREE` để trả RAM kiểu lười, các vùng heap đã dọn vẫn nằm nguyên trong chỉ số `RSS` cho tới khi OS thiếu RAM thật. Biểu đồ Kubernetes liên tục báo sắp tràn bộ nhớ dù heap Go đang rỗng, nên tới Go 1.16 đội ngũ runtime phải đưa `MADV_DONTNEED` về lại mặc định.

Giữa một vòng lặp Go và giới hạn container là năm tầng phần cứng và runtime nối tiếp nhau:

1. **Cache CPU, false sharing và song song cấp lệnh (ILP):** vì sao cách xếp byte và phụ thuộc dữ liệu quyết định tốc độ vòng lặp trước cả phép tính.
2. **Căn lề struct và byte đệm (struct alignment & padding):** xếp lại trường sao cho bớt RAM và giảm số dòng cache phải đọc.
3. **Stack vs. Heap, escape analysis, inlining và BCE:** đọc thẳng `-gcflags="-m=2"` và `-d=ssa/check_bce/debug=1"` trên code thật, gồm cả handler `Todo`.
4. **Bộ nhớ ảo (`VSS` vs. `RSS`), `madvise` và bộ cấp phát 3 tầng:** cách `mcache`, `mcentral` và `mheap` tách vùng `scan` với `noscan`.
5. **GC 3 màu, `GOGC` và `GOMEMLIMIT`:** cách rào ghi giữ an toàn khi app vẫn chạy song song và cách đặt ngưỡng pod không bị GC đốt CPU.

<Concepts title="Giải thích nhanh mấy thuật ngữ nền tảng">

- **Bức tường bộ nhớ (Memory wall)**: khoảng cách tốc độ ngày càng doãng rộng giữa nhân CPU cực nhanh và DRAM chậm (~80-100 ns mỗi lần đọc nguội), khiến vòng lặp thường tốn thời gian chờ dữ liệu hơn là tính toán.
- **Cache line**: khối cố định 64 byte (x86-64) hoặc 128 byte (Apple Silicon) được CPU bốc một lần từ DRAM lên cache mỗi khi chương trình chạm dù chỉ 1 byte.
- **Phân tích thoát (Escape analysis)**: pha kiểm tra lúc biên dịch quyết định một biến ở lại stack riêng của goroutine hay phải đẩy ra heap dùng chung.
- **VSS vs. RSS**: Virtual Set Size (`VSS`) là toàn bộ dải địa chỉ ảo tiến trình xin trước; Resident Set Size (`RSS`) mới là số khung RAM vật lý thực sự đang được gắn ở thời điểm đo.

</Concepts>

## 1. Cache CPU, false sharing và song song cấp lệnh

Nhân CPU hiện đại chạy hàng tỷ lệnh mỗi giây, nhưng mỗi lần với ra DRAM nguội lại làm cả nhân đứng đợi hàng chục nano-giây, đủ lâu để thực thi xong hàng trăm phép tính. Để che khoảng trống ấy, trên đế chip luôn có các tầng SRAM siêu nhanh (`L1`, `L2`, `L3`) cùng mạch nạp trước phần cứng (hardware prefetcher) đoán trước bước nhảy tuyến tính.

| Tầng phần cứng / hệ thống | Độ trễ ước lượng | Tỉ lệ nhẩm | Ý nghĩa khi viết Go |
| :--- | :--- | :--- | :--- |
| L1 cache hit (riêng từng nhân) | ~1 ns | 1x | Giữ vòng lặp nóng duyệt tuần tự slice giá trị `[]T` |
| L2 / L3 cache hit | ~4-15 ns | 4-15x | Struct càng gọn càng trụ lâu trong cache trên chip |
| DRAM cache miss | ~80-100 ns | ~100x | Tránh chuỗi con trỏ (`*A -> *B -> *C`) trong vòng lặp nóng |
| RPC nội bộ cùng Availability Zone | ~500 µs - 2 ms | ~1.000.000x | Giảm số vòng gọi mạng trước khi gọt từng nano-giây CPU |

Mỗi lần Go đọc `s[0]` bị hụt L1, CPU bốc nguyên một **cache line** (64 byte trên máy chủ x86-64, 128 byte trên Apple Silicon), kéo theo các phần tử nằm sát bên gần như miễn phí. Quy luật vật lý đó lý giải vì sao **cục bộ không gian (spatial locality)** (`#91`) làm thay đổi hẳn tốc độ giữa các đoạn code có cùng độ phức tạp Big-O.

### Cục bộ không gian, AoS vs. SoA và bước nhảy khó đoán (`#91`)

### False sharing giữa hai nhân CPU (`#92`)

Vì L1 và L2 nằm riêng trên từng nhân vật lý, hai goroutine chạy trên hai nhân khác nhau đồng bộ bộ nhớ đệm thông qua giao thức như MESI ở **mức cả cache line**, không phải từng biến lẻ. Nếu Goroutine 1 tăng `c.a` còn Goroutine 2 tăng `c.b` khi hai biến `atomic.Int64` nằm kề nhau trên cùng một cache line, mỗi lần ghi của nhân này lại hủy sạch cache line bên nhân kia dù code hoàn toàn không có data race trong Go.

```go
type CountersUnpadded struct {
	a atomic.Int64
	b atomic.Int64 // nằm chung một cache line với a
}

type CountersPad128 struct {
	a atomic.Int64
	_ [120]byte    // x86-64 line 64B cần _ [56]byte; Apple Silicon dùng line 128B
	b atomic.Int64
}
```

### Song song cấp lệnh (ILP) và phụ thuộc dữ liệu (`#93`)

Nhân CPU hiện đại là máy **siêu vô hướng (superscalar)**: trong một chu kỳ xung nhịp, nó có thể giải mã và chạy song song nhiều lệnh độc lập. Hai loại rào cản phá thế song song đó:
- **Rào cản điều khiển (control hazard):** nhánh `if` khó đoán khiến pipeline phải xả bỏ các lệnh đoán sai (tốn 10-20 chu kỳ), dù với phép gán có điều kiện đơn giản trình biên dịch Go thường hạ thành lệnh `CSEL`/`CMOV` không rẽ nhánh.
- **Rào cản dữ liệu (data hazard):** nếu lệnh `B` cần đọc biến mà lệnh `A` vừa tính, CPU buộc phải đợi `A` xong trước.

Tách một biến cộng dồn duy nhất (`total += s[i]`) thành hai biến cộng dồn độc lập (`a += s[i]; b += s[i+1]`) cắt đứt chuỗi chờ đọc-sau-ghi để nhân CPU chạy hai phép cộng song song:

```go
func sumSingleAccum(s []int64) int64 {
	var total int64
	for i := range s {
		total += s[i] // mỗi vòng phải đợi kết quả total của vòng trước
	}
	return total
}

func sumDualAccum(s []int64) int64 {
	var a, b int64
	i := 0
	for ; i+1 < len(s); i += 2 {
		a += s[i]     // chuỗi phụ thuộc độc lập 1
		b += s[i+1]   // chuỗi phụ thuộc độc lập 2
	}
	if i < len(s) {
		a += s[i]
	}
	return a + b
}
```

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Cục bộ không gian (Spatial locality)**: xếp các dữ liệu thường đọc nối tiếp nằm sát cạnh nhau trong RAM (`[]T` hoặc Structure of Arrays) để mỗi lần kéo cache line tận dụng tối đa số byte mang lên L1.
- **False sharing**: tụt hiệu năng khi nhiều nhân cùng ghi vào các biến độc lập vô tình nằm chung một cache line vật lý, buộc phần cứng liên tục hủy cache của nhau.
- **Song song cấp lệnh (Instruction-level parallelism, ILP)**: khả năng của CPU siêu vô hướng chạy đồng thời nhiều lệnh trong một chu kỳ khi giữa chúng không có dây chuyền phụ thuộc dữ liệu.
- **Critical stride / conflict miss**: bước nhảy bộ nhớ khớp đúng khoảng chia tập (set) của cache làm các hàng liên tiếp đá lẫn nhau ra khỏi cùng một cache set.

## 2. Căn lề struct và byte đệm

Kích thước một struct trong Go thường lớn hơn tổng kích thước các trường cộng lại. Trên hệ 64-bit, biến 1 byte như `bool` hay `uint8` đặt ở địa chỉ nào cũng được, `int32` muốn địa chỉ chia hết cho 4, còn `int64`, `float64` hay con trỏ đòi địa chỉ chia hết cho 8. Để giữ đúng cam kết đó mà không chẻ đôi một biến qua hai từ nhớ, trình biên dịch chèn thêm các byte **đệm trống (padding)**, và **Go không tự sắp lại thứ tự trường trong struct cho bạn** (`#94`).

## 3. Stack, Heap, Escape Analysis, Inlining và BCE

Trong C hay C++, bạn tự tay phân biệt biến stack với `malloc`. Trong Go, bạn cứ viết `&x` hoặc truyền giá trị bình thường, còn trình biên dịch tự tính xem biến nào đặt ở đâu (`#95`):

- **Stack của goroutine:** mỗi goroutine giữ một vùng nhớ liên tiếp riêng (bắt đầu từ `2 KiB` trên Linux và macOS 64-bit) tự co giãn theo độ sâu hàm gọi. Cấp phát biến cục bộ chỉ là trừ con trỏ stack (`SP`), lúc `return` chỉ cần nhấc `SP` lên, không tốn khóa mutex, không phiền GC theo dõi, lại nằm sẵn rất ấm trên L1 cache.
- **Heap dùng chung:** kho bộ nhớ toàn cục chia sẻ giữa mọi goroutine (`runtime.mallocgc`). Mọi biến sống qua thời điểm hàm kết thúc đều phải ra heap, buộc GC sau đó quét con trỏ và dọn dẹp lại.

| Đặc tính | Stack Frame của Goroutine | Go Heap dùng chung |
| :--- | :--- | :--- |
| Chi phí cấp phát | Dịch con trỏ `SP` | Tra size class + xóa 0 + cập nhật bitmap con trỏ |
| Chi phí thu hồi | Tự sạch ngay khi `return` (`0` tốn GC) | Đợi chu kỳ đánh dấu & quét của GC |
| Tranh chấp đồng thời | Riêng một goroutine (không cần khóa) | Dùng chung toàn tiến trình |
| Áp lực lên GC | Vô hình với `GOGC` & `GOMEMLIMIT` | Tính thẳng vào ngưỡng kích hoạt GC |

Quy tắc thực chiến dễ nhớ nhất là **truyền xuống thì ở stack; trả lên thì ra heap**. Truyền `&a` xuống cho `sumDown(&a, &b)` giữ `a` và `b` yên ổn trên stack của hàm gọi vì hàm gọi còn sống lâu hơn `sumDown`. Trả `&z` ngược lên từ `sumUp(a, b)` ép `z` nhảy ra heap, khiến `BenchmarkStackVsHeap_Ptr` tốn `8 B/op, 1 alloc/op` (`~8,6-11,2 ns/op` so với `~2,8-3,5 ns/op` khi trả thẳng `int` theo giá trị trên Apple M2).

Những tình huống thường gặp khác cũng kéo biến lên heap:
- Gán con trỏ (hoặc struct chứa con trỏ) vào biến toàn cục hoặc đẩy qua channel.
- Tạo slice có độ dài chỉ biết lúc chạy (`make([]byte, n)`), vượt ngưỡng kích thước stack tối đa hoặc làm tràn mảng nền khi `append`.
- Closure bắt giữ biến bị thay đổi, hoặc đóng hộp giá trị vào tham số `any` / interface.

Ta thấy ngay bẫy đóng hộp interface đó trên hàm `writeJSON(w http.ResponseWriter, status int, v any)` của Bài 10 khi handler truyền `Todo` theo giá trị:

```go
	w.WriteHeader(status)
	_ = json.NewEncoder(w).Encode(v)

func writeTodo(w http.ResponseWriter, t Todo) {
	writeJSON(w, http.StatusOK, t) // t bị đóng hộp vào v any
}
```

### Inlining (`#97`) và khử kiểm tra biên BCE

Hai dòng đầu tiên của `-gcflags="-m=2"` cho thấy Go áp một **ngân sách chi phí inline tối đa là 80**. Hàm nào nhỏ gọn (`cost <= 80`) sẽ được dán thẳng thân hàm vào chỗ gọi, vừa bỏ chi phí gọi hàm vừa thường giữ biến nằm trên stack thay vì thoát qua ranh giới hàm. Từ Go 1.9, **mid-stack inlining** cho phép inline cả hàm có gọi hàm con, kỹ thuật mà thư viện chuẩn dùng qua mô hình **tách đường nhanh / đường chậm (fast-path / slow-path outlining)** trong `internal/sync/mutex.go`:

<GitHubCode repo="golang/go" path="src/internal/sync/mutex.go" lines="L61-L71" url="https://github.com/golang/go/blob/go1.27.1/src/internal/sync/mutex.go#L61-L71" caption="Mẹo thật trong stdlib Go 1.27.1: Mutex.Lock tách lockSlow() ra hàm riêng để đường khóa nhanh khi không tranh chấp nằm gọn dưới ngân sách inline 80.">
```go
func (m *Mutex) Lock() {
	// Fast path: grab unlocked mutex.
	if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
		if race.Enabled {
			race.Acquire(unsafe.Pointer(m))
		}
		return
	}
	// Slow path (outlined so that the fast path can be inlined)
	m.lockSlow()
}
```
</GitHubCode>

Kèm thêm cờ `-d=ssa/check_bce/debug=1`, ta soi được luôn **Bounds Check Elimination (BCE)**. Go tự chèn lệnh kiểm tra an toàn trước khi đọc slice (`if idx >= len(s) { panic }`) trừ khi pha SSA chứng minh được chỉ số không thể vượt biên. Tạo cửa sổ 4 phần tử rồi chạm `_ = win[3]` một lần giúp trình biên dịch gỡ hết các bước kiểm tra bên dưới:

```go
package bce

func sumEveryFourth(s []int) int {
	var total int
	for i := 0; i+3 < len(s); i += 4 {
		total += s[i] + s[i+1] + s[i+2] + s[i+3] // 4 lần kiểm tra IsInBounds mỗi bước
	}
	return total
}

func sumWithBCEHint(s []int) int {
	if len(s) < 4 {
		return 0
	}
	var total int
	for i := 0; i < len(s)-3; i += 4 {
		win := s[i : i+4]
		_ = win[3] // chứng minh dài đủ 4 ngay đầu vòng lặp -> 0 kiểm tra bên dưới
		total += win[0] + win[1] + win[2] + win[3]
	}
	return total
}
```

### Ba cách thực tế để giảm cấp phát bộ nhớ (`#96`)

1. **Thiết kế API truyền đệm từ trên xuống:** `io.Reader` nhận `Read(p []byte)` thay vì tạo và trả `[]byte` mới, giúp bên gọi tái sử dụng một buffer duy nhất qua hàng nghìn lượt đọc.
2. **Tận dụng tối ưu tra map của trình biên dịch:** tra một map bằng `[]byte` dài hơn 32 byte qua biến trung gian `k := string(key); v = m[k]` sẽ cấp phát chuỗi trên heap (`26,0 ns/op, 64 B/op, 1 alloc/op` trên Go 1.27.1), còn viết gộp `v = m[string(key)]` kích hoạt đường tra map không cấp phát (`8,1 ns/op, 0 B/op, 0 allocs/op`).
3. **Tái sử dụng buffer qua `sync.Pool`:** dùng pool `*bytes.Buffer` giúp công đoạn dựng buffer 1 KiB giảm từ `147,8 ns/op, 1024 B/op, 1 alloc/op` xuống còn `10,7 ns/op, 0 B/op, 0 allocs/op` trên Go 1.27.1. Nhớ bỏ vào pool kiểu con trỏ (`*bytes.Buffer`, vì đóng hộp header `[]byte` 24 byte vào `any` vẫn phát sinh cấp phát), gọi `Reset()` trước khi `Put`, và hiểu rằng GC sẽ dọn các phần tử rảnh trong pool ở chu kỳ thu gom rác. Phần chuyên sâu về pooling và Three Rs nằm ở [Các mẫu tối ưu Go](/blog/go-three-rs-optimization-patterns-streaming-pooling/).

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Khử kiểm tra biên (BCE, Bounds Check Elimination)**: bước tối ưu trên biểu diễn SSA tự xóa các lệnh kiểm tra vượt chỉ số mảng khi biểu thức khống chế phía trên đã bảo đảm an toàn.
- **Tách fast-path để inline (Fast-path outlining)**: dời phần xử lý chậm ít gặp sang hàm riêng để phần đường nóng giữ kích thước dưới ngưỡng ngân sách 80 node và được inline.
- **`sync.Pool`**: kho tái sử dụng object tạm an toàn cho nhiều goroutine theo từng `P`, giúp cắt giảm cấp phát rác nhưng vẫn cho phép GC thu hồi khi cần RAM.

</Concepts>

## 4. Bộ nhớ ảo (`VSS` vs. `RSS`), `madvise` và bộ cấp phát 3 tầng

Tiến trình không bao giờ chạm thẳng địa chỉ DRAM vật lý. Mỗi binary Go chạy trong một **Không gian địa chỉ ảo (`VSS`)** riêng, chia thành các **trang 4 KiB** và ánh xạ sang **khung DRAM vật lý (`RSS`)** qua bộ dịch địa chỉ MMU và bộ đệm TLB của CPU.

Bộ nhớ ảo hoạt động giống chuyện hãng hàng không bán vượt số ghế: gọi `mmap` xin vùng nhớ mới chỉ là giữ trước số địa chỉ ảo, còn kernel chỉ gắn khung RAM vật lý thật thông qua ngắt phần cứng **page fault** ngay lần đầu chương trình đọc hoặc ghi vào trang 4 KiB đó. Trên Go 1.27.1, `syscall.Mmap` và `syscall.Getrusage` cho thấy ranh giới này rất rõ:

1. **Đừng nhìn `VSS` để săn memory leak:** lượng địa chỉ ảo đăng ký trước có thể lớn hơn cả thanh RAM gắn trên máy mà chưa tốn một byte DRAM nào.
2. **Vì sao `RSS` vẫn cao ngay sau khi GC vừa quét xong:** sau khi đỉnh tải đẩy heap lên `420 MiB` rồi GC dọn về còn `90 MiB` dữ liệu sống, Go giữ lại các span trống một lát đề phòng sắp có đợt tải tiếp, rồi mới để goroutine **scavenger** chạy nền gọi **`madvise(MADV_DONTNEED)`** trên Linux. Lời gọi này báo kernel rút ngay khung RAM vật lý về để `RSS` (`container_memory_working_set_bytes`) hạ xuống mà vẫn giữ nguyên dải ảo `VSS`.

### Bộ cấp phát 3 tầng kiểu TCMalloc (`mcache` / `mcentral` / `mheap`)

Nằm ngay phía trên lớp địa chỉ ảo của OS là bộ cấp phát 3 tầng (`src/runtime/malloc.go` và `src/internal/runtime/gc/sizeclasses.go`), giúp các goroutine xin bộ nhớ nhỏ mà hiếm khi phải giành khóa heap toàn cục:

<GitHubCode repo="golang/go" path="src/runtime/malloc.go" lines="L114-L120" url="https://github.com/golang/go/blob/go1.27.1/src/runtime/malloc.go#L114-L120" caption="Các hằng số nền trong src/runtime/malloc.go của Go 1.27.1 gắn bộ gom biến siêu nhỏ, 67 lớp kích thước (tới 32 KiB), trang runtime 8 KiB và các arena ảo 64 MiB.">
```go

	maxTinySize   = _TinySize
	tinySizeClass = _TinySizeClass
	maxSmallSize  = gc.MaxSmallSize
	pageSize      = 1 << gc.PageShift
	pageMask      = pageSize - 1
```
</GitHubCode>

<GoP16ThreeTierAllocator />

Go chia các cấp phát nhỏ thành **67 lớp kích thước (size classes)** từ `8 B` tới `32 KiB` qua ba tầng:
1. **`per-P mcache` (không khóa):** mỗi processor logic `P` giữ riêng một danh sách span trống theo từng lớp kích thước, kèm bộ gộp tiny allocator cho biến không con trỏ dưới 16 B. Phần lớn cấp phát nhỏ xong ngay tại đây mà không chạm mutex.
2. **`mcentral` (khóa theo lớp cỡ):** khi `mcache` hết chỗ trống, nó xin thêm span từ `mcentral`. Điểm đắt giá là `mcentral` tách hẳn **`scan` span** (chứa con trỏ) khỏi **`noscan` span** (chỉ chứa dữ liệu thuần như `[]int64` hay `[]byte`) để GC bỏ qua hoàn toàn mảng không con trỏ, giúp cấu trúc phẳng tránh được cơn ác mộng quét LRU cache như ở Discord.
3. **`mheap` (khóa toàn cục):** quản lý các trang 8 KiB cắt từ arena ảo `64 MiB` trên Unix 64-bit (`4 MiB` trên Windows và 32-bit), và trực tiếp cấp phát cho các khối lớn hơn `32 KiB` không đi qua `mcache`.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **Gắn trang theo nhu cầu (On-demand paging / Page fault)**: ngắt phần cứng xảy ra lần đầu code chạm vào trang ảo 4 KiB chưa có khung RAM, buộc kernel gắn một khung RAM vật lý lúc đó.
- **`madvise(MADV_DONTNEED)`**: lời gọi hệ thống được scavenger nền của Go dùng trên Linux để trả ngay khung DRAM của vùng heap rảnh cho kernel.
- **Span `scan` vs. `noscan`**: cách chia rạch ròi giữa vùng chứa con trỏ (GC phải duyệt) và vùng thuần số liệu/byte (GC không cần đụng tới).

</Concepts>

## 5. Thuật toán GC 3 màu đồng thời và Hybrid Write Barrier

Bộ thu gom rác trong Go (`src/runtime/mgc.go`) hoạt động **đồng thời, không chia thế hệ (non-generational) và không dời ô nhớ (non-compacting)**, nghĩa là nó dọn rác song song lúc goroutine ứng dụng vẫn chạy và giữ nguyên địa chỉ các object đang sống. Hãy hình dung việc dọn văn phòng ngay giữa giờ nhân viên đi lại làm việc:

1. **Mark Setup (dừng STW cực ngắn):** Go tạm dừng mọi goroutine trong chớp mắt để bật **Hybrid Write Barrier** và tô **Xám** toàn bộ con trỏ gốc trên stack lẫn biến toàn cục (*còn sống, chưa quét hết con*).
2. **Đánh dấu đồng thời (~25% CPU nền):** goroutine app chạy lại bình thường trong khi worker GC lấy dần node Xám, tô Xám các node con nó trỏ tới rồi chốt node cha sang **Đen** (*giữ lại*). Nếu app cấp phát nhanh hơn tốc độ quét nền, Go kích hoạt **Mark Assist**, buộc chính goroutine đang xin RAM phụ quét mark một phần rồi mới được cấp phát tiếp.
   Nhưng lỡ giữa chừng app gán một node còn **Trắng** `D` vào sau một node đã **Đen** (`A.Next = D`) thì sao? Nếu không chặn lại, GC sẽ không quay lại xem node Đen `A` và có thể xóa nhầm `D` đang sống. **Hybrid Write Barrier** tự động tô Xám cả con trỏ mới nối lẫn con trỏ bị ghi đè trong suốt pha mark nên dữ liệu sống luôn được giữ lại.
3. **Mark Termination (dừng STW ngắn) & Quét lười:** một cú dừng ngắn thứ hai tắt rào ghi, rồi các ô còn **Trắng** được trả dần về `mcache`/`mcentral` ngay lúc có lượt cấp phát mới.

Bấm từng bước qua ba màu Trắng-Xám-Đen, tình huống Write Barrier cứu node `D` và bẫy ngưỡng `GOMEMLIMIT` ở trình mô phỏng tương tác bên dưới:

- **Hybrid Write Barrier**: đoạn kiểm tra do trình biên dịch chèn quanh thao tác ghi con trỏ (chỉ kích hoạt lúc GC đang mark), tô Xám các đích bị đổi để bảo toàn đồ thị object sống.
- **Mark Assist**: cơ chế hãm nhịp buộc goroutine cấp phát quá nhanh phải phụ chạy bước đánh dấu tỷ lệ theo lượng RAM nó vừa xin.

## 6. Tinh chỉnh `GOGC` và `GOMEMLIMIT` an toàn trên Kubernetes

Go chỉ đưa ra hai núm chỉnh chính để đánh đổi giữa CPU và RAM (`#99`):

1. **`GOGC` (mặc định `100`, hoặc `debug.SetGCPercent`):** đặt phần trăm **rác mới được phép sinh thêm** so với lượng heap sống sót sau vòng trước (`Target = Live × (1 + GOGC/100)`). Nếu dữ liệu sống là `50 MiB`, `GOGC=100` sẽ đợi tới `100 MiB`. Tăng `GOGC=200` nâng trần lên `150 MiB` và giảm gần nửa số vòng GC, giải thích vì sao để mặc định `100` trong container dư RAM bị tốn CPU oan (câu chuyện 70K nhân ở Uber). Ngay cả khi tắt bằng `GOGC=off`, runtime vẫn ép chạy GC nếu quá 2 phút chưa quét lần nào, đúng chu kỳ 2 phút từng làm Discord giật p99.
2. **`GOMEMLIMIT` (trần mềm từ Go 1.19, hoặc `debug.SetMemoryLimit`):** đặt ngưỡng mềm cho tổng bộ nhớ Go quản lý (`MemStats.Sys - MemStats.HeapReleased`: gồm heap, stack và metadata runtime, không tính phần binary, `cgo` hay `syscall.Mmap` ngoài). Nhờ có trần này bạn mới dám tăng `GOGC` (hoặc đặt `off`) mà không lo pod chết OOM khi tải tăng.

<QuoteCard author="Michael Knyszek" role="Đội ngũ Go Runtime & GC" sourceTitle="Go runtime: 4 years later" sourceUrl="https://go.dev/blog/go1.19-runtime">
Runtime sẽ giới hạn GC ở mức tối đa 50% tổng thời gian CPU, kể cả khi điều đó khiến bộ nhớ vượt qua ngưỡng giới hạn.
</QuoteCard>

Vì `GOMEMLIMIT` khóa trần CPU cho GC ở mức **50%** để tránh ứng dụng treo cứng trong vòng lặp dọn rác vô tận (**GC thrashing**), đừng đặt `GOMEMLIMIT` sát mép giới hạn cgroup của container. Hãy chừa lại 15-20% khoảng thở cho OS page cache, phần ngoài Go runtime và các cú vọt đột ngột:

| Chật (`<= 256 MiB`) | `200MiB` (~80%) | Giữ `100` | Dữ liệu sống >170 MiB đẩy GC quay cuồng đốt CPU |
| Chuẩn (`1 GiB`) | `850MiB` (~85%) | `100-200` | OS page cache phình khi đọc ghi file lớn |
| Dư RAM (`4 GiB`, live 200 MiB) | `3400MiB` (~85%) | `300-500` hoặc `off` | Tải vọt giữ >3 GiB dữ liệu sống vượt trần |

Thay thử một service giữ `50 MiB` dữ liệu sống trong pod `512 MiB` vào công thức `Target = Live × (1 + GOGC/100)`:

| Cấu hình (`Live = 50 MiB`, Pod = `512 MiB`) | Ngưỡng kích GC kế tiếp | Rác mới cho phép mỗi vòng | Tần suất GC tương đối |
| :--- | :--- | :--- | :--- |
| `GOGC=50`, không đặt trần | `75 MiB` | `25 MiB` | 2x (gấp đôi số vòng GC so với mặc định) |
| `GOGC=100` (mặc định) | `100 MiB` | `50 MiB` | 1x, làm mốc (bỏ phí ~300 MiB RAM trống) |
| `GOGC=400`, `GOMEMLIMIT=400MiB` | `250 MiB` | `200 MiB` | 0,25x (~ít vòng GC hơn 4 lần so với mặc định) |
| `GOGC=off`, `GOMEMLIMIT=400MiB` | ~`400 MiB` tổng | ~`340 MiB` khoảng thở | Thấp nhất tới khi dữ liệu sống chạm trần |

Khi đẩy dịch vụ lên Kubernetes, có hai mảnh ghép đi liền với tinh chỉnh GC: cách `GOMAXPROCS` (đã nhận diện container từ Go 1.25+) phối hợp với **CFS CPU throttling** trên Linux nằm ở [Go trên production](/blog/go-production-stdlib-cpu-cache-gc-kubernetes/). Còn để chứng minh tốc độ bằng số liệu chuẩn và lần đúng điểm nóng qua `pprof`, hai bước kế tiếp là [Đo hiệu năng và benchstat](/blog/go-observability-metrics-microbenchmarks-benchstat/) cùng [Profiling Go với pprof](/blog/go-profiling-pprof-flamegraphs-off-cpu-continuous/).

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **`GOGC`**: tỷ lệ phần trăm heap được phép tăng thêm trước khi chạy chu kỳ GC kế tiếp (`100` nghĩa là chờ lượng rác bằng đúng kích thước dữ liệu đang sống).
- **`GOMEMLIMIT`**: ngưỡng bộ nhớ mềm do Go runtime quản lý (heap + stack + metadata, không gồm `cgo` và page cache của OS), ép GC chạy dày hơn khi sát trần nhưng chặn tối đa ở 50% CPU.
- **GC thrashing (GC quay cuồng)**: vòng lặp dọn rác liên hoàn xảy ra khi dữ liệu sống thực sự chiếm sát `GOMEMLIMIT`, khiến GC chạy liên tục mà giải phóng được rất ít RAM.

</Concepts>

## Điểm rút ra (Key takeaways)

- Giữ dữ liệu nóng nằm liền kề trong slice giá trị (`[]T` hoặc SoA) và tách các biến đếm song song sang cache line khác nhau (64 B trên x86-64, 128 B trên Apple Silicon) hoặc dùng biến cục bộ để các nhân không hủy cache của nhau.
- Xếp trường trong các struct lớn từ kích thước lớn xuống nhỏ để bỏ byte đệm thừa; dồn hai biến `bool` xuống cuối rút `TodoBad` từ 40 xuống 32 byte và tăng tốc quét 2 triệu `Unpadded` lên ~2,6 lần.
- Kiểm tra vị trí cấp phát bằng `go build -gcflags="-m=2 -d=ssa/check_bce/debug=1"`: truyền con trỏ xuống dưới thay vì trả `&x` lên trên, để ý trường hợp đóng hộp `any` như trong `writeJSON`, và giữ đường nóng dưới ngân sách 80 node để được inline.
- Theo dõi bộ nhớ container bằng `RSS` vật lý (nhờ `MADV_DONTNEED`, mặc định trên Linux từ Go 1.16) thay vì `VSS`, đồng thời ưu tiên kiểu dữ liệu `noscan` để giảm tải quét con trỏ cho GC.
- Phối hợp tăng `GOGC` cùng `GOMEMLIMIT` ở mức 80-85% RAM pod để tận dụng bộ nhớ trống giảm CPU cho GC, nhưng luôn tối ưu bớt cấp phát rác trước khi dữ liệu sống áp sát trần 50% CPU.
