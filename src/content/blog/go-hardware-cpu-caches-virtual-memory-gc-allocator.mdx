### Three production incidents born in silicon, virtual pages, and GC pacing

High-level Go code reads so smoothly that it is easy to imagine an idealized machine where every slice read, pointer dereference, and memory free happens at constant speed. Real production clusters routinely remind teams otherwise:

- **Discord's pointer-heavy cache tail spikes.** Holding millions of in-memory message pointers forced Go's concurrent collector to inspect huge live pointer graphs periodically, driving multi-millisecond p99 pauses until workloads stripped raw pointers (`noscan`) or moved latency-sensitive caches off pointer trees.
- **Uber reclaiming ~70,000 CPU cores across 30 services.** Microservices defaulting unconditionally to `GOGC=100` on containers with plenty of idle RAM spent up to **25–30% of cluster CPU** running needless garbage-collection cycles on tiny 100 MiB heaps—cutting fleet compute dramatically once pacer targets scaled dynamically against real pod headroom.
- **Kubernetes pods OOMKilled while Go reported 40% free heap.** Teams watching only `runtime.MemStats.HeapAlloc` got blindsided by `cgroup container_memory_working_set_bytes` spikes because freed spans stay mapped in OS RSS temporarily until Go's background scavenger issues `madvise(MADV_DONTNEED)`.

To optimize Go intentionally at Levels 3–5, let's trace the complete vertical stack from CPU pipelines up to Go's garbage collector:

1. **Superscalar CPUs, 64-byte cache lines, and pointer-chasing stalls**: why row-major slice scanning halves latency cleanly compared to strided or linked hops.
2. **OS virtual memory (`VSS` vs. `RSS`), page faults, and `madvise(MADV_DONTNEED)`**: understanding container OOM limits accurately.
3. **Go's 3-tier allocator (`mcache`, `mcentral`, `mheap`) and `noscan` spans**: lock-free per-P size-class allocation up to `32 KB`.
4. **Tri-color concurrent mark-sweep GC and the Hybrid Write Barrier**: keeping STW pauses sub-millisecond while preserving mutated graphs safely.
5. **Tuning `GOGC` and `GOMEMLIMIT` safely**: avoiding the GC CPU death spiral verified against live Go 1.27 `gctrace=1` logs.

<Callout type="note" title="TL;DR">
Main DRAM sits **~100x slower than L1 cache** (`~100 ns` vs `~1 ns`), so pack values sequentially in slices instead of chasing `[]*Node` pointer graphs (`noscan` spans skip GC scanning too!). Inspect **`go build -gcflags="-m=1 -d=ssa/check_bce/debug=1"`** to verify Inlining & Bounds Check Elimination (`_ = win[3]`), ignore `VSS` when hunting Kubernetes memory spikes (`RSS` + `MADV_DONTNEED` govern pod limits), and set **`GOMEMLIMIT`** around 80–90% of container RAM without squeezing live heap until GC thrashes CPU.
</Callout>

<Concepts>

- **64-byte Cache Line**: fixed 64-byte slab copied from DRAM into CPU L1/L2 caches whenever a program reads even 1 byte; neighboring elements inside the same 64 bytes ride along practically free.
- **Pointer chasing**: walking linked lists or `[]*Node` indirections where the CPU cannot compute address `i+1` until DRAM returns pointer `i`, flushing superscalar instruction pipelines.
- **Page Fault (`VSS` vs. `RSS`)**: lazy OS mapping connecting reserved virtual memory ranges (`VSS`) to physical 4 KiB DRAM frames (`RSS`) only upon first write access.
- **Tri-color GC + Hybrid Write Barrier**: Go's concurrent non-compacting mark algorithm painting heap objects White, Grey, and Black alongside brief sub-millisecond pauses.

</Concepts>

## 1. Superscalar CPUs, 64-byte cache lines, and pipeline stalls

Reading a cold cache line from off-chip DDR5 DRAM costs **~100 ns**—long enough for a modern 3.5 GHz Apple M2 core executing 4+ instructions per cycle to finish over **1,000 arithmetic instructions!** Modern silicon bridges that cliff through tiered SRAM caches directly on the die (`L1 ~1 ns`, `L2 ~4 ns`, `L3 ~15 ns`) fed by **64-byte cache lines** and hardware prefetchers predicting linear access strides.

<Figure src={cpuDie} alt="Close-up silicon die photograph of an HP PA-RISC 7000 microprocessor" caption="Look inside real silicon: most surface area around tiny ALUs belongs to on-die SRAM caches and branch prediction logic feeding instructions cleanly." sourceTitle="Wikimedia Commons: PA-RISC 7000 silicon die" sourceUrl="https://commons.wikimedia.org/wiki/File:HP-HP9000-PARISC-PA7000-CPU-Chip-Closeup-Project-Mustang.jpg" />

Watch how **spatial locality** transforms identical Go arithmetic across a `512×512` `int64` matrix (`2 MiB`) right on Apple M2 Go 1.27. Row-major traversal consumes all eight `int64` integers inside every 64-byte cache line; column-major traversal skips `4,096 bytes` every step, throwing away 56 unused bytes from every fetched cache line:

```go
// Row-major walks contiguous 8-byte steps (8 int64s per 64B cache line -> L1 hit!)
for r := 0; r < 512; r++ {
	for c := 0; c < 512; c++ { sum += m[r][c] }
}
// Column-major leaps 4,096 bytes per step, thrashing cache lines -> ~2x slower!
for c := 0; c < 512; c++ {
	for r := 0; r < 512; r++ { sum += m[r][c] }
}
```

Notice two deeper compiler secrets inside that Apple M2 benchmark:
1. **Why pointer chasing ruins superscalar execution:** when looping `[]*Node`, each iteration depends serially on loading `n.Next` before decoding fields. Packed value slices (`[]Node` or parallel Structure-of-Arrays slices) feed Go's hardware prefetcher uninterrupted AND generate **`noscan` spans** so the garbage collector skips scanning them entirely!
2. **Branchless `CSEL` instructions:** sorted vs. unsorted branching matched (`~20.5 µs`) because Go's ARM64/x86-64 SSA backend compiles trivial `if v >= 128 { sum += v }` patterns into branchless conditional moves (`CSEL`/`CMOV`), eliminating branch misprediction flushes completely!

<Concepts>

- **Spatial locality**: storing sequentially accessed fields side-by-side (`[]Order`) so loading element `i` pulls `i+1..i+7` onto CPU L1 cache automatically.
- **Branchless `CSEL` / `CMOV`**: CPU conditional-select machine instructions computing both outcomes and picking without speculative pipeline jumps or misprediction penalties.
- **Structure of Arrays (SoA)**: splitting a fat struct array into parallel tight slices (`[]IDs`, `[]Amounts`) so hot loops scan 1 field without polluting cache lines with cold fields.

</Concepts>

## 2. Go compiler passes (`gcflags`) & napkin math estimator

Before blaming hardware speed, inspect what Go's compiler already removes—or misses—via **`-gcflags="-m=1 -d=ssa/check_bce/debug=1"`**. In hot loops scanning slices stride-by-stride, inserting one **Bounds Check Elimination (`_ = win[3]`)** hint lets Go verify loop limits once at the top instead of emitting four panic checks per step:

```go
func SumEveryFourth(s []int) int {
	var total int
	for i := 0; i+3 < len(s); i += 4 {
		total += s[i] + s[i+1] + s[i+2] + s[i+3] // emits 4 IsInBounds checks inside loop!
	}
	return total
}

func SumWithBCEHint(s []int) int {
	if len(s) < 4 { return 0 }
	var total int
	for i := 0; i < len(s)-3; i += 4 {
		win := s[i : i+4]
		_ = win[3] // proves win[0..3] safe once at top -> zeroes checks inside loop!
		total += win[0] + win[1] + win[2] + win[3]
	}
	return total
}
```

## 3. Virtual memory (`VSS` vs `RSS`), Linux `madvise`, and Go's 3-tier allocator

Operating systems never hand binaries raw physical DRAM chips directly; every process lives inside its own sandboxed **Virtual Address Space (`VSS`)**. Reserving `256 MiB` via `mmap` barely touches physical RAM because Linux and macOS map real **4 KiB DRAM frames (`RSS`)** lazily through OS **Page Faults** only when memory writes occur!

Watch a notorious Kubernetes pitfall explained cleanly below: after a traffic spike pushes Go's Heap to `420 MiB` and concurrent GC collects garbage back down to `90 MiB`, Go **retains clean freed spans briefly in `RSS`** to avoid expensive kernel allocation round-trips on the next request wave—then calls **`madvise(MADV_DONTNEED)`** asynchronously in a background **scavenger** goroutine to drop OS RSS smoothly back toward `110 MiB`:

<Figure src={vmPages} alt="Operating system virtual memory pages mapping dynamically across physical RAM frames" caption="Every Go allocation lives inside virtual address tables mapped lazily onto physical RAM frames in 4 KiB pages on first write." sourceTitle="Wikimedia Commons: Memory virtualization addressable level" sourceUrl="https://commons.wikimedia.org/wiki/File:Memory_virtualization_addressable_level.png" />

<GoHwLinuxRssMadvise />

Directly atop virtual OS arenas sits Go's **TCMalloc-inspired 3-tier allocator** (`src/runtime/malloc.go`). Instead of contending on one giant global heap lock, Go divides sizes into **67 tiny/small classes (`8 B` up to `32 KB`)** managed across:
- **`per-P mcache`** (zero mutex locks! Each active CPU processor slot `P` serves small allocations straight from its private local free lists)
- **`mcentral`** (global per-size-class central lists partitioned into `scan` vs pointer-free `noscan` spans, only touched via mutex when `mcache` empties)
- **`mheap`** (coarse multi-page spans carved from 64 MiB virtual arenas on 64-bit Unix / 4 MiB on Windows)

<Concepts>

- **`per-P mcache`**: fast thread-local span cache bound strictly to one logical processor `P`, allowing normal small Go heap allocations (`<= 32 KB`) with **zero lock contention**.
- **`scan` vs. `noscan` span**: Go splits allocations holding pointers (`scan`) from raw data slices like `[]byte` or `[]int64` (`noscan`), cutting GC marking time dramatically on pointer-free structs.
- **`madvise(MADV_DONTNEED)`**: Linux syscall invoked by Go's background scavenger telling the OS kernel it may reclaim unreferenced backing 4 KiB physical pages cleanly (`RSS` shrinks without changing `VSS`).

</Concepts>

## 4. Tri-color concurrent mark-sweep GC and the Hybrid Write Barrier

Think of collecting heap garbage like decluttering an office building *while staff keep walking between rooms working*:
1. **Mark Setup (brief Stop-The-World ~50 µs):** Go halts goroutines momentarily, switches on the **Hybrid Write Barrier**, and paints root references on Stacks & Globals **Grey** (meaning *"alive, needs children scanned"*).
2. **Concurrent Marking (~25% background CPU):** app goroutines resume full traffic while background GC workers pop Grey objects, scan their outbound pointers to shade reachable children Grey, and turn fully-scanned objects **Black** (kept). Wait—what if a user goroutine wires an already-Black node `A.Next = D` onto a still-White node `D` mid-GC? The Hybrid Write Barrier shades `D` Grey instantly so no live data ever gets swept!
3. **Concurrent Sweep (non-compacting):** remaining **White** slots are marked free lazily without moving living objects around in memory (zero pointer-fixup pauses!).

<Concepts>

- **Stop-The-World (STW)**: micro-pauses (~10–100 µs in modern Go) at Mark Setup and Mark Termination solely to toggle barrier state safely across `GOMAXPROCS`.
- **Hybrid Write Barrier**: Go 1.8+ compiler-inserted check active *only during GC marking*, shading both newly linked pointers and overwritten slots Grey so live objects survive concurrent mutation.
- **Non-compacting mark-sweep**: Go avoids relocating living objects (unlike Java G1/ZGC), relying instead on TCMalloc size classes to maintain tiny fragmentation with microsecond pauses.

</Concepts>

## 5. Tuning `GOGC` and `GOMEMLIMIT` safely in Kubernetes pods

With tri-color internals clear, look at Go's two primary GC knobs in production clusters:

1. **`GOGC` (default `100`):** scales GC frequency proportional to **live heap survival**. If `20 MiB` survives GC, `GOGC=100` waits until heap reaches `20 + 20 * 100% = 40 MiB`. Doubling to `GOGC=200` halves GC CPU cost at the price of 3x peak RAM headroom; leaving it fixed on low-heap/high-RAM containers wastes CPU scanning overly often (which is how Uber reclaimed ~70k cores).
2. **`GOMEMLIMIT` (Go 1.19+ soft total target):** overrides `GOGC` safely upward so high `GOGC=400` or `GOGC=off` workloads run cheap without crossing Kubernetes container OOM ceilings (`container_memory_working_set_bytes`).

<QuoteCard author="Michael Knyszek" role="Go Runtime & GC Lead" sourceTitle="A Guide to the Go Garbage Collector" sourceUrl="https://tip.golang.org/doc/gc-guide">
Because GOMEMLIMIT is a soft memory limit, Go caps GC CPU overhead near 50% rather than hanging infinitely if live retained memory truly exceeds your container limit—making allocation reduction far safer than pushing GOMEMLIMIT right against your OOM ceiling.
</QuoteCard>

<GoEffGcPacingCicd />

| Kubernetes Pod RAM Limit | Recommended `GOMEMLIMIT` | Recommended `GOGC` Strategy | Primary Hazard to Monitor |
| :--- | :--- | :--- | :--- |
| **Tight (`<= 256 MiB`)** | `200MiB` (~80%, reserve OS/stack overhead) | Keep `100` (avoid bursting) | True live cache >170 MiB -> GC CPU thrash |
| **Standard (`1 GiB`)** | `850MiB` (~85%, leaves ~150 MiB buffer) | `100–200` (smooth throughput) | Page cache spikes under large file I/O |
| **High-headroom batch worker (`4 GiB`, live 200 MiB)** | `3400MiB` (`85%`) | Raise to `300–500` or `off` bounded by `GOMEMLIMIT` | Suddenly loading 3 GiB live maps into memory |

To build intuition for the exact trade-off, plug a steady service with **`Live = 50 MiB`** surviving each cycle inside a `512 MiB` pod into Go's pacing formula `Target = Live * (1 + GOGC/100)` capped by `GOMEMLIMIT=400MiB`:

| Setting (`Live = 50 MiB`, Pod = `512 MiB`) | Next GC Trigger Heap | New Garbage Allowed per Cycle | Relative GC Frequency | Production Outcome |
| :--- | :--- | :--- | :--- | :--- |
| **`GOGC=50`, no `GOMEMLIMIT`** | `75 MiB` | `25 MiB` | **4x cycles** | Tiny RAM footprint (~`75 MiB`), highest GC CPU tax |
| **`GOGC=100` (default)** | `100 MiB` | `50 MiB` | **2x cycles** | Safe baseline, wastes ~`300 MiB` of paid idle pod RAM |
| **`GOGC=400`, `GOMEMLIMIT=400MiB`** | `250 MiB` (soft cap `400 MiB`) | `200 MiB` | **0.5x cycles** | **4x fewer GC pauses** using unused RAM safely below pod OOM |
| **`GOGC=off`, `GOMEMLIMIT=400MiB`** | ~`400 MiB` total runtime | ~`340 MiB` (incl. stacks/meta) | Minimum steady rate | Beware sudden burst >`400 MiB` causing rapid back-to-back cycles |

One subtle Kubernetes detail trips up first-time Grafana readers: after Go sweeps freed spans back to `mheap`, Linux containers measure memory via **`container_memory_working_set_bytes`**, which includes OS pages that Go still holds until the background `scvg` scavenger calls **`madvise(..., MADV_DONTNEED)`**. Since Go 1.16+, Go defaults to `MADV_DONTNEED` rather than lazy `MADV_FREE`, so unused pages drop out of container `RSS` eagerly instead of triggering false-alarm Prometheus memory alerts.

<Concepts>

- **`GOGC` (Garbage Collection Target Percentage)**: heap growth ratio before initiating the next GC cycle (`100` = trigger when newly allocated bytes equal surviving live heap).
- **`GOMEMLIMIT` (Soft Memory Limit)**: Go 1.19+ target capping total Go runtime memory (Heap + Stacks + Metadata) around 80–90% of pod limits before thrash protection caps GC CPU at 50%.
- **GC CPU Thrashing**: feedback loop where genuine live objects consume ~95% of `GOMEMLIMIT`, forcing GC cycles to execute back-to-back continuously while freeing negligible bytes.

</Concepts>

### Ba cú vấp sản xuất bắt nguồn từ silicon, trang nhớ ảo và nhịp chạy GC

Code Go đọc qua êm ru dễ làm nhiều người lầm tưởng CPU hay RAM hoạt động đều đặn như nhau ở mọi cấu trúc dữ liệu. Thực tế production thường dạy ngược lại rất phũ phàng:

- **Cơn đau p99 của Discord vì cache đầy con trỏ.** Giữ hàng triệu struct tin nhắn nối nhau qua con trỏ ép bộ thu gom rác đồng thời của Go phải quét đi quét lại cây con trỏ khổng lồ, tạo các đợt khựng p99 nhiều mili-giây cho tới khi tách bỏ con trỏ (`noscan`) hoặc đổi kiến trúc.
- **Uber thu hồi ~70.000 nhân CPU chỉ bằng cách chỉnh nhịp GC.** Các microservice chạy mặc định `GOGC=100` trong những container dư dả RAM lại đốt tới **25–30% CPU toàn cụm** chỉ để quét lặp đi lặp lại đống Heap bé tẹo `100 MiB` — tiết kiệm khổng lồ ngay khi cho mục tiêu GC co giãn theo trần RAM trống thật của pod.
- **Pod Kubernetes chết OOMKill ngay lúc Go báo Heap còn trống tới 40%.** Nhiều team chỉ nhìn `HeapAlloc` nên bị đánh úp bởi biểu đồ `container_memory_working_set_bytes` tăng vọt, quên mất các trang đã giải phóng tạm thời vẫn bám trên RSS của Linux tới khi goroutine scavenger gọi `madvise(MADV_DONTNEED)`.

Để tối ưu hiệu năng sâu ở Tầng 3–5, ta hãy đi xuyên dọc từ nhân chip silicon lên tận bộ thu gom rác của Go:

1. **CPU siêu vô hướng, Cache Line 64-byte và bẫy nhảy con trỏ**: vì sao duyệt slice liền khối nhanh gấp đôi nhảy cột, và câu chuyện lệnh `CSEL` không rẽ nhánh.
2. **Các pha tối ưu của trình biên dịch Go & bảng nhẩm phần cứng**: Inlining, BCE (`_ = win[3]`), và Escape Analysis.
3. **Bộ nhớ ảo Linux (`VSS` vs `RSS`), `madvise(MADV_DONTNEED)` và bộ cấp phát 3 tầng**: cách `mcache`/`mcentral`/`mheap` né lock và bỏ qua vùng `noscan`.
4. **Thuật toán GC 3 màu đồng thời & Hybrid Write Barrier**: giữ dừng STW dưới một phần nghìn giây mà không làm mất object đang sống.
5. **Tinh chỉnh `GOGC` & `GOMEMLIMIT` an toàn trên Kubernetes**: tránh vòng xoáy đốt 50% CPU qua số đo thật `GODEBUG=gctrace=1`.

<Callout type="note" title="Tóm tắt nhanh (TL;DR)">
Truy cập thanh DRAM **chậm hơn ~100 lần so với L1 cache** (`~100 ns` vs `~1 ns`), nên hãy xếp dữ liệu liên tiếp trong slice giá trị `[]T` thay vì `[]*Node` (vừa kích hoạt prefetch L1 vừa thành `noscan` né được quét GC!). Bật **`-gcflags="-m=1 -d=ssa/check_bce/debug=1"`** kiểm tra Inlining & BCE, đo tràn RAM bằng **RSS** (đừng nhìn VSS), và đặt **`GOMEMLIMIT`** tầm 80–90% giới hạn container nhưng đừng để dữ liệu sống thật bám sát trần đó kẻo GC quay cuồng đốt sạch CPU.
</Callout>

<Concepts title="Giải thích nhanh mấy thuật ngữ nền tảng">

- **Cache Line 64-byte**: khối cố định 64 byte được CPU bốc một lần từ DRAM lên L1/L2 mỗi khi chạm tới 1 byte — mọi biến nằm cạnh nhau trong 64 byte đó được đọc ké gần như miễn phí.
- **Nhảy con trỏ (Pointer chasing)**: duyệt danh sách liên kết hoặc mảng con trỏ `[]*Node`, khiến CPU không tính trước được địa chỉ phần tử kế tiếp cho tới khi DRAM trả về, làm tắt nghẽn đường ống lệnh.
- **Page Fault (`VSS` vs `RSS`)**: cơ chế ánh xạ lười của hệ điều hành — chỉ gắn khung 4 KiB RAM vật lý (`RSS`) vào không gian địa chỉ ảo (`VSS`) ngay lần đầu chương trình thực sự ghi vào trang đó.
- **GC 3 màu + Hybrid Write Barrier**: thuật toán đánh dấu đồng thời Trắng/Xám/Đen không dời chỗ ô nhớ, phối hợp rào ghi bảo toàn object sống chỉ tốn pha dừng STW vài chục micro-giây.

</Concepts>

## 1. CPU siêu vô hướng, Cache Line 64-byte và bẫy tắt đường ống lệnh

Một cú với ra thanh DRAM rời bên ngoài tốn **~100 ns** — đủ lâu để một nhân Apple M2 3.5 GHz chạy xong hơn **1.000 phép toán số học**! Chip hiện đại che hố sâu đó bằng các tầng SRAM đệm ngay trên đế chip (`L1 ~1 ns`, `L2 ~4 ns`, `L3 ~15 ns`) tải theo lát **64-byte cache line**, kết hợp mạch nạp trước phần cứng (hardware prefetcher) tự đoán bước nhảy tuyến tính.

<Figure src={cpuDie} alt="Ảnh cận cảnh nhân silicon vi xử lý PA-RISC 7000" caption="Trên bề mặt con chip silicon thật, phần lớn diện tích quanh cụm tính toán dành cho các mảng bộ nhớ đệm SRAM (L1/L2) và mạch đoán nhánh." sourceTitle="Wikimedia Commons: PA-RISC 7000 silicon die" sourceUrl="https://commons.wikimedia.org/wiki/File:HP-HP9000-PARISC-PA7000-CPU-Chip-Closeup-Project-Mustang.jpg" />

Xem sức mạnh của **tính cục bộ không gian** khi cộng cùng một ma trận `512×512` `int64` (`2 MiB`) trên Apple M2 Go 1.27. Duyệt theo hàng dùng trọn 8 số `int64` trên cùng 1 cache line 64 byte; duyệt theo cột nhảy bước `4.096 byte` liên tục vứt đi 56 byte vừa tải khiến thời gian tăng gần gấp đôi:

```go
// Duyệt theo hàng (Row-major): 8 số int64 liên tiếp nằm gọn trong 1 cache line 64B
for r := 0; r < 512; r++ {
	for c := 0; c < 512; c++ { sum += m[r][c] }
}
// Duyệt theo cột (Col-major): nhảy cóc 4.096 byte mỗi bước, làm rụng cache line!
for c := 0; c < 512; c++ {
	for r := 0; r < 512; r++ { sum += m[r][c] }
}
```

Có hai điểm chuyên sâu cực kỳ giá trị nằm sau con số đo kia:
1. **Nhảy con trỏ làm liệt CPU siêu vô hướng & ép GC làm thêm việc:** duyệt `[]*Node` khiến CPU buộc phải đợi đọc xong con trỏ `n.Next` rồi mới đi tiếp. - **Tính cục bộ không gian (Spatial locality)**: xếp dữ liệu hay đọc cùng lúc nằm sát bên nhau trong RAM (`[]Order`) để mỗi lần tải cache line 64B kéo sẵn cả 7 phần tử tiếp theo lên L1.

- **Structure of Arrays (SoA)**: tách mảng struct lớn thành nhiều slice song song theo từng trường (`[]IDs`, `[]Amounts`) để vòng lặp nóng không làm bẩn cache line bằng dữ liệu thừa.

## 2. Soi 3 pha của trình biên dịch Go & bảng tính nhẩm phần cứng

Trước khi nghi ngờ tốc độ runtime, hãy kiểm tra trình biên dịch Go đã tự dọn gì (hoặc còn giữ gì) thông qua cờ **`-gcflags='-m=1 -d=ssa/check_bce/debug=1'`**. Trong vòng lặp duyệt bước cố định, chỉ một dòng gợi ý **Bounds Check Elimination (`_ = win[3]`)** giúp xóa sạch 4 lần kiểm tra vượt mảng thừa bên trong vòng lặp:

```go
func SumEveryFourth(s []int) int {
	var total int
	for i := 0; i+3 < len(s); i += 4 {
		total += s[i] + s[i+1] + s[i+2] + s[i+3] // chèn 4 lần check IsInBounds mỗi bước!
	}
	return total
}

func SumWithBCEHint(s []int) int {
	if len(s) < 4 { return 0 }
	var total int
	for i := 0; i < len(s)-3; i += 4 {
		win := s[i : i+4]
		_ = win[3] // chứng minh trước tới chỉ số 3 -> sạch bóng check biên bên dưới!
		total += win[0] + win[1] + win[2] + win[3]
	}
	return total
}
```

## 3. Bộ nhớ ảo Linux (`VSS` vs `RSS`), `madvise` và 3 tầng cấp phát Heap

Hệ điều hành cấp riêng cho mỗi binary một không gian địa chỉ ảo (`VSS`). Xin cấp `256 MiB` qua `mmap` ban đầu hầu như không tốn DRAM vật lý bởi nhân Linux/macOS chỉ gắn từng trang **4 KiB thật (`RSS`)** thông qua ngắt **Page Fault** ngay lúc code chạm vào dữ liệu!

Đây là lý do khiến nhiều đội vận hành Kubernetes hoảng hốt oan: sau đợt spike kéo Heap lên `420 MiB`, dù GC đã dọn sạch rác về còn `90 MiB` dữ liệu sống, Go vẫn **tạm giữ phần trang trống đó trong `RSS`** một lát đề phòng sắp có đợt tải mới, rồi mới để goroutine **scavenger** chạy ngầm gọi syscall **`madvise(MADV_DONTNEED)`** trả khung RAM vật lý lại cho nhân Linux (kéo RSS về ~`110 MiB`):

- **`per-P mcache`**: nằm riêng trên từng processor logic `P` — cấp phát biến nhỏ **0 cần Mutex lock**!
- **`mcentral`**: danh sách trung tâm theo từng size class, tách rạch ròi **`scan`** (chứa con trỏ) với **`noscan`** (chỉ là dữ liệu thô), chỉ khóa nhẹ lúc `mcache` hết chỗ.
- **`mheap`**: quản lý trang lớn cắt từ các heap arena `64 MB` trên Linux/macOS 64-bit (`4 MB` trên Windows).

- **`per-P mcache`**: kho cấp phát cục bộ gắn riêng cho từng logical processor `P`, giúp các cấp phát Heap nhỏ (`<= 32 KB`) không bao giờ phải tranh Mutex giữa các CPU core.
- **Span `scan` vs. `noscan`**: Go tách vùng nhớ chứa con trỏ (`scan`) khỏi vùng dữ liệu thuần như `[]byte` hay `[]int64` (`noscan`), giảm mạnh tải quét cho GC.
- **`madvise(MADV_DONTNEED)`**: lời gọi hệ thống được goroutine scavenger của Go phát ra để nhân Linux thu hồi lại khung RAM 4 KiB dư thừa mà không cần hủy dải địa chỉ ảo `VSS`.

## 4. Thuật toán GC 3 màu đồng thời & Hybrid Write Barrier

Hãy tưởng tượng dọn dẹp văn phòng *ngay trong lúc nhân viên vẫn đang đi lại làm việc bình thường*:
1. **Mark Setup (dừng STW cực ngắn ~50 µs):** Go tạm dừng chớp mắt để bật **Hybrid Write Barrier** và tô **Xám** toàn bộ điểm neo gốc (Stack & biến toàn cục — nghĩa là *"đã sống nhưng chưa quét hết con cháu"*).
2. **Đánh dấu đồng thời (~25% CPU nền):** app chạy lại bình thường trong khi worker GC bốc từng node Xám ra xem các con trỏ bên trong, tô Xám đám con rồi chuyển node cha sang **Đen** (giữ lại). Còn nếu code app bỗng dưng nối node Trắng `D` vào sau một node đã tô Đen `A.Next = D` ngay giữa chừng? Lớp bảo vệ Write Barrier lập tức tô Xám `D` để đảm bảo object đang sống tuyệt đối không bị thu hồi oan!
3. **Quét đồng thời không dời vùng nhớ (Non-compacting Sweep):** mọi slot còn lại mang màu **Trắng** tự động trả lại danh sách trống trên mspan mà không phải dịch chuyển địa chỉ các object đang sống.

- **Stop-The-World (STW)**: hai điểm dừng cực ngắn (~10–100 µs) đầu và cuối pha đánh dấu chỉ để bật/tắt trạng thái hàng rào ghi đồng bộ trên toàn bộ `GOMAXPROCS`.

## 5. Tinh chỉnh `GOGC` & `GOMEMLIMIT` an toàn trên cụm Kubernetes

Khi đã thông suốt cơ chế quét 3 màu, hai tham số điều khiển nhịp GC mạnh nhất trong production lộ rõ:

1. **`GOGC` (mặc định `100`):** chọn thời điểm kích hoạt vòng lặp kế tiếp theo **tỷ lệ tăng trưởng Heap**. Nếu dữ liệu sống là `20 MiB`, `GOGC=100` đợi chạm `40 MiB` (`20 + 20 * 100%`). Tăng lên `GOGC=200` giảm một nửa công sức CPU cho GC — nhưng ngược lại các container thừa RAM mà để `GOGC=100` sẽ bị GC quét quá dày (đó chính là cơ hội giúp Uber thu hồi ~70.000 nhân CPU).
2. **`GOMEMLIMIT` (trần mềm từ Go 1.19+):** ép GC quét tích cực khi tổng bộ nhớ runtime sắp chạm ngưỡng giới hạn của pod (`container_memory_working_set_bytes`), cho phép nâng `GOGC` lên cao an toàn mà không lo sập OOMKill bất ngờ.

<QuoteCard author="Michael Knyszek" role="Trưởng nhóm Go Runtime & GC" sourceTitle="A Guide to the Go Garbage Collector" sourceUrl="https://tip.golang.org/doc/gc-guide">
Vì GOMEMLIMIT là giới hạn mềm, runtime Go tự hãm trần CPU dành cho GC ở khoảng 50% chứ không treo cứng vĩnh viễn nếu bộ nhớ sống thật vượt quá mức giới hạn — do đó giảm rác cấp phát vẫn an toàn hơn việc đẩy GOMEMLIMIT sát mép OOM.
</QuoteCard>

<GoEffGcPacingCicd />

| Giới hạn RAM Pod Kubernetes | Gợi ý `GOMEMLIMIT` | Chiến lược `GOGC` khuyên dùng | Rủi ro cần theo dõi |
| :--- | :--- | :--- | :--- |
| **Pod nhỏ (`<= 256 MiB`)** | `200MiB` (~80%, chừa phần OS/stack) | Giữ `100` (ưu tiên an toàn tràn RAM) | Cache sống thật >170 MiB -> GC quay cuồng đốt CPU |
| **Chuẩn backend (`1 GiB`)** | `850MiB` (~85%, chừa đệm ~150 MiB) | `100–200` (cân bằng p99 + CPU) | OS page cache tăng cao khi đọc file nặng |
| **Batch worker dư RAM (`4 GiB`, live 200 MiB)** | `3400MiB` (`85%`) | Tăng `300–500` hoặc `off` có `GOMEMLIMIT` bảo vệ | Lệch đột ngột tải lên >3 GiB dữ liệu sống |

Để hình dung rõ con số thực tế, thử thay một service giữ **`Live = 50 MiB`** sau mỗi vòng quét (chạy trong pod `512 MiB`) vào công thức `Target = Live * (1 + GOGC/100)` kèm trần `GOMEMLIMIT=400MiB`:

| Cấu hình (`Live = 50 MiB`, Pod = `512 MiB`) | Ngưỡng kích GC kế tiếp | Rác mới được phép trước khi quét | Tần suất chạy GC | Hệ quả trên Production |
| :--- | :--- | :--- | :--- | :--- |
| **`GOGC=50`, chưa đặt `GOMEMLIMIT`** | `75 MiB` | `25 MiB` | **Dày gấp 4x** | RAM rất nhỏ (~`75 MiB`), nhưng trả thuế CPU cho GC rất nặng |
| **`GOGC=100` (mặc định)** | `100 MiB` | `50 MiB` | **Gấp 2x** | An toàn chuẩn, nhưng bỏ phí ~`300 MiB` RAM nhàn rỗi đã thuê |
| **`GOGC=400`, `GOMEMLIMIT=400MiB`** | `250 MiB` (trần mềm `400 MiB`) | `200 MiB` | **Giảm còn 0.5x** | **Giảm 4 lần số nhịp GC** nhờ tận dụng RAM trống mà vẫn dưới ngưỡng OOM |
| **`GOGC=off`, `GOMEMLIMIT=400MiB`** | ~`400 MiB` tổng runtime | ~`340 MiB` (gồm cả stack/meta) | Tối thiểu ở tải đều | Cẩn thận nếu tải dội lên sát `400 MiB` sẽ kéo GC chạy liên hoàn |

Một chi tiết dễ làm người mới giật mình khi mở Grafana Kubernetes: sau khi GC quét rác xong, chỉ số **`container_memory_working_set_bytes`** chỉ thực sự tụt xuống khi goroutine **`scvg` (scavenger)** chạy nền và gọi xuống Linux **`madvise(..., MADV_DONTNEED)`**. Từ Go 1.16 trở đi, runtime mặc định dùng **`MADV_DONTNEED`** (thay vì `MADV_FREE` trả chậm như trước) nên page RAM thừa được thu hồi khỏi `RSS` rất nhanh, tránh cảnh báo OOM ảo trên dashboard Prometheus.

<Concepts title="Giải thích nhanh mấy thuật ngữ ở trên">

- **`GOGC`**: tỷ lệ phần trăm Heap mới được phép cấp thêm trước khi kích hoạt chu kỳ GC kế tiếp (`100` nghĩa là chờ rác cộng thêm đúng bằng kích thước Heap đang sống).
- **`GOMEMLIMIT`**: ngưỡng tổng bộ nhớ mềm (Go 1.19+) bao gồm Heap, Stack và Metadata; khi tiệm cận trần này, GC chạy thường xuyên hơn nhưng được hãm trần tối đa 50% CPU.
- **GC Thrashing (Quay cuồng đốt CPU)**: hiện tượng dữ liệu sống thật chiếm tới ~95% `GOMEMLIMIT`, khiến các chu kỳ GC nổ liên hoàn suốt cả giây mà chẳng giải phóng được bao nhiêu RAM.
