### The 41 font sizes in one stylesheet
In traditional letterpress printing, typography had physical boundaries. If you needed a headline, you pulled metal sorts from a specific drawer: 14pt, 18pt, 24pt, 36pt. You could not ask the foundry for a `16.5pt` slug just because your layout felt slightly cramped. You set your type into a composing stick of fixed width, and you added strips of lead (*leading*) between lines to adjust vertical spacing.

Web development dissolved those physical constraints. CSS gave us an infinite slider: any real number followed by `px`, `em`, or `rem`. Then AI coding tools arrived. When you ask an LLM to "make this label slightly smaller" or "fit this title on one line", it happily generates `text-[13.5px]`, `text-[17px]`, or `leading-[1.38]`. It solves a hyper-local layout squeeze by inventing a brand-new font size.

To see what happens when nobody enforces a typographic scale, we ran an audit on this very site's stylesheet (`src/styles/style.css`):

```python
# type_audit.py
import re, sys

with open(sys.argv[1]) as f:
    css = f.read()

sizes = re.findall(r"font-size:\s*([0-9.]+)(px|em|rem)", css)
px = [float(s[0]) if s[1] == "px" else round(float(s[0]) * 16, 2) for s in sizes]
distinct = sorted(set(px))

off = [v for v in px if v not in scale]

print(f"distinct px values: {len(distinct)}")
print("values:", " ".join(f"{v:g}" for v in distinct))
print(f"off the 9-step scale: {len(set(off))} values, {len(off)} uses")
```

## A scale, not a slider

The foundation of readable UI typography is limiting your choices. If you allow yourself to choose any integer between 12 and 24, you will end up using all twelve of them. The differences between 14px, 15px, and 16px are too subtle to establish meaningful visual hierarchy, yet distinct enough to make your interface look untidy.

### The modular scale trap
Design articles often recommend "modular scales" based on mathematical ratios (such as the Golden Ratio 1.618, or the Major Third 1.25). You start with a base size (16px) and multiply:

```text
16px × 1.25 = 20px → 20px × 1.25 = 25px → 25px × 1.25 = 31.25px → 39.06px
```

Modular scales work well for long-form print essays, but they fail in modern application UIs for two reasons:
1. **Fractional pixel sizes**: Multiplying ratios generates awkward sub-pixel computed values (`19.53px`, `31.25px`) that blur rendering on standard screens.
2. **Missing UI increments**: In application headers, cards, and tables, you frequently need subtle distinctions near the base font (such as 12px for badges, 14px for secondary labels, 16px for body, and 18px for card titles). A $1.25$ ratio jumps from 16px straight to 20px, skipping the most useful sizes.

<ModularVsHandScale />

### The hand-crafted UI scale
Instead of a mathematical formula, use a hand-crafted scale tailored for digital screens:

| Step | Size | Typical Role | Tailwind Equivalent |
| :--- | :--- | :--- | :--- |
| **xs** | 12px | Badges, tags, breadcrumb hints | `text-xs` |
| **sm** | 14px | Form inputs, table cells, secondary copy | `text-sm` |
| **base** | 16px | Primary body text, default reading | `text-base` |
| **lg** | 18px | Large body text, card headers | `text-lg` |
| **xl** | 20px | Small section titles, modal headers | `text-xl` |
| **2xl** | 24px | Section headers, page subheadings | `text-2xl` |
| **3xl** | 30px | Page titles, primary dashboard metrics | `text-3xl` |
| **4xl** | 36px | Major landing headers, marketing titles | `text-4xl` |
| **5xl** | 48px | Hero display numbers, splash banners | `text-5xl` |

Nine steps sound restrictive until you build a screen with them. The dashboard below uses seven, and nothing on it asks for a size in between:

<ScaleScreen />

Always write this scale in `px` or `rem`, never nested `em`. When you nest `0.875em` inside an element already styled with `1.25em`, the computed result is `1.25 × 0.875 × 16px = 17.5px` &mdash; an off-scale fractional size that re-introduces drift.

## Cap line length at 45–75 characters

The most common bug in AI-generated responsive layouts is full-width body text. When a developer prompts an AI agent for a dashboard card or an article section, the model writes:

```html
<div class="w-full">
  <p class="text-slate-600">
    Long continuous explanation rendered edge-to-edge across a 1440px viewport...
  </p>
</div>
```

On a desktop display, this paragraph stretches across 1,200 pixels &mdash; containing 160 or more characters on a single line.

### The mechanics of eye tracking (Saccades)
When humans read, our eyes do not glide smoothly across text. They move in rapid, jerky jumps called **saccades**, pausing momentarily (**fixations**) to ingest words.

When a line contains more than 80 characters, your visual system encounters a severe physical problem: **the sweep return**. After reaching the far right margin, your eyes must jump all the way back to the left edge. Over long distances, the eye's peripheral vision struggles to calculate the exact vertical drop, causing the reader to land on the wrong line (either re-reading the same line or skipping one entirely).

Conversely, if a line has fewer than 40 characters, the eye must reverse direction every two or three words, breaking reading cadence like a ping-pong match.

### The CSS solution: `ch` units and `max-w-prose`
Never leave paragraph containers unconstrained. Use CSS `ch` units (which measure the width of the glyph `0` in the current font):

```css
/* Lock paragraph width to the optimal reading range */
.prose-body {
  max-width: 65ch; /* ~65 characters per line */
}
```

In Tailwind CSS, applying `max-w-prose` applies `max-width: 65ch;` directly. Even if the parent grid or card spans 1,200px, your text column remains readable.

## Proportional line-height

In CSS, `line-height` is frequently treated as a single global variable (like `line-height: 1.5;` set on the body). Applying a uniform multiplier across every heading and body element breaks visual grouping.

Line-height must follow two inverse laws:
1. **As font size increases, line-height must decrease.**
2. **As column width increases, line-height must increase.**

<ProportionalLeading />

### Why large headlines require tight leading
Small body text (14–16px) requires ample line-height (`1.5` to `1.7`) so the reader's eye can distinguish vertical space between lines from the horizontal space between words.

However, when you apply `leading-normal` (1.5) or `leading-loose` (1.75) to a 32px or 40px headline, the vertical gap between lines swells to 20–30 pixels. Under Gestalt psychology's **Law of Proximity**, elements that are far apart are perceived as separate objects. A loose headline stops reading as a unified title and breaks apart into isolated lines.

For large headlines (24px and above):
* Use tight line-height: `1.1` to `1.25` (`leading-tight` in Tailwind).
* The lines stay compact and read as a single visual unit.

### Why wide columns require taller leading
If you have a wider paragraph (65–75 characters), the eye must travel further on the sweep return. Increasing line-height from `1.5` to `1.65` widens the white space between lines, creating a clear horizontal runway that prevents the eye from accidentally grabbing the adjacent row.

| Text Context | Font Size | Line Length | Recommended `line-height` |
| :--- | :--- | :--- | :--- |
| **Display Headline** | 36px–48px | Short (1–2 lines) | `1.1` &ndash; `1.15` |
| **Section Heading** | 24px–30px | Medium | `1.2` &ndash; `1.25` |
| **Dense UI / Table** | 13px–14px | Short snippets | `1.3` &ndash; `1.4` |
| **Body Paragraph** | 16px | Standard (~65ch) | `1.55` &ndash; `1.65` |

## Align by baseline, not center

When developers combine two different font sizes on one horizontal row &mdash; such as an invoice title (26px) paired with a status badge or a date (13px) &mdash; the default flexbox habit is:

```html
<div class="flex items-center gap-3">
  <h2 class="text-2xl font-bold">Invoice #1042</h2>
  <span class="text-xs text-slate-500">Paid on Oct 14</span>
</div>
```

`align-items: center` aligns the geometric centers of the two bounding boxes.

<BaselineVsCenter />

Because the 26px heading has substantial cap-height and ascenders, its center of mass sits much higher than that of the 13px text. As a result, the secondary text looks like it is floating in mid-air, detached from the heading.

### The fix: `align-items: baseline`
In typography, the **baseline** is the invisible datum line upon which all letterforms sit (excluding descenders like the tail of `p`, `y`, or `g`).

When you switch to `items-baseline`:
```html
<div class="flex items-baseline gap-3">
  <h2 class="text-2xl font-bold">Invoice #1042</h2>
  <span class="text-xs text-slate-500">Paid on Oct 14</span>
</div>
```
The browser aligns the font baselines directly. Even though one text is twice as large as the other, they share the exact same floor. The human brain perceives them as belonging to a single continuous line of thought.

*(Note: If the smaller element is a rounded pill badge with a solid background, vertical centering is correct because the badge boundary forms a standalone geometric container. For pure text and dates, always use baseline.)*

## Lock numbers with tabular figures

Financial dashboards, crypto trackers, and order books share one universal requirement: users need to scan down columns of numbers to compare values.

By default, modern typefaces use **proportional numerals**. Digits have varying horizontal widths:
* A digit `1` or `.` is slender (e.g., 6px wide).
* A digit `8` or `0` is wide (e.g., 11px wide).

If you stack `$11,111.11` directly above `$88,888.88`, the second number is noticeably wider despite having the exact same number of digits. In a table, this causes the decimal points to drift and wobble horizontally.

<TabularNumsComparison />

### The OpenType solution: `tabular-nums`
In the past, developers wrapped numbers in `font-family: monospace` to force uniform alignment. While effective, it forced interfaces to look like terminal emulators.

Modern web typography provides a native OpenType feature: `font-variant-numeric: tabular-nums;` (mapped to the `tnum` feature tag). When enabled, the browser renders every digit (0–9) at the exact same fixed advance width while retaining the primary UI typeface.

Combine two rules for any numeric column:
1. **Right-align the cell**: `text-align: right;` ensures units line up with units, tens with tens, and hundreds with hundreds.
2. **Apply tabular figures**: `font-variant-numeric: tabular-nums;` (or the `tabular-nums` class in Tailwind).

```css
/* Bulletproof financial numbers */
.num-cell {
  text-align: right;
  font-variant-numeric: tabular-nums;
}
```

Now, every decimal point forms a straight vertical laser line. Users can scan portfolio balances, inventory quantities, and latency metrics in milliseconds without reading fatigue.

## Letter-spacing: tighten headlines, widen all-caps

Letter-spacing (*tracking*) is the overall spacing applied across a block of text. For standard 15px body copy, the typeface designer has already tuned letter-spacing for optimal reading. Adjusting it usually harms legibility.

There are two critical exceptions where intervention is mandatory:

<LetterSpacingRules />

### 1. Tighten large headlines (`-0.025em`)
Most popular UI fonts (Inter, Roboto, Arial, System UI) were designed primarily for small screen text (14–16px). At small sizes, letters require built-in generous spacing so adjacent shapes do not bleed into each other on low-resolution displays.

When you scale that body font up to a 32px or 40px headline, that built-in spacing scales up proportionally. The letters end up looking unnaturally spread out and loose.

Applying `letter-spacing: -0.025em` (Tailwind's `tracking-tight`) pulls the glyphs closer together, giving large headings a sharp, punchy, editorial weight.

### 2. Widen all-caps tags and badges (`+0.08em`)
Lowercase text is effortless to read because the mixture of ascenders (`h`, `d`, `k`, `b`) and descenders (`g`, `y`, `p`, `q`) creates distinct silhouette outlines for every word.

All-caps text (like `STATUS: ACTIVE` or table headers) loses those silhouettes. Every word becomes a uniform rectangular brick. Because all uppercase letters share the same height, they crowd one another.

Adding `letter-spacing: 0.08em` to `0.1em` (Tailwind's `tracking-wider`) gives uppercase letters breathing room, allowing the reader's eye to isolate each glyph immediately.

## Keep AI-written type on the scale

The 41 sizes at the top of this post were not typed by careless humans alone. Of the 22 commits that touched `src/styles/style.css` up to commit 9528380, 17 carry a Claude co-author line. Each size was a sensible answer to one request: make this label a bit smaller, make that title fit. A model sees the line it is editing, not your scale, so it reaches for the slider.

Every rule in this post fails the same way with an AI, and has the same fix: name the rule in the prompt, then check what comes back.

<AiTypeBeforeAfter />

**1. Put the scale and the rules in the project instructions.** Paste them into the file your assistant reads on every task (`CLAUDE.md`, `AGENTS.md`, Cursor rules), so they apply to every edit and not only to one chat:

```text
Font sizes: use only text-xs, text-sm, text-base, text-lg, text-xl,
text-2xl, text-3xl, text-4xl, text-5xl. Never write text-[..px],
leading-[..] or a new font-size value; if no step fits, ask me.
Body paragraphs get max-w-prose. Headings 24px and up get
leading-tight and tracking-tight. A title next to a date or label
uses items-baseline. Numeric table columns get text-right tabular-nums.
After editing, list every font-size and line-height you added.
```

The last line matters most. A new value you have to read in the model's own summary is much harder to miss than one buried in a diff.

**2. Check, do not trust.** If you use Tailwind, arbitrary values are easy to find:

```bash
# every arbitrary Tailwind size or line-height in the source
grep -rnE 'text-\[[0-9.]+(px|rem)\]|leading-\[' src/
```

For plain CSS, run the `type_audit.py` script from the top of this post in CI and give it a budget: end it with `sys.exit(1 if len(off) > 118 else 0)`, where 118 is today's count of off-scale uses. The build then fails whenever someone, human or model, adds one more, and you lower the number as you clean up.

## Key takeaways

1. **Pick a discrete 9-step scale in pixels or rems**: Never use continuous sliders or arbitrary AI sizes like `text-[13.5px]`. Eliminate fractional pixel values from your stylesheets.
2. **Cap paragraph width at 45–75 characters**: Stop allowing text to span 100% of large desktop viewports. Enforce `max-width: 65ch` (`max-w-prose`) to protect readers from eye tracking fatigue.
3. **Invert line-height as text grows**: Large display titles need tight leading (`1.1` to `1.25`) to stay grouped; body copy needs breathing room (`1.5` to `1.65`).
4. **Align mixed font sizes by baseline**: Replace default `items-center` with `items-baseline` when pairing large headings with metadata or timestamps.
5. **Enforce `tabular-nums` and right alignment on data tables**: Lock decimal points into vertical alignment to make numerical comparison instantaneous.
6. **Tighten headlines, loosen all-caps**: Subtract tracking (`-0.025em`) on large titles set in body fonts; add tracking (`+0.08em`) on uppercase tags and labels.
7. **Give the AI the scale, then check its output**: State the steps and rules in the project instructions, ask the model to list new values, and fail CI when off-scale sizes grow.

Trong thời kỳ in ấn truyền thống, typography bị giới hạn bởi các vật thể vật lý. Khi cần một tiêu đề, người thợ in phải mở đúng ngăn kéo để lấy con chữ chì: 14pt, 18pt, 24pt, 36pt. Không ai có thể đòi xưởng đúc một con chữ `16.5pt` chỉ vì bố cục hôm đó bị chật một chút. Sự xuất hiện của công nghệ web đã xóa bỏ các rào cản vật lý đó. CSS trao cho lập trình viên một thanh trượt vô hạn: bất kỳ con số nào đi kèm đuôi `px`, `em`, hay `rem` đều hiển thị được. Rồi các công cụ sinh code bằng AI xuất hiện. Khi bạn yêu cầu AI "cho chữ này nhỏ đi một chút" hoặc "chỉnh tiêu đề này nằm gọn trong một hàng", mô hình ngôn ngữ lớn rất vui vẻ tạo ra `text-[13.5px]`, `text-[17px]`, hay `leading-[1.38]`. Nó giải quyết bài toán chật chội cục bộ bằng cách đẻ ra một cỡ chữ hoàn toàn mới.

Để thấy rõ điều gì sẽ xảy ra khi không ai kiểm soát thang đo typography, chúng mình đã quét thử chính file stylesheet của blog này (`src/styles/style.css`):

```python
print("values:", " ".join(f"{v:g}" for v in distinct))
print(f"off the 9-step scale: {len(set(off))} values, {len(off)} uses")
```

## Thang đo, không phải thanh trượt

Nền tảng của một giao diện gọn gàng là tự giới hạn lựa chọn của chính mình. Nếu bạn cho phép mình chọn bất kỳ kích thước nào giữa 12 và 24, cuối cùng bạn sẽ dùng sạch cả 12 kích cỡ đó. Sự chênh lệch giữa 14px, 15px và 16px quá nhỏ để tạo ra phân cấp thị giác rõ ràng, nhưng lại vừa đủ để khiến trang web trông lem nhem, thiếu đồng bộ.

### Cái bẫy của thang tỷ lệ toán học (Modular Scale)
Nhiều tài liệu thiết kế khuyên dùng "thang tỷ lệ mô-đun" dựa trên các tỷ lệ toán học (như Tỷ lệ Vàng 1.618 hay Tỷ lệ Quãng ba 1.25). Bạn bắt đầu từ cỡ chuẩn (16px) rồi nhân lên:

```text
16px × 1.25 = 20px → 20px × 1.25 = 25px → 25px × 1.25 = 31.25px → 39.06px
```

Thang tỷ lệ toán học rất đẹp trong sách in hoặc bài xã luận báo chí, nhưng lại thất bại thảm hại trong giao diện phần mềm vì hai lý do:
1. **Sinh ra số lẻ thập phân**: Phép nhân tỷ lệ tạo ra các giá trị lẻ như `19.53px`, `31.25px`, làm màn hình máy tính phải khử răng cưa mờ nhạt.
2. **Thiếu các bậc cần thiết cho UI**: Trong bảng dữ liệu, form nhập hay thẻ component, bạn rất cần các nấc tinh tế gần cỡ chuẩn (như 12px cho nhãn badge, 14px cho mô tả phụ, 16px cho thân bài, 18px cho tiêu đề thẻ). Tỷ lệ $1.25$ nhảy vọt từ 16px lên thẳng 20px, bỏ qua mất những nấc quan trọng nhất.

## Giới hạn dòng ở 45–75 ký tự

Lỗi phổ biến nhất trong các giao diện responsive do AI dựng là để văn bản dàn ngang toàn màn hình. Khi bạn bảo AI dựng một thẻ thông tin hay mục bài viết, mô hình thường sinh ra:

```html
<div class="w-full">
  <p class="text-slate-600">
    Đoạn văn bản giải thích trải dài từ mép trái sang mép phải trên màn hình 1440px...
  </p>
</div>
```

Trên màn hình máy tính để bàn, đoạn văn này trải rộng tới 1.200 pixel &mdash; chứa từ 150 đến 180 ký tự trên đúng một dòng duy nhất.

### Cơ chế chuyển động mắt khi đọc (Saccade)
Mắt người không lướt đi êm ả như một dải lụa khi đọc. Mắt chúng ta di chuyển bằng các bước nhảy ngắn và giật cục gọi là **saccade**, dừng lại tích tắc ở các điểm cố định (**fixation**) để thu nhận từ ngữ.

Khi một dòng chữ dài quá 80 ký tự, mắt gặp phải một trở ngại vật lý cực kỳ mệt mỏi: **hành trình đảo dòng (sweep return)**. Sau khi đọc tới tận cùng mép phải, mắt phải thực hiện một cú nhảy thật xa quay về lại mép trái. Trên một khoảng cách dài như vậy, tầm nhìn ngoại vi rất khó ước lượng chính xác độ rơi của trục dọc, khiến người đọc dễ bị "nhảy cóc" dòng &mdash; hoặc đọc nhầm lại chính dòng vừa xong, hoặc bỏ sót mất một dòng tiếp theo.

Ngược lại, nếu dòng ngắn hơn 40 ký tự, mắt phải đảo chiều liên tục sau mỗi 2–3 từ, khiến nhịp đọc bị ngắt quãng giật cục như xem một trận bóng bàn.

## Dãn dòng tỷ lệ nghịch với cỡ chữ

Trong CSS, nhiều lập trình viên có thói quen đặt một giá trị `line-height` toàn cục cho cả trang web (như `line-height: 1.5;` trên thẻ `body`). Việc áp dụng một hệ số dãn dòng duy nhất cho mọi thành phần từ tiêu đề lớn tới chữ thân bài là một lỗi thiết kế nghiêm trọng.

Khoảng cách dãn dòng phải tuân theo hai quy tắc tỷ lệ nghịch:
1. **Cỡ chữ càng to, line-height càng phải nhỏ lại.**
2. **Dòng chữ càng dài, line-height càng phải tăng lên.**

<ProportionalLeading />

### Tại sao tiêu đề to cần line-height hẹp?
Đoạn văn chữ nhỏ (14–16px) cần khoảng cách dòng rộng rãi (`1.5` đến `1.7`) để mắt người phân biệt được khoảng trắng giữa hai dòng chữ so với khoảng cách giữa hai từ kế bên.

Thế nhưng, nếu bạn áp dụng hệ số `1.5` hoặc `1.75` cho một tiêu đề to 32px hay 40px, khoảng trống giữa hai hàng tiêu đề sẽ phình to ra tới 20–30 pixel. Theo **Định luật Gần gũi (Law of Proximity)** trong tâm lý học Gestalt, những vật thể nằm xa nhau sẽ bị não bộ hiểu là những thực thể tách biệt. Một tiêu đề bị dãn dòng quá rộng sẽ vỡ vụn thành các dòng đơn lẻ, mất đi tính liên kết của một câu hoàn chỉnh.

Đối với tiêu đề lớn (24px trở lên):
* Dùng line-height hẹp: từ `1.1` đến `1.25` (tương đương `leading-tight` trong Tailwind).
* Các dòng chữ sẽ gắn kết chặt chẽ, tạo thành một khối thông tin thống nhất.

### Tại sao dòng dài cần dãn dòng rộng hơn?
Khi độ dài dòng chạm mốc 65–75 ký tự, mắt người phải di chuyển một quãng đường dài hơn trong cú đảo dòng. Tăng nhẹ line-height từ `1.5` lên `1.65` sẽ tạo ra một khoảng đệm an toàn, giống như một đường băng rõ ràng giúp mắt hạ cánh chính xác vào đầu dòng tiếp theo mà không bị dính vào dòng trên.

| Thành phần văn bản | Cỡ chữ | Độ dài dòng | Hệ số `line-height` khuyến nghị |
| :--- | :--- | :--- | :--- |
| **Tiêu đề lớn (Display)** | 36px–48px | Ngắn (1–2 dòng) | `1.1` &ndash; `1.15` |
| **Đầu mục (Heading)** | 24px–30px | Vừa phải | `1.2` &ndash; `1.25` |
| **Giao diện bảng biểu** | 13px–14px | Cụm từ ngắn | `1.3` &ndash; `1.4` |
| **Đoạn văn đọc chính** | 16px | Chuẩn (~65ch) | `1.55` &ndash; `1.65` |

## Căn theo đường chân chữ, đừng căn giữa

Khi bạn muốn xếp hai đoạn chữ có kích cỡ khác nhau trên cùng một hàng ngang &mdash; ví dụ mã hóa đơn to (26px) đứng cạnh ngày thanh toán nhỏ (13px) &mdash; thói quen phản xạ của phần lớn lập trình viên dùng Flexbox là:

```html
<div class="flex items-center gap-3">
  <h2 class="text-2xl font-bold">Hóa đơn #1042</h2>
  <span class="text-xs text-slate-500">Đã thanh toán 14/10</span>
</div>
```

Lệnh `align-items: center` sẽ căn chỉnh trọng tâm hình học của hai chiếc hộp chữ với nhau.

<BaselineVsCenter />

Bởi vì chữ tiêu đề 26px có chiều cao thân chữ (cap-height) rất lớn, tâm của nó nằm ở tít trên cao. Kết quả là dòng chữ nhỏ 13px trông như đang bị treo lơ lửng giữa trời, hoàn toàn trật khỏi nhịp đọc của mắt.

### Cách xử lý đúng: `align-items: baseline`
Trong typography, **baseline (đường chân chữ)** là đường thẳng ngang vô hình nơi mọi chữ cái cùng tựa chân lên (ngoại trừ các phần đuôi thò xuống dưới của các ký tự như `p`, `y`, hay `g`).

Khi bạn chuyển sang dùng `items-baseline`:
```html
<div class="flex items-baseline gap-3">
  <h2 class="text-2xl font-bold">Hóa đơn #1042</h2>
  <span class="text-xs text-slate-500">Đã thanh toán 14/10</span>
</div>
```
Trình duyệt sẽ khóa các đường chân chữ nằm thẳng tắp trên cùng một cao độ. Dù một chữ to gấp đôi chữ kia, chúng vẫn cùng đứng trên một mặt sàn. Não bộ của chúng ta sẽ lập tức nhận diện chúng như một câu hoàn chỉnh, tự nhiên và vững chãi.

*(Lưu ý: Nếu thành phần nhỏ là một huy hiệu dạng viên thuốc bo tròn có màu nền đặc, căn giữa hình học là chuẩn xác vì viền huy hiệu tạo thành một khối độc lập. Nhưng với chữ thuần túy, luôn ưu tiên căn theo baseline).*

## Khóa số liệu với tabular-nums

Các ứng dụng tài chính, bảng theo dõi tiền điện tử và danh sách lệnh giao dịch đều có chung một bài toán: người dùng cần quét mắt dọc theo các cột số để so sánh độ lớn.

Theo mặc định, các bộ font hiện đại sử dụng **chữ số tỷ lệ (proportional numerals)**. Các con số có chiều rộng hoàn toàn khác nhau:
* Con số `1` hay dấu chấm `.` rất thanh mảnh (chỉ rộng khoảng 6px).
* Con số `8` hay `0` lại rất bè (rộng tới 11px).

Nếu bạn đặt dòng `$11,111.11` nằm ngay trên dòng `$88,888.88`, dòng thứ hai trông dài hơn hẳn dòng thứ nhất dù chúng có cùng số lượng chữ số. Trong một bảng tính, điều này làm dấu phẩy thập phân bị thụt thò, nhảy múa theo chiều ngang.

<TabularNumsComparison />

### Giải pháp OpenType chuẩn mực: `tabular-nums`
Trước đây, các lập trình viên thường phải ép kiểu `font-family: monospace` để ép các con số thẳng hàng. Cách này hiệu quả nhưng biến giao diện thành một màn hình terminal thô kệch.

Typography trên web hiện nay có sẵn tính năng OpenType gốc: `font-variant-numeric: tabular-nums;` (kích hoạt cờ `tnum`). Khi bật tính năng này, trình duyệt sẽ vẽ mọi con số từ 0 đến 9 ở cùng một chiều rộng cố định y hệt nhau, trong khi vẫn giữ nguyên phông chữ đẹp đẽ của hệ thống.

Luôn ghi nhớ hai nguyên tắc bất di bất dịch cho mọi cột số:
1. **Căn lề bên phải**: `text-align: right;` giúp hàng đơn vị thẳng hàng đơn vị, hàng chục thẳng hàng chục, hàng trăm thẳng hàng trăm.
2. **Kích hoạt chữ số dạng bảng**: `font-variant-numeric: tabular-nums;` (hoặc dùng lớp `tabular-nums` trong Tailwind).

```css
/* Chuẩn mực cho hiển thị số liệu tài chính */
.num-cell {
  text-align: right;
  font-variant-numeric: tabular-nums;
}
```

Giờ đây, các dấu phẩy thập phân sẽ xếp thành một đường thẳng đứng như kẻ chỉ. Người dùng có thể lướt qua hàng chục dòng số dư ví, khối lượng giao dịch hay độ trễ p99 chỉ trong vài phần trăm giây mà không bị mỏi mắt.

## Khoảng cách chữ: siết tiêu đề, nới all-caps

Khoảng cách chữ (*letter-spacing* hay *tracking*) là khoảng giãn đều áp dụng cho toàn bộ khối văn bản. Với văn bản thân bài cỡ 15px thông thường, các nhà thiết kế phông chữ đã căn chỉnh khoảng cách này hoàn hảo cho mắt đọc. Tự ý thay đổi nó thường chỉ làm chữ xấu đi.

Tuy nhiên, có hai trường hợp ngoại lệ bắt buộc bạn phải can thiệp:

<LetterSpacingRules />

### 1. Siết tiêu đề lớn (`-0.025em`)
Hầu hết các bộ font UI phổ biến (Inter, Roboto, Arial, System UI) được thiết kế tối ưu cho chữ nhỏ hiển thị trên màn hình (14–16px). Ở cỡ nhỏ, các con chữ cần khoảng cách thoáng đãng để không bị dính vào nhau trên các màn hình có mật độ điểm ảnh thấp.

Thế nhưng khi bạn phóng to bộ font đó lên cỡ tiêu đề 32px hay 40px, khoảng hở tích hợp sẵn đó cũng bị phóng to theo. Kết quả là các con chữ trông bị rời rạc, lỏng lẻo.

Bổ sung `letter-spacing: -0.025em` (lớp `tracking-tight` trong Tailwind) sẽ kéo các ký tự lại gần nhau hơn một chút, giúp tiêu đề to trở nên sắc sảo, đanh thép và có trọng lượng thị giác hơn.

### 2. Nới rộng chữ hoa toàn bộ (`+0.08em`)
Chữ viết thường rất dễ đọc vì sự đan xen giữa các nét nhô lên (`h`, `d`, `k`, `b`) và các nét thò xuống (`g`, `y`, `p`, `q`) tạo ra một hình khối đường bao (silhouette) rất đặc trưng cho từng từ.

Chữ in hoa toàn bộ (như `TRẠNG THÁI: HOẠT ĐỘNG` hay đầu mục bảng) làm mất sạch các đường bao này. Mọi từ ngữ đều biến thành những khối chữ nhật vuông vức như viên gạch. Vì chiều cao bằng chằn chặn, các chữ cái sẽ chen chúc lấn át lẫn nhau.

Thêm `letter-spacing: 0.08em` đến `0.1em` (lớp `tracking-wider` trong Tailwind) sẽ mở ra khoảng thở cần thiết, giúp mắt người nhận diện rõ từng mặt chữ ngay lập tức.

## Điểm rút ra (Key takeaways)

1. **Khóa thang chữ 9 bậc bằng pixel hoặc rem**: Tuyệt đối không dùng thanh trượt vô cấp hoặc để AI tự ý sinh ra các cỡ chữ tùy tiện như `text-[13.5px]`. Quét sạch các cỡ chữ nửa pixel ra khỏi stylesheet của bạn.
2. **Khống chế độ rộng dòng ở 45–75 ký tự**: Đừng bao giờ thả nổi đoạn văn bản trải dài 100% màn hình máy tính. Luôn áp dụng `max-width: 65ch` (`max-w-prose`) để mắt người đọc không bị mỏi khi đảo dòng.
3. **Dãn dòng tỷ lệ nghịch với cỡ chữ**: Tiêu đề to cần line-height hẹp (`1.1` đến `1.25`) để giữ chặt khối thông tin; văn bản thân bài cần khoảng thở thông thoáng (`1.5` đến `1.65`).
4. **Căn các cỡ chữ lệch nhau theo baseline**: Thay thế thói quen dùng `items-center` bằng `items-baseline` khi đặt tiêu đề lớn đứng cạnh các nhãn phụ hoặc mốc thời gian.
5. **Bắt buộc dùng `tabular-nums` và căn phải cho bảng số liệu**: Cố định trục dọc của các dấu phẩy thập phân để người dùng nhận biết ngay độ lớn số liệu mà không cần tính nhẩm.
6. **Siết tiêu đề lớn, nới rộng chữ hoa toàn bộ**: Áp dụng tracking âm (`-0.025em`) cho tiêu đề lớn dùng font văn bản; bù đắp tracking dương (`+0.08em`) cho các nhãn huy hiệu in hoa toàn bộ.
7. **Đưa thang chữ cho AI, rồi kiểm tra kết quả**: Ghi các bậc và quy tắc vào chỉ dẫn dự án, yêu cầu mô hình liệt kê giá trị mới, và cho CI báo lỗi khi số cỡ lạc thang tăng.
